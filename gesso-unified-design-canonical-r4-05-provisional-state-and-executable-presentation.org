* Part V — Provisional state and executable presentation
:PROPERTIES:
:CUSTOM_ID: part-05-provisional-state-and-executable-presentation
:PART_REVISION: 05-20261107
:END:

This part defines provisional presentation, local continuity, prepared view
bindings, portable execution, and the separation of executable plans from
diagnostic evidence. It uses Part IV's command outcomes, scoped observations,
and acquisition/installation distinctions. Part VI specifies browser
coordination and physical realization; Part VII closes the assembled application
path before a managed affordance is served.

The intended architecture supports the full application language through the
[[#req-full-language-construction][checked construction contract]]. Declarative
interfaces and a portable coordination vocabulary make behavior inspectable;
they do not require every computation or renderer to be expressed in a small
proof language. Opaque functions retain explicit contracts and premises wherever
their behavior has not been mechanically established.

Examples use illustrative declaration and API names. They specify intended
semantics, not a promise that the displayed syntax already exists. Inspection
maps and tables describe admitted values; copying their fields does not create
authority, provenance, resource ownership, or execution rights. Generated
fragments explain one canonical construction, rather than additional plans
application authors must maintain independently.

** Optimism
:PROPERTIES:
:CUSTOM_ID: req-optimistic-projection
:END:

Optimism is an explicit provisional trajectory associated with a semantic
command. It permits responsive local presentation while authority determines
the command's result. It does not predict a future database state with certainty
and does not grant permission to make that prediction authoritative.

A provisional projection means:

#+begin_quote
Given these admitted observations and declared local inputs, this is the
presentation permitted for this command while its authoritative disposition is
unresolved. Its derivation, owner, affected scope, and resolution policy are
known. The authoritative model remains free to produce any result allowed by
the operation contract.
#+end_quote

The runtime distinguishes at least:

| Category | Meaning |
|----------+---------|
| Authoritative observation | An admitted acquisition or operation output establishes specified facts within its scope and evidence contract. |
| Provisional projection | A declared local derivation associated with a command; it is not evidence of incorporation. |
| Authoritative absence | A successful admitted observation establishes absence within its complete authorized scope. |
| Unknown or unavailable | Required evidence has not been established or cannot currently be acquired/disclosed. |
| Local draft | User input or interaction state which has not become an authoritative assertion. |

A visually identical card can belong to different categories. The runtime
retains the distinction even when rendering produces similar Hiccup or DOM.
Representations may be ordinary immutable values or opaque wrappers; the
requirement is correct admission and use, not one mandatory host-language type.

The evidence category, command disposition, and installation/adoption progress
are *independent dimensions*. A permitted provisional value can be installed
locally while its semantic command remains unresolved; that installation
establishes only the local presentation effect, not incorporation or an
advance in authoritative adopted knowledge. A valid command-specific success
can also be known while the fresh card is unavailable or has not installed.
Even visually identical provisional and authoritative renderings do not
collapse these boundaries. Adoption requires a suitable admitted observation,
the current authorized target and owner, and the applicable completed physical
effect. A successful renderer call, a prior command outcome, or permission to
perform a swap is not substitute evidence of completed installation. Unmet
acquire-and-adopt obligations remain until independently discharged.

*** Provisional derivation contract

Each optimistic operation declares:

1. its semantic command binding and entry conditions;
2. the authoritative observations, local inputs, and explicit assumptions used
   to derive the provisional value;
3. affected entity, query-membership, field, and presentation scopes;
4. the derivation implementation and its input/output types;
5. owners and resource instances permitted to install, update, or remove it;
6. its concurrency and dependency policy relative to other local work;
7. settlement, supersession, timeout, cancellation, retirement, and recovery
   continuations;
8. the evidence and physical completion required before claiming adoption.

An optimistic update normally depends on an admitted authoritative observation.
The contract expresses the actual dependency, rather than demanding an existing
entity snapshot in every operation. Optimistic creation may depend on an
admitted collection scope, policy observation, declared draft inputs, and a
temporary local entity identity. It must not manufacture authoritative
nonexistence or assume a client-chosen ID is available. The server enforces
creation conditions.

Purely local drafts need not be mislabeled optimistic domain operations. If the
application renders under weaker entry knowledge, its declared assumptions
remain visible and the projection cannot imply guarantees requiring absent
observations. Missing required knowledge is an admission failure; an assertion
cannot silently supply that missing binding.

Several observations may justify one projection. Its basis is then a scoped set
of premises, not necessarily one universal database token. The derivation cannot
strengthen acquired coverage or turn mixed observations into a common snapshot.
Part IV's progression and scope contracts apply. A permitted draft may display
its author's local inputs, but those inputs do not establish authoritative
facts, protected relationships, global collection membership, or another
principal's disclosure rights. The derivation must respect the admitted
visibility and source scope of each protected observation it actually uses.

*** Presentation state is not a new domain status

An optimistic Claim can display a pending helper and a Claiming label while the
last admitted Request still has domain status =:open= and no helper. A pending
presentation tag must not be inserted into a closed domain enum unless the
model defines that state.

An inspection view might be:

#+begin_src clojure
{:projection/type :request/card
 :projection/status :provisional
 :gesso/command-id C42
 :execution/id E42
 :resource-instance/id card-owner-instance
 :premises {:observation-ref card-observation-ref}
 :subject {:request-id R}
 :presentation
 {:phase :claim/pending
  :display-helper-id Alice
  :label "Claiming..."
  :busy? true}}
#+end_src

The schematic =:display-helper-id= is a view-level cue, not HumanHelp's
persisted primary =RequestAssignment= relationship. Neither it nor the pending
label may be used as the current-model eligibility guard or submitted as an
already-established assignment. Part IV's authoritative operation protects
the real relationship and its current eligibility conditions.

This does not assert =:request/status :claiming= as authoritative domain data.
The private representation may be smaller, but the categories remain
recoverable. A renderer consumes admitted presentation state; it does not
establish provenance by writing =:projection/status=.

The admitted command boundary supplies or admits C42 before the first possible
send. Allocation happens once for the intent and is retained through retry.
E42 names one local execution; =card-owner-instance= names one presentation
resource. Neither substitutes for the command ID.

*** Provisional entry and presentation evidence cases

The following pairs exercise the boundary between an admitted local
presentation and independently established authoritative effects. They
specify finished-system acceptance, not a particular browser helper API.

| Eligible positive case | Adversarial or incomplete case | Required classification |
|------------------------+--------------------------------+-------------------------|
| Alice has a trusted, scoped Request R observation at X17 and binds C42 before installing a pending Claim view. | A browser supplies an identical-looking unadmitted card or copies a `:projection/status` field, but the required observation or current actor binding is absent. | The positive view is provisional under its owner; the forged or missing entry evidence cannot qualify the required optimistic construction or authorize Claim. |
| A creator previews a new Request from admitted collection/policy context, explicit draft inputs and a temporary local identity. | The preview asserts that its chosen final entity ID is unique or that the record already belongs to the authoritative board cohort. | Permit the correctly scoped local preview, but neither entity existence/absence nor collection membership is established; the server protects creation and subsequent observations. |
| C42's success is admitted while no canonical Request card has completed installation. | A settlement callback or successful provisional render relabels the still-tentative DOM as authoritative or clears unrelated Refresh debt. | Retain established command knowledge separately; keep the displayed representation provisional or otherwise explicitly unadopted until qualified installation; preserve outstanding adoption obligations. |

A positive witness must not be made to pass by constructing a fabricated
admission map. Its intended source and owner bindings are inputs to the
admitted mechanism, while the adversarial variant changes exactly the
relevant premise. The physical test must observe actual installation or
its absence; a copied inspection envelope is not that evidence.

*** Optimism cannot confer authority

An adversarial browser can fabricate provisional values, labels, bindings, and
purported machine state. The trusted model boundary independently establishes
principal identity, command binding, and current authorization. It never
accepts an optimistic assignment or browser authorized flag as permission.

This remains true for a legitimate binding rendered by the server earlier.
Membership or policy may have changed. Historical issuance or observation
evidence is not current authorization; an observed-basis claim is not proof the
caller acquired or adopted the observation. Trusted authentication and
transaction-current business guards protect *new incorporation*. Resolving a
previously incorporated command is a different operation: its immutable
command binding, current authorization to seek resolution, and permission to
disclose a historical result are checked independently. Revocation of a
current permission cannot rewrite a past incorporation; neither does a
retained result grant perpetual disclosure or new execution authority.

The model chooses legal authoritative outcomes. Choreography and its admitted
presentation contract choose provisional and resolution behavior. Views choose
the visual treatment. These responsibilities must not collapse into a helper
that changes the DOM and independently decides business policy.

*** Separate command knowledge from presentation progress

A participant tracks several questions:

| Dimension | Examples of established state |
|-----------+-------------------------------|
| Command knowledge | Qualified incorporation of the bound command, terminal rejection under the declared exclusion policy, or unresolved/unknown disposition. |
| Physical attempt | Preparation, delivery, aborted/failed attempt, submitted attempt, or qualified invocation-specific result; one attempt does not settle other compatible attempts. |
| Acquired evidence | A particular admitted Request observation is available. |
| Installation progress | Not requested, pending, completed, failed, or indeterminate under its physical-effect contract. |
| Adopted presentation | A scoped observation or provisional projection owns the current visible representation. |
| Recovery ownership | This execution or another admitted owner is responsible for remaining work. |

This does not require a separate mutable store for every row. It requires enough
information to avoid false implications between them. A command can be known
committed while a fresh card is unavailable. An authoritative card can be
installed while attribution to the original command remains unknown.

Recording acquired evidence is not recording completed visual adoption. A
semantic transition may request installation and enter a pending-installation
state. It cannot discharge acquire-and-adopt obligations until the required
physical completion has been admitted, as specified in
[[#req-advisory-discharge][Part IV's adoption contract]]. A terminal
settlement may release the local execution while a provisional DOM remnant
still waits for canonical replacement; release does not relabel the remnant
authoritative or erase independent acquisition/adoption debt.

*** Worked example: HumanHelp Claim

Alice has an admitted Request-card observation for R at basis X17. Its scope
includes the Request, projection/schema version, authority/database incarnation,
temporal interpretation, and permitted visibility context. Its admitted
projection says the Request is open and represents no active primary helper
under the qualified RequestAssignment read/coverage contract. That is not a
promise that a scalar =:request/helper-id= exists in HumanHelp's production
model, or that a pre-read proves absence at incorporation. Preparation offers
a Claim affordance using public model semantics.

This observation supports the example's provisional presentation. It does not
prove Membership, policy, or Request state will still permit Claim when the
server receives it. Part IV's model operation protects those conditions at
incorporation.

Activation binds C42 to the Claim intent and creates E42 with its own resource
instances. The admitted entry path records those identities before issuing any
transport effect. A retry reuses the existing C42 binding rather than allocating
a replacement intent.

The provisional overlay can show Alice as tentative helper and disable the
conflicting Claim affordance. It does not replace the retained authoritative
observation or authorize further domain actions solely from that tentative
assignment.

| Admitted event or evidence | Command knowledge | Presentation continuation |
|----------------------------+-------------------+---------------------------|
| Successful =:committed= result for C42. | Incorporation established. | End or transform the pending overlay; install an admissible result projection if supplied, or acquire the required card. |
| Successful permitted =:already-incorporated= result. | Prior incorporation established. | Use the accepted successor without incorporating again; the historical result snapshot is not automatically current. |
| Authoritative =:rejected= result. | Rejection established under the command policy. | End the pending overlay and obtain or retain a justified presentation through the rejection path. |
| =:commit-unknown= or indeterminate delivery. | Outcome unknown. | Use a truthful unknown/recovery presentation and retain or transfer command-resolution responsibility. |
| Current Request observation without command attribution. | C42 may remain unknown. | Supersede the provisional card after permitted installation, without inventing attribution. |

Model outcomes map explicitly to presentation settlements =:accepted=,
=:rejected=, and =:unknown=. Labels such as confirmed, reconciled, and superseded
may describe how provisional ownership ended. They are not extra model outcomes
or substitutes for incorporation evidence.

**** Accepted command, card still pending

Suppose the server establishes C42's incorporation but fresh card acquisition
fails. The browser can know Claim succeeded while lacking an installable current
card. It must not turn the acquisition failure into rejection or overwrite
established incorporation with unknown.

Presentation can say the action succeeded and current details await refresh.
An old observation remains historical or awaiting refresh. Tentative values do
not become a complete authoritative card merely because the command succeeded.

A result projector may supply an admitted observation with adequate scope and
progression. It then follows the installation contract: record installation
pending, issue a scoped effect, and adopt only after actual completion is
admitted. Focus-restoration failure afterward does not undo that adoption.

**** Rejection with a conflicting current state

Suppose Bob's different command claims R first, and the qualified
command-resolution mechanism also establishes terminal rejection of C42 under
its declared exclusion/fencing policy. A subsequent admitted card may show
Bob as primary helper. These are separate facts with separate evidence:
rejection of C42 and the observed state of R. If all that is known is that
one Alice submission failed its guard, the browser has evidence of that
*attempt*, not automatically a terminal command rejection; another compatible
C42 attempt may still have incorporated.

The rejection reason comes from permitted model evidence, such as already
claimed under this simplified policy. Presentation cannot infer that reason
from the card. A rejected result need not always contain a disclosable card:
authority may permit the outcome but not fresh details, or only a less detailed
message.

One aborted physical attempt is insufficient to establish command rejection;
a competing compatible attempt may have incorporated C42. Part IV's
[[#req-command-participant-uncertainty][command-disposition contract]] determines
which evidence is definitive.

**** Timeout and two recovery tasks

A settlement timer establishes a local deadline event, not command rejection.
Admission checks its resource owner and relevance to the current phase. If
definitive evidence was already recorded, a late timer cannot replace it with
unknown.

For an unresolved command, the runtime may retire E42's provisional ownership
and enter or transfer recovery. Two tasks can remain:

- acquire an authorized current card to recover presentation;
- resolve C42 through permitted command-result evidence to recover attribution.

The first does not automatically complete the second. A read-only resolver also
does not supply an executable recovery driver. The contract names the owner,
triggers, retry policy, evidence source, retention, and behavior when automatic
progress ends.

Retry exhaustion may stop automatic work while leaving the command unknown.
The product can provide manual reconciliation or another declared handoff. It
cannot silently replace C42 with a new command merely to resume a pending UI.
A successor recovery owner receives newly admitted rights for its own
resource instances; inheriting C42's immutable intent does not inherit E42's
retired timeout, DOM, transport, or role-local knowledge. Failure to disclose
a retained historical result may leave C42's participant attribution unknown
even if a separate authorized card read restores current presentation.

**** Authoritative supersession without attribution

Suppose an authorized observation at X19 shows Alice as helper and is permitted
to replace the provisional card. After installation completes, that observation
justifies the display. C42 remains unknown if no command-specific evidence
establishes its disposition; another cause could have produced the same state.

If C42's success arrives later, it may resolve retained command knowledge
through the current resolution owner. It cannot revive E42, regress the card
to an older result snapshot, or repeat Claim. Installation and command-resolution
rights are distinct.

For a stronger temporal case, suppose C42 really incorporated Alice's Claim,
then an authorized manager's later Reassign installed Bob as the new primary
helper. A permitted compatible C42 replay still establishes Alice's
*historical* success. A separately admitted complete current Request/
RequestAssignment observation establishes Bob's *current* responsibility.
Neither can be substituted for the other: the result cannot reinstall Alice,
and Bob's card cannot prove C42 failed. Scope, temporal context and qualified
provider progression, not increasing-looking basis labels or callback arrival
order, determine which observation may replace which presentation.

**** Conditional restoration instead of unconditional rollback

An optimistic snapshot captures a previously justified presentation. It does
not prove authority still has that state. Restoration is allowed only under the
current owner, target instance, observation context, and intervening adoption or
local-edit policy.

The safe default removes the owned provisional overlay and renders from the
current admitted base where available. If the implementation restores captured
content, its guard is checked at the physical mutation boundary. An earlier
Boolean check is insufficient if another installation or owner change can
intervene.

After X19 is adopted, a late E42 failure cannot reinstall X17. Even before
supersession, restoring X17's visual shape retains recovery-pending or unknown
classification. It does not assert that the model rolled back or C42 failed.
The current physical owner check must be made at the actual mutation boundary;
a formerly authorized snapshot is no longer a rollback right after owner,
target instance, scope, principal visibility, or independently newer local
state changes. If restoration fails or completes only partially, preserve
the actual physical presentation uncertainty and repair debt. No presumed
rollback success can close command resolution or unrelated Refresh obligations.

**** Paired command and presentation histories

These paired cases preserve the R4 counterexamples while testing the
stronger Part IV command and adoption contracts:

| Positive history | Adverse or ambiguous variation | Required boundary |
|------------------+--------------------------------+-------------------|
| A qualifying command-specific outcome establishes C42's incorporation, but current card installation is pending. | A success-shaped response or HTTP 200 has no qualified outcome correlation, or the still-provisional DOM is merely relabeled authoritative. | Preserve only justified command knowledge; admit physical adoption separately, under its current owner and completion evidence. |
| Qualified terminal closure excludes every compatible C42 incorporation attempt before presenting rejection. | Alice's attempt A1 aborts while compatible A2 has already incorporated or remains in flight. | A1's failure is not terminal C42 rejection; retain unknown or disclose the qualified historical outcome, never fabricate closure. |
| The owner retires E42 after timeout, then a new authorized owner resolves C42 or independently reacquires the card. | A late E42 timer or callback mutates the new target, or a current card is used to claim old command attribution. | Preserve retired resource boundaries and separate command-resolution versus presentation-recovery obligations. |
| A current scoped observation installs Bob after a later authorized Reassign while a compatible replay reports C42's earlier success for Alice. | The historical success resets the card to Alice, or Bob's current card is treated as proof C42 was rejected. | Preserve both historical and current propositions; reject stale presentation and false command-causality inferences. |
| A guarded rollback restores a still-compatible local view without claiming authority. | A newer adopted card, different target instance, or incomplete physical compensation makes the captured snapshot stale. | Do not overwrite newer ownership or silently claim canonical installation; retain recovery debt and honest visible classification. |

The positive controls must reach the same trusted, browser and physical
boundaries whose adverse cases they challenge. A fixture that simply assigns
=:committed=, =:rejected=, =:authoritative=, or =:installed= cannot issue
evidence or satisfy an actual-operation acceptance claim.
*** Every provisional trajectory requires resolution semantics
:PROPERTIES:
:CUSTOM_ID: req-provisional-resolution
:END:

The operation accounts for accepted incorporation, rejection, unknown outcomes,
authoritative supersession, local cancellation, incompatible-plan retirement,
and physical-effect failure wherever those cases can occur. Every terminal path
ends or explicitly transfers provisional and resource ownership. Physical
cleanup has its own completion/failure contract.

Not every operation needs every branch, but omitted branches need a supported
reason they cannot occur. Static preflight need not predict dynamic facts; it
requires declared handling for conditions capable of stranding the operation.
Each transition identifies the current execution and effect owners, which
command-attribution and acquisition/adoption debts survive, which physical
resources are retired or transferred, and which effects must be retried or
repaired. Semantic retirement takes effect without waiting for best-effort DOM
cleanup; a still-visible provisional remnant remains visibly provisional.
A recovered authoritative card can settle presentation while the original
command's disposition remains unknown.

A recovery path is not proof it eventually succeeds. Liveness claims identify
continued authority, backend/network availability, retention, scheduling, and
user-action premises. Unknown and retired states must remain safe even when
those progress premises fail.

Cancelling a local wait or dismissing an overlay does not cancel an authoritative
command. A genuine cancellation operation has model-defined effects and can
itself be too late, rejected, or uncertain. Wording preserves this distinction
where it affects the user's decisions. The recovery owner must not reuse a
retired execution's timer, callback, transport, DOM target rights, or
authenticated principal authority merely because it retains a compatible
semantic command identifier. A terminally failed submission attempt does
not by itself establish a terminally rejected command.

*** Concurrent provisional work and application-defined resolution

Different clients can hold incompatible provisional projections without creating
multiple authoritative histories. The model resolves commands under its policy.
Within one browser, overlapping provisional effects also require a policy;
untracked DOM replacement must not choose it accidentally.

An operation family declares one of these or another equally precise strategy.
Its conflict relation covers the actual read, write, field, query-membership,
target/installation, and separately retained local-draft scopes used by the
provisional operations; equal or different DOM node IDs alone do not establish
that semantic effects are disjoint. The selected policy states its arbitration
and successor-owner rule at the point where overlapping work is admitted:

- serialize conflicting commands or disable conflicting activation;
- permit independent overlays on disjoint declared scopes;
- supersede local presentation ownership while retaining older command
  resolution responsibility;
- compose or rebase overlays under an admitted dependency/conflict rule.

Gesso does not assume all optimistic effects commute. If C2 depends on C1's
provisional output, that dependency and its resolution are explicit. Rejection,
unknown resolution, or changed authoritative results for C1 can invalidate
C2's projection. C1's provisional output cannot silently become an
authoritative premise for C2.

The continuation depends on whether C2 is only a local draft, has an admitted
but unsent command, or may already have been submitted. A local draft may be
rederived, suspended, discarded, or presented as needing review under the
declared strategy. An already-issued C2 must retain its own immutable
command binding and independent disposition/recovery; retracting its overlay
does not retract its possible authoritative effects. A dependency failure is
not automatically a terminal rejection of C2. Rebase, composition and
supersession must preserve any independently newer adopted observation and
outstanding command and installation obligations.

Rebasing an overlay does not authorize changing an already-issued command's
immutable arguments. Changed intent follows a declared new-command or
cancellation/replacement protocol, retaining uncertainty about any old command.

Application-defined strategies remain ordinary Clojure/ClojureScript behind
typed registered contracts. Inputs identify admitted observations, scopes,
owned overlays, command knowledge, current owners, relevant dependencies,
and declared local inputs. Outputs specify retention, removal, recomputation,
deferred admission, or acquisition, with explicit unresolved debt and resource
handoffs. They do not write domain state, disclose a protected observation,
transfer authority, or create evidence by returning a success tag.
A stale result or callback from the superseded owner is rechecked against
current owner and scope before any physical mutation.

Analyzable strategies can support derived properties. Opaque strategies retain
asserted behavioral premises while structure and runtime bindings are checked.
No strategy may suppress required recovery debt or relabel an unknown command
as rejected merely to simplify the display.

*** Multi-target presentation and membership

One operation can affect a card, count, board membership, and notification
surface. Its presentation contract declares scopes and required local atomicity.
A collection of DOM swaps is not automatically one atomic installation.

Where partial installation is possible, the runtime records *per-target*
completed, pending, failed, or indeterminate effects with their source
observations, coverage, owners, and recovery paths. It cannot advance a
global adopted frontier for all targets because one card installed. A
requirement for atomic multi-target presentation must name an actual
all-or-nothing physical mechanism or a declared compensating protocol
whose intermediate state and failure cases are admitted; ordinary
sequential DOM writes cannot be called physically atomic. Retiring one
card's provisional owner need not remove unrelated overlays or advisory debt.
A later broad board refresh also cannot erase a separately newer
creator-local card or membership without the selected adoption policy.

HumanHelp can permit immediate correlated self-action updates while other
participants receive advisories. A card alone does not prove a complete new
board selection. Search, sorting, terminal-item visibility, and local filters
preserve that scope distinction.

*** No silent downgrade

Missing required optimism, command identity, scoped entry knowledge, or
resolution support prevents an enabled incomplete realization. The framework
cannot silently emit an ordinary =hx-post= and hope for equivalent behavior.

An explicitly declared non-optimistic alternative may be selected when its own
realization is complete and is permitted by the authored operation and
application contract. That is an explicit construction or invocation decision,
not a catch-all fallback for missing plans or adapters. In a managed HTMX
operation the required command/plan/correlation gate is enforced before the
physical send becomes irreversible; a missing projector, wrong owner, or
unready transport handoff fails that attempted path closed without a naked
replacement request. Other supported transports may realize asynchronous
provisional derivation under their declared buffering and failure contract:
one particular HTMX bridge's current synchronous limitation is not a
finished-system prohibition.

An unavailable affordance preserves operation identity and reason without an
active weaker transport path; it does not count as a working capability in an
eligible acceptance scenario. Raw HTMX remains legitimate for explicitly
unmanaged interactions and for authored non-optimistic paths with their own
complete authorization, effects, and recovery semantics.

Views remain free to use labels, badges, spinners, CSS, layout, and accessible
treatment. They render state rather than choose business outcomes or redefine
progression.


*** Paired resolution and capability cases

The finished application must admit useful eligible paths, not merely pass
negative checks by declining all optimistic work.

| Positive admitted history | Adverse history | Required independent result |
|---------------------------+-----------------+-----------------------------|
| E1 times out; successor E2 acquires a current card and later resolves C1 under its retained binding. | E2 reuses E1's retired timeout or DOM rights, or the card read is labeled as C1's command result. | Presentation recovery, command attribution, and owner retirement remain distinct, with a qualified effect at each boundary. |
| C2 is a not-yet-submitted provisional draft depending on C1; C1's rejection selects the declared suspend/rederive continuation. | C2 was already sent, but removing its local overlay is used to mark C2 rejected or to allocate a silent replacement command. | Unsent local work may be recomputed; submitted C2 retains immutable identity and independent reconciliation debt. |
| Two independent local overlays use proven disjoint declared semantic and installation scopes. | Their card targets differ but both modify the same board count or membership, or one consumes the other's unadopted premise. | Admit overlap only under the stated conflict/ordering strategy; no accidental commutativity or fabricated authoritative input. |
| An operation installs its card while a required board count remains pending, then follows a declared repair. | The first successful DOM swap is claimed to atomically install all targets or clear unrelated Live/Refresh debt. | Observe exact per-target completion and retain unmet scope and recovery obligations. |
| An authored non-optimistic operation uses its complete admitted HTTP path, and a managed optimistic operation issues C42 through its full projected path. | Required optimistic construction is missing, yet an ordinary =hx-post= is issued as a fallback. | Preserve positive legal raw/declared modes; reject the incomplete managed send before physical handoff without changing operation meaning. |

These cases must exercise their claimed model, admission, browser and host
boundaries. A diagnostic map or artificial rejection before the intended
boundary is not proof of correct physical enforcement.
** Continuity
:PROPERTIES:
:CUSTOM_ID: req-continuity-boundary
:END:

Continuity preserves browser-local interaction state across representation
replacement: focus, selection, scroll, open details, and explicitly selected
local drafts. It does not establish domain facts, authoritative provenance,
command validity, or agreement.

Ordinary continuity belongs behind the browser-effect boundary. Portable
choreography observes the effect outcome defined by that boundary, not separate
focus-restored or layout-finished events. An application can deliberately give a
browser interaction semantic meaning through an explicit contract; such meaning
is not inferred merely because continuity captured the interaction.

*** Ownership and physical captures

A continuity capture belongs to an admitted replacement/effect scope and a
concrete target instance. It need not invent a command execution for an ordinary
fragment refresh. Its identity distinguishes the logical slot, capture instance,
owner, and relevant target incarnation. Part II's
[[#req-resource-instance-identity][resource-instance contract]] applies.

The imperative shell can retain opaque DOM references and capture resources.
Portable semantic state retains the owner/resource references and lifecycle
needed to control their use. A DOM node still existing does not prove its owner
is current. A delayed restore must not consume or overwrite a newer capture.

The default capture registry binds a capture to the restore implementation and
capture format which produced it. Re-registering a box implementation must not
reinterpret an older capture under incompatible code. An explicit versioned
migration may be supported; otherwise incompatible captures are retired. This
binding does not permit an old implementation to execute after its rights have
been revoked by the current runtime policy.

Capture/restore hooks are ordinary host code. The framework can validate their
interfaces, registered identity, declared footprint, and resource use; claims
about arbitrary hook behavior remain explicit assertions unless established by
another mechanism. A custom hook must not acquire semantic installation rights
by calling an internal DOM helper.

*** Continuity does not preserve arbitrary DOM state

A continuity policy selects what may be captured and restored. It must not copy
an old fragment wholesale or restore authoritative security/context fields such
as credentials, anti-forgery tokens, operation bindings, principal identifiers,
or hidden command arguments as if they were harmless input drafts.

Restoration respects the newly admitted rendering. It may reopen a Request
already present and permitted in the new board, but cannot recreate a removed
or undisclosable Request. Duplicate or ambiguous element keys require a declared
failure policy; selecting the first matching node can restore into the wrong
control.

Local draft preservation also needs a product policy. A draft can be retained as
local user input without claiming it matches authoritative data. If replacing a
form would lose important unsaved work, the application can declare a prompt or
block-before-install policy. That is an explicit interaction requirement,
separate from ordinary best-effort focus or scroll restoration. It cannot turn
an already committed model operation into a rejection.

*** Search text and query meaning must remain aligned

A search control's draft text is local input. The applied query and the membership
of its result set have semantic meaning. Restoring one does not establish the
other.

If a board observation was acquired for search =cabinet=, restoring the control
to =cabinet hinge= must not silently label those results as satisfying the latter
query. The application must retain the distinction between draft and applied
query, acquire the newly requested scope, or follow another declared transition.
The same rule applies to server-side sorting, filters, and pagination.

Filtering a locally adopted set may be a legitimate view operation. It does not
prove complete membership for a new authoritative query. The query contract
states whether a control is local presentation, an unapplied draft, or the
selector of authoritative acquisition.

*** Worked example: replacing a HumanHelp board

Bob has applied search =cabinet=, opened Request R17, focused Refresh, and
scrolled partway down the board. A refresh acquires a complete authorized board
observation for that same applied query at X31.

An inspection view of a continuity capture is:

#+begin_src clojure
{:slot :request-board
 :capture-instance/id I1
 :owner {:replacement/id O1}
 :target-instance/id B1
 :capture-format :board-continuity/v1
 :local
 {:focus-key :board/refresh
  :scroll-anchor {:request-id R17 :offset 12}
  :open-request-ids #{R17}
  :search-draft "cabinet"}
 :context
 {:applied-query-ref board-query-ref
  :captured-edit-instance edit-instance-1}}
#+end_src

The actual resource can be opaque and include implementation-specific physical
handles. The context prevents a draft restore from misrepresenting the applied
query or overwriting newer edits. Neither =board-query-ref= nor X31 is admitted
merely by appearing in this inspection map.

A replacement follows these phases:

| Phase | Required behavior |
|-------+-------------------|
| Prepare | Check the observation and proposed target; establish the replacement owner and its effect identity. |
| Capture | Capture permitted local state under that owner; optional box failures remain local diagnostics. |
| Install | Recheck current owner, target instance, scope, and progression at the mutation boundary; perform the permitted update. |
| Admit completion | Record actual installation success, failure, or partial/indeterminate realization under the effect contract. |
| Restore | Restore only still-applicable local state, checking ownership at every deferred mutation boundary. |
| Release | Retire the capture and release physical resources without disturbing newer ownership. |

If installation succeeds but Refresh is absent, focus restoration may fail
while the new board remains adopted. The result distinguishes installation from
optional continuity:

#+begin_src clojure
{:installation
 {:status :completed
  :effect-id install-effect-1
  :observation-ref board-observation-X31}
 :continuity
 {:status :partial
  :restored #{:scroll :details}
  :skipped {:focus :target-no-longer-present}}}
#+end_src

This inspection result is not a browser-issued credential. The admitted shell
completion supplies the evidence the semantic owner needs. It must not be
converted into a generic failed swap which triggers stale rollback.

Now replacement O2 captures I2 while I1 still awaits layout. O2 owns the current
board instance, and Bob has typed =cabinet hinge=. I1's delayed callback must
not restore =cabinet=, consume I2, move focus back, or reset O2's scroll state.
Checking ownership only when scheduling the callback is insufficient; it is
checked again immediately before the delayed mutation.

Even without O2, a user edit after I1's capture may make restoration stale.
The policy compares the relevant local edit instance or equivalent ownership
information before overwriting input or focus. The rule is not that a numerically
larger capture always wins; it is that only the current permitted owner can
perform the particular mutation.

Open details are intersected with the newly authorized rendering. A local
capture can request R17 be open if R17 remains present; it cannot recreate R17
if the new scope excludes it. A scroll anchor that disappeared uses the declared
fallback, such as the nearest surviving anchor or a bounded raw offset.

*** Failure and cleanup

Optional capture failure must not prevent an otherwise permitted installation.
Optional restoration failure must not erase an installation already completed.
Promises and deferred callbacks need the same failure isolation as synchronous
hooks; catching only synchronous exceptions does not contain asynchronous
failure.

If installation itself partially applies, the result must preserve that
uncertainty and follow the repair contract. Neither the semantic state nor the
UI may pretend the entire fragment is installed. Continuity success cannot
compensate for missing installation evidence.

Semantic retirement revokes restoration rights before best-effort physical
cleanup. Failed cleanup is diagnostic/resource debt, not authority for an old
callback to act again. Resource release should be idempotent and scoped to the
resource instance it owns.

A style lock illustrates the requirement. Seeing the same min-height value that
an old effect once wrote does not necessarily prove it still owns that value;
a newer effect might have written the same value. Cleanup must use the resource
ownership contract or a justified equivalent, rather than rely solely on
same-shaped physical state. It must not undo a newer lock.

Physical resource lifetime may outlast semantic ownership. In that case the
remaining handle is powerless cleanup debt. Portable Choreo needs only the
contracted installation/effect outcome; browser diagnostics may report the
failed optional focus, scroll, or capture operation separately.

** Views and UI annotation
:PROPERTIES:
:CUSTOM_ID: req-view-operation-binding
:END:

Views declare semantic intent and render prepared presentation. They do not
redefine choreography, duplicate domain authorization policy, or independently
assemble transport/protocol parameters for a managed operation.

The ordinary path is:

1. a public semantic operation and choreography declare the behavior;
2. application assembly resolves its plan, transport, acquisition, settlement,
   server capabilities, and artifact requirements;
3. preparation binds per-render arguments and admitted observation context;
4. the view supplies element choice, labels, classes, layout, and accessibility;
5. the renderer derives a complete managed realization from the admitted binding.

A view may use a prepared binding directly or a concise declaration normalized
through the same preparation boundary. Multiple convenient authoring forms must
not create multiple independent meanings of Claim.

*** Binding values versus operation-owned policy

The registered operation owns its choreography, supported realization modes,
settlement mapping, provisional derivation, recovery policy, required resources,
and compatibility constraints. Per-render binding supplies only admitted
variable inputs: subject/arguments, observation references, and target context
where the operation permits them.

Those binding fields have a closed schema. A view cannot override an operation's
plan, timeout semantics, principal authority, rollback policy, or result mapping
by inserting an extra key. Presentation options occupy a distinct checked area;
unknown semantic keys fail with a precise error.

For example:

#+begin_src clojure
(defn prepare-request-card [trusted-context admitted-card]
  (let [card (observation/value admitted-card)
        claim (actions/prepare
               trusted-context
               {:operation request-choreo/claim
                :arguments {:request-id (:request/id card)}
                :observations {:request-card admitted-card}})]
    {:request {:id (:request/id card)
               :title (:request/title card)
               :status (:request/status card)}
     :actions {:claim claim}}))
#+end_src

This illustrative preparation path verifies that the observation, argument,
operation, principal context, and target scope agree. It obtains availability
through public model/application interfaces. The renderer does not rerun a
second Claim policy in Hiccup.

The prepared affordance need not serialize principal credentials, server
capabilities, or proof objects. When the browser returns binding data, the server
re-establishes trusted principal identity and the required semantic bindings.
Canonical command arguments use the same declared mapping as Part IV; a domain
Request ID must not be confused with =:http-request-id= or another transport ID.

*** Availability, input collection, and construction defects

Prepared actions distinguish legitimate product states from broken realization:

| Preparation result | Meaning and permitted rendering |
|--------------------+---------------------------------|
| Available | A complete admitted entry affordance can be enabled. |
| Policy unavailable | Current prepared semantics do not offer the operation; hide or disable under the declared disclosure/presentation policy. |
| Needs input | A declared interaction must collect further user input before final invocation; the offered input-collection entry path itself is complete. |
| Deferred or dynamically unavailable | A declared prerequisite cannot yet be established; show the contracted pending/unavailable state and recovery path. |
| Construction failure | Required operation, plan, binding, capability, route, or semantic input is missing or inconsistent; reject the incomplete enabled realization. |

These classifications have closed payload contracts. Missing or =nil= entries
cannot silently stand for every kind of unavailability. A product may use a
compact representation internally, but the preparation boundary must establish
which meaning it has.

A missing Reassign helper ID is not inherently a defect if the action is meant
to open an admitted helper-selection form. That entry action is fully specified,
and final Reassign remains unavailable until its required arguments are bound.
If the application tries to emit the final mutation without a required helper
ID, that is a construction failure. The declaration determines which case
applies; the renderer must not guess.

An inspection action set could look like:

#+begin_src clojure
{:claim
 {:availability :available
  :binding-ref claim-binding-ref}
 :cancel
 {:availability :unavailable
  :reason :policy/not-offered}
 :reassign
 {:availability :needs-input
  :entry-binding-ref helper-selection-binding-ref
  :required-inputs #{:helper-id}}}
#+end_src

The references resolve to admitted objects. A plain map with these fields is not
sufficient. Reasons must obey disclosure policy; a disabled button must not leak
a private Membership or Organization fact.

Preparation validates the complete required action set, including actions that
will not be rendered. A hidden action cannot conceal a malformed required
binding. Separately, application acceptance compares the intended capability
catalog against representative eligible scenarios. Tests derived only from the
buttons that happened to render cannot detect a missing product action.

*** A small view API

Once preparation succeeds, view code can remain ordinary Hiccup:

#+begin_src clojure
(defn request-card-view [{:keys [request actions]}]
  (let [claim (actions/require-prepared! :request/claim (:claim actions))]
    [:article.request-card
     [:h3 (:title request)]
     [:p.status (name (:status request))]
     (case (actions/availability claim)
       :available
       (gesso/action
        {:binding (actions/binding claim)
         :presentation {:pending-label "Claiming..."
                        :class "gesso-action gesso-action--primary"}}
        "Claim")
       :unavailable
       nil
       :deferred
       [:span.action-status "Claim is temporarily unavailable."])]))
#+end_src

This example's Claim preparation contract admits available, unavailable, and
deferred variants. Its final mutation has no input-collection phase; an
unexpected needs-input result is a contract mismatch, not an implicit nil.
Construction failure is raised by preparation/validation before this view can
serve an incomplete active control.

The renderer derives routes, HTMX attributes, command-wire fields, plan and
artifact references, correlation, and progression handling from the assembly.
A view author does not repeat these details in strings. If required metadata is
missing, the renderer reports the exact missing edge or emits an explicitly
non-executable unavailable affordance where the declared policy permits it.

Semantic identity is preserved through rendering. Binding, encoding, and
transport selection may elaborate an operation but cannot silently substitute
another operation or weaken its required protocol. An opaque encoded binding is
not necessarily authenticated, and authentication of its bytes would still not
establish current model authorization.

*** Prepared affordance is not a security capability

The term /prepared affordance/ is preferable for the object consumed by a view.
If the implementation calls it an operation capability, diagnostics must
qualify that meaning. It is not an irrevocable or unforgeable authorization
credential merely because the server prepared it.

A trusted execution capability has a different contract: it permits a scoped
server action under current admission rules. A view binding cannot supply the
transaction handle, authenticated principal, or other trusted resource required
by the model.

Browser-returned observation information is an observed-basis claim unless a
trusted boundary establishes something stronger. An authenticated receipt can
prove its issuer's stated historical fact under that receipt contract. It does
not prove the human saw the card, the browser installed it, or permission still
holds now.

Gesso constructs or admits stronger semantic values at the boundary with enough
information. Web developers should not have to hand-assemble proof wrappers to
render an ordinary button. In-process admission discipline prevents accidental
misuse; it is not a sandbox against a determined author with arbitrary trusted
host access.

*** Raw HTMX and presentation freedom

Ordinary HTMX remains a first-class mechanism for interactions deliberately
outside Choreo's promises. The distinction is explicit: an ordinary affordance
has its ordinary contract; a managed affordance has a complete managed
realization or a precise non-executable failure/unavailability state.

An ordinary route still obeys server authentication and model safety. It must
not occupy a route reserved for a managed operation as a way to bypass its
protocol. Declaring fewer client guarantees does not authorize direct
unprotected writes.

Views own text, element choice, semantic CSS, icons, layout, ARIA, pending
labels, and how provisional or authoritative states look. They must not
interpret a newer database token as command rejection or choose reconciliation
policy. They display the decisions made by the admitted model/runtime contract.

Status must be understandable without relying only on color or motion.
Keyboard activation, form submission, disabled/busy semantics, and duplicate
activation handling must match the declared entry policy. Disabling a button
alone is not the framework's command deduplication mechanism.

*** Assembly obligations and diagnostics

An enabled managed control creates obligations for its complete path: operation,
choreography, projected plan, loaded browser artifact, transport, trusted server
entry, model realization, outcome mapping, acquisition, and presentation.
Part VII checks these before serving, including dynamically generated surfaces.
Its later position in this document does not permit serving incomplete controls
until a future check runs.

Errors preserve source component, operation, role/subject when disclosable,
expected binding/plan/capability, and the missing or incompatible edge. Missing
plans should not collapse into generic malformed HTML errors. Diagnostics must
also preserve the difference between policy unavailability and implementation
failure.

** Clojure and ClojureScript execution
:PROPERTIES:
:CUSTOM_ID: req-portable-execution
:END:

The permanent executable semantic core gives projected behavior one meaning
across supported hosts. Shared =.cljc= definitions are the preferred realization
where practical. JVM, Node, and Chromium must not carry independently handwritten
versions of the same state machine merely because their callbacks differ.

This commitment does not make the whole application portable. Database access,
trusted authentication, arbitrary server code, DOM manipulation, and network
integration belong to declared host boundaries. Full-language actions remain
available there. The core interprets their contracts and admitted completions;
it does not need to understand or emulate all application code.

The executable semantic core is distinct from the later proof kernel/checker.
The former executes admitted transition meaning. The latter checks derivations
or other stated judgments about that meaning. Compiler, verifier, and proof
machinery need not ship to the production browser.

*** One vocabulary from construction through execution

Part III's role-local vocabulary is canonical:

| Node kind | Runtime responsibility |
|-----------+------------------------|
| =:local= | Request the declared local action and consume its admitted completion. |
| =:authoritative= | At the appropriate trusted role, request a public model operation and consume its admitted typed result. |
| =:branch= | Select a declared successor using an established typed value. |
| =:send= | Issue a declared participant communication with the required known payload. |
| =:receive= | Await an admitted participant message matching one unambiguous alternative. |
| =:await= | Await a declared environment event from its registered source contract. |
| =:return= | Complete this role's local trajectory with its declared outcome. |

Optimism does not introduce a separately handwritten transition-table language
with different guard or outcome semantics. Provisional derivation, command
handling, acquisition, and installation are declared actions/events coordinated
through the same vocabulary and the browser adapter's explicit ownership
contract.

A projected =:receive= is not satisfied by an environment event with the same
keyword. A normalized map cannot select its own trust or ownership class.
Participant communications, authoritative observations, local action completions,
and environment events retain their distinct admission paths.

The plan format has closed semantic keys and versioned interpretation. Unknown
opcodes, unresolved action references, malformed successor locations, overlapping
receive alternatives, or unsupported event contracts are construction failures.
An explicit extension area can carry nonsemantic metadata without changing
execution. Semantic extensions require a registered interpretation and their own
assurance contract.

*** State ownership and effects

The role-local machine owns its protocol state and established values. The
shared browser coordinator owns cross-execution target arbitration, obligations,
and resource lifetimes where required. These are composed responsibilities,
not competing copies of one machine. Each semantic fact has one declared owner.

The imperative shell owns physical handles: DOM references, timers, transport
objects, listeners, and opaque continuity captures. It interprets admitted
effects and reports correlated completions/failures. It does not independently
choose successors or reinterpret a domain outcome from a status string.

An abstract transition can update semantic intent immediately and request a
physical effect. The facts it records must match that point in the lifecycle:
request issued is not request completed; observation acquired is not observation
installed; installation permitted is not adoption completed.

The runtime allocates fresh effect/resource instances through a declared
mechanism. Nondeterministic choices such as UUIDs and sampled time enter as
explicit admitted inputs or action results. A pure transition does not secretly
consult a global clock or allocate different command IDs when replayed in a
test. Before a command's first possible send, its stable binding is already
recorded by the appropriate owner.

Physical effects carry the owner, target/resource instance, operation/command
correlation where relevant, and typed payload/reference required for admission.
A callback copies the correlation issued with that physical resource. It must
not fetch a newly current execution ID and relabel an old callback as belonging
to the replacement execution.

*** A concrete installation segment

The following is an inspection of a generated local segment using the canonical
node kinds. Entry already supplies an admitted observation reference and an
admitted installation request. Registered action and event contracts supply
schema, provenance, current-owner, and failure obligations not repeated in this
compact payload.

#+begin_src clojure
{:gesso.choreo/type :gesso.choreo/executable-plan
 :gesso.choreo/version 1
 :role :browser
 :initial 0
 :states
 {0 {:op :local
     :action :presentation/request-installation
     :requires #{:installation/request}
     :outputs #{:installation/effect-ref}
     :next 1}
  1 {:op :await
     :events {:presentation/installation-completed 2
              :presentation/installation-failed 3}
     :event-contracts
     {:presentation/installation-completed
      {:required #{:installation/effect-ref :installation/completion-ref}
       :optional #{}
       :open-data? false}
      :presentation/installation-failed
      {:required #{:installation/effect-ref :installation/failure-ref}
       :optional #{}
       :open-data? false}}}
  2 {:op :local
     :action :presentation/adopt-completed
     :requires #{:installation/request :installation/completion-ref}
     :outputs #{:presentation/adoption-ref}
     :next 4}
  3 {:op :local
     :action :presentation/retain-and-recover
     :requires #{:installation/request :installation/failure-ref}
     :outputs #{:presentation/recovery-owner-ref}
     :next 5}
  4 {:op :return :outcome :presentation/ready}
  5 {:op :return :outcome :presentation/recovery-handed-off}}}
#+end_src

The representation version is illustrative. A concrete emitted segment must
satisfy the actual selected schema and its registered interfaces; this excerpt
is not a second author-maintained implementation.

The request action completes when installation work has been registered and
issued under the host contract. It does not claim that the DOM changed. The host
must buffer or otherwise serialize an immediate completion so it cannot be lost
before the machine reaches its await boundary.

The completed event is admitted only from that issued effect and for the current
permitted target owner. The completion reference resolves to actual physical
completion evidence. It does not become authoritative because an environment
payload calls itself completed. The adopt action consumes that admitted evidence
and updates the appropriate semantic owner; merely possessing a reference with
a familiar shape is insufficient.

The failed path preserves the failure's scope, including partial or indeterminate
installation where applicable, and establishes the declared recovery owner before
returning. It does not reject an already incorporated command. Owner retirement,
source loss, or unbounded absence of a completion follows the segment's registered
interruption/deadline and recovery contract. Assembly must reject a required
physical effect with no such handling when it can strand this wait.

The fragment does not claim that all browser state belongs to one execution.
The adopt action communicates with the shared coordinator through its admitted
interface. That coordinator updates current adoption and advisory debt from its
latest state, preserving obligations which arrived after installation was
requested.

*** Claim execution uses independent outcome and installation paths

A complete generated Claim trajectory composes segments like the one above with
command handling. The following table describes semantic boundaries rather than
an alternative executable format:

| Boundary | Required successor behavior |
|----------+-----------------------------|
| Invocation admitted | Record stable intent and execution ownership; derive permitted provisional presentation; issue declared effects. |
| Command submitted or delivery attempted | Retain pending/unknown knowledge until evidence establishes more; submission alone is not incorporation. |
| Accepted command evidence | Record permitted incorporation knowledge independently of whether a current card is available. |
| Rejected command evidence | Record the authoritative rejection and select its declared presentation/recovery path. |
| Unknown delivery or local deadline | Preserve unknown unless stronger evidence already exists; retain or transfer recovery ownership. |
| Observation acquired | Validate scope and progression; propose installation without claiming adoption. |
| Installation completed | Admit completion under the current owner; update adoption and discharge only covered obligations. |
| Installation failed | Preserve command knowledge and unresolved presentation debt; follow repair or reacquisition. |
| Execution retired | Revoke its local rights; preserve or transfer unresolved command/work obligations according to the contract. |

A deadline racing with a participant response requires explicit arbitration
between the projected machine and its owner-relative adapter. The timeout is
not smuggled into =:receive= as a forged participant message. The supported
waiting/interruption mechanism must preserve the declared race semantics; a
projection backend lacking that mechanism rejects the unsupported construction
rather than dropping the timeout branch.

Whichever event is admitted first may change local ownership, but it cannot
change what evidence means. A later success can still resolve a retained command
through an admitted recovery owner. It cannot restore retired installation
rights. A late timer cannot erase a known success.

*** Boundary shapes, knowledge, and provenance

Actions declare required values, optional inputs where supported, closed outputs,
possible failures, effects, and completion behavior. Validators are compiled
for the admitted schema/registry version and invoked unconditionally at the
relevant boundaries. Optional assertions disabled in production are not boundary
validation.

Missing, present nil, false, and absent optional output are distinct according
to the schema. A later completion which omits an optional field must not inherit
an old value accidentally. An unknown branch selector is a typed contract fault
rather than permission to choose an arbitrary default.

Passing a value schema establishes shape. An opaque local function returning a
map is not automatically an authoritative source. Its output retains the
provenance and asserted properties justified by its declared action contract.
Authoritative outputs and observations cross their dedicated admission boundary;
ordinary event normalization does not upgrade them.

Full-language implementations may access facilities beyond the portable core
under their declared host contracts. Properties such as purity, effect footprint,
termination, and semantic accuracy remain explicit premises when not derived or
enforced. A managed local action with an asserted functional contract is valid
under an accepting assurance policy; an unresolved action reference is not.

*** Normalization precedes admission

The browser boundary converts raw HTMX, timer, EventSource, DOM, and lifecycle
callbacks into bounded normalized data. It may decode and copy primitive values
and issued correlation. It does not derive authority from mutable attributes,
HTML shape, event names, or a physical handle's continued existence.

Admission identifies the event class from its registered source path, resolves
the declared owner, checks current applicability, validates payload and binding,
and then delivers the event to the appropriate semantic transition. Untrusted
fields cannot opt into a weaker ownership class.

A nominal record or opaque wrapper may prevent accidental substitution within
cooperating code. After untrusted serialization, the receiving boundary must
re-establish the required category through validation, authentication,
acquisition, or verification. The wrapper's name is not transferable proof.

*** Explicit transition and failure results

For every supported state/event class, the runtime has an explicit result:
advance, accepted no-op, stale/duplicate rejection, recovery transition, or
runtime/contract fault. Unknown event classes and invalid plan versions are
classified at admission. Unexpected exceptions are faults, not evidence the
input combination was mathematically impossible.

Event-admission results use a separate vocabulary from presentation settlements
and model outcomes. For example, =:step/applied= and =:step/ignored-stale= describe
a runtime decision; they do not mean Claim was accepted or rejected.

Selection must be deterministic under the declared contract. Construction
rejects overlapping alternatives unless their equivalence or explicit arbitration
is established. A runtime must not simply take the first matching event keyword
from several candidates and silently ignore the rest.

A total dispatcher over a supported event vocabulary does not prove arbitrary
Clojure callbacks terminate. It also does not imply every event is valid. The
scope of totality, supported value domain, and callback premises must be stated.
Invalid states can produce typed invariant violations with a safe fault/recovery
path rather than undefined mutation.

*** Cross-host portability

The shared core and corpus run under JVM Clojure, Node ClojureScript, and
Chromium ClojureScript. Tests compare normalized semantic transitions, emitted
abstract effects, correlation, and fault classifications for the same admitted
inputs, including stale and adversarial schedules.

The portable data contract specifies numeric range and precision, equality,
collection semantics, missing/nil/false behavior, encoding, and errors. JavaScript
numeric precision must not silently alter an identity or selector. Platform
objects, mutable DOM references, and arbitrary functions do not appear in the
portable plan payload. Registered action references bind host implementations
through the assembly's separate implementation contract.

Source sharing reduces divergence but does not prove every compiler/runtime
behavior equivalent. Cross-host conformance tests remain evidence for exercised
cases. A stronger claim identifies its formal correspondence and external
compiler/runtime premises.

Production tests execute the canonical emitted plan and the production semantic
core. Pure tests can substitute declared effect interpreters; browser integration
tests additionally exercise the actual shell and DOM/HTMX lifecycle. A mock that
always returns installed does not establish physical installation correctness.
Advanced compilation and actual packaged assets need their own relevant checks.

*** Compatibility and deployment

The runtime distinguishes plan representation version, operation/interface
meaning, protocol compatibility, admitted assembly identity, and exact packaged
artifact identity. Deployment identity records physical rollout where needed;
it does not substitute for any of these contracts or give all resources one
shared lifetime.

Parsing old bytes does not establish continuation compatibility. A suspended
browser can retain an unresolved command while its old local plan is retired.
The admitted compatibility/recovery policy must preserve that command reference
and current disclosure requirements without resuming incompatible state.

The production browser executes admitted local plans; it does not reconstruct
the global choreography, rerun projection, load proof DAGs, or solve obligations
to decide an ordinary transition. Executable guards and necessary admission
contracts remain executable. Their explanations remain separate.

** Executable projection and diagnostic sidecars
:PROPERTIES:
:CUSTOM_ID: req-executable-plan-sidecar-boundary
:END:

Construction emits one canonical =ExecutablePlan= per projected role and
separate compiler/diagnostic evidence products. The executable plan is the
semantic runtime payload used by production and tests. A
=DiagnosticProofSidecar= may explain it but cannot complete or alter its meaning.

A build may use a rich internal representation while checking and projecting.
The commitment is that production does not execute one machine while verification
or proof-enabled tests quietly execute a different, richer client machine.
Compiler transformations still need their stated correspondence; separating the
sidecar does not eliminate the projection or packaging proof obligation.

*** What belongs in each product

| Product | Contents |
|---------+----------|
| ExecutablePlan | Supported local node structure, executable selectors/guards where defined by the format, action/message/event contracts, successors, and runtime interpretation fields. |
| Admitted runtime state and inputs | Concrete command/execution/resource bindings, established values, observations, outstanding effects, and lifecycle state. |
| Assembly/implementation binding | Registered action realizations, trusted boundaries, loaded versions, supported host capabilities, and applicable admission policy. |
| Compiler correspondence data | Mapping from source semantics to actual runtime locators, including generated/synthetic states and continuation relationships. |
| DiagnosticProofSidecar | Explanations, source locations, checked derivations or references, named premises, and exact executable correspondence. |
| Packaged artifact manifest | Relationship between the admitted plan set, implementation/runtime closure, and emitted assets. |

These products need not be stored as six separate files. Their meanings and
trust boundaries must remain distinct. In particular, application execution
cannot depend on a source span or optional explanation object to discover which
guard it was supposed to run.

The executable semantic core and browser coordinator do not accept a diagnostic
sidecar as a transition input. The conceptual interface is:

#+begin_src clojure
(semantic/step executable-plan admitted-state admitted-event)
;; Returns the next semantic state, declared abstract effects,
;; an explicit step classification, and the actual transition locator.
#+end_src

Guards operate on admitted runtime premises and executable contracts. The proof
kernel/checker may explain why those guards contribute to a property; it does
not supply current runtime permission by having accepted a derivation earlier.

*** Exact identities and their domains

The design distinguishes:

| Identity | Question it answers |
|----------+---------------------|
| Runtime locator | Which state, transition, or effect in this exact emitted plan was selected? |
| Source semantic name | Which authored or generated concept does that locator explain? |
| Normalized semantic dependency identity | Which exact semantic definitions and dependencies a claim or construction uses. |
| Proof-obligation identity | Which proposition/derivation is being checked or explained? |
| Exact executable identity | Does this sidecar describe this exact canonical runtime payload and coordinate layout? |
| Compatibility identity/judgment | May this runtime safely participate or continue under the selected server/assembly contract? |
| Packaged asset identity | Which actual emitted browser/server asset bytes are loaded? |

Runtime locators need not be stable across compilations. Source names can remain
useful while behavior changes, so equal names do not preserve proof applicability.
Two plans can be compatible while having different exact payload identities.
The same plan payload can also be bound to different opaque implementations;
applicable assurance therefore includes the relevant implementation/assembly
closure, not merely the plan digest.

*** Canonical payload identity

The exact identity recipe specifies:

- the object being identified: canonical plan terms, a plan set, or exact asset
  bytes;
- encoding and schema versions;
- type-preserving representation of supported scalars and collections;
- deterministic map/set ordering without discarding semantic distinctions;
- unsupported values and their rejection behavior;
- excluded self-identifying fields, or an external identity envelope;
- the digest algorithm and its accepted collision premise;
- interpretation dependencies bound separately when not included in the payload.

A printed EDN map is not automatically a canonical encoding. Nil versus absence,
keyword versus string, list versus vector where meaningful, numeric forms, and
map/set order require explicit treatment. Host functions and DOM objects cannot
be silently printed into a supposedly portable canonical digest.

A convenient design keeps the payload free of its own digest:

#+begin_src clojure
(def executable-identity
  (artifact/digest
   {:algorithm :sha-256
    :encoding :gesso-plan-canonical-v1
    :value executable-plan}))

(def plan-manifest-entry
  {:role :browser
   :executable-identity executable-identity
   :plan-format-version 1
   :runtime-contract-ref runtime-contract-ref
   :implementation-closure-ref implementation-closure-ref})
#+end_src

The algorithm and format labels illustrate a declared recipe, not a new trust
source. If identity is embedded in an envelope, the payload domain excludes that
self-identifying field. It must not hash an object including the very digest
being computed.

Hashing canonical plan terms is not hashing the emitted JavaScript bundle.
Packaging must establish which plan set and runtime/implementation closure the
actual asset contains. A copied or stale generated stamp cannot substitute for
that relationship. Exact equality of a stamp supplied by two untrusted locations
is not construction evidence.

*** Binding sidecars to the actual compilation

Compiler correspondence is generated alongside the executable plan from the
same admitted semantic subject. It records the actual mapping, including
synthetic states or compacted continuations, rather than reconstructing it later
from similar state names.

A sidecar inspection view can be:

#+begin_src clojure
{:sidecar/version 1
 :role :browser
 :executable-identity executable-identity
 :semantic-subject-ref semantic-subject-ref
 :checker-result-ref checker-result-ref
 :implementation-closure-ref implementation-closure-ref
 :locations
 {installation-complete-locator
  {:semantic-id :request-claim/presentation-installed
   :source-ref source-ref
   :claims
   [{:proposition-ref adoption-proposition-ref
     :mechanism :checked-derivation
     :evidence-ref derivation-ref
     :premises [shell-completion-premise
                current-owner-premise]
     :coverage-ref coverage-ref}]}}}
#+end_src

The locator comes from the actual emitted plan mapping. The symbols above denote
bound values; replacing them with copied identifiers cannot authenticate the
claims. The sidecar may contain checked and unverified claims with distinct
status. Its existence does not prove every listed obligation was discharged.

Attaching behavioral correspondence evidence requires the exact semantic and
executable subject to agree with the artifact being explained. Evidence for
choreography A cannot be composed with an artifact generated from choreography
B merely because their operation names or state counts match.

Diagnostic admission first validates the sidecar format and exact executable
identity. Where tooling labels claims checker-verified, it additionally validates
provenance, the checker result, applicable premise set, and implementation
binding. A fabricated sidecar can copy the digest. Exact correspondence and
trusted claim acceptance are separate checks.

If exact identity mismatches, diagnostics must refuse correspondence for that
plan. They cannot guess by timestamps, similar names, or near-matching runtime
coordinates. Ordinary execution may continue if its own admission and
compatibility remain valid. An unavailable explanation is not an executable
failure and is not evidence of a safe transition either.

*** Observe the selected transition, not a recomputation

A trace contains the locator selected by the actual semantic step, its admitted
subject identity, and a bounded description of its result/effects. The observer
uses that locator to retrieve correspondence. It must not rerun guards or
transition selection independently to guess what happened.

Recomputation can diverge if callbacks are effectful, registries change, state is
not identical, or the observer has different inputs. Even when the pure core
would reproduce the same result, reporting the actual selected locator gives a
clearer correspondence contract.

Optional diagnostic access is read-only. It does not receive mutable live
objects or authority-bearing handles it can modify. Redacted immutable trace
values are preferable to whole contexts, DOM captures, credentials, or unrestricted
command payloads. Missing or redacted data is reported as such; an explanation
must not invent an unavailable premise.

*** Diagnostic noninterference

For the same admitted initial state, canonical plan, runtime interpretation,
and normalized event sequence, adding, removing, corrupting, or replacing a
sidecar must not change semantic transitions or abstract effects, apart from
permitted diagnostic output.

#+begin_example
semantic-trace(run(plan, initial-state, events))
  = semantic-trace(run-with-diagnostics(plan, initial-state, events))
#+end_example

This is a conditional noninterference claim over fixed semantic inputs. It does
not claim instrumentation has no wall-clock, memory, scheduling, or resource
cost, or that every real browser receives the same event sequence with debugging
enabled.

Excluding a sidecar parameter is necessary but insufficient. Ambient mutable
registries, shared callbacks, exception propagation, hidden source lookups, or
observer decisions fed back into admission can reintroduce a control path.
Module/API boundaries and implementation contracts must prevent those paths.

Optional diagnostics must not gate required effects or completion delivery. The
normal path records the actual transition and issues its required work according
to the semantic contract. A bounded best-effort trace queue can feed observers
independently; overflow drops diagnostic work under a visible diagnostic policy,
not semantic work.

Catching an observer exception does not contain a nonterminating or blocking
observer. In-process custom observers require an explicit bounded/nonblocking
premise, or execution isolation adequate for the promised containment. The
framework cannot prove arbitrary observer code harmless just because its return
value is ignored. Redaction and diagnostic failure reporting must also be
bounded and contained.

If an audit action is required for the operation's correctness or compliance
contract, it is a declared semantic effect with its own failure policy. It must
not hide inside an optional observer whose loss is advertised as irrelevant.

*** Sidecars carry no authority

A browser-side sidecar cannot establish principal identity, current model
permission, authoritative state, subscription authorization, or permission to
read protected data. The server accepts commands under its trusted boundary,
regardless of the browser's proof-looking material.

Sidecars can themselves reveal source details, policy names, or private values.
Production packaging omits them by default; authorized diagnostic distribution
follows the application's disclosure contract. Normal execution must remain
complete when they are absent.

The implementation can enforce part of this separation by dependency direction
and closed runtime formats, and test it with missing, malformed, mismatched,
throwing, and resource-heavy observers. Such checks support their stated scope;
they do not establish a sandbox for arbitrary same-process trusted code.

*** Build output and assembly closure

Build output supplies machine-checkable correspondence among the current
semantic subject, projected plan set, registered implementation closure, runtime
contract, packaged assets, and optional exact sidecars. Test, diagnostic, and
production modes execute the same admitted semantic payload for a given build.

Part VII's [[#req-assembly-construction-phases][assembly admission phases]] verify
that the served application loads the required artifacts and bindings. A source
file containing a correct plan is insufficient when the browser actually loads
an older bundle. A browser's claimed artifact identity is likewise not server
authorization.

The build may legitimately transform or optimize code. Any transformation that
changes the object covered by a claim needs the declared correspondence or
requalification. Sidecar separation avoids a second proof-annotated runtime;
it does not excuse testing only an unoptimized development realization while
claiming the production shell has been exercised.

** Conformance and acceptance obligations

The same canonical semantics must support construction checks, runtime
interpretation, and focused conformance cases. Part IX supplies certification
judgments; Part X supplies the stronger soundness and implementation
correspondence arguments. This part requires the following cases at their
appropriate boundaries.

| Area | Case | Required behavior |
|------+-------+-------------------|
| Provisional typing | Claiming label is rendered over an open Request. | Presentation phase does not become an undeclared authoritative domain status. |
| Entry knowledge | Required observation is absent or belongs to another Request. | The required optimistic construction is rejected; no silent ordinary-request fallback. |
| Creation | A local preview is created before authoritative entity existence. | Its declared collection/local-input premises remain explicit; the preview does not prove uniqueness or absence. |
| Command identity | Transport retries or a new execution continue an unresolved intent. | Stable command binding is preserved; physical retry does not allocate a new intent. |
| Accepted outcome | Command success arrives without a fresh card. | Record incorporation knowledge and retain presentation recovery; do not invent rejection or require an unavailable card to believe valid success evidence. |
| Rejection | Current card resembles a conflicting outcome but no rejection evidence exists. | Do not infer command rejection from current state. |
| Timeout | Timer arrives after accepted evidence. | Do not erase established command knowledge or revive retired timer rights. |
| Supersession | A fresh card installs while original command attribution is unknown. | Recover presentation while retaining the independent attribution obligation. |
| Installation | Permission is granted but the DOM effect fails. | Do not mark adoption complete or discharge acquire-and-adopt debt. |
| Late rollback | Old failure follows newer adopted authority. | Do not restore the obsolete snapshot. |
| Local concurrency | One provisional command depends on another. | Apply the declared dependency/resolution policy; no silent promotion of provisional inputs. |
| Rebase | New authority changes the local projection after a command was sent. | Recompute permitted presentation without silently changing immutable command arguments. |
| Multi-target effects | One of several required swaps completes. | Record only established installation coverage and retain repair work for the rest. |
| Continuity failure | Focus restore throws after successful installation. | Preserve adoption; report local continuity failure separately. |
| Deferred continuity | An old layout callback follows a new capture or user edit. | Recheck current rights and preserve the newer local state. |
| Query controls | Draft search differs from the query that produced the board. | Keep draft/applied-query distinction or reacquire; do not relabel stale results. |
| Capture implementation | Restore implementation changes after capture. | Use the compatible bound implementation or explicit migration/retirement. |
| Cleanup ownership | A newer style lock has the same physical value as an older lock. | Old cleanup cannot infer current ownership solely from equal values. |
| Protected content | A Request disappears from the authorized board. | Continuity cannot recreate its content or disclosure. |
| Availability | Reassign intentionally requires helper selection. | Admit the complete input-collection entry path; prevent incomplete final invocation. |
| Construction defect | A required action is missing, even if hidden. | Fail the appropriate preparation/assembly check rather than treating nil as policy absence. |
| View binding | A renderer tries to override registered operation policy. | Reject the incompatible binding field. |
| Event classes | An environment event copies a participant message name. | Do not cross the declared admission class. |
| Event selection | Several alternatives overlap. | Reject or use explicitly established arbitration/equivalence; no incidental first-match semantics. |
| Callback correlation | An old physical callback reads the new current execution ID. | Reject that rebinding; correlation comes from the issued resource. |
| Immediate completion | Effect completes before its await state is reached. | The host registration/buffering contract prevents losing or misrouting completion. |
| Portability | Missing/nil/false or numeric representation varies across hosts. | Preserve the declared value semantics or reject unsupported representations. |
| Opaque action | Full-language implementation has an asserted contract. | Admit under an accepting policy while retaining the assertion and structural checks. |
| Exact sidecar | Sidecar belongs to another emitted plan with similar names. | Refuse diagnostic correspondence without changing otherwise valid execution. |
| Forged proof metadata | A sidecar copies the correct executable digest. | Do not treat its claims as checked without provenance and applicable evidence. |
| Observer failure | Observer throws, blocks, or floods output. | Contain under the declared mechanism/premises; never silently suppress required semantic work. |
| Trace locator | Diagnostic code tries to recompute the selected transition. | Use the actual recorded locator and exact compilation mapping. |
| Packaging | Current source plan differs from the loaded asset. | Fail the required assembly/artifact admission relationship. |
| Missing product action | Rendered buttons are internally valid but an intended eligible action is absent. | Independent capability acceptance detects the omission. |

Negative tests must fail for the intended reason, not because an unrelated
malformation prevents reaching the behavior under examination. Positive cases
must retain ordinary raw HTMX, explicit non-optimistic modes, valid retries,
full-language implementations, permitted partial observations, and useful
application-defined resolution strategies under their contracts.

Pure tests compare admitted transitions and effects; shell tests exercise actual
completion, ownership races, and failure handling; cross-host tests exercise the
portable representation; asset checks bind the shipped realization. Passing
these tests does not promote asserted callbacks, backend premises, or browser
behavior into general proofs.

Completion means the declared presentation path can execute and recover with
truthful state classifications. A page that starts, emits valid-looking markup,
or returns HTTP 200 has not thereby satisfied this part.
