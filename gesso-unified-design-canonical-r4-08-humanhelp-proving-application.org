* Part VIII — HumanHelp proving application
:PROPERTIES:
:CUSTOM_ID: part-08-humanhelp-proving-application
:PART_REVISION: 08-20261108
:END:

This part specifies a complete proving application for the contracts in Parts
I–VII. HumanHelp supplies real domain rules, authenticated users, persistent
Requests and assignments, a useful board, concurrent browsers, and recoverable
failures. It must demonstrate that the assembled path works, rather than merely
that its components can each return a successful check.

This is a normative application design. Requirements describe the system to be
built; they are not assertions that the corresponding implementation or proof
already exists. The selected product policies are stated here so that browser
behavior has an independent acceptance oracle. A remaining unresolved product
contract is identified explicitly and cannot be counted as completed.

Examples use illustrative construction and inspection notation. They do not
introduce a second public API alongside production model and Gesso contracts.
In particular, a plain map containing an operation, evidence reference, or
successful verdict is not an issued executor, admitted observation, or permit.

** Purpose, scope, and independent claims

The immediate application is the HumanHelp example UI, backed by the production
=net.humanhelp.site.model.*= models. The eventual production UI may consume the
same contracts. Its completion is a separate product milestone; the example
must not depend on that unfinished interface to supply essential behavior.

The example owns integration and presentation. It does not own a parallel Request
store, a simplified Membership policy, a substitute assignment model, or a
browser-specific interpretation of Request states. Development fixtures create
valid production entities and enter through declared initialization paths.

Three claims must be reported separately:

| Claim | HumanHelp evidence |
|-------+--------------------|
| Declared closure | One application definition connects required operations, plans, routes, providers, acquisitions, rendered actions, and recovery paths. |
| Production enforcement | Actual serving, dispatch, model invocation, transaction submission, and browser effect boundaries enforce the admitted contracts. |
| Behavioral completeness | Independent user scenarios succeed through real controls and persisted production semantics. |

An application can be closed after accidentally deleting Reassign. A model can
be correct while the browser never sends its command. A browser can display
success while no authoritative assignment exists. Each must fail the claim it
violates; none is repaired by a green result in another column.

HumanHelp is a broad reference consumer. It exercises authentication, creation,
all required lifecycle operations, selective adoption, search, sort, visibility,
details, continuity, response interaction, disconnect/reconnect, and concurrent
use. A single Claim demonstration is a necessary vertical slice, not the whole
application.

*** Generic mechanisms and application policy

Gesso supplies operation identity, projection, semantic admission, managed effect
ownership, authority and observation boundaries, scoped progression, application
closure, evidence classification, and recovery composition. HumanHelp supplies
Request eligibility, Organization and Membership policy, assignment meaning,
board ordering, and the choice to defer remote changes until Refresh.

HumanHelp failures can justify a generic improvement when they expose a reusable
missing obligation or enforcement boundary. A missing way to preserve unknown
command outcomes is such a gap. A wrong rule about who may reassign a Request
is a HumanHelp model defect. Gesso must not acquire HumanHelp business rules to
make a reference application pass.

 
*** The proving UI is the selected real application, not a parallel demo

During this integration milestone, the global =/app= entrypoint actually
selects =net.humanhelp.example.app= through the application's normal
routing and startup path. The incomplete =net.humanhelp.site= UI is *not*
another acceptance implementation and need not be finished to demonstrate
this reference application. Eventually it may consume the same production
model and Gesso contracts; its completion is independently scheduled.

The boundary is strict in both directions. Production
=net.humanhelp.site.model.request.core= and the relevant public
Organization, Membership and User model APIs own their persistent facts,
eligibility and guarded transitions. The model-owned
=net.humanhelp.site.model.request.choreo= coordinates those *public*
operations and exports semantic browser capabilities. The example
provides board/query composition, views, routes and user interactions,
but cannot invent an easier RequestAssignment schema, mutate an
example-only Request store or implement authorization in a card
component. A broken production transition is repaired in its
production owner; replacing it with a sample mutation to make
Chromium green is an invalid migration.

The physical browser participant =:helper= in the current Request
choreography is not evidence of actual helper Membership: the same
signed-in participant can display requestor and manager affordances.
Its trusted authority role, the authenticated principal, selected
target helper, physical server host and current model guard remain
distinct. Example request inputs and generated browser operation
metadata cannot supply the principal or bypass current Organization
and Membership checks.

Development fixtures bootstrap genuine production User,
Organization, Location and relevant Membership/assignment
relationships through declared model/initialization paths.
A fixed example Organization or Location used by a selected
fixture is *not* a substitute for tenant-scoped authorization
or complete production capability coverage. Tests identify
their fixture and actor assumptions, and exercise the real
public production model rather than a mock that merely returns
a plausible Request card.

** One application definition and actual installation

HumanHelp has one source-owned application definition. It composes production
model operations and choreography with concrete browser and server realizations,
physical routes, acquisition scopes, views, assets, capabilities, and the chosen
assurance policy. The constructor returns the admitted application used by
startup, rendering, dispatch, and inspection.

Tests call that constructor with explicit fixture dependencies. They do not
maintain a second operation registry or a shadow assembly. Product acceptance
remains independent: its list of required capabilities cannot be generated solely
from whatever operations happen to remain in the application definition.

 
*** Product scope must not be confused with a closed lifecycle slice

The application has multiple overlapping but nonidentical inventories.
The model-owned operation catalog identifies what the production model
can execute. The browser-plan registry identifies the lifecycle
operations currently exposed through one client projection. The
application's complete protected effect/writer scope includes
other sources such as Create, initialization and background work.
The independently selected HumanHelp product profile defines
what a *complete proving application* must make usable.

A structural checker can validly close a six-operation browser
lifecycle slice — Claim, Unclaim, mark on the way, Complete, Cancel
and Reassign — without thereby having checked Request Create,
authentication, read authorization, search, details, selectable
response interaction, all model writers or positive end-to-end
product behavior. The finished application must *compose* its
distinct Create operation and every other required protected
capability into appropriate route, trusted model, effect,
rendering and acceptance evidence. Its report states what was
included, intentionally separate or still unqualified, never
advertising a partial fragment as a fully admitted product.

The acceptance oracle is independently selected and includes
the full required-capabilities contract in 08.03, not merely the
set of current browser plan keys. Removing manager Reassign from
a plan may leave a smaller graph that passes its own checks;
that must still fail the independent product gate. Likewise
a green lifecycle preflight is not evidence that a real
Create dialog produces a persistent Request with immediate
creator-local visibility.

Late renderer resolution can break a namespace dependency cycle. It cannot allow
a renderer to escape admission or be silently replaced after its binding has
been checked. Reload creates a new candidate assembly and adopts it coherently
under Part VII.

 
Source ownership also distinguishes *public-model* calls from
private implementation reuse. Cross-model decisions use
the owning model's =*.core= API and required guarded
dependencies; the example must not reach into another
model's =domain=, =fx= or =graph= internals to create a
more convenient eligibility path. The Request Choreo
coordinates the same public operations; it cannot
embed a competing set of Organization or Membership rules.

A concrete route declares which trusted callable it actually
uses, which semantic operation it exposes, what principal and
Request selector it receives, and which physical model/
transaction and authorized acquisition follow. A view
that displays a semantic capability cannot silently
downgrade to an anonymous HTMX POST because its optimistic
basis is missing. A raw writer or alternate Ring route
outside the plan inventory remains relevant to the
protected-effect scope; a report of zero declared
uncovered writers cannot prove that actual writers are
absent.

*** A concrete construction path

The supported path performs these steps:

1. Load production definitions and explicit configuration, including the runtime
   profile, board policy, trusted capabilities, and assurance requirements.
2. Resolve the operation catalog, semantic declarations, opaque host contracts,
   choreography projections, and required acquisition/recovery continuations.
3. Derive browser plans and the manifest from that source; build the generated
   bootstrap and exact asset set under the qualified compiler/build profile.
4. Bind physical dispatch to the issued server realizations and the trusted
   context/provider mapping. Include relevant non-HTTP writers in the scope of
   the application claims.
5. Admit concrete view preparation and render boundaries, query scopes, Live
   declarations, effect implementations, and product-specific adoption policy.
6. Apply the selected structural and assurance gates, preserving unresolved
   premises and the actual scope of each result.
7. Install the admitted handler and runtime resources into the serving host;
   expose ordinary service only after the required initialization succeeds.

The serving host must actually consume the checked handler. Merely returning
one from a helper or storing it in a system map does not establish adoption by
a running server. Tests observe the installed entrypoint and exercise it.

 
The example application route selected globally, the canonical
application constructor, emitted browser artifact, guarded HTML
output and physical server startup are *joined deployment facts*.
A build script and a runtime may share a source declaration yet
load different JavaScript bytes, or a Gesso module may install
a checked =:biff.ring/handler= while an alternate server captures
a different callable. Those are distinct failed/unsupported
evidence claims, not successful application installation.

On Biff 2, all module =:init= functions can run before ordered
=:start= functions. Mandatory preflight must therefore fence
protected listener, scheduler, writer and public operation
effects even when private initialization is allowed. The
actual Aleph server must consume the admitted handler before
ordinary service; a later handler/asset/provider replacement
invalidates the affected evidence. No startup policy may
pretend a successful check rolls back a mutation that already
committed or resolves a command whose response disappeared.

Test setup and the running application use the *same*
construction owner and original production model definitions.
Controlled defects remove a real required operation,
route, provider, plan, artifact or acquisition edge and
must fail the corresponding gate. A test-only duplicate
assembly remaining green after the production constructor
breaks is not valid acceptance evidence.

*** Assurance is explicit and useful

HumanHelp uses the full host language. Pure functions, FX composition, ordinary
Clojure and ClojureScript, and opaque integration code remain available. The
application identifies the contracts on which its claims depend and proves the
parts supported by the selected semantic fragment.

The admission profile must require structural closure and the applicable issued
callable/plan bindings. For operations represented by the source-owned relational
construction, it also requires their declared invariant checks, rule exercise,
and operation/outcome coverage. Conditional induction is required where the
application claims that stronger result; a finite exploration result is not
renamed an induction theorem.

Unsupported operation semantics must be declared as opaque premises with an
owner, effect/dependency interface, and conformance obligations. The admission
policy explicitly accepts or rejects those premises for the claimed application
invariant. It must not make an incomplete model look total by omitting the opaque
operation from writer coverage.

For example, a proof of unique active primary assignment may depend on the
Request command implementation, initialization, collaborator/reassignment writers,
and the qualified transaction adapter. A theorem about the finite abstract
operation catalog alone does not establish the corresponding physical database
invariant.

The permanent executable semantic core governs admitted transitions. A proof
checker or later small proof kernel checks a specified class of proof evidence.
Neither replaces HumanHelp's transaction boundary or current authorization.

** Production model truth and public operation boundaries

A Request belongs to its production Organization and Location. Its helper
relationship is represented by production RequestAssignment semantics. The UI
must not replace those facts with a convenient =helper-id= field or infer the
whole lifecycle from whether one optional field is present.

The canonical Request states for this application are =:open=, =:claimed=,
=:on-the-way=, =:done=, and =:cancelled=. Display text such as “Completed” may
label =:done=; it must not introduce a competing persisted =:completed= state.
Public predicates and prepared projections provide state meaning to presentation.

 
*** Production aggregate, state vocabulary, and source authority

The production Request and RequestAssignment are separate persisted entities
forming one model-owned Request aggregate. A Request owns Organization,
Location, requestor, content and lifecycle identity. A primary or collaborator
RequestAssignment owns its helper, role, active/ended state, provenance and
history. An active primary assignment is not interchangeable with a
convenient =:request/helper-id= view field, a provisional label or the
browser's selected target.

The public =request.core= predicates and snapshots, not example component
conditionals, determine =:open=, =:claimed=, =:on-the-way=, =:done= and
=:cancelled= and the assignment relationships each permits. Terminal
completion and cancellation close the assignments required by the production
operation; Reassign preserves a lawful historical end of the previous
primary and creation of the new primary in one protected operation.
Collaborator writes, Request editing, initialization and Organization/
Membership changes remain within the relevant invariant/writer scope
even when this proving UI does not expose each as a dedicated control.

Use public =net.humanhelp.site.model.request.core=,
=membership.core=, =organization.core= and =user.core= semantics
for cross-model decisions. The production =request.choreo= layer
coordinates these public operations; neither it nor the example
may independently reimplement private =domain=, =fx= or =graph=
policy to win a race against the public model.

*** Atomic dependencies, not a sequence of reassuring reads

A lifecycle handler may parse inputs, authenticate, prepare context, and perform
advisory reads. The public production operation remains responsible for the
resolve-or-incorporate protocol in [[#req-atomic-authoritative-transition]].

For a new Claim, the protected dependency set includes the targeted Request,
its Organization/Location association as required by policy, the actor and
selected helper where distinct, effective Membership, Organization policy,
relevant assignment facts, and command exclusion. The ownership change,
assignment changes, command result, and required durable publication intent
are established at the declared atomic boundary.

The actual set follows the production rule. If eligibility depends on a related
entity or on the absence of another active assignment, that dependency must be
protected too. Guarding only the Request document is insufficient. Conversely,
the example should not invent unrelated dependencies merely to make a diagram
appear comprehensive.

Separate reads of Request, Membership, and Organization followed by an unguarded
write leave a race. Rechecking only the rendered card's revision leaves a race.
A transaction plan must preserve every relevant dependency through the qualified
submission mechanism, including absence or query dependencies where required.

 
*** Guard construction and physical correspondence are different claims

The admitted Claim plan has a source-relative obligation to protect
the aggregate snapshot, current operational Organization/Location
scope, selected target's active eligible Membership and relevant
role/skill assignment, and (for manager-assisted Claim) the actor's
current supervisor/administrator authority. It additionally excludes
active assignments as a *cardinality/absence* condition. The exact
dependency footprint is determined by the real model policy,
not by a hand-authored audit approximation.

Gesso's generic transaction representation may combine
=:commands= (Request/RequestAssignment mutations),
=:guards= (versioned dependency evidence),
=:assertions= (including set-level absence/cardinality)
and =:changes= (semantic changes for Live). These
are different kinds of obligations: guarding each observed
assignment is insufficient by itself when a new matching
assignment could appear. The Request aggregate concurrency
root and required relevant absence assertions must be
honored by the selected XTDB transaction semantics.

The *model planner* may have a well-formed protected plan
while the *physical backend* still requires independent
qualification for transaction-internal evaluation,
assertion atomicity, contending writers, post-commit
progression and actual submission/observation provenance.
An optional finite proof of the source-owned rule does
not authenticate every XTDB attempt. Likewise,
calling =model.tx/transact!= is not proof that unregistered
maintenance writers cannot bypass Request invariants.
The application can qualify the bounded real transaction
behavior it has observed without calling that evidence
universal linearizability or a complete-writer certificate.

The browser's previously adopted basis =X17= is an
authoritative *scoped observation frontier*, not the
Request's revision, a global snapshot of all HumanHelp
state, or an automatic stale-command veto. Unrelated
commits may advance the database while Claim remains
valid; a relevant Membership/assignment change must be
reconsidered by the model and guarded at incorporation.

*** Actor, target helper, and command identity

The authenticated principal comes from the trusted request/runtime context.
Browser fields, rendered capabilities, certificates, selected personas, and
knowledge of a UUID do not establish that principal.

A target helper can be a legitimate domain argument. Reassign requires target
selection; a production Claim variant may permit a manager to claim for another
eligible helper. That argument does not replace the actor. The model checks the
actor's authority to select the target and the target's eligibility atomically.
The basic Claim control in this proving UI means “claim for myself”; any separate
manager-assisted variant is labelled and tested as such.

Before the first possible send, the admitted command boundary supplies a stable
=:gesso/command-id= and binds it to the operation/interface, canonical arguments,
authority domain, and principal. A declared mapping may expose that value as
=:command-id= at the public model boundary. Retries preserve the binding.

The HumanHelp domain argument =:request-id= denotes a Request. Transport
correlation uses =:http-request-id= or =:transport-request-id=. Execution,
resource instance, board owner, assembly/deployment, and command identities stay
distinct. One generic “generation” field cannot stand in for all of them.

 
*** Request actor, target, scope, and trust separation

For the ordinary =:request/claim= control, *claim for myself*
binds target helper to the currently authenticated actor
within the trusted operation, not from a posted =:helper-id=.
A distinct manager-assisted Claim may legitimately supply
a different =:helper-id=, but the authoritative model must
protect both the actor's **exact** supervisor or
administrator role at the applicable Location and the
chosen target's separate helper eligibility. HumanHelp
does not grant manager authority merely by a role-name
hierarchy or by the browser using the one physical
=:helper= choreography participant.

Reassign likewise must not equate an actor's permission
to choose a target with the target's eligibility to
hold the new assignment. Relevant Organization
scope, Location, current Membership, active role
assignments and declared skills are model dependencies.
A target-helper picker can narrow options for UX;
it cannot authorize a protected transaction.

A route must reconcile the normalized path Request ID
with the semantic command's Request argument. A
separately chosen target/helper/skill cannot replace the
trusted principal or ownership context. A valid
operation capability or browser-chosen principal
identifier is inert presentation data. Public
model authorization and its current protected
dependencies determine the actual transition.

*** Resolve an existing command before applying new-command guards

A compatible repetition checks the retained command record's binding and current
permission to disclose its outcome. It returns the permitted historical result
without incorporating again. The fact that the Request is now claimed does not
justify rejecting a retry of the successful command that claimed it.

A new command must pass the current commit guard. Concurrent compatible attempts
must not both establish a new incorporation. Incompatible reuse is a typed
protocol failure. A failed physical attempt is not automatically a definitive
command rejection when another delivery of that command may still succeed.

Command retention, exclusion after result expiry, recovery across interface
versions, and disclosure after role changes follow Part IV. The browser may not
create a new identifier merely to make an unresolved operation appear retryable.
A command-recovery record and a current Request read answer different questions.

 
*** Historical incorporation requires an actual selected implementation

The complete target protocol is *resolve or incorporate*:
a trusted server obtains an authoritative record for the
original typed command binding (principal, operation,
canonical argument set, interface/authority domain and
stable command ID), verifies current disclosure rights,
and returns the recorded result when repetition is
compatible. An unresolved original command never becomes
permission to mint a fresh ID merely because a timeout
occurred or the current Request looks claimed.

For new incorporation, the command record/exclusion
and Request/RequestAssignment guarded mutations must
share the qualified atomic boundary. An existing
record must be effectively immutable for the selected
retention contract. Record expiry must not permit
duplicate logical incorporation while an old retry
can still arrive; the operation must define exclusion,
compatibility or manual reconciliation through that
lifetime. Retried transport attempts can reach another
Aleph node without changing their semantic identity.
A later current-policy or principal-role change may
forbid disclosure of a previously successful result
without reversing the historical commit.

This is a **required finished-system protocol**, not
an assertion that every current `request.core` call
already persists command ID and outcome. Current
production public Request operations expose
transaction =:commit/status= and progression; their
model transaction success is not, by itself, a
durable same-command replay certificate. Gesso's
source-level command-record helper is experimental
construction with a trusted disclosure/lookup
assumption, not an installed HumanHelp
exactly-once service. The application must connect,
qualify and test that mechanism before claiming
the stronger recovery property.

*** Outcome and presentation contracts

| Model evidence | Presentation and recovery obligation |
|----------------+--------------------------------------|
| =:committed= with permitted success evidence | Settle the bound operation as =:accepted=; install only the observations the result or a follow-up acquisition justifies. |
| =:already-incorporated= with a permitted successful recorded outcome | Use the same accepted successor without another mutation or duplicate publication intent. |
| =:rejected= with authoritative command disposition | Follow the rejection branch and permit the declared scoped reacquisition; preserve any undisclosable details. |
| =:commit-unknown= | Keep command disposition unknown and invoke the bound reconciliation path. |
| Malformed input, incompatible reuse, invalid credentials, or disclosure denial | Use its declared typed handling; do not invent a domain rejection or reveal a protected prior result. |

A replayed success is historical. It does not prove that the helper still owns
the Request after later Unclaim or Reassign. The UI may say that the command
succeeded while displaying a newer permitted card observation with a different
current assignment.

A timeout does not mean rollback. A publication failure after a known commit
does not erase that commit. The server can know =:committed= while a disconnected
browser knows only =:unknown=. A lost response is resolved with authoritative
command-specific evidence, not by guessing from a fresh card that another actor
could have produced.

 
*** Distinguish the current model API from the intended protocol layers

The present public Request operation reports
=:commit/status :committed= and, when available,
a composable authoritative =:progression=. The
current Request choreography checks that committed
result and constructs its own protocol-v3
=:confirmed= authority projection. These are
different *interfaces* from the Part IV
=:committed= / =:already-incorporated= /
=:rejected= / =:commit-unknown= command
disposition taxonomy and from the browser's
=:accepted= / =:rejected= / =:unknown=
presentation. A correct adapter preserves
the evidence required for each mapping;
matching words or a generic 200/500 response
do not supply the missing durable record.

For the initiator, a direct correlated success can
justify an explicitly scoped card acquisition or
adoption if it meets the protocol's trust and
progression requirements. A remote browser may
receive only an advisory and is not automatically
entitled to reread the board; one-user-Refresh
remains a separate grant. Validating a current
card can supersede provisional display even
while command-specific historical attribution
remains unknown.

A post-commit error in HTML generation,
publication or response delivery cannot
reinterpret the actual Request/RequestAssignment
commit as rollback. If physical storage reports
an uncertain write, neither the model nor
participant may invent a definitive rejection
until admissible authoritative evidence settles
the bound command. Recovery has a real retained
owner, trigger, authorization, progressive read,
expiration and explicit blocked/manual state
when automatic resolution is not possible.

*** Distinguish authority, delivery, and a successful browser test

A positive browser Claim test observes the generated command's exact
operation, Request argument, stable logical command identity,
execution/physical target, route and supported observed basis.
It then correlates the trusted production result and any
authoritative progression-bearing response with a permitted
card acquisition and actual installed DOM. A fresh authorized
reread or reload verifies that the Request and *primary*
RequestAssignment persist. A provisional badge alone does
not qualify success; neither does seeing a 200 response
whose body was never installed.

The first eligible claim transition changes the persisted
Request and primary assignment together. A rival new Claim
with another command cannot create a second active primary;
an open-state Request guard without the active-assignment
absence/cardinality assertion is insufficient. A model-defined
rejection for invalid current Membership or an already
claimed Request is legitimate *runtime behavior*, not
application assembly corruption.

There are three distinct settlement contexts: the public
=Request core= result with =:commit/status= and transaction
progression; the trusted current protocol-v3 optimistic
server's =:confirmed= result with a justified projection;
and the finished-system Part IV command taxonomy
=:committed=, =:already-incorporated=, =:rejected=,
=:commit-unknown= with browser =:accepted=, =:rejected=,
=:unknown=. Their mappings are explicit, not inferred
from an HTTP status or equal-sounding strings. In
particular, the present source-backed Claim route does
not establish durable historical replay of C42 merely
by generating a protocol command ID. The Part IV
same-transaction command-record/retention and
disclosure mechanism remains a separate required
implementation and qualification.

If Bob concurrently claims R17 with a different command, at most one new Claim
can establish primary ownership from the eligible open state. In a fault-free
run with both outcomes delivered, the other command receives the appropriate
authoritative rejection. When outcome delivery is deliberately lost, unknown is
a valid intermediate participant state and reconciliation is required.

If C42 commits but its response is lost, Alice's retry preserves C42 and its
binding. It does not fail solely because R17 is now claimed. If a later Reassign
has changed R17, a permitted replay can still report C42's historical success;
the fresh card must reflect the distinct current observation.

If the result response fails render validation after commit, the invalid output
is blocked. The commit remains real. Diagnostics and recovery must keep those
facts separate rather than pretending preflight rolled back the transaction.

A checked semantic certificate can justify admitting the Claim plan under its
premises. Separate evidence establishes installed dispatch and current atomic
enforcement. Returning that certificate from the browser creates no Membership,
principal, current Request state, or permission to disclose the command result.

** Board projection and selective adoption
:PROPERTIES:
:CUSTOM_ID: req-humanhelp-selective-adoption
:END:

The board separates authoritative truth from the information this browser has
adopted. A database change does not automatically change a user's visible board.
An advisory reports that the view may need attention; it is neither domain
content nor permission to fetch and install everything currently available.

The selected policy is prompt adoption of the user's own correlated results and
explicit Refresh for remote changes. Search, sorting, visibility options, and
ordinary details interaction operate on already adopted information. These
choices must be represented in application policy, not inferred from incidental
HTMX route or callback behavior.

*** Scope, cohort, and presentation

A board scope includes Organization, Location, authority context, projection
contract, temporal interpretation, and any declared collection bounds. Its
adopted cohort is the set of Request identities admitted into that scope, with
scoped observations and permitted display projections.

The default proving scope is one authorized Location and includes active and
terminal Requests within its declared collection bounds. Terminal visibility is
a presentation option. Reading only active Requests and later making “Show
terminal” issue a fresh collection query would violate that option's contract.

The profile declares finite response/retention limits. If a complete result
exceeds those limits, the server must return a typed scope-too-large result or
use an explicitly declared paging/window contract. Silent truncation cannot
justify complete membership or authoritative absence. A page covers its stated
window, not the whole Organization. Moving to another page or Location is a new
explicit acquisition intent, not a local sort operation.

Local text search and sort options do not change this authoritative collection
scope. They derive a visible subset and order from the cohort. A future remote
search feature must be labelled and specified as a different acquisition policy;
it cannot borrow the “local presentation only” guarantee.

The complete-board acquisition composes Request, assignment, and permitted User
display projections under the same qualified observation context. Repeated reads
against an advancing database are not silently treated as one snapshot. If an
integration deliberately combines observations, it preserves their separate
provenance and proves only the relationships that their evidence supports.
Current disclosure checks also remain distinct from the historical observation
being displayed.

toolbar/list may be server-rendered, but a
fragment's token does not by itself prove
the other fragment has matching membership
or counts. Any relevant change between

authorized reacquisition. Merely connecting
SSE does not establish a no-gap baseline.

A complete cohort result has an exact

read basis, finite bounds and completeness
claim. Querying Requests, assignments and
User display fields through successive
reads against an advancing database does
not prove one atomic snapshot. Either
qualify their common context or retain
the distinct provenance of every subread.

Displayed =:total-count=, =:active-count=
and =:terminal-count= refer to this
adopted cohort (or explicitly narrower
adopted visible subset), not to the
current global database. Unsupported,
incomplete, unauthorized or truncated

The rendered dialog collects editable Request content. The trusted server
resolves the authenticated production User and selected authorized
Organization/Location, not a posted requestor ID or a fixed fixture value
promoted into authority. The public
=net.humanhelp.site.model.request.core/create= operation owns content
normalization, active-user and operational-Location dependencies, command
construction and atomic Request incorporation. The reference application
may set a fixed example Location as a declared *fixture scope*, but it
must not infer tenant or Membership permission from that constant.

Model planning needs real current-time, generated-ID/seed, transaction
and XTDB capability inputs with the correct trust and lifetime. The
canonical Biff/Gesso assembly checks their required provider contracts
and actual handler adoption where knowable. A missing
=:biff.fx/now=, =:biff.fx/seed= or production commit dependency that
can be established before protected service is an admission defect,
not a surprise error after a user has filled the dialog. The exact
Biff FX provider mechanism is a physical host contract, not a
browser-supplied clock or a stand-in demo function.

Validation failure is *pre-effect*: preserve the user's submitted
title/details/location-detail, render source-owned field errors
without creating a Request, and preserve the current board and
its advisory/option state. A submit interrupted after the effect
may have occurred is *not* a validation failure. It follows the
stable command and unknown-outcome recovery contract.

On known successful creation, the user's own Request is acquired and installed
through a correlated result path. That path can adopt the new Request into the
current cohort only when it establishes the selected scope's membership
predicate and permitted display projection. An entity identity or success flag
alone is insufficient.

The response must not issue an unrestricted board query and replace the whole
list as a convenience. Such a query can reveal unrelated remote Requests that
this user has not chosen to adopt. A committed command's progression requirement
is a minimum read condition, not authorization for every observation at that
position.

*** Success while a local filter excludes the new Request

The user must receive visible confirmation without an implicit filter reset.
This design provides a “Your new Request” result area adjacent to the board when
the new card would otherwise be hidden by local options. It shows the permitted
authoritative card and explains that the current filters exclude it.

The result area offers a visible action to reveal the Request in the ordinary
list by explicitly changing the relevant local options. It does not offer an
unlabelled whole-board Refresh as if that were required to see the user's own
result. When the Request already matches the filters, it appears in the list
and the confirmation can reference that card without creating a second active
operation surface for the same logical target.

The area retains the latest completed local creation result; replacing or
closing it affects only that presentation. Prior creations remain in the adopted
cohort when eligible. A pending or unknown creation retains its independent
command recovery state and is not discarded by a later successful creation.

 
The result area has a stable, permitted installation owner and accessible
success/uncertainty message. Its “Reveal in board” action changes only
local search, ordering or terminal visibility when that is sufficient;
it does not issue an implicit new domain acquisition. When S is
actually outside the selected Location, page/window or authorization
scope, the area labels that difference and requires an explicit
navigation/new acquisition. Closing a success result cannot silently
discard S's admitted cohort membership, and rendering a second success
must not erase an earlier unresolved command's recovery reference.

The result area is a normative finished-product design choice.
The present example renders a success toast and replaces the
toolbar/list; it does not yet demonstrate a separately owned
“Your new Request” surface that remains visible when a current
search filter excludes the new Request. The positive acceptance
test must type the excluding search *before* creating S, then
verify S's committed result and visible confirmation *before*
any filter reset. A dialog closing or a “Request created”
toast alone does not prove that the filtered-out Request
is visible as a usable authoritative result.

If creation succeeds outside the current cohort's declared bounds, the result
area can still show the permitted result under its own scope. It must label the
scope difference and offer an explicit navigation/acquisition action rather
than pretending the board's membership rule admitted it.

Prompt visibility means that the confirmed result is usable after the declared
result installation completes. A provisional card before confirmation is allowed
but is visibly pending and owned by the creation execution. No toast, modal
closure, or speculative row by itself proves successful incorporation.

 
*** Commit, response, advisory and historical recovery are distinct

The production model's =:commit/status :committed= and scoped
=:progression= justify an authoritative incorporation/read
claim within their proven physical meaning. The stronger
Part IV same-command replay result, permitted historical
disclosure and browser =:accepted= presentation need
their own typed evidence. A generated Request UUID,
a visible toast or a current postcommit card does not
by itself prove the historical outcome for original
command C19.

The creator response and remote notification are separate
postcommit responsibilities. The current source intentionally
constructs the creator's response before calling
=send-new-request-advisory-best-effort!=, excludes the
authenticated creator from the other-client broadcast,
and logs advisory fanout failure without changing
committed authority into an HTTP rejection. This is a
valuable concrete prevention of false retries *when
response construction succeeds*.

There are additional histories to qualify. If Request
incorporation succeeds but creator-response rendering
throws before the advisory helper is called, the mutation
is still committed, neither creator installation nor remote
advisory delivery is established, and the participant
needs correlated recovery. If the response was constructed
but transport or OOB installation fails, the server
cannot infer that the creator saw S. If advisory delivery
fails after response construction, the creator's success
need not be revoked, but the other participants'
notification/reconnect obligations must have a declared
durable or otherwise honestly weaker recovery policy.
The existing best-effort log is not evidence of universal
eventual remote delivery.

An application with reliable postcommit delivery
records the necessary publication intent and
command recovery debt under the selected atomicity/
retention premise. It must not claim two-phase
commit or cross-client exactly-once effects merely
because a single Node/XTDB transaction was
committed. Retried Create with the original
stable binding is resolved before re-incorporation;
an unqualified implementation without such
deduplication keeps the outcome uncertain and
does not blindly regenerate S.

*** Worked example: remote R and local S

Bob has adopted board observation Q17. Alice creates Request R. Bob then creates
Request S. Both are eligible for the same board collection; Bob's text filter
matches R but not S. P18 and P19 below name provider-issued positions with the
specified coverage judgments, not numbers the browser is allowed to compare.

|------+-------------------------------------------+----------------------|
| Baseline Q17 is installed. | The baseline cohort only. | None established; subscription continuity must also be justified. |

| Bob searches or changes sort options. | Only the baseline cohort is presented differently; R stays absent. | The remote obligation remains. |

The test must assert S's visibility before changing the excluding filter. Clearing
search first would hide the product failure this scenario is intended to detect.
It must also wait for observable advisory delivery before asserting continued
absence of R, so that an assertion made before the remote event cannot pass
vacuously.

 
The test also checks Bob's pre-Refresh cohort identity and current
local options, one permitted Create result for S, requestor identity,
production persisted Request state, retained pending R obligation,
and physical installation of the dedicated S result area. A card
for R appearing merely because the Create success response queried
all new Requests is a failure, even if R's contents are accurate.
If the R advisory arrives after S's result, the absence requirement
is still meaningful; the test explicitly synchronizes that
notification and verifies that S's local result did not
consume it retroactively.

The R4 example is a *logical history*, not an instruction to compare
the decimal portions of P18 and P19. The provider defines which
basis/coverage statements may be composed. Local search and sort
must not silently query the newest database as a workaround.

*** Correlation is narrower than global adoption

A command result can justify updating its affected card and, where declared,
selectively adding/removing a member. It does not adopt every Request mentioned
in an unrelated response, every row from an incidental reread, or every change
before its progression position.

 
*** A correlated result is narrower than a recomputed board

For an admitted creator-local insertion, the settled result identifies
the newly committed Request and its original command/execution binding.
The trusted authority establishes its requestor and scope, the relevant
transaction/progression and a permitted Request/assignment/User display
projection. A successful HTTP status or submitted title alone does not
justify that new member or its physical DOM.

The implementation may acquire a single affected Request/card with
sufficient progression, or install the admitted complete result of a
separately granted board acquisition. It may *not* reuse Create success
as permission for an unrestricted =requests-for-location= reread
whose resulting toolbar/list quietly imports remote Requests that
the user had not chosen to adopt. A committed basis P19 can justify
the creator's S read while membership for unrelated R remains Q17.

The current HumanHelp example takes a meaningful but **different**
path: =example.app/create-request!= calls production
=request.core/create=, composes its committed progression,
then =create-request-success-response= recomputes
=board-fragments= and returns toolbar/list OOB replacements
through =views/create-request-success=. This demonstrates
production-backed read-your-writes and a visible successful
Create response in selected HTTP integration tests. It
does **not** independently establish selective *single-member*
adoption: the fresh whole-board query can include an unrelated
remote R. The target design must introduce admitted selective
membership or a separately authorized full-board grant,
rather than labelling the existing response as complete
compliance.

A board fragment and toolbar may need different membership/count
evidence. A newer card for S does not make the toolbar's total,
open count or other cards current. The UI reports a mixed
cohort truthfully and preserves any pending remote advisory.

Advisory debt is discharged by the relevant observation and installation scope.
The application cannot clear “Updates available” simply because it received a
newer local result. Two obligations with different scopes or required stages may
need different evidence even when their provider positions are comparable.

** Remote lifecycle adoption policy
:PROPERTIES:
:CUSTOM_ID: decision-humanhelp-remote-lifecycle-adoption
:END:

Selected policy: remote creation and remote lifecycle changes both require
explicit board Refresh for ordinary domain-content adoption. This includes
changes to Requests already visible. An advisory may update the pending indicator
and explanatory status; it does not silently replace a card or its cohort.

This policy is intentionally separate from two permitted local continuations:

- The user's own accepted command may install its declared affected-card/result
  observation and selective membership effect.
- A rejected or uncertain local command may invoke its declared scoped recovery
  read. That read can reveal current state of the affected Request, even when
  another actor caused it. It cannot import unrelated collection members or
  automatically resolve the uncertain command's attribution.

An old displayed Claim button can therefore remain visible after another helper
claims the Request. Clicking it is safe only because the public model enforces
current authority. The resulting rejection and affected-card acquisition explain
the conflict. An advisory may say the view has updates, but must not infer the
winner or current domain state from advisory payload alone.

Authentication loss, explicit scope change, and an established loss of disclosure
rights are separate context transitions. They retire incompatible execution and
installation rights and remove protected projections where the supported client
can do so. They are not delayed merely to preserve a board Refresh preference.
No application can retract information already disclosed to an untrusted or
offline browser; the enforceable guarantee is current checks at subsequent
trusted disclosures and mutations, plus the declared supported-client behavior.

 
*** R4's open lifecycle policy is now an explicit R5.1 decision

R4 settled remote Create as advisory-only but deliberately left
remote *lifecycle* adoption open. R5.1 selects a stricter HumanHelp
product policy: remote Claim, Unclaim, On-the-way, Complete, Cancel
and Reassign are also advisory until a user's explicit Refresh.
The choice is a normative end-state requirement, not a statement
that existing Live invalidation already satisfies it.

The present =example.live/compiled-live= excludes =:created=
from managed toolbar/list invalidation but still routes =:updated=
changes into both managed fragments. Gesso can then cause
automatic authoritative rereads and replacement. Thus the
current implementation does **not** establish the final
advisory-only policy for remote lifecycle updates.
HumanHelp must change the application routing/adoption
contract while preserving semantic change publication
for local command resolution and permitted recovery.

A remote change to an already visible T must not reveal
its new helper, terminal status or Request content through
a supposedly advisory payload. A stale Claim button
remains subject to current Request guards. A rejected
or uncertain local command may independently acquire the
affected T to explain conflict, without silently importing
other Requests. Authentication loss or established revoked
read rights are different trusted safety transitions:
they retire forbidden projections and mutation permissions
rather than waiting for optional Refresh. Previously
disclosed bytes in an untrusted/offline browser cannot
be retrospectively erased.

** Explicit Refresh, coverage, and races
:PROPERTIES:
:CUSTOM_ID: req-humanhelp-refresh-coverage
:END:

A Refresh click creates a grant for one logical acquisition of the current board
scope and authority context. It captures the outstanding requirements and the
current non-regression obligations. Its lifetime ends on completion, failure,
expiry, owner retirement, or incompatible scope/context change.

The default has one acquisition and no automatic successor read. It can obtain
a complete current query result that includes changes beyond the captured
requirements. Installation can discharge any current obligation covered by that
actual result within the grant's scope. It does not authorize a second read just
because another advisory arrived.

A new explicit Refresh or Retry can create a new grant. While a cycle is active,
additional clicks are coalesced into at most one user-authorized successor intent
with current captured requirements; they do not create an unbounded queue. A
pending indicator alone never creates that intent. The UI reports whether it is
refreshing, waiting for another explicit action, or unable to refresh.

 
*** Refresh permission and current implementation scope

A single user gesture creates a bounded grant with an
authenticated principal, current Location/collection scope,
board owner and deployment generation, captured requirements,
physical target, expiry and permitted *one logical* query.
The trusted server checks its authority independently of
browser-supplied scope, basis, client stamp or form values.
A malformed/impossible progression token must be rejected
or boundedly deferred, not force an indefinite query wait.
Advisory arrival is not a new read permission.

A second real click while a query runs can authorize at
most one successor intent; neither an automatic retry
nor a duplicate wakeup may create an unlimited queue.
Expired, incompatible or cancelled grants preserve
unresolved advisory debt and allow an explicitly
admitted retry.

The current =example.views/refresh-form= renders an HTMX
POST with =hx-include= of board-state form inputs.
=example.app/refresh-requests!= calls the production-backed
=board-fragments= and returns toolbar/list OOB updates.
That establishes a concrete, user-triggered board query,
but the inspected route does not show a one-use grant,
captured requirement ledger, admitted response owner
or completed physical installation certificate.
A refresh button plus HTTP 200 is not sufficient evidence
of the stronger R5.1 protocol.

A deployment may choose a bounded automatic repair/drain policy instead, but that
is an explicit product-policy change with its own budgets, expiry, and acceptance
cases. It is not an adapter optimization invisible to the user contract.

*** Acquisition and adoption are separate stages

1. Register the cycle, transport identity, scope, target owner, and requirements
   before physical dispatch.
2. Authenticate the actual read and validate the query/progression input under
   the qualified provider contract. A hostile or impossible token must not force
   an unbounded wait.
3. Acquire a projection with evidence of actual observation, completeness, and
   applicable authority context. Echoing the requested minimum does not prove
   the read met it.
4. Admit installation against the current owner, target instances, grant, scope,
   compatibility, and non-regression requirements.
5. Perform the qualified physical replacement/merge and report completion.
6. Record adoption and discharge only obligations satisfied at their required
   stage. Render current local options over the newly adopted cohort.

HTTP completion, response receipt, a proposed swap, or a backend read alone does
not complete stage 6. If installation fails, acquired evidence may remain useful
but the adoption/repair obligation remains visible.

Toolbar counts, list membership, cards, and board evidence must refer to the
same declared installation or explicitly identified partial result. The primary
full-board path renders one coherent board projection and coordinates its
affected surfaces as one adoption batch. Where HTMX performs several physical
mutations, admission is checked before the protected work and completion tracks
each required effect; multi-fragment delivery is not claimed to be DOM-atomic.
A partial failure leaves the batch incomplete, prevents a false “up to date”
claim, and exposes repair without rolling back a newer independently admitted
card. Re-fetching toolbar and list independently cannot manufacture a coherent
board observation merely because both responses arrived successfully.

 
*** HTMX OOB output has distinct completion stages

With =hx-swap="none"=, a response may still change
toolbar, list, board-state and advisory targets through
individual out-of-band effects. The coordinator must
validate the planned complete board and current resource
ownership before the effects, observe each required
physical installation, preserve compatible current
search/options and only then mark the batch adopted.

If the toolbar swaps but the request-list target is
absent, HTTP receipt is not a coherent refresh.
The application records a partial batch, retains
unsatisfied advisory/repair requirements, and does
not discard a newer locally installed S card.
If one component needs a separately scoped
acquisition, the result is labelled *partial*
rather than falsely presenting a common snapshot.

The current =example.live/request-toolbar-query=
sets =:pending-open-count 0= and =:stale? false=.
Those are presentation defaults, not evidence
that a later advisory was covered or that OOB
installation completed. Replacing the advisory
surface with non-stale markup cannot itself
consume a read grant or discharge a semantic
Refresh obligation.

*** Race rules

The default allows a non-regressing complete-query advance even when a stronger
remote advisory remains outstanding. This is partial satisfaction of current
debt, not partial or fabricated completeness of the query result. The remaining
advisory stays visible for a later user action.

| Race or failure | Required result |
|-----------------+-----------------|
| A later advisory arrives during a Refresh. | Preserve it; clear it only if the actual installed observation covers it. |
| The read covers the captured obligation but not the later one. | Adopt the non-regressing result and retain the later obligation; no automatic successor without a grant. |
| A qualified read also covers the later obligation. | Discharge both after successful installation within the permitted scope. |
| A local Create/Claim result is installed while an older board read is in flight. | Recheck the incoming board result against the newer local observation/membership obligations; do not overwrite or remove the justified local result. |
| An older result cannot establish safe replacement. | Decline that installation, preserve the local result and debt, and expose Refresh/Retry. A separately admitted selective merge needs its own coverage argument. |
| A stronger result arrives from a retired request or board owner. | Reject its installation rights; stronger progression does not revive a retired resource. |
| A read succeeds but physical installation fails. | Preserve remaining adoption debt and a usable retry path. |
| Local search/options change during the read. | Install into the same acquisition scope if still valid, then apply the current local options; do not restore obsolete options from the response. |
| Organization, Location, page/window, or authority context changes. | Retire or explicitly transition the owner; the old response cannot populate the new scope. |
| A command remains unresolved when a board refresh completes. | Update permitted presentation without claiming the command succeeded or failed solely from current card state. |

A full-board replacement must not regress any retained observation whose scope
it supersedes. If proof of safe replacement is unavailable, the default rejects
that replacement and requires a new acquisition. It does not silently union an
old complete result with arbitrary newer rows and call the union a complete
snapshot. A mixed selective projection can be valid, but must retain its mixed
provenance and must not claim snapshot-wide properties.

 
*** Opaque progression and notification delivery premises

Generic Gesso progression bases are opaque. A trusted
XTDB/provider relation, not integer comparison,
HTTP arrival order or the latest visible token,
establishes whether a read actually covers a
captured or subsequently arriving requirement.
An affected-card observation may advance one
subject while the board cohort remains older.
The same user action can legitimately satisfy
more than one obligation if the *one* authorized
read and completed adoption cover each; a
later advisory never creates a second read grant.

HumanHelp's separate app-owned creation advisory
uses =client-plumbing= to queue non-adopting
Refresh OOB/toast presentation to connected
clients other than the creator. Gesso
=live.client= owns finite ephemeral pending
mailboxes, including disconnected-client
overflow and drop policies. This mechanism
does not prove durable eventual delivery
through disconnection, queue overflow,
multi-node failover or a missed subscription.
A stronger product guarantee needs
source-owned reconnect/fence/replay or
authorized reacquisition. Without it the
system must expose the weaker contract,
not report a permanently silent stream
as current board knowledge.

The notification is a wakeup, not the
authoritative current Request state,
a sufficient current disclosure capability,
or a count of unseen new Requests.
A durable command record and a board
Refresh are separate recovery subjects.

*** Membership removal and authoritative absence

An authoritative query result can remove a cohort member only with the required
coverage and current installation rights. A filtered-out row, a failed read,
missing markup, or an empty partial page is not evidence of domain deletion.
Terminal filtering hides =:done= and =:cancelled= in the default view without
removing their admitted cohort membership.

If an affected-card read establishes that a Request has left the authorized
scope, the UI follows the declared non-disclosing absence/unavailability branch.
It must not reveal whether an inaccessible entity was deleted, moved, or made
private unless policy permits that distinction. Such a read still does not
resolve a prior command's attribution without command evidence.

Pending provisional presence has a resolution owner. It cannot survive every
complete authoritative observation indefinitely, and it cannot disappear with
its command-recovery record merely because a DOM row was removed. Part VI's
separate rules for presentation supersession and command uncertainty apply.

** Search, ordering, visibility, and local state

The ordinary board presenter is a pure function of the adopted permitted
projection, normalized local options, and the current authenticated-viewer
projection. Its DOM realization is an admitted effect. Presentation does not
re-evaluate production write authorization and does not manufacture observations.

Search uses a declared shared normalization contract: trim the input, apply the
selected case normalization, and perform substring matching against the prepared
search text. The contract specifies the supported character behavior and is
checked on both host runtimes where both implement it. Search text comes from
already disclosed Request title, details, location description, and explicitly
permitted displayed labels. New private fields cannot become searchable merely
because they are present in a production document.

The empty search matches the adopted cohort. No match means no visible adopted
row matches; it does not assert that the database has no matching Request.

 
*** The adopted-cohort search contract and its current realization

The search index is an *already authorized projection*, not a
second Request model and not a backdoor query. For each current
viewer the index may contain only approved display/search
fields from the admitted Request, RequestAssignment and
User projections. Whether a field is drawn visibly or only
used to decide matches does not change its disclosure
classification: a match against an otherwise undisclosed

*** Ordering is a single explicit key

“Mine” means requested by the authenticated viewer or assigned to that viewer
as active primary helper. It is a presentation category, not permission to act.
The prepared projection supplies these facts from the production models. A missing
viewer ID must not make two absent identifiers compare as “mine”.

When both priority options are enabled, mine-first is the primary grouping and
unclaimed-first is the secondary grouping. Creation time then uses the selected
newest/oldest direction, with canonical Request identity as the deterministic tie
breaker. The UI makes this priority order apparent.

An illustrative key over prepared display rows is:

#+begin_src clojure
(defn board-sort-key [row options]
  [(if (and (:mine-first? options) (:viewer-related? row)) 0 1)
   (if (and (:unclaimed-first? options) (:open-unassigned? row)) 0 1)
   (case (:created-order options)
     :oldest (:created-order-key row)
     :newest (:reverse-created-order-key row))
   (:canonical-request-order-key row)])
#+end_src

The temporal order keys are prepared under the declared portable ordering
contract; the example does not assume arbitrary host timestamps are negatable
JavaScript numbers. Unknown order options are rejected or normalized through the
explicit option schema before this function runs. A malformed creation time is
a projection error, not silently the Unix epoch.

 
The current Clojure presenter derives an epoch
millisecond value only for a Java =Instant=;
=instant-epoch-milli= returns =0= for a
malformed/missing temporal value, and
=created-sort-value= negates a valid epoch
for newest-first. This is a bounded
implementation detail of the current JVM
board, **not** a portable browser sort
contract or compliant malformed-data
diagnostic. The finished projection
validates the declared source timestamp,
constructs comparable portable newest/
oldest keys without overflow or host
representation assumptions, and preserves
the Request-ID tie breaker. Zero is a
legitimate date coordinate in some
representations, not a safe error sentinel.

“Unclaimed” is a model-derived open/unassigned category. A terminal Request with
no active assignment does not become unclaimed. Multiple independent sort passes
must not accidentally change which option is primary.

 
The current =example.board/row-sort-key=
conditionally constructs a lexicographic
vector of mine-first, unclaimed-first,
creation key and Request ID; this is
a sound source-level direction.
The product must still test *both*
priority flags together, exact ties,
missing authenticated viewer,
and valid terminal/open assignment
distinctions. An absent viewer must
never match an absent requestor or
assignment ID. For ordinary board
sorting, "mine" is a production-backed
viewer relationship; it does not
authorize Claim, Reassign, details
or protected reads. "Unclaimed"
requires the model's actual open/
unassigned meaning, not simply
the absence of an active helper

Order of transformations is declared:
authorized adopted cohort, terminal
visibility, local search, primary/
secondary sort groups, temporal key,
canonical identity. A filter does
not mutate adopted cohort membership;
a changed order does not grant
new authoritative read permission.

*** Durable publication strategy

The primary application profile records publication intent atomically with the
command's authoritative transition and result. A durable worker publishes that
intent and records its progress under a declared at-least-once policy. Its work
identity remains stable across retry; receivers tolerate duplicate advisories.

A crash after commit and before publication therefore leaves recoverable work.
The worker's authority, ownership/lease, restart behavior, retry limits and
backoff, dead-letter/escalation state, and retention are explicit profile
contracts. A retryable delivery failure cannot create another domain Claim.
If the worker is unavailable, the UI can still recover current state through an
authorized Refresh under the declared liveness assumptions.

A deployment that instead relies on periodic reconciliation or user-initiated
Refresh must declare that weaker publication recovery policy and test it. Merely
registering a post-commit callback does not establish recovery after process loss.
The application must not claim durable delivery if its selected backend/profile
cannot atomically retain the required intent.

** Optimistic presentation and command recovery

HumanHelp's Claim, Unclaim, Mark on the way, Complete, Cancel, and Reassign
remain source-owned production Request operations whether their presentation
is optimistic, explicitly non-optimistic, or unavailable. A provisional card
is participant knowledge, never an authorization decision, transaction
witness, command verdict, or new authoritative Request fact. The production
model owns its guarded transition; Gesso owns portable command and execution
semantics and physical effect admission; the assembled HumanHelp application
owns available user-facing presentations and recovery paths.

*** Prepared operation, authority, and provisional basis

Each enabled managed lifecycle control requires its real semantic operation,
typed arguments, Request identity, applicable plan/artifact, qualified
observed basis, physical target/transport, and matching trusted server route.
When its provisional trajectory cannot be prepared, the application selects
only an explicitly admitted non-optimistic realization, a disabled/unavailable
control with acquisition/explanation, or checked rendering failure. Missing
optimistic basis never causes an anonymous ordinary =hx-post= to the same
protected route or erases the operation identity.

An available Claim control is not authoritative permission. The trusted
executor authenticates the current principal and rechecks production
Request/RequestAssignment, Membership, Organization and other relevant guards.
A browser-provided command, target ID, CSS class, authorization-looking card,
wall-clock timestamp or document revision cannot fabricate a qualified XTDB
observation or grant authority. An observed basis is scoped to what was
actually established; it does not imply a universal order of all facts.

*** Distinct command, execution, transport and physical ownership

One user intention has stable semantic command identity C42 and exact binding
to its operation, arguments, subject and trusted principal. Local execution
E42, HTMX attempt H1, target instance T1, provisional generation G1, callback,
timer, listener, and recovery resource are distinct identities. Compatible
retransmission H2 of C42 must not silently become a new C43. A genuinely new
user intention may have a new command ID only through its own admission,
not merely because the previous request timed out.

The browser admits semantic state before issuing effects. The physical
shell registers each provisional installation, timer, network continuation,
rollback handle and callback to its current owning execution, target instance
and generation. It checks effect admission before actuation, not merely at
promise completion. HTMX event and settlement correlation uses the actual
issued execution/transport, not changing DOM position or a copied command
string. Retirement removes the obsolete effect's authority even if the
original HTTP request subsequently completes.

A decoded response, HTTP 200, generic =afterSwap=, OOB update, or completed
provisional DOM installation is not command-specific authoritative
incorporation. Real target-specific physical completion establishes that
an effect was installed; its provisional nature persists until qualified
authoritative adoption or safe compensating rollback.

*** Pending state, rollback and supersession

Pending transport, awaiting authoritative settlement, installed provisional
presentation, command-outcome unknown, known rejection, historical
incorporation, and adopted current Request truth are distinct statuses.
While an execution owns pending presentation, the card exposes an accessible
nonterminal pending indicator and guards against duplicate user submission.
It does not claim terminal success before its promised authoritative
confirmation. Semantic retirement removes the old spinner's ownership; an
independent visible unknown-command recovery affordance may persist.

A rollback may restore only the exact legitimate pre-provisional structural
baseline while its semantic right, physical target identity, installation
generation and continuity ownership remain current. It may not replace a
newer authorized card, undo another successful action, reintroduce a
retired provisional owner, or restore a Request no longer disclosed to
the viewer. Restoring the provisional DOM of E1 as if it were canonical
after E2 fails is forbidden. A snapshot of such DOM may be used solely to
compensate the immediately failed physical installation, not as a terminal
semantic rollback baseline.

If rollback is unsafe, missing, or superseded, the runtime preserves honest
provisional/uncertain status and requests permitted authoritative acquisition
or exposes a repair action. It cannot silently strip a provisional marker
to make physically orphaned DOM appear authoritative. A later justified
installation of T2 revokes the old T1/G1 restore rights; a late E1 failure
cannot overwrite T2. A stale callback can be ignored or diagnosed without
falsely claiming the old semantic command was rejected.

Independent operations may overlap under an application-declared
commutativity/dependency policy. Dependent operations are ordered, deferred,
or rejected under their admitted semantic plan. Retirement or supersession
of one presentation owner does not automatically settle the historical
command of another. Local card adoption also does not erase unrelated
remote advisory evidence or one-use Refresh debt under the HumanHelp
selective-adoption policy.

*** Command-specific outcome versus current Request truth

The trusted server distinguishes what happened to C42 from what is currently
true of R17. A selected durable-command profile records the exact command
binding and admitted historical outcome under its declared transaction,
unique-ID, consistency and retention requirements, coupled atomically with
the domain transition when the profile promises atomic incorporation.
Lookup and replay require authenticated identity, current permission to
disclose the record, exact binding comparison, and a qualified authoritative
read. No browser command ID, protocol shape, or archived receipt grants
that permission by itself.

The recovery decision distinguishes:
- disclosed, binding-exact historical incorporation and its recorded outcome;
- properly supported authoritative rejection and its actual provenance;
- incompatible or undisclosable binding/result;
- no matching record under a precisely qualified lookup/retention scope;
- still-unknown transport, transaction or observation outcome.

An absent record from a partial, lagging, unauthorized or expired lookup
does not prove the command did not commit. Even a complete read is interpreted
against record lifetime and any possible in-flight original submission.
The client cannot convert an unknown C42 into a new C43 merely to retry it.
Reissuing C42 requires the declared idempotent, exclusion-checked protocol
and current admission; otherwise the participant reconciles or truthfully
reports uncertainty. A duplicate exact C42 may return the historical
authorized outcome without executing Claim again; a changed operation,
principal, Request or arguments is incompatible.

A fresh permitted Request read can correct the visible R17 card even while
C42's history remains unresolved. Conversely, a disclosed incorporated C42
does not say R17 is *still* assigned to the same helper: a later authorized
operation may have changed it. Historical attribution and current card
presentation therefore have separate acquisition and adoption obligations.
A newer locally adopted card does not imply permission to adopt unrelated
remote Request membership or dismiss outstanding Refresh debt.

*** Recovery across retirement, reload and evidence expiry

An uncertain command transfers to a declared recovery owner before its
provisional physical owner is retired. The recovery contract states how
a minimally sufficient command receipt or authenticated server-side
recovery index survives navigation, reload, crash, compatible deployment
and loss of the original target. No suspended old execution, callback or
browser artifact resumes merely because C42 remains recoverable. The
recovery owner is distinct from the original card and may continue after
the card is filtered out or physically replaced.

Browser storage, if used, contains only limited, context-bound recovery
references; it is not a second source of business truth or a credential.
Sensitive command arguments, historical outcome and even tenant-scoped
Request existence remain subject to current trusted disclosure checks.
Logout, principal change, policy revocation or missing local storage does
not imply rejection. Where the profile cannot recover a lost receipt,
it reports that limit rather than inventing a historical answer.

Automatic retries/reconciliation obey a declared bound on attempts,
time, work, rate and retention; after exhausting the budget the user
receives an actionable, accessible recovery explanation. Beyond the
supported record/discovery horizon the correct answer may be
"historical outcome no longer determinable", not "rejected".
Any promised eventual resolution identifies the durable storage,
backend qualification, fairness, availability and disclosure premises
on which its liveness depends.

alternate response helpers, error views, redirects and OOB payloads.

the qualified profile. A cached fragment is revalidated against
the currently served assembly and recipient policy when required;
a stored "checked" marker from a different generation is not an
unrestricted permit.

Out-of-band updates and multi-target installations have actual
target identities and completion reports. A valid response before
serialization does not prove every requested DOM effect occurred.
Partial OOB completion retains its specific recovery obligations.
A committed Request mutation is not reversed by a later failed

the handler after preflight. Application preflight rejects a missing

connected SSE subscriptions, one-use Refresh permissions and

authorization to adopt remote Request state.

recovery state; it must not expose an accidental mixture while

to request- and execution-scoped ownership. A global one-use lease
that serializes every HumanHelp write is not a valid substitute for
per-command exclusion, per-Request conflict resolution or qualified
XTDB atomicity. An intentionally narrow single-request test profile
does not certify the real multi-client service.

Backend qualification follows [[#req-backend-assumption-qualification]].
HumanHelp must establish the required atomic guard/write and
RequestAssignment uniqueness behavior, exact-binding command
exclusion/observation, query completeness and authoritative absence
where claimed, post-commit outcome and visibility guarantees, and
the effect of concurrent writers. The evidence has precise
version/configuration, source and physical execution scope; it is
not a proof of all XTDB behavior. A changed backend assumption
invalidates dependent certification until it is requalified.

This section describes the finished-system test obligation, not a

** Semantic model, proof obligations, and conformance evidence

The HumanHelp proving application must make its actual production Request
rules precise enough for Gesso to assemble, evaluate, challenge and, for
supported propositions, prove or check. This is not a second HumanHelp
domain language maintained in =example.*= and not a requirement that an
application author write TLA+, Quint, Recife or proof scripts. The
source-owned Request model defines the business meaning; Gesso derives
admissible semantic subjects and checking obligations from it and from
explicit, typed dependency and effect contracts.

A correct model of the wrong policy is still a wrong application. The
independent HumanHelp product contract therefore remains an external
acceptance oracle for required operations, permissions, assignment
semantics, user-visible behavior and adverse outcomes. Neither model
generation nor executor agreement with that same source can prove the
source expresses the intended HumanHelp rule. Conversely, a product
test cannot by itself prove all legal traces or complete physical
writer correspondence.

*** Production ownership and the checked semantic subject

The protected aggregate comprises Request and its separate
RequestAssignment history, scoped to Organization and Location and
dependent on User, Membership and Organization-owned authority.
Request's public model boundary owns domain transitions and outcomes;
its graph/FX implementations own the actual relevant dependency
acquisition, guarded planning and authoritative transaction assembly.
Request Choreo binds the *public* operations and their distributed
presentations without reimplementing Claim, Unclaim, Mark on the way,
Complete, Cancel or Reassign eligibility in the browser or example UI.

The Gesso semantic subject identifies the original production source
and version, declared state and relationship types, operations,
actor/target arguments, transition constructors, frames, observable
outcomes, initial-state predicates, invariant propositions,
external dependencies and explicitly opaque host effects. A
projection of these declarations into a finite transition system is
not a second editable operation registry. A changed source, effect
footprint, model policy, schema or dependency invalidates the
applicability of evidence derived from its former identity.

There are independent closure questions:

| Question | Required evidence |
|----------+-------------------|
| Is the declared model well formed? | Typed, closed source and effect/role/transition construction for the selected language |
| Does the model capture intended HumanHelp behavior? | Independently supplied positive and negative product requirements, including policies not inferred from current UI exposure |
| Does the abstract machine preserve its claims? | Exact finite exploration or a separately checked initialization/preservation derivation under its admitted assumptions |
| Does issued Clojure execution correspond? | Original-source-to-executor binding, admitted input/frame/guard correspondence, with opaque portions named |
| Does actual XTDB/host execution refine that model? | Qualified transaction, readback, actual writer/guard and state-representation evidence with temporal and trust scope |
| Does the running browser/app exhibit required behavior? | Installed route, generated artifact, real HTMX/DOM and authoritative outcome evidence, plus independent user-level acceptance |

No one row is silently inferred from another. Structural admission, finite
model checking, conditional induction, runtime guard enforcement,
observed physical agreement and end-to-end conformance are distinct
judgments, not a numeric ladder whose higher rung automatically proves
all lower ones.

*** HumanHelp invariant and obligation families

The admitted Request application declares at least these property
families, with ownership, scope, assumptions and counterexample
conditions visible:

| Property family | Precise intended contract |
|-----------------+---------------------------|
| Entity and relationship validity | The public Request, RequestAssignment, Organization/Location, Membership and User references obey their declared entity schemas and qualified referential rules; valid IDs alone do not establish the existence or eligibility of referenced facts |
| Primary assignment uniqueness | For a Request there is *at most one* active primary RequestAssignment under the declared aggregate semantics; permitted collaborators are not counted as additional primary helpers |
| State/assignment correspondence | A Request in the relevant assigned states has the required active primary assignment; Unclaim, Complete and Cancel close or retain assignments according to their actual model transitions, not a UI status guess |
| Command eligibility | A new Claim/Reassign/other command passes the current trusted actor, Request state, Organization/Location and helper Membership/role/skill requirements when the protected transition commits |
| Guarded aggregate atomicity | Request and affected assignment writes, exclusion/absence checks and dependency versions either commit together or leave no partially admitted new aggregate state |
| Transition/frame safety | Each operation changes only the admitted Request/assignment and declared associated fields/effects, preserving unaffected facts unless the model explicitly permits them to change |
| Command exclusion and historical result | Exact-binding replay cannot reincorporate; incompatible reuse cannot mutate or disclose another command's outcome; unknown delivery cannot be reclassified by local timeout |
| Read, absence and disclosure | A read's scope and completeness, authoritative basis, access policy and interpretation of missing entities justify only the observation actually obtained |
| Local and remote knowledge | Creator-local correlated adoption and remote advisory/one-use Refresh obey their distinct permissions; an unrelated remote row does not become locally adopted by association |
| Browser/physical ownership | Retired E42, target T1, subscriptions and provisional generations cannot actuate protected effects, restore obsolete DOM or discharge independent command/Refresh obligations |
| Source and writer coverage | Every declared model writer and physically reachable protected writer is classified and either covered under the selected assurance policy or explicitly open/unsupported |

The *at most one* primary assignment rule does not by itself prove
that every claimed Request has one; the latter is a separate existence
and state-correspondence obligation. The existence/uniqueness of an
active primary must also be distinguished from historic or collaborator
assignments. An action's protected prestate may contain Request R17
and a complete guarded absence of active primary assignment; a
snapshot of one returned assignment alone is not such an absence
proof unless the query and exclusion contract establish completeness.

A helper's current Membership eligibility is normally a
*commit-time precondition*, not automatically a permanent invariant.
If Membership expires after a valid Claim, the policy must choose
whether the old assignment remains historically valid, becomes
operationally ineffective, or triggers a model-owned reassignment
or revocation. The proof must not assert that every existing
assignment is presently eligible while omitting Membership
revocation, Organization policy changes, Location moves, User
deactivation, administrative edits and external writers. Such
operations either preserve the claimed invariant, perform a
specified repair transition, or remain explicit premises of a
properly narrower result. Live publication cannot repair
a violated database invariant.

*** Closure, induction and cross-model interference

For an invariant I and the named admitted transition relation T,
the ordinary abstract safety obligation has the shape:

#+begin_example
Initial(s) => I(s)

I(s) and T(s, operation, s') => I(s')
  for every admitted operation and its required environment step
#+end_example

The initial condition includes more than "the test database was
seeded without errors": it identifies permitted initial Request,
assignment and dependency configurations, including legal empty
states, and why real initialization/legacy import reaches them.
An induction argument must show preservation by *every member*
of the complete relevant transition catalog; checking Claim alone
cannot certify Unclaim, Reassign, policy changes or a background
assignment writer. For a nonclosed environment the claim remains
conditional on an explicit interference assumption. A source-bound
catalog report is not proof that no undeclared physical mutation path
exists.

Guarded transition generation is required to expose actual read
dependencies and protected write footprints. If an Organization
policy or Membership predicate is implemented by an opaque Clojure
function or backed by a query with an unproven exclusion guarantee,
the abstract argument records that premise. It must not replace
the function with a hand-authored conveniently matching predicate
and describe the agreement as implementation correspondence.

Application-defined transition preservation includes concurrent
interference: two helpers competing for the same R17; manager
Reassign racing Membership revocation; Complete/Cancel racing an
assignment change; initialization/import racing ordinary claims;
and non-Choreo mutations affecting the same protected relation.
The chosen qualified XTDB guard/transaction semantics must exclude
forbidden joint outcomes at the physical boundary. A proof of serial
atomic *reference* steps does not establish that the deployed
backend executes only those steps.

A conditional inductive result identifies its original source,
proposition, initial-state coverage, per-operation proof
dependencies, explicit environmental assumptions and independent
checking mechanism. A report copied from another assembly, a
digest with matching text, or an in-process admission handle alone
does not discharge the higher-level physical/assumption obligations.

*** Finite state families and non-vacuous exploration

Finite exploration exercises a deliberately bounded subset of
the HumanHelp state and command space. Required example families
include:

- two eligible helpers contending for one open Request and a third
  authorized actor attempting a later Reassign;
- two distinct Organizations/Locations, permitted and forbidden
  cross-scope reads, and incompatible actor/target-helper identities;
- active, expired, absent and role/skill-ineligible Membership,
  including changed policy between preparation and submission;
- Request states =:open=, =:claimed=, =:on-the-way=,
  =:done= and =:cancelled= with active, ended and historic primary
  and collaborator assignments;
- Claim, Unclaim, Mark on the way, Complete, Cancel, Reassign and
  Create, including invalid attempts and valid eligible positives;
- unique C42/C43 commands, compatible duplicate C42, incompatible
  command rebinding, lost settlement and post-commit uncertainty;
- local Create S after remote unadopted R, with local selective
  adoption and outstanding Refresh debt;
- source and host changes that alter dependencies, writer sets,
  application generation and read/disclosure permission.

Not all families must form one giant Cartesian product. Small
independently checked families are legitimate when each obligation
identifies its own state universe, command/actor/argument domains,
initializers, number of attempts, bounds, checker configuration,
transition-preparation strategy, coverage and omitted interference.
If a stronger joined claim requires interaction between families,
that composition itself needs a checked or explicitly assumed
argument. A prepared-plan permutation explores precomputed
choices against a selected initial state; it is not equivalent to
rebuilding every operation after each successor state. A
state-dependent reachable checker must cover changing enablement
where the obligation relies on it.

Non-vacuity is an admission requirement. For each required
independent capability there is an actual eligible source state,
a successful attempt, a meaningful denied/current-policy attempt
and the applicable retry/concurrency branch under the selected
scope. A universally true invariant over a model in which no
Request can be created or no Claim is ever enabled does not meet
the HumanHelp capability contract. A source rule never matched by
any selected state is reported unexercised, not silently checked.
Removing Reassign from both the production declaration and the
derived formal subject still fails the independently specified
HumanHelp positive capability gate.

Where finite search finds a counterexample, the report exposes
the smallest available typed, reproducible operation/state trace
under the selected model and its assumptions, without disclosing
protected tenant facts to a browser. Finiteness and lack of a
counterexample mean only "none in this checked subject"; they
do not establish an unbounded theorem, a sound compiler, or an
XTDB/HTMX physical result.

*** Host functions, proof premises and policy adequacy

Supported pure Clojure rules, typed operations and finite data
constructors may be interpreted or translated for model checking,
provided the transformation's semantic-preservation argument is
visible. Opaque predicates, callbacks, time providers, database
queries, serializers and side effects participate only through
declared contracts. Sample tests of a function and its printable
name do not prove its behavior for all admissible states.

Host/FX capabilities are explicit inputs, not hidden powers.
Current authenticated principal, current time, transaction
identity, random/seed generation, external provider results and
authoritative observation are separate premises. Trusted runtime
validation can establish concrete input/output schemas, exact
command binding, observed version, permitted read or verified
effect call at a named boundary; it cannot prove the function
unconditionally pure, the backend fully serializable or the
external world compliant. If the selected assurance policy
requires a stronger contract than the chosen host can supply,
the protected operation is not certified/admitted under that
policy; it is not granted a fictitious weaker proof.

Independent policy adequacy is illustrated by Reassign: a
generated transition and its executor may agree while omitting
the essential authorized target-helper selection, or while
misinterpreting collaborator history as primary ownership.
The separate product oracle must reject that deficient design.
A model with only the presently rendered Claim action also fails
independent Unclaim, Mark on the way, Complete, Cancel and
Reassign requirements even if the reduced machine is internally
consistent.

*** Actual execution and refinement evidence

An abstract successor and a trusted XTDB transition are different
objects. Source-to-physical correspondence requires a declared
representation relation between abstract Request/assignment/
dependency state and actual stored documents, plus evidence for
the guard/prestate seen at the *transaction boundary*. A read
taken before submission and a post-commit document read are not
automatically the transaction's internal prestate and successor.
Command-record readback, transaction ID, externally supplied
status and displayed outcome must retain their precise provenance
and trust scopes.

A meaningful observed-step report correlates at least:
- the admitted source, operation, typed arguments and exact
  issued executor/route/actor binding;
- the selected initial/abstract state and qualified physical
  prestate, including relevant checked absences and dependency
  versions;
- the actual submitted guard/write footprint and backend
  transaction identity or a clearly delimited observation gap;
- qualified incorporation, rejection or unresolved submission
  outcome with separately disclosed command-specific evidence;
- the relevant complete/partial poststate read, basis and observed
  representation relation;
- the actual independently observed physical writer and
  installed host/asset generation where the claimed scope
  includes them.

These are not automatically one adjacent execution history.
A caller may supply a sequence of individually matching states
from unrelated XTDB snapshots. The checker must establish the
needed chronology, exclusivity/interference frame, correlated
transition lineage and observation completeness before claiming
a particular path refinement. A successful read of a complete
canonical command record following one submitted write is useful
bounded co-observation; it does not, without stronger origin
proof, establish the identity of every writer or that this
command caused the observed state.

Protected physical writer coverage includes real HTTP handlers,
public model calls, raw XTDB access, initialization, repair,
imports, background work, external processes and privileged
administrative paths. A host-observed list of registered writers
is evidence about that *enumerator* and its inspected runtime;
it is not by itself evidence that the enumerator saw every
process, that all write capabilities are restricted, or that
the deployed router uses the checked handler. Unknown inventory
is an open coverage obligation, never an empty set by default.

A qualified backend can establish particular guard/write,
unique-primary, command-exclusion, query/absence, progression
and visibility properties for its named XTDB version and
configuration. Version or configuration changes reopen affected
obligations. This is not a claim that one integration test
proves all physical XTDB executions or every database behavior.

*** Assurance report and joined acceptance

The HumanHelp assurance explanation reports each precise
proposition with its subject, source identities, checked
transition families, observed operation coverage, writer
inventory scope, evidence mechanism, proof dependencies,
versioned physical assumptions, untested cases, applicability
and status. It separates a verified finite statement, a
conditional abstract theorem, an enforced runtime guard, a
bounded concrete observation, an opaque host assertion and
an independently exercised product requirement. An unadmitted
candidate, copyable ledger or structural handle is never itself
a release certificate or grant of transaction authority.

#+begin_example
Positive — competing Claim under a qualified guard:
  A and B are eligible for open R17 with no primary helper.
  Both submit through the real guarded production operation.
  The finite semantic subject forbids two new active primaries.
  A qualified backend test forces an actual conflicting
  guarded submission; at most one is incorporated.
  The other receives its actual supported outcome.
  Fresh Request/assignment reads agree with that result.
#+end_example

#+begin_example
Adversarial — missing Membership revocation writer:
  The abstract Claim-only catalog preserves a predicate
  that every active primary helper is currently eligible.
  Membership is revoked through a real administrative path.
  The property no longer follows. The plan must cover that
  writer and repair transition, narrow the proposition or
  retain an explicit external assumption; "checked" is not
  a valid full-application answer.
#+end_example

#+begin_example
Adversarial — false physical trace stitching:
  A test reads prestate P, executes another actor's command,
  then supplies a later unrelated snapshot Q and a copied
  C42 result label to a comparison checker.
  Agreement of isolated values is not transaction causality
  or a contiguous trace without the required lineage.
#+end_example

#+begin_example
Adversarial — vacuous operation catalog:
  An implementation deletes Reassign and its formal plan.
  Every remaining checked transition preserves uniqueness.
  The independent product oracle still requires an eligible
  Reassign and rejects the deficient application.
#+end_example

Concrete HumanHelp acceptance includes (1) positive Request
creation and each required lifecycle operation through public
model semantics, (2) invalid actor/target and competing-state
rejections, (3) relevant Membership/Organization/Location and
other writer interference, (4) compatible/incompatible command
replay and truthful unknown delivery, (5) qualified real XTDB
guard/assignment/readback evidence, (6) application and browser
installation/continuity/advisory evidence, and (7) explicit
assumption and coverage-failure rejection cases. Part VIII's
following test architecture states how these are exercised.
Part IX owns compositional certificate policy, Part X the
stronger proof-kernel/refinement and physical correspondence
arguments. Their open work is not preemptively declared done
by this sectional review.

** Test architecture and oracles

HumanHelp is a proving application only if its tests exercise the real
production Request models and the actual Gesso/HTMX/Biff/XTDB realization.
The test architecture is a collection of independently meaningful
judgments, not one green build, a second hand-authored application, or an
unqualified claim that a rendered page proves a database invariant. The
accepted requirements describe the finished Gesso/HumanHelp system even
where existing test suites provide only a narrower precursor.

*** Independent test layers and evidence owners

| Layer | What it establishes | What it cannot silently establish |
|-------+---------------------+-----------------------------------|
| Production domain and model | Request/RequestAssignment schemas, current actors and targets, Organization/Membership dependencies, exact lifecycle rules, guards and outcome classes | Real browser command construction or a fully qualified installed XTDB writer boundary |
| Projected choreography and semantic machine | Typed role-local plans, knowledge/continuations, provisional/status ownership, finite or inductive propositions with declared state/operation coverage | Correct business intent, arbitrary opaque host callbacks or actual deployed physical effects |
| Qualified XTDB/FX integration | Actual guarded Request/assignment transaction, relevant dependency/absence assertions, returned progression and persisted readback under the tested backend configuration | Every writer, unbounded concurrent schedules, genuine browser-to-command binding, or all XTDB configurations |
| Application assembly and rendered output | Real source-owned operation/route/Live/browser closure; concrete effective HTMX/native-form requests; fail-closed diagnostics | That this exact handler or JavaScript artifact was physically installed or that a protected request committed |
| Physical adapter and browser conformance | Real HTMX/SSE/DOM event behavior, effect ownership, continuity, output/swap and failure paths against admitted transitions | HumanHelp product policy or trusted current Request authorization |
| Installed host and publication | Actual Biff/Aleph startup, checked Ring handler, current asset bytes and dependency/provider lifecycle, including denied/stale startup | Correctness of all outside writers or all future rolling deployments |
| Real-browser product acceptance | A genuine logged-in user can complete required HumanHelp tasks through rendered controls and sees the correct settled, authorized result | Universal formal safety, all temporal traces or complete external-system qualification |

A useful test names the exact operation, source/application generation,
actor and target, provider/version assumptions, reachable starting
state, injected fault if any, real enforcement boundary, authoritative
postcondition and expected diagnostics. Results retain which parts
were genuinely observed, constructed, assumed or untested. The same
test should not use a private mock to produce both the behavior under
test and the supposedly independent oracle.

*** Valid fixtures and independent product requirements

Normal fixtures establish real public User, Organization, Location,
Membership, Request and RequestAssignment facts through the selected
public production model and admitted initialization path. They bind
distinct actor, requestor, helper, candidate target and manager
identities to genuine authentication/session contexts; generated
UUIDs, a crafted =:session :uid= map, or browser identity fields alone
do not demonstrate authentication. Fixtures preserve actual
progression/transaction receipts and test each authorized read at
its intended scope. Deliberately malformed database state may be
introduced only for an explicitly labeled corruption/rejection test;
it must not become the conveniently seeded positive case.

The independent product oracle requires Create, Claim, Unclaim, Mark on
the way, Complete, Cancel and Reassign, with a genuinely eligible
positive for each and meaningful negative/changed-policy cases.
Search, board sorting and terminal options, remote advisory-only
presentation, one-use explicit Refresh, selective creator-local
adoption, details/continuity, reconnect and the independently selected
response-flow behavior are separate requirements. Removing a required
capability from both the production catalog and its generated tests
does not make the product complete. Required positives must not be
satisfied only by constructing a disabled action or by a mock
executor that always reports rejection.

A test can use isolated public-model seams to investigate a narrow
Request aggregate, provided it calls the result a *seam-qualified*
test and separately tests real Organization/Membership persistence,
concurrency and disclosure at the relevant connected boundary.
One invalid foreign-model stub cannot be used to certify the entire
authenticated HumanHelp application.

*** Browser-originated Claim and lifecycle acceptance

The installed product test launches the supported generated Gesso
browser artifact, authenticates a real test principal, navigates to
the actual served =/app= page and locates the real eligible Claim
control. It clicks the control as the user would. The actual browser
runtime, not test code, constructs its protocol-v3 command, local
execution identity and HTMX request; the trusted route binds that
command to Claim and the selected Request. Production Request
model/FX commits the real guarded transition, the response carries
truthful settlement/progression, and current authoritative
acquisition and physical completion install the settled card.
A fresh reload and independent model read establish persisted
Request and primary assignment truth.

#+begin_example
Claim positive oracle:
  authenticated helper A -> served Claim(R17) control
  real browser -> semantic command C42, transport H1
  actual checked HTTP route -> public Request Claim
  qualified XTDB guards + Request/assignment writes
  authoritative outcome + permitted readback
  physically installed settled card -> page reload
  public Request/RequestAssignment query agrees with the result
#+end_example

A server unit test may deliberately manufacture a well-formed wire
command to test trusted decoding or Request routing; it cannot
be counted as this browser-originated positive. Likewise page
evaluation must not call the private lifecycle executor, inject
=__gesso_live_optimistic_command=, swap a prebuilt success body,
or silently replace the generated client with a test implementation
that already knows the expected outcome. Observation-only browser
instrumentation and controlled network faults are legitimate when
they do not supply the missing action, settlement or authority.

Every exposed lifecycle operation repeats the appropriate installed
control-to-model-to-physical-result path with the real operation
identity and necessary user input. Reassign must include a legitimate
target-helper choice and must preserve the production transition's
actual Request state and assignment history; it is not another
Claim with a different label. Unclaim returns to the model-defined
open state and ends the selected primary participation; Mark on the
way establishes =:on-the-way=; Complete and Cancel establish
=:done= and =:cancelled= respectively with their specified
assignment closure and terminal visibility. Each eligible positive
is accompanied by appropriate policy denial, malformed-binding,
stale-state and replay cases. A terminal Request cannot regain an
enabled Claim merely because its display row has no active helper.

The oracle is not "DOM contains Claimed" or "HTTP was 200":
it checks the transaction-related Request/assignment facts from a
qualified fresh read, exact current actor/target, the committed
operation's semantic outcome, authorized user-visible settlement,
absence of obsolete provisional presentation, and persistence
after reload. A response-render error after a valid commit is
not retroactive domain rejection. Unexpected page/console errors,
failed HTTP requests, missing command, absent model mutation,
unhandled asynchronous errors and mismatched artifacts fail the
scenario rather than being swallowed by the green status.

*** Deterministic concurrency, causality and negative knowledge

Two Playwright clicks at nearly the same time are a useful user
experience test, not proof that two XTDB transitions competed over
the same protected prestate. The backend test uses a controlled
barrier after both real contenders have acquired the relevant
preparation/guard snapshot and before their submitted guarded
effects become mutually ordered, under the named backend profile.
It confirms both reached the intended contested boundary and
that at most one incompatible new primary is incorporated. It
checks the losing request's actually delivered model outcome,
rather than assuming all losing transports must report a
particular HTTP code. If the barrier changes the guard mechanism
or prevents the tested real submission, its result cannot
qualify the physical concurrence claim.

An authorized manager Reassign racing target Membership revocation,
a simultaneous Complete and reassignment, and compatible/
incompatible C42 replay are separate concurrency or command tests.
Atomicity and non-partial result must be read from the actual
persisted Request and assignment set, not from an in-memory
precomputed transaction plan or the last browser card alone.

Negative assertions need a completed, causal observation window.
For example, to establish that remote R was not automatically
adopted, the test first observes R's committed authority and
that the intended already-connected B received the relevant
advisory (or qualified gap/debt). It then records B's adopted
membership and monitors the actual forbidden acquisition and
installation paths until a defined synchronization milestone.
A momentary count of zero before B receives any event cannot
show the policy was respected. A single sleep cannot exhaust
all possible late callbacks; deterministic adapter exploration
and instrumented physical events cover the specified schedules.
Claims beyond the observed window retain a liveness or fairness
premise, never an invented absence proof.

Positive outcome delivery and unknown delivery have distinct test
branches. A competing Claim with healthy confirmed transport
must produce the supported definitive delivered outcome; a
controlled lost response after submission may legitimately leave
C42 unknown. A current claimed card cannot attribute the exact
historical command. Each fault case documents precisely which
transaction outcome is observed, which is uncertain, and which
subsequent authorized command-specific recovery is permitted.

The selected HumanHelp policy is **remote advisory without automatic

| Scenario | Required user and physical outcome |
|----------+------------------------------------|
| Initial page | Genuine authenticated principal, authorized cohort/scope, meaningful defaults, correct generated asset and honest initial subscription/observation coverage |
| Create ordinary | Creator's confirmed R appears promptly; a separate already-connected viewer gets advisory/toast/Refresh signal but not auto-adoption |
| Create under excluding filter | Creator sees authorized local result/confirmation while search/options and prior adopted cohort remain unchanged |
| Remote R, then creator-local S | S is selectively adopted for the actor; remote R remains outside that actor's adopted cohort and its advisory debt persists |
| One-use Refresh | An explicit permitted click triggers one corresponding authoritative acquisition/adoption; duplicate/synthetic triggers do not acquire extra membership |
| Advisory during Refresh | A later uncovered advisory remains outstanding after earlier captured requirement returns |
| Local result races older Refresh | Old board/fragment response cannot remove or regress a newer justified card or newer local membership |
| Read succeeds but swap fails | Adoption and notification debt are not falsely cleared; visible repair remains available |
| Scope-limited/empty/error response | No invented complete absence, removed authorized rows or resolved unknown command |
| Search/options after remote advisory | Only adopted entries change local presentation; no implicit server-side collection requery or debt discharge under the selected contract |
| Newest/oldest, mine-first and unclaimed-first | Actual stable order: mine-first primary, unclaimed-first secondary, creation order then identity tie breaker |
| Terminal visibility | =:done= and =:cancelled= are hidden/shown within adopted membership without changing database state |
| Details/focus/scroll | Compatible same-identity replacement preserves declared continuity; target retirement or lost read permission cannot resurrect private DOM |
| Rapid input, stale callbacks | Later local edits and justified installations dominate stale search/option/continuity callbacks |
| Remote lifecycle change to visible R | Existing adopted R fields remain until the specified user-approved Refresh or authorized actor-specific read |
| SSE disconnect/reconnect | Lost interest/coverage is reported and recovered within the selected mechanism; reconnect never silently grants remote adoption |
| Duplicate/retired events | No duplicate protected effect, obsolete target resurrection or foreign recipient disclosure |
| Response flow | The independent response interaction product contract must be selected and passed; an unresolved decision remains an acceptance blocker |

All remote/local cases use at least two independently authenticated
browser contexts, preferably distinct principals, with independently
verified sessions, permission scopes and actual network connections.
A pair of pages sharing one mutable auth fixture is not enough.
Cross-Organization and cross-Location tests challenge both payload
disclosure and metadata/count/interest leakage. The test distinguishes
a user-local option from a server-side query change: where a
new authoritative collection query is actually required, it needs
its own authorization and scoped read/adoption permission; it
cannot be smuggled in as mere presentation search.

*** Fault, recovery and environmental qualification

| Fault or changed premise | Required evidence and safe result |
|--------------------------+-----------------------------------|
| Failure before actual submission | No new authoritative effect; typed local failure and permitted new admission |
| Submission with lost result | C42 remains unknown until exact authorized command-specific evidence; current card read alone cannot attribute C42 |
| Known commit, failed rendering/transport | Persistent transition remains; invalid output blocked and actor has qualified acquisition/recovery |
| Crash after commit before Live publish | Transaction-coupled durable publication intent or the explicitly chosen tested alternative closes the declared recovery path |
| Live delivery gap or reconnect | Interest/grant fencing, scope and basis recovery; no accidental automatic adoption |
| Result lookup denied/expired | No protected disclosure; denial/retention expiry is not evidence of rejection |
| Fragment read timeout/partial/error | No invented complete authoritative absence, and no false Refresh-debt discharge |
| Partially installed OOB/multi-target response | Per-target physical completion and repair rights; no claimed atomic multi-target adoption |
| Older network/optimistic callback | Retired E42/T1 cannot overwrite newer justified installation or restart old plan |
| Deployment A to B while client A persists | Matching assets/compatible protocol or declared reload/retirement; no mixed-generation actuation |
| Wrong installed Biff handler or receipt | No protected service with unsupported assembly; paired valid startup still succeeds |
| Membership/Organization change in flight | Proper current guards, read/disclosure revocation and usable permitted recovery |
| Unknown/extra physical writer | Coverage obligation remains open; it cannot borrow the declared operation's proof |
| Changed XTDB/HTMX/compiler qualification | Dependent proposition requalified, blocked or honestly reported unsupported, never silently left certified |

Fault injection records the exact boundary and ordering: before send,
after send/before transaction, after commit/before response, after
commit/before publication, read-success/swap-failure, owner retirement
and browser reload. It must not replace a real backend/handler with a
fake transition while claiming physical refinement. Fault-free tests
must not tolerate synthetic unknown outcomes; fault tests must not
convert unknown to rejection. Automatic retry budgets, retention
horizons, user recovery affordances and resource cleanup are
separately observed.

Unexpected console/page/network failures and unrelated non-2xx
responses fail the test. The fixture may accept an *expected* typed
fault only in the case that injected it, with exact operation/subject,
first enforcing boundary, permitted outcome and current poststate.
Blanket suppression of 4xx/5xx, all timeouts, or all exceptions
would conceal a broken product path. Negative cases pair with
a valid, eligible positive so "reject everything" cannot pass.

*** Evidence ledger, suite composition and completion

The finished HumanHelp acceptance report connects the real
production assembly, generated browser manifest/build receipt,
physically served asset, authenticated sessions, rendered controls,
browser-created commands, installed Ring route/handler, XTDB
transaction/readback evidence, actual SSE/HTMX/OOB effect events,
current adopted frontier and independent product outcomes. Each
reference has its source, version, trust boundary, observation
scope and limitations. It must not use a copy of one green
preflight result as evidence of all these independent edges.

The suite reports distinct statuses for domain/model, bounded
semantic checking, backend qualification, declared and actual
writer coverage, structural/render rejection, installed-host
adoption, real browser lifecycle, full two-client board/Refresh,
failure/reconnect, and independent response-flow requirements.
A partial pass is reported as partial. A missing positive
capability, unqualified real writer, untested physical join, or
still-unselected response-flow contract prevents full HumanHelp
product acceptance, even when every available test passes.

A future strengthened Gesso checker can produce more of the
required oracles automatically from one source-owned application,
but it cannot silently generate the independent HumanHelp
business intent or prove physical causality from unchecked
report-shaped maps. Part IX owns compositional certification;
Part X owns the proof/refinement correspondence conditions.
Section 08.13 details deterministic structural rejection,
while 08.14–08.15 join deployment evidence and final
acceptance gates. Their work remains open until demonstrated,
not declared complete by this section.
** Structural rejection and production enforcement

Controlled defects are introduced before admission or at an explicitly tested
runtime replacement boundary. A copied inspection report is not a credential;
associating new values into a report must not manufacture a current application.
Each negative case has a paired valid path through the same enforcing boundary.

| Defect | Required enforcing boundary and evidence |
|--------+-------------------------------------------|
| Unknown semantic operation in a view | Preparation/construction rejects it with operation and source context; no fuzzy execution. |
| Missing required browser plan | Assembly rejects the missing realization edge; no ordinary HTMX fallback. |
| Missing physical route | Closure reports the required transport and unresolved dispatch binding. |
| Route bound to a different operation/executor | Construction or installed-dispatch guard rejects the mismatch before the prohibited model invocation. |
| Missing trusted capability | Construction rejects a statically known omission; runtime capability failure follows its typed path without unauthorized submission. |
| Missing initial acquisition or recovery path | Admission rejects the incomplete managed scope even though it cannot predict whether a future dynamic failure occurs. |
| Enabled render lacks basis required by its selected plan | Concrete preparation/render rejects it; it cannot drop semantic identity. |
| Anonymous action on a lifecycle route | Actual served-output guard rejects it and identifies the semantic route collision. |
| Stale manifest or wrong asset bytes | Build/startup/serving rejects the mismatched subject under the selected receipt contract. |
| Forged build labels without qualified production | The application does not accept copied labels as compiler correspondence. |
| Malformed command protocol or forbidden actor field | Trusted input boundary rejects it before mutation, with the exact selected typed outcome. |
| Browser advisory used as an installation grant | Coordinator/effect admission rejects the unauthorized read or adoption. |
| Retired target, request, or continuity slot | Final effect admission denies the stale physical act. |
| Handler checked but a different handler installed | Host adoption evidence fails; a green constructor report cannot satisfy the gate. |
| Unclassified relevant writer | The applicable coverage claim is blocked or retains the explicit accepted premise; the writer does not disappear from the report. |
| Required user capability removed from an otherwise closed assembly | Independent acceptance fails. |

Diagnostics use stable structured fields for category, subject, source location,
expected/actual binding where safe, and first enforcing boundary. Tests assert
those fields rather than depending only on an English exception-message regex.
Diagnostics redact credentials, protected content, and complete command payloads
unless the relevant diagnostic audience is explicitly authorized.

Static preflight need not predict dynamic facts. It must still require declared
handling and recovery paths for dynamic conditions that can strand an operation:
unknown outcome, failed acquisition, denied disclosure, lost subscription,
obsolete plan, exhausted retry budget, and unavailable provider. A structurally
valid “send” with no permitted continuation after uncertain delivery is incomplete.

** Connected evidence and operational limits

At least the Claim, Create/selective-adoption, Reassign, and explicit-Refresh
journeys retain connected evidence of their actual boundaries. A report links:

- canonical application/source and assembly/deployment identities;
- prepared operation and rendered control, browser plan and actual asset identity;
- registered execution/resource instances and physical transport correlation;
- installed route and issued server realization;
- trusted actor/context and relevant provider contracts, with protected data redacted;
- authoritative command outcome, publication/recovery intent where applicable;
- scoped acquired observation, installation permission, physical completion,
  adopted evidence, and remaining obligations;
- claim classification, test/model scope, and unresolved or accepted premises.

The references come from the canonical construction and observed execution.
A second hand-maintained table of operation IDs is not an evidence chain. Nor
is a list of success-shaped maps without a trustworthy relationship to the
actual callables, transactions, and physical effects.

Absence of an unexpected error is useful but insufficient. The report also
establishes the expected command, authoritative transition, or visible adoption.
For a rejection case it establishes the absence of the prohibited effect at the
relevant boundary; it must not claim that a later output guard undid an earlier
valid commit.

Safety and progress are reported separately. Correct rejection of an old response
is a safety result. Eventual convergence requires the stated availability,
qualification, scheduling, retention, and user-action premises. Under explicit
Refresh policy, a user who never refreshes is allowed to retain an older board.
The application must still make the pending condition and recovery action clear.

*** Resource limits and cleanup

The profile bounds active acquisitions/installations, coalesced successor intent,
physical remnants after failed abort, pending effect resources, retained command
recovery references, local drafts, and projection size. It defines compaction or
backpressure for advisory debt without claiming that one scheduling slot bounds
the information in all unresolved obligations.

Cleanup revokes semantic rights before disposing physical resources. Timer,
subscription, and request cleanup is idempotent under duplicate completion and
partial failure. Removing a component cannot erase the only owner of an unresolved
command or publication intent.

The final application has no parallel demo store, alternate revision counter used
as authoritative progression, duplicate operation registry, anonymous lifecycle
fallback, or obsolete compatibility path that contradicts the admitted contract.
Source changes and removals remain traceable through repository history and the
relevant replacement rationale. This is a design requirement for a coherent
application, not a migration checklist embedded in the product specification.

runtime profile. Passing gates for a subset is reported as that subset; an open
product contract or unqualified backend assumption cannot be hidden by a green
aggregate label.

** HumanHelp proving-application invariant

The HumanHelp example is a useful application of production model truth. It has
one admitted construction, an actual installed realization, and independently
specified user capabilities. Its browser controls preserve semantic identity;
its trusted operations enforce current authority and atomic dependencies; its
command outcomes distinguish historical incorporation, rejection, and uncertainty.

The creator can see a correlated confirmed Request promptly without adopting
unrelated remote work. Remote creation and lifecycle changes remain advisory
until explicit Refresh, except for separately admitted local-result/recovery
scopes. Search, sort, visibility, and continuity operate on permitted adopted
information. Refresh records adoption only after safe physical installation and
discharges only the obligations that its actual scope and evidence cover.

Application claims remain proportional to their evidence. Executable semantics,
conditional proofs, backend qualification, installed-path enforcement, and real
browser acceptance support different conclusions. HumanHelp must make their
connections concrete while preserving the assumptions and limits of each.
