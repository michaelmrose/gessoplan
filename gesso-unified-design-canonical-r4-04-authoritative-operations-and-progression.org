* Part IV — Authoritative operations and progression
:PROPERTIES:
:CUSTOM_ID: part-04-authoritative-operations-and-progression
:PART_REVISION: 04-20261107
:END:

This part defines the public model boundary, authoritative construction and
execution, command disposition, durable propagation, and scoped acquisition of
authoritative state. It connects the assurance classifications of Part I, the
identity and evidence model of Part II, and the operation contracts of Part III.
Browser coordination follows in Part VI; whole-application closure follows in
Part VII.

The central requirement is that the operation which an application admits, the
transition which it submits, and the outcome which it reports describe the same
semantic act. A well-typed declaration alone cannot establish that relationship.
Neither can a successful HTTP response, a copied certificate, a local callback
return, or an independently observed database state.

Ordinary full-language Clojure remains available under the
[[#req-full-language-construction][checked construction contract]]. Gesso proves
what its admitted semantics and evidence support, identifies what remains an
assertion or environmental premise, and preserves those distinctions through
execution. An opaque implementation is not silently treated as proved, and a
restricted proof mechanism does not define the limits of the application
language.

The declarations and API names below are illustrative specifications. They do
not claim that the exact displayed functions are already implemented. Inspection
maps explain admitted objects; constructing a similar map does not create an
execution capability or authoritative evidence. Example identifiers denote
separately bound fixture values unless a literal is supplied.

** Model integration
:PROPERTIES:
:CUSTOM_ID: req-model-public-boundary
:END:

Application models own domain truth. HumanHelp supplies the running examples,
but Membership, Organization policy, and Request lifecycle rules remain
HumanHelp semantics rather than special cases in Gesso.

A model may organize its implementation as follows:

| Namespace | Responsibility |
|-----------+----------------|
| =request.domain= | Business predicates and pure transitions. |
| =request.schema= | Public value schemas and private persistence representations. |
| =request.graph= | Relationships and declared graph/query semantics. |
| =request.fx= | Acquisition, preparation, and authoritative effect realization. |
| =request.core= | Narrow public semantic interface. |
| =request.choreo= | Distributed programs consuming public model interfaces. |

The layout is conventional; the dependency rule is normative. Public =core=
operations may use their model's internals. Choreography consumes public =core=
interfaces and does not reach through them into private domain, graph, schema,
or FX implementation. A model's =core= does not facade its choreography.

For example:

#+begin_src clojure
(ns net.humanhelp.site.model.request.choreo
  (:require
   [gesso.choreo.core :as choreo]
   [net.humanhelp.site.model.request.core :as request]))

;; The authoritative participant invokes a public model operation.
;; trusted-context is supplied by that participant's admitted runtime.
(choreo/at :request-authority
  (request/claim! trusted-context claim-command))
#+end_src

This is not permission for the browser to supply =trusted-context=, nor for the
choreography to call =request.fx= directly.

*** Placement and semantic ownership

The placement test is whether a rule still matters when the model operation is
called synchronously from one JVM, without a browser or distributed protocol.
Claim eligibility, current authorization, valid state transitions, command
deduplication promised by the model, and atomicity normally pass that test.
Browser optimism, role participation, transport retries, projected execution
lifetime, and presentation settlement normally belong above the model.

Some information crosses this boundary because it has an independent model
meaning. A stable command ID can be a public model input because durable replay
requires it. An expected domain version can be a public precondition. Neither
requires the model to know a tab's execution ID or HTMX swap policy.

Choreography may consume a public business judgment; it must not reimplement a
slightly different Claim policy. A view may suppress a button as a convenience,
but that suppression does not establish permission to commit. Conversely,
business policy must not exist only inside choreography while =core= remains a
pass-through to unconstrained writes.

Cross-model calls use public semantic interfaces. When Request depends on
Membership and Organization, their models expose the necessary facts,
predicates, and composable authoritative obligations through those interfaces.
They need not expose private storage paths. A coordinating operation may then
protect the combined obligations in one transaction.

A cross-model public interface must make its *semantic commitment*
inspectable without disclosing the consulted model's private storage
or implementation. For a condition needed by another model's
authoritative transition, this includes its logical subject and
parameters, relevant trusted principal/authority, declared read
dependencies, and the point at which the condition must hold.
An admitted implementation may supply a data-level obligation,
a qualified guard constructor, or a trusted callback bound to that
public contract. Merely naming =:membership/active= in an operation
manifest does not establish that its actual guard is installed.

A successful preliminary Membership or Organization read is evidence
of that observation at its qualified basis, not automatically proof
that its predicate still holds when a later Request Claim commits.
Where Claim promises atomic enforcement of combined eligibility,
the authoritative operation must compose the relevant model-owned
conditions into the *actual protected decision* using qualified
transaction-current guards, assertions, or an equivalently justified
backend mechanism. A stability premise may replace such a guard only
when separately admitted for the precise interval and scope; an
unchecked preflight Boolean or caller-supplied `authorized?` cannot.
If the chosen backend cannot protect the promised combined condition,
report the missing enforcement/correspondence obligation or weaken
the *declared* atomic guarantee explicitly; do not silently accept
a race.

| Cross-model construction | Required judgment |
|--------------------------+-------------------|
| Request Claim composes Request state, current Membership eligibility, and Organization policy at one admitted authoritative incorporation boundary | Permit the operation under its declared backend and trusted-guard premises; keep the originating public rule owners distinct |
| A prior Membership read returned =:active=, but Membership was revoked before the Claim commit | The stale read alone cannot authorize incorporation; enforce the current guarded condition or retain the explicitly qualified stability premise |
| A browser or choreography sends ={:claim-allowed? true}= and the transaction uses that value in place of current model guards | Reject the attempted authority substitution, regardless of input shape |
| A coordinating operation uses admitted public constraints from two models without importing either model's private FX or XTDB schema | Permit composition where the declared atomic backend contract and cross-model dependencies are actually satisfied |
| The backend cannot enforce the promised joint invariant, but an assembly report infers safety from two separately successful reads | Do not certify the joint transition; report an open or failed physical obligation at the correct boundary |

The rule and its source owner remain the same in a single application
process or across several web nodes sharing one qualified logical
authority. Multi-node routing and propagation can change which host
learns about a change or when it can observe a sufficient basis;
they cannot introduce a second Claim policy or substitute a stale
host-local authorization cache for transaction-current enforcement.


A workflow spanning peer models should live at the level that owns the workflow.
An onboarding flow coordinating Invitation, Membership, Organization, and
external provisioning need not belong to Invitation merely because it starts
there. Semantic dependency also does not dictate a literal namespace load order.
Contracts may be represented separately to avoid circular implementation loads.

*** Public interfaces expose commitments, not implementation privilege

A public operation interface must expose enough information for a caller and
the assembly checker to establish:

- the semantic operation and interface version;
- input and outcome schemas, including closed semantic discriminants;
- required authority and the source of the trusted principal binding;
- semantic preconditions and the point at which they must hold;
- promised atomic effects and explicitly separate later effects;
- command binding, replay, disclosure, and uncertainty policies;
- authoritative observation or progression evidence supplied with outcomes;
- named assumptions and the assurance status of each claimed guarantee.

It must not make callers depend on private XTDB forms, FX scratch values, or
helper Vars. A synchronous REPL invocation remains meaningful when supplied an
admitted context and authorized principal; bypassing HTTP does not bypass the
model's contract.

Ordinary application code should receive scoped semantic capabilities rather
than a raw database mutation handle. Clojure namespace privacy, records, and
nominal wrappers do not sandbox a determined author in the same trusted process.
The assurance claim therefore states its trusted-code and writer boundaries.

A bypass writer can invalidate assumptions used by later supported operations,
not merely forfeit assurance for its own invocation. Coverage must account for
jobs, migrations, imports, administrative tools, other services, and direct
database access wherever their writes can affect a protected invariant. An
admission policy may accept a named external-writer premise; it must not report
that premise as established by observing only Gesso-issued calls.

*** Well-formed rules and appropriate policy are separate judgments

Where semantic types are known, malformed rules must fail admission. Comparing
a closed status enum as though it were a number cannot become a certified rule.
For ordinary Clojure predicates outside the analyzable vocabulary, the interface
records their types, contracts, implementation binding, and asserted meaning.
Merely invoking such a predicate does not prove its contract.

Neither type checking nor invariant preservation decides whether a business
policy is desirable. Gesso can establish that the declared Claim policy is
consistently enforced under stated premises. HumanHelp still chooses that
policy. The executable semantic core and any later proof kernel/checker have
different responsibilities, as established in Part I.

** Core, FX, and choreography

FX realizes the authoritative commitments of a public model operation. It may
acquire data, compute candidates, construct a protected transition, invoke a
backend, and translate evidence into a typed outcome. It must not invent a
second business semantics or a second distributed truth model.

One semantic operation can span a public =core= function, domain predicates, a
registered transition constructor, an FX pipeline, and a backend adapter. Those
are implementation components of the operation, not automatically separate
commands. Their contracts must agree on inputs, authority, permitted effects,
and outcomes.

The public model operation and the choreography invoking it are not required
to have identical callable signatures or host representations. A REPL,
scheduled job, installed HTTP handler, or another admitted Choreo realization
may invoke the same =:request/claim= meaning under its own authorized entry
contract. A shared keyword, copied interface map, route name, or successful
transport return is not evidence that the installed callable implements that
meaning. Application assembly binds the source-owned operation, selected
trusted executor, actual guard/write coverage, outcome interpretation, and
permitted disclosure to the same qualified semantic contract. Every path
claiming to implement the operation must satisfy its declared boundary;
passing through choreography is not a prerequisite for ordinary model use.

Conversely, a single command may involve several internal FX callbacks,
backend statements, and asynchronous publication attempts. Those do not
acquire independent authority to rewrite the business result or allocate a
second domain command identity merely because they execute separately.
A later notification worker has its own work/attempt identity and effect
contract, but its work remains correlated to the authoritative command
and retained publication intent under the selected protocol.

Choreography adds coordination obligations: which role calls the operation,
which participants learn its outcome, what they may provisionally display, and
how they recover when delivery is uncertain. Those obligations do not authorize
Choreo to manufacture model outcomes or bypass current model guards.

*** A concrete public Claim contract

For this example, Claim moves an eligible open Request to its production
=:claimed= state and creates the corresponding active *primary
RequestAssignment* for the authenticated helper. RequestAssignment owns
the helper relationship and its uniqueness/history semantics; a convenient
=:request/helper= field must not become a competing source of truth.
Collaborator assignments are not mistaken for a second primary helper.
The helper must have current active Membership in the Request's Organization,
and current Organization policy must permit the claim.

This worked operation explicitly selects a *durable work-recorded publication
profile*: successful new incorporation records the command result, the
required durable notification intent, and the protected Request plus primary
assignment transition together. Another operation may lawfully choose an
admitted best-effort profile, but it must publish a correspondingly weaker
contract rather than silently claiming work-recording or guaranteed delivery.
The durable intent is not evidence that a notifier received a message or
that an external effect completed.

The public value schema is small:

#+begin_src clojure
(def ClaimCommand
  [:map {:closed true}
   [:request-id uuid?]
   [:command-id uuid?]])

(def valid-claim-command? (m/validator ClaimCommand))

(defn claim! [trusted-context command]
  (when-not (valid-claim-command? command)
    (throw (ex-info "Invalid Claim input"
                    {:gesso/error :model/invalid-input
                     :operation :request/claim})))
  (model-runtime/invoke-admitted!
   trusted-context :request/claim command))
#+end_src

Validation is an unconditional boundary check, not an optional assertion that a
production configuration can disable. The example does not log the entire
command or trusted context in an error. A concrete application may use a typed
error return instead of an exception if its public interface declares that
choice.

=invoke-admitted!= resolves the exact registered operation and its capability
binding. It does not accept an arbitrary caller-provided guard/write map as an
equivalent operation. The browser's wire field =:gesso/command-id= may map to
the public model field =:command-id= through an admitted boundary mapping.
=:request-id= here denotes the HumanHelp domain Request; transport correlation
uses =:http-request-id= or =:transport-request-id=.

An inspection view of the contract might be:

#+begin_src clojure
{:operation :request/claim
 :interface-version 1
 :arguments ClaimCommand
 :principal-source :trusted-runtime-context
 :command-policy :claim-command-policy-v1
 :publication-profile :durable-work-recorded
 :new-incorporation
 {:requires [:request/argument-target-matches
             :request/open
             :request-assignment/no-active-primary
             :membership/principal-and-organization-match
             :membership/active
             :organization/claim-permitted]
  :establishes [:request/claimed
                :request-assignment/active-primary-recorded
                :request-assignment/primary-uniqueness-preserved
                :command/result-recorded
                :publication/intent-recorded]}
 :replay
 {:requires [:command/binding-compatible
             :command/current-disclosure-permitted]
  :effect :return-permitted-recorded-outcome}}
#+end_src

These keywords are schematic *inspection labels*, not a second registry of
facts or an executable guard-language API. The public RequestAssignment model
owns what =no-active-primary=, =active-primary-recorded= and
=primary-uniqueness-preserved= mean, including which other writers may
alter assignment state. The application derives or supplies their qualified
transaction-current realization through its admitted model/authority
interface; copying this map cannot establish that the operation, installed
handler, backend guard or durable worker exists.

A collection of reassuring labels is not a proof. In particular,
new-incorporation conditions do not apply unchanged to replay: after a
successful Claim the Request is claimed and has an active primary assignment,
but a compatible authorized repetition must still be able to recover the
historical recorded success. A later Unclaim or Reassign may change the current
Request and assignment without changing that historical command outcome.
Result disclosure still depends on current authorized policy.

| Public Claim construction | Required model/coordination judgment |
|---------------------------+--------------------------------------|
| An eligible authenticated helper claims an open, unassigned Request using a newly admitted command | The protected transaction establishes the =:claimed= state, exactly the permitted active primary RequestAssignment, recorded command outcome, and durable intent for the chosen profile |
| A different collaborator assignment already exists, but the primary slot is eligible and empty | Do not mistake collaborator presence for a conflicting primary; admit or reject according to the actual public RequestAssignment policy |
| A client supplies a matching =:request-id= and a forged helper identity in a transport wrapper | The trusted principal binding selects the actor; input shape or a matching route name cannot grant the claimed identity |
| A previous Claim committed and is replayed compatibly after the Request became claimed or was later reassigned | Resolve the prior command with permitted historical disclosure and without adding a second primary assignment or publication intent |
| An installed handler invokes a similarly named helper or FX callback that omits assignment uniqueness or actual durable work recording | Reject the stronger declared operation/assembly correspondence; accepting a map of obligations is not proof of enforcing them |
| A best-effort notice is selected by a separately admitted contract | Permit the weaker published guarantee; do not advertise =:publication/intent-recorded= or delivered receipt as a consequence of this weaker operation |

*** Model outcomes and invocation errors

The operation interface uses the following model outcomes:

| Outcome | Required meaning |
|---------+------------------|
| =:committed= | Authoritative evidence establishes incorporation of this command by the invocation being reported. |
| =:already-incorporated= | A compatible retained command record establishes prior incorporation; the permitted recorded outcome is returned without incorporating again. |
| =:rejected= | Authoritative evidence establishes command rejection under the declared rejection/closure policy; this is not merely an unsuccessful physical attempt. |
| =:commit-unknown= | Available evidence does not establish an authorized definitive command outcome. Incorporation may or may not have occurred. |

Outcome variants have closed discriminants and variant-specific payload schemas.
A successful variant carries command binding and result evidence; a rejection
carries its permitted reason and disposition evidence; an unknown variant
carries the admitted reconciliation reference and uncertainty classification.
Fields are not made optional merely to allow every variant through one loose
map schema.

Malformed inputs, unsupported interface versions, incompatible reuse, invalid
credentials, disclosure denial, and backend qualification failure require typed
handling. They are not all domain rejections. For example, an unauthorized
caller must not be able to create a terminal rejection record for somebody
else's command. A disclosure denial must not falsely say that the command was
never incorporated. Privacy policy may require an intentionally indistinguishable
unavailable response for several underlying conditions.

The outcome recorded for replay is a historical operation result. A Request
projection freshly acquired alongside it has a different meaning: it describes
state at that acquisition's scope and basis. The API must distinguish these
values. It must not imply that a recorded successful Claim guarantees the
Request is still assigned to that helper now.

Presentation mapping is explicit:

| Model evidence | Presentation settlement |
|----------------+-------------------------|
| Permitted committed success | =:accepted= for the bound presentation operation. |
| Permitted already-incorporated success | The same accepted successor, without a new incorporation. |
| Authoritative command rejection | =:rejected= through the declared rejection branch. |
| Commit unknown | =:unknown= until admissible reconciliation evidence resolves it. |

A model may define successful results other than Claim success, and rejection
details may be undisclosable. Assembly must check the actual variant mapping,
disclosure requirements, and permitted presentation effects. A new command ID
is not an acceptable way to disguise an unresolved retry.

*** An explicit invocation sequence

The following logical phases may be implemented by one FX pipeline or several
cooperating components. The semantics must survive either arrangement.

| Phase | Responsibility | What it does not establish by itself |
|-------+----------------+-------------------------------------|
| Admit | Validate inputs, operation/interface identity, trusted principal, and capability. | Permission to commit after mutable authorization changes. |
| Resolve or prepare | Recover a compatible prior result, or acquire data and compute a candidate. | A pre-read is not the atomic command-existence guard. |
| Incorporate | Protect semantic dependencies and atomically establish the domain transition, command record, and required durable intents. | A submitted request is not necessarily a committed transaction. |
| Propagate | Attempt publication or arrange durable recovery according to the operation contract. | Delivery success to all participants. |
| Respond | Return only the outcome and observation evidence the invocation can justify and disclose. | A browser has received, installed, or adopted the response. |

Replay does not blindly rerun notifications or other effects. A recorded durable
intent may remain unfinished and be resumed by its declared recovery owner, but
it retains its original work identity. A compatible replay is not a new reason
to create a second notification or charge.

** Atomic authoritative transitions
:PROPERTIES:
:CUSTOM_ID: req-atomic-authoritative-transition
:END:

An authoritative transition establishes the invariant-bearing effects of one
semantic command at a declared atomic boundary. Preparation may be extensive:
queries, calculations, validation, composition of model constraints, and
construction of proposed writes can occur before that boundary. They do not
become authoritative merely because preparation succeeded.

If preparation itself reserves stock, creates a lease, or persists an intent,
that change is a separate authoritative transition with its own valid state and
recovery obligations. It must not be hidden inside something described as a
pure pre-read.

For each transition, the contract identifies:

1. the authority and semantic state being changed;
2. the operation, command, canonical arguments, and trusted principal binding;
3. the conditions that must hold at incorporation;
4. the permitted state change and what must remain unchanged;
5. the command-result and durable-work effects included in the same boundary;
6. the backend mechanism protecting these commitments;
7. the evidence that distinguishes incorporation, rejection, and uncertainty.

The required protection concerns semantic dependencies, not automatically every
field read during preparation. An unused display name need not become a commit
guard. Conversely, absence, uniqueness, aggregate limits, and relationships may
be semantic dependencies even when no existing document contains the fact to
guard. Protecting only returned rows cannot establish that no matching row was
inserted concurrently.

Atomic writes alone are insufficient. A backend can atomically apply writes
derived from stale or incompatible facts. The qualification must establish that
the required conditions hold at the operation's declared incorporation point,
using an appropriate transaction isolation, conditional mutation, transaction
function, constraint, or equivalent qualified mechanism.

*** Semantic rules become implementation obligations
:PROPERTIES:
:CUSTOM_ID: req-authoritative-semantic-obligations
:END:

Every rule used to justify admission or a safety claim must have an explicit
path to its authoritative realization. The path identifies the semantic
predicate, bound values, mutable dependencies, protection mechanism, and
evidence status. It also identifies the frame: effects outside the declared
change are forbidden unless separately specified.

For Claim, the obligation set is:

| Semantic obligation | Binding or protection required |
|---------------------+--------------------------------|
| The requested Request is the acquired target. | Equality between the command's Request ID and the acquired authoritative identity, in the correct authority scope. |
| The Request is open and unclaimed. | Both conditions protected at incorporation; open status alone is insufficient. |
| Membership belongs to this helper and Organization. | Principal, Membership, Request, and Organization associations protected together. |
| Membership is active. | Current eligibility protected at incorporation under the policy's temporal meaning. |
| Organization permits the claim. | The relevant policy and any inputs it depends on protected at incorporation. |
| Assignment is the permitted change. | The helper comes from the trusted principal binding; other Request fields obey the frame. |
| The command is not incorporated twice. | Atomic command-binding compatibility and uniqueness within the declared command namespace. |
| Success can be recovered and propagated. | Command result and required durable publication intent share the transition's atomic boundary. |

Evidence may establish some of these obligations by construction, others by a
checked derivation, others by runtime checks, and others only under accepted
backend or opaque-code premises. The report must preserve those classifications.
The word /checked/ must identify what was checked; it must not silently include
all unexamined behavior beneath that check.

*** Canonical construction and physical submission

The default managed path derives a transition from the admitted operation's
canonical semantics and bound inputs. It does not ask application code to
independently maintain three descriptions of the same effect: a business rule,
a reassuring guard map, and an unconstrained transaction vector.

The derived or checked construction binds at least:

- the operation/interface and semantic-definition identities;
- the exact admitted implementation and relevant adapter/profile identities;
- typed argument, principal, authority, and target bindings;
- acquired input provenance and any required acquisition capabilities;
- protected predicates, permitted writes, and frame obligations;
- command-result and durable-work effects;
- the invocation and physical submission to which resulting evidence belongs.

The execution gate must account for the complete submitted transaction, not just
a selected domain fragment. Command ledger writes, outbox entries, creates,
updates, deletes, transaction options, and any effective backend-side hooks must
be included in the checked effect boundary or covered by an explicit accepted
premise. An extra write or a weakened guard cannot be ignored because the
original domain fragment still matches a certificate.

An inspection report is not the executable capability. The runtime must prevent
ordinary callers from substituting a new transaction, changing a target,
replacing the executor, or attaching a report from an unrelated successful call.
The result must be linked to the actual issued invocation, submitted material,
and qualified backend return path. Structural equality with expected output is
not evidence of that provenance.

Different construction mechanisms can support different subsets. A proof for
one scalar document update does not cover nested values, nullable fields,
inserts, deletes, multi-document transitions, or arbitrary transaction programs
unless its proposition says so. Those operations remain available through
broader checked mechanisms or explicitly asserted contracts. They must not be
quietly forced into the narrow proof's vocabulary.

*** Representation and frame fidelity

The mapping between semantic fields and physical storage must be explicit and
checked for the supported representation. Distinct semantic fields must not
silently collide on one physical field. Required fields, system metadata, nested
paths, deletion, and field ownership need declared treatment.

Presence matters. A missing field, a field with =nil=, a field with =false=, and
an empty collection are not interchangeable unless the model explicitly makes
them equivalent. A proof that depends on a complete acquired entity cannot use
a partial projection whose missing =:request/helper= is interpreted as unclaimed.

Whole-document replacement must preserve the declared frame despite concurrent
changes. Comparing a selected subset of fields and then replacing an entire
stale document can overwrite unrelated updates. Valid solutions include a
qualified full-state guard, an appropriately maintained revision guard, or a
backend update whose semantics preserve untouched fields. The chosen solution
must actually support the claimed frame.

A revision field is sufficient only under a premise that every relevant writer
maintains it and that its comparison has the required semantics. An equal
before/after value does not prove that no intermediate change occurred. History
or non-repetition properties require stronger evidence than a state predicate;
ordinary state invariants do not universally require an ABA-prevention mechanism.

*** Capability lifetime and command lifetime

Execution capabilities are scoped to the admitted runtime and operation. Their
contract states whether they may be used once, reused, transferred to an
asynchronous worker, or retained beyond a request. One-shot consumption must be
atomic with respect to competing local users of that capability.

A one-shot capability prevents reuse of that capability instance. It does not
prevent another request from obtaining a different capability for the same
semantic command. Durable command deduplication still belongs to the command
protocol. Similarly, a thread ID, request path, or callback identity does not
replace the semantic command binding.

Retiring a request-local capability prevents future use according to its
contract; it does not roll back an already submitted transaction. Transferring
work to a durable worker requires an admitted transfer and a new appropriate
capability, not accidental retention of a web request's ambient authority.

*** A complete Claim preparation example

The following pure function illustrates candidate computation. It assumes that
all four model values have already passed their public schemas and that Request
includes a present, explicitly nullable helper field. The function neither
commits nor establishes replay disposition.

#+begin_src clojure
(defn claim-candidate-decision
  [command principal request membership organization]
  (cond
    (not= (:request-id command) (:request/id request))
    {:candidate/status :invalid :reason :target-mismatch}

    (not= :open (:request/status request))
    {:candidate/status :ineligible :reason :request-not-open}

    (some? (:request/helper request))
    {:candidate/status :ineligible :reason :already-claimed}

    (not= (:principal/id principal) (:membership/user membership))
    {:candidate/status :ineligible :reason :membership-principal-mismatch}

    (not= (:request/organization request)
          (:membership/organization membership)
          (:organization/id organization))
    {:candidate/status :ineligible :reason :organization-mismatch}

    (not= :active (:membership/status membership))
    {:candidate/status :ineligible :reason :inactive-membership}

    (not (true? (:organization/claims-enabled? organization)))
    {:candidate/status :ineligible :reason :claims-disabled}

    :else
    {:candidate/status :eligible
     :request-id (:request/id request)
     :helper-id (:principal/id principal)}))
#+end_src

This simplified policy is illustrative; a richer Organization predicate has its
own declared dependencies. Trusted authentication establishes who the principal
is. It does not by itself establish current Membership or permission.

The managed operation binds this candidate to canonical transition construction.
The authoritative realization protects the target, eligibility, associations,
and frame together with the ownership change, command record, and required
publication intent. A caller never gains authority by returning
={:candidate/status :eligible}=.

A candidate rejection from a pre-read is not automatically the final command
outcome. A concurrent attempt might already have incorporated the same command.
The command protocol below resolves that case before it reports authoritative
rejection. Conversely, a positive candidate must be revalidated or protected at
incorporation; it cannot survive arbitrary Membership or policy changes merely
because preparation succeeded.

| Interleaving | Required result |
|--------------+-----------------|
| Membership is deactivated after preparation, before incorporation. | The new Claim cannot incorporate under the old eligibility unless the declared policy expressly permits that temporal meaning. |
| Request moves to another Organization before incorporation. | The stale association cannot justify the assignment. |
| Another helper claims first. | At most the operation allowed by the protected current state incorporates. |
| The same command already succeeded but its response was lost. | A compatible authorized repetition can recover the recorded success even though the Request is now claimed. |
| This physical attempt aborts while another attempt for the same command commits. | The command is incorporated; this attempt's abort is not command rejection. |

*** API boundaries do not force transaction boundaries

Models may expose composable constraints and effect constructors through public
interfaces, allowing one coordinator to establish a cross-model invariant in a
single atomic transition. Combining those components must check shared target
bindings, incompatible writes, frame overlap, and the conjunction of their
requirements. Concatenating independently prepared write lists is insufficient.

If the participating authorities cannot share the required atomic boundary, the
design must name valid intermediate states and a recovery protocol. A sequence
of individually atomic calls is not an atomic cross-model operation merely
because it appears in one FX vector or choreography step.

** Command identity and authoritative disposition

A semantic command identifies one intended invocation under a declared command
policy. It survives physical retry. It is distinct from the operation definition,
the choreography execution that attempted it, and the transport exchanges that
carry it.

| Identity | Meaning and lifetime |
|----------+----------------------|
| Operation identity | The public semantic operation, such as =:request/claim=. |
| Operation interface version | The input, result, and behavioral contract being invoked. |
| Semantic command ID | One bound intent whose disposition can be deduplicated and recovered. |
| Choreography execution ID | One distributed execution and its protocol-local resources. |
| Transport request ID | One HTTP exchange or other delivery attempt. |
| Backend submission-attempt ID | One physical attempt to submit or execute a transaction. |
| Capability instance ID | One issued execution or acquisition right. |
| Resource instance ID | One lifecycle instance of a managed resource or installation target. |
| Principal-context identity | The authenticated context relevant to authority and disclosure. |

Other identities, including deployment and projected-plan compatibility, may be
needed. They must be named for their purpose; a bare universal =generation=
coordinate must not stand in for them all.

*** Command binding and canonical inputs

The admitted command boundary supplies or admits a stable =:gesso/command-id=
before the first possible send. A browser may carry an identifier, but choosing
its bytes confers no permission. The trusted boundary establishes the binding
and must preserve it through retransmission and reconciliation.

The command policy defines the namespace in which IDs are unique and the
immutable binding compared on repetition. That binding normally includes:

- authority/tenant and command namespace;
- semantic operation and compatible interface identity;
- canonical semantic arguments and their canonicalization version;
- the principal or explicitly declared delegated authority responsible for the
  intent;
- any domain preconditions that are part of the intent, such as an expected
  entity version.

Command compatibility is not equality of an arbitrary serialized map. Defaults,
omitted fields, numeric representation, ordered versus unordered collections,
and schema evolution require defined canonicalization. If a digest stands in
for canonical arguments, the contract identifies its algorithm and accepted
collision premise; a short convenience hash is not automatically an adequate
binding.

An observed read basis used only as a freshness hint need not be an immutable
semantic argument. An expected version that the user intentionally conditions
the command on is an argument. The interface must distinguish the two. Retry
must not silently turn a conditional command into an unconditional one.

Server-generated timestamps, random identifiers, and other choices also need
declared semantics. Values defining the user's intent or the identity of a
created entity must be stabilized or recoverable as the policy requires.
Transaction-local candidate calculations may be recomputed when permitted, but
their variation cannot change the command binding or invalidate replay.

*** Command identity is not an idempotency policy

Attaching a UUID does not provide deduplication. An operation must declare its
incorporation policy, storage boundary, compatible-repetition behavior,
incompatible-reuse handling, retention horizon, and recovery mechanism.

For Claim, the intended policy is one incorporation for a compatible command
binding. Repetition after incorporation returns a permitted recorded outcome.
Distinct command IDs can still conflict on the same Request; command
deduplication does not replace domain concurrency control.

An operation that intentionally permits repeated independent effects must say
what constitutes a new semantic command. A new delivery attempt is not, by
itself, a new intent. If the product supports repeating an action, the admitted
entry path issues a fresh command for that deliberate action.

The command store need not contain an in-flight row for every implementation.
Its protocol must nevertheless distinguish evidence of incorporation, evidence
of terminal rejection or closure when promised, and the absence of a definitive
result. A transient local registry may assist scheduling; it cannot replace a
durable record where process failure recovery is promised.

*** Atomic resolve-or-incorporate protocol

The following is a semantic algorithm, not a requirement to implement one giant
callback in the database:

1. Validate the admitted operation, interface, canonical arguments, authority
   scope, and trusted principal. Establish which command binding this caller is
   permitted to invoke or resolve.
2. If a retained command record is found, check binding compatibility and
   current permission to disclose the result. Return the permitted recorded
   disposition without applying the operation again. An incompatible record
   cannot be overwritten or treated as a new command.
3. If no definitive record is established, protect command uniqueness together
   with the conditions for new incorporation. An earlier non-transactional
   absence check is only a hint.
4. At the authoritative boundary, either establish the permitted domain
   transition, command result, and required durable intents together, or do not
   establish that transition. Conflicting concurrent attempts must not each
   incorporate the same command.
5. Interpret the backend result according to its qualified contract. A local
   return that means submitted or queued must not be translated into committed.
6. On contention, an abort, or an ambiguous return, resolve whether another
   attempt established a command disposition. Return only what the admitted
   evidence supports. If the result remains indeterminate, preserve unknown.

The implementation may use retries internally. Such retries retain the semantic
command and must not execute unrepeatable external effects inside a callback
that the backend may rerun.

*** Rejection must name its scope

There are three distinct negative facts:

- preparation found a currently ineligible candidate;
- one physical transaction attempt definitely did not incorporate;
- the semantic command is authoritatively rejected under its declared policy.

Only the last justifies the model outcome =:rejected= as a definitive command
settlement. A successful competing attempt can coexist with either of the first
two facts.

If the operation promises a stable terminal rejection, its mechanism must close
the command against pending and future compatible incorporation. One solution
is an atomic terminal rejection record which contends with the incorporation
record; another is a qualified equivalent closure or fencing protocol. A mere
lookup that finds no record cannot provide this guarantee while a previously
submitted attempt could still commit.

A rejected database transaction generally cannot also be assumed to have
persisted its own rejection record. If closure requires a subsequent
transaction, that transaction has its own races and possible uncertainty. It
must resolve against any competing incorporation before the model reports a
definitive rejected command.

This does not require every backend failure or bad request to create a durable
terminal record. Interfaces may expose typed invocation failures or unresolved
attempt diagnostics without claiming terminal command rejection. An operation
with a different rejection lifetime must make that scope explicit and provide
a presentation mapping that does not falsely promise finality.

A fresh intentional action after rejection may use a new command ID. Automatic
retry after an unknown result must not do so merely to escape the unresolved
record. An unauthorized or malformed invocation cannot close another party's
otherwise valid command.

*** Retention, upgrades, and expiry

Deduplication guarantees have a declared horizon. Deleting a result while old
messages can still be accepted may permit reintegration of a previously
incorporated command. The design must choose a coherent policy: retain the
necessary record or tombstone, reject commands outside an admitted validity
window, retire the command namespace with a protected fence, or provide an
equivalent mechanism.

Result disclosure retention can differ from incorporation-prevention retention.
A compact tombstone may prevent duplicate effects without retaining sensitive
response data. In that case the public resolver reports only the information
the tombstone and disclosure policy justify; it does not fabricate the original
payload.

Interface upgrades must specify compatibility for retained commands. Changing
argument canonicalization or the meaning of a policy version cannot silently
rebind an old ID. A database restore, tenant migration, or authority fork must
also define which command namespace and records remain valid. Backend position
numbers alone do not preserve those identities.

*** Command disposition and participant knowledge
:PROPERTIES:
:CUSTOM_ID: req-command-participant-uncertainty
:END:

The command's authoritative disposition and a participant's knowledge are
different state components. The backend may have committed while the caller
still knows only that delivery failed. =:commit-unknown= describes this missing
knowledge; it does not assert a mysterious third kind of database commit.

Unknown must be preserved when the available evidence cannot distinguish
incorporation from non-incorporation. A timeout, disconnected SSE channel,
retired browser execution, failed response serialization, or exhausted retry
budget cannot turn that uncertainty into rejection.

Definitive knowledge is also subject to authority. A runtime may know that a
record exists while the current participant is not permitted to learn its
contents. The public interface must represent unavailable disclosure without
inventing a domain failure or leaking the existence of protected information.

*** Worked example: Claim committed, response lost

Let =R= be the Request ID. Let =C42= be a scalar command ID; the command value is
a separate map:

#+begin_src clojure
(def C42 #uuid "f1bf42ee-7965-4a53-905b-c59038f75e42")

(def claim-command
  {:request-id R
   :command-id C42})

;; Wire representation at the admitted browser boundary.
(def claim-wire-arguments
  {:request-id R
   :gesso/command-id C42})
#+end_src

Alice's original choreography execution is =E1=. A server invocation admits
=claim-command= under Alice's trusted principal context. Its authoritative
transition assigns Request R, records C42's compatible binding and successful
outcome, and records the required publication intent. The response is lost.

| Location | Established fact |
|----------+------------------|
| Authoritative model | C42 was incorporated successfully. |
| Publication worker | Durable work exists; delivery may still be pending. |
| Browser execution E1 | Delivery became indeterminate; no admitted success evidence arrived. |
| Browser presentation | The command remains unknown, with the declared reconciliation path available. |

Reading Request R and finding Alice as helper does not attribute that state to
C42. Another command might have caused the same state; R may also have changed
again since C42. A command resolver therefore uses retained outcome evidence,
not pattern matching on the current Request.

The public resolution path is conceptually:

#+begin_src clojure
(request/resolve-claim!
 trusted-context
 {:request-id R :command-id C42})
#+end_src

This operation resolves the full immutable binding required by the contract,
including authority scope, operation/interface compatibility, canonical
arguments, and principal or delegation. It checks current permission to disclose
the prior outcome. It is not a public wrapper around unrestricted raw database
lookup.

Resolution results distinguish:

| Resolution classification | Meaning |
|---------------------------+---------|
| Resolved incorporation | A compatible retained record justifies the permitted recorded result. |
| Resolved rejection | Qualified command-closure evidence justifies the permitted rejection. |
| Not established | This lookup did not establish a definitive disposition; pending incorporation or unavailable retained evidence has not been ruled out. |
| Unavailable | Acquisition or permitted disclosure could not supply a result. Privacy policy determines how much detail may be returned. |
| Incompatible | The admitted binding conflicts with the retained binding, when this distinction may be disclosed. |

These are resolver classifications, not additions to the canonical model outcome
set. The interface declares how each maps to an operation outcome or typed
invocation error. In particular, not established does not mean rejected.

A compatible invocation of =request/claim!= can alternatively recover the same
record through its replay branch. It returns =:already-incorporated= and the
permitted success even though the Request is now claimed. It must not rerun the
new-incorporation guard first and reject solely on that changed state.

If another physical attempt finds a retained success after its own ambiguous
submission, that proves command incorporation. It does not necessarily prove
which physical attempt incorporated it. Reports and tests must preserve this
distinction when attributing execution evidence.

*** Reconciliation needs an owner, not only a lookup

A read-only resolver is useful but is not an executable recovery strategy by
itself. An admitted unknown branch identifies who requests reconciliation, how
the command reference survives local retirement, which evidence sources are
used, when retries are allowed, and what happens when automatic recovery stops.

The recovery policy may include backoff, bounded automatic attempts, a durable
queue, user-triggered refresh, or operator handling. Its safety claim must hold
when progress never occurs. A liveness claim additionally names assumptions
such as eventual backend availability, retained evidence, scheduling fairness,
and continued authorization. A timeout budget can end automatic work without
establishing non-incorporation.

Static preflight need not predict dynamic conditions. It must nevertheless
require declared handling or recovery paths for conditions that can strand an
operation, including unknown commit, undisclosable replay, incompatible retained
interfaces, and unavailable authoritative acquisition.

Retiring E1 revokes E1's installation and settlement rights according to its
resource policy. It does not cancel C42 or erase its result. A later execution
E2 may reconcile C42 through an admitted participation path. Late evidence must
not revive E1 or install into a resource instance now owned by another
execution.

Cancelling a local request is similarly distinct from an authoritative
cancellation command. Whether an authoritative operation can be cancelled is a
model question with its own valid transitions. Once incorporated, an effect may
require a compensating operation rather than retrospective cancellation.

** External systems and valid intermediate states

One database transaction cannot generally atomically commit a database change
and an arbitrary external provider effect. The model must represent valid
intermediate states and durable recovery rather than describing a remote API
call as if it were part of the database's atomicity guarantee.

The durable-workflow boundary of [[#req-durable-workflow-boundary][Part III]]
applies: a process-local choreography execution is not automatically a durable
owner of unfinished business work.

*** Worked example: placing an order with payment authorization

Suppose the business policy permits an Order to become placed once the provider
has authorized the specified payment. Capture and settlement are separate
effects unless the operation explicitly includes them. This example must not
call an authorization receipt proof of a completed charge.

Money is an amount in a declared currency, with a supported precision and
rounding rule. A bare floating-point number or unqualified decimal is not the
complete payment argument. The immutable payment intent binds the Order,
merchant/provider account, operation type, amount, currency, instrument
reference, and relevant policy/interface versions.

The local public entry operation is conceptually:

#+begin_src clojure
(order/place-intent!
 trusted-context
 {:command-id order-command-id
  :cart-id cart-id
  :payment-instrument-ref instrument-ref})
#+end_src

The authoritative model validates ownership and eligibility of the Cart and
instrument reference, computes or validates the authoritative price, and
protects the inputs required by its pricing and inventory policy. It atomically
creates a valid pending Order, records the command result, and records durable
payment work. The pending Order is a committed domain state, not an optimistic
browser fiction.

The Order command's success means that this intent was established. If the UI
wants to wait for final placement, choreography must distinguish intent
acceptance from business completion. It must not display a final placed result
merely because =place-intent!= committed.

*** Provider request identity and evidence

The durable payment intent has its own stable identity. Provider requests use an
idempotency key derived or allocated under the provider's actual key scope and
retention rules. The binding includes the merchant/account, provider operation,
and immutable request meaning. A globally formatted string does not by itself
establish global uniqueness or deduplication at the provider.

The qualification contract states whether repeated requests with that key are
deduplicated, how conflicting payloads are handled, how long records remain,
and how an indeterminate request can be resolved. Provider idempotency is an
external premise; Gesso cannot manufacture it by storing a local key.

If the provider does not supply a sufficient deduplication or lookup contract,
the application must use a recovery strategy appropriate to that limitation.
An unknown effect may require manual reconciliation. Blindly sending a fresh
key after a timeout can create a second charge or authorization.

Provider evidence must be authenticated or otherwise admitted by a qualified
adapter and bound to the exact payment intent. Its interpretation checks the
merchant/account, provider operation, Order or intent reference, key, amount,
currency, and result status. Receiving an untrusted webhook map with a familiar
status string is insufficient. Signature verification alone also does not prove
that the signed event refers to this intent or establishes the required effect.

The adapter must distinguish authorization, capture, decline, pending status,
and an indeterminate transport result. A provider lookup that finds no record
does not establish non-occurrence while an earlier request may still be in
flight, unless the provider contract supplies that stronger guarantee.

*** Incorporating a provider result

A worker resolves or submits the provider operation under the durable intent.
It then invokes a public model result-incorporation operation with the admitted
provider evidence. That operation protects the payment intent and current Order
state, records the accepted receipt, makes the permitted domain transition, and
updates durable work in the same local atomic boundary.

| Current local state and admitted evidence | Required treatment |
|------------------------------------------+--------------------|
| Payment pending; matching authorization succeeds. | Record authorization and advance according to the placement policy. |
| Payment pending; definitive matching decline. | Record the decline and move to the declared failure or alternative-payment state. |
| Payment pending; response lost or provider result unresolved. | Keep a truthful pending/unknown condition and retained recovery work. |
| Matching receipt already incorporated. | Return a compatible recorded result without applying the effect twice. |
| Receipt conflicts with immutable intent or prior evidence. | Reject or quarantine the evidence through a declared diagnostic/recovery path. |
| Cancellation requested; a late authorization succeeds. | Record the real external outcome and enter the declared void, compensation, or review path. |

Workers may use leases or fencing to prevent stale local writes. Such mechanisms
do not retroactively stop a remote call already issued by an old worker. Late
evidence must still be handled according to the actual external effect and
current model state.

Cancellation therefore needs explicit states such as cancel requested, void
pending, refund pending, or review required when those distinctions matter. A
terminal cancelled label must not cause the system to discard evidence that
money was authorized or captured. Compensation is a new effect with its own
identity, uncertainty, and recovery obligations; it is not an atomic undo of
history.

*** Safety and progress for external work

The system can promise that no Order is reported placed without the required
admitted authorization evidence, under the provider and backend premises. It
cannot promise that every payment finishes merely because a worker exists.
Eventual resolution additionally depends on provider availability, usable
lookup/idempotency behavior, durable scheduling, and any required human action.

Required work must remain discoverable after process loss. Acknowledging a job
because an HTTP call was sent, rather than because the contracted work state
was durably incorporated, can lose the only recovery owner. Queue acknowledgment,
lease expiry, and model work completion require a declared relationship.

** FX value flow and lifecycle

FX should make value dependencies and effects inspectable while remaining usable
from ordinary Clojure. Pure calculations consume explicit values and return
explicit values. Effectful steps declare their inputs, outputs, failure classes,
and effect boundary. A context is a capability-bearing environment, not a
hidden bus into which every step writes arbitrary intermediate state.

*** Context and values have different roles

The context may contain admitted database/acquisition capabilities, a trusted
principal binding, clocks or randomness with declared semantics, tracing, and
scoped backend interfaces. Intermediate Request data, candidate decisions,
prepared transitions, and outcomes should normally flow as explicit arguments
and results.

This permits the system to explain which value justified a step and to detect
missing or mismatched inputs. It also reduces accidental use of stale ambient
data. A capability's presence in context does not extend its lifetime or widen
its authority. Authentication state captured at entry does not freeze mutable
authorization unless that temporal policy is explicitly part of the contract.

Graph or multistate implementations obey the same rule. They may provide a
convenient evaluation strategy, but hidden mutable cells must not become an
untracked second model of operation state. Pure dependency nodes and effectful
nodes require distinct semantics, including recomputation and retry behavior.

*** Ordering and completion are explicit

An ordered effect description specifies what each step waits for, how values
flow, and what happens after failure. Merely placing effects in a vector is not
enough if the interpreter may run them concurrently or treat enqueue as
completion.

An illustrative descriptor could distinguish:

#+begin_src clojure
{:fx/type :sequence
 :steps [:admit-command
         :resolve-or-prepare
         :incorporate-authoritative-transition
         :construct-response]
 :failure-policy :phase-aware}
#+end_src

The registered step definitions supply types, branches, capability requirements,
and completion semantics. The map alone is not an executable operation.
Independent publication work may proceed separately once durable intent exists;
it need not delay an otherwise justified commit response unless the public
contract explicitly promises that stronger acknowledgment.

Exceptions are interpreted by phase and evidence. A failure before submission,
an ambiguous failure during submission, a post-commit publication failure, and
a response-rendering failure are different events. A generic catch that turns
all four into =:rejected= violates the operation contract.

Retryable backend callbacks must not contain unprotected external effects.
Clock and random values used in semantic decisions need declared sampling and
retry semantics. Ordinary Clojure functions and macros may implement these
steps, but any opaque effect footprint remains an explicit contract premise.

*** Post-commit delivery debt
:PROPERTIES:
:CUSTOM_ID: req-post-commit-recovery
:END:

Once a command commits, failure to notify, render, or deliver does not uncommit
it. Required later work becomes explicit delivery or recovery debt. The
operation contract identifies what must be durable, who owns it, how it is
retried, and what counts as completion.

For a durable publication requirement, the domain transition and publication
intent must share an atomic boundary or an equivalently qualified discovery
mechanism. A commit followed by an unprotected best-effort publish can leave a
permanent gap if the process dies between those actions.

The intent binds the authoritative effect, relevant subject/query impact,
progression requirement, and stable delivery/work identity. It need not capture
every currently connected subscriber. A durable change log or outbox can feed
later routing and interest matching. Delivery semantics must state whether
duplicates are possible and how consumers recognize compatible repetition.

An in-memory list of local interests is not proof that all affected participants
will learn a change. If publication is conditioned on known interests, the
design must cover remote interests, subscription races, disconnects, and router
failover to the extent that its convergence claim includes them. Otherwise that
claim must be limited explicitly. The particular routing topology belongs to
the transport design; the no-lost-required-work obligation belongs here.

Publication completion also has a scope: queued, durably recorded, accepted by a
broker, delivered to a connection, admitted by a participant, and adopted by a
projection are distinct milestones. The contract names the milestone it can
observe and retains downstream obligations where required.

Recovery failure may leave debt visible and unresolved. It must not manufacture
success, discard the command record, or turn the committed domain operation
into a rejection. If an effect is intentionally best effort, its omission and
the resulting weaker guarantee must be part of the public contract.

** Authoritative basis and XTDB

An authoritative basis describes the database observation context justified by
the backend adapter. It is not a domain entity version, command ID, execution
ID, or universal time coordinate. A basis may advance because unrelated data
changed. Equal entity content at different bases does not make the bases equal,
and a changed basis does not by itself make a command's business preconditions
false.

XTDB integration should use XTDB-specific consistency mechanisms where they
provide useful guarantees. Gesso must describe those mechanisms through a
qualified adapter contract rather than inventing generic arithmetic on opaque
tokens or claiming guarantees from a dependency's name alone.

The [[#req-backend-assumption-qualification][backend qualification contract]] of
Part I applies. A Gesso proof may be conditional on specific XTDB premises. It
need not prove the whole database implementation, but it must make visible
exactly which database behavior would invalidate the proof.

*** Backend assumptions are distinct obligations

The adapter/profile identifies the loaded backend version and relevant build,
configuration, transaction API, query API, value codec, temporal options, and
Gesso realization. A supported version range requires evidence of compatibility
under its declared policy; it is not an invitation to ignore version changes.

| Premise | Required meaning |
|---------+------------------|
| Atomic publication | The protected domain changes, command record, and required durable intents are established together or not established as that transition. |
| Dependency protection | The semantic predicates, including cross-document, absent-row, or aggregate conditions where used, hold at the declared incorporation boundary. |
| Representation and frame | Encodings, field presence, update semantics, and untouched data correspond to the admitted transition. |
| Command exclusion | Competing compatible attempts cannot each incorporate the same command under the declared namespace and retention policy. |
| Outcome interpretation | The qualified return or later evidence actually establishes the claimed committed, rejected, or unresolved status. |
| Read visibility | The read mechanism honors the declared progression and temporal requirement, and its observation evidence reports what was established. |
| Durability and recovery | Retained command and work evidence survives the failures included in the promise. |
| Writer coverage | Every writer capable of invalidating a dependent invariant follows the required discipline or is covered by an explicit external premise. |

These premises are not interchangeable. Atomic writes do not prove predicate
protection. A row count does not prove target or principal binding. A committed
transaction ID does not prove an exact immediate poststate unless the backend
contract supplies that relationship. A source-bound local return does not
prove all remote backend semantics.

The adapter must specify the actual protected mechanism for each supported
operation class. It must not imply that arbitrary Clojure callbacks execute
inside every XTDB transaction, or that a particular SQL construction has a
stronger isolation meaning than its qualified contract establishes.

*** Qualification and conformance evidence

Qualification combines the declared backend contract, implementation binding,
checked Gesso-side correspondence, and targeted conformance evidence. Useful
tests include positive cases, deliberately weakened guards, altered targets,
extra submitted writes, representation edge cases, contention, and lost or
ambiguous returns.

Finite tests can falsify assumptions or detect incompatibilities; they cannot
prove that no current or future XTDB behavior violates a premise. Gesso must
therefore avoid promising that qualification will detect every possible backend
defect. Its defensible promise is that assumptions are explicit, evidence is
bound to the actual supported profile, relevant changes invalidate or trigger
requalification, and observed violations propagate to dependent assurance.

Qualification should target the behavior on which proof depends. A dependency
version string check is useful configuration evidence, but is not a semantic
conformance test. Likewise, a passing abstract transition model does not test
the actual adapter's transaction construction or backend interpretation.

If a required premise is violated or its support becomes unavailable, the
affected proof claim cannot remain unqualified. Admission policy may stop the
affected operation, accept a named weaker assurance class, or require operator
action. It must not silently keep the old certified label. In-flight commands
whose outcomes are uncertain still require resolution; qualification failure
does not establish their rejection.

*** Acquired prestate and actual transaction state

An acquired prestate can support preparation and construction checks. It is not
automatically the backend's internal prestate at the later incorporation point.
The protection mechanism must establish the needed relationship despite that
interval.

The design does not universally require the backend to expose an internal
prestate token. A sufficient qualified guard, isolation contract, or conditional
transition may establish the required refinement without such a token. Where
that relationship is only a backend premise, it must remain named as such.

Reading before and after a concurrent transaction also does not necessarily
produce its exact state pair. Another writer may intervene. A read guaranteed
to include a commit can legitimately include later effects. That is useful
visibility evidence, but not an exact immediate poststate witness.

*** Commit evidence, visibility requirements, and observations

Submission acceptance, transaction completion, and query visibility may be
different backend milestones. The adapter must distinguish them. A log position
allocated to an aborted or merely submitted transaction must not be presented
as evidence that the domain command incorporated.

After a confirmed commit, the adapter may issue a progression requirement that
an authoritative read must satisfy to include the relevant effect. The read
path must enforce that requirement or return a typed unavailable/unsupported
result. It must not silently read from an older available snapshot and label it
current enough.

The actual observation can be later than the minimum requested basis. The
evidence must distinguish a minimum visibility guarantee from an exact observed
basis. It must not relabel the requested minimum as the exact snapshot used.
If the adapter can establish only a lower bound, the observation contract says
so and permits only conclusions justified by that bound.

Temporal interpretation matters separately. A transaction can be visible in
system time while a query at a different valid time returns a different domain
state. Authority/database incarnation, tenant, valid-time selection, system-time
selection, and relevant authorization context are part of scope compatibility.

A restore, fork, or migration may create an authority/database incarnation in
which old tokens have no comparable meaning. The adapter must establish an
explicit migration relation or reject comparison. Equal-looking numbers or
token bytes from different incarnations are not evidence of continuity.

** Scope-aware progression and authoritative acquisition
:PROPERTIES:
:CUSTOM_ID: req-progression-scope
:END:

A progression requirement asks for an observation of a particular meaning at a
sufficient authoritative frontier. It is not merely a token. A later Hotel
observation cannot satisfy a Flight obligation simply because the database
position appears newer.

An admitted acquisition declaration must make the following information
mechanically available, directly or through stable references:

- authority, tenant, database incarnation, and qualified provider;
- entity or query meaning, schema/projection version, and parameters;
- selection, filters, ordering, pagination, and coverage requirements;
- principal/visibility context and the policy for current disclosure;
- valid-time and system-time interpretation;
- the required progression relation and its evidence source;
- the acquisition owner and resource-instance correlation;
- the requested completion milestone: acquisition alone, or acquisition with
  permitted installation/adoption.

An acquisition result includes evidence of its actual scope and coverage, not
just the data. A familiar shape, a token supplied by the browser, or a tag saying
=:authoritative= is not enough to admit it. Admission follows the trusted
acquisition contract from Part II.

*** Query meaning and completeness

Entity contents and aggregate membership are different scopes. A Request card
can establish facts about one Request without establishing the complete board.
A board acquisition must identify its authorized selection, search terms,
filters, sort order, page/cursor interpretation, and completeness claims.

Changing a server-side search or filter changes the query meaning. Sorting a
locally adopted set changes presentation order, not knowledge of authoritative
membership. Neither operation silently grants permission to adopt unrelated
new rows.

An empty query result establishes absence only within the successfully evaluated
authorized scope and coverage. A partial response, timeout, inaccessible page,
or denied query must not become authoritative absence. Privacy policy may limit
which distinctions can be disclosed, but it cannot make a failed acquisition
evidence of a domain fact.

One page can satisfy a requirement for that page under a stable query/cursor
contract. It cannot satisfy a complete-board requirement merely by carrying a
sufficiently recent token. A set of separately acquired pages establishes a
complete common snapshot only when the paging contract supplies that stronger
relationship.

*** Opaque progression and comparison judgments

The progression provider owns token interpretation. Generic Gesso code may
preserve opaque values and ask the admitted provider for supported relations;
it must not infer ordering from string comparison, integer-shaped encodings, or
HTTP arrival order.

Comparison distinguishes at least equivalent, advances, precedes, established
incomparable, and not established. Invalid or incompatible evidence is also a
typed failure. Unavailable comparison is not established incomparability, and
neither is equality.

For some providers, equality is the only available relation without additional
evidence. Equality of admitted tokens in a compatible context can be useful;
equality of untrusted bytes is still just equality of bytes. An advancement
witness must be admitted from a provider capable of establishing that relation
and bound to its endpoints, scope, incarnation, and relevant contract version.
Validating the witness map's shape alone does not establish its truth.

*** Worked example: travel observations with different scopes

Consider two requirements for one authorized travel-planning session:

| Requirement | Scope and coverage | Progression requirement |
|-------------+--------------------+-------------------------|
| F | Flight 17 availability, specified cabin and fare-class selection, projection v1, session visibility context, declared temporal policy. | Visibility through admitted flight requirement PF20. |
| H | Hotel 9 availability for check-in D1 and check-out D2, specified room/occupancy selection, projection v1, the same permitted context where applicable. | Visibility through admitted hotel requirement PH24. |

The symbols PF20 and PH24 are illustrative opaque values. Their numeric-looking
suffixes do not authorize arithmetic. Even if both are realized by one XTDB
database, scope remains part of the requirement.

Suppose the provider and acquisition boundary establish the following evidence:

| Observation | What it can establish |
|-------------+-----------------------|
| Full Flight 17 projection, correct cabin/fare selection, compatible time/context, admitted advancement through PF20. | Satisfies F. |
| Hotel 9 projection with advancement through PH24. | May satisfy H; it does not satisfy F. |
| Flight 17 seat count alone at a newer compatible basis. | Satisfies only an appropriately narrow seat-count requirement, not the full F projection. |
| Hotel 9 for different dates. | Does not satisfy H even if its basis is later. |
| Correct hotel query, first page only, when H requires complete offered-room coverage. | Does not satisfy H's completeness obligation. |
| Correct values with an unadmitted basis tag. | No authoritative satisfaction judgment follows from that tag. |
| Correct selection at incompatible valid time or visibility context. | Requires a declared relation; it is not silently interchangeable with the requested scope. |

F and H may be fulfilled by separate admitted acquisitions. That does not
establish that the combined travel display is one atomic database snapshot, or
that either offer remains reservable. Booking eligibility remains a current
authoritative model obligation at the booking boundary.

*** Requirement satisfaction and safe combination
:PROPERTIES:
:CUSTOM_ID: req-progression-combination
:END:

The executable semantic core defines the following relations for each supported
scope and progression contract. The notation does not prescribe API names.

- =satisfies(O, R)=: admitted observation O establishes R's scope, coverage, and
  consistency requirements.
- =entails(R2, R1)=: every admitted observation satisfying R2 also satisfies R1.
- =combine(R1, R2)=: a representation retaining both requirements, or an explicit
  unsupported result where the requested representation cannot do so.
- =fulfills(E, B)=: the admitted evidence collection E fulfills every obligation
  in bundle B at each obligation's declared completion milestone.

The default conservative combination is conjunction: retain both obligations.
A provider may offer a sound compact representative or join. A successful
single-observation combination must satisfy the law:

#+begin_example
satisfies(O, combine(R1, R2))
  implies satisfies(O, R1) and satisfies(O, R2)
#+end_example

When no one observation can satisfy both, a bundle may allow separate
acquisitions. Bundle fulfillment does not imply a common snapshot. It also does
not erase the distinction between acquiring evidence and adopting it.

Dropping R1 because R2 supersedes it requires established entailment, including
compatible scope and coverage. A later-looking token for another query is not
such evidence. Unknown comparison does not authorize dropping either obligation.

Normalization preserves semantic meaning and is deterministic where stable
identity depends on it, under the declared semantic/provider versions. If the
implementation coalesces duplicates, reorders, or regroups requirements, it must
establish the corresponding idempotence, commutativity, or associativity of
obligation meaning. These need not be claims of byte-identical representation.

A stronger combined requirement may preserve safety while making acquisition
impossible. A liveness claim must therefore establish that the strengthened
requirement is satisfiable by the admitted read path under its declared progress
premises. Soundness is not permission to promise eventual acquisition of an
impossible join.

*** Bounded representation and backpressure

One in-flight request does not imply bounded retained debt. A coordinator may
accumulate incomparable scopes or requirements while that request is pending.
Its bounds must distinguish request concurrency, obligation count, representation
size, and any finite abstraction used in model checking.

For a finite scope domain with sound subsumption, one representative per scope
may suffice. Otherwise the implementation may retain bundles, partition work,
apply backpressure, request an authorized broader acquisition, or report an
unsupported configuration. It must not silently discard obligations to make a
counter stay below a limit.

Broader acquisition requires permission and a coverage contract. It does not
automatically authorize broader visible adoption. A user who has not chosen to
refresh board membership must not acquire a new visible board merely because
the coordinator compacted its metadata.

Resource retirement may legitimately end obligations scoped solely to that
resource, under an explicit retirement policy. It must not erase durable
command uncertainty or work owned elsewhere. The reason for retiring an
obligation is part of its lifecycle semantics, not a claim that it was satisfied.

*** Mixed observations do not imply an aggregate snapshot

A board may retain membership justified at P17 while one Request card is
updated through a later correlated operation result at P19. That can be a valid
application state under its adoption policy. It is not a complete board snapshot
at P19.

The representation must preserve enough provenance to support only the claims
actually established. It need not use a universal persisted fact graph, one
mutable object per fact, or a per-entity integer revision. It does need to
distinguish the scope of the later card observation from the older board
membership observation.

Replacing an adopted projection requires its declared supersession or
reconciliation relation. An incomparable observation may remain useful evidence
without being eligible to replace the current display. Equivalent bases also
do not make different projection schemas, principals, or query meanings
interchangeable.

*** Progression flows through propagation

When an authoritative change creates a required invalidation, the propagation
path preserves enough information for the resulting reread to include that
change. The sequence is:

1. Qualified outcome evidence establishes the authoritative change.
2. The durable change/publication record carries an admitted progression
   requirement and affected scope information.
3. Routing delivers an advisory to a relevant participant under its transport
   and recovery contract.
4. The participant's acquisition requests a scope and progression sufficient
   to cover the relevant obligation.
5. The acquisition boundary admits only evidence that actually establishes the
   promised coverage and visibility.

The advisory remains advisory: it can establish that an acquisition is needed
without supplying the new authoritative contents. Preserving progression does
not require every stage to repeat the complete token; a protected reference to
the requirement is sufficient when it can be resolved under the contract.

A tokenless advisory needs an alternative qualified fence or acquisition rule
that prevents a satisfying reread from preceding the triggering change. Merely
reading something newer than the participant's old display may still miss that
change. If the transport cannot supply such a rule, the weaker guarantee must
be explicit.

*** Initial acquisition and subscription races

Initial content for a managed projection participates in the same scope,
authority, progression, and installation contract as refresh content. Being
server-rendered does not exempt it. The owner/resource instance and any initial
basis claim must be established through the admitted bootstrap path.

The relationship between initial read and subscription must avoid an uncovered
interval when the application promises eventual awareness of changes. Suitable
strategies include an admitted read/subscription fence, replay from a durable
cursor, buffered changes across registration, or another qualified recovery
mechanism. Each strategy states how it handles reconnect and owner replacement.

A periodic authoritative refresh may provide a weaker eventual-awareness
strategy under explicit scheduling and availability assumptions. It does not
prove delivery of every invalidation. A router's successful local subscription
does not by itself prove that no relevant upstream change was lost before its
interest became visible.

*** Observed basis is not authority to commit

A browser-supplied observed basis can be useful as an untrusted input to
freshness handling. It does not prove that the browser acquired or adopted the
corresponding data, and it does not establish current authorization. Stronger
claims require admitted evidence bound to the relevant observation and actor.

The server must also bound and validate requested consistency behavior. A
malformed, foreign-incarnation, or unattainable token must not force unbounded
waiting or silently downgrade to an unconstrained read.

Advancement alone does not invalidate a command. The model checks its actual
business preconditions. When the operation explicitly requires an expected
domain version, the server enforces that condition as part of command meaning;
when it does not, unrelated database advancement is not a reason to reject.

Dependency upgrades must not silently change token interpretation, read
visibility, temporal defaults, or command/result compatibility. The assembly
and qualification artifacts bind the relevant provider contract, and persisted
requirements need an explicit compatibility or migration policy.

** Advisory obligations and adoption
:PROPERTIES:
:CUSTOM_ID: req-advisory-discharge
:END:

An advisory obligation records what a participant must still acquire or adopt
under the application's declared policy. It is scoped debt, not a Boolean
global dirty flag. Its meaning includes the required observation, coverage,
progression, owner/resource lifetime, and completion milestone.

Advisory knowledge and adopted authoritative knowledge remain separate. A
participant can know that newer relevant authority exists while deliberately
retaining its current visible board until the user chooses Refresh. A glow or
toast may represent that debt without adopting new membership.

The obligation representation must distinguish:

- an obligation to acquire admissible evidence;
- an obligation to acquire and semantically adopt it;
- any required physical installation that realizes that adoption;
- retirement or transfer of an obligation under an explicit lifecycle policy.

These distinctions need not create four public APIs or four universal stores.
They must be explicit wherever a completion claim depends on them.

*** Acquisition, permission, installation, and adoption

The following milestones cannot be collapsed:

| Milestone | Established fact |
|-----------+------------------|
| Acquisition completed | An admitted observation has arrived with the required source, scope, and correlation. |
| Installation permitted | Current owner, resource, scope, progression, and presentation policy allow this proposed installation. |
| Installation completed | The permitted physical effect actually completed under the realization contract. |
| Adoption recorded | The semantic state now treats the justified contents or membership as adopted, using the required completion evidence. |

For an acquire-only obligation, the first milestone may suffice. For an
acquire-and-adopt obligation whose realization includes a DOM update, merely
returning true from =can-install?= or emitting an HTMX allow-swap decision does
not suffice.

The final installation-right check and the physical mutation must be serialized
against competing owner changes and relevant installations, or protected by an
equivalent mechanism. Checking a right, yielding, and later mutating an arbitrary
replacement target can install into the wrong resource instance.

The physical completion or failure is correlated to the admitted installation
effect, owner, target instance, and observation. Adoption and debt discharge use
that evidence under the current semantic state. A synchronous implementation
may establish these milestones together; an asynchronous shell needs explicit
completion/failure handling.

If a physical update can partially apply, the realization must define that case.
It may require repair, authoritative reacquisition, or a representation-unknown
state. It cannot report complete installation merely because the effect began.
Similarly, loss of a completion event requires a reconciliation path if the
physical representation may already have changed.

*** Worked example: two advisories during one refresh

Let B denote one complete authorized board query: Organization selection,
filters, search, ordering, projection version, visibility context, and temporal
policy are fixed for this example. Its owner and target are one admitted
resource instance. The board has adopted an observation at P17.

The provider establishes that an observation through P18 includes the change
announced by O1, an observation through P20 includes the change announced by O2,
and P21 covers both requirements in this compatible scope. It also establishes
the advancement relations used below. These are admitted provider judgments,
not arithmetic inferred from the names.

Advisory O1 creates an acquire-and-adopt obligation for B through P18. The user
chooses Refresh. The coordinator allocates a fresh acquisition resource A1 under
the managed lifecycle and issues the read for O1's requirement. Its identity is
not merely a reusable request number; reuse would need a separate admitted
instance discriminator.

While A1 is outstanding, advisory O2 creates a further obligation for B through
P20. The coordinator must retain O2. Completing A1 must not restore an old copy
of the obligation set captured before O2 arrived.

Assume the application permits adoption of a non-regressing partial advance
while stronger advisory debt remains visible. The sequence is:

| Event | Adopted board | Retained acquire-and-adopt debt | Required action |
|-------+---------------+--------------------------------+-----------------|
| Initial admitted state | P17 | None | No refresh required. |
| Receive O1 | P17 | O1 through P18 | Offer or schedule acquisition under the product policy. |
| Start A1 for O1 | P17 | O1 | Record current acquisition ownership and requirement. |
| Receive O2 | P17 | O1 and O2 through P20 | Retain O2 while A1 remains outstanding. |
| A1 completes with admitted B observation at P18 | P17 | O1 and O2 | Validate coverage; prepare a permitted installation. |
| Installation is allowed but has not completed | P17 | O1 and O2 | Keep adoption debt; permission is not completion. |
| Installation of P18 completes and is admitted | P18 | O2 | Adopt the covered advance and discharge O1 only. |
| Later permitted acquisition and installation covers P20 | At least the required frontier under provider evidence | None of these two obligations | Discharge O2 using its actual coverage and completion. |

If A1 instead returns an admitted B observation at P21 and its installation
successfully completes, that evidence can discharge both O1 and O2. The
coordinator checks the latest obligation set at completion, not only the set
that happened to start A1. The acquisition's actual evidence can be stronger
than its requested minimum.

If installation fails, neither acquire-and-adopt obligation is discharged by
that attempt. The acquired observation may remain available as evidence under
its lifetime and disclosure contract, but the visible board has not thereby
adopted it.

If a different permitted path already adopted P21, the late P18 response must not
roll the board backward. The existing adopted P21 evidence may already satisfy
O1 and O2; that is a separate justification for discharge. Rejecting the late
installation does not mean the coordinator must keep debt that independently
admitted adoption evidence has already fulfilled.

An application may instead require an acquisition to satisfy all current board
debt before adopting anything. Under that policy, P18 is retained or discarded
as acquired evidence and the coordinator requests enough evidence for P20.
Either policy is valid when declared; the framework must not switch between
them accidentally according to response timing.

*** The coordinator's semantic obligations

The example is implemented through admitted transitions, not direct mutation by
arbitrary transport callbacks. A useful transition decomposition is:

1. =advisory-received=: admit source and scope, then add or soundly combine debt.
2. =acquisition-requested=: allocate the managed owner/resource and bind the
   requested scope and progression to a declared effect.
3. =acquisition-completed=: admit the effect completion and observation, then
   determine which requirements its evidence can cover.
4. =installation-requested=: propose only the permitted effect for the current
   target and owner; preserve obligations still awaiting adoption.
5. =installation-completed=: admit actual completion, update justified adoption,
   and discharge only obligations fulfilled in the current state.
6. =acquisition-failed= or =installation-failed=: retain unresolved obligations,
   release or retire resources according to policy, and select the declared
   recovery continuation.

These are semantic phases, not a mandatory source-file layout. Part VI specifies
their browser realization and the refinement between DOM effects and semantic
adoption. The permanent executable semantic core owns the transition meaning;
proof artifacts explain why the admitted realization preserves it.

Every completion checks current owner and resource-instance correlation. A
response for an obsolete search, principal context, route, or target instance
must not install merely because its database basis is recent. Evidence may be
usable through another declared admission path, but cannot resurrect a retired
execution's private rights.

The obligation set is updated from current state. Removing O1 must not remove a
newer obligation with a superficially similar key, overwrite a concurrently
added scope, or clear a global dirty flag representing several independent
requirements. Sound coalescing may replace the representation, but must preserve
the combined meaning.

*** HumanHelp's selective adoption policy

HumanHelp can use these generic contracts to show the creator's own committed
Request immediately through a correlated admitted result, while other viewers
receive an advisory and explicitly refresh board membership. The policy must
state which scopes a correlated operation result can update and how that update
relates to the existing board selection.

A card outcome can update an already adopted Request without proving a complete
new board query. An operation that introduces or removes a visible row needs an
explicit membership-adoption rule. Filters, sorting, retained selection, scroll
continuity, and optimistic overlays must not cause that scope distinction to
disappear.

The framework does not hard-code HumanHelp's particular choice. It provides
checked acquisition, ownership, progression, installation, and obligation
mechanisms from which the application declares that choice.

** Assurance obligations and acceptance cases

Part IV's assurance is a chain of bounded claims. The semantic transition must
express the intended rule; construction must bind it to the actual inputs and
implementation; the complete submission must realize the protected effect;
qualified backend behavior must justify the outcome; propagation and acquisition
must preserve scope and progression; installation must justify adoption.

A report uses Part I's separate claim dimensions: proposition, subject,
mechanism, premises, coverage, applicability, and status. It distinguishes
derivation or construction checking, runtime enforcement, testing, and explicit
assertion. Named environmental premises qualify a claim; conditionality is not
an additional proof mechanism. These descriptions are not interchangeable
assurance grades. A strong proof of an abstract fragment cannot conceal an
unexamined physical execution boundary.

*** Required invariant families

The supported construction and runtime must establish, or explicitly qualify,
at least the following property families:

1. *Binding fidelity*: operation, command, canonical arguments, principal,
   authority, target, and realization cannot be silently substituted between
   admission, submission, outcome, and reconciliation.
2. *Authoritative safety*: each incorporated transition satisfies its protected
   business conditions and declared frame under the backend/writer premises.
3. *Command consistency*: compatible repetition does not incorporate again;
   incompatible reuse cannot overwrite the old binding; terminal disposition is
   reported only with evidence of its declared scope.
4. *Truthful uncertainty*: absence of outcome evidence, timeout, and local
   retirement do not manufacture non-incorporation.
5. *Recoverable required work*: committed operations retain the declared
   command/result and propagation or external-work evidence across promised
   failure modes.
6. *Scoped observation*: acquired data supports only its admitted scope,
   coverage, temporal interpretation, visibility context, and progression.
7. *Justified adoption*: only current permitted installation/adoption paths
   advance adopted knowledge and discharge adoption debt.
8. *Evidence fidelity*: a classification, certificate, or passing test is not
   promoted into a stronger proposition than it establishes.

Liveness claims are separate. They identify scheduling, delivery, backend,
provider, retention, authority, and human-participation assumptions. Safety must
not depend on pretending that those assumptions always produce timely success.

*** Executable conformance cases

The implementation must provide conformance cases for the supported mechanisms,
including negative cases and relevant interleavings. These cases complement
semantic derivations; passing them does not prove arbitrary backend behavior.

| Area | Case | Required observation |
|------+-------+----------------------|
| Target binding | Command names R1; acquisition or submitted mutation targets R2. | Admission or execution rejects the mismatch; no claimed R1 transition is established from R2's state. |
| Claim eligibility | Request is open but already has a helper. | New Claim cannot incorporate under the unclaimed policy. |
| Relationship | Membership belongs to another principal or Organization. | New Claim is not authorized by that Membership. |
| Concurrent authorization | Membership, Organization association, or relevant policy changes after preparation. | Incorporation obeys the declared current-condition policy. |
| Same-command concurrency | Two compatible attempts race. | At most one incorporation; the other resolves or remains unknown rather than inventing command rejection. |
| Different-command concurrency | Two helpers claim the same unclaimed Request. | Only transitions allowed by protected current state incorporate. |
| Replay | Original Claim succeeded, response was lost, Request is now claimed. | Compatible permitted replay returns the recorded outcome without a second effect. |
| Incompatible reuse | Same ID, changed canonical arguments or authority binding. | No overwrite or new incorporation under the old binding; disclosure follows policy. |
| Terminal rejection | A pending attempt races with rejection closure. | The protocol cannot settle rejection while permitting that command to incorporate later. |
| Unknown outcome | Submission may have committed; local response is lost. | Unknown remains until admitted evidence resolves it. |
| Disclosure | A former caller no longer has permission to read a recorded result. | No unauthorized result disclosure and no invented domain rejection. |
| Atomic footprint | Domain update succeeds but ledger/outbox write is removed or fails. | The promised combined transition cannot be reported established. |
| Submission fidelity | A checked fragment is followed by an extra write, changed option, altered target, or weakened guard. | The actual complete submission fails the relevant admission/correspondence check. |
| Return provenance | A copied success report or unrelated callback return is substituted. | It does not establish this invocation's outcome. |
| Frame | Unrelated fields change concurrently before a whole-document replacement. | The frame is preserved or the guarded transition fails. |
| Representation | Missing, nil, false, nested values, and field-name collisions are exercised. | Unsupported cases reject explicitly; supported cases preserve declared semantics. |
| Predicate protection | A row is inserted that defeats an absence, uniqueness, or aggregate condition. | The operation cannot incorporate using an inadequately protected pre-read. |
| Writer coverage | An external writer bypasses a required revision or invariant discipline. | The dependent premise is identified; local writer observation is not reported as universal coverage. |
| Capability lifetime | One capability is raced, reused, or retained beyond its admitted lifetime. | Its use policy is enforced independently of command deduplication. |
| Opaque code | A full-language callback uses an asserted effect contract. | Supported execution remains possible, with the assertion retained in the assurance report. |
| External intent | Provider evidence changes account, operation, amount, currency, or intent identity. | It cannot authorize the expected payment transition. |
| External uncertainty | Provider request times out and later succeeds. | No blind new-key retry; the effect remains recoverable under the provider contract. |
| Cancellation race | Authorization arrives after cancellation was requested. | The actual effect enters the declared void, compensation, or review path. |
| Scope | A newer Hotel or single-card observation is offered for a Flight or complete-board obligation. | The unrelated or narrower scope does not discharge the obligation. |
| Temporal context | Token bytes match but incarnation, valid time, query, or visibility context differs. | Compatibility is established explicitly or the substitution is rejected. |
| Acquisition failure | An empty-looking result actually represents failure, denial, or partial coverage. | No authoritative absence or completeness claim is created. |
| Adoption | Installation is allowed, then fails or targets a retired owner. | Acquire-and-adopt debt is not discharged by permission alone. |
| New advisory | O2 arrives while an acquisition for O1 is pending. | Completion preserves O2 unless its actual evidence and adoption cover O2. |
| Late response | P18 completes after compatible P21 was adopted. | No regression; independently fulfilled debt need not be retained. |
| Subscription race | A relevant change occurs between initial read and effective subscription. | The declared fence, replay, or recovery mechanism covers the gap, or the weaker guarantee is explicit. |
| Retention | A stale retry arrives after result eviction. | The namespace/horizon/tombstone policy prevents an unjustified duplicate effect. |
| Dependency change | Backend or adapter behavior changes beneath a retained proof claim. | Relevant qualification is invalidated or re-established; old evidence is not silently reused. |

The semantic cases should be derived from the same canonical definitions used
for construction wherever practical. Independent adversarial and mutation cases
then challenge the correspondence boundary rather than merely restating the
implementation. Backend integration cases exercise the actual qualified adapter
and its relevant transaction/read paths.

Test fixtures must distinguish admitted evidence from illustrative maps. A
fixture that creates an advancement witness by changing a token field does not
test provider truth. A fixture that returns a successful predicate without
performing installation does not test adoption. A diagnostic resolver that
finds a retained record does not demonstrate a durable recovery driver.

*** Completion criteria for this part

An implementation satisfies this part for an admitted operation family when its
public interface, canonical semantics, construction, physical submission,
backend profile, outcome interpretation, command policy, propagation, and
acquisition/adoption paths form one inspectable contract. Supported mechanisms
must reject mismatches early and explain the exact unsatisfied obligation.

Unsupported proof cases do not disappear. They are either implemented through
another supported mechanism, admitted with explicit accepted assertions under
policy, or rejected with a usable explanation. Dynamic unavailability has an
explicit continuation. Success means the claimed semantic effect and evidence
were established, not merely that the application started without errors.

An assertion cannot repair a missing operation binding, malformed schema,
unresolved capability, or contradictory effect declaration. It supplies a named
premise about otherwise well-formed behavior; structural admission obligations
still have to be discharged.
