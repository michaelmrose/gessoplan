## Question and method

Does a command such as HumanHelp Claim **C42** retain exactly the same business meaning when its first HTTP request is lost, a different host retries it, the original browser execution retires, an authorized participant recovers the historical result, a current Request view changes, and a new release is activated?

A locally reviewed section cannot answer this across its own boundary. This review tested the joined rules against the original R4 distinction between command disposition and participant uncertainty, the R4 sleeping-browser C77 example, the preferred R5's versioned source-first operation architecture, and the now-accepted R5.1 sectional audits. R4 \`main\`, R5 \`r5\`, and R5.1 have different editorial roles; their agreement is not itself independent formal evidence.

## Ownership and non-equivalence

| Coordinate | Owner and required evidence | What it must *not* imply |
| --- | --- | --- |
| Business operation | Original application model and independently required capabilities | A rendered affordance or typed rule proves current eligibility |
| Principal and authority | Trusted authenticated context, scope, actual current guards | A browser actor, role label, command ID or executing host possesses authorization |
| C42 identity | Immutable scoped command binding: canonical inputs, principal, operation, authority and version/compatibility | UUID equality alone grants idempotence, replay, or disclosure |
| A1/A2 attempts | Actual identified guarded physical submissions and their own outcomes | A1's failure settles C42 if A2 may still incorporate |
| Historical command disposition | Qualified, binding-compatible incorporated record or exclusion/closure evidence | Timeout, HTTP 200, stale negative read or a current Request card establishes that disposition |
| Current Request state | Authorized basis-/coverage-qualified domain observation | A later card proves who incorporated C42, or C42 success proves the present owner |
| Participant knowledge | Admissible role-local evidence plus current disclosure rights | One actor knows every host's evidence or can read protected history |
| Browser execution | Currently admitted plan, resource instance, effect generation and actual target ownership | Command recovery restores old P7 callbacks or mutates P8's reused target |
| Live acquisition | Durable selected notification work, qualified scope read and actual browser adoption | SSE delivery creates a remote read grant, or advisory alone clears debt |
| Proof and release | Source-bound proposition, independent requirement denominator, trusted issuer and applicable physical evidence | A proof-shaped value, abstract model check or candidate build proves active installation |

A historical result, attempt acknowledgment, abstract state transition, visible board state and browser presentation status are different propositions. Use an evidence-specific vocabulary for each.

## Paired positive and adverse histories

1. **Unknown delivery and compatible recovery.** A1's response is lost after possible incorporation; a currently admitted read finds a fully compatible C42 result. Historical replay is disclosed where authorized, without performing another incorporation. **Forbidden:** timeout → \`:rejected\`; C42 → new C43 as an automatic retry; compatible result → unsupported claim that A1 was the winning attempt.

2. **One failed physical attempt, another succeeds.** A1 aborts on a protected guard; compatible A2 incorporates C42 through shared qualified exclusion. A1 is failed, C42 is incorporated. **Forbidden:** persisting a terminal rejection supposedly written by A1's aborted transaction, or treating one failed attempt as durable non-incorporation of C42.

3. **Two different commands compete.** C42 and C43 are separate, otherwise eligible Claim intents on the same Request. Command deduplication stops duplicate *C42*, but cannot alone prevent two different active primary RequestAssignments. **Required:** source-owned current business guards, transaction-internal protection, uniqueness and coverage of other protected writers. **Forbidden:** declaring the application safe because the command table has unique keys.

4. **Later state is not historical causality.** C42 Claim commits; a later independent Reassign replaces Alice. A scoped read can reveal the new primary; a permitted C42 result can separately reveal historical success. **Forbidden:** identifying C42's origin from the present card, or concluding the old command failed because ownership changed.

5. **Retention, expiry and backup.** Erasure of sensitive result payload may coexist with a retained command fence. Old submitted/offline attempts must remain excluded according to the declared horizon. **Forbidden:** deleting prevention evidence and then accepting old work, or treating a restored database's missing C42 row as proof of noncommit without migration/epoch qualification.

6. **Old browser and new deployment.** P7 sleeps with unresolved C42; P8 becomes active. The old machine and physical effects retire. A new qualified path may reconcile C42 without reviving P7. **Forbidden:** treating parseability of P7 bytes as execution compatibility, reusing a stale DOM ID as effect permission, or changing bound inputs under the same command ID.

7. **Private command and advisory-only remote state.** Bob can receive a Live notice and may have permission to read a current Request but not C42's historical private result. Bob's explicit one-use Refresh grants only its stated scope. **Forbidden:** leaking C42's record through outcome/error shape, ungranted SSE-triggered remote reads, or clearing advisory debt without actual sufficient acquisition and installation.

8. **Physical readback and attribution.** A pinned XTDB snapshot observes a matching command row and transaction-related metadata, but cannot identify the winning submission. The report supports only its qualified observation and compatible historical recovery. **Forbidden:** invocation-specific \`:committed\` based on co-observation alone, or an abstract proof being promoted to physical transaction evidence.

9. **Nonvacuous success.** A real, authorized Claim must be representable as a positive incorporation and compatible recovered presentation under the chosen qualification profile; forbidden effects must be tested independently. **Forbidden:** accepting reject-all semantics, omitting original mandatory HumanHelp capabilities from generated denominators, or announcing release solely from a green generated subset.

## R4 preservation and R5.1 architectural improvement
