# R5.1 Part IV — 04.10 R4 preservation and Gesso correspondence

**Section:** `r5-source/04/04.10-fx-value-flow-and-lifecycle.org`  
**Disposition:** tenth substantively reviewed Part IV candidate section.
The normative Org describes the finished framework; this record describes
the source comparison and currently evidenced implementation boundaries.
Part IV and the full R5.1 plan remain editorial drafts.

## R4 preservation baseline

R4 Part IV, “FX value-flow architecture” through “Post-commit delivery
debt is explicit,” separates ambient context, the original machine
invocation argument, and previous-state output. Its Biff illustration
uses `:start (fn [ctx operation-input] ...)` and later
`:next (fn [ctx previous-output] ...)`. This is a semantic contract,
not a preference for one syntactic FX interpreter.

The R4 section also requires:

- Explicit state/output dependencies, rather than turning context into a
  mutable bus of hidden intermediate data.
- An origin-bearing trusted capability context. Untrusted input cannot
  overwrite principal, database, or clock capabilities by map merge;
  knowably missing capabilities should fail early.
- No provenance upgrade from client data to business authority, or from
  local query results to remote participant knowledge, merely because
  an FX state processed those values.
- Interpreter-defined ordering and completion. A vector representing an
  effect's *value* is not intrinsically a sequence of effects; ordering
  is not atomicity or durability.
- Model-owned operation contracts independent of private FX internals;
  graph/multistate facilities obey the same explicit value-flow rule.
- After incorporation, propagation failure remains delivery/recovery
  debt, never a retroactive domain rejection. Commit-before-publication,
  lost settlement, reconnection and duplicated delivery are distinct
  scenarios.
- A convergence claim must specify real recovery: durable work/change log,
  qualified acquisition, explicit Refresh or equivalent, with the
  appropriate process-loss and fairness assumptions.

These obligations remain in the revised R5 section.

## R5 improvements retained

R5 keeps the FX contract flexible for ordinary Clojure. It makes the
capability boundary and effect metadata introspectable without requiring
Choreo to understand each state graph. It distinguishes phase-aware
failure classes, opaque effect premises, transaction-related value
sampling, durable intent alternatives, subscriber interest races,
single-node versus multi-node routing as physical implementation
details, and actual publication milestones through participant
adoption. It preserves deliberate best-effort contracts rather than
making a universal durable queue mandatory.

The schematic `{:fx/type :sequence ...}` illustration remains clearly
non-executable until registered step definitions and interpreter
semantics give it meaning. We did not restore R4's examples as a second
required DSL, nor prescribe one generic provider or bus implementation.

## Focused normative edits

1. Restore explicit separation of invocation inputs, earlier outputs and
   ambient capabilities; state how later graph/FX steps receive values.
2. Require trusted context provenance, prevent untrusted shadowing and
   fail early on known missing capabilities, without pretending
   mutable authorization becomes permanent.
3. Make state boundaries preserve client/authority/remote-knowledge
   provenance; keep public model effects independent of the private FX
   machine graph.
4. Disambiguate effect-vector data, ordering, completion and atomicity.
5. Add a phase/evidence table distinguishing pre-submission failure,
   unknown submission, post-commit delivery failure, and lost
   settlement/rendering after a confirmed commit.
6. Require an actual commit-before-publication recovery mechanism and
   subscription-inception path for any stated automatic convergence.
7. Add seven paired accepted/adversarial construction and recovery cases
   to prevent both underchecking and reject-everything vacuity.

## Inspected Gesso application-assurance v1622

In `src/gesso/model/core.clj`, generated create and update
`fx/machine` states receive original operation input in `:start`;
later states receive explicit state-result maps containing selected
values and the transaction result. The code uses
`:biff.fx/next`/`:biff.fx/return` and `model.tx/transact-effect`.
This is concrete positive correspondence for the basic value-flow
distinction, **not** proof of every handwritten application FX path,
capability origin, or independent Choreo refinement.

In `src/gesso/model/tx.clj`, generic transaction plans explicitly
separate commands, guards, assertions and semantic changes. That
representation does not itself certify arbitrary effect sequencing
or source-owned domain policy.

In `src/gesso/live/core.clj`, `transact-and-notify!`
distinguishes a pre-commit XTDB failure from an already-committed
transition whose subsequent `:sync` emit or `:async` submission
fails; `post-commit-delivery-failure?` recognizes the latter.
`test/gesso/live/core_test.clj` contains fixtures for pre-commit
failure, partial synchronous/async delivery, debugging failure,
and no reexecution of a committed mutation after publication failure.

These inspected fixtures were **not executed** during this document
revision. Classifying the post-commit failure is not equivalent to
durably recording the publication work, automatically recovering
after a process crash, establishing all observer interests, or
proving that a remote browser installed a fresh authoritative view.
Those are separate application/backend/Live obligations.

## Cross-part joins and future verification

- **Parts I–II:** capability and rule provenance, participant identity,
  authority scope, typed truth versus observation, and opaque premises.
- **Part III:** a result passing through local FX does not become a
  message or role-local knowledge without its declared pathway.
- **Part IV 04.01–04.09:** model-owned operation semantics, transaction
  guards, compatible command replay, provider uncertainty and durable
  external work. Retry scopes must not accidentally re-run the wrong
  effect class.
- **Part IV 04.11–04.17:** backend basis and read visibility,
  progression requirements, delivery/adoption milestones and evidence.
- **Parts V–VII:** browser ownership and actual installation,
  Live interest inception, deployed route/writer/worker coverage, and
  physical delivery qualification.
- **Parts VIII–X:** real HumanHelp acceptance, proof obligations and
  independent physical implementation correspondence.
- **Parts XI–XII:** release gates must test paired admitted/adverse FX,
  post-commit failure and recovery, not just parse an effect descriptor.

No whole-plan certification, complete provider/XTDB deployment proof,
Live reconnect test, browser integration test or universal formal
refinement was established by this editorial revision.
