# R5.1 Part IV — section 04.01 R4 preservation and Gesso correspondence

**Source:** `r5-source/04/04.01-model-integration.org`
**Disposition:** first substantive Part IV section review; Part IV as a
whole is still an unreviewed R5.1 draft. The canonical Org describes
the *finished* Gesso, not current implementation status.

## Comparison with R4

R4 Part IV, under `Model integration`, explicitly required:

- A model's domain/schema/graph/FX internals below its narrow public
  `core` interface, with choreography consuming public model semantics
  rather than implementing or bypassing them.
- The semantic placement test: does a rule still matter when invoked
  synchronously in a single JVM without a browser/network protocol?
- Cross-model dependencies through Membership/Organization public
  interfaces, without leaking their private storage implementation.
- A higher-level flow/choreography owner for genuinely cross-model
  workflows such as onboarding, rather than turning the initiating
  model into an arbitrary coordinator.
- HumanHelp business policy staying in HumanHelp rather than becoming
  hard-coded generic Gesso semantics.
- Typed rule well-formedness versus independent correctness of product
  intent; permitted full-language host behavior is not automatically
  mechanically proved.

The stronger R5 source already preserved those requirements and added
exact operation version, trusted principal, replay/disclosure,
uncertainty, progression and source/implementation assurance claims.
It explicitly warns that a registered callable or copied inspection map
does not confer authority, and that direct trusted writers outside
Gesso may violate invariants for *other* operations.

## Defect resolved: cross-model read versus commit-current guard

The original 04.01 said a coordinating operation *may* protect public
cross-model commitments in one transaction, but did not sufficiently
explain the difference between an earlier public Membership query
and the current Membership guard actually enforced by the Request
Claim transaction. Consequently, a model author might mistake a
previously true or wire-supplied `claim-allowed?` value for an
authoritative binding of the public business rule.

The revision now requires a public rule dependency to retain its
logical subject, trusted parameters, relevant authority, read
dependencies and necessary temporal enforcement point. The operation
must justify the installed backend guard/assertion or a specifically
qualified stability premise for the same actual protected decision.
This does not require disclosing private XTDB details or freezing a
specific compiler/helper API.

Five conformance cases distinguish:

1. Valid atomic Request/Membership/Organization rule composition.
2. Revocation between a preliminary read and the actual Claim commit.
3. Caller-forged authorization Boolean.
4. Legitimate public-rule composition without private FX/schema access.
5. Unsupported backend atomicity despite apparently successful reads.

There is also an explicit deployment-invariance bridge: single-node
and multi-node Gesso have one model policy and authoritative
incorporation contract; router placement/latency does not define a
new business policy.

## Actual Gesso implementation evidence inspected

At `michaelmrose/gesso` branch `application-assurance`, v1622:

- `gesso.model.core` compiles ordinary model descriptors into Malli
  persistence, Graph lookup/projection, simple FX operations and Biff
  module assembly; complex relationships and workflows remain
  application-authored.
- `gesso.model.command` defines version/expected-state guards as
  generic persistence prerequisites, **not an intrinsic
  authorization proof**.
- `gesso.model.tx` composes commands, guards, assertions and Live
  changes in generic atomic transaction mechanics; its own
  documentation explicitly does not own domain transitions or
  authorization policy.
- `gesso.model.resolved-operation` accepts trusted callbacks and
  optional table/target/effect contracts for an application operation.
  This code is not, by its interface alone, a proof that every
  installed physical writer is covered.
- `gesso.assurance.admission` issues scoped in-process structural
  admission handles, and `gesso.assurance.dependency` checks
  source-relative dependency graphs. Neither establishes the
  business proposition nor grants production authorization.
- `gesso.assurance.proof.operation-interface-composition` analyzes
  alternative operations over shared abstract state, explicitly
  **not** their sequentially atomic physical transaction.
- Inspected `test/gesso/model/command_test.clj`,
  `test/gesso/model/tx_test.clj` and
  `test/gesso/assurance/proof/operation_interface_provenance_mutation_test.clj`
  for coverage topics and limitations; tests were **not executed**.

These sources support the value of specifying a cross-model
composition/physical-enforcement join. They do not establish that the
finished guard-qualified feature already exists or that v1622
production enforcement is formally certified.

## Remaining cross-part obligations

- **04.02–04.05:** qualify the actual public Claim invocation, plan
  construction, current Membership/Organization read dependencies,
  full authoritative backend frame and post-state.
- **04.06–04.08:** reconcile compatible command replay with
  new-incorporation guards; don't apply new-claim eligibility to a
  permitted recorded-success replay.
- **04.09–04.10:** external effects and postcommit publication remain
  separate obligations under their own identity/uncertainty contracts.
- **04.11–04.16:** scope-complete XTDB observations, authoritative
  progression and browser selective adoption must retain current
  permission and actual installed-state evidence.
- **Parts VII, IX–XI:** source-derived public model contracts must
  be connected to real registered handlers/writers and qualified
  backend physical enforcement, not only a structurally coherent
  interface or abstract finite proof.
- **Parts X/XII multi-node:** the same public model and Claim
  semantics operate on all web hosts; distributed invalidation
  routing and recovery are implementation choices, not alternate
  business semantics.

## Documentary checks and limits

The change is restricted to 04.01, published Part IV, this audit and
the Part IV source README. The remaining 16 Org units are unmodified.
The published part is the exact concatenation of those 17 sources.
The Part IV root heading and original anchor IDs remain intact.
No actual runtime, XTDB, browser or theorem test is claimed from
this editorial revision. `python3 script/assemble_r5.py --check`
was not executed in a repository checkout; byte-exact GitHub
readback and structural checks supply the documentary verification.
