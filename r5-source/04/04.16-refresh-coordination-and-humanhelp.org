*** Worked example: two advisories during one refresh

Let B denote one complete authorized board query: Organization selection,
filters, search, ordering, projection version, visibility context, and temporal
policy are fixed for this example. Its owner and target are one admitted
resource instance. The board has adopted an observation at P17.

The provider establishes that an observation through P18 includes the change
announced by O1, an observation through P20 includes the change announced by O2,
and P21 covers both requirements in this compatible scope. It also establishes
the advancement relations used below. These are admitted provider judgments,
not arithmetic inferred from the names.

Advisory O1 creates an acquire-and-adopt obligation for B through P18. The user
chooses Refresh. The coordinator allocates a fresh acquisition resource A1 under
the managed lifecycle and issues the read for O1's requirement. Its identity is
not merely a reusable request number; reuse would need a separate admitted
instance discriminator.

While A1 is outstanding, advisory O2 creates a further obligation for B through
P20. The coordinator must retain O2. Completing A1 must not restore an old copy
of the obligation set captured before O2 arrived.

Assume the application permits adoption of a non-regressing partial advance
while stronger advisory debt remains visible. The sequence is:

| Event | Adopted board | Retained acquire-and-adopt debt | Required action |
|-------+---------------+--------------------------------+-----------------|
| Initial admitted state | P17 | None | No refresh required. |
| Receive O1 | P17 | O1 through P18 | Offer or schedule acquisition under the product policy. |
| Start A1 for O1 | P17 | O1 | Record current acquisition ownership and requirement. |
| Receive O2 | P17 | O1 and O2 through P20 | Retain O2 while A1 remains outstanding. |
| A1 completes with admitted B observation at P18 | P17 | O1 and O2 | Validate coverage; prepare a permitted installation. |
| Installation is allowed but has not completed | P17 | O1 and O2 | Keep adoption debt; permission is not completion. |
| Installation of P18 completes and is admitted | P18 | O2 | Adopt the covered advance and discharge O1 only. |
| Later permitted acquisition and installation covers P20 | At least the required frontier under provider evidence | None of these two obligations | Discharge O2 using its actual coverage and completion. |

If A1 instead returns an admitted B observation at P21 and its installation
successfully completes, that evidence can discharge both O1 and O2. The
coordinator checks the latest obligation set at completion, not only the set
that happened to start A1. The acquisition's actual evidence can be stronger
than its requested minimum.

If installation fails, neither acquire-and-adopt obligation is discharged by
that attempt. The acquired observation may remain available as evidence under
its lifetime and disclosure contract, but the visible board has not thereby
adopted it.

If a different permitted path already adopted P21, the late P18 response must not
roll the board backward. The existing adopted P21 evidence may already satisfy
O1 and O2; that is a separate justification for discharge. Rejecting the late
installation does not mean the coordinator must keep debt that independently
admitted adoption evidence has already fulfilled.

An application may instead require an acquisition to satisfy all current board
debt before adopting anything. Under that policy, P18 is retained or discarded
as acquired evidence and the coordinator requests enough evidence for P20.
Either policy is valid when declared; the framework must not switch between
them accidentally according to response timing.

*** The coordinator's semantic obligations

The example is implemented through admitted transitions, not direct mutation by
arbitrary transport callbacks. A useful transition decomposition is:

1. =advisory-received=: admit source and scope, then add or soundly combine debt.
2. =acquisition-requested=: allocate the managed owner/resource and bind the
   requested scope and progression to a declared effect.
3. =acquisition-completed=: admit the effect completion and observation, then
   determine which requirements its evidence can cover.
4. =installation-requested=: propose only the permitted effect for the current
   target and owner; preserve obligations still awaiting adoption.
5. =installation-completed=: admit actual completion, update justified adoption,
   and discharge only obligations fulfilled in the current state.
6. =acquisition-failed= or =installation-failed=: retain unresolved obligations,
   release or retire resources according to policy, and select the declared
   recovery continuation.

These are semantic phases, not a mandatory source-file layout. Part VI specifies
their browser realization and the refinement between DOM effects and semantic
adoption. The permanent executable semantic core owns the transition meaning;
proof artifacts explain why the admitted realization preserves it.

Every completion checks current owner and resource-instance correlation. A
response for an obsolete search, principal context, route, or target instance
must not install merely because its database basis is recent. Evidence may be
usable through another declared admission path, but cannot resurrect a retired
execution's private rights.

The obligation set is updated from current state. Removing O1 must not remove a
newer obligation with a superficially similar key, overwrite a concurrently
added scope, or clear a global dirty flag representing several independent
requirements. Sound coalescing may replace the representation, but must preserve
the combined meaning.

*** HumanHelp's selective adoption policy

HumanHelp can use these generic contracts to show the creator's own committed
Request immediately through a correlated admitted result, while other viewers
receive an advisory and explicitly refresh board membership. The policy must
state which scopes a correlated operation result can update and how that update
relates to the existing board selection.

A card outcome can update an already adopted Request without proving a complete
new board query. An operation that introduces or removes a visible row needs an
explicit membership-adoption rule. Filters, sorting, retained selection, scroll
continuity, and optimistic overlays must not cause that scope distinction to
disappear.

The framework does not hard-code HumanHelp's particular choice. It provides
checked acquisition, ownership, progression, installation, and obligation
mechanisms from which the application declares that choice.
