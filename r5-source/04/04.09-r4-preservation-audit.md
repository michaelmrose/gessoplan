# R5.1 Part IV — 04.09 R4 preservation and Gesso correspondence

**Section:** `r5-source/04/04.09-external-systems-and-provider-effects.org`  
**Disposition:** ninth substantively reviewed Part IV candidate section.
Part IV remains an editorial draft, and this review does not certify an
actual payment provider, production checkout implementation or backend.

## R4 obligations and counterexamples inspected

R4 Part IV's `External systems require explicit valid intermediate states`
gives a store checkout case with an intentionally false pseudo-atomic
`charge!` plus Order insertion, then a truthful pending Order, durable
payment debt, provider authorization, separate local incorporation,
definitive decline and recovery after provider success followed by local
process failure.

Its substantive requirements survive:

- A local XTDB transaction cannot roll back an arbitrary remote effect.
  A committed pending state is a legitimate business fact.
- The initial local operation records Order intent, compatible command
  identity and required durable provider work in one qualified atomic
  decision. A retried command cannot substitute a payment instrument.
- Remote effect identity and provider idempotency are separate from the
  local semantic command identity and must meet the provider's own scope
  and retention contract.
- Provider authorization and definitive decline require admitted evidence
  before their respective local state changes; an unknown result is
  neither success nor rejection.
- Payment success followed by process loss before local incorporation has
  a recoverable state. Compensation is a new effect, not retroactive undo.
- An Order may be placed on authorization only when that is the declared
  product policy. Actual charge/capture, inventory, fulfillment and
  settlement are separate facts unless their admitted contracts say otherwise.

## Stronger R5 design preserved

R5's preferred version uses an immutable payment intent bound to
merchant/provider account, operation, amount and currency, instrument and
versioned policy. It distinguishes provider idempotency from local command
replay, authenticated but mismatched evidence, duplicate receipts, worker
fencing, cancellation races, provider retention limits, and conditional
liveness. It does not force a universal outbox, one payment API, a mandatory
state enum, or obsolete `authoritative/submit!` demonstration code into
the normative public Gesso API.

The R4 pseudo-atomic code and illustrative `defschema`/`record-payment-`
helpers were not recopied as a second normative contract. Their exact
failure and recovery behavior is expressed in the revised R5 semantic
example and acceptance pairs. This preserves meaning while avoiding
misrepresentation of schematic APIs as currently runnable.

## Focused normative changes

1. Make the provider-invocation boundary explicit in the worked example:
   no provider charge/authorization inside a local retryable transaction
   callback; call only after durable intent/work commitment.
2. Make expiration of provider deduplication retention a change of
   recovery capability, not a license to use the same or a fresh key.
3. Restore R4's critical provider-success/local-incorporation-crash
   history, distinguishing a real external effect, recorded local
   knowledge, and a browser's limited observation.
4. Add eight paired acceptance families for legal construction,
   authentic receipt versus mismatch, lost response, retention,
   duplicate/reordered effects, cancellation races, durable worker
   ownership, and conditional progress. Valid positive cases must
   remain accepted; rejecting everything is not conformance.

## Implementation correspondence (Gesso application-assurance v1622)

Inspected `src/gesso/model/tx.clj`: the canonical model transaction
fragment has commands, guards, assertions and semantic changes. The
implementation does not thereby establish arbitrary payment-provider
atomicity, remote idempotency, or complete domain authorization.

Inspected `src/gesso/model/command_resolution.clj`: the experimental
durable command-result construction states that the application supplies
the authorized domain plan and disclosure predicate. Its assurance scope
does not establish durable notification debt, domain guards or all
physical contention/disclosure properties.

Inspected `src/gesso/live/core.clj`: post-commit Live publication errors
have a distinct failure stage and must not be construed as transaction
rejection. This is relevant to the generic work/delivery distinction,
not an implemented payment outbox or provider connector.

Inspected `src/gesso/assurance/proof/xtdb_gateway_command_outcome_bridge.clj`:
its bounded local-return/pinned-readback observation explicitly does not
establish transaction causality, principal/argument authentication,
provider effect provenance or an application's reported response.
That observation must not stand in for external effect evidence.

The source has generic command and XTDB correspondence tests, but no
provider-specific payment behavior was executed for this documentary
revision. These implementation observations belong in this audit,
not in the timeless normative section.
