** Command identity and authoritative disposition

A semantic command identifies one intended *semantic action occurrence* under
a declared command policy. It survives physical retry and authorized
reconciliation. It is distinct from the operation definition, any particular
server invocation, choreography execution, backend submission attempt and
transport exchange. One command can have several physical attempts without
becoming several admitted business actions.

| Identity | Meaning and lifetime |
|----------+----------------------|
| Operation identity | The public semantic operation, such as =:request/claim=. |
| Operation interface version | The input, result, and behavioral contract being invoked. |
| Semantic command ID | One bound intent whose disposition can be deduplicated and recovered. |
| Choreography execution ID | One distributed execution and its protocol-local resources. |
| Transport request ID | One HTTP exchange or other delivery attempt. |
| Backend submission-attempt ID | One physical attempt to submit or execute a transaction. |
| Capability instance ID | One issued execution or acquisition right. |
| Resource instance ID | One lifecycle instance of a managed resource or installation target. |
| Principal-context identity | The authenticated context relevant to authority and disclosure. |

Other identities, including deployment and projected-plan compatibility, may be
needed. They must be named for their purpose; a bare universal =generation=
coordinate must not stand in for them all.

A nominal identity wrapper or distinct wire tag is useful for preventing
accidental interchange of =:command-id=, =:execution-id= and
=:transport-request-id=. Its bytes do not authenticate an actor or prove a
durable command exists. A new transport exchange or compatible projected-plan
execution can carry the same command ID; it cannot reuse a retired execution's
resource/installation authority. Conversely, preserving an ID across a
deployment does not automatically make an incompatible old projected plan
safe to resume. Protocol continuation and stored command disposition are
separately admitted.

*** Command binding and canonical inputs

The admitted command boundary supplies or admits a stable =:gesso/command-id=
before the first possible send. A browser may carry an identifier, but choosing
its bytes confers no permission. The trusted boundary establishes the binding
and must preserve it through retransmission and reconciliation.

The command policy defines the namespace in which IDs are unique and the
immutable binding compared on repetition. That binding normally includes:

- authority/tenant and command namespace;
- semantic operation and compatible interface identity;
- canonical semantic arguments and their canonicalization version;
- the principal or explicitly declared delegated authority responsible for the
  intent;
- any domain preconditions that are part of the intent, such as an expected
  entity version.

Command compatibility is not equality of an arbitrary serialized map. Defaults,
omitted fields, numeric representation, ordered versus unordered collections,
and schema evolution require defined canonicalization. If a digest stands in
for canonical arguments, the contract identifies its algorithm and accepted
collision premise; a short convenience hash is not automatically an adequate
binding.

The public command namespace and the physical lookup/uniqueness key must
correspond. A model can choose globally unique IDs or IDs local to an
authority/tenant namespace, but two distinct admitted command identities
must not silently alias the same durable record. Conversely, a second
tenant or principal must not gain a foreign outcome by guessing an ID.
Record identity, full immutable binding, retained disposition and current
disclosure policy have distinct jobs: the record key locates a candidate;
it does not authenticate the caller or establish compatibility. A
canonicalization or interface upgrade must either preserve the admitted
old binding meaning through a declared compatibility relation or keep the
old command unresolved/unsupported with its own recovery; reinterpreting
a retained ID as a new intent is forbidden.

An observed read basis used only as a freshness hint need not be an immutable
semantic argument. An expected version that the user intentionally conditions
the command on is an argument. The interface must distinguish the two. Retry
must not silently turn a conditional command into an unconditional one.

Server-generated timestamps, random identifiers, and other choices also need
declared semantics. Values defining the user's intent or the identity of a
created entity must be stabilized or recoverable as the policy requires.
Transaction-local candidate calculations may be recomputed when permitted, but
their variation cannot change the command binding or invalidate replay.

*** Command identity is not an idempotency policy

Attaching a UUID does not provide deduplication. An operation must declare its
incorporation policy, storage boundary, compatible-repetition behavior,
incompatible-reuse handling, retention horizon, and recovery mechanism.

For Claim, the intended policy is one incorporation for a compatible command
binding. Repetition after incorporation returns a permitted recorded outcome.
Distinct command IDs can still conflict on the same Request; command
deduplication does not replace domain concurrency control.

A fresh Claim must protect *two independent exclusions*: the command
namespace cannot incorporate the same bound intent twice, and the Request
cannot acquire two concurrently active primary RequestAssignments.
Command uniqueness does not prove primary-assignment uniqueness; checking
only the Request's current revision or a node-local command cache does not
protect either property in all implementations. The Request, admitted
primary-assignment change, command record and required durable publication
intent of the selected Claim profile are one protected effect. Every actual
writer capable of violating a relied-upon rule must be included in the
qualified writer/enforcement coverage or treated as an explicit premise.

An operation that intentionally permits repeated independent effects must say
what constitutes a new semantic command. A new delivery attempt is not, by
itself, a new intent. If the product supports repeating an action, the admitted
entry path issues a fresh command for that deliberate action.

The command store need not contain an in-flight row for every implementation.
Its protocol must nevertheless distinguish evidence of incorporation, evidence
of terminal rejection or closure when promised, and the absence of a definitive
result. A transient local registry may assist scheduling; it cannot replace a
durable record where process failure recovery is promised.

The resolution boundary also needs a truthful *acquisition classification*.
A qualified, complete read finding no command record is an observation of
absence at its basis, not an exclusion of a concurrent or pending submission.
An unavailable, stale, unqualified, wrong-namespace or undisclosable
lookup is not such a read. It cannot safely authorize fresh incorporation
or be recast as a public =not-found= existence oracle. Existing-record
disclosure and new-command permission are distinct policy checks:
a compatible replay need not satisfy the now-false preconditions for
*new* incorporation, while any returned historical result still requires
current permission to learn it.

*** Atomic resolve-or-incorporate protocol

The following is a semantic algorithm, not a requirement to implement one giant
callback in the database:

1. Validate the admitted operation, interface, canonical arguments, authority
   scope, and trusted principal. Establish which command binding this caller is
   permitted to invoke or resolve.
2. If a retained command record is found, check binding compatibility and
   current permission to disclose the result. Return the permitted recorded
   disposition without applying the operation again. An incompatible record
   cannot be overwritten or treated as a new command.
3. If no definitive record is established, protect command uniqueness together
   with the conditions for new incorporation. An earlier non-transactional
   absence check is only a hint.
4. At the authoritative boundary, either establish the permitted domain
   transition, command result, and required durable intents together, or do not
   establish that transition. Conflicting concurrent attempts must not each
   incorporate the same command.
5. Interpret the backend result according to its qualified contract. A local
   return that means submitted or queued must not be translated into committed.
6. On contention, an abort, or an ambiguous return, resolve whether another
   attempt established a command disposition. Return only what the admitted
   evidence supports. If the result remains indeterminate, preserve unknown.

The implementation may use retries internally. Such retries retain the semantic
command and must not execute unrepeatable external effects inside a callback
that the backend may rerun.

The preliminary lookup in step 2 is an optimization, not an atomic
absence guarantee. A preliminary record read or candidate ineligibility
judgment can select an attempt's path, but does not settle command disposition
on its own. The protected incorporation/exclusion mechanism and qualified
backend outcome interpretation own that stronger judgment. Compatible replay
must resolve retained results without rerunning mutable eligibility guards
for *new* incorporation. Concurrent compatible invocations may both observe no
record and prepare candidate transitions. The qualified authoritative
mechanism must ensure that at most the policy-permitted incorporation wins
for the command namespace; a loser resolves the surviving record under
its own trusted disclosure conditions, rather than reporting terminal
business rejection solely because its physical transaction aborted.
An incompatible competing binding must not overwrite the winner's
record or enter the old command's authorized replay branch. A distinct
command ID cannot avoid the independent RequestAssignment concurrency
rules. A transaction that committed its domain effect without the
required command record is not a valid realization of this policy.

The same algorithm applies to one or several application nodes sharing
the qualified logical database. On another node, the command retains its
canonical identity and public semantics even if its local execution,
transport request and capability instances differ. A local registry,
cached negative lookup or lagging reader is never the authority for
deduplication; any replay or new submission must use a sufficient
authoritative acquisition/protected incorporation path. Cross-node
router placement and Live invalidation delivery do not define or
strengthen the command's business identity.

*** Command identity and incorporation acceptance cases

| Construction | Required judgment |
|--------------+-------------------|
| An eligible helper sends one Claim and the transaction protects Request, primary RequestAssignment, command result and selected durable work | Admit the new incorporation under qualified guards; the command record and model effects share the actual boundary |
| The same compatible command is retried after a lost response or on another web node | Resolve its retained binding and permitted historical result without constructing another domain or durable-work effect |
| Two same-binding attempts both read an absent command record before one commits | Only the protected incorporation wins; the other attempts compatible resolution and may not report its own abort as terminal command rejection |
| A concurrent attempt reuses one command ID with different target, principal, tenant or canonical arguments | Do not treat a collision as replay or create effects under the first binding; apply typed incompatible/undisclosable handling |
| Two tenants use IDs valid in their separately declared namespaces | Preserve both legitimate identities without physical record-key aliasing, while refusing cross-tenant disclosure |
| Two different command IDs attempt primary Claim for the same open Request | Command deduplication alone is insufficient; the protected RequestAssignment uniqueness/lifecycle policy determines the winner |
| A stale follower or node-local cache sees no command record despite an in-flight or incorporated transaction | Its absence is not definitive; require sufficient authoritative resolution and atomic uniqueness before any new incorporation |
| A successful Claim is replayed after its helper loses Membership or after a later Reassign | Do not reapply new-Claim eligibility guards; return only the permitted recorded outcome, distinct from current RequestAssignment state |
| An old record exists but the caller cannot disclose it or invokes an incompatible projected plan | Preserve command disposition without revealing protected data or reviving retired protocol resources; use the declared reconciliation/upgrade path |
| A canonicalizer upgrade changes argument meaning while an old command record remains retained | Require an explicit versioned compatibility judgment; neither silently recast an old binding as a new one nor fabricate a rejection |
| A command is durably recorded only after its domain write, or a direct writer bypasses protected uniqueness | Reject the stronger exactly-once/atomic correspondence or retain the identified writer premise; a successful test of one wrapper does not close the global writer set |
