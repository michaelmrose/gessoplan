## R4 requirements and specific omission

R4 Part IV's `Atomic authoritative transitions`, `Authoritative
transition contract`, `Semantic rules become authoritative implementation
obligations`, and `Preparation may be rich without weakening atomic
publication` require preparation and physical incorporation to be distinct,
protected semantic dependencies and effects to share the atomic boundary,
and postcommit publication failure not to invert the committed result.

R4 distinguished semantic guards satisfied by trusted principal input,
immutable command binding, transaction-current data, relationship/
uniqueness constraints, complete write-set postconditions, and explicit
opaque premises. It also specified an important *inverse* obligation:
business-policy branches hidden in implementation code that change
admission, writes, authority or disclosure belong in the auditable
semantic surface; they cannot silently define a narrower operation
while the report certifies the declared public policy. Incidental
retry, logging, serialization and performance choices are not new
business rules.

The strong R5 section already preserved atomicity, disjoint preparation,
full submitted-transaction coverage, nontransferable capabilities,
source-bound construction and honest unsupported cases. The review
restores R4's inverse mapping in a sharper form: **bidirectional
semantic-to-physical and physical-to-semantic correspondence**. It
explicitly permits independent declared platform safety gates
without misrepresenting product intent or inventing a universal
business-policy proof.

## Repair of Claim's actual multi-document obligation

The R5 04.04 table said that Claim changes an assigned helper
while preserving the rest of the Request frame. That is now
inconsistent with R5.1 04.02 and Part VIII, which establish
HumanHelp's actual primary helper relation via RequestAssignment.
The revised obligation table names:

- Request `:claimed` lifecycle state;
- protected *absence* of an existing active primary RequestAssignment;
- creation of the new active primary RequestAssignment;
- correct trusted helper identity, Organization associations,
  and collaborator/primary distinction;
- the complete frame/history of both Request and RequestAssignment;
- the bound command result and required durable work for the
  example's explicitly selected work-recorded publication profile.

The table does **not** invent or require an R5.1 runtime keyword
in the HumanHelp production model; it states semantic obligations.

A version guard on Request alone does not prove the absence of a
concurrent newly inserted primary assignment. The accepted physical
profile must protect the relevant *set predicate* under the
qualified isolation, uniqueness, transaction assertion or
equivalent backend condition. The normative wording intentionally
does not claim every XTDB SQL `ASSERT` or finite witnessed
execution has that concurrency property absent backend
qualification.

## Current Gesso source correspondence

Inspected Gesso `application-assurance` at v1622:

- `src/gesso/model/command.clj`: generic version/expected
  guard semantics; its documentation does not assign intrinsic
  application authorization meaning to a guard.
- `src/gesso/model/tx.clj`: composes `:commands`,
  `:guards`, `:assertions`, `:changes` and supports
  `assert-none`, `assert-one`, `assert-at-most-one`,
  document-current/absence, and field-count assertions.
  It lowers explicit assertions, dependency guards and
  command preconditions before writes. These mechanisms are
  tools for realizing selected rules, not proof that the
  application's entire policy/authoritative writer set is covered.
- `src/gesso/model/tx-refinement.clj`: finite pure
  relation between a serial reference model and supplied
  observed documents; says explicitly that observation honesty,
  physical isolation and general refinement remain assumptions.
- `src/gesso/model/tx-refinement-xtdb.clj`: controlled
  write-performing XTDB comparison with qualified pinned
  read phases, no intervening writer assumption, and open
  transaction-internal read snapshot/production execution
  correspondence. Its successful witness is not a universal
  backend serializability proof.
- `src/gesso/model/relational-invariant.clj`: source-interpreted
  bounded referential checks, not an actual database foreign-key
  constraint or complete application invariant inventory.
- `src/gesso/assurance/proof/operation-interface-composition.clj`:
  checks conditional alternative operation interfaces against
  abstract state; explicitly not a physical sequential or
  atomic transaction proof.
- Inspected test case names/subjects in
  `test/gesso/model/tx_test.clj`,
  `test/gesso/model/tx_refinement_xtdb_test.clj`,
  `test/gesso/model/relational_invariant_test.clj`,
  and `test/gesso/model/command_test.clj`; these cover
  physical stale guards, complete document/field-count
  comparisons, multi-document atomic rejection, missing
  targets and finite model safety. **Tests were not executed**
  during this editorial revision.

This source supports the distinction between constructible
transaction obligations and a physically qualified installed
operation. It is not a claim of existing complete
RequestAssignment/XTDB admission or proof-kernel soundness.

## Positive and adversarial obligations added

Nine document-level acceptance cases cover valid complete
atomic Claim, collaborator versus primary eligibility,
insertion races on active primary assignment, stale
Membership, undeclared extra business guard, missing
durable-work atomicity, unapproved effective write,
unsupported physical uniqueness qualification, and
valid opaque Clojure with an explicit conditional premise.

A reject-all implementation or source-only rule checker
cannot pass these cases by concealing positive
constructions. An unsupported proof mechanism does not
render otherwise valid operations semantically illegal.
