This audit compares the finished-system contract with the historical

## R4 and HumanHelp preservation

R4 Part IV's O1/P18, O2/P20 in-flight Refresh example requires later
advisory debt to survive A1 completion unless its actual authorized
observation and required installation cover both. An admitted P21
completion can fulfill both. An old P18 result cannot overwrite a
newer adopted view, and an allowed swap is not an installed view.

R4 Part VIII preserves immediate creator-local visibility after
authoritative Create, remote advisory followed by explicit Refresh,
and the separate case in which Bob creates S while remote R remains
unadopted. The original R4 also allowed multiple possible remote
lifecycle policies; accepted R5.1 Part VIII has now selected one:
remote creation *and* remote lifecycle changes require explicit board
Refresh for ordinary remote-content adoption. This selected policy is
used here rather than leaving it implicit in the generic coordinator.

R5.1 Part VIII also requires:
- One authorized Location/Organization cohort with honest completeness
  and separate card versus whole-board observation provenance.
- A creator's S that fails the current local filter remains visible in
  a "Your new Request" result area, without automatically resetting
  search or adopting remote R.
- Local search/sort/terminal options operate on adopted data; no
  incidental authoritative collection reread or membership expansion.
- Source-owned production RequestAssignment establishes active primary
  helper ownership, not a shortcut `:request/helper` presentation key.
- Correlated Create/Claim may update its declared affected-card or
  selective membership scope but cannot discharge unrelated remote
  board debt or resolve command-attribution uncertainty.
- A Refresh acquisition grant binds current owner, query scope, principal,
  Location, budget and lifetime. One click grants one logical read
  rather than indefinite automatic remote-adoption authority.
- Installed coherent board representation and current local options
  survive interleaved mutations and stale/partial physical responses.

## Stronger R5 design preserved

R5's 04.16 already describes provider-qualified opaque P17/P18/P20/P21
relations, distinct acquisition and installation stages, owner-relative
event admission, late callbacks, selective partial advancement, and
the permitted policy alternative that requires clearing all current
board debt before any replacement. Those framework-level mechanisms
are retained; the HumanHelp selection is recorded as application
policy rather than generalized into the Gesso core.

The revision keeps semantic events descriptive rather than prescribing
specific mutable queues, Clojure namespaces, required HTMX internals,
or a universal successor-read algorithm.

## Focused normative edits

1. Bind A1 to one explicit Refresh grant, including owner, selected
   scope, principal and budget; an advisory does not extend that grant.
2. Specify HumanHelp's selected non-regressing partial advance while
   O2 remains, without silently allowing a second automatic read.
3. Preserve separate physical completion and unknown/partial
   installation recovery before claiming adopted P18/P21.
4. Make scope/owner/current-options races explicit when a response
   belongs to obsolete search, Location, principal or board target.
5. Select explicit Refresh for remote lifecycle changes as well as
   remote creation; reserve local correlated operation outcomes for
   their authorized affected scopes.
6. Tie Claim helper truth to the production RequestAssignment model,
   and prevent unrelated board reads from establishing a command's
   historical attribution.
7. Restore the R4 remote R/local S sequence with the R5.1 Part VIII
   excluding-filter/result-area requirement and preserved advisory.
8. Add twelve paired acceptance rows addressing O1/O2, one-grant
   discipline, selective adoption, filtered confirmation, lifecycle,
   command uncertainty, non-regression and partial DOM failure.

## Inspected Gesso application-assurance v1622

`gesso.live.browser.adapter` is a pure adapter with current
request-generation checking, conservative distinct-basis sets,
`:queued-refresh?` and `:queued-requirements`. It produces an
automatic successor `:fragment/refresh` when a queued advisory
remains at the end of an active managed refresh. That is useful
generic coordination, but does **not** establish HumanHelp's chosen
"one explicit Refresh = one logical acquisition" policy without an
application-level grant/authorization gate and admitted realization.

The same adapter distinguishes `:htmx/allow-swap` at the before-swap
boundary from `:authoritative/installed` emitted on correlated
after-swap, and rejects stale/non-monotone swap candidates. This
is relevant semantic machinery, not independent proof of physical
DOM coherence across arbitrary multi-target partial mutations.

`gesso.live.browser.core` normalizes HTMX beforeSwap, afterSwap
and afterRequest through current active request records. Shell
observers do not independently prove current HumanHelp query scope,
effective consent, active primary RequestAssignment or historical
command attribution.

`gesso.live.progression` retains opaque basis requirements without
guessing order, and `gesso.live.consistency.xtdb` supplies trusted
provider-specific comparison. Those provide necessary consistency
mechanisms, not a universal proof that a particular board acquisition
ran a complete authorized query or installed the whole UI.

No browser runtime suite, real HumanHelp database acceptance test,
coherent DOM-batch qualification or formal proof was executed for
this documentary revision. The full HumanHelp proving application
has stronger acceptance gates in Part VIII.
