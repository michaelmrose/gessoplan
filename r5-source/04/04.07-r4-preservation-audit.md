**Section:** `r5-source/04/04.07-rejection-retention-and-knowledge.org`
**Disposition:** seventh reviewed R5.1 Part IV sectional candidate.
Part IV and the complete twelve-part R5.1 plan remain editorial drafts.
Normative Org text specifies the intended finished framework, not

## R4 material preserved and R5 gains

R4 Part IV's `Command disposition and participant knowledge are distinct`
(requirement anchor `req-command-participant-uncertainty`) distinguishes
authoritative domain state, semantic command disposition and participant
evidence. It forbids a timeout, browser retirement or response loss from
becoming a definitive business rejection. R4 additionally distinguishes
one definitely aborted physical attempt from another attempt's possible
command incorporation, and warns that negative command lookup may be
stale, incomplete or beyond retention.

R5 already improved these rules with a closed public outcome vocabulary,
conditional terminal rejection/closure, separate typed invocation errors,
retention horizons, compact privacy-preserving tombstones and explicit
upgrade/authority-migration concerns. This revision preserves all of those
and makes the physical and temporal contracts precise without requiring
a particular database schema or specialized formal language.

## Main repair: terminal rejection must exclude pending attempts

A *permanent terminal command rejection* requires an admitted exclusion
mechanism that contends with actual concurrent incorporation, including
an already pending submission on another web node. An absent command
record at a read basis, a preflight authorization denial, or a rejected
XTDB transaction is not that mechanism. An aborted transaction cannot
be assumed to have persisted its own terminal-rejection row. A
separate closure transaction has independent races and uncertainty.

The operation must name its command namespace, closure lifetime,
linearization/exclusion mechanism and qualified observation. A policy
that instead returns a narrower attempt-scoped or basis-scoped
failure remains valid, but its API and browser mapping must not
misrepresent that as irrevocable semantic rejection. Bad or
unauthenticated callers cannot close another principal's
valid command merely by submitting malformed bytes.

## Main repair: expiry requires enforcement, not just deletion

A deduplication guarantee concerns old *already submitted* and
delayed/offline attempts, not only new HTTP retries. Deleting
the retained outcome without an enforceable validity window,
tombstone, epoch/fence or equivalent exclusion can admit a
duplicate effect after expiry. A web-layer TTL alone does not
fence older backend transactions.

The audit explicitly distinguishes retaining duplicate-prevention
evidence from retaining a disclosable result payload. An erased
result with an active fence may support a truthful unavailable
response, not a recreated historical payload. Likewise, restore
and tenant migration cannot recover command dispositions merely
by copying the latest Request documents. The resumed authority
must qualify the namespace and exclusion history, or fence
previous accepted attempts and expose unresolved cases.

These policies remain optional *implementations* of the
same semantic retention and recovery contract; no single
outbox/tombstone/lease design is mandatory.

## Participant knowledge and acceptance

Three coordinates remain separate: current domain state,
bound command disposition, and participant evidence/permission.
A newer RequestAssignment state cannot establish which
historical Claim incorporated. Conversely, a compatible
recorded Claim can remain true history after Reassign.
A browser executor's retirement changes its installation
rights without rewriting command history. Sharing a
logical authority across one or multiple web nodes does
not make differently qualified reads interchangeable.

Twelve positive and adversarial documentary acceptance
cases now cover terminal rejection/inclusion races,
non-authoritative precheck denial, one failed attempt
with compatible successful incorporation, delayed closure
transactions, privacy tombstones, delayed retries after
expiry, legitimate fresh commands after a fenced window,
restored-backup gaps, interface upgrades, disclosure denial,
cross-host stale reads and late evidence after retirement.

Both affirmative admission of a genuinely closed rejection
and legitimate new commands remain possible. The contract
must not devolve into a reject-all implementation.

## Correspondence with actual Gesso implementation

Inspected `michaelmrose/gesso` branch `application-assurance`
at v1622:

- `src/gesso/model/command_resolution.clj` has a closed
  incorporation-record construction and exact typed
  `:command-id`, `:principal`, `:operation`,
  `:arguments` binding. Its persisted record status
  is `:incorporated`; its pure `reconcile` yields
  `:unresolved`, `:unavailable`, `:incompatible`
  or `:replay` depending on authoritative record
  presence, permitted disclosure and binding compatibility.
  It does not itself implement terminal-rejection records,
  retention expiry, tombstones, namespace migration
  or a recovery scheduler.
- `src/gesso/model/resolved_operation.clj` builds a
  server-side resolved operation that checks a retained
  record before constructing an incorporation plan and
  attempts readback on ambiguous results. Its
  `:incorporated` and `:unresolved` vocabulary
  is a bounded implementation classification, not
  automatic evidence of the finished model's
  `:committed`/`:rejected`/`:commit-unknown` variants.
- `test/gesso/model/command_resolution_test.clj`
  covers absence as unresolved, permission-limited
  disclosure, exact binding, real-XTDB atomic
  incorporation, duplicate write rejection and
  a failed domain commit leaving no command record.
  These tests exercise the bounded implementation,
  not the future closure/expiry guarantee.
- `test/gesso/model/resolved_operation_test.clj`
  covers read-before-construct replay, unknown
  acknowledgments, explicit physical rejection,
  authorization/disclosure and real XTDB readback.
  These tests were inspected; **none was executed**.

Current Gesso's recorded success path is valuable
implementation evidence but is not an assertion that
permanent terminal rejection, safe result deletion,
restore fencing or all multi-host enforcement already
exist. No proof of physical linearizability is
inferred from this source inspection.

## Cross-section and cross-part follow-ups

- **04.08:** C42 must distinguish authoritative command
  history, current RequestAssignment, lost response,
  attempted submission and owner-relative browser
  admission; its recovery owner cannot treat expired
  evidence as certain non-incorporation.
- **04.09–04.10:** a durable command result or privacy
  tombstone is separate from externally actuated
  provider effects and work debt; deletion cannot
  abandon unfinished obligations without a
  declared durable recovery/retention policy.
- **04.11–04.16:** basis scope, negative read
  completeness, eventual acquired evidence,
  Live advisory and browser installation are
  independent evidence subjects.
- **Parts VII–VIII:** production HumanHelp
  RequestAssignment, actor/principal/authority,
  installed writer coverage and tenant namespace
  must supply actual policy/exclusion premises.
- **Parts IX–XI:** scoped finite-checking,
  proof subject, backend evidence and deployed
  release evidence must not be conflated with
  a timeless terminality theorem.
- **Parts X/XII:** a single-node and multi-node
  deployment preserve the same command semantics;
  cross-process routing and replay are physical
  realizations, not new command outcomes.
