**Preferred design:** Gessoplan `r5` Part VI.
**Reviewed candidate:** `r5-source/06/06.03-htmx-transport-and-response-safety.org`,

## R4 requirements preserved and sharpened

- HTMX retains its ordinary declarative transport, response, native
  OOB, swap and settle responsibilities; Gesso supplies only
  admitted semantic correlation/allow/veto and physical observation.
  The design does **not** require a custom HTMX extension to
  reconstruct a transport that HTMX already implements.
- Versioned HTMX/extension/configuration behavior is a named
  external assumption with real physical hook coverage. An
  allow/cancel callback cannot establish a protected invariant
  if that particular mutation is not actually preventable
  before it occurs. An unsupported mode is rejected or
  supplied with an independently qualified realization.
- Request construction and synchronous send admission remain
  distinct from response interpretation, main-target swap
  permission, OOB/secondary mutations, post-swap completion
  and trusted business command outcomes.
- An HTMX primary-target permit cannot silently authorize
  OOB targets, response-header effects, navigation/history,
  active content, extension actions or a changed submitter.
  Physical scopes, owner generations, partial completion and
  recovery are separate obligations.
- Response-data provenance and active-content safety are
  independent. A trusted domain observation does not make
  untrusted rendered markup, scripts or `hx-*` processing safe.
  Source-owned model/route authorization remains mandatory.
- Stable Live/HTMX/continuity owners are preserved across
  fragment replacement or explicitly reconstructed as a
  new admitted owner. A one-time successful refresh is
  insufficient evidence of ongoing Live functionality.

R4's lengthy browser FFI and Claim walkthroughs are not copied
into a second executable specification; their obligations are
preserved in one stronger R5.1 contract. Sections 06.04–06.05
continue the exact Claim/FFI and physical-installation
responsibilities.

## Focused changes

1. Defined the *actual integration profile* over HTMX version,
   extension/configuration, request modes, response statuses,
   headers, target/OOB/active-content behavior and deployed asset
   identity—not just a matching dependency name.
2. Made the admitted footprint explicit at pre-send, response
   processing, each physical mutation, completion and root
   replacement/recovery. Permits cannot be broadened by
   `HX-Retarget`, `HX-Reswap`, dynamic markup or an extension.
3. Named an important HTMX 2 case: `hx-swap="none"` suppresses
   the main insertion, but OOB swaps and applicable response
   headers may still cause effects. Thus a command-result-only
   endpoint is not safe merely because it says `none`.
4. Required response-triggered actions, secondary target writes,
   and script/HTMX attribute activation to have their own
   admission or be actually excluded before they mutate a
   protected scope.
5. Distinguished physical completion per target from successful
   HTTP responses, admitted command disposition, provisional
   presentation and broad authoritative cohort adoption.
6. Preserved legitimate raw/unmanaged HTMX and useful
   explicitly non-optimistic operations without allowing
   silent managed-to-raw downgrade or unprotected server writes.
7. Added six paired eligible/adverse physical histories
   including unauthorized OOB, retargeting, form overrides,
   markup injection, lost SSE roots, and false adoption.

## Concrete Gesso v1622 implementation observations

Inspected the supplied Gesso `application-assurance` snapshot
at `1b5e10e71c00e7784b019dee7dc1198a96fd03f6`:

- `src/gesso/live/browser/core.cljs` documents its narrow
  HTMX-normalization role. Its listener inventory includes
  `htmx:configRequest`, `htmx:beforeRequest`,
  `htmx:beforeSend` (observe only), `htmx:beforeSwap`,
  `htmx:afterSwap`, `htmx:afterRequest`, request error,
  fragment cleanup and SSE events. It does not replace
  HTMX transport or implement a general response parser.
- In that same file, `on-before-request!` binds one
  physical request ID/adapter generation and invokes shell
  dispatch; an exception calls `prevent-event!`.
  `on-before-swap!` correlates the active managed request
  and invokes the adapter; on exception it calls
  `cancel-swap-event!`, which sets `detail.shouldSwap`
  false and calls `preventDefault` when available.
- `src/gesso/live/browser/adapter.cljc` checks the current
  fragment request/generation, enforces scoped authoritative
  candidate constraints before the main swap and records
  qualified installation on `:htmx/after-swap` for that
  tracked request. This is bounded code evidence, not
  a universal physical-completion or OOB-coverage proof.
- `src/gesso/live/browser/shell.cljs` treats HTMX as
  externally owned and interprets adapter effect dispositions.
  Its recorded state precedes effect handling, but the
  source does not establish all secondary-target, header,
  script, history or extension behavior under every
  supported profile.
- `src/gesso/live/application_preflight.clj` checks
  canonical rendered response/operation bindings under
  its installed wrapper, and explicitly does not imply
  comprehensive coverage of alternate startup paths,
  pre-serialized HTML, uninspected dynamic handlers,
  or every deployed browser response path.
- `test/gesso/live/browser/chromium_integration.clj`
  uses actual HTMX 2.0.7 and SSE extension 2.2.4
  WebJar assets in the tested browser fixture. These
  integration tests establish only cases actually exercised
  on that profile, not generic HTMX/extension correctness.

The source-level integration specifically documents
`beforeRequest` and `beforeSwap` gating; the inspected
listener list does **not** itself demonstrate managed
`htmx:oobBeforeSwap` authorization or the complete
response-header/active-content footprint. That is
a *correspondence and coverage obligation*, not a
claim that every current Gesso application is vulnerable:
a narrower, physically enforced response profile might
exclude the unaccounted effects. The actual configured
serving/extension paths must be examined before either
accepting or rejecting the deployed guarantee.

## External HTMX documentation checked separately

The HTMX documentation for the 2.x-style response model
states that `hx-swap="none"` still processes OOB items,
and the response-header reference describes client-side
events, retargeting and swap overrides. Documented
`htmx:beforeRequest` can veto sending, while
`htmx:beforeSend` is noncancelable; other hooks require
their own version/profile check. Those external docs are
background constraints on the *selected* runtime profile,
not test results from Gesso itself.

## Cross-part obligations and acceptance boundaries

- **06.04–06.05:** the concrete Claim/FFI and scoped
  installation sequences must admit each effect and
  obtain real current-target completion, preserving
  partial or indeterminate physical effects.
- **06.06–06.07:** Live refresh, local search and
  one-Refresh selective adoption must preserve stable
  coordinator/root identity and retention of outstanding
  advisory requirements.
- **06.08–06.11:** plan/deployment compatibility,
  retired callback ownership, physical effect lifecycle,
  source-normalized async admission and complete
  response/extension coverage need their own evidence.
- **Parts IV–V:** an accepted C42 historical outcome is
  independent of current RequestAssignment, permitted
  acquisition and installed DOM. Managed/no-downgrade
  and diagnostic nonauthority remain mandatory.
- **Parts VII–X:** assembled routes, HTTP methods,
  workers, all rendered and pre-rendered entrypoints,
  loaded browser assets, actual authorizations,
  HumanHelp positive capabilities and physical proof
  premises cannot be certified from a single
  parsed response or a source-generated test map.

Each positive case has an independent eligible fixture
and its nearby adverse case must reach the boundary
being tested. Unknown/incomplete host, deployment or
security evidence remains unresolved rather than a
silent affirmative result. Ordinary legitimate HTMX
remains part of the intended framework.

The original Part VI eight `CUSTOM_ID` anchors remain
stable. This revision changes no Gesso implementation,
no accepted R5.1 Part I–V and no unrelated Part VI
numbered source.
