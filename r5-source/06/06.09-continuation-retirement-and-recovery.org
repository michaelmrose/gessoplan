*** Retirement transfers surviving obligations before cleanup

Retiring a stale execution revokes its private presentation, callback, timer, and
send rights. It does not cancel a server transaction that may already have been
submitted, and it does not establish a rejected command outcome.

If unresolved command or delivery obligations must survive, retirement transfers
them to a declared current recovery owner as one semantic ownership transition.
Only then may the old execution's private resources be released. The transfer
preserves binding and existing evidence without giving the new owner permission
to reuse old DOM targets or machine locators.

For recovery promised across page loss, a merely in-memory owner is insufficient.
The assembly supplies durable client retention, authenticated server discovery,
or another declared mechanism that survives the promised failure domain. If a
retention horizon expires, the resulting unresolved/manual-reconciliation state
is explicit; forgetting the record does not establish non-incorporation.

*** Worked example: a sleeping checkout crosses a deployment

A browser running executable plan P7 submits command C77 to the admitted
=place-intent!= operation. The server may have atomically created an Order in
payment-pending state and durable payment work. The response is lost, so the
browser knows only that C77 is unresolved. The tab sleeps while deployment D8
introduces plan P8.

On resume:

1. The runtime checks P7's continuation compatibility and the current authority
   context. If P7 may not continue, it revokes P7's private execution rights.
2. It transfers C77's binding and recovery obligation to an admitted recovery
   owner. It does not treat the old timeout as proof of payment or rejection.
3. It admits the current runtime/plan and obtains the resolver contract capable
   of interpreting C77's retained operation binding.
4. The trusted resolver checks current permission to disclose the result. It may
   establish prior incorporation, authoritative rejection, or continued unknown.
5. The browser separately acquires and installs the permitted current Order
   projection, observing its actual payment/workflow state.
6. Further payment progression follows Part IV's durable workflow contract, not
   the old browser's optimism or the mere success of =place-intent!=.

| Resolved condition | Permitted presentation |
|--------------------+------------------------|
| C77 incorporated; payment remains pending. | Show the acquired pending Order and its declared recovery/progress state. |
| Current evidence establishes the later successful payment transition. | Show the acquired completed state allowed by the Order model. |
| Authoritative rejection is disclosable. | Present that rejection and the permitted continuation. |
| Outcome remains indeterminate. | Preserve unknown with the declared resolver/backoff/manual path. |
| Current user cannot receive the old result. | Use the permitted nondisclosing outcome; do not expose the record or infer rejection. |
| The retained command contract is unavailable. | Block incompatible repetition and expose the declared recovery limitation. |

A card displaying a similar Order is not, by itself, proof that C77 created it.
Current-state acquisition and command attribution are separate evidence claims.
Likewise, P8 cannot simply execute C77's old arguments using a newly changed
operation meaning.

*** Recovery is a bounded, visible protocol

Every recoverable branch declares who acts next, which evidence is requested,
what authority is needed, what can be retried automatically, and when user or
operator action is required. A label saying recoverable is not a strategy.

The policy covers unavailable plans/assets, unsupported retained schemas,
network failure, resolver failure, denied disclosure, expired retention,
subscription gaps, and failed installation. It may stop in a truthful read-only,
blocked, unknown, or manual-reconciliation state. It must not create an infinite
reload loop or silently fall back to an incompatible old plan.

Offline duration does not oblige the system to replay every missed UI event. A
current authorized observation may suffice for current-state presentation. Durable
business work retains its own completion obligations regardless of how much
intermediate UI history is discarded.
