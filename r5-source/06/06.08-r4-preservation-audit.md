## Preserved R4 requirements

- Old browser states remain potentially live across deployment,
  page suspension, bfcache, service workers and network isolation.
  A parseable old plan is not automatically compatible with the
  active interpreter, operation, wire, authority or physical host.
- R4 distinguishes choreography representation, projected plan,
  semantic operation, wire envelope, command ID, local execution
  and assembly/deployment identity. The revision retains these
  separately scoped judgments and refuses to make one global
  monotonically increasing version a universal compatibility rule.
- Incompatible state is conservatively *semantically retired*
  before attempted physical cleanup and current authoritative
  reconstruction. A stale callback loses rights independently
  of whether timer or request cancellation physically succeeds.
- A historical submitted C77 can remain outcome-unknown while P7
  becomes incompatible with P8. The browser cannot infer rejection,
  use altered arguments with the same command ID, or invent a
  second command to escape uncertain incorporation.
- The original authenticated principal/tenant and current
  disclosure context remain trusted-server policy subjects.
  Locally saved plan bytes, a recovery reference and even a valid
  old execution must not authorize an old protected read.
- Transparent migration of arbitrary suspended DOM captures,
  effects, timers, machine locators and closures is not required.
  Specific explicitly justified migrations and authoritative
  reconstruction are allowed.

This preserves the stronger R5 permanent executable semantic
interpretation and distinct proof/checker subject rather than
restoring R4's illustrative compatibility predicate as a second
runtime source of truth.

## Focused improvements in 06.08

1. Expanded the compatibility matrix across executable
   interpretation, local continuation, new invocation,
   historical command resolution, compatible replay,
   observation/rendering, wire, physical HTMX/FFI and
   trusted authority/deployment closure. Compatible
   historical resolution does not imply the old
   physical execution may resume.
2. Distinguished actual installed executable/asset
   identity from the semantic relationship authorizing
   interoperation, including service-worker caches,
   rolling deployments and mixed-version peers.
3. Required re-admission at page startup, bfcache
   restoration, tab wake, asset replacement,
   subscription reconnect and the last controllable
   protected physical act. Lifecycle callbacks are
   advisory wakeups, not compatibility certificates.
4. Specified separate *compatible*, *recognizable
   incompatible*, *malformed/untrusted*, and
   *indeterminate/unavailable* dispositions, with
   truthful command and physical recovery state.
5. Allowed bounded cached/leased judgments with
   explicit invalidation and renewal premises, not
   blind rescanning or permanent reliance on old
   browser-side policy.
6. Defined required semantic command bindings,
   resolver retention, operation-version compatibility,
   privacy-preserving server references and replay
   limits without making a client command ID a bearer
   credential.
7. Qualified principal/Organization change and
   honest-client future display/privacy limits,
   avoiding impossible claims of retroactive erasure
   from an adversarial browser.
8. Added eight paired positive/adverse histories
   covering plan format, C77 replay, bfcache, old
   cached assets, principal change, resolver
   disclosure, scoped migration and offline
   compatibility uncertainty.

## Gesso v1622 implementation context (source inspected)

The user-supplied Gesso application-assurance v1622
snapshot is 1b5e10e71c00e7784b019dee7dc1198a96fd03f6.

- src/gesso/live/browser/choreo.cljs calls
  machine/executable-plan-format-status in start-plan!.
  A recognizable incompatible plan retires the
  current matching execution before invoking its
  configured incompatible-plan recovery handler.
  The default browser handler requests a full reload;
  where no host location exists, it returns
  :reload-unavailable. A thrown recovery handler
  is classified after attempted semantic retirement.
- The stale-plan-retirement! code distinguishes
  :retired, :retired-with-cleanup-error,
  :retirement-failed and :not-active, rather than
  assuming physical timer/XHR cancellation always
  succeeds. The runtime does not attempt arbitrary
  suspended-machine migration through that path.
- src/gesso/live/browser/runtime.cljs composes one
  shared shell/AdapterState owner with Choreo and
  optional optimism/HTMX bridge. Its runtime?
  checks component-instance identity, supplying
  source evidence of local implementation closure.
  That is not a proof of loaded asset identity
  or of arbitrary server-version compatibility.
- src/gesso/live/browser/core.cljs treats
  online, persisted pageshow and foreground
  visibilitychange as advisory managed-fragment
  recovery triggers. Those events do not carry
  a qualified server version, policy lease or
  proof of complete subscription catchup.
- src/gesso/live/browser/adapter.cljc
  keeps generation-based stale-event and
  optimistic incompatible-protocol dispositions;
  these are useful local safeguards but do
  not establish old-command replay policy or
  current protected data disclosure by themselves.
- Source-inspected Gesso tests include
  incompatible-protocol-retirement-uses-authority-reconstruction-policy-test
  in test/gesso/live/browser/adapter_test.cljc.
  The inspected test and source are not a
  browser/deployment integration certificate.

No local Gesso JVM/Node/Chromium, XTDB or formal
checker was executed for this editorial revision.
The code supports a conservative local stale-plan
recovery design, not complete deployment/asset
closure or every possible cross-version operation
and command-history resolver.
