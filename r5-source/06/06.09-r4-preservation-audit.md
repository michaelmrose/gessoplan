## R4 requirements preserved and intentional supersession

- R4 explicitly revoked stale plan E7's execution-private
  rights before best-effort physical cancellation, which
  may fail. That safety requirement survives without
  tying logical progress to destruction of every old
  browser timer, event listener or transport.
- The R4 checkout example treated C77 as a separate
  semantic command whose possible incorporation survives
  P7 becoming incompatible. A later P8 cannot assume a
  new command was safe or that successful parsing allows
  continuation of obsolete machine state.
- R4's authoritative Order read and historic command
  attribution remain different claims. An Order card
  can be current when C77 causality remains unknown;
  command incorporation does not establish completion
  of separately durable payment work.
- Current user/principal and protected data disclosure
  remain trusted-model decisions even when a browser
  retains a command ID, old cached markup or
  server-issued recovery reference.
- R4 deliberately does not promise arbitrary migration
  of suspended machine state, closure/timer/DOM captures,
  transport resources or provisional rollback. Current
  authoritative reconstruction is the safe default.
- Failure to load P8 or a protected read requires an
  honest bounded blocked/retry/manual path rather than
  fallback to incompatible P7 or a fabricated rejected
  C77 disposition.

The R5.1 design uses one executable semantic interpretation,
separate historical command and browser resource owners, and
the accepted Part IV/Part V operation/projection vocabulary.
R4's large example-only Clojure helper functions are not
restored as a parallel runtime API, but their physical
and authoritative obligations remain explicit.

## New and sharpened obligations

1. Handoff is defined as an obligation-survival and
   old-owner revocation contract. A command recovery
   record must already survive, or a transfer must be
   admitted atomically with revocation. A process reload
   cannot claim durability from a pending Promise or
   an in-memory only owner.
2. Failure domains are named: local execution replacement,
   page loss, browser process/device restart, offline
   duration, deployment rollover, backend failover,
   account change and retention expiry differ.
   Persistent client and server mechanisms carry
   distinct security/privacy premises.
3. Immutable command intent includes original operation
   meaning/schema, actor and canonical arguments,
   resolver/deduplication/retention relations and
   evidence. Old IDs are neither bearer credentials
   nor safe licenses to replay changed arguments.
4. Full sleeping-checkout case distinguishes
   =place-intent!= transaction incorporation from
   later payment-workflow completion and states
   realistic unknown, rejected, pending, disclosed,
   denied and unavailable branches.
5. Recovery distinguishes current authorized Order
   acquisition/installation from historical C77
   attribution, and continuity/Live debt from
   user-granted Refresh permissions.
6. Failed abort, storage/handler error and unavailable
   current assets leave old private effects retired
   and retain a truthful visible fault/recovery path
   with bounded resource/backoff and manual options.
7. Explicitly acknowledged that partial/current-state
   replay need not reconstruct every missed UI event,
   but durable event-processing workflows need their
   own separately owned correctness contract.
8. Added nine eligible/adverse histories for durable
   handoff, stale cleanup, payment distinction,
   current-view ambiguity, original-binding replay,
   cross-principal disclosure, reload/Refresh scope,
   bounded failure and permitted local-draft migration.

## Inspected Gesso v1622 source, not run

The supplied Gesso application-assurance archive is at
commit 1b5e10e71c00e7784b019dee7dc1198a96fd03f6.

- src/gesso/live/browser/choreo.cljs:
  start-plan! checks machine/executable-plan-format-status.
  Recognizably incompatible plans enter
  recover-incompatible-plan!, which attempts semantic
  retirement before invoking the configured recovery
  handler; its default asks the browser location to
  reload. stale-plan-retirement! distinguishes
  :retired, :retired-with-cleanup-error,
  :retirement-failed and :not-active. A throwing
  recovery handler is surfaced without reactivating
  the already retired generation.
- src/gesso/live/browser/adapter.cljc:
  retire-execution* removes the matching generation's
  execution and target ownership from AdapterState
  and emits cleanup effects for owned timers and
  pending transport, plus separate terminal
  :execution/retired or :execution/completed.
  The cleanup effect is not the authoritative
  transition that invalidates the old callback.
- src/gesso/live/browser/runtime.cljs:
  stop! marks the composition stopped and calls
  core/stop! for semantic retirement before
  best-effort detachment of optimism and Choreo
  physical handlers in a finally path. This is
  runtime lifecycle groundwork, not durable
  command recovery across a destroyed browser.
- test/gesso/live/browser/adapter_test.cljc:
  incompatible-protocol-retirement-uses-authority-reconstruction-policy-test
  rejects fabricated trusted settlement on protocol
  incompatibility. optimistic-network-failure-does-not-fabricate-trusted-settlement-test,
  explicit-execution-retirement-cancels-owned-timers-test,
  and related retirement tests address bounded
  pure adapter behavior. Their test sources were
  inspected; tests were not executed here.

These source observations support the local semantic
retirement and best-effort cleanup design. They do
**not** establish durable C77 command binding across
browser loss, the selected Order resolver/retention
schema, actual XTDB/payment workflow causality,
current authorized HumanHelp Claim history, served
asset closure, general physical browser cleanup
or end-to-end recovery and nonvacuous product acceptance.
The revised specification intentionally requires
those additional properties as finished-system work.

## Cross-part evidence and completion obligations

- **06.08:** exact loaded plan/asset/authority
  compatibility must be checked before old work
  continues; recovering the old command is not
  equivalent to resuming its private browser state.
- **06.10–06.11:** actual physical cleanup handles,
  last-actuation checks, late callbacks, shared
  resources and correlated failure classification
  must refine semantic retirement, including
  reentrant cleanup and partial effects.
- **Parts IV–V:** historical command disposition,
  exact owner/actor binding, eligible model
  transitions, provisional status, observation
  and adopted physical state remain distinct.
- **Parts VI.06–VI.07:** recovery may retain
  subscription gap, unmet advisory and Refresh
  obligations; a fresh read needs an explicitly
  admitted bootstrap or user-action policy.
- **Parts VII–VIII:** construction/serving must
  include real recovery endpoints, durable data,
  all physical browser entrypoints and eligible
  HumanHelp Create/Claim/Reassign/one-Refresh
  paths, not merely a successful source mock.
- **Parts IX–XII:** claims about storage retention,
  readback, transaction deduplication, proof
  subject and multi-node failure recovery need
  named provider, fairness, durability and
  deployment premises. Passing a local finite
  trace is not automatic production certification.
