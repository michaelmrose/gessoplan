*** Worked example: Claim followed by protected acquisition

Alice sees HumanHelp Request R in a qualified, authorized observation of the
currently selected Organization/Location. The rendered Claim affordance binds
one public model-owned operation and typed arguments. It does not mint a trusted
principal, establish current Membership, or authorize the write merely because
the browser displays =Claim=. The observed pre-read may report an =:open=
Request with no active primary =RequestAssignment= under its stated coverage;
that is not an atomic, transaction-current eligibility decision.

The example uses these distinct subjects:

| Subject | Meaning |
|---------+---------|
| R | HumanHelp's model-owned Request identity; not an HTTP request. |
| C42 | Stable semantic Claim command intent and protected binding, allocated before the first possible submission. |
| E42 | One local browser Choreo/optimism execution with separately revocable physical rights. |
| H1, H2 | Distinct physical transport attempts that may carry a compatible retry of C42. |
| B1, B2 | Physical incarnations of the Request-card target, not merely the same DOM selector. |
| CardObs1 | An admitted card observation, with its own source, covered scope and qualified progression. |
| P1 | A runtime-issued installation permit for an exact representation, target and effect instance. |

The values are illustrative. A later execution may continue permitted C42
reconciliation, but does not inherit E42's retired transport, timer, target
or actor-local branch knowledge. Two requests that reuse C42 are not
automatically interchangeable in their transport-result correlations.
The command's immutable semantic intent is bound to its operation,
arguments, actor/authority context and compatible replay contract under
Part IV. A copied ID in a request header is not that admission.

The following trajectory is a supported *design*, not a claim that
these names are already the public browser API:

| Stage | Required semantic/physical correspondence |
|-------+-------------------------------------------|
| Prepare | Admit the current view binding and relevant scoped observation. Establish a stable C42 intent and local E42/target owner before any possible send, preserving required actor, operation and argument bindings. |
| Provisional | Derive and install only the locally admitted provisional presentation; failed physical installation is reported as such and never fabricated into command rejection. |
| Request construction | Bind an exact H1 physical attempt, current execution/generation and effective HTMX method, route, inputs and send footprint. HTMX retains native transport ownership. |
| Send admission | At the supported synchronous hook, verify the projected send state, still-current attempt/target owner, complete physical request binding and source. No missing projector, correlation or plan silently downgrades to ordinary HTMX. |
| Trusted Claim | Authenticate the actual principal and guard current Request, Organization/Membership/actor and active primary RequestAssignment facts through the real model-owned transaction and backend contract. A browser pre-read or self-asserted plan cannot replace the transaction guard. |
| Outcome observation | Admit binding-scoped C42 command evidence from the qualified response or permitted readback. Distinguish incorporation, terminal rejection, compatible replay and unknown delivery; do not translate network failure or an HTTP status into a domain result. |
| Acquisition | Independently admit permission to read the current authorized card or board cohort, its required query/scope and progression. A historical C42 result alone does not yield a current CardObs1 observation. |
| Installation | Derive a prepared representation from the admitted CardObs1 observation and acquire a current P1 covering its actual target instance, physical action and allowed mutation footprint. Recheck P1 at the last controllable act, including delayed/reentrant work. |
| Completion/adoption | Admit actual completed physical effect/postcondition for the matching CardObs1/P1/target. Discharge only its covered presentation/adoption obligations; do not call a whole board refreshed after installing one card. |

Part IV owns the *authoritative* Claim transaction and historical command
knowledge, Part V the local provisional derivation/settlement treatment,
and Part VI the browser's actual effect and installation boundary.
These are composed responsibilities, not competing interpreters.

A permitted =:committed= result, or a qualified
=:already-incorporated= result for C42, establishes the specified
historical incorporation, subject to the authoritative source and
binding contract. It may permit an =:accepted= presentation status;
it is not an assertion that today's primary helper is Alice, that a
particular HTML fragment installed, or that the board cohort changed.
A terminal =:rejected= command outcome requires its own qualified
exclusion evidence. =:commit-unknown= remains unresolved until an
admitted resolver establishes more. The browser's generic optimism
=:confirmed=, =:reconciled=, =:failed= and timeout dispositions are
not substitutes for the public model outcome vocabulary.

Two independent histories make this distinction unavoidable:

- H1 may have incorporated C42, then the network response was lost.
  The browser can retire H1/E42's physical resources, recover the
  current card through CardObs1, and still lack C42-specific historical
  attribution. It must retain or transfer the command-resolution
  obligation rather than asserting that the new card proves H1
  succeeded or failed. Retrying C42, if permitted, must preserve
  immutable command binding without executing a second incorporation.
- C42 may have successfully installed Alice's primary assignment,
  followed by a manager's authorized Reassign to Bob. A historical
  C42 result and a newer qualified Request/RequestAssignment
  observation are simultaneously true. An old settlement callback
  cannot reinstall Alice over Bob; a current Bob card does not turn
  C42's earlier success into rejection.

Claim's response and card acquisition may use separate physical HTMX
requests, which is a particularly clear realization. A combined result
and observation is also possible, but each proposition must pass
its own source, disclosure, scope, and completion gates. An
=hx-swap="none"= command response must still satisfy section 06.03's
OOB/header/secondary-effect contract. Its success cannot be counted
as a card swap. A raw =afterSwap= callback is not automatically
physical proof of installation in an unrelated or retired target.

When provisional derivation requires asynchronous computation but the
chosen HTMX gate requires a synchronous allow/veto, that derivation must
complete *before* entering the gate or be deferred to an admitted
re-entry/reacquisition path with a new physical attempt. The gate
cannot allow the send on hope of eventual projection. Failed,
missing or incompatible managed realization remains an explicit
typed failure; authored raw or non-optimistic alternatives keep
their independently complete authorization and recovery contracts.

HumanHelp's board has an additional adoption distinction. Alice's
correlated local Claim may update her own card promptly after the
relevant qualified outcome/observation and actual installation.
Other actors may receive only a scoped Live advisory until their
explicit Refresh grant. Local text search, sorting, selected card,
open details and scroll state remain continuity of an already adopted
authorized cohort, not proof of a new server query. A creator-local
newer S must not be overwritten by an older whole-board R snapshot;
one explicitly granted remote Refresh must satisfy its stated
scope without silently acquiring an extra cohort. The detail of
these policies belongs to Parts IV–V and 06.05–06.07, not to
an ad hoc Claim listener.

*** Browser FFI contracts are small but substantive

The browser FFI is the physical interpreter of *adapter-issued*
effects, not another source of command meaning, business rules
or Choreo branch selection. HTMX owns its native request/response
and supported swap behavior; a Gesso-owned effect handler may
intervene at admitted HTMX gates or perform distinct Gesso-owned
timer, provisional DOM, continuity, subscription and cleanup work.
It may not quietly duplicate an HTMX request or swap.

Every supported physical effect handler has a registered contract:

- **Input and binding:** typed effect kind, implementation and
  protocol/asset identity, closed required inputs and admitted
  normalized source; unsupported inputs fail explicitly.
- **Ownership:** exact runtime, semantic effect instance, resource
  incarnation, current owner/generation, target incarnation,
  representation and allowed physical footprint.
- **Actuation:** synchronous/async classification, actual
  last-controllable permit check, required serialization with
  protected mutation, and any possible host reentrancy.
- **Outcomes:** actual completion postcondition, correlated effect
  and target, failure, cancellation, partial/indeterminate
  mutation, duplicate delivery, and unknown physical result.
- **Cleanup/recovery:** registration before issue, handling of
  immediate callbacks and handles returned after retirement,
  exact-resource release, stale callback no-op, observable
  residual debt and any necessary compensating/reacquisition path.
- **Premises/evidence:** supported host/HTMX version, external
  behavior relied on, test/proof scope, and unproved opaque or
  third-party effect assumptions.

A handler returning a syntactically successful envelope does not
establish a physical action. The completion contract must identify
what the host actually accomplished, or classify its result as
unknown/partial. An absent, throwing or misbound mandatory handler
must not silently satisfy the projected semantic obligation.
A sidecar or observer callback cannot supply the missing effect.

The shell's physical registry maps adapter-issued references to
actual opaque host objects. Correlation is established at issue or
registration and carried through callbacks, not rediscovered by
whatever element currently matches a selector. A timer cancellation
cannot remove the successor owner's identically named timer.
A delayed DOM write cannot act on B2 using a revoked B1 permit
merely because the eventual callback would be rejected. If the
host supports a guarded last-actuation section, its check and
mutation must preserve current ownership under the declared
serialization/reentrancy contract. If it does not, the selected
physical realization is unsupported for that strong guarantee.

The current semantic transition is installed before issued effects
are interpreted. Immediate physical callbacks must therefore see
committed ownership and effect state. A nested callback may retire
the outer owner before its remaining effects run; every remaining
protected effect must recheck current permission. Concurrent
dispatchers need a genuine serialization mechanism rather than
two mutable competing copies of the same semantic state.
The FFI may retain physical handles, but cannot choose a semantic
successor or transfer authority as a shortcut around that protocol.

Ordinary application code and third-party browser libraries can
mutate the same DOM and trigger network work. For a protected
footprint, those actions must participate in the admitted host
profile, be prevented from interfering, or remain an explicit
noninterference/trust premise with corresponding limits on the
claim. Full-language Clojure application development does not
eliminate physical or opaque effect obligations.

*** Paired Claim and FFI correspondence histories

These cases state nonvacuous finished-system acceptance conditions;
each successful path must reach the actual intended source and
physical effect, and each adverse control must fail at its
target boundary rather than at an unrelated invalid fixture.

| Eligible positive history | Adversarial or incomplete history | Required conclusion |
|---------------------------+-----------------------------------+---------------------|
| Alice has authorized Request/assignment pre-read; C42/H1 executes against current trusted Claim guards and creates one valid active primary RequestAssignment. | A stale Request, revoked Membership, second competing helper, or browser-supplied =:display-helper-id= is treated as current transaction authority. | Only the trusted guarded operation decides Claim; positive transaction and competing negative cases demonstrate real model protection. |
| H1 has unknown delivery and a compatible H2 replay of C42 obtains qualified historical incorporation evidence. | H1's timeout is treated as terminal rejection, or H2 is assigned a new command ID and commits a second Claim. | Preserve one immutable C42 intent and separate physical attempts; do not invent rejection or duplicate incorporation. |
| C42's permitted historical result is admitted, and a separately authorized CardObs1 card is physically installed at current target B2. | A 200 response, =hx-swap="none"=, untrusted decoded HTML, or an =afterSwap= for B1 is reported as adopted B2. | Record command history, acquisition and exact physical adoption separately; retain incomplete adoption debt when installation is absent. |
| A new primary helper Bob is authoritatively reassigned after Alice's Claim, and a qualified newer card installs. | A late E42 timer, provisional rollback or old C42 outcome reinstalls Alice's card over Bob. | Retired execution/target permits cannot mutate the newer authoritative presentation; C42's earlier attribution may remain true. |
| An effect is registered before issue and its immediate callback re-enters dispatch; mandatory handler reports a checked real postcondition. | A missing/throwing handler emits fabricated success, or an outer queued effect mutates after a nested dispatch retired its permit. | Commit-before-effect, current last-actuation gate and precise failed/unknown effects; no empty handler accepted as physical completion. |
| A correlated self-action updates Alice's card; a remote actor receives advisory R, while an independently newer local S survives the actor's one granted Refresh. | A stale board snapshot erases S, or a hidden second acquisition is used to pass the refresh fixture. | Preserve per-scope and per-actor adoption evidence, local continuity and the declared one-Refresh positive product criterion. |
| A legitimate third-party host operation uses a declared and qualified protected mutation footprint. | An unexamined script changes the same target while the FFI claims all mutations are exclusively owned by Gesso. | Include or exclude that real path, or report the noninterference claim as unproved rather than claiming complete physical correspondence. |

Parts VII–X retain independent installed route/asset coverage,
backend/physical correspondence, HumanHelp positive capability
and proof-kernel obligations. An accepted design example, test
fixture or emitted plan digest does not certify the actual
deployed application.
