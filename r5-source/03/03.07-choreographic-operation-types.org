** Choreographic operation types
:PROPERTIES:
:CUSTOM_ID: req-choreographic-operation-contract
:END:

A choreographic operation type is richer than an ordinary function type.

An ordinary function type is roughly:

#+begin_example
A -> B
#+end_example

A choreographic operation type describes an entry into a distributed protocol
and the valid continuations from that entry.

It may include:

- ordinary value schemas;
- evolving values and their basis;
- roles participating in the operation;
- principal and authority requirements;
- facts known by each role on entry;
- provenance justifying those facts;
- facts on which roles agree;
- resources required by operations;
- facts and values produced;
- possible outcomes;
- provisional execution permissions;
- authority transitions;
- continuation requirements;
- compatibility/version requirements where a suspended projection may outlive a
  deployment.

The operation type should *not* duplicate the complete choreography by manually
listing every branch already represented by the choreography.

The choreography is the source of truth for control flow.

The type declaration supplies external semantic commitments that cannot or
should not be inferred, while analysis derives as much as possible from the
actual choreography.

An admitted operation type therefore joins several different judgments,
rather than representing one large schema:

- *value and presence*: input/output shapes, required versus optional
  values, and the distinction between absence, nil, and a present false;
- *knowledge and provenance*: which role can justify using each fact at
  entry and at each use, not merely which keys appear in the global store;
- *authority and resources*: the bound principal and public model-operation
  interface, plus the resource and ownership permissions needed for effects;
- *control and settlement*: permitted semantic results, role-local
  continuations, and required recovery when an outcome remains uncertain;
- *compatibility*: which source contract, projection, artifact, and version
  conditions allow an already-started execution to continue.

The choreography body supplies derivable branches and value flow. The public
model operation owns its dynamic guard and authoritative effects. An external
operation type may import the model's exposed contract, but may not fabricate
proof of source Clojure predicates, transaction-current enforcement, or
deployed handler correspondence from a matching operation keyword. A checked
judgment identifies the exact supported language and which obligations were
proved, runtime-enforced, asserted, or remain open.

For example, the declaration may state:

#+begin_src clojure
{::choreo/roles
 {:helper
  {:principal :user
   :actor :client}

  :request-authority
  {:authority :request}}

 ::choreo/inputs
 {:request-id
  {:schema :uuid
   :known-by #{:helper}
   :provenance :input}

  :observed-basis
  {:schema ObservedBasisClaim
   :known-by #{:helper}
   :provenance :input}}

 ::choreo/authority
 {:request-authority #{:request/claim}}

 ::choreo/optimism
 {:role :helper
  :projection :request/claim}}
#+end_src

This example declares role requirements, input knowledge, and the intended
optimistic realization. It does not grant claim authority to whoever sends a
matching role label. Trusted server admission must establish the concrete
principal, subject, and operation premises. The helper's input knowledge of an
=ObservedBasisClaim= is knowledge of the claimed token, not evidence that the
helper acquired the observation it names. A schema check on that token can
establish its shape, not its issuer, observation coverage, progression, or
permission to use it as a trusted basis. If a later boundary needs an acquired
=:request/card= observation for optimism, a browser-submitted token alone
cannot satisfy that acquisition premise.

The names =ObservedBasisClaim= and =AuthoritativeBasis= are conceptual semantic
categories.  They do not require two unrelated physical token formats, nor do
they require a particular Clojure nominal-type implementation.  The browser may
carry the same underlying XTDB token bytes that trusted code later compares or
uses to construct a consistency requirement, while the semantic status of those
values remains different.

XTDB-specific representation belongs in the XTDB/Live consistency adapter rather
than being permanently baked into the generic Choreo type vocabulary.

The verifier derives knowledge changes, branch requirements, and continuation
structure from the choreography body. Where a claim depends on an external
model guard, opaque derivation, registered runtime producer, or physical
effect, the checker must retain the corresponding obligation rather than
inventing a derivation from control-flow structure.

*** Operation type admission counterexamples

| Apparent well-typed input | Required classification |
|---------------------------+-------------------------|
| The browser supplies a valid UUID-shaped principal or command identifier | Shape is not authenticated principal or admitted stable command binding |
| The browser supplies a well-formed observed-basis token | An input claim is not a qualified authoritative observation or fresh progression witness |
| A role branches on a declared fact available only on another role's path | Reject unsupported role-local use, even if the global value schema accepts the fact |
| A projected outcome is =:accepted= while authoritative incorporation remains =:commit-unknown= | Preserve the unknown command-specific continuation; presentation cannot manufacture commit evidence |
| A valid operation schema refers to an absent resource or retired DOM owner | A type-shape check does not authorize physical actuation or restore resource rights |
| A suspended execution resumes against a changed contract with the same operation keyword | Require admitted contract/artifact/version compatibility; same name does not validate continuation |
| A typed model operation declares a business invariant but its executable guard is opaque or uninspected | Retain an implementation/policy premise; static schema typing does not prove current model correctness |

A report should identify the failing boundary or open premise: malformed
value, missing role knowledge, unauthenticated provenance, unauthorized
operation, unsupported continuation, or unqualified physical realization.
These categories must not collapse into one successful "typed" verdict.
Finite projection or typed-rule checks may discharge their named properties
without being promoted into an end-to-end physical certification.

The exact Clojure syntax remains tentative. These semantics are the intended
contract.
