** Semantic acceptance obligations

The definitions above require executable judgments, constructive admission
paths, and focused conformance cases. Part IX owns compositional certification;
Part X owns soundness and implementation correspondence. The semantic
definitions used by construction, static verification, projection, the
portable machine, host realization, and assurance tools must agree on their
shared meaning. They must not silently introduce alternative meanings for
a role, value, message, transition, authority, or terminal result.

A case is evaluated against an identified semantic subject, application
assembly where relevant, selected assurance profile, and declared environment
and trust assumptions. The outcome distinguishes a justified admission, a
specific rejected violation, an unresolved obligation, and a capability
outside the selected supported profile. Calling a case "accepted" never means
that all stronger properties have been established. Rejection cannot be used
to claim success when the system should have accepted an ordinary valid
application under the same declared contract.

The following cases constrain Gesso's completed semantic language and its
realizations. Each case remains a mandatory conformance obligation:

| Case | Required result |
|------+-----------------|
| Valid opaque Clojure action with a complete admitted interface | Admit under the selected assurance policy; retain asserted functional/effect premises |
| Missing operation binding or malformed continuation | Reject; an assertion cannot supply the absent structural edge |
| Role uses a value known only to another role | Reject or report the exact missing knowledge obligation |
| Optional message field absent on one path | Do not treat it as definitely present at the join |
| Optional field actually sent without sender knowledge | Reject that semantic send |
| New asserted output overwrites an authoritative binding | Do not inherit the old provenance or dependent applicability |
| Ordinary environment event matches a participant message name | Do not cross the event-class boundary |
| Two receive alternatives accept the same correlated message with different behavior | Reject ambiguity or require an explicit discriminator/equivalence justification |
| Role has equivalent local continuations under the supported relation | Omit an unnecessary discriminator without disclosing private data |
| A result-bearing notifier message contains an authorized =:review/result= but the proof treats it as a neutral message because the displayed notice is identical | Keep the notifier's actual communicated knowledge in the property; reject the unjustified privacy/equivalence claim or admit an independently checked neutral protocol |
| An authored invocation projects an authority-owned result directly into the caller without an admitted transfer or observation | Reject the unearned caller knowledge; preserve the authority event and establish the actual declared return path |
| A browser's successful HTTP response is recorded as a trusted authority operation solely because the helper named it =:authoritative= | Reject incorrect semantic owner and origin; require the installed trusted authoritative binding and command-specific result |
| A recorded/no-notification receiver chooses the variant from missing optional result keys instead of validating the declared tag | Require disjoint literal discriminators and closed variant schemas, or reject ambiguous incoming messages |
| A command-bound =:review-unavailable= message names a fabricated command when pre-command acquisition failed | Reject false command correlation and require authored session-only retirement or a protocol without the waiting participant |
| The sender locally completes a required no-notification disposition and the global outcome is marked complete before receiver consumption or permitted durable handoff | Reject unsupported global termination while preserving allowed local completion and any explicit recovery obligation |
| The first projected role completes, but a required receiver/effect remains outstanding and the proof reports global terminal completion | Require terminal compatibility and disposition of required effects or durable handoffs; local completion is not global termination |
| Role must wait in one branch and return in another | Require a distinguishing path or an explicit conditional-participation contract |
| Unrelated authoritative read follows a foreign commit | Do not discharge a command-specific causal dependency |
| Timeout after submission | Preserve command uncertainty; do not infer a rejected commit |
| Compatible replay returns permitted recorded success | Use the accepted continuation without incorporating again |
| Old resource completion matches the command but not current owner | Reject its stale local effect; separately admit useful reconciliation evidence when permitted |
| Required notification is lost after commit | Preserve the command result and its declared delivery/recovery obligation |
| A required post-commit notification exists only as a browser's future send, and the browser closes after C2 commits | Reject the claimed durable-publication guarantee; require atomic model-side work intent or equally qualified rediscovery |
| A durable worker completes its own valid notification, but an assurance report attaches its receipt to an old manager-to-notifier global plan whose required message was never sent | Reject the proof-subject and topology mismatch; the worker path may satisfy only its admitted graph and explicitly joined business-level obligation |
| A manager browser vanishes after C2 commits; the outbox worker later notifies successfully, but projection claims the manager's required =:send= and the old notifier =:receive= occurred | Reject invented participant transitions; admit the separately authored worker path or a checked delegation/continuation, with distinct terminal claims |
| An accepted C2 is followed by a lost best-effort browser send and the checker selects =:no-notification= as though it were the authoritative result | Preserve C2's recorded outcome; require the exact admitted timeout/closure or weaker attempt-only contract without falsifying command history |
| A durable outbox and optional browser hint both request the same notification, but the provider is invoked twice under unrelated publication identities | Enforce the declared work/occurrence correlation and deduplication or qualified repeat policy; no implicit exactly-once effect is inferred |
| A notifier consumes a command outcome message, then the system reports external notification delivered before the effect provider admits completion | Reject conflation of semantic communication and physical notification; require exact effect-stage evidence for the stronger claim |
| A provider times out after perhaps delivering a notification, and the worker creates a new unrelated work identity to retry | Preserve the original durable intent, uncertain effect outcome, and supported deduplication/reconciliation; do not assume exactly-once execution |
| A formal checker establishes the manager's work-recorded terminal, but an application assurance report calls the notification delivered although no registered worker/provider effect was observed | Preserve the valid review claim; reject the unsupported stronger physical-effect claim and identify missing effect-source evidence |
| The application proves C2 created durable work, but the deployed assembly has no qualified worker ingress, recovery scheduler or permitted discovery path while the release promises eventual notification | Leave the conditional progress/install-coverage obligation unresolved or reject that stronger release claim; a retained outbox row alone is not the recovery mechanism |
| A worker execution reports a provider result for work identity W2, while the composed certificate joins it to C2's retained work W1 solely because their notification payloads match | Reject the unproved work/effect provenance join; require stable admitted work/attempt identity and installed provider correlation |
| A provider acknowledges notification dispatch, but a certificate asserts that a person saw the message | Limit the report to the provider's evidenced stage; require independent fulfillment/receipt evidence for the stronger proposition if its contract supports it |
| A coarse distributed trace omits an effectful =:local= node, yet a proof certificate claims the notification was physically delivered | Require a property-specific physical observation/refinement judgment; coarse terminal trace alone proves no such effect |
| Old typing timer or duplicate report arrives after replacement | Do not hide the new indicator or extend its expiry |
| New valid artifact has different runtime locators | Require exact sidecar correspondence and a separate continuation-compatibility decision |
| Finite graph has a path to return but can loop forever | Report the structural result without a universal termination claim |
| A Malli-valid command claims a privileged principal or authoritative basis | Validate its shape where appropriate but require independently admitted identity, provenance, authorization and basis progression |
| A cached validator or custom predicate is reused after its effective contract changes | Requalify the dependency and affected consumer or report an unresolved premise; names alone are not schema equivalence |
| An explicitly open transport payload contains an undeclared semantic-looking field | Permit only admitted nonsemantic carriage; do not make the extra field role knowledge, authority or a branch input |
| A projector removes an authored communication because an authorized reread might return the same value | Preserve the required semantic occurrence unless an authored alternative or justified protocol refinement establishes the replacement |
| A transport send succeeds, but the destination role never admits the corresponding receive | Do not establish recipient knowledge or stronger delivery/adoption claims from enqueue or transport acknowledgment |
| A semantic message occurrence is delivered twice through different physical attempts | Admit at most the declared semantic effect for that occurrence; equal bytes from separate legitimate occurrences remain distinct |
| A foreign authoritative step is followed by an unrelated current read of the same domain object | Require the exact causal proposition, subject and command/result evidence before discharging the successor barrier |
| A scoped advisory has a valid schema but belongs to a retired subscription or unauthorized recipient | Reject the shared event at its actual source, owner, scope and disclosure boundary |
| An authorized Request acquisition completes but its required browser installation is cancelled | Preserve the outstanding acquire-and-adopt obligation; an HTTP response or proposed swap is not actual adoption |
| An earlier accepted typing =false= is followed by a delayed lower-sequence =true= on the same source | Preserve the high-water mark; do not resurrect a retired indicator or extend its timer |
| A pending durable workflow survives deployment but its original runtime execution is gone | Retain discoverable authoritative work and permit fresh authorized execution; do not assume old execution resources survived |
| Manager review admits direct approval, but the application schedules Finance as if escalation were recorded | Preserve the chosen, command-bound manager branch; Finance is eligible only after the admitted awaiting-Finance outcome |
| The current Expense is approved and the application attributes approval to a specific historical command | Require recorded command-result/causal evidence; current state alone does not identify the initiating actor or operation |
| An old client communicates with a new server and its plan-name matches | Check that directional client/server, operation, codec and route compatibility actually holds or retire/recover before incompatible work |
| A proof sidecar matches an old artifact but the new artifact is only continuation-compatible | Preserve exact evidence identity or establish new proof applicability; operational compatibility does not move exact-coordinate claims |
| A proof of one concrete schedule is reported as universal refinement, liveness or confidentiality | Report the witness-scoped trace and property only; broader claims require separately qualified theorems and premises |

Tests exercising these cases are conformance evidence for the tested subjects
and profiles. They do not replace a proof of the general projection relation,
prove arbitrary host callbacks, or establish every external-system premise.
Negative and mutation cases must reject for the intended semantic reason, not
merely because the fixture became malformed in an unrelated way.

*** Acceptance evidence and claim boundaries

Each exercised obligation records enough stable information to understand
which judgment was tested or checked:

| Evidence dimension | Required distinction |
|--------------------+----------------------|
| Subject | Authored normalized declaration, verified global machine, emitted role plan, assembled application, physical handler, or observed execution, as appropriate |
| Claim | Exact structural, knowledge, authority, projection, trace, safety, progress, privacy, deployment or model-operation proposition being assessed |
| Scope | Relevant actors, data, roles, operations, schema/predicate definitions, application generation, deployment pair and environment assumptions |
| Result | Admitted, rejected with a relevant semantic counterexample, unresolved with named premises, or outside a declared supported profile |
| Origin | Semantic locations and exact artifacts/interfaces on which the evidence depends, with applicable trusted-issuer and disclosure constraints |
| Coverage | Whether the evidence is a test fixture, bounded model check, finite structural theorem, concrete witness, conditional general proof, or installed-application correspondence result |

The generator and assembly checker expose these distinctions without making
ordinary Gesso application authors handwrite a second formal-methods language.
When a model checker, proof kernel, static analyzer, runtime validator, or
physical test discharges an obligation, its actual property and premises remain
visible in the assurance record. A stronger dependent judgment cannot be
claimed merely because a weaker component returned success. A conditional
proof remains conditional, and an unsupported assertion about arbitrary
host-language behavior cannot be relabeled as verified implementation fact.

Cross-layer conformance includes both directions needed for the selected
property: valid authored actions must have justified projected/runtime paths,
and observable projected behavior must trace back to admitted semantics.
A generated runtime cannot introduce a hidden authority, a new observable
effect, or an alternate terminal result merely because no positive fixture
exercised the difference. Tests for message loss, duplication, stale callbacks
or deployment changes exercise the relevant admissible schedules and
recovery premises; they do not assume fair delivery by choosing only
successful schedules.

An accepted physical realization establishes no stronger claim than its
covered installed entry points and writers, runtime artifacts, decoders,
owners, effect implementations, persistence providers and trust bindings.
A test of a mock operation or selected route cannot certify every
production invocation path. The release-level proof/coverage obligations
remain owned by Parts VII, IX, X and XI. The semantic requirements here
are independent of a particular implementation revision.

*** Positive construction acceptance

Acceptance also includes positive cases. The framework must not achieve
apparent soundness by rejecting every meaningful application or by requiring
every application author to implement their own formal toolchain.

| Valid construction | Required positive capability |
|--------------------+------------------------------|
| An ordinary Clojure/ClojureScript function has a complete admitted operation/effect contract but is opaque to the closed prover | Permit it under the selected qualified assurance profile, retaining the relevant explicit premises rather than claiming a proof of its body |
| Two remote branches have equivalent authorized local behavior | Project the legal local continuation without requiring an unnecessary discriminator or revealing private global values |
| An application chooses either a result-bearing or a truly neutral notifier contract for the same manager decision | Admit the chosen protocol with its actual knowledge, authorization, source evidence and disclosure policy; do not force all apps to reveal the branch or to hide it |
| A manager's declared invocation elaborates through a trusted authority role and a correlated result acquisition | Admit the checked expansion and its actual participant-message or environment-observation path without inventing an extra transport message or promoting HTTP success to incorporation |
| A tagged result-bearing or no-notification message uses a checked closed discriminator and sender/receiver source correlation | Admit both unambiguous variants under their disclosure and knowledge contracts, including permitted session-only closure before a command is allocated |
| A sender finishes a local send while the recipient is still processing a required message | Permit local completion and independent receiver progress without claiming the global terminal until its declared communication/effect or recovery obligations are satisfied |
| A successful Expense command records qualified durable notification work, and the notification worker processes it after the manager execution retires | Permit independent command settlement and later stable-identity delivery, retaining debt until the named completion milestone and enforcing disclosure/duplicate policy |
| A review notification is explicitly best effort and its declared terminal promises only the admitted attempt or retirement | Permit that weaker protocol without fabricating a durable notification obligation or claiming external fulfillment |
| Manager review returns after C2 atomically records durable notification work, while an authorized worker's independent execution is still pending | Admit the weaker review-level work-recorded terminal and retain the worker's physical delivery debt; do not invent an old manager send or premature effect fulfillment |
| A durable C2 records stable notification work, then a separate authorized worker execution acquires the pending work and notifies after the manager retires | Admit the declared worker origin, current visibility and effect obligations without fabricating an old manager send or requiring the browser execution to survive |
| A browser-side review notice is deliberately best effort and is lost after C2 incorporation, with an admitted timeout or retirement alternative | Permit the command's independent success and the weaker notification terminal; neither claim global receiver consumption nor create imaginary durable delivery debt |
| The selected assembly has an authenticated C2 operation, recoverable publication work, an independently admitted worker with installed effect bindings, and separately qualified provider observations | Admit the supported *composed* property under its exact command/work/attempt and artifact identities, preserving any remaining provider and progress premises rather than pretending every stage is unconditional |
| An application promises a work-recorded review terminal and separately conditional notification progress, while the worker has not yet fulfilled the effect | Permit the review terminal and keep the documented worker debt open; do not require immediate delivery for the weaker claim or count unresolved progress as completed fulfillment |
| A declared open extension carries nonsemantic adapter data | Permit the extension under its contract while maintaining semantic payload closure |
| A trusted operation is retried compatibly after its state has advanced | Return the permitted recorded outcome under current disclosure rules without attempting a second incorporation |
| A valid projected schedule reorders independent hidden steps | Permit the supported partial order while preserving required causal and observable relations |
| A scoped authoritative reread legitimately establishes a current fact | Admit the fact with its provenance and basis, without demanding an unnecessary peer message or fabricating command-specific history |
| A creator has a correlated accepted Request result and the application allows immediate local update | Permit scoped presentation from that admitted result; other viewers retain their own selective-adoption policy |
| A typing report is lost under an admitted ephemeral policy | Permit absence/expiry without invented durable replay or global workflow failure |
| A valid pending business task outlives E1 and an authorized E2 starts under a newer compatible plan | Admit new execution ownership and current model guards without requiring E1's process to survive |
| A plan changes only diagnostic-only material while its declared continuation relation remains valid | Permit the qualified continuation without treating old exact proof metadata as attached to the new artifact |

Success requires both the expected rejections and these permissible
constructions within their named profiles. The acceptance matrix is a
minimum cross-layer conformance basis, not a closed enumeration of every
valid Gesso program or a substitute for general correctness arguments.
The finished design is accepted only with consistent semantics,
property-specific justified claims, explicit boundary premises, and
nonvacuous support for meaningful application construction.
