*** Choreography may be partial with respect to the whole application

One choreography need not describe an application's entire lifetime.

A choreography may describe one distributed semantic operation or one coherent
short-lived protocol.  Durable model facts may connect many such protocols over
hours, days, deployments, or browser lifetimes.

This means that the following are both legitimate:

A short Claim choreography invokes the operation, interprets the authoritative
outcome or preserves uncertainty, settles its local obligations, and terminates
or hands off recovery under the declared contract.

and:

| Execution | Authoritative role in the workflow |
|-----------+------------------------------------|
| E1 | Create the approval request, establish pending state, and settle or hand off its command |
| E2, later | Acquire current approval premises, act on the request, and settle its own command |

The durable relationship between E1 and E2 lives in authoritative model state
unless the application explicitly adopts a durable workflow facility.
The later execution must acquire its own current premises and authority,
not inherit an expired browser execution's knowledge, resource rights,
pending callbacks, or command identity. E1's command may still need
separately owned reconciliation after E1's presentation retires.
The model's durable relation supplies continuity of business state,
not an implicit suspended local program or permission to replay E1.

This separation prevents Gesso from smuggling a universal workflow engine into
ordinary Choreo merely because some business processes span human time.

*** Choreography validity and application realizability are distinct questions

A choreography can be internally valid while the surrounding application fails
to realize a required use of it. An intentionally unexposed operation is not
automatically an assembly defect: required exposure follows the declared
realization scope and independent product acceptance.

For example, a verified operation may still be unusable because:

- no view binds it;
- no projected browser plan is packaged;
- the packaged artifact is stale;
- no transport binding reaches the trusted server;
- the server has no corresponding execution capability;
- no authoritative acquisition path can observe the successor state.

Missing required realization edges are whole-application assembly failures.
Omitting an intended user capability can instead leave the remaining assembly
closed while failing behavioral completeness. Those distinctions follow the
[[#req-application-assurance-claims][three application assurance claims]] in Part I.
Neither failure changes the meaning of choreography validity itself.

An assembly claim is therefore relative to an *admitted required-use scope*,
not every operation merely present in the model. For a declared use, closure
requires the specified correspondence edges across the projection, artifact,
route, execution capability, model operation, settlement, and observation or
recovery path. A route whose name happens to match does not prove the actual
deployed handler or physical outcome; that stronger claim needs separately
qualified evidence. An omitted optional affordance may be acceptable for
assembly closure and nevertheless fail the product's independent capability
acceptance. The checker must report which question it answered.

The distinction is important:

#+begin_example
valid choreography
    !=
complete application realization
#+end_example

and equally:

#+begin_example
HTTP route exists
    !=
valid choreography
#+end_example

The unified design therefore preserves Choreo as a strong semantic layer while
also requiring whole-application checks of the joins between semantic and
physical/application layers, production enforcement of those checks, and
independent capability acceptance. Closure results retain their actual assurance
classification rather than automatically becoming semantic theorems.

*** Construction must fail when the contradiction is already knowable

Choreography construction and verification must reject known contradictions at
the earliest supported boundary possessing enough information to establish them.
Unsupported constructs must be identified explicitly; they must not receive a
successful result by omission from the checker.

Definition-time failures include, for example:

- unknown roles;
- malformed transitions;
- impossible branch references;
- invalid message declarations;
- inconsistent operation metadata;
- use of an undeclared authority;
- a local behavior that requires a fact that the role can never know.

These failures should not be deferred to browser execution merely because a
runtime implementation could eventually notice them.

This does not mean Gesso should pretend to know dynamic domain facts in
advance.  A Request becoming claimed by another user after rendering remains a
runtime/domain event.  Static strictness applies only where the contradiction is
already present in the declared semantic structure. Static admission must
also require declared handling or recovery for dynamic conditions that can
strand a required operation. It can check that an unknown-result path exists
without predicting whether the next network delivery will be indeterminate.

A structural contradiction, unsupported proof obligation, and accepted opaque
contract are different results. Full-language code is admitted through its
declared boundary and assurance policy; a missing role, unresolved operation
binding, or impossible continuation is not waived by calling it an assertion.

A declared recovery branch is not sufficient on its own when an application
requires that branch to be usable: its owner, required knowledge, temporal
and authority scope, executable plan, and necessary physical route or
acquisition must also be checked at the layer that can inspect them. If a
required edge is known missing, report an assembly failure rather than
calling the branch 'conditionally proven'. If the edge exists only under
an uninspected trusted-host premise, retain that premise explicitly rather
than calling it a proven deployment guarantee. Runtime uncertainty remains
possible even after a sound static check of the available paths.

*** Distinct diagnostic and acceptance cases

| Situation | Correct judgment |
|-----------+------------------|
| An operation is well-formed but intentionally unpublished and not a required application use | Not an assembly closure defect; product completeness is judged separately |
| A declared Claim affordance references a missing browser plan or command transport route | Missing required realization edge; application preflight must reject the required assembly |
| A graph branch reads a value never definitely available to its owning role | Static choreography knowledge/use failure under the admitted entry contract |
| A correctly declared operation races with another actor's Claim | Dynamic authoritative outcome and declared recovery; static validation must not invent rejection or success |
| A =:commit-unknown= route names reconciliation but has no usable registered recovery capability | Reject required-path assembly when checkable; otherwise retain an explicit open binding premise |
| A preflight report agrees with supplied route declarations but no deployed-handler adoption evidence exists | Report bounded source/declaration closure, not a certified installed-server correspondence |
| E2 begins after E1 completed, using a current authorization read | Valid new execution with its own admission; E1's resource/callback rights do not transfer |

The checks can fail at definition, projection, application assembly,
startup or authoritative runtime depending on which trusted facts are
available there. An accepted opaque contract does not override a
known contradiction. A finite local check must not be promoted to a
global proof, and a structurally complete application must not be
called behaviorally complete without its independent acceptance evidence.
