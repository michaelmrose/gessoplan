# R5.1 Part III — 03.07 Choreographic Operation Types

**Baseline:** R4 `main`, Part III “Choreographic operation types” through
the example and its immediate type/knowledge interpretation.
**Candidate:** `r5.1` source unit 03.07.
**Status:** focused R4 preservation audit, not acceptance of whole Part III,
a proof of universal distributed operation typing, or certification of the
deployed application.

## R4 requirements retained

- Choreographic operation types are richer than ordinary `A -> B`
  function types: they describe entry, participating roles, provenance,
  principal/authority, required knowledge, resources, produced facts,
  possible outcomes, provisional permissions, continuations and version
  compatibility.
- Control flow and internal branch structure are derived from the
  choreography rather than redundantly repeated in type metadata.
- The type declaration supplies external semantic commitments, while
  checker/projector analysis derives internal structure and useful
  diagnostics from the one authored semantic machine.
- The example distinguishes an input `ObservedBasisClaim` from
  independently established trusted `AuthoritativeBasis`, regardless
  of whether the physical XTDB token bytes have identical representation.
- A role label or apparent principal shape cannot authenticate a caller
  or grant authority to execute `:request/claim`.
- Generic choreography semantics must not require an XTDB-specific
  representation or a forced Clojure nominal class.
- The illustrative namespaced Clojure declaration remains tentative.

## Stronger R5 design preserved

- Separate command binding, real-world principal authentication, model
  current guards, scope-qualified observation and ownership of provisional
  UI resources, as established in reviewed Parts I–II and 03.03–03.06.
- An operation's semantic identity is distinct from transport and physical
  representation. Contract compatibility is a further check; neither
  unchanged keyword spelling nor token shape establishes compatibility.
- A generic exported interface remains smaller than the full execution
  body; typed model/policy evidence and physical correspondence have
  independently identified owners and premises.

## Changes in this revision

1. Specify five operation-type judgment families: value/presence,
   role-local knowledge/provenance, authority/resources,
   outcome/control/recovery and continuation/version compatibility.
2. Keep choreography-derived branches distinct from externally imported
   model guard facts, and state that an imported operation keyword does
   not prove opaque Clojure or deployed handler correctness.
3. Clarify that a valid observed-basis token shape does not establish
   issuance, coverage, ordering or permission to satisfy an optimistic
   acquired-observation premise.
4. Require the checker to distinguish proved, runtime-enforced, asserted
   and open obligations rather than returning an unqualified type success.
5. Add seven concrete negative cases for untrusted identities, basis
   claims, unavailable role-local facts, premature accepted settlement,
   stale physical ownership, incompatible continuation and opaque
   uninspected model policy.

## Gesso implementation correspondence and limits

- `gesso.choreo.type` provides Malli-backed portable shape categories
  including Role, Principal, Actor, Authority, CommandId and ExecutionId.
  Its own contract states that shape validation cannot authenticate
  identities, justify knowledge or establish model legality.
- `gesso.choreo.verify` implements definite-value availability,
  role-local must-knowledge and definite-authoritative classifications,
  but disclaims authority authenticity, progression, full refinement,
  runtime resources, browser execution and arbitrary liveness.
- `gesso.choreo.proof` has exact finite structural/compiler projection
  checks and explicit dynamic step-refinement nonclaims; these are not
  a general end-to-end operation-type theorem.
- `gesso.assurance.proof.typed-rule-admission-correspondence` compares
  admitted typed-rule sources against independent branch-sensitive
  semantics on three synthesized states, with universal equivalence
  explicitly unproved.
- `gesso.assurance.proof.operation-interface-composition` composes
  bounded source-derived abstract operation contracts and retains open
  invariant premises, but does not issue physical writer coverage,
  admission, authorization or concurrency-refinement certificates.
- This implementation contains useful type, analysis and assurance
  pieces; no current component inspected claims to combine them into
  the full R5 distributed operation-type admission guarantee.
