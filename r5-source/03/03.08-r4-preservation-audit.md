# R5.1 Part III — 03.08 Operation Identity and Boundary Categories

**Baseline:** R4 `main`, Part III “Operation identity is semantic, not
transport identity” and “Semantic categories at operation boundaries.”
**Candidate:** `r5.1` source unit 03.08.
**Status:** individual preservation review, not Part III acceptance or
certification of trusted admission and physical execution.

## R4 normative obligations retained

- The semantic identity of `:request/claim` differs from a route, HTTP
  method, view element, browser plan index, physical handler or host.
- Keeping an operation keyword constant does not prove that a changed
  rule, input requirement, outcome, postcondition or authority is compatible.
  A compatible physical refactor need not change the semantic contract.
- `ObservedBasisClaim` and acquired `AuthoritativeBasis`,
  `CommandId` and `ExecutionId`, provisional and authoritative facts,
  raw declarations and admitted values, and raw versus checked evidence
  remain meaningfully non-interchangeable.
- No particular `defrecord`, Java type, forced wrapper class or
  separate physical basis token representation is required; choose the
  smallest practical mechanism for the supported threat model.
- Ordinary application code should supply domain values and source
  declarations, leaving derived category establishment to Gesso where
  possible. Unadmitted or unknown values produce precise diagnostics.
- Wire serialization, client-provided labels and matching shape do not
  preserve authenticated or checker-established status.
- Deliberately hostile host code with equivalent JVM/database privileges
  remains outside this ordinary-cooperating-code misuse boundary.

## Stronger R5 design retained

- The normalized semantic contract, its source ownership and version,
  command binding, separate execution identity, actor/principal/role,
  authority scope and physical ownership are independently meaningful.
- Static semantic checking and role-local knowledge do not confer
  production authorization. Physical target/host replacement requires
  source-qualified compatibility rather than accidental name equality.
- The distinction between structural, trusted runtime, and proof-kernel
  evidence persists through transported and serialized interfaces.

## Changes in 03.08

1. Explicitly separate semantic operation name, normalized source
   contract/version, command intention, individual execution, principal,
   host/authority and exact ExecutablePlan artifact content.
2. Qualify semantic fingerprints/digests as content comparisons under
   canonicalization and source binding, not independent proofs of
   authorization, source equivalence or physical installation.
3. Require compatible replay to retain the trusted binding rather than
   permitting principal/argument/authority changes under one command ID.
4. State category evidence is scoped to issuer, subject, consumer and
   temporal/authority context; structural handles and descriptions do not
   become transferable trusted admissions by serialization.
5. Add seven counterexamples for changed policy, incompatible replay,
   same-shaped IDs, wire identity, forged/copied assurance, digest-only
   deployed matching, and stale owner/authority basis.

## Current Gesso correspondence

- `gesso.choreo.identity` provides tagged, shape-distinct identities
  for principal, actor, authority, host, command and execution. It does
  not authenticate them or prove the raw value portable over arbitrary
  serialization codecs.
- `gesso.choreo.type` validates the Malli shape of these semantic
  categories and an opaque basis, but does not establish authorization,
  provenance, basis progression, or distributed refinement.
- `gesso.choreo.knowledge` preserves explicit authoritative
  observation/basis scope and checks closed progression witness shape;
  its own contract says shape does not prove the authority-specific
  ordering relation is truthful.
- `gesso.assurance.admission` issues JVM-local, identity-bound handles
  for named structural checks only. A copied report or forged handle
  is not admitted, and a real handle is not a theorem or production
  authorization capability.
- `gesso.choreo.artifact` computes canonical SHA-256 digest identities
  for exact ExecutablePlans and binds diagnostic sidecars to artifact
  data. That does not authenticate an installed server or its model
  behavior.
- `gesso.model.command-resolution` checks structural command binding
  and recorded-outcome shape and guards duplicate command ID creation,
  while deferring principal authentication, domain-guard completeness,
  permitted disclosure and physical XTDB behavior to separate premises.
