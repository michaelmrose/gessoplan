# R5.1 Part III — 03.06 Canonical Authoring Principle

**Baseline:** R4 `main`, Part III “Canonical authoring principle,” including
its illustrative Claim declaration, projected helper, application binding and
trusted handler. **Candidate:** `r5.1` section 03.06.
**Status:** individual R4 preservation review, not Part III acceptance,
current public-API compatibility or certified application installation.

## R4 requirements preserved

- A Gesso application author describes semantic intent once wherever lower
  level plans, view descriptors, transport bindings or diagnostics can be
  derived. The author should not copy the same operation semantics across
  independent registries and hope strings remain synchronized.
- Independent physical choices (for example routes, actual model bindings,
  hosts and implementation adapters) may remain independent but require
  explicit, checked correspondence to the declared semantic operation.
- Choreo remains a global coordination specification, not one macro or
  source-language replacement that owns every aspect of the application.
- HumanHelp Claim requires trusted principal authentication and
  transaction-current Request, Membership, Organization and corresponding
  organization/claim-authority policy checks; browser possession of a
  Request id or observed card does not establish those premises.
- The command is identified before its first possible send, bound to
  operation, arguments and principal, and preserved across retries.
  Replay of a compatible recorded success differs from new incorporation.
- Accepted, rejected and indeterminate command outcomes have distinct
  continuation, reacquisition and recovery semantics.
- A view naming Claim does not independently establish that its generated
  browser plan, transport, deployed handler, model implementation and
  recovery path all correspond or are available.
- The R4 defoperation, defview, project-operation and bind-operation examples
  were provisional authoring notation, not verified present APIs.

## Superior R5 treatment preserved

- Source-owned business-rule dependencies are imported through the public
  model operation; authoring input/entry knowledge and provisional display
  do not replace transactional claim guards.
- A stable bound command identity and an execution/target/resource owner
  contract are distinct; later reconciliation does not restore obsolete
  callback DOM rights.
- Settlement distinguishes `:committed`, compatible
  `:already-incorporated`, `:rejected` and `:commit-unknown`, including
  current disclosure and authoritative successor acquisition.
- Assembly closure is relative to required exposures; optional surfaces
  and product capability completeness have separate acceptance tests.
- A proposed trusted handler obtains the dispatched route binding from
  trusted runtime context and the authenticated principal from the session,
  not from browser-supplied role, command or route names.

## Changes in 03.06

1. Specify the ownership of individual semantic facts rather than treating
   “one declaration” as a universal map: model owns business rules; Choreo
   owns coordination; view owns presentation intent; deployment owns
   genuinely independent physical bindings.
2. Require source identity, applicable version, derivation/import provenance
   and explicit opaque-premise classifications for generated joins. Do not
   promote matching strings or imported model operation names to proof.
3. Preserve R4's dynamic Membership, Request, Organization and
   claim-authority dependencies explicitly through the R5 imported model
   operation interface, including an observable contract revision.
4. Mark =gesso/action=, =assembly/realize-operation= and the shown
   bound-handler APIs as proposed interfaces rather than claiming they
   are all implemented public functions today.
5. Add seven acceptance cases covering missing plans, deployed route
   adoption, missing guard dependencies, untrusted client identity,
   optional affordances, stale DOM owners and dynamic raw HTML bypass.

## Correspondence to current Gesso

- `gesso.choreo.core` supplies the concrete six-opcode global authoring
  API, not the fully generated R5 Claim declaration surface.
- `gesso.choreo.preflight` checks canonical executable plans, required
  PlanRegistry keys, roles and optional artifact digests. It explicitly
  does not establish operation authorization or whole-application binding.
- `gesso.live.application-preflight.assurance` describes bounded
  application/supplied-render-surface closure, explicitly leaving actual
  Biff handler adoption, bypass routes and full dynamic surface enumeration
  as unproved physical premises.
- `gesso.live.application-preflight.semantic-audit` states that actual
  trusted model predicates, guards and rule dependencies are not exposed
  in the current operation summaries, so importing a name does not prove
  Claim's current guard implementation.
- `gesso.assurance.proof.application-assurance-report` is a conditional,
  nonauthoritative source-derived report; installed handler, full writer
  coverage, browser/HTMX correspondence and kernel soundness remain open.
- A constructor call, structural match or copied report is not a grant
  of authority or a guaranteed runtime capability.

## Cross-part obligations

- 03.07–03.14: operation type imports, closed source semantics, typed
  inputs and outputs, source-derived metadata, policy/opaque contracts.
- 03.15–03.25: checked projection and knowledge, owner-relative browser
  effects, continuation and notification semantics.
- Part IV: atomic guarded incorporation, compatible command replay,
  authority-specific recorded outcomes and protected disclosure.
- Parts VI–VII: executable HTMX/CLJS binding, routes, actual Biff handler
  adoption, rendered Hiccup surfaces, physical producer/consumer closure.
- Parts VIII–X: HumanHelp Claim acceptance, formal model correspondence
  and independently qualified evidence.

All R4 authoring and Claim authority requirements remain represented.
Existing Part III headings and anchors are unchanged. This audit is a
documentary result and does not claim these proposed interfaces already
exist or that every opaque model obligation has been checked.
