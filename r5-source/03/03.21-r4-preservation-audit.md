# R5.1 Part III — 03.21 Projected Guards and Failure Diagnostics

**R4 baseline:** Part III, “Local executable guards belong in the executable
projection,” “Projection failure should identify the missing justification,”
and “Host-language callbacks may not bypass projected semantics.”
**R5.1 candidate:** section 03.21.
**Disposition:** focused R4 preservation audit. Canonical Org describes the
completed framework, not this implementation's current feature count.

## R4 normative requirements preserved

- Proof derivations and global proof trees remain outside the production
  browser. Required local semantic guards remain executable at the
  appropriate runtime or trusted admission boundary.
- Resource instance, execution and shared owner identities are distinct;
  a universal generation comparison is not a valid substitute for
  operation-specific ownership and correlation.
- Passing an owner check does not manufacture knowledge, provenance,
  authentication, authorization or authoritative progression.
- The executable semantic core evaluates runtime guards; assurance
  can explain why they are sufficient but does not eliminate the check.
- The machine does not depend on optional proof sidecars for transitions.
- Projection failure reports role, location, divergence, required facts,
  provenance, missing knowledge and potential paths when available.
- Host callbacks realize declared effects, return normalized outcomes,
  and undergo owner-relative event admission before any semantic state
  transition; direct callback mutation is not a second transition API.

## Superior R5 treatment retained

- The compact runtime guard/proof-sidecar comparison remains, with the
  diagnostic artifact bound to its exact executable subject.
- The explicit R5 prose is retained as semantic meaning, but the R4
  transition sequence is restored as a compact example to avoid
  grammatical ambiguity in the unmodified R5 subsection.
- Browser runtime evidence remains owner-relative: execution-private
  callbacks and shared fragment/subscription events use different
  scopes, while proof material does not add a new executable owner.

## Improvements in 03.21

1. Bind guards to their operational contracts, inputs, evaluation points,
   failure continuations, and trusted physical admission sites. Server
   authorization is never downgraded to a browser-supplied Boolean.
2. Require normalized effect completion, current owner and transition,
   resource correspondence, applicable schemas, and serialized or
   equivalently safe final mutations. A detached precheck is not enough.
3. State that diagnostic sidecar removal leaves runtime semantics
   unchanged, while a missing runtime guard changes the contract and
   requires renewed assurance.
4. Expand projection diagnostics to distinguish definite invalidity,
   unresolved assumptions/opaque predicates, unsupported constructs
   and physical-admission failures, with provenance and origin mapping.
5. Apply disclosure/redaction to compiler and runtime reports, preserving
   useful identifiers without leaking private branch predicates.
6. Clarify stale callback versus independent authoritative command
   disposition; ignoring a browser effect is not proof of rejection.
7. Add ten counterexamples covering stale ownership, wrong shared
   owner, client authorization forgery, check/use races, uncorrelated
   completions, sidecar misuse, synthetic facts, privacy and command
   uncertainty.

## Current Gesso correspondence (audit only)

- `gesso.choreo.project` emits compact executable plans and retains a
  separate compiler-side provenance/diagnostic mapping.
- `gesso.choreo.artifact` binds non-executable diagnostic/proof
  sidecars to exact runtime plan digests and rejects mismatched
  artifact combinations.
- `gesso.choreo.verify` performs explicit role/value/knowledge
  must-analyses and exposes diagnostics, but its documentation
  excludes a claim that every runtime ownership guard is proven.
- `gesso.choreo.machine` retains protocol state and declared inputs;
  effect execution, trusted authoritative admission and physical
  browser actions remain outside the portable role-local machine.
- `gesso.live.browser.adapter` owns normalized effect transitions,
  execution and timer generations, stale-callback rejection and
  scoped fragment events, but its declarations do not themselves
  prove browser DOM installation or server authorization.
- `gesso.choreo.proof` explicitly distinguishes finite structural
  projection properties from universal dynamic refinement.

## Cross-part obligations and joins

- Part II: `req-owner-relative-event-admission` requires only the
  identity and correspondence checks relevant to a given boundary;
  a matching id is never complete provenance or progression evidence.
- Parts IV–VI: trusted operation admission and settlement, stale
  callbacks, browser DOM/HTMX installation, optimistic command
  reconciliation and owner-lifecycle safety.
- Parts VII and IX–X: exact installed assembly, source-to-artifact
  identity, property-specific assumptions, proof scope and the
  boundary between executable guards and assurance products.
- Section 03.22: durable workflow waiting does not grant suspended
  in-memory machine state or accidentally retain retired resources.

No substantive R4 requirement was intentionally discarded. Unfinished
implementation obligations remain in the audit and do not narrow the
timeless target specification.
