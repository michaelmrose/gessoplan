# R5.1 Part III — 03.23 Later Executions and Expense History

**R4 baseline:** `main` Part III, “A later choreography is not automatically
the same execution,” including Monday/Thursday/Friday Expense examples.
**R5 candidate:** the 03.23 tabular Expense and command-history account.
**Disposition:** focused R4 preservation and future-target design review,
not a statement of which capabilities are installed today.

## R4 normative obligations preserved

- One continuous domain workflow may consist of separate E1/E2/E3
  choreographies with new execution identities, principals, entry
  knowledge, resource ownership and applicable plans.
- Command C1, C2 and C3 identities do not collapse into process
  execution, domain identity, workflow identity or transient
  transport/invocation attempts.
- Monday's authoritative Expense submission checks current ownership,
  draft status and other model guards atomically with the submission
  and command outcome.
- Thursday's manager operation has two distinct authoritative
  continuations: approval by manager or escalation to Finance,
  depending on current Expense and policy evidence.
- Friday's Finance review applies only to a qualifying
  awaiting-Finance Expense and requires fresh authorization,
  selection, observation and authoritative commit guards.
- Compatible command replay returns recorded historical outcomes
  with current disclosure checks, not fresh incorporation under
  Monday's old draft-state preconditions.
- Unknown incorporation remains reconciliable despite process/UI
  retirement; current status is not proof of a specific command's
  historical disposition.
- Effective and recording time are distinct where the model's
  semantics require them; historical and runtime identities can be
  inspected without mandating one event-history storage layout.
- Persisted machine continuations are optional and have additional
  checkpoint, versioning and recovery obligations.

## Superior R5 treatment retained

- Keep R5's compact tables and public model interface, rather than
  restoring R4's large `defchoreo` illustrative programs and
  application-supplied `:commit-guards` that could suggest users
  bypass model-owned business authorization.
- Preserve stable bound-command identity and honest model outcome
  classification: committed/already-incorporated/rejected/unknown.
- Preserve the explicit distinction between externally generated
  submission time and canonical semantic command arguments.
- Keep R5's illustrative history as an inspection view, not a
  requirement for one long event vector or universal event DAG.
- Keep future opt-in durable continuation available without making
  it the default life-cycle model.

## Focused improvements in 03.23

1. Distinguish durable domain facts from execution-private authority
   and note that physical invocation IDs can change across a
   compatible replay of the same command.
2. Restore the R4 manager-approved *or* escalation branch in the
   R5 example; bind C2 to exactly the selected operation, and make
   Friday Finance conditional on actual escalation.
3. Specify that queue selection and pre-observed policy are not
   commit-time authorization. The model protects current mutable
   Expense/Policy dependencies on each incorporation.
4. Mark example operation function names as schematic contracts,
   not claims of current literal implementation.
5. Clarify command intent canonicalization, replay disclosure, issuer
   scope, historical result meaning and what changes across plan
   deployments without retroactive rewriting.
6. Distinguish domain effective/recording time and transport attempt
   time, preserving recorded values on compatible retries.
7. Make unresolved command handoff survive local process/UI
   retirement without multiplying effects or inventing new intent.
8. Add twelve counterexamples covering bulk approval, branch
   substitution, stale policy, extraneous Finance, borrowed
   principal, replay guards, disclosure, uncertain retries, time
   change, history inference, deployment compatibility and
   conflicting concurrent attempts.

## Current Gesso implementation evidence (audit only)

- `gesso.choreo.type` separates tagged command identities from
  execution identities, and describes command meaning as distinct
  from physical execution.
- `gesso.choreo.machine` admits separate command and execution
  identity bindings in portable protocol execution. It does not
  itself own business principal authentication or persistence.
- `gesso.choreo.knowledge` distinguishes authoritative observations,
  input, communicated, derived and asserted facts, but does not
  itself establish application-specific Expense authorization.
- `gesso.choreo.project` emits role-local executable plans and
  supports separately checked plan compatibility; that is not
  proof of durable cross-deployment business-state migration.
- Gesso's current core is not used as a ceiling for the intended
  Expense model, replay or assurance contracts; the canonical
  Org text names completed-system obligations.
