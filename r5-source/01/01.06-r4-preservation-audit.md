# R5.1 — Part I section 01.06 preservation audit

**Source:** R4 `main` compared with R5.1 `01.06-runtime-assumptions-and-evidence.org`.
**Status:** sectional normative review complete; full Part I and twelve-part
R5 acceptance remain open. This is not an executable conformance result.

## R4 commitments retained

- All nine R4 semantic subsections are preserved, including runtime-enforced
  premises, trusted assumptions, application assertions, assembly verification,
  conditional liveness, tested evidence, claim composition, failure repair,
  and the assurance-model invariant. R5 adds backend qualification as a
  distinct subsection without deleting those responsibilities.
- Dynamic principal, authorization, scope, command, progression, and effect
  premises still require actual trusted enforcement, rather than a pre-read,
  self-attested report, or downgraded fallback HTMX action.
- Explicit trust premises remain named, scoped, and carried into dependent
  claims; application assertions remain distinct from framework assumptions.
- Finite checking, browser tests and assembly graph validation retain their
  actual evidence classes and do not become universal formal proofs.
- Liveness remains conditional on scheduler/environment/user action, and
  operational failure points to the actual owning repair boundary.

## This revision's focused corrections

1. Backend qualification now explicitly includes *durable command exclusion*
   and retention/expiry behavior, distinguishing duplicate-incorporation
   prevention from result-disclosure retention. Where required, command result,
   domain change, and publication intent share the admitted atomic boundary;
   delivery itself remains a separate protocol. Test coverage includes
   conflicting/replayed command bindings and expiry.
2. Structural assembly verification no longer says that a declared startup
   ordering **makes preflight unavoidable**. It proves an obligation about
   declared graph/lifecycle construction; actual Biff server adoption, captured
   dispatch paths, and non-HTTP writers still require production evidence.
3. Liveness and recovery distinguish *converged current presentation* from
   *known historical command disposition*. A card read can repair UI state
   without attributing a prior command. Eventual attribution needs command
   evidence, compatible binding, retention, authorization for disclosure and
   active reconciliation. Explicit Refresh requires a user action where that
   product contract applies, not merely an outstanding advisory.

## Cross-part consistency

- Part IV owns authoritative command incorporation, retention, outbox and
  authoritative progression.
- Parts VI and VIII own owner-relative browser settlement, explicit Refresh,
  acquisition, and physical installation.
- Part VII owns deployed application path enforcement and writer coverage.
- Parts IX and X own genuine assumption discharge and formal-to-physical
  correspondence; Part XI owns mandatory release gate interpretations.

No original R4 normative obligation was intentionally discarded here. The
new clarifications do not assert that current Gesso or XTDB has already
established all those requirements.
