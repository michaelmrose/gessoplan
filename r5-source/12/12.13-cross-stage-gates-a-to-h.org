** Cross-stage acceptance invariants

These invariants apply whenever the corresponding boundary is present. They are
not a final ceremonial checklist that can excuse an earlier unchecked path.
The owning Parts define the complete contracts; a roadmap summary cannot weaken
them.

*** Gate A -- No silent semantic downgrade

A declared semantic operation retains its command, plan, provider, authority,
result, and recovery requirements through the actual invocation. Missing required
data rejects or renders an explicitly unavailable affordance. It cannot silently
drop the operation's managed contract and issue an ordinary request.

Explicit unavailability can be structurally valid while still failing a product
milestone that requires the operation to work. The independent capability oracle
prevents that distinction from disappearing.

*** Gate B -- One connected semantic subject

Runtime, tests, proof subjects, projected plans, and generated artifacts consume
one admitted meaning or an explicitly justified representation relation. A richer
test-only model cannot substitute for production. A second representation is
allowed; an unaccounted second application semantics is not.

The permanent executable semantic core, dedicated semantic checkers, small proof
kernel, and external proof checker retain different responsibilities. Stronger
proof does not replace the runtime or make a sidecar a new control channel.

*** Gate C -- Source ownership stays single

Public models own business truth; choreography owns interaction; projection and
build derive their realizations; application assembly joins them. The audit and
proof surfaces derive from those objects. They do not manually synchronize a
second rule inventory or inject HumanHelp-specific policy into the framework.

Opaque host code is part of the same construction through its explicit contract.
Its unproved properties remain premises rather than duplicated pretend rules.

*** Gate D -- Authority remains at the trusted boundary

Browser-supplied role or principal claims, certificates, plan-looking maps, basis
tokens, and DOM state grant no server authority. Trusted invocation binds identity,
and current public model rules govern protected reads, subscriptions,
command-result disclosure, and mutations.

A certificate about an operation cannot manufacture a current Membership or
Organization policy. A checked rendering cannot replace authorization when a
hostile client bypasses the page.

*** Gate E -- Exact artifact and implementation binding

Where exact correspondence is claimed, the actual bytes, plan registry, issued
callables, and installed bindings are checked. A name, timestamp, copied digest,
source similarity, or local report is not sufficient. The build receipt binds
the admitted manifest and qualified build path to its actual output.

Semantic compatibility and exact byte identity are separate relations. A changed
implementation requires reconsidering its physical evidence even if an abstract
contract remains reusable.

*** Gate F -- Dynamic premises remain dynamic

Static preflight need not predict current authorization, future availability,
transaction races, or callback schedules. It must require the declared compatible
handling and recovery paths in [[#req-preflight-dynamic-handling-coverage]].
Runtime boundaries then acquire or enforce concrete premises at their proper
use points.

An existing path proves neither that its scheduler runs nor that its required
user action occurs. Safety must continue when liveness premises fail.

*** Gate G -- Real physical integration remains required

Portable state-machine checks do not replace the real browser lifecycle, backend
transaction, installed server, or multi-node failure boundary. Each acceptance
claim identifies the actual subjects and observation origins it exercised.

A required failed, skipped, unavailable, unsupported, stale, missing, or incomplete
check does not pass. Expected negative tests must reach their intended boundary;
an unrelated earlier failure is not equivalent evidence.

*** Gate H -- Reject contradictions when they become knowable

A statically known incompatibility blocks construction. A concrete malformed
render blocks delivery through the real response boundary. Invalid invocation
blocks protected work; an invalid transaction guard blocks incorporation; expired
effect permission blocks physical mutation.

The first applicable boundary is specific to the obligation. A later render
failure cannot undo an already incorporated command, and diagnostics must not
claim that it did.
