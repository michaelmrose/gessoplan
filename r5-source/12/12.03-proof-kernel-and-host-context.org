*** Stage 3 -- Small proof kernel and guarded proof mechanisms

Build the narrow proof-checking foundation alongside runtime construction. It
is a separate component from the executable semantic core and is a prerequisite
only for claims that require its judgments. Ordinary operational delivery does
not wait for external formalization of this kernel.

Deliver the actual closed propositional rules from Part IX: premise, truth
introduction, implication reflexivity, conjunction introduction and elimination,
implication elimination, and disjunction introduction. Check source syntax,
subject/type bindings, prior-step references, exact conclusions, and premise
accounting. Do not introduce atomic truth axioms, arithmetic solving, or
hypothetical premise discharge through an undocumented shortcut.

Elaboration may search for or generate candidate derivations, but the small
kernel checks their source independently. A failed or bounded-out search reports
that result; it cannot add a truth axiom or silently turn an obligation into a
premise. Proof search need not be part of the trusted kernel.

Dedicated guarded-transition mechanisms describe pre-state, input, guards,
simultaneous assignments, and framed fields. They produce the supported
consequence and invariant-preservation judgments. Conditional induction checks
the initial condition and every operation against every required invariant in
one declared catalog, with the source-derived obligations intact.

Acceptance includes valid conditional proofs, malformed derivations, wrong
subjects, invalid substitutions, omitted preservation cases, unsupported effects,
and false premise discharge. Positive initial-state and operation examples expose
vacuous unusable constructions. A proof of a declared abstract machine does not
establish a real initializer, all physical writers, or database refinement.

The result is a checkable derivation or dedicated judgment result under named
premises. Certificate issuance and complete cross-layer composition are separate
consumers. Copying a checked report does not create an issued capability.

*** Stage 4 -- Qualified host, lifecycle, and invocation context

Select and qualify the concrete Biff, Ring/Aleph, runtime, browser/HTMX, compiler,
and XTDB integration contracts the application will use. A label such as “final
Biff 2” is not a substitute for the actual dependency identity and behavior.
The plan does not require waiting for an unspecified future dependency release.

Deliver:

- explicit invocation input and previous-output value flow for model/FX execution;
- stable lifecycle identities, dependency ordering, ownership, start/init behavior,
  and cleanup;
- private construction and installation before managed application exposure;
- a supported server handoff that adopts the actual guarded handler;
- request-local assembly and authority context with independent concurrent scopes;
- explicit context transfer and retirement for supported asynchronous work,
  deferred responses, streams, workers, and subscriptions;
- qualification records and assumption-sensitive tests for the selected substrate.

Acceptance verifies real handler adoption, missing-provider rejection, startup
failure cleanup, concurrent request separation, and permitted deferred completion.
A thread-local binding alone cannot authorize work after its scope ends. One
global one-use writer or lease is not a general concurrent application model.

This stage supplies the lifecycle and enforcement interfaces. It cannot report
whole-application closure before Stage 10's actual required checks exist. A
private listener or separately admitted health response must not expose unchecked
application behavior under a startup exception.
