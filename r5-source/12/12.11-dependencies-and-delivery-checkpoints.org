** Dependency structure and delivery checkpoints

*** Prerequisites describe contracts, not completed stage numbers

The following table gives the principal entry dependencies. “Contracts from” means
the specific supported slice being consumed; it does not mean every possible
feature of that earlier stage must be complete. A claimed exit gate still requires
all applicable acceptance evidence for its scope.

| Stage | Principal contracts from stages | Additional scope condition |
|-------+---------------------------------+----------------------------|
| 1 | None | Declare semantic ownership and independent requirements |
| 2 | 1 | Use one versioned rule/value interpretation |
| 3 | 1, 2 | Proof-required claims only; no physical execution inferred |
| 4 | 1 | Select actual host/provider applicability envelopes |
| 5 | 1, 2, 4 | Public operation contracts and real command protocol |
| 6 | 4, 5 | Qualify the actual physical forms and provider semantics used |
| 7 | 1, 2, 5 | Project public contracts without copying domain policy |
| 8 | 4, 7 | Qualify physical browser events and effect gates |
| 9 | 5, 6, 8 | Bind publication, reads, grants, coverage, and adoption |
| 10 | 4, 5, 6, 7, 8, 9 | Close and install the selected application slice |
| 11 | 10 | Apply release/profile and environment-specific gates |
| 12 | 5, 6, 7, 8, 9, 10, 11 | Complete independent HumanHelp requirements and product decisions |
| 13 | 3, 5, 7, 10 | Add the real Claim browser slice; full rich-board completion is not a prerequisite |
| 14 | 2, 5, 6, 7, 8, 9, 10 | Add 3 and 13 for proof-specific mutation coverage |
| 15 | 1, 2 | Consume actual later boundary evidence when available; label early fixtures |
| 16 | 2, 3 | Select a stable formal theorem domain |
| 17 | 11, 13, 16 | Bind the formal result to the actual requested production scope |
| 18 | 4, 5, 6, 8, 9, 10, 11 | Use the deployed application's required behavior and actual topology |

The table contains no backward requirement that an unfinished response feature
must be invented before a Claim theorem can be checked. It also contains no
requirement to finish external formalization before testing host loss. Such work
can proceed with honest narrower scope while full milestones retain their gates.

The lifecycle boundary exists before full assembly checking, but a placeholder
closure result cannot admit a full application. Diagnostics exist before formal
backends, but a fixture explanation cannot claim generated-backend coverage.
Release machinery exists before complete HumanHelp, but a narrow candidate cannot
claim the full product milestone. These are incremental scopes, not circular
permissions to skip checks.

*** Useful integrated checkpoints

The shortest useful operational path combines the relevant portions of Stages 1,
2, 4–11 and the first Claim case from Stage 12. Stage 3 and formal work can run
alongside it when their semantic subjects are ready. The checkpoints are:

| Checkpoint | Concrete result | Required limitation |
|------------+-----------------+---------------------|
| Semantic operation | One public Claim contract with commands, dependencies, outcomes, and explicit premises | No assertion that a physical transaction already implements it |
| Qualified authoritative slice | Actual mediated Claim writes and command resolution satisfy the selected physical contract | Report backend premises and writer coverage honestly |
| Installed browser slice | A rendered Claim reaches that operation and produces permitted settlement or recovery through the actual plan | Claim alone does not complete HumanHelp |
| Rich proving application | All Part VIII gates pass, including independent capabilities and response contract | No implication of external proof or production multi-node completion |
| Compositional Claim | The same subjects compose through required closure, issued evidence, and actual realization bindings | Accepted implementation/provider premises remain conditional |
| External kernel transfer | Declared formal result applies through its stated production correspondence | No automatic extension to every Gesso operation or physical system |
| Production topology | Declared multi-node envelope passes real failure, compatibility, and load evidence | No unconditional liveness or universal message delivery claim |

The first browser checkpoint includes rejection and unknown recovery, not just
one successful response. Adding more proof infrastructure while that path is
miswired does not repair its missing provider, stale artifact, or physical effect
boundary. Conversely, a working button does not discharge a required invariant
or omitted source dependency.

*** Completion mapping

Part XI owns the completion criteria. This map prevents roadmap progress from
being confused with a different milestone:

| Completion scope | Principal evidence | What cannot substitute |
|------------------+--------------------+------------------------|
| [[#milestone-operational-application][Operational application]] | Stages 1, 2, 4–12 plus applicable runtime cases and explanations from 14–15 | Closed subset, Claim-only demo, or disabled required capability |
| [[#milestone-compositional-certification][Compositional certification]] | Stages 1–3 and 13 joined to the relevant runtime/application path, with 14–15 coverage | An isolated proof fixture or copied report hierarchy |
| [[#milestone-external-formal-verification][External formal verification]] | Stages 16–17 with the declared theorem set and production transfer | Finite examples or a theorem about an unrelated checker |
| [[#milestone-multi-node-production][Production multi-node]] | Stage 18 with applicable operational and release contracts | Two host labels, one successful balanced request, or untested recovery |

No row authorizes dropping a mandatory profile requirement. A release asking for
stronger assurance remains blocked when that requirement is unsupported or its
evidence is missing. A deliberately narrower release changes its declared scope
and retains the original full requirement set as unmet.
