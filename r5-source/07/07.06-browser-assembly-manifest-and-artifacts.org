** Browser assembly manifest and physical artifacts
:PROPERTIES:
:CUSTOM_ID: req-browser-assembly-manifest
:END:

The browser build consumes the admitted semantic/build inputs of the same
application definition. Its manifest identifies the exact admitted plan set,
operation-to-plan correspondence, executable identities, interpretation/profile
contracts, required physical handlers, and relevant implementation/toolchain
inputs. It does not contain a digest of bytes that do not yet exist.

The admitted plan inventory must cover every required operation realization and
identify any deliberately included shared or currently unused plans. Missing,
duplicate, incompatible, or undeclared executable entries fail the applicable
inventory contract. Bundling an explicitly admitted extra plan is not intrinsically
wrong; letting an unexamined executable enter the claimed closed registry is.

 
*** Source-derived inventory and independent build choices

The required manifest is derived from the same admitted operation and role
sources as rendered actions, server transport and application preflight. It
names each executable plan's exact semantic digest and supported role,
features, protocol, source/projection version and compatible host runtime.
Derivation cannot start from a second manually maintained browser registry
whose members happen to agree today. A newly required Claim/Reassign plan
therefore changes the admitted build input even before any JavaScript exists.

| Inventory class | Required treatment |
|-----------------+--------------------|
| Required executable plans | Exactly matched to the admitted operation/role projection, with no missing, duplicate or mismatched entries. |
| Shared or deliberately inactive plans | Explicitly classified; they cannot be treated as active product capabilities or silently escape the effective executable/handler inventory. |
| Runtime/host effects | Enumerate physical handlers, event sources, transports, acquisition and supported completion/failure protocols for every reachable admitted effect. |
| Compiler, runtime and physical realization | Bind the implementations and options capable of changing emitted behavior, not merely friendly version labels. |
| Dynamically imported code and workers | Account for the transitive loaded resource set and the declared runtime loading/qualification contract. |

Source-owned semantic identity, exact projected payload identity, build
environment identity and emitted asset bytes identify distinct objects.
The manifest must not infer trusted source provenance from a filename or
self-advertised digest, and its graph must remain acyclic: the digest of an
output cannot be included in the very same unqualified bytes it digests.

*** A concrete generated-entrypoint construction

The normal build uses a Gesso-owned generated bootstrap source. It embeds or
imports the exact admitted manifest/plan payloads and invokes the canonical
runtime bootstrap. Application code supplies typed physical realization options;
it cannot replace the manifest-owned operation registry or plan resolver through
those options.

A concrete build sequence is:

1. Resolve the application definition once into the candidate semantic inputs and
   selected browser realization.
2. Derive the manifest and exact executable payloads from that construction.
3. Generate the bootstrap entrypoint and explicit imports for the admitted
   physical realization implementations.
4. Compile with the declared toolchain, dependency versions, options, and inputs.
5. Record the generated-input correspondence and digest the actual emitted assets.
6. Verify the staged manifest/receipt/asset set before publication.
7. Admit an immutable asset location set and bind it to the candidate assembly.

A low-level emitter accepting arbitrary JavaScript plus a copied manifest is not
equivalent to this construction. It may remain a testing or integration API with
a narrower guarantee.

 
The default builder must actually generate the entrypoint from the admitted
manifest and resolve its physical realization options through a constrained,
typed interface. A physical options value may select concrete DOM/HTMX
adapters and integration callbacks, but may not inject a second plan resolver,
rewrite admitted operation IDs, replace semantic transitions or bypass required
effect handlers. The options Var's identity, its resolved implementation,
compiler classpath and deployment profile participate in evidence invalidation.

The exact build result is tied to the *source-generated input* and the
compiler/toolchain actually invoked. A successfully staged JavaScript file
does not prove that the compiler preserved Gesso's intended semantics; that
remains a named fidelity/correspondence premise until stronger checking exists.
Likewise the existence of a generated entrypoint in source does not prove
the intended runtime bundle was emitted or later loaded.

There is no requirement for a magical parser that extracts all semantic plans
from arbitrary optimized JavaScript. Source-generation correspondence, compiler
fidelity under a named premise, and exact emitted-byte binding provide a concrete
argument. Stronger independently checked compiler/artifact correspondence can
replace the relevant premise when available. A runtime registry probe can add
conformance evidence, but a self-reported registry is not independent proof of
all code executed by the bundle.

 
A supported producer may expose an independently checked emitted-plan
inventory, but the method of obtaining it must be declared. It cannot be
satisfied by merely copying the expected plan digests into a receipt beside
unrelated bytes. If the compiler does not support a trustworthy registry
extraction, the build can instead retain its exact source-generation
witness and a scoped compiler-fidelity premise, with real-browser
startup/plan execution supplying additional behavioral evidence. Neither
method licenses a claim of universal equivalence for arbitrary optimized
JavaScript, third-party scripts or dynamically loaded unknown chunks.

*** Receipts bind provenance and bytes separately

A detached build receipt records the manifest identity, generated input/plan
identities, compiler/runtime/implementation closure, relevant build options, and
the exact digest/size/location of each emitted asset. Its evidentiary value depends
on provenance from the admitted build/checking boundary, not on the receipt's
own claims. It conveys no permission to perform a domain operation.

Verifying a digest establishes equality with recorded bytes under the digest
premise. It does not establish that those bytes implement the intended semantics.
Conversely, trusted compilation from the correct source does not establish that
the server later serves those same bytes. Both relationships belong in closure.

 
The receipt and build manifest have *different provenance*. A copied receipt
with matching expected labels cannot authenticate either the emitting
compiler or the served file. The receipt issuer must be the admitted
build/checking boundary or another independently qualified source, and the
checker must read the actual bytes being admitted at the relevant storage
boundary. Exact byte digest matching is a content-identity assertion under
the collision premise, not a proof of inclusion, runtime behavior or
permission to execute a protected domain operation.

If the selected output is more than one file, each member's digest, relative
location, dependency edge, load policy and serving identity contribute to
the retained asset-set evidence. Content/security headers, cross-origin
loads, service-worker caches and import maps can alter which code executes
even when the entrypoint file itself is correct; the selected physical
profile accounts for these paths or leaves their implications explicitly
unestablished.

The asset set includes dynamic chunks, workers, imported runtime libraries, and
other resources whose behavior affects the claim. Relevant CSS or configuration
that can suppress or redirect an affordance also has a declared dependency or
qualification role. Diagnostic-only sidecars retain their separate noninterference
contract from Part V; they do not become executable semantic inputs.

Build inputs include opaque physical implementation changes where their behavior
matters. Reusing the same named =current= toolchain/runtime label across changed
implementations cannot preserve evidence applicability. Deterministic compilation
is useful but not a prerequisite for naming actual emitted bytes: a receipt can
bind one actual output even when another valid build yields different bytes.

*** Publication and serving preserve the checked binding

Candidate builds use isolated staging locations. A failed build or rejected
candidate cannot overwrite assets still served by an admitted assembly. Atomic
replacement of one file is insufficient if readers can observe a new bundle with
an old receipt or a mixture of old and new chunks. Publish a verified immutable
asset set, then switch the admitted serving reference.

The concrete serving strategy must prevent or detect substitution between check
and use. Content-addressed/versioned immutable assets are a useful default. An
open immutable resource handle, qualified store, or equivalent serving contract
can also work. Reading a mutable file once at startup and trusting its path
forever is not exact serving correspondence.

A page generated under assembly A must reference assets bound to A even if
assembly B activates before the browser requests them. A mutable logical URL that
now serves B can break that relationship. Versioned URLs or a qualified
assembly-specific asset selection protocol close it. Cache, CDN, service-worker,
and old-client behavior follow the selected deployment/profile contract.

 
*** Atomic set activation and failure recovery

Staging one JavaScript file and separately writing its receipt with atomic
per-file renames is *not* atomic publication of the pair, much less of a
multi-file bundle. If the artifact is replaced but receipt publication then
fails, the failed candidate cannot be considered admitted even when a
subsequent reader notices the mismatch. More importantly, changing a mutable
live asset path may already have disturbed the previously served generation.
A valid end-state design stages a complete candidate set in isolation,
verifies it, and activates an immutable set reference atomically with the
serving-generation selection or provides an equivalently qualified mechanism.

The previous admitted generation must remain serveable until its references
and permitted old-client lifetimes have been retired. Candidate failure,
cancelled compilation or a partial publish does not overwrite or delete its
live assets. A publish pointer switch may be rolled back only under an
explicitly safe deployment/compatibility policy; restoring asset bytes after
clients have fetched the new set does not undo those clients' execution.

A successful build receipt establishes only the candidate artifact relation.
Activation additionally needs actual route/static-handler adoption and the
asset set available at the URLs generated for that assembly. A page rendered
under A is bound to A's immutable asset coordinates even if B becomes current
before the browser fetches them. The storage, CDN and cache policy must
either preserve that binding or detect a mismatched response before
accepting it. Same-name shared URLs are safe only with a qualified
generation-aware selection or compatibility contract.

The currentness check asks whether the assets intended for this admitted assembly
match its required build. It does not demand that every sleeping browser already
runs the newest deployment. Older continuations follow Part VI's compatibility
and recovery rules, including retained command resolution.

 
Browser plan compatibility is weaker than build/serve exact currentness:
an older client may legitimately continue or recover under Part VI even
while a new deployment must reject its stale build receipt. Conversely,
byte-equal current assets do not automatically make a retired execution
legal, confer principal authority, preserve a stale physical target or
resolve a submitted command. Both generation/host identity and exact
resource/command lifetimes remain necessary.

A build that adds a required manager Reassign control and plan to assembly
B cannot reuse A's browser bundle merely because the old Claim plan is
still present or both bundles advertise a compatible transport version.
An application that starts with B's semantic registry but serves A's
runtime has not closed its protected operations. It must refuse
activation or explicitly choose and admit a compatible, honestly
described lesser realization that still meets independent product
requirements.

Tests of startup/currentness use the same verification mechanism and actual
artifact path as production. Synthetic stamped files can test a narrow checker,
but cannot stand in for the real generated runtime in application acceptance.

 
*** Positive and adversarial artifact histories

Tests and deployment qualifications must connect the *real* source-generated
browser bundle to the admitted application. A unit test with arbitrary
JavaScript and a copied stamp has a narrower subject.

| History | Required disposition |
|---------+----------------------|
| The canonical application constructor derives Claim and Reassign plans, builds the generated CLJS bootstrap, verifies actual staged bytes and receipt, activates an immutable set, and a real browser loads it. | Distinct semantic-plan, builder, byte-identity, served-set and runtime adoption evidence are established at their respective boundaries. |
| R5.1 application B requires Reassign but the browser artifact and receipt still belong to A. | Reject B's startup/activation as stale even if the old Claim plan would have remained protocol-compatible. |
| An extra unregistered executable plan appears in a supposedly closed runtime bundle. | Reject or classify the extra entry under the declared inactive/shared contract; do not infer that untracked code is authorized. |
| A caller supplies arbitrary JavaScript and manually stamps it with the correct plan digests. | The low-level byte/receipt relation may be checkable, but the ordinary source-generated implementation claim remains unestablished. |
| A build updates the exact JavaScript bytes but leaves the previous receipt or tampers with its digest. | Fail byte/receipt currentness; a matching filename or nominal version is insufficient. |
| A generated entrypoint embeds the right plans while its declared physical realization Var points to a changed implementation. | Invalidate the affected build correspondence and rebuild/requalify the executable implementation dependencies. |
| The JavaScript entrypoint is current, but an old dynamically imported chunk or service-worker cache provides incompatible runtime behavior. | The qualified transitive resource/serving relation is unsatisfied; entrypoint digest equality cannot close it alone. |
| Candidate B's compilation fails before publication, while A is still serving. | Keep A's admitted asset set intact and available; reject B without damaging live A. |
| Candidate B replaces the shared JavaScript filename, then receipt publication fails. | Fail B; report the old generation's serving risk and repair it rather than claiming two atomic file moves made an atomic set. |
| A is rendered before B activates, and the browser fetches an unversioned URL that now serves B's incompatible bundle. | Prevent the cross-generation substitution through immutable coordinates or qualified generation-aware serving. |
| A current asset receipt matches locally, but the network server or CDN sends different bytes. | The local candidate check is not deployed serving evidence; reject or explicitly leave the stronger serving claim open. |
| The new B bundle is exact, but a sleeping A browser still owns a durable unknown Claim. | Apply the old-plan continuity/command resolver policy; do not relabel the historical command or force unsafe migration merely because B is current. |
| A unit checker passes on a fake stamped bundle, but the actual shipped browser cannot register or execute Claim. | The unit test remains valid for its narrow relation; real-browser positive acceptance and source-generation conformance fail. |
| A build's compiler or physical handler is outside a declared proof/qualification profile. | Record unsupported or open premises and refuse an unearned strong certificate; do not invent a compiler proof. |

These cases do not require every build to be bitwise reproducible. They
require that *the actual admitted bytes* and their required dependencies
are identified and correctly served with provenance sufficient for the
selected profile. The source-generated pathway, exact content check,
physical activation and real-browser behavior are complementary claims,
not substitute green flags.
