** Application explanation and semantic audit
:PROPERTIES:
:CUSTOM_ID: req-whole-application-semantic-audit-surface
:END:

The application exposes a structured, read-only semantic audit derived from its
actual admitted sources, construction products, and evidence. It supports review
of the correctness-relevant policy without treating a large implementation as
an undifferentiated body of code.

The audit is not a second editable policy registry. Business-rule prose, operation
cards, diagrams, and evidence summaries are projections of the same admitted
subject. Prose explains meaning and rationale; it does not gain mechanical force
by appearing beside a checked predicate.

 
*** Inspection scope and source lineage are part of the artifact

An audit has an identified *subject*: the admitted application generation,
original semantic/source versions, selected operation catalog, assembled
realization/deployment profile, checker versions and evidence dependencies.
Views are derived from those same objects, not from a second registry,
a stale report-shaped map or a source scan that merely found familiar names.
A current, successful assembly report can authorize *describing that assembly*;
it is not itself authorization to execute operations or a proof that an
uninspected model callback implements its descriptive policy.

The root view states, at minimum, which declarations and real sources were
inspected, the admission/checking mechanism, which evidence is only
source-relative, the completeness of each inventory, and the claims not
established. Counts always have an inventory qualifier:

| Count or scope | Permitted interpretation |
|----------------+--------------------------|
| Declared operations and relational rules | Exact members of the selected admitted source catalog, not proof that no other business rules exist. |
| Checked finite state/operation/rule instances | Exercise over the stated initializers, principals, arguments and reachable-state bounds, not all production cases. |
| Observed routes, writers and browser artifacts | Physical observations under the named host/serving scope, not all unobserved entrypoints or future replacements. |
| Open declared structural edges | Failed or unmet edges within the known closed subgraph, not an inventory of human intent. |
| Opaque model callbacks and external effects | Preserved named premises and unsurveyed implementation surface; unknown never means zero. |

An omitted semantic rule that never entered the declared source cannot be
proven absent by successfully checking its smaller catalog. The
source-owned rule catalog, application/operation cards, proof dependencies
and runtime observations therefore retain both their positive *included*
inventory and the relevant completeness/opaque qualifications.

*** Required audit views

| View | Information and required limits |
|------+---------------------------------|
| Business-rule catalog | Stable rule identity, meaning/rationale, formal or opaque contract, source, affected operations, authority, enforcement, and actual evidence. |
| Operation card | Typed inputs, principal/authority dependencies, guards, transition/frame, outcomes, command repetition/disclosure, effects, and recovery. |
| Authorization/disclosure | Current authority sources and policies for invocation, reads, subscription, and prior-result resolution. |
| Domain lifecycle | Actual admitted states and transition relation, generated from semantic definitions rather than guessed from route names. |
| Realization path | Exposed surfaces, plans, assets, routes, actual handlers/executors, providers, acquisition/installation, and serving bindings. |
| Rule/evidence dependencies | Claims affected by a changed rule, operation, implementation, backend profile, or accepted premise. |
| Writer/entrypoint coverage | Declared, installed, observed, classified, excluded, and still-unestablished paths at their actual scope. |
| Opaque-premise report | Each retained premise, its owner/reason, applicability, available tests, and dependent claims. |
| Assurance and exercise | Exact finite bounds, rule/operation/outcome exercise, conditional induction, runtime gates, conformance results, and gaps. |
| Recovery/continuity | Owners and triggers for unknown commands, failed adoption, missed publication, subscription gaps, and version incompatibility. |

A domain lifecycle view uses the operation model's actual enum. It must not rename
HumanHelp's states to superficially similar completed/cancelled labels or infer
terminality from a UI caption.

 
*** Business rules, operations and actual authority

The rule catalog is a normative future capability whenever the application
expresses relevant semantics. For each named rule it records the
source-owned identity, exact proposition or relational terms (when
machine-readable), domain meaning and rationale, affected operations,
authoritative owner, required enforcement site, source-to-implementation
correspondence, and independent evidence or retained premise. A rule that
has a formally stated predicate but no demonstrated XTDB transaction guard
remains a source declaration with an *unestablished physical conformance*
edge, not a production-proved invariant.

For example, HumanHelp Claim's active Membership condition must identify
that the authenticated helper's current Membership in the Request's
Organization is checked at authoritative Claim incorporation. The audit
must distinguish that declared obligation from evidence about the
actual guarded transaction, actor/Request/Organization scope and
interference. A matching rule name, handler name or passing finite
fixture cannot establish current live Membership protection.

Operation cards preserve an executable contract rather than a marketing
summary: typed Request and principal/argument sources, authority,
guards/prestate, transition and frame, command identity and duplicate
handling, authoritative outcomes and disclosure, provider/effect
requirements, physical route/plan/asset, and the permitted acquisition
and recovery paths. A current participant's authorization is determined
by the trusted model and observation context, not by reading a previously
generated audit card. Rendering an eligible or unavailable button does
not change what Claim is allowed to do.

The authorization/disclosure view distinguishes at least *invocation*,
*current Request read*, *subscription/Live interest*, *prior command
result disclosure*, and manager Reassign authority. Sharing a role label
does not establish equivalent permissions. Current user policy and
tenant/Organization context are dynamic model facts, even when the
application has structurally established the existence of their
trusted enforcement bindings.

Where model states and transitions are declared, the lifecycle view
reports their exact internal identifiers and transition relation.
It cannot infer an unexpressed `:completed` or `:cancelled` state
from a UI label, or mark a terminal state because a component hides
its actions. A model exposing no inspectable state relation yields
an explicit unknown/opaque lifecycle view, not an invented diagram.

*** Unknown inventory is not an empty inventory

If a model adapter exposes only a public operation name, the audit cannot infer
its internal predicates or atomic dependency protection. It reports those bodies
as not inspected with their explicit conformance premise. An empty business-rule
list would misleadingly suggest there were no relevant rules.

The same distinction applies to writers, side effects, publication, and policy
branches. Zero unresolved declared edges is not proof of complete human intent
or absence of undiscovered behavior in arbitrary host code.

 
The audit must distinguish three situations that are often mistaken for
one another: (a) a *known complete* catalog with zero entries of a
particular class; (b) a partial catalog containing some inspected
declarations; and (c) an unavailable source whose cardinality is
unknown. A zero count is valid for (a) only within its explicit
closure scope. An empty vector shown alongside =:count :unknown=
in (c) means *no enumerated rules were available to this projection*,
not that the actual application has no rules.

Opaque boundaries remain explicit when registered model functions
can branch on Membership, perform unreported reads, mutate protected
state or publish topics outside the admitted declarative surface.
Where the supported semantic language has precise relational or
state-transition terms, the same audit can enrich those rule cards
with meaningful checked facts. It must not infer that arbitrary
adjacent Clojure was consequently proved equivalent.

Enriching the application with source-owned relational rules or checked transition
terms adds concrete audit coverage. It does not retroactively establish that
uninspected callbacks contain no extra policy. The view distinguishes complete
coverage of a supported construction subset from registered opaque boundaries
and unexamined external behavior.

*** Declared Live overlap is not a transaction dependency proof

Part IV's guard and footprint contracts determine authoritative
dependency meaning; shared Live topics establish presentation impact only.

 
A *dependency* view has typed edges and provenance. A rule-to-operation
edge may be source-declared, derived from the admitted transition
relation, or observed from a specific physical guard. A Live topic
overlap is instead a source-relative *presentation impact* edge.
Operations that touch different protected records can publish
one shared board topic, while two operations that share one guarded
RequestAssignment dependency can legitimately publish different
topics. Reclassifying either relationship as complete transactional
conflict information would mislead application assurance and
incremental invalidation.

For a given changed predicate, model operation, opaque callback,
provider, route, generated plan, artifact or host deployment premise,
the audit can identify *known downstream dependent claims* and
which admission/checker/production evidence must be revisited.
A missing source-ownership edge or an opaque implementation with
unknown side effects creates an open impact boundary; the tool
cannot promise that the listed dependents are complete.
Reusing evidence requires matching original subject, source and
implementation versions, proof/certificate premises, physical
profile and checker semantics, not just equal operation IDs.

*** Explain one operation end to end

A useful explanation of Claim identifies:

1. the exact semantic source, rule dependencies, and operation interface;
2. exposed controls and their selected realization alternatives;
3. projected roles, executable identities, physical handlers, and asset bindings;
4. route/input correspondence and the actual installed executor;
5. provider contracts, invocation gates, and current authoritative guard obligations;
6. model-to-presentation outcome mapping, including repetition and unknown;
7. acquisition, propagation, installation, and recovery paths;
8. assembly/installation identity, policy, evidence applicability, retained premises,
   and unresolved or excluded claims.

The output may show a local issued-handler binding as established while leaving
backend transition refinement conditional on its qualified provider. It may show
finite rule exercise without claiming that every production predicate branch was
executed. Those distinctions are useful information, not deficiencies to hide
behind a single green label.

 
*** Assurance classifications are proposition-specific

A rule's *declared guard binding*, an abstract invariant,
a finite exploration result, conditional induction, the
physical XTDB realization of that guard, the deployed
writer-coverage boundary, and real browser adoption are
different claims. Each report row names its proposition,
source/evidence class, checking mechanism, exact scope,
assumptions, dependencies, proof or observation status,
open contradictions and validity lifetime.

In particular, `assembly-verified` can describe correct
source-owned route/plan/provider structure, while a
model-implementation-conformance proposition remains
`trusted` under an explicitly named premise. A finite
model checking every selected principal/argument pair
does not prove those pairs cover all humans or requests.
A conditional inductive argument does not automatically
establish physical XTDB refinement, all-writer coverage,
kernel soundness or no-gap SSE delivery. A bounded
physical observation cannot be promoted to universal
deployment correctness.

The explanatory surface retains unsupported, inconclusive,
contradicted, open and established evidence at their
individual subjects. Contradiction to one physical
realization cannot be hidden by a successful structural
check of another. Nor can a checked rule be advertised
as exercised when the finite exploration visited no
state in which its source predicate applied.

*** Inspection does not execute or authorize

Explanation reads admitted results and immutable/redacted trace values. It does
not invoke operation callbacks, submit transactions, rerun model builders,
mutate runtime registries, or repair missing edges. Expensive fresh checking is
an explicit separate action whose result has its own identity and scope.

No diagnostic output needs to expose live executor handles, credentials,
principal-sensitive data, or unrestricted command arguments. Redaction reports
what is unavailable rather than fabricating a replacement explanation. Internal
repair detail and client-facing errors can have different disclosure policies.

 
The inspection API must not convert an arbitrary supplied report into
freshly admitted truth. The normal public path re-derives or verifies the
current application assembly and its source dependencies before
producing an audit. A lower-level projection accepting an already
checked report has a strict caller precondition; it is not an
authenticated report verifier in isolation. A private issued executor,
proof/checker handle or live DOM/Request object may be inspected only
through its qualified boundary and is never copied into public
audit output.

A source location may be important for repair but still sensitive.
The selected diagnostic consumer and privilege determine which
source paths, rule literals, principal scopes, commands, tokens
and observations may be disclosed. A redacted field is explicitly
marked redacted/unavailable and cannot be used as evidence
that the hidden dependency is absent. Deterministic view
ordering, stable semantic identity and bounded generation
make comparison and review practical; these are UX
properties, not additional execution authority.

The tool can suggest which *source owner* needs correction,
but it must not automatically rewrite a rule, select a
near-matching operation for dispatch, change a provider
binding, or use a report as a new command. A separate
source correction and admission is required to change
the application's meaning. Sections 07.13–07.14 own
structured diagnostics and full acceptance qualification.

The explanatory surface can show an incomplete candidate's rejected/open
obligations without making that candidate executable. A stale sidecar or trace
mapping must not explain a different executable plan by matching similar names;
Part V's exact correspondence rules apply.

 
*** Positive and adversarial semantic-audit histories

Acceptance exercises the audit through its source-owned
application explanation path. It distinguishes a view of
an admitted candidate from a deployed or behaviorally
accepted system; tests of individual projections have
a correspondingly narrower claim.

| History | Required audit disposition |
|---------+----------------------------|
| A source-owned Claim rule explicitly requires active helper Membership at commit and is connected to an admitted model transition and checked implementation evidence. | Show its exact rule, source, affected Claim, current guard/effect scope, mechanism, relevant assumptions and checked evidence without inventing physical proof. |
| A Claim operation is exposed through a browser plan, HTTP POST, issued executor, typed provider and authorized reread. | Produce an end-to-end operation card with distinct source owners, actual installed/candidate identities, command outcomes and recovery; preserve each edge's assurance class. |
| A legacy model adapter exports only a public Claim name and opaque callback. | Report business rules, authorization predicates, transaction dependencies and lifecycle transitions as not inspected or unknown; an empty returned list is not evidence of no rules. |
| A checked finite relational rule has never matched a source entity in any explored state. | Report that bounded vacuity/exercise fact rather than claiming the business predicate was substantively exercised. |
| An induction proof conditionally preserves an abstract single-owner invariant but host writer inventory is incomplete. | Keep abstract proof evidence and open physical writer/XTDB correspondence as separate propositions. |
| Claim and Cancel both publish =:request/change=, but only their Live topics overlap in the observed source. | Display declared presentation impact; do not infer transaction conflict, common guarded fields or business-rule dependencies. |
| A raw scheduled writer modifies RequestAssignment outside the declared operation registry. | Retain unclassified/unknown physical writer coverage; a closed operation-ID set cannot show complete effects. |
| The selected manager Reassign operation has correct semantic structure but is absent from the installed controls. | Distinguish an available declaration from actual exposure; product completeness cannot be inferred from a valid operation card. |
| An application reports zero declared structural obligations while its opaque model code has uninspected authorization branches. | Show closed declared graph and explicitly unknown model-policy coverage simultaneously. |
| A report-shaped caller map asserts a fully checked rule catalog without a fresh trusted source/assembly. | Refuse to promote copied summary data to current admission, certification or operation authority. |
| A stale browser source map or artifact sidecar names the right operation but belongs to another generated bundle. | Reject/qualify artifact-to-source mapping before displaying it as current provenance; matching names are insufficient. |
| A candidate changes a provider Var, guarded callback or source rule but reuses last generation's green coverage report. | Invalidate affected evidence and re-derive dependent audit views from actual new source/admission. |
| A command has an authenticated historical incorporation while a later Reassign changes the current card. | Preserve independent historical-command and current-state propositions; neither the audit nor the card rewrites the earlier outcome. |
| A limited-privilege caller requests an audit containing private principal or command information. | Disclose only the allowed redacted view, retaining its scope/unknown markers; absence after redaction is not evidence. |
| A UI repair agent sees a nearby valid operation name or provider adapter in the report. | Offer a source-local suggestion only; no automatic semantic substitution, protected invocation or report-to-capability promotion. |
| A real HumanHelp implementation passes structural proof/report checks but cannot execute an eligible Claim or manager Reassign. | Report the established structural evidence but leave independent positive product acceptance failed or open; no universal green badge. |

These cases require concrete original sources and honest
evidence for the selected application and audit level,
not an independently maintained idealized rule document.
Part VIII's real browser product tests and Parts IX–X's
formal/physical proofs can *add* evidence to the
same source-bound audit when justified; a copied
or self-issued report cannot substitute for them.
