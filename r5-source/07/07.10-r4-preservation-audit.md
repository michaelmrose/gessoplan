## R4 obligations preserved

1. **Native Biff 2 lifecycle ownership.** Stable qualified module
   identifiers, dependencies and concrete native start/stop
   responsibilities replace preview-era arbitrary shared vectors
   of stop callbacks. IDs alone do not establish callable or
   resource ownership; this revision preserves source/implementation
   provenance and shared resource retirement.
2. **Mandatory Gesso managed startup.** The normal supported
   application-start function supplies the canonical source-owned
   ApplicationAssembly, current browser artifact, selected assurance
   policy and guarded HTML/operation path. The application author
   does not manually remember a preflight module ID or use separate
   checked-dev and unchecked-production entrypoints.
3. **Correct ordering is a partial order over actual effects.**
   R4 explicitly required preflight to finish before normal Aleph
   application serving, not to be first among every config and
   private XTDB initializer. The refined section makes Biff's
   *all init before start* order explicit: first in the start list
   does not authorize side effects already performed by init.
   Listener, scheduled worker, writer and other protected effect
   exposure must be privately fenced until all required
   admission/installation gates are satisfied.
4. **Reject malformed candidates before application service.**
   A stale artifact, missing route/capability or wrong handler
   cannot become a normally usable application whose first
   user request merely returns a preflight diagnostic.
   Separately admitted health/unavailable protocol is permitted
   only when it cannot expose protected application behavior.
5. **Actual serving adoption is distinct from local wiring.**
   R4 required the handler actually invoked by the server to
   pass through the checked boundary. Local Biff system-map
   wrapper installation, observer callbacks, issued handler
   identity and actual network serving adoption are different
   propositions. Later handler replacement, server ignoring
   `:biff.ring/handler` and raw pre-rendered HTML remain
   explicit unestablished or separately qualified paths.
6. **Immutable generation and coherent hot reload.** Construct
   and check B before activating it; never expose B routes with
   A browser assets, providers or reports. Use compare-and-activate
   or equivalent to prevent out-of-order candidates. Requests
   retain their exact issued generation and cannot blindly
   consult changed global Vars.
7. **Asynchronous lifetime and old-client obligations.**
   Deferred responses, streams, workers and old browser pages
   may outlive one Ring handler return or the current generation.
   They require resource ownership, retained guard/asset
   bindings, safe revocation and independently authorized
   command reconciliation. Current model authorization remains
   a dynamic effect check.
8. **Module-owned cleanup and primary-failure preservation.**
   Failed private startup cleans or accounts for acquired
   resources even when the module failed before returning a
   normal result. Cleanup errors remain secondary to the
   primary failure; failed cleanup cannot grant serving
   rights or erase already committed domain effects.
9. **No false all-deployment claim.** Correct Biff module
   ordering cannot establish that remote/router nodes, an
   alternate server or real production traffic adopted the
   checked installation. A single-node and multi-node
   application have the same semantic admission rules,
   with additional deployment/traffic/epoch evidence.
10. **Nonvacuous acceptance.** Eighteen positive/adversarial
    histories include successful real serving and Claim,
    stale artifact, forged canonical module, early initializer
    exposure, raw writer, wrong captured handler, hot
    replacement, asynchronous A/B lifetime, mixed assets,
    racing reloads, failed candidate/invalid old fallback,
    cached old client, partial socket acquisition, cleanup
    failure, uncertain command, raw HTML bypass and a valid
    post-admission user workflow.

The older R4 schematic `gesso.application/start!` and
`:biff.core/id` module examples are retained as behavioral
requirements, not asserted to be currently shipped
public APIs. The preferred R5 separation between private
prepare/install/activate and externally observable serving
is maintained.

## R5 strengths preserved and sharpened

- Native lifecycle and operation checking share canonical source
  ownership without requiring one monolithic function.
- Module identities are checked against the actual selected
  implementations and provider/resource owners.
- A real early-effect safety fence, not a sorted list, governs
  Biff init-time side effects and listener availability.
- Preparation, physical installation, activation, deployment
  adoption and observed runtime enforcement have distinct
  evidence subjects.
- Deferred completion retains request-bound generation and
  guard, while durable work has its own lifetime/transfer.
- Coherent compare-and-activate and immutable asset references
  prevent partial A/B release and late stale candidate overwrite.
- Failures preserve primary cause, partial resources, cleanup
  errors and separately owned command/publication debt.
- Current security/policy invalidation revokes future effect
  permissions even when an old generation is still physically
  present.
- Eighteen real positive/adversarial histories make these
  rules falsifiable without counting reject-all as acceptance.

## Actual Gesso v1622 source correspondence and limitations

- `src/gesso/live/application_preflight.clj` exports
  `application-handler-module` and
  `start-biff-application!`. The canonical module
  is a Biff 2 `:biff.core/start` entry, and the
  start wrapper expects a current ApplicationAssembly,
  the actual canonical module exactly once in the
  supplied modules Var, and that module ID first
  in the start order.
- `src/gesso/live/application_preflight/biff.clj`
  implements the native module and startup. Biff
  executes all `:biff.core/init` entries before
  start ordering. Installation requires a current
  assembly and callable `:biff.ring/handler`,
  wraps the handler with the canonical Gesso HTML
  guard, and removes the temporary assembly
  startup system key. Canonical module identity is
  checked using its start function identity,
  not just the `:biff.core/id` keyword.
- The current canonical wrapper rechecks the
  ApplicationAssembly for each `gesso.http/html-response`
  rendered response on its wrapped synchronous path.
  Direct `biff.core/start`, a later replacement of the
  handler, an alternate server ignoring that key,
  raw pre-serialized HTML and deferred rendering
  outside its dynamic guard remain explicit escapes.
  The current code does not implement a general
  versioned private-install/atomic-activation
  coordinator, distributed deployment fencing or
  full resource-retirement protocol.
- `src/gesso/live/application_preflight/assurance.clj`
  represents canonical Biff HTML enforcement as
  available under that *specific* startup boundary
  and keeps external serving adoption as an
  unestablished premise; it publishes warnings for
  optional static Hiccup sample completeness rather
  than misreporting dynamic enumeration.
- `src/gesso/live/application_preflight/relational_application.clj`
  offers an opt-in source-relative model admission
  before delegating to the *same* canonical Biff
  lifecycle; it does not create a second production
  application entrypoint authority.
- Relevant source tests:
  `test/gesso/live/application_preflight/biff_test.clj`
  checks module identity, ordering, wrapped HTML
  boundary and direct Biff delegation using a stub;
  `test/gesso/live/application_preflight/lifecycle_integration_test.clj`
  exercises real Biff start/module installation,
  malformed-affordance blocking and observed local
  handler installation. Those tests do not prove
  an actual Aleph production server or deployed
  traffic always adopts the checked handler.
  They were read as source; no fresh JVM,
  XTDB, Chromium or live-service tests were run.
