* Part VII — Whole-application construction
:PROPERTIES:
:CUSTOM_ID: part-07-whole-application-construction
:PART_REVISION: 07-20261108
:END:

This part specifies how one source-owned application definition becomes an
admitted construction and an actual serving application. It joins executable
Choreo projections, trusted model operations, Clojure/ClojureScript handlers,
server routes, generated browser assets, rendered controls, Live interests,
authoritative acquisition, recovery, and the physical lifecycle. Parts I–VI
define the meaning and ownership of those components; Part VII establishes
that the required *connecting edges* are present and are enforced in the
realization that actually runs. Parts IX–X provide the stronger proof and
implementation-correspondence arguments and preserve their evidence scope.

Gesso applications retain ordinary Clojure, ClojureScript, server rendering,
HTMX, and application-specific effects. The framework does not require all
business logic to be written in a formal language or every local operation to
use Choreo. Instead, construction identifies the interfaces, effects,
producers, consumers, runtime dependencies, trusted premises, and observable
boundaries on which each selected guarantee relies. A sound declaration of
an opaque effect remains a named contract or assumption until its relevant
implementation correspondence is established; calling it application code
does not make its effects disappear.

Examples use illustrative operation and assembly names. A valid-looking
inspection map, plan digest, source label or success report does not issue a
runtime permission or trusted transaction credential. Present execution
conditions, including the authenticated actor, current authorization, model
facts, resource incarnation and installation permit, are checked at their
proper runtime/model boundaries rather than inferred from construction.

** Whole-application realization and preflight closure
:PROPERTIES:
:CUSTOM_ID: req-whole-application-closure
:END:

A valid choreography, model transaction, compiled browser plan or Ring route
can be correct in isolation while the combined application is broken. A
rendered Claim button may not emit its declared operation; its shipped plan
may be absent; a correct browser send may reach a different physical route;
the trusted route may lack its required execution provider; the command may
commit while no permitted authoritative acquisition or repair can establish
the resulting display. Each local component can pass its own tests.

*Whole-application closure* requires every effect and observation edge needed
by the selected application construction and assurance contract to have a
compatible, source-owned realization. This checks the composition of the
actual submitted application, not merely whether several independently
constructed registries look plausible. The supported construction is an
inspectable semantic/physical artifact with an identity, selected capabilities,
trusted premises, supported host/deployment profiles, and specific closure
and enforcement obligations.

Closure is *not* a second choreography. Choreo states which distributed
behaviors are admitted; projection derives executable role-local behavior;
application assembly establishes that each required concrete/browser/server
realization is supplied. A route cannot legalize an invalid Choreo trajectory,
and a valid plan cannot manufacture a missing route, model operation,
subscription or generated asset.

The required edges depend on the kind of work:

| Admitted application behavior | Realization that must be closed | Edges that are not invented |
|-------------------------------+---------------------------------+-----------------------------|
| Managed browser command such as Request Claim | Rendered affordance, projected plan, loaded browser/HTMX host, issued send, trusted method/route, guarded model operation, qualified outcome, acquisition and adopted presentation or declared recovery. | A fictitious global exact-once transport guarantee or a second runtime semantic interpreter. |
| Server-owned operation or background task | Registered event/worker, trusted operation and providers, applicable publication, durable intent/retry and readback or error policy under its own owner. | A browser plan and button for a task with no browser role. |
| Ordinary read-only HTMX or search route | Actual HTTP/read source, current disclosure authorization, declared query/coverage, rendered response/target and relevant Live or cache obligations. | A Choreo command solely because HTML is swapped. |
| Local draft/filter/focus interaction | Current local state owner, presentation and continuity permissions, effective physical effects, expiry and privacy boundaries. | A database transaction solely because the user types or changes a local filter. |
| Explicit ordinary mutating endpoint | Its declared model writer, authenticated input and current transaction guard, output/disclosure, invalidation and effect coverage. | Automatic exemption from invariants because the endpoint has no Choreo annotation. |

No semantic metadata is required on irrelevant static assets. However, a
managed route or physical writer whose effects can invalidate an invariant
must belong to that invariant's coverage argument or remain an explicitly
trusted and bounded environment premise. The application cannot claim
whole-writer safety while a reachable unaccounted raw route changes the
same RequestAssignment state behind its guarded Claim.

*** Three application claims remain independent

The authoritative [[#req-application-assurance-claims][Part I application-assurance claims]]
retain distinct evidence subjects:

| Claim | Required positive evidence | What the claim does not establish |
|-------+----------------------------+-----------------------------------|
| Declared structural closure | Every required operation, route, source, artifact, capability, observation, effect and recovery edge in the *declared application scope* has a compatible current binding; unsupported requirements are rejected or retain an explicitly allowed weaker profile. | That omitted business capabilities were intended or implemented; that arbitrary Clojure render states were statically enumerated. |
| Actual production enforcement | Real installed handler/startup paths, issued transport and renderer/HTML/HTMX boundaries perform the required checks *before* their protected send, trusted operation or response; the served/loaded asset and declared host are the ones checked. | The correctness of all future authority facts or an unobserved deployment merely because an assembly report passed. |
| Independent behavioral completeness | Eligible users can perform the required product operations using actual controls, trusted model effects, permitted acquisitions and physically installed results; nearby adverse and recovery cases also exercise those paths. | A universal proof of every execution from one positive browser example, or success when the relevant capability was intentionally disabled. |

The three claims can be simultaneously true, false or not yet established
in different combinations. A closed application can omit a required manager
Reassign control. Production may bypass its checked response wrapper even
though the assembly was valid. A test may manufacture C42 by calling a
helper directly even when the real Claim control emits no command. These
are distinct failures and cannot be flattened into one =:verified?= flag.

Application construction always requires its selected mandatory structural
and real admission boundaries. Stronger proofs and finite-model campaigns
are selected by an explicit assurance policy, not silently necessary for
every ordinary use. Omitting an optional theorem cannot disable required
route, actor, artifact, source or physical checks. Selecting an ambitious
proof does not make a disconnected checker an enforcing gate; only an
actual installed, correctly scoped boundary supplies enforcement.

*** Ownership of whole-Part-VII cross-section obligations

The Claim, Live and XTDB examples recur because they cross independently
checked boundaries, not because each section declares another model,
registry or policy. These sections own different *relations*:

| Section(s) | Primary whole-application obligation |
|------------+--------------------------------------|
| 07.01–07.03 | Application scope, source-owned assembly, typed closure and evidence graph. |
| 07.04 | Assurance policy, operation/exercise and physical writer coverage. |
| 07.05–07.07 | Actual trusted route/executor, built and served browser assets, effective rendered HTML/HTMX. |
| 07.08–07.09 | Command-specific settlement, Live/progression and required recovery handling. |
| 07.10–07.11 | Installed Biff lifecycle, actual serving adoption and physical fault-injection evidence. |
| 07.12–07.13 | Source-owned semantic audit, non-authoritative diagnostics and source-local repair. |
| 07.14 | Independent positive product acceptance and backend/evidence change qualification. |
| 07.15 | Qualified end-state security invariant and trusted authority boundary. |

Part I owns the application-assurance claims, Parts II–III model/Choreo
semantics, Part IV authoritative guarded transactions and command truth,
Parts V–VI browser realization and physical continuation. Part VIII owns
HumanHelp positive user acceptance; Parts IX–XII own stronger proof,
physical refinement, multi-node deployment and release obligations.
Part VII does not create duplicate semantic or proof authorities.

Complete *declared* operation coverage, independent promised product
capabilities and actual protected writer/deployment completeness are
three different inventories. The absence of an unknown raw writer
cannot be proved by an empty declared registry; a selected weaker
assurance profile cannot silently delete a known protected effect
or manager Reassign promised by the independent product profile.

*** Coverage follows effects, not the presence of Choreo metadata

Coverage is relative to the properties, security and product claims made.
The assembly identifies the admitted ingress, egress and state-changing
effects through actual HTTP routes, model functions, background work,
queues, scheduled tasks, administration, imports, initialization,
migrations, Live publication, external systems and browser/local writers
that may affect those claims.

An ordinary search endpoint can be the declared current authoritative
acquisition for a board without being a command choreography. A preference
update can use a simple guarded model operation. An explicitly raw HTMX
endpoint may remain legitimate under its own complete authorization and
effects contract. None obtains a silent right to bypass a selected
whole-application invariant because it lacks =:choreo/op= metadata.

A sound assembly represents *known writers*, their model-affecting
footprints, operation and route identities, required providers, publication
and observation obligations, and any explicitly scoped external writers.
Declared coverage is not a proof that a dynamically loaded plugin,
unobserved scheduler, hidden route or unbounded external system is absent.
Where discovery is incomplete, the report must distinguish an *unknown*
inventory from an actually enumerated empty one. A stronger closed-world
claim may require controlled registration, an enforced runtime boundary,
independent deployment inspection or an explicitly qualified assumption.

The closure graph has positive obligations for commands that succeed:
trusted incorporation must have the declared settlement, affected-scope,
publication, acquisition, adoption or repair path. Live interest without
a permitted first acquisition cannot establish a current initial view;
Live invalidation without a supported registration-gap recovery cannot
promise complete continuity. A command path that is perfectly guarded yet
always lacks its provider, or an entire screen that can never adopt its
observation, is not a realized product capability.

*** Construction-time knowledge and current-world authority

The finished assembly validates every requirement whose meaning and
inputs are available at construction, build, preflight or installation.
For example, it can check a declared missing plan, absent trusted route,
incompatible method/template, unsupplied required provider, stale browser
artifact/receipt, ambiguous physical realization, uncovered output,
unregistered source or undeclared recovery branch without waiting for a
real user to encounter the defect.

Some properties cannot be decided when the application is assembled:
the eventual Claim winner, the current principal, RequestAssignment
eligibility at transaction time, the outcome of an uncertain send,
the arrival of an SSE advisory, or the physical existence of a target
after another execution supersedes it. Each belongs to its current
trusted or physical admission boundary. A dynamic condition is acceptable
only where a specified enforcement and recovery/rejection path handles
it; it is not permission to replace a protected action with raw HTMX.

A production path is considered enforced only while the checked
construction is still the one being used. The checked callable must
be the installed callable, the verified asset must be served/loaded,
and the actual response must pass the required pre-serialization
or protected physical gate. Rebuild, handler replacement, route
override, alternate response encoding, stale service worker and
third-party extension paths must be closed by the qualified deployment
or remain named unsupported/assumed profiles. Successful compilation
or a copy of the expected report is not proof of these installed facts.

An application with arbitrary Clojure rendering cannot claim that a
finite catalog of sample Hiccup values enumerates every future
conditional control. It can still admit a current route/operation
backbone and enforce the required Choreo/physical request check
at every *actual canonical render*. Other response producers
need their own guard, an enforced shared serving boundary or
a weaker explicitly scoped claim. The absence of an observed
unauthorized control in a small snapshot is not completeness evidence.

*** Assurance vocabulary describes the checked proposition

The report retains what was checked, for whom, where, under which
version/coverage and what remains conditional. Useful distinctions
include:

| Evidence state | Interpretation |
|----------------+----------------|
| =preflight-closed= or =assembly-verified= | A specified declarative graph/construction was checked for its listed obligations at an identified current assembly and artifact identity. |
| =production-enforced= | Evidence ties the actual installed handler, physical effect, route or output boundary to the selected required check in the stated profile. |
| =runtime/model-enforced= | Present authentication, authorization and guarded model transitions are checked by their trusted current sources, not by a browser assertion. |
| =behaviorally-demonstrated= | An eligible end-to-end product case exercised real user, backend, transport and presentation paths within the stated test/environment limits. |
| =formally-proved= or =finite-checked= | Only the precisely defined theorem or finite model subject and its assumptions are discharged; neither term is a synonym for deployment correctness. |
| =inconclusive=, =unsupported= or =open= | A required premise is not established, the selected realization is unsupported or more evidence is needed; none is silently rewritten as success. |
| =contradicted= (evidence) | A grounded observation contradicts the exact proposition; it is not automatically a rejected domain command. |
| =rejected= (admission) | The candidate or invocation is blocked at its applicable construction/enforcement gate; distinct from Part IV's authoritative =:rejected= command outcome. |

For instance, one application report may state that Choreo semantics
are proved for a named finite/symbolic subject, the browser artifact
correspondence is assembly-verified, the authenticated principal
is runtime-enforced, and actual HTMX behavior is covered by tested
host assumptions. It must not summarize those subjects as a single
unqualified "verified Gesso application." A diagnostic label,
digest or report has no power to authorize a business transition.

*** R4 preservation: broken compositions and positive controls

The following adjacent histories describe eligibility *and*
the failure mechanism. They are not merely tests that all requests
can be rejected:

| Eligible application history | Broken composition or adverse history | Required construction/enforcement conclusion |
|------------------------------+---------------------------------------+---------------------------------------------|
| A rendered authorized Request Claim control has a bound plan, shipped current runtime and trusted POST route. | The view emits the same POST without its managed operation identity, or the plan is absent. | Fail before protected send/HTML delivery under the relevant supported boundary; do not silently downgrade. |
| The current generated browser asset and receipt match the installed assembly and selected host profile. | A stale browser bundle, alternate script entrypoint or service worker supplies an incompatible plan after preflight. | Construction/build or actual serving/currentness gate rejects the stale realization. |
| A guarded Claim route has the required authenticated principal, clock/transaction provider and model-owned operation. | A missing =:biff.fx/now= or otherwise required execution provider becomes apparent only on click despite a knowable missing binding. | Reject the missing declared capability early; runtime still checks genuinely dynamic provider validity. |
| A qualified C42 incorporation produces covered publication/acquisition and physically adopted card or honest repair. | The command commits, but no permissible authoritative acquisition or installation path exists. | Reject the structurally missing continuation or declare an explicit recovery/blocked path; never fabricate adoption. |
| An initialized Live interest has a permitted baseline and reconnect/interest-fence recovery. | A board subscribes only to future invalidations but has no initial knowledge or permitted read. | Do not claim initial/current Live agreement; close the initial acquisition or expose the weaker contract. |
| A canonical guarded Biff/HTML path validates the actual rendered control before serialization. | A later handler replacement or hand-built serialized Ring response bypasses that guard while an app claims universal response coverage. | Actual installation/served-route enforcement must cover the alternate path or explicitly narrow the guarantee. |
| An ordinary read/search HTMX endpoint is correctly authorized and responds as an ordinary route. | The same raw route mutates protected RequestAssignment state outside the claimed writer inventory. | Preserve ordinary HTMX as a supported mode; account for its real write effects and transaction guard. |
| A manager uses an eligible real Reassign control; another helper's competing Claim is rejected at the trusted model boundary. | Tests build a coherent shadow registry or submit synthetic commands although the production Reassign button is absent. | Distinguish production assembly from test surrogates and require independent positive product acceptance. |
| The assembly accounts for named background, scheduled, migration and administration writers affecting Request state. | A known external writer is omitted so a formally checked operation invariant ignores its reachable transitions. | State explicit source coverage, trusted external contract or an honest weaker claim; do not hide the writer. |
| An application enables stronger finite/proof assurance with its own checked subject and runtime gates intact. | The checker is not connected to the admitted artifact, or a finite pass is used as proof that all routes and browsers are correct. | Retain source-bound assurance scope and actual enforcement; neither proof presence nor absence changes runtime semantic authority. |

Part VII's later sections specify the ApplicationAssembly shape,
closure graph, concrete routes, renderer, artifact manifest, Live
and recovery mechanics, lifecycle and diagnostic surfaces. This
opening section establishes the admission *scope* and its three
independent success conditions; it does not provide a second
implementation of those later checkers.

Part VIII must exercise nonvacuous positive HumanHelp Create, Claim,
Reassign, Done/Cancel, creator-local presentation, remote advisory with
exactly one explicitly granted Refresh, and local search/selection/
scroll continuity as appropriate to the selected product contract.
Parts IX–X must relate admitted declarative edges and physical
occurrences to their actual formal and implementation evidence.
