* Part VII — Whole-application construction
:PROPERTIES:
:CUSTOM_ID: part-07-whole-application-construction
:PART_REVISION: 07-20261108
:END:

This part specifies how semantic declarations, executable plans, trusted model
operations, routes, providers, browser assets, Live acquisition, and serving
boundaries become one admitted application. It applies the contracts of Parts
I–VI to construction and production installation. Parts IX and X specify stronger
certification and implementation-correspondence arguments; this part defines
where their evidence enters application admission and how its scope is preserved.

The intended system supports ordinary Clojure and ClojureScript. Application
code need not fit entirely inside a proof language. Its interfaces, effects,
source bindings, and unproved contracts must nevertheless be explicit where
application claims depend on them. A correct assembly makes those dependencies
inspectable and enforces the checks it promises at the actual effect and output
boundaries.

Examples describe intended contracts using illustrative names. They are not
claims that every displayed API already exists. An inspection map, digest,
metadata tag, or successful-looking report does not confer admission or runtime
authority merely by having the displayed shape.

** Whole-application realization and preflight closure
:PROPERTIES:
:CUSTOM_ID: req-whole-application-closure
:END:

Valid components can compose into an unusable application. A correct model
operation does not ensure that a rendered button emits its command, the installed
route invokes that operation, the browser contains its plan, or the result can
be acquired and installed. Whole-application construction checks these connecting
obligations and makes their enforcement part of the supported application path.

A managed operation must have the realization required by its actual contract.
For a browser command, that normally connects its prepared affordance, projected
execution, shipped runtime, transport, trusted dispatch, authoritative operation,
outcome interpretation, and declared observation/recovery continuations. A
server-only operation has no invented browser requirement. A local draft edit
has no invented database transaction.

Closure is not a second choreography. The choreography defines allowed distributed
behavior. Projection derives local coordination. Assembly establishes that the
selected application supplies compatible implementations and dependencies for
that behavior. A matching route cannot make an invalid trajectory valid, and a
valid trajectory cannot create a missing route.

*** Three application claims remain independent

The [[#req-application-assurance-claims][three application assurance claims]]
from Part I apply throughout this part:

| Claim | Required evidence and limit |
|-------+-----------------------------|
| Declared closure | Every required edge in the stated application construction is discharged under its declared policy; this does not discover omitted product intent. |
| Production enforcement | The installed entrypoints, effects, and response paths actually use the admitted checks before the relevant protected action or output. |
| Behavioral completeness | Independently specified user capabilities work through the real application, with the promised authoritative and presentation outcomes. |

A closed application can omit a required Claim control. A correct checker can be
bypassed by an unwrapped production handler. A browser test can succeed only
because it manually supplied the protocol command that the real control failed
to emit. Those are different failures and need different evidence.

An ordinary supported Gesso application has mandatory structural admission and
production boundaries. Stronger proof requirements are selected by an explicit
assurance policy. Omitting an optional theorem does not disable structural
checks, and selecting a theorem does not make an unconnected checker enforce it.

*** Coverage follows effects, not the presence of Choreo metadata

Ordinary HTMX, read-only routes, static assets, local controls, and application
functions remain legal. They do not all need choreographic plans. Their relevant
effects still belong in the application's coverage argument.

For example, an ordinary search endpoint can be a declared authoritative
acquisition without being a command choreography. A preference update may use a
simple admitted operation. If either can write state relevant to an application
invariant, it must be classified and covered as a writer or remain an explicit
external premise of that claim. Calling it ordinary does not remove its effects.

Closure scope includes the managed application's actual ingress and egress:
HTTP, background work, queues, scheduled jobs, administration, migrations,
initialization, imports, and relevant external writers. The specific claims may
cover different subsets, but the exclusions and cross-boundary dependencies are
visible. A raw writer can invalidate a later managed operation's invariant even
when the raw writer has no browser affordance.
