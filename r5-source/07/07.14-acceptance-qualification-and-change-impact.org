** Acceptance, qualification, and change impact

*** The application is usable as well as closed

Independent product acceptance specifies promised user capabilities and outcomes
without copying the framework's route/operation registry. Removing a required
capability must fail that acceptance even when the smaller assembly remains
internally consistent.

For HumanHelp, a coherent disabled Claim control does not satisfy a milestone
requiring helpers to claim Requests. A board that never acquires anything is not
complete because no malformed swap occurred. Positive paths, authorized rejection,
uncertainty/recovery, and relevant multi-client behavior are all part of the
appropriate capability acceptance.

This independence does not require independent duplicate implementations of
business policy. The product oracle describes intended observable behavior;
the semantic construction remains the source of executable operation meaning.
A disagreement prompts review of the specification, implementation, or oracle,
not automatic rewriting of one to match the other.

*** Conformance is bound to actual subjects

Evidence records the source/implementation identity, assembly/configuration,
provider and browser profiles, test/checker version, exercised paths, bounds, and
known limitations. A passing fixture with mocked providers is not evidence that
an unexamined production transaction or subscription implementation conforms.

Each backend profile names the assumptions required by dependent claims, including
atomic dependency protection, command-record incorporation, outcome interpretation,
read progression, retention, and failure/retry semantics where used. A current or
future backend version is qualified against those same assumptions. Detecting a
violation invalidates or blocks the dependent claim; it must not be hidden by a
version update or a stale successful receipt.

Conformance tests can expose an assumption violation without proving the entire
backend. That is a useful and intended contract. Unknown qualification after a
relevant upgrade remains unknown until the selected admission policy establishes
sufficient applicability; a changed version number is neither proof of failure
nor proof of continued correctness.

*** Required verification scenarios

The verification strategy covers semantic construction, production enforcement,
and product behavior with appropriately scoped evidence. At minimum, relevant
application profiles exercise:

| Scenario | Evidence sought |
|----------+-----------------|
| Same canonical definition feeds build, startup, render, and tests | Removing or changing an owned declaration affects the actual consuming paths. |
| An opaque builder returns an invalid candidate | The actual candidate is rejected before submission without claiming all builder behavior was proved. |
| Finite exploration reaches its declared bound or exhausts its resource budget | Scope-complete finite results remain distinct from inconclusive computation and unbounded claims. |
| Rule/operation/outcome exercise is vacuous | Required exercise gates reject; the report does not inflate attempted or disabled operations into commits. |
| A copied report or metadata-equivalent function replaces an issued product | Admission rejects the substitution or explicitly establishes a new binding. |
| The server captures an earlier handler while the system map later changes | Installation evidence detects or limits the server-adoption claim rather than trusting the later map. |
| A worker writes state outside the HTTP catalog | Its path is classified and covered, or the dependent closed-world claim fails/remains explicitly conditional. |
| Two valid requests overlap and complete in reverse order | Their scoped capabilities, outcomes, and rendering contexts remain separate and reusable. |
| A deferred/streamed/cached response bypasses the synchronous guard | The selected response contract prevents unchecked managed output or reports the unsupported path. |
| A fragment's effective form/action depends on outer context | Checking uses admitted context or rejects the unestablished interpretation. |
| Old HTML requests assets after a new assembly activates | It receives the bound compatible asset set or follows the declared compatibility failure/recovery path. |
| Artifact, handler, policy, provider, or backend premise changes | Dependent evidence is invalidated/rechecked without mutating an old admission in place. |
| Startup or activation fails after acquiring resources | No unchecked application exposure remains; cleanup and surviving work are accounted for. |
| The response fails after authoritative incorporation | Server knowledge and participant uncertainty remain distinct and recoverable. |
| A disconnected subscriber misses relevant changes | Initial/reconnect acquisition closes the required gap without needing a new advisory to arrive. |
| A required user capability is removed while the remaining graph closes | Independent product acceptance fails. |

Formal checks, controlled-defect tests, observed execution correspondence, and
real-browser acceptance are complementary. A unit test of a report shape cannot
replace evidence that the actual handler or browser edge is used. A successful
request cannot establish every route or every possible schedule.

The suite includes positive controls for each rejection gate. Rejecting all
requests, never exposing a control, or disabling concurrency universally is not
an acceptable way to satisfy the intended application's behavioral requirements.
