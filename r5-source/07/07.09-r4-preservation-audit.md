## R4 requirements preserved

1. **Preflight is mandatory for the supported managed startup.**
   R4 explicitly rejects optional "remember to call the checker"
   architectures, separate test-only assemblies and starting an
   invalid application in the hope users avoid malformed controls.
   R5.1 preserves a source-owned canonical assembly and mandatory
   structural admission in the intended finished system.
   Unmanaged compatibility APIs remain possible with narrower
   claims, not inherited managed assurance.
2. **Structural failures reject at their earliest legitimate layer.**
   Invalid role/operation semantics fail at construction; missing
   plan, artifact, route, provider, acquisition and required
   recovery fail when the assembly can know them; malformed
   rendered affordances fail before emission; dynamic
   authorization and transaction races remain trusted runtime
   model decisions. The revision strengthens separate
   installed/serving adoption and actual effect gates.
3. **A structurally valid Claim can fail at runtime.** Current
   Membership, Organization policy and RequestAssignment state
   are not predictions a startup checker can freeze. A missing
   literal `:biff.fx/now` binding, by contrast, is a static
   provider wiring error when already knowable.
4. **Preflight covers required dynamic-condition handling.**
   The failure/outcome contract creates distinct continuation
   obligations; a terminal node, generic catch-all exception
   handler, happy-path route or boolean "recovery exists" does
   not close the coverage relation.
5. **Concrete recovery wiring is checked.** R4 required each
   continuation's outcome shape, input/correlation, owner,
   trigger and permitted acquisition, together with
   uncertainty/retirement behavior. The expanded source
   identifies provenance, owner lifetime, invocation rights,
   physical bindings, remaining evidence premises and
   failure disposition.
6. **Post-submission uncertainty is not ordinary rejection.**
   Lost settlement, nondisclosable historical command,
   insufficient progression, stale DOM target, Live gap,
   failed continuity restoration and a known postcommit
   render error require distinct continuation semantics.
   Part IV canonical outcomes and Parts V–VI's resource/grant
   policy are retained.
7. **Static coverage does not prove eventual recovery or
   arbitrary host-code correctness.** R4 explicitly retained
   environmental, scheduling, user-action and resource
   premises. The revised section distinguishes an
   available checked path from actual liveness and from
   opaque callback conformance.
8. **Controlled-defect tests must exercise real gates.**
   R4 required a removed/misbound handling edge to reject
   in supported production construction or output, with
   matching valid fixtures and recovery fault scenarios.
   The expanded sixteen-case table includes positive
   Claim, preflight clock failure, missing command resolver,
   no authorized trigger, dynamic Membership rejection,
   uncertain delivery, nondisclosure, one-Refresh grant
   exhaustion, insufficient progression, subscription gap,
   post-DOM continuity failure, postcommit malformed card,
   replaced handler, recovery queue limit, proof budget
   exhaustion, and reject-all product inadequacy.
9. **Unfinished resource budgets do not become success.**
   Limits, expiry and work retention must have typed
   dispositions, compatible with known commit, unknown
   delivery and physical presentation. Refusing an
   unsafe effect cannot turn into rejecting all valid
   product operations and claiming acceptance.

R4's illustrative failure-layer diagram and named examples
are retained as stage-specific obligations. R5's stronger
policy/evidence distinctions and source ownership remain
the preferred formulation; the diagram is not copied as
a second ad-hoc implementation specification.

## Strengthening relative to R5

- Makes policy/admission and installation/activation physically
  separate with explicit open premises; preflight acceptance
  does not certify the server captured the checked handler.
- Derives recovery duties from model/Choreo failure classes
  rather than a duplicate human-maintained operation registry.
- Defines a precise source, owner, typed input, authorized
  trigger, effect/target and evidence/applicability row for
  each required recovery continuation.
- Distinguishes a pre-effect guard, read-only command resolver,
  permitted authoritative acquisition, presentation repair
  and separately admitted compensating operation.
- Preserves current command-specific knowledge and exact
  original binding after delivery uncertainty; neither
  HTTP errors nor current-state cards prove command rejection.
- Requires the actual selected HTMX error/settlement profile
  to make the recovery trigger available rather than
  relying on a map that a browser never reads.
- Enforces resource budget semantics for long-lived work,
  generation retirement, cancellation and durable records.
- Provides sixteen controlled success/failure histories
  that detect silent fallback and nonvacuous product failure.

## Gesso v1622 correspondence and implementation limits

- `src/gesso/live/application_preflight.clj` currently
  recognizes a closed `ApplicationAssembly` through
  `require-application-assembly!` by joining the
  `OperationAcquisitionAssembly`, current browser
  artifact path/receipt and optional rendered Hiccup
  surfaces. It rechecks current physical artifact
  correspondence. Static samples are not a proof
  that all dynamic render branches are covered.
- The same file provides `require-rendered-surface!`,
  `checked-rendered-response!`, `wrap-application-handler`
  and Biff lifecycle integration on the supported
  canonical Gesso HTML response boundary. Those
  paths do not independently establish that the
  deployed server adopts them, that arbitrary
  post-return deferred rendering is covered or that
  pre-serialized raw Ring HTML is inspected.
- `src/gesso/live/optimistic/execution_preflight.clj`
  joins route-exposed semantic operations to the
  exact prepared optimistic server and verifies
  declared required/supplied capabilities and
  settlement contracts. It explicitly does not
  prove arbitrary provider implementation behavior,
  current model authorization or handler invocation.
- `src/gesso/live/operation_acquisition_preflight.clj`
  derives publication-to-managed-fragment acquisition
  relations; nil required publication fails, an
  explicitly empty set is distinguished, and a
  topic consumed outside this Live app may be a
  warning. This is closed against trusted
  application declarations, not proof the model
  actually publishes after commit or of durable
  reconnect/multi-node delivery.
- `src/gesso/live/optimistic/resolution_assurance.clj`
  supplies an explicitly bounded diagnostic around
  one registered resolved-operation executor. A
  diagnostic failure after execution must not be
  interpreted as transaction failure; its report
  is not portable certification or automatic
  evidence for unrelated invocations.
- `src/gesso/live/application_preflight/assurance.clj`
  records conditional canonical Biff/HTML enforcement,
  warnings on static-surface completeness and named
  direct-start, later-handler-replacement,
  unwrapped-server and raw-response escape paths.
  It does not claim a complete all-failure recovery
  catalog or unconditional production integration.
- Existing scoped regression test sources include
  `test/gesso/live/application_preflight_test.clj`,
  `test/gesso/live/operation_acquisition_preflight_test.clj`,
  `test/gesso/live/acquisition_preflight_test.clj`,
  and `test/gesso/live/application_preflight/semantic_route_test.clj`.
  Their source/test presence was inspected. No fresh
  JVM, XTDB, Chromium or formal test run was
  performed for this editorial revision.

The stronger source-owned comprehensive failure
continuation checker, authorized trigger/owner graph,
end-to-end production-path qualification and systematic
resource/liveness contracts are retained as finished
Gesso design goals, not represented as already
universally implemented in the v1622 preflight.

  proof-assumption classes remain source-owned;

  remain authoritative.

  own their distinct recovery state machines.

  route/clock, required publication and authorized

  establish production enforcement or eventual
  progress.

  actual deployed path, diagnostics and
  positive HumanHelp acceptance require
  independent evidence. A checked failure
  branch cannot satisfy a missing product action.

  remain independently qualified.
