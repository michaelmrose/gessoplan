** Production-path enforcement evidence
:PROPERTIES:
:CUSTOM_ID: req-production-path-enforcement
:END:

Checker correctness and production integration require different tests. A checker
can reject malformed input perfectly while the actual application never calls it.
The supported construction therefore provides observable seams for controlled
faults at the real startup, route, effect, and response boundaries.

Each enforcement case records:

- the admitted source/configuration and actual entrypoint under test;
- the controlled defect and the subject/edge it breaks;
- the earliest boundary with enough information to reject it;
- the expected structured diagnostic or typed disposition;
- the prohibited output or physical effect whose absence is observed;
- any already-performed effect or surviving uncertainty that must be preserved;
- a corresponding valid case showing the path remains usable.

A test-only wrapper that rejects before the real entrypoint does not establish
production enforcement. Removing the actual enforcement connection must make the
appropriate integration test fail. The test must distinguish prevented effect,
detected violation after effect, and inability to establish either.

*** Controlled defects exercise actual construction and installation

| Controlled defect | Boundary and required result |
|-------------------+------------------------------|
| Required plan omitted from the source-derived browser build | Build/admission rejects the missing realization. |
| Correct receipt paired with different asset bytes | Asset admission rejects; the candidate does not serve that pair. |
| Correctly named route installed with a different executor | Installation/invocation gate rejects the mismatched binding. |
| Required provider name exists but returns/binds the wrong shape | Static contract mismatch or concrete provider admission rejects at the applicable boundary. |
| Required assurance policy is selected but its gate is omitted | Managed installation/activation fails; a standalone checker test cannot mask it. |
| Render guard removed or an outer guard shadowed | Concrete malformed output cannot pass the managed delivery boundary. |
| Deferred response loses assembly/guard context | Completion rejects or uses the declared safe failure path; it cannot serialize unchecked. |
| Final renderer introduces an anonymous semantic action | Final structured-output checking detects it even if preparation was valid. |
| Post-check middleware changes the protected action | The transformation is rejected, rechecked, or lacks the claimed admission. |
| Undeclared writer appears in the actual covered inventory | Required closed-coverage admission fails; otherwise the affected claim is explicitly limited under its policy. |
| Candidate activation changes only routes and leaves old assets/providers | Coherence check prevents partial activation. |
| Post-commit rendering fails | Malformed output is withheld while incorporation/participant uncertainty remains truthful. |

These defects use isolated fixtures and the supported production constructor.
They do not alter a real user's live data to test failure. The corresponding
assertions observe the actual server/effect/output seam relevant to the claim.

*** Real browser acceptance starts from real controls

Top-level browser acceptance loads the actual generated runtime and operates the
application's rendered controls. It observes the emitted protocol, selected route,
trusted model result, returned evidence, physical installation, and subsequent
authoritative read as required by the capability.

It must not repair a missing command field by injecting a valid envelope or
manually dispatching the event the button failed to produce. Such setup is useful
in a lower-level protocol test, whose claim is deliberately narrower.

Acceptance includes valid repetition and concurrent activity, not just the first
successful request. Request-scoped issuance must allow later requests and the
admitted degree of concurrency. Out-of-order completions must preserve separate
invocation/command/target ownership. A one-shot test harness cannot establish a
reusable production route.

Expected fault diagnostics are asserted specifically. Broadly ignoring console,
page, or request errors would hide the integration failure this layer exists to
catch. Conversely, a deliberate network-loss test need not pretend no diagnostic
should occur.
