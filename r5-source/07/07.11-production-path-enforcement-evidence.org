** Production-path enforcement evidence
:PROPERTIES:
:CUSTOM_ID: req-production-path-enforcement
:END:

Checker correctness and production integration require different tests. A checker
can reject malformed input perfectly while the actual application never calls it.
The supported construction therefore provides observable seams for controlled
faults at the real startup, route, effect, and response boundaries.

 
*** Evidence is an observed boundary, not the availability of a checker

A production-enforcement claim identifies the *specific installed
application generation and deployment profile*, its selected
assurance policy and every relevant physical path carrying that
claim. It links:

#+begin_example
source-owned semantic application
  -> admitted plan, artifact and trusted route/executor
  -> actual constructed Biff/Aleph handler and provider
  -> network-facing request/effect/output boundary
  -> observed guarded transaction, response and client adoption
#+end_example

These are different evidence subjects. A valid application report
does not attest the selected server module. A checked handler in
=:biff.ring/handler= does not prove a deployed listener consumed
it. A successful Ring invocation does not prove a remote proxy
uses the same route or serves the same asset bytes. A 200 response
does not prove the authoritative model committed. A correct
browser snapshot does not prove the required command was emitted
from a real control, nor that an earlier command incorporated.

Each test report names its original source, concrete generation,
entrypoint and binding identities, installed dependency/handler
versions, checker or observer mechanism, physical observation
and unresolved host premises. Tests may use isolation and
controlled fixtures, but must state which real layers they
replace. A report containing green flags without source-to-
physical causality cannot become an issued executor, deployment
attestation or transferable certificate.

Each enforcement case records:

- the admitted source/configuration and actual entrypoint under test;
- the controlled defect and the subject/edge it breaks;
- the earliest boundary with enough information to reject it;
- the expected structured diagnostic or typed disposition;
- the prohibited output or physical effect whose absence is observed;
- any already-performed effect or surviving uncertainty that must be preserved;
- a corresponding valid case showing the path remains usable.

 
A controlled mutation starts from a valid source-owned candidate
and changes one specified dependency or installed realization;
the expected failure must be attributable to that mutation.
Changing an unrelated test oracle to reject every request is
not enforcement evidence. Mutation selection includes
*removing the guard itself*: tests which still pass when the
real production enforcement connection is absent have failed
to establish its presence.

Failure evidence is stage-specific. A prevented protected
write requires an actual pre-effect guard and a checked absence
of that effect under the stated physical observation scope.
A mismatch detected after XTDB incorporation or response
delivery is a *post-effect contradiction*, with retained
incorporation/disclosure/recovery obligations, not prevention.
A checker timeout, unavailable observation or incompletely
instrumented host produces an explicit unestablished result,
not an assertion that no effect happened.

A test can inspect an issued handler's identity and observed
local Biff-system invocation, or independently verify a real
network listener/route, or observe a guarded XTDB mutation.
It describes exactly which of those links it established.
Satisfying all of them for one fixture remains bounded
physical correspondence under stated principal, environment,
input and writer assumptions; it does not prove every
arbitrary Clojure handler or all deployment traffic.

A test-only wrapper that rejects before the real entrypoint does not establish
production enforcement. Removing the actual enforcement connection must make the
appropriate integration test fail. The test must distinguish prevented effect,
detected violation after effect, and inability to establish either.

*** Controlled defects exercise actual construction and installation

| Controlled defect | Boundary and required result |
|-------------------+------------------------------|
| Required plan omitted from the source-derived browser build | Build/admission rejects the missing realization. |
| Correct receipt paired with different asset bytes | Asset admission rejects; the candidate does not serve that pair. |
| Correctly named route installed with a different executor | Installation/invocation gate rejects the mismatched binding. |
| Required provider name exists but returns/binds the wrong shape | Static contract mismatch or concrete provider admission rejects at the applicable boundary. |
| Required assurance policy is selected but its gate is omitted | Managed installation/activation fails; a standalone checker test cannot mask it. |
| Render guard removed or an outer guard shadowed | Concrete malformed output cannot pass the managed delivery boundary. |
| Deferred response loses assembly/guard context | Completion rejects or uses the declared safe failure path; it cannot serialize unchecked. |
| Final renderer introduces an anonymous semantic action | Final structured-output checking detects it even if preparation was valid. |
| Post-check middleware changes the protected action | The transformation is rejected, rechecked, or lacks the claimed admission. |
| Undeclared writer appears in the actual covered inventory | Required closed-coverage admission fails; otherwise the affected claim is explicitly limited under its policy. |
| Candidate activation changes only routes and leaves old assets/providers | Coherence check prevents partial activation. |
| Post-commit rendering fails | Malformed output is withheld while incorporation/participant uncertainty remains truthful. |

These defects use isolated fixtures and the supported production constructor.
They do not alter a real user's live data to test failure. The corresponding
assertions observe the actual server/effect/output seam relevant to the claim.

 
*** The production seam must actually fail the negative control

Controlled faults are submitted through the normal managed
startup or actual qualified runtime path, not by calling only
a test-side validator with fabricated route/manifest data.
In particular:

- A source-derived browser build test uses the real generated
  entrypoint and actual emitted bytes. A forged receipt tests
  receipt rejection, not correct compiler semantics or served
  network assets.
- A route/executor test verifies the issued callable and
  *actual* selected method, decoded subject and trusted
  principal. A string-equal route table supplied only to a
  checker does not establish installed dispatch.
- An operation/physical-write test captures the original
  command, guard and transaction identities and reads back
  authorized authoritative state. If the physical submitter
  can be replaced with a function returning a fake committed
  map, the test must not report authenticated incorporation
  without a stronger independent write observation.
- A render test exercises the final checked serialization
  path, including malformed *dynamic* Hiccup and relevant
  HTML/HTMX effective actions. The alternate raw or deferred
  output path is separately qualified or outside the claim.
- A lifetime test distinguishes early Biff module
  =:init= side effects, module =:start= ordering, actual
  host handler selection, a deferred completion, and a
  reload replacing the generation. Preflight's appearance
  first in the start list does not fence earlier init work.
- A writer-coverage test challenges the real effect
  boundary or independently qualified host inventory.
  An operation-ID list checked against another declaration
  list does not prove absence of unregistered raw writers.
- A command/Live test distinguishes actual model commit,
  durable command attribution, post-commit publication,
  baseline/subscription coverage, acquisition permission
  and physical browser adoption. A mocked SSE frame
  establishes neither an emitted invalidation nor delivery.

Every test's failure interpretation states whether it
established rejection of an invalid candidate, rejection
of an invalid invocation, blocked output, observed
contradiction, or an unresolved external premise. Cleanup
and preservation of prior committed work are asserted
where relevant. An invalid candidate must not activate
protected service, but a failed response check cannot
retroactively reject a valid previously committed Claim.

*** Real browser acceptance starts from real controls

Top-level browser acceptance loads the actual generated runtime and operates the
application's rendered controls. It observes the emitted protocol, selected route,
trusted model result, returned evidence, physical installation, and subsequent
authoritative read as required by the capability.

 
A genuine browser case starts with a server-rendered,
source-owned HumanHelp control and its actual compiled
JavaScript, real HTMX events and physical target. It records
a causal chain from the control activation to the command
envelope, selected trusted HTTP route, source-owned model
operation, durable result, authorized acquisition and
installation. A direct HTTP fixture sending an idealized
command remains useful, but is only a server/protocol test.

The browser qualification includes expected loaded artifact
identity, actual URL and asset bytes under the selected serving
profile. The initial HTML and SSE connection provide their
required authoritative baseline/interest relationship.
Multi-client tests exercise remote advisory without granting
automatic Refresh, then an explicit one-use authorized
Refresh that establishes and installs a sufficient current
observation. A lost response or duplicated advisory must
retain command/Refresh debt without inventing command
outcomes or extra acquisition permission.

Direct, same-process Ring tests and a real Chromium/browser
over loopback HTTP/SSE are complementary. A loopback
integration verifies its socket/bridge and observed client
behavior, but does not by itself prove a public deployment's
load balancer, CDN, credential boundary, all writers or
inter-node router failover. The report retains that
qualification rather than attaching one generic
=:runtime-enforced= label to all environments.

It must not repair a missing command field by injecting a valid envelope or
manually dispatching the event the button failed to produce. Such setup is useful
in a lower-level protocol test, whose claim is deliberately narrower.

Acceptance includes valid repetition and concurrent activity, not just the first
successful request. Request-scoped issuance must allow later requests and the
admitted degree of concurrency. Out-of-order completions must preserve separate
invocation/command/target ownership. A one-shot test harness cannot establish a
reusable production route.

 
*** Independent positive product completeness

The tests separately declare the minimum required *real
capabilities* that constitute HumanHelp acceptance: an
eligible creator can create and immediately see a Request;
an eligible helper can Claim; authorized users can Unclaim,
complete and cancel as their models permit; a manager can
Reassign; participants can observe initial state and later
advisory/Refresh behavior under the prescribed ownership
policy. Each capability identifies a positive reachable
scenario, authoritative result, valid control and, where
applicable, physical presentation.

A reduced application can be internally consistent, reject
every malformed operation and display a coherent empty
page while entirely omitting Reassign or Claim. Structural
and negative enforcement tests may pass; the product-
completeness gate must fail. Positive acceptance cannot be
satisfied with a hidden or permanently disabled button,
manually injected protocol message, test-only model callback
or fabricated server response. A test may isolate a trusted
external provider with a qualified fixture, but it must
record exactly which effects and assumptions that fixture
replaced.

Tests also exercise valid *subsequent* operations after one
successful command and at least the concurrency policy
advertised by the application. Two legitimate concurrent
Claim attempts are not supposed to both acquire an
incompatible RequestAssignment. They should instead reach
independent request-local admission, then receive truthful
guarded incorporation, rejection or recovery under the
declared atomicity model. Rejecting one attempt because
a global single-use test slot was already occupied is not
evidence of normal concurrent application usability.

Expected fault diagnostics are asserted specifically. Broadly ignoring console,
page, or request errors would hide the integration failure this layer exists to
catch. Conversely, a deliberate network-loss test need not pretend no diagnostic
should occur.

 
*** Positive and adversarial enforcement histories

The following histories illustrate independent evidence
propositions, not a universal single test fixture:

| History | Required evidence or limitation |
|---------+--------------------------------|
| The installed managed application serves a real eligible Claim control, which commits and is followed by authorized card acquisition and physical adoption. | Trace original source, generated bytes, control, actual route/executor, authoritative write and permitted read; retain assumptions about the tested deployment and physical observer. |
| Removing the actual managed startup/preflight module still lets the test's standalone validator pass. | The production integration test must fail, because the normal startup was not gated. |
| An early Biff =:init= callback starts an unchecked protected worker before preflight's first =:start=. | Detect/fence the exposure; module start ordering alone is not a valid no-exposure proof. |
| A correct checked Biff system map is built, but the actual server captures an older handler. | A local slot report stays local; required deployment adoption fails or remains explicitly unestablished. |
| A locally issued Biff host-adoption handle matches a copied returned system map. | It is not independent server attestation, and cannot be promoted into a production certificate. |
| The browser receives a correctly named JavaScript asset but its emitted bytes differ from the checked receipt. | Reject physical artifact correspondence for the relevant serving boundary. |
| Two valid, independently constructed products exchange an execution handler, Live fragment, or asset while preserving familiar operation IDs. | Reject the mismatched source/realization join; matching names do not justify substitution. |
| A malformed semantic POST loses =:choreo/op= only after final conditional Hiccup rendering. | The actual output guard blocks the anonymous semantic action before delivery, not merely a test-side snapshot scanner. |
| A native detached submitter or second =hx-*= action bypasses a checked button's main transport. | Resolve all supported effective physical requests and reject the unadmitted semantic route. |
| The selected server route decodes Request R2 while the browser command binds Claim to R1. | Reject trusted selector contradiction before the protected model effect. |
| A request's selected provider advertises =:clock= but does not supply the consumed =:biff.fx/now= shape. | Reject at a knowable provider gate; a provider keyword or a later exception is not successful execution. |
| A physical XTDB submitter is replaced by a fake =:committed= result that performs no write. | A 200 or committed map is insufficient; independent authoritative state/transaction attribution is required to claim incorporation. |
| A valid Claim incorporates but the response's Cancel affordance is malformed. | Block invalid output while retaining the real committed command and participant-relative settlement/unknown recovery; do not assert no mutation occurred. |
| A failed settlement leaves the Claim command uncertain while a later card happens to show a helper. | Preserve command attribution as unknown until a permitted command-specific resolver obtains admissible evidence. |
| The Live baseline precedes interest registration and a relevant update occurs between them. | Demonstrate actual fence/replay/reacquisition or retain the no-gap premise; a healthy SSE socket alone does not suffice. |
| A remote client receives duplicated advisories after using its one permitted Refresh. | Do not issue another Refresh grant or discharge fresh advisory debt on the basis of duplicate delivery alone. |
| A deferred response retains an old generation while a new handler and assets activate. | Verify its admitted guard, physical target and compatible retirement path; no silent new-generation splice. |
| A scheduler or raw XTDB path changes protected state without appearing in the registered operation inventory. | Refuse a claimed all-writer enforcement proof unless the physical capability boundary or independent complete inventory covers it. |
| Two consecutive valid Claims on independent Requests are rejected by a shared consumed invocation slot. | Fail the advertised reusable/concurrent route; a one-shot test cannot establish normal operation. |
| An application passes all negative checks but omits the required Reassign control and executor. | Fail independent positive product completeness even if its smaller assembled graph is closed. |
| A Chromium test injects a valid Claim envelope instead of clicking the broken actual button. | Record only a protocol/server fixture success; top-level browser acceptance remains unmet. |
| A network-loss scenario produces its declared command-unknown diagnostic while all unexpected browser errors remain visible. | Assert expected errors precisely and require subsequent permitted resolution; neither a blanket console-error ignore nor an immediate rejection is acceptable. |

Tests exercise the original admission and effect boundaries with
isolated disposable state and explicit failure injection; they
do not corrupt real users' records. The report separates
*prevented effect*, *observed post-effect violation*, *physical
completion*, *current-state read* and *historical command
incorporation*. Known open assumptions, unsupported probes
and test-environment substitutions remain in the provenance
of the reported claim.

Sections 07.12–07.15 must expose these same distinctions
through explanation, diagnostics, acceptance qualification
and the security invariant. Parts VIII–XII retain independent
positive product proofs, formal/model correspondence and
deployment/release assurance. An implementation may make
substantial progress on one layer without being entitled
to the stronger adjacent layer's certificate.
