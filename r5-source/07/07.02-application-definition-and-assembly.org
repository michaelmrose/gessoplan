** Application definition and ApplicationAssembly
:PROPERTIES:
:CUSTOM_ID: req-application-assembly
:END:

One source-owned application definition composes the declarations that their real
owners export. Its normalized realization is the conceptual
=ApplicationAssembly=. It is a graph of typed subjects, bindings, obligations,
and evidence, not a collection of unrelated success flags.

The public authoring surface should remain small. Source owners declare genuine
choices once; construction derives repeated identities and verifies independently
chosen physical correspondences. Applications should not maintain separate
operation registries for browser compilation, preflight, startup, rendering,
model checking, and tests.

*** Source ownership and derivation

| Source owner | Authored facts | Derived or checked products |
|--------------+----------------+-----------------------------|
| Domain/model module | Typed operation meaning, guards, dependencies, transitions, outcomes, command/recovery contract, opaque premises. | Model interfaces, candidate obligations, operation catalog, rule/audit views. |
| Choreography module | Distributed roles, permitted knowledge flow, coordination, local recovery choices. | Role-local plans and compiler correspondence. |
| View/component | Selected operation, concrete arguments/observations, presentation, availability choice. | Prepared action binding, effective transport annotation, render obligations. |
| Route/ingress module | Supported physical dispatch and input mapping. | Installed dispatcher, route index, selector-consistency checks. |
| Trusted execution adapter | Public model delegation and actual implementation/provider binding. | Issued callable, invocation gate, outcome encoder. |
| Acquisition/Live module | Projection/query scope, observation contract, subscription and refresh policy. | Acquisition bindings, coordinator requirements, advisory/recovery edges. |
| Runtime/build profile | Compiler/runtime, physical handlers, assets, supported host behavior. | Browser manifest, generated bootstrap, build receipt, qualification obligations. |
| Application composition | Selected modules, configuration, assurance policy, lifecycle/deployment profile. | One admitted application and its explanation. |

An exported declaration is not accepted solely because it came from a namespace
with the right name. Construction validates its semantic category and required
source/implementation correspondence. A raw declaration, an admitted operation,
an issued executor, and a copyable report can use similar host representations
without being interchangeable.

 
The application definition must also identify the *coverage of its source
inventory*: which declarations exhaust the selected deployment's known routes,
workers, scheduled writers, renderer producers, external effects, and extension
points; which are only sampled or discovered; and which remain unknown. A map
with no registered writer is not evidence that no relevant physical writer
exists. If a strong assurance policy depends on complete source or effect
coverage, incomplete inventory is an open or blocking obligation, not success.

Model semantics, physical route selection, provider selection, rendered
affordance selection and build/runtime installation are independently authored
choices. Construction derives facts that have one semantic owner, checks each
independent choice against that owner, and retains source provenance for
diagnostics and change invalidation. Matching strings or plausible metadata
must never convert a physical selection into semantic authority.

A schematic composition might be:

#+begin_src clojure
(defn application-definition [config]
  {:application/id :humanhelp/example
   :domains [request/definition
             organization/definition]
   :flows [request-flow/definition]
   :surfaces [request-card/definition request-board/definition]
   :ingress (routes/definitions config)
   :execution (server/execution-bindings config)
   :acquisitions (live/acquisition-definitions config)
   :providers (server/provider-bindings config)
   :browser-profile browser/profile
   :lifecycle (system/lifecycle-definition config)
   :assurance-policy assurance/managed-application-policy})
#+end_src

Each referenced module exports its actual owned declarations; the example does
not stand in for omitted definitions. The composition does not retype operation
IDs, argument schemas, settlement variants, or plan digests already determined by
those declarations. Independent physical route selection and provider selection
remain real choices that must be checked.

Tests instantiate this constructor with declared fixture configuration. They can
replace a clock or storage provider for a scoped test, but must identify that
substitution and avoid transferring its evidence to an unexamined production
provider. A hand-built shadow assembly is not production-closure evidence.

 
*** Worked Claim source-owner join

The following is schematic application composition. The referenced Vars and
the precise constructor spelling are illustrative, not claims about the
current public Gesso API. Each module exports its own actual declarations:

#+begin_src clojure
(defn claim-application [config]
  {:domains [request-model/definition organization-model/definition]
   :flows [request-choreo/definition]
   :surfaces [request-card/definition]
   :ingress (request-routes/definitions config)
   :execution (request-server/operation-bindings config)
   :acquisitions (request-live/definitions config)
   :providers (request-server/provider-bindings config)
   :browser-profile browser/profile
   :assurance-policy assurance/managed-application-policy})
#+end_src

For the =:request/claim= slice, construction checks the following distinct
facts instead of recopying one operation ID into six registries:

| Owner | Required relation and rejected near miss |
|-------+------------------------------------------|
| Request model/Choreo | The admitted Claim targets the current Request and RequestAssignment under trusted principal, Membership and Organization guards; a similarly named unchecked handler is not the same transition. |
| Request-card view | A real eligible control supplies the operation, typed Request argument and required observation/command binding; a disabled or absent control does not satisfy positive product acceptance. |
| HTTP route | Actual POST method, path template and decoded path Request match the command's Request target; a matching operation name with mismatched target is rejected. |
| Trusted executor | Installed callable implements the model-owned command and recovery contract; an entry naming a different function does not establish execution correspondence. |
| Providers | The actual clock and principal have the value shapes required by the executor, including =:biff.fx/now= when that concrete model FX integration is selected; simply listing =:clock= is insufficient. |
| Browser and Live | The loaded generated plan/physical handlers, authorized reread, progression and subscription/Refresh policy join the same admitted operation; a build-only manifest or missing acquisition does not close the path. |

One command identity persists through permitted delivery uncertainty and retry;
a later current card observation is not by itself historical incorporation
evidence. Current authorization, atomic execution and actual DOM installation
require their own runtime evidence. The Claim illustration cannot stand in
for separately required Create, Unclaim, Cancel or manager Reassign paths.

*** Checked construction supports opaque application code

An ordinary Clojure function can implement a rule, renderer, projection, candidate
builder, or input conversion behind a declared interface. Construction establishes
what can be checked and retains a named premise for the rest, under
[[#req-admission-assurance-policy][the admission policy]].

For a candidate builder, the actual returned targets, assignments, frame,
command binding, and supported effect footprint can be checked before submission.
That instance check does not prove that the builder had no hidden earlier effect
or that it produces valid candidates for every input. Effect containment and
functional conformance remain separate enforcement or assumption obligations.

Normalization must not silently execute arbitrary application work to discover
its meaning. Functions invoked during construction have an explicit purity,
determinism, totality/failure, and resource contract. Compilation, dependency
resolution, and model exploration use their declared budgets. An effectful
builder cannot be called repeatedly by inspection or diagnostics as though it
were inert data.

 
The boundary between a checked *instance* and a function's general behavior
is retained in the report. A pure bounded export may be evaluated under its
admitted inputs; an uncontained effectful callback cannot be probed for
inspection as though it were data. Exception, timeout, unknown dependency,
nondeterminism or undeclared side effects produce explicit dispositions rather
than an empty declaration. Agreement between a callback's own generated
assumptions and its reported result is not independent evidence.

A canonical admitted construction should derive execution and checking products
from the same semantic subject wherever possible. An independently supplied
reference model remains useful, but its relation to the production operation is
an explicit obligation. Agreement between two copies of the same mistaken policy
is not evidence that the intended business rule was correct.

*** Closed registries and explicit extension boundaries

Registries declared closed reject unknown, duplicate, ambiguous, or incompatible
members before use. Extension points identify how new modules, routes, operations,
or providers become a newly admitted construction. Dynamically loading a plugin
must not mutate an admitted registry while retaining old closure evidence.

 
Closure is scoped by registration source, deployment profile, effect family and
inventory boundary. A closed declared route table does not imply an exhaustive
inventory of background writers. A validated collection of rendered Hiccup
snapshots does not prove all future conditional responses. Where a stronger
claim needs that coverage, the system needs independent inventory evidence,
a real producer/effect-boundary guard, or a truthful weaker disposition.

Adding or replacing a plugin creates a candidate new generation with new
admission and compatibility decisions. During rolling installation, older
requests and workers retain their previously admitted generation; loading new
code cannot silently grant them the new generation's rights.

Unused declarations can be available for composition without being exposed or
active. They are labeled accordingly. A generated executable or installed writer
that claims a role in the active application must have a corresponding source
and coverage classification; it cannot disappear from the graph as unused merely
because no UI currently invokes it.

*** Construction phases and admitted assembly identity
:PROPERTIES:
:CUSTOM_ID: req-assembly-construction-phases
:END:

Construction has an acyclic dependency order. It may expose several internal
products without asking application authors to maintain several definitions.

| Phase | Product and admission responsibility |
|-------+--------------------------------------|
| Normalize | Resolve source-owned semantic declarations, physical choices, configuration, and explicit opaque contracts. |
| Derive | Produce required role plans, interfaces, closure graph, proof obligations, and the browser build manifest. |
| Build/check | Generate assets and correspondence products; run applicable semantic, closure, qualification, and assurance checks. |
| Admit candidate | Bind accepted evidence and retained premises to an immutable candidate realization under the selected policy. |
| Install | Construct actual router, wrapped handler, providers, worker entrypoints, and asset serving from that candidate. |
| Activate | Verify the required installation relationships and permit external application service. |
| Retire | Revoke or transfer owned rights/work, drain permitted users, and release resources under the lifetime contract. |

Some installation facts cannot exist before installation. The lifecycle therefore
allows private preparation and a final activation gate, while preventing unchecked
application operations from becoming externally available. A report saying a
candidate is structurally closed is not a report that its server was activated.

 
The activation gate verifies what was actually installed or bound for serving:
the dispatcher and checked handler, executable and served assets, provider
and worker registrations, required acquisition paths, and the selected
deployment's physical applicability premises. A constructed router value alone
does not establish that the serving host adopted it. An unsuccessful build,
partial installation or rejected activation must not expose unchecked operations;
already acquired resources retain identified cleanup, cancellation and
surviving physical-remnant obligations. Repeated startup must not silently
duplicate workers or reuse another generation's installation receipt.

The identities used in these phases identify different objects:

- normalized semantic/realization input identity;
- concrete implementation closure and qualification-profile identity;
- exact executable plan identity;
- browser manifest identity;
- emitted asset content identity;
- checker result/evidence identity with its applicability;
- admitted assembly instance, optionally described as an assembly generation;
- deployment instance/placement identity.

An assembly generation is a scoped application-construction lifetime. It is not
a universal freshness number, browser execution ID, resource incarnation, command
ID, or database progression token. Examples use =:assembly-instance/id= when
referring to that admitted lifetime.

A digest recipe specifies the object, canonical encoding, schema, relevant
compiler/provider dependencies, excluded self-identifying fields, and collision
premise. Formatting-only source changes need not alter semantic identity, but a
changed opaque implementation can invalidate implementation evidence even when
its public contract is unchanged. Part V's exact plan and asset distinctions
apply here.

 
Identity comparisons are typed relations. Equal semantic identities may
coexist with different handler implementations; equal artifact bytes can be
installed under different execution permissions; distinct deployment instances
can use one generation. Evidence is reusable only when its *complete*
dependencies, mechanism and applicability premises remain valid. A digest
cannot issue a trusted executor, prove artifact provenance, or establish
physical serving. The normalization contract must detect omitted dependency
fields and ambiguous encodings, not merely select a digest algorithm.

The final asset digest cannot be an input to the same bytes containing that
digest without an explicit cycle-breaking construction. Detached receipts and
content-addressed asset locations provide a straightforward solution.

*** Immutable admitted bindings and scoped revalidation

An admitted assembly binds the actual implementations, providers, policy,
qualification profiles, route semantics, rendering contract, and artifact set
on which its claims depend. A request captures that assembly instance at entry.
Its later callbacks, rendering, and response completion preserve that reference.

 
Capturing a generation never freezes changing principal authority, live
RequestAssignment state, transaction progression or physical target/resource
ownership. Those are re-established at the relevant current effects. An
incompatible deployment may permit an old request to finish only under its
explicit retirement policy; otherwise its obsolete physical actuation rights
must be revoked and any surviving durable command resolved through compatible
recovery. A callback must not splice a new route, plan or provider into an old
continuation merely because names still match. Subscriptions and background
workers require corresponding generation and resource lifetimes.

An immutable map containing mutable Vars or registries is not automatically an
immutable realization. The supported construction captures applicable callable
bindings, uses assembly-owned registries, or detects and re-admits relevant
replacement before dependent use. An ordinary reload is a declared construction
transition, not an arbitrary mutation excused by development mode.

Construction evidence may be cached by its complete dependency identity and
applicability conditions. There is no requirement to recompile plans, explore a
finite model, or hash every asset on every response. The runtime must preserve
or re-establish the relevant binding at the boundary where it is used. A mutable
asset path or live registry needs a concrete stability/invalidation mechanism;
a cached green report cannot supply one.

Admission handles can be opaque process-local values; explanatory reports remain
copyable data. A private issuance registry can prevent accidental substitution of
a copied map for an issued executor. Object identity alone is not durable proof,
remote attestation, or a sandbox against hostile code sharing the JVM. Process
restart reconstructs local admissions from their actual sources and any
independently checkable durable evidence.

 
*** Positive and adversarial construction histories

| History | Expected disposition |
|---------+----------------------|
| An eligible Claim has source-owned model, control, POST, issued executor, correct clock, built-and-served browser asset and authorized card acquisition. | Admit the candidate; require separate real installation, execution and product acceptance evidence for stronger claims. |
| A route and command use the same operation name but select different Request IDs. | Reject the route/command correspondence before a protected effect. |
| A provider is named =:clock= but the executor never receives the required =:biff.fx/now= value. | Reject the provider binding or block actual execution at the capability gate. |
| Sampled Hiccup cards are valid, but a conditional render emits an unannotated POST to a protected command route. | A static snapshot is insufficient; the installed response guard must reject the actual rendered request or the stronger claim remains open. |
| An unlisted background writer can mutate protected RequestAssignment state. | Treat writer coverage as incomplete; do not certify a complete protection argument from a declared subset. |
| A plugin adds a route or a mutable Var points to a new handler after admission. | Invalidate affected evidence and re-admit a new generation before dependent use. |
| A delayed callback belongs to a retired generation or superseded browser target. | Prevent stale actuation; retain only separately owned command/recovery obligations. |
| A fixture constructor passes with test providers but production uses another actual handler. | Preserve fixture-scoped evidence and leave production correspondence open. |
| A candidate is checked but the serving router never adopts its guarded handler. | Report candidate closure, not deployed enforcement or demonstrated user behavior. |
| A finite checker exhausts its budget or cannot express the selected obligation. | Report inconclusive/unsupported and apply the admission policy; neither success nor counterexample may be fabricated. |

These are scoped construction requirements, not a demand to prove every
ordinary Clojure function. Plain Clojure and explicit ordinary HTMX remain
legitimate while their real effects must respect any application-wide safety
property being claimed. Later sections define the detailed closure edges,
serving enforcement, diagnostics and positive acceptance criteria.
