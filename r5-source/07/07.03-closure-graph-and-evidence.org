** Whole-application closure graph and evidence

The graph represents semantic interfaces and actual realization relationships.
It must expose enough structure to locate a failure without forcing a reviewer
to reverse-engineer many namespaces. The runtime need not carry the entire graph
on every request; it uses admitted bindings derived from it.

 
The graph has *typed nodes* for semantic sources and obligations, selected
application realizations, installed physical bindings, and the propositions
whose evidence can support admission. These are not interchangeable merely
because all happen to be represented by Clojure maps. Each node identifies its
source owner, semantic category, scoped identity, admitted generation where
applicable, and the implementation or deployment profile against which it is
being checked. A generated browser plan and the bytes that were actually
served are distinct nodes with a correspondence edge between them.

Edges identify a *relation and its justification*, not only the existence of
two endpoints. Construction derives required edges from each admitted
operation's interface, the independently specified application capabilities,
and the selected assurance/deployment policy. An explicit source declaration
and an observed physical binding can disagree; neither may silently rewrite
the other to make the graph close.

The realization graph may contain legitimate feedback paths such as command
settlement, Live advisory and authoritative reacquisition. Its *evidence
dependency argument*, however, must be well-founded: a report cannot certify
its own source binding, and two success summaries cannot mutually establish
one another without an independently admitted base. The proof-DAG layer of
Parts IX–X records these dependencies; Part VII requires their ownership and
non-circular applicability already at assembly time.

*** Operation-specific edges

| Edge or obligation | Required correspondence |
|--------------------+-------------------------|
| Affordance to operation | Concrete arguments, observations, selected realization, and availability implement the named operation. |
| Operation to choreography/projection | Required role-local behavior follows the admitted coordination and knowledge contract. |
| Plan to executable artifact | The generated runtime contains the intended admitted plans and bound implementation/profile dependencies. |
| Executable plan to physical handlers | Every reachable required effect has a compatible handler and completion/failure protocol. |
| Transport to ingress | Method, route semantics, encoding, selectors, correlation, and protocol agree. |
| Installed ingress to executor | Actual dispatch invokes the selected issued/admitted callable, not a metadata-equivalent substitute. |
| Executor to public model operation | The trusted operation binding implements the declared model interface and preserves its command/authority obligations. |
| Operation to providers | Required typed resources resolve to compatible providers with the right origin and lifetime. |
| Candidate to authoritative realization | Checked targets, guards, assignments, frame, and effects reach the admitted lowering/submission boundary. |
| Model outcome to participant settlement | Each supported outcome maps explicitly without collapsing incorporation, rejection, repetition, and uncertainty. |
| Required propagation to recovery | Publication/durable work, progress requirements, and missed-delivery recovery have actual owners and paths. |
| Observation to presentation | Scope, progression, authorization, representation, target ownership, and physical completion support the claimed adoption. |
| Application policy to enforcement | Mandatory checks are invoked at the actual construction, installation, request, effect, and output boundaries. |
| Product capability to acceptance | Independent promised behavior is exercised through the admitted application; closure alone does not establish it. |

Not every operation needs every edge. The operation's admitted interface derives
its obligations. A read cannot require a fictional mutation just to fit a universal
pipeline, and a mutation cannot omit recovery because it looks like an ordinary
POST.

 
*** Graph coverage, orphan nodes and independent capabilities

The assembly checks *both directions*: every required semantic effect has the
appropriate realization, and every installed realization that claims a
semantic/effect role is connected to an admitted contract and classified
coverage. A generated plan with no source operation, a semantic route with no
registered executor, a Live acquisition without its managed projection, or an
installed state writer outside the admitted effect inventory cannot be hidden
by reporting only successful edges. A declared but unused component may be
classified =available-not-active=; an installed writer that changes protected
state cannot use that classification to escape global invariant obligations.

A useful closure explanation distinguishes at least:

| Subject | Required graph disposition |
|---------+----------------------------|
| Exposed managed operation | All reachable semantic, physical, settlement and recovery edges required by its interface are checked or explicitly qualified under policy. |
| Ordinary read-only HTMX route | Its real transport, authorization, data/projection and response contract are accounted for; no fictional command mutation is added. |
| Ordinary state-changing route or non-HTTP writer | Its physical effects are classified and checked for interaction with protected state and invariants, even without a Choreo browser plan. |
| Installed worker, provider, browser asset or subscription | Its source ownership, effect scope, lifecycle and actual deployment binding are represented with applicable evidence. |
| Available but inactive declaration | Not counted as a deployed behavior or as positive product acceptance. |
| Unknown source, unclassified writer or incomplete host inventory | Remains an explicitly scoped coverage gap; silence or an empty supplied list cannot close it. |

Closure is always relative to a stated inventory, effect footprint,
deployment generation and policy. An operation whose *required* edge is
missing fails the corresponding admission gate; where the environment cannot
establish exhaustive physical inventory, the stronger all-writer or
production-enforcement claim remains open rather than being inferred from
the discovered subset. Section 07.04 owns the complete application assurance
policy and its writer-coverage obligations.

*** Evidence is attached to a proposition, not a prestige label

A checked edge records its subject, expected relation, actual binding, source
ownership, mechanism, premises, coverage, applicability, and result. These are the
[[#req-assurance-classification][assurance dimensions]] from Part I.

An illustrative inspection row is:

#+begin_src clojure
{:obligation/id :claim/installed-route-to-executor
 :subject {:assembly-instance/id assembly-id
           :route/id :route/request-claim
           :operation/id :request/claim}
 :expected {:executor/ref admitted-claim-executor-ref}
 :observed {:installation/ref route-installation-ref}
 :mechanism :issued-dispatch-construction-check
 :evidence/ref checked-binding-evidence-ref
 :status :established
 :scope :this-installed-dispatcher
 :premises [server-adopts-dispatcher-premise
            implementation-closure-premise]}
#+end_src

The checker derives this result from the relevant construction/installation.
Writing =:status :established= into a map does not satisfy the obligation. A
handler's operation name proves neither its body nor adoption by the real server.

 
The illustrative row is a *diagnostic view* of a checked proposition, not a
public constructor for trusted evidence. The original sources, selected
implementations, independent observations and actual checker mechanism remain
separately identifiable. For example, a route-to-executor report can establish
that the issued dispatcher closes over a particular callable in the current
construction; it cannot also assert that the deployed web server uses that
dispatcher, that the handler has no additional side effects, or that the
current caller is authorized. Those require separate evidence or named
premises at their actual boundaries.

For each edge the report records whether the relation was required,
how its expected and observed values were obtained, the exact identity and
lifetime of each physical participant where relevant, the evidence's
validation mechanism, the checker and input versions, and the original
source/dependency subject. A copied success report or forged discriminator
does not reproduce a live issued binding. A source-derived explanation can be
retained after admission without conferring the permissions of the admitted
executor or current physical target.

A report distinguishes unresolved structural edges from retained runtime or
external premises. Structurally arranging a trusted principal provider can close
an edge; the actual principal's current authorization remains a runtime/model
condition. The report must not list every future authorization decision as an
unfinished build task.

 
The same temporal discipline applies to command outcomes and presentation:
an issued command, a submitted XTDB transaction, a pinned historical readback,
a current authorized Request-card observation, and completed physical DOM
adoption answer *different propositions*. A branch receipt, callback label,
HTTP 200 or current-looking card cannot certify all five. Application closure
requires a lawful path to obtain each required fact; the actual fact remains
scoped to its source, time, authorization and physical observation.

*** Checked, unsupported, inconclusive, and contradicted are distinct

The admission policy identifies which obligations are mandatory, which require a
particular evidence mechanism, and which may remain named assertions. A missing
route, mismatched executor, invalid schema, wrong authority source, or missing
required recovery cannot be excused by adding a trusted flag.

Unsupported proof fragments and exhausted checking budgets do not establish
falsehood or success. They receive explicit dispositions under the policy. A
known counterexample to the same scoped claim cannot be relabeled an accepted
assumption to make admission green. Correcting an abstraction, narrowing a claim,
or fixing implementation requires a new explicit check of the changed subject.

Claims such as assembly-verified, runtime-enforced, exact-finite-checked, and
proof-kernel-checked describe different evidence at different scopes. They do
not combine into an unexplained percentage or one universal verified Boolean.
The permanent executable semantic core remains distinct from the proof kernel
and from dedicated correspondence/conformance checkers.

 
*** Evidence dispositions and safe composition

For a proposition and its exact scope, the evaluator distinguishes:
=established= with retained assumptions and mechanism, =open= when
required evidence has not been obtained, =unsupported= when the selected
checker cannot express the obligation, =inconclusive= when an attempted
check did not finish or exhausted its declared budget, and =contradicted=
when grounded evidence establishes a counterexample to the proposition.
The vocabulary in a concrete report may be more specific, but it must
preserve these semantic distinctions. An unsupported theorem cannot be
made established by an application-side label; an explored counterexample
cannot be discarded merely by lowering the assurance policy silently.

Evidence composition uses *matching subjects and applicability*, not just
matching successful statuses. A finite model pass supports its bounded
state/transition proposition; conditional induction supports the exact
declared abstract catalog and retained premises; an in-process handle
supports its specified source/issuance identity; and observed XTDB or
browser behavior supports only the checked physical occurrence and
profile. The composite claim records every essential dependency, the
unproved bridge between independently authored model and implementation,
and any unknown writer, deployment adoption or host-trust assumption.
There is no transitive promotion from structural closure to universal
runtime correctness.

A sound failure report points to the minimal broken relation and its
owning source without presenting an inferred repair as a completed one.
A missing plan is not repaired by changing a server-side operation name.
A wrong HTTP target cannot be repaired by adding a browser success marker.
A model execution with an unknown outcome cannot be relabeled rejected
because the current card no longer shows the assignment.

*** A Claim realization closes more than its happy path

For HumanHelp Claim, the source-owned model operation protects current Request
state, helper Membership, Organization policy, and their association under the
Part IV command protocol. Assembly must connect that operation to all required
browser and trusted-server paths.

| Concrete requirement | Failure it prevents |
|----------------------+---------------------|
| Generated Claim binding includes typed Request arguments and the admitted observation context. | A visually enabled control lacks the input/basis its realization requires. |
| The actual browser asset loads the matching plan and physical handlers. | Startup succeeds but clicking the button cannot execute the plan. |
| The real request carries the selected command envelope and stable =:gesso/command-id=. | A working =hx-post= reaches the route without the required command. |
| Path Request selector and decoded command argument are checked for agreement. | The URL selects one Request while the command targets another. |
| Installed route invokes the bound public operation through its admitted executor. | A similarly named handler performs a different transition or bypasses command records. |
| Provider binding supplies sampled time in the representation the executor consumes. | A declared clock exists but the required context value is absent. |
| Model outcomes have explicit participant mappings and disclosure checks. | Repetition after a successful commit is mistaken for a fresh failed Claim. |
| Unknown has a current reconciliation owner and compatible resolver path. | Lost response strands the command or provokes a duplicate new command. |
| Scoped acquisition and physical installation close the presentation path. | HTTP 200 is counted as a current card despite no successful swap. |
| Required Live propagation and reconnect recovery close remote participant behavior. | The initiating user succeeds while other interested boards can never recover. |

The explanation derives these rows from the admitted construction and its evidence.
A shorter example that omits the resolver, physical completion, or publication
recovery must identify its narrower scope instead of being labeled a complete
application proof.

 
*** Required positive and adversarial graph histories

Each case is evaluated against the same source-owned assembly, not a manually
constructed substitute graph. The evidence mechanism and negative case are
independently identified; supplying a prefilled report is not a test.

| Observed history or construction | Required disposition |
|----------------------------------+----------------------|
| An eligible helper can render and execute Claim through the actual admitted browser plan, trusted request, guarded transaction, authorized reread and installed card. | Every applicable edge is discharged at its own scope; separately tested user behavior establishes positive acceptance, not automatically a theorem. |
| The generated artifact lacks the selected Claim plan, despite a valid choreography. | Fail the plan-to-actual-artifact edge; a green model proof cannot close it. |
| The POST route exists but selects Request R2 while the command and card select R1. | Reject transport/selector correspondence before a protected write; a matching operation name is insufficient. |
| A server realization advertises =:clock= but never supplies the required =:biff.fx/now= value. | Reject its typed provider edge or block at actual execution admission; not a successful Claim. |
| The model commits Claim, but no authorized Request-card acquisition or compatible unknown-command resolver is installed. | Leave settlement/recovery/acquisition edges open or reject the selected mandatory profile; HTTP success alone does not discharge them. |
| A Live advisory arrives but the remote user's one-Refresh grant has already been consumed. | Keep advisory/Refresh debt; do not invent another authorized physical read from a successful publication edge. |
| The current card no longer displays the helper after a later Reassign, while an earlier Claim remains historically incorporated. | Keep current-state and historical-command propositions separate; do not report the earlier command as rejected. |
| An apparently unused generated plan or installed write route has no admitted semantic owner, or a scheduled writer is missing from the declared catalog. | Report its orphan/unclassified scope and the resulting coverage gap; no false full-writer closure. |
| A static render sample passes, but a conditional response later emits a protected unannotated HTMX action. | Require actual response-boundary rejection or retain the production-enforcement gap; static Hiccup coverage is insufficient. |
| A finite checker times out, or a known source-bound counterexample contradicts a claimed invariant. | Return inconclusive or contradicted respectively; never substitute a successful assembly-edge status for proof. |
| A production server replaces the checked handler after preflight or serves an older JavaScript artifact. | Separate candidate graph closure from current deployed correspondence; invalidate or refuse the affected claim. |
| An ordinary authorized read or a server-only workflow has no browser command plan. | Admit the *applicable* read/server edges without requiring fictitious optimistic or command nodes. |

These histories preserve the R4 requirement that the same Claim can fail at
different edges for different reasons. They also prevent an error-free but
incomplete graph, a reject-all construction, or a certificate-shaped report
from being mistaken for a useful and fully realized application. The formal
policy and physical enforcement of these edges are developed in 07.04–07.15.
