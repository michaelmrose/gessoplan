## Preservation verdict and important distinctions

The preferred R5 baseline is meaningfully better than the R4 conceptual
example: it gives an explicit bounded AST, exact reader footprint, nominal
enum descriptors and strict Boolean evaluation. Preserve that design. R4 also
contained valuable higher-level requirements which R5's short rule section
could make easy to lose: full Clojure as the user-facing language, separately
checked original-source elaboration, distinct intrinsic versus distributed
admissibility, explicit opaque extensions, product-policy independence, and
non-vacuous valid/invalid examples. Those are now made explicit without
pretending advanced relational constructs are baseline operators.

This is a *timeless target contract*. The code review indicates which parts
are already narrow, concrete Gesso mechanisms, not a reason to constrain
the eventual certified language to present v1219/v1221/v1223 syntax forever.

## R4 semantic-preservation decisions

1. **Well-formedness is not policy correctness.** R4's valid open-state
   conjunct may encode an insufficient HumanHelp authorization policy.
   A closed type checker rejects enum-versus-number comparisons but
   cannot decide whether Organization intended to permit Claim.
2. **User-facing full Clojure survives.** Ordinary functions, models,
   guards and operations remain normal Clojure; the closed data AST
   is the supported *certifiable subset*, not a mandated second
   application program. Any automatic translation from a Clojure
   source subset to AST requires an explicit correctness premise or
   checked translation relation. One manually copied predicate
   agreeing with the function in a test is not that relation.
3. **R4's candidate advanced rule operators remain future typed
   extensions.** Relationship paths, role/capability predicates,
   deterministic derivations, nominal variant tests, finite
   collections and exhaustive match are not silently promised
   by the tiny baseline. Each needs a closed grammar, type
   judgment, evaluation meaning, provenance/dependency and
   semantic/refinement bridge; 09.04 owns the extension boundary.
4. **The pure AST has a real grammar and sandbox boundary.**
   Exact recognized reader declarations, plain vectors,
   finite homogeneous literal sets, closed operators, arity,
   node/depth/size limits and non-executing decoding preserve
   R4's no-arbitrary-host-execution requirement. Reader-eval,
   custom comparator, function-valued payload and ambient
   Principal/Var lookup cannot become certified rule syntax
   by passing through a Clojure host evaluator.
5. **Intrinsic syntax, nominal type, concrete value and distributed
   placement are four different checks.** R4 requires the
   authoritative private Request field to be unavailable at a
   browser point that lacks knowledge/provenance even when the
   predicate is intrinsically well typed. A true Boolean result
   is not a current actor/Request/XTDB commit capability.
6. **Reader/type footprints are exact for the represented rule.**
   The author-declared reader set and type map must match the
   syntactic reads. This is not evidence that an unrelated
   Clojure callback has no hidden reads or side effects.
7. **Nominal/presence semantics are retained.** Required versus
   optional, nullable versus nonnullable, absent versus
   present-nil versus present-false, and distinct enum domains
   remain separate. R4's optional-refinement and invalid-variant
   cases are preserved, with detailed branch calculus in 09.04.
8. **Strict Boolean and left-to-right short circuit are part of
   the language, not incidental host behavior.** Changing
   evaluation order can invalidate safe optional dereferences.
   A pure syntactic normalization may not arbitrarily commute
   or flatten expressions; exact rewrite rules belong to 09.04
   and a checked semantics-preservation obligation.
9. **Integer comparison has mathematical semantics.** The
   type-level integer is not a claim of JavaScript Number
   precision, JVM fixed-width overflow freedom or safe
   cross-runtime parsing. A selected codec/boundary must
   guarantee representability or use qualified exact
   arithmetic; rejecting unrepresentable inputs is valid.
10. **Totality is scoped to a valid closed binding environment.**
    Runtime wrong types, missing required fields, exceeded
    budgets or unsupported source do not evaluate to false;
    they reject/incomplete with typed diagnostics. An
    evaluated true result is an instance fact about the
    supplied snapshot, not database authenticity.
11. **The HumanHelp Claim pilot must include real policy.**
    R4 insists on actual role, Request state, membership,
    organization and protected assignment dependencies.
    The open-status conjunct cannot be silently promoted
    into full Claim certification. Nor can source-derived
    proof coverage silently ignore promised Reassign.
12. **Positive and adversarial cases must share the same
    enforcing boundary.** Type checker must accept a
    genuinely legal rule and reject incompatible operands;
    the Choreo gate must reject valid-but-unavailable
    distributed use, and the trusted model must enforce
    current mutation authority even when the typed
    predicate was true earlier.

## Current Gesso implementation — inspected, not executed

- `src/gesso/assurance/rule.clj` is the v1219
  closed syntax constructor, `check-rule!`. It
  accepts only recognized expression constructors
  and exact reader declarations and explicitly
  does **not** typecheck, interpret, prove or
  authorize. Its concrete finite literal-set profile
  rejects empty sets, non-plain collections and
  executable metadata, and recommends
  `clojure.edn/read-string` instead of reader eval.
- `src/gesso/assurance/rule_type.clj` is the
  v1221 `check-rule-type!` constructor. It requires
  an exact reader-type map, nominal enum identity
  and nonempty domain, independent optional/
  nullable flags and path-sensitive flow facts.
  Under the *current* baseline, numeric ordering
  is only for nonnullable integers, not strings,
  dates or arbitrary Clojure `Comparable` values.
- `src/gesso/assurance/rule_eval.clj` is the
  v1223 interpreter `evaluate-rule!`, using
  a typed plain persistent binding map,
  explicit absence/nil semantics, strict
  Boolean control and exact Clojure integer
  comparisons. It deliberately **cannot**
  attest to snapshot provenance, external
  data correctness or permission to commit.
- `src/gesso/assurance/rule_normalize.clj`
  normalizes the actual original rule and
  type declarations before computing a
  source-relative fingerprint. It equates
  mathematical integer representations and
  map/set order but preserves operand order,
  nominal types and optional/nullable flags.
  It returns an unadmitted structural report.
- `src/gesso/assurance/opaque.clj` retains
  typed input/output and declared effects
  for ordinary Clojure or external policy
  used beyond this AST; such declarations
  do not prove complete confinement,
  termination or purity.
- `test/gesso/assurance/rule_test.clj`,
  `rule_type_test.clj`, `rule_eval_test.clj`
  and `rule_normalize_test.clj` contain
  source-written positive and mutation tests
  for strict arity, unknown readers,
  enum mismatch, optional/null guard order,
  exact large-integer behavior, binding
  rejection and conservative identity.
  Source inspection is **not** evidence
  these test suites ran or passed during
  this document revision.

The actual current implementation still
has open original-Clojure-source elaboration,
arbitrary host-function conformance,
browser/CLJS numeric and string-codec
qualification, real Request/Organization
source completeness and source-to-XTDB
physical correspondence requirements.
The normative section intentionally
does not pretend these are already proven.

## Concrete acceptance and counterexample corpus

1. Valid source-owned open-state conjunct on Request
   status `:open` parses, typechecks and yields true
   on a qualified binding.
2. R4 invalid `(< request.status 10)` maps to a
   nominal enum/integer type rejection, not
   a false Boolean value.
3. Status variant `:completed` instead of
   persisted `:done` is rejected as a value
   outside the closed RequestStatus enum.
4. Unknown, undeclared or unused reader
   declarations reject with exact source path.
5. Optional read before `:present` rejects;
   the same read after dominating presence
   is accepted on a valid path.
6. Present nil and present false are distinct
   from absent; nullable numeric comparison
   without non-nil refinement rejects.
7. Incorrect equality across two differently
   named closed enums cannot become valid
   because their raw keywords look alike.
8. Heterogeneous set or unsupported empty
   baseline set rejects rather than guessing
   its type and membership semantics.
9. An invalid arity, unsupported form,
   reader-eval payload or custom-collection
   object does not cause host execution.
10. Huge AST, literal, reader or set exceeds
    the selected budget with a typed
    incomplete/rejected result, not success
    or a hidden unchecked fallback.
11. Left-to-right `:and` and `:or`
    preserve safe optional reads; a
    reordered unguarded comparison is
    rejected at the type boundary.
12. An integer outside the selected
    portable runtime representation
    rejects on encoding/decoding or
    uses a separately qualified exact
    codec without rounding.
13. Rule evaluation true for R17
    remains insufficient to authorize
    a browser that lacks trusted
    observation or a stale helper at
    current Request commit time.
14. Complete Claim checking includes
    actor, Membership, Organization
    and assignment absence under
    guarded semantics, not only status.
15. Deleting promised Reassign from
    source and derived rule coverage
    still fails independent HumanHelp
    positive capability acceptance.
16. A legitimate Clojure policy
    outside the AST remains usable
    under a typed opaque contract;
    the stronger proof profile
    exposes its open implementation
    and effect-confinement premises.

- 09.01 owns the governing separation among
  original-source semantics, executive
  interpretation, proof kernel and
  independent product obligation.

  conditional evidence and source-derived
  ledger completeness.

  rule syntax, intrinsic type/evaluation

  portable interpretation boundary.

  09.09–09.12 own certified construction,

  HumanHelp Claim/Reassign/Refresh
  product path; successful intrinsic
  rule checks cannot replace it.
