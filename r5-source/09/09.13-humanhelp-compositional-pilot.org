** HumanHelp compositional certification pilot
:PROPERTIES:
:CUSTOM_ID: req-humanhelp-certification-pilot
:END:

HumanHelp Request Claim is Gesso's first required substantial end-to-end
*compositional assurance pilot*. Its purpose is to demonstrate inspectable
inheritance of real public model commitments through rules, authoritative
operations, Choreo, projections, executable plans, whole-application assembly,
installed host/browser realizations and a qualified physical user journey.
A toy scalar transition, an isolated checked graph, or a browser test with a
handmade protocol envelope is useful subordinate evidence, not this pilot.

The pilot is built from the same source-owned HumanHelp production model
and example application required by Part VIII, rather than a second,
convenient proof-only Request store, operation catalog or business-rule
machine. It uses the actual public User, Membership, Organization, Location,
Request and RequestAssignment interfaces *where Claim genuinely depends on
them*. The model's private domain, graph, FX and persistence code do not
become application-owned semantic authority merely to simplify extraction.
Cross-model commitments pass through the owning public =*.core= interfaces
and admitted exported contracts.

The pilot must not invent a persisted =:request/helper-id= field, a
=:completed= lifecycle state, or an =organization/claiming-enabled?= Boolean
solely because an example proof is easier with them. Part VIII's canonical
Request lifecycle is =:open=, =:claimed=, =:on-the-way=, =:done= and
=:cancelled=; an active primary RequestAssignment is a separate authoritative
entity with its own history and constraints. A derived view may offer an
equivalent display projection only if its source mapping, eligibility, scope,
provenance and coverage are themselves qualified. Illustrative schema
symbols and sample operation names are not declarations of production facts.

*** The compositional chain and edge categories

The required root is a *real application* proof/evidence graph. Its
conceptual shape is:

#+begin_example
User / Membership / Organization / Location public semantics
                    |                    Request + RequestAssignment
                    +-------------------+------------+
                                        |
                     domain refinements / relationships
                                        |
                      Claim rules + exact scoped premises
                                        |
                     authoritative Claim operation contract
                                        |
                              global Choreo source
                           /                      \
                  helper projection         authority projection
                           \                      /
                         compatible executable plans
                                        |
                   source-owned ApplicationAssembly
                     /               |            \
          browser build/plan    transport/route    issued server
               / asset              / host         executor/model
                     \               |            /
                          actual deployed realization
                                        |
                     Claim transaction / durable outcome
                                        |
                permitted acquisition / scoped DOM adoption
                                        |
                   evidence-root + independent product oracles
#+end_example

This diagram contains *different kinds of edges*. Admitted
justification/guarantee dependencies must be well-founded.
An =implements= or =installed-with= edge needs source and physical
correspondence evidence; a runtime event edge needs actual observation,
actor and execution lineage. A matching node or proof-DAG hash cannot
establish those other kinds of relationship. Retry, reassign, reconnect
and subscription loops belong to the runtime graph, not circular proof
justification.

Every source-relative proof node identifies its normalized subject,
original producing declaration, selected checker/profile semantics,
required exported guarantee, actual dependencies, used premises and
evidence class. Every realization node additionally identifies the
selected callable/route/provider/build and the installation generation
to which its claim applies. A later observation node identifies the
specific command, principal, operation target, physical attempt, source
and scope of its observed result. Copyable root reports explain these
links; they are not capabilities or certificates in their own right.

*** Independent Claim obligation manifest

The required obligation set is derived from the *original* source and
requested assurance profile, then checked against the supplied evidence.
A well-formed graph whose developer omitted Reassign, a writer,
a required Claim premise or an outcome branch must not pass because
the remaining subset happens to be consistent.

| Subject | Required source/realization obligation |
|---------+----------------------------------------|
| Public model truth | Actual Request, RequestAssignment, User, Membership, Organization and Location public interfaces are source-owned; real field and status identities and primary/collaborator assignment roles are preserved. |
| Input and identity | Exact Request target, operation and canonical arguments, authenticated principal, target helper when distinct, stable command C42 and separate H1/H2 transport/execution identities. |
| New-command eligibility | Current Request lifecycle, actor's effective Membership, relevant Organization/Location policy and relationships, target eligibility, active primary/cardinality constraints and all actual policy dependencies. |
| Abstract state machine | Reachable initial states, every declared Claim-related invariant, all relevant operations and guarded/frame transitions, including other protected writers and initializers under their actual declared scope. |
| Atomic incorporation | Qualified same-transaction guard on actual protected prestate/absence conditions; Request/assignment changes, canonical command record and required durable publication intent satisfy the selected atomicity contract. |
| Rejection/uncertainty | Malformed and unauthorized invocation remain distinguished from a model's justified new-command rejection, existing compatible incorporation, and unknown submitted outcome. |
| Compatible replay | Original command/target/actor/arguments and historic disposition are resolved without a second incorporation; current outcome disclosure is checked independently. |
| Operation interface | All four =:committed=, =:rejected=, =:already-incorporated= and =:commit-unknown= variants and their exact provenance/payload meanings remain represented. |
| Global Choreo | Roles, branch discriminator knowledge, protected communication, causality, non-escalation, outcome/unknown-recovery branches and logical command continuity satisfy the admitted global semantics. |
| Projections/plan | Helper and authority projections preserve their qualified global contract; issued runtime plans cover actual admitted outcomes under their declared refinement/correspondence scope. |
| Installed application | Real rendered enabled Claim control, generated browser payload, actually served/loaded assets, trusted route and issued server executor all bind to one source/assembly generation. |
| Physical writer/host | Biff/Ring authentication, request mappings, actual XTDB gateway, other effect-capable routes, background/admin/import/migration writers and source-to-writer coverage meet the claimed profile. |
| Historical outcome | Actual command/transaction provenance, pinned compatible readback, durable retention and truthful reconciliation are distinguished from a current Request snapshot or merely matching ledger fields. |
| Browser adoption | Permitted authoritative card acquisition, source/target-specific HTMX completion, provisional retirement, current owner and adopted cohort scope are observed separately. |
| Assumptions/release | Every opaque policy, provider/atomicity, compiler, host, writer coverage, progress/retention and proof-kernel premise is accounted for with its profile, expiry and nonclaim. |

No blank or fabricated item may be marked discharged merely to populate
the manifest. A checked catalog is a claim about its specified abstract
operations; physical writer completeness needs independent qualified
inventory/correspondence, and a root must not borrow broad installed
coverage from a caller-selected set of writer names. An inherited open
premise remains linked to the *particular guarantee* using it, rather
than disappearing into one undifferentiated list of trusted dependencies.

*** Worked Claim history: actor, assignment and atomic boundary

Let Alice be an authenticated, currently eligible helper, and R17 an
authorized Request whose public model says =:open= with no active primary
assignment. Alice's adopted card carries the correct Request identity
and a qualified observation frontier X17. X17 is not proof that the
Request, Membership or Organization state is still eligible at a later
transaction. The actual rendered Claim affordance binds the Choreo
operation, compatible executable plan, concrete DOM target and current
asset/assembly generation, not a browser-derived authorization token.

1. The real browser control generates logical command C42 and an
   independent physical execution/transport attempt. The test does not
   fabricate =__gesso_live_optimistic_command= or the wire envelope
   on behalf of a disabled or broken control. A lower-level API fixture
   that constructs such input is a separately labelled *route-only* test.
2. The installed server route selects the admitted operation and obtains
   Alice's authenticated principal from trusted ingress. It checks
   canonical Request/command arguments and source compatibility;
   the browser role =:helper= is not evidence of effective helper
   Membership or authority to act for a different person.
3. A compatible prior C42 binding is reconciled first under its
   retention and disclosure rules. Otherwise the real public Request
   operation applies the full current guard to actual Request,
   RequestAssignment, Membership, Organization/Location and command
   exclusion dependencies at the qualified atomic boundary. A
   pre-read, rendered card or post hoc comparison is not that guard.
4. At most one previously open R17 can acquire a newly active primary
   assignment from competing different commands. An authorized new
   Claim establishes the required Request/assignment, command
   disposition and publication-intent facts under its actual selected
   atomicity and writer contract. A rejected competitor must not
   leave a partial primary assignment.
5. The participant settles only from the reported authoritative outcome
   and justified acquisition. The backend's four dispositions map
   explicitly to its separate =:accepted=, =:rejected= and =:unknown=
   presentation statuses. HTTP 200, optimistic “Claiming…”, copied
   certificate or SSE delivery does not mean incorporated.
6. The installed target/card read and physical DOM completion give
   actual scoped adoption under the permitted acquisition and current
   owner/target identities. A newly committed Request/assignment
   confirmed by authorized fresh read/reload is independent evidence;
   a visible provisional badge is not.

If Bob, also eligible, races for R17 using a different command, the
qualified model guard must preserve one-primary safety under the actual
backend concurrency semantics. Concurrent clicks or success-shaped
responses without contested guarded incorporation are not a useful
physical race oracle. If Alice's Membership is revoked after the card
was rendered, a new Claim must be rejected at the real trusted model
boundary; the old client affordance does not grant authority.

If C42 incorporated but its response was lost, Alice can have an
unknown presentation while the historical transaction is already
committed. A compatible retry retains C42 and its original binding,
resolves its *historical* result where retention/qualification permits,
and must not perform a second Request assignment. If a later legitimate
Reassign changes the current helper, C42 may still have a true past
incorporation and a different currently read Request card. An
expired command horizon can leave honest indeterminacy; it cannot be
silently converted to rejection or a fresh command.

A committed transaction followed by broken HTML, failed OOB install,
missing Live delivery or rendering rejection stays committed. Recovery
requires separate current disclosure, acquisition and physical
installation rights. Neither browser cleanup nor a later mismatch
report can retroactively undo the domain write.

*** Other real writers, Reassign and invariant preservation

The pilot's main safety proposition may be expressed as “at most one
active primary RequestAssignment for a Request in each relevant
authoritative state,” under exact Request/assignment model semantics.
Its source-derived induction covers shared initialization and *every*
operation that can change the protected aggregate in its selected
catalog. That includes new Claim, Unclaim, lifecycle completion or
cancellation, manager Reassign, collaborator/assignment changes,
Request edits where relevant, administrative repair and any additional
registered protected mutation. The source checker must not quietly
shrink the catalog to Claim to make the induction pass.

Physical correspondence is more demanding. Effective Membership and
Organization policy may be changed by writers outside the Request
operation's own namespace; an invariant about *current helper
eligibility* must either include those transitions and repair/rule
semantics, narrow the invariant to what the operation actually
enforces, or retain the external interference premise explicitly.
The actual host's discovered writer inventory is not a proof that all
processes, raw XTDB paths and external writers were found.

For Reassign, the manager actor, selected replacement helper and
existing primary helper are distinct. A real approved target
selection and current helper/manager Membership are revalidated
at incorporation, and the old primary's historical end and new
primary's activation are represented by one admitted operation
under its actual atomic guard. “Take over” is not automatically
the same semantic action. The pilot's Claim success does not
establish these independent Reassign positive and negative gates.

Any abstract state-machine model checked by Recife, Quint/TLA+ or
another checker is generated or linked from admitted Gesso semantics
with original-source coverage and checker trust premises. Application
developers are not required to maintain a second hand-written
specification or copy proof identities. An exact finite witness
over the stated bounds and a conditional induction over the
declared catalog retain those scopes; neither alone proves the
real XTDB prestate, all physical writers or host execution.

*** Browser and selective multi-client realization

The vertical Claim slice must traverse the real issued browser plan,
compiled/served asset and generated command, installed Ring/Biff
route, public model call, justified outcome and card installation.
The strong profile additionally needs qualified evidence of
the *actual installed* handler and loaded browser runtime. A copied
manifest stamp, an in-process issued callable not installed in the
server, a deterministic source replay or a synthetic successful
request cannot substitute for these occurrence-level facts.

The proving application also exercises a separately correlated Create
under its real production model: the creator may immediately install
a permitted local new Request/card S without importing unrelated
remote collection revision R. For another participant, remote creation
and lifecycle changes, including changes to an already-visible
Request, remain advisory. The user explicitly grants a scoped
one-Refresh acquisition; actual provider coverage and completed
target installation discharge only the obligations it covers.
A new advisory, pending refresh debt, a newer-looking basis token or
a single card is not an implied whole-board read grant.

Search, sort, mine-first/unclaimed-first, terminal visibility, details,
scroll/focus and local draft continuity operate on justified adopted
cohort state, never as excuses to silently pull remote changes.
Unknown/rejected Claim and refresh failures retain usable bounded
recovery and correct owner retirement. The pilot may test a selected
Claim slice without declaring that the full rich board or
response-flow product requirements have been accepted.

*** Three independent conclusions and final product gates

The pilot reports three independently evaluated conclusions:

1. *Semantic certification:* the model/rule/operation/Choreo/
   projection/plan construction establishes its exact
   source-relative propositions with scoped proof evidence,
   checked complete dependencies and still-open assumptions.
2. *Production realization:* issued functions and actual
   installed host, physical writers and transaction/outcome,
   generated and loaded assets, real browser affordances and
   adoption relate to that construction with authenticated,
   correctly scoped correspondence or explicit open premises.
3. *Independent product acceptance:* real eligible browser-originated
   interactions and current production Request/assignment truth
   satisfy the independently selected product behaviors,
   adversarial controls and fault/recovery scenarios.

Each conclusion has different failure modes and evidence owners.
A green browser test cannot fill a missing abstract induction or
projection proof; a complete abstract theorem cannot install a
handler or prove the Claim button works. A successful isolated
Claim pilot is a milestone, not the completion of HumanHelp.

Part VIII independently requires eligible positive cases for
Create, Claim, Unclaim, Mark on the way, Complete, Cancel and
manager-target Reassign, plus authentication, rich-board continuity,
two-client advisory/Refresh, recovery, actual generation/host and
assurance qualification. Its fourteen separately specified
completion gates remain product requirements irrespective of the
number of operations the generated catalog currently contains.
Deleting a required operation from both program and proof cannot
turn a missing feature into a success.

The HumanHelp response-flow decision remains a genuine open
product decision under [[#decision-humanhelp-response-flow]].
The pilot must not invent a messaging/contact policy or equate
“response” with Claim simply to make the root report green.
If a product authority later selects a precise response
interaction, that separately versioned choice and its eligible
positive, negative, privacy and recovery tests enter the
original-source closure and independent product acceptance.

*** Generated root report and certificate boundaries

One readable *illustrative* root report is:

#+begin_src clojure
{:root {:application :humanhelp/example
        :operation :request/claim
        :assembly/ref assembly-ref
        :profile/ref profile-ref
        :source/ref original-application-source}
 :claims [{:claim/ref typed-claim-rule
           :evidence/ref checked-rule-evidence
           :premises []}
          {:claim/ref unique-primary-preservation
           :evidence/ref conditional-induction-evidence
           :premises [catalog-coverage-premise
                      implementation-conformance-premise
                      physical-writer-premise
                      backend-guard-premise]}
          {:claim/ref issued-to-installed-claim-path
           :evidence/ref scoped-host-correspondence
           :premises [router-adoption-premise]}
          {:claim/ref real-browser-claim-scenario
           :evidence/class :tested
           :evidence/ref actual-two-helper-run}]
 :dependency-closure/ref original-source-derived-closure
 :obligation-ledger/ref complete-claim-obligations
 :selected-derivations/ref checked-proof-choices
 :open-premises/ref exact-claim-scoped-premises
 :application-evidence/ref installed-host-and-asset-evidence
 :product-gates/ref independent-humanhelp-capabilities
 :unresolved-obligations/ref actual-open-items
 :applicability/ref current-build-host-provider-scope
 :decision/ref profile-admission-decision}
#+end_src

These maps depict *readable output*, not user-authored certificate
input or proof of existing implementation behavior. References
must resolve to trusted subject-bound records with claim, checker
version, source/provenance, scope, open assumptions, evidence
mechanism and actual result. A label like =:tested= must identify
the real executed scenario and its complete allowed assertion,
not merely a test name or passing definition. A successful
typing claim with no domain premises does not eliminate its
proof-kernel interpretation and trust assumptions.

The root reports source/type/operation evidence, projection and
plan guarantees, implementation and host bindings, real
command/transaction/read/DOM evidence, policy and provider
premises, untested product capabilities, and every unresolved
required obligation separately. Admission is a typed decision
under the explicitly selected profile, not a global Boolean.
An accepted conditional root carries its premises and does
not grant runtime authorization. An unfinished source-to-host
link or unselected product response cannot be hidden behind
an artifact-wide =:accepted= stamp.

*** Paired acceptance and counterexample corpus

The pilot must admit genuinely valid source/physical/user
scenarios and reject nearby defects at their *actual first*
enforcing boundary. The corpus includes at least:

- valid public Request/RequestAssignment schema and Claim
  rule; missing/renamed status, invented helper field,
  incompatible relationship cardinality and wrong model
  namespace must reject or become explicit unsupported scope;
- a complete original operation/invariant catalog with
  Claim/Unclaim/Reassign cases; a pruned but structurally
  valid proof DAG cannot pass source-derived coverage;
- valid Organization/Membership/Location guarded Claim;
  stale Membership, wrong tenant, fabricated browser helper
  status and a manager acting for an ineligible target
  cannot pass the protected production boundary;
- a qualifying two-helper same-Request race with at most
  one new primary; two independent pre-read-and-write
  paths or a partial Request/assignment mutation fail;
- actual C42 incorporation, lost reply and compatible
  historical reconciliation; new-command retry,
  unsupported record retention and post-Reassign
  current-card substitution cannot manufacture history;
- source-issued and actually installed executable
  routing and browser bytes; uninstalled handler,
  copied certificate, wrong Choreo projection,
  changed asset or anonymous HTMX fallback cannot
  meet the strong profile;
- real completed target/card adoption with proper
  stale-target cleanup; HTTP success or provisional
  badge cannot count as installed state;
- legitimate creator-local S and remote advisory-only R
  with one eligible user-granted Refresh; an automatic
  remote whole-board adoption, second ungranted read
  or local S erased by older R fails the declared policy;
- conditional proof preserving opaque model/provider
  assumptions and actual writer limitations; a
  forged status map, dropped premise or fabricated
  production observation cannot issue a stronger
  certificate;
- independent positive Unclaim, Mark-on-the-way,
  Complete, Cancel, Reassign, board interaction and
  eventually selected response flow; a reject-all
  checker, disabled controls or a reduced authored
  catalog cannot satisfy the missing product gates.

The expected disposition and first semantic, model,
source-coverage, construction, installation,
transaction, physical effect or independent
product-test boundary are specified *before* each
mutant. An abstract counterexample is not an
authenticated production history, and one real
successful browser trace is not universal
refinement over all deployed executions.
