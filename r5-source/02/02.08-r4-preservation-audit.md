# R5.1 Part II — 02.08 Trust Boundaries and Adversarial Browser Actors

**Baseline:** R4 `main`, Part II, “Trust boundaries and adversarial browser
actors.” **Candidate:** `r5.1` source section 02.08.
**Status:** focused R4 preservation review; not a proven adversarial-security
property, physical deployment audit, or completed Part II reconciliation.

## R4 requirements retained

- The browser is a fully untrusted participant; it may alter the projected
  code, machine, DOM, fields, command envelope, provenance markers, local
  result, proof sidecar, and correlation data.
- A browser can propose an operation but cannot assert its own principal,
  role entitlement, authority, permission, authoritative fact or successful
  server continuation.
- Trusted server code must authenticate, resolve admitted operations, validate
  current policy, protect dynamic guards at the authoritative transition, and
  produce appropriately scoped settlements/progression.
- The security target concerns authorized authoritative transitions and
  protected disclosure, not stopping a user from lying in their local UI.
- Hidden buttons/cards and signed but non-authorizing tokens are not access
  control; protected reads and Live subscriptions require server authorization.
- Browser proof artifacts cannot be authority-bearing credentials.
- Ordinary trusted Clojure host code is not sandboxed: deliberate lower-level
  writers and bypasses invalidate any dependent assurance unless excluded or
  retained as explicit trusted premises.

## R5 strengths preserved

- Differentiate compatible historical command replay under current disclosure
  from guarded new incorporation, including concurrent attempts, uncertain
  commit status, and transaction-current authorization dependencies.
- Protect command identity, canonical arguments, authority and principal
  scope rather than trusting client-supplied typed structures.
- Explicitly protect subscription metadata, counts, existence hints and
  command-response disclosure; spell out policy after revocation.
- Scoped effect capabilities, writer inventory and application assurance
  distinguish local construction checks from actual deployed enforcement.
- Trusted-host bypass assumptions can affect *all* dependent invariants,
  not merely the bypassing invocation.

## Changes in this revision

1. State that trusted principal authentication, domain authorization and
   current disclosure are independently required even when client values
   have valid structure or proof metadata.
2. Clarify branch-specific replay/new-incorporation treatment and explicitly
   separate readback agreement from physical transaction causality.
3. Mark the sample `C42`, `R` and `X17` as schematic; client-proposed
   observed basis is not an authenticated observation witness.
4. Add later read/stream/response/error disclosure boundaries and a scoped
   existence-oracle requirement without claiming universal side-channel proof.
5. Clarify that source inventories, locally installed Biff wrappers and
   one-shot writer reports do not establish deployed-handler adoption,
   external-writer exclusion or universal model refinement.
6. Provide an eight-case adversarial coverage matrix including identity
   forgery, command rebinding, authorization races, fabricated progression,
   subscription drift, proof/capability spoofing, unknown commits and
   bypassing physical writers.

## Current Gesso correspondence and open premises

- `gesso.model.command-resolution` describes a structural durable command
  record and explicitly relies on trusted application authentication,
  authorization, accurate outcomes and disclosure decisions.
- `gesso.assurance.proof.checked-biff-host-adoption` and
  `xtdb-gateway-biff-request-mediation` establish bounded local handler/
  request mediation while listing deployed server adoption, host coverage,
  principal/source authorization and direct writer bypasses as open.
- `gesso.assurance.proof.xtdb-gateway-writer-coverage` establishes narrow
  identity-registered callback correspondence, not comprehensive physical
  writer or transaction causality proof.
- `gesso.assurance.proof.application-assurance-report` retains open
  obligations for deployed adoption, physical writer completeness and
  universal abstract-to-physical refinement.
- None of these scope-limited reports should be presented as complete
  hostile-browser security certification.
