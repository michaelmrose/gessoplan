# R5.1 Part II — 02.05 Logical Identity and Physical Realization

**Baseline:** R4 `main`, Part II, “Logical identity and physical realization.”
**Candidate:** `r5.1` source section 02.05.
**Status:** one focused normative preservation review; not an executable proof,
release gate, or completed Part II cross-section acceptance.

## R4 requirements preserved

- Logical identity is not inferred from physical identity. Role, principal,
  actor, authority, semantic operation, command, protocol execution,
  choreography, projected plan, exact artifact, logical target, physical
  resource, transport attempt, assembly generation, deployment and host are
  distinguishable where relevant.
- A retained command may be reconciled across new HTTP attempts, host changes,
  or a new admitted execution without equating those identities.
- Finding a domain Order does not automatically establish incorporation of
  the particular checkout command.
- Plan compatibility is different from exact executable-artifact identity;
  neither label equality nor approximate version order proves correspondence.
- A deployment and its hosted assembly do not substitute for command,
  execution, or physical resource identities.
- The HumanHelp domain `:request-id` is not an HTTP request identifier; stale
  callback and replaced DOM-node ownership must remain distinguishable.

## Stronger R5 design retained

- Command identity binds canonical semantic arguments, principal, operation,
  authority, retention horizon, and safe retry or reconciliation conditions.
- New execution creation requires admitted runtime authority and compatibility
  rather than a fixture changing `:execution/id` or `:artifact/id`.
- Backend submission-attempt identities and scoped writer capability instances
  are distinct from semantic-command deduplication and transport correlation.
- Exact artifact evidence is tied to physical emitted bytes and qualified
  build provenance; compatibility may be narrower or broader for specified
  uses, but cannot silently substitute for exact identity.
- Logical target continuity also carries actor/principal/projection scope,
  not just a CSS ID preserved across navigation or account switching.

## Changes in 02.05

1. **Remove a misleading SHA-256-looking placeholder.** The example artifact
   is explicitly illustrative. Actual Gesso artifact receipts require a real
   digest of emitted bytes and corresponding manifest/build evidence.
2. **Keep domain attribution out of fixture mutation.** An `assoc` placing
   `:order/id` on a map does not link an Order to command C77.
3. **Label schematic recovery APIs and proof limits.** The recovery and command
   reference function names in the example are not assertions that those Vars
   exist or that an inspection map confers execution authority.
4. **Qualify artifact correspondence.** Byte/hash agreement is not alone a
   theorem about the compiler, runtime semantics, or browser trustworthiness.
5. **Qualify physical readback.** Process-local submission-return identity and
   pinned domain/command/ledger co-observation cannot, on their own, establish
   transaction causality, authenticated arguments, or permission to retry.
6. **Make mismatch behavior testable.** Preserve explicit negative cases for
   incompatible command rebinds, expired records, retired callbacks, stale
   artifacts, unqualified authority reincarnation, and unproven Order links.
   Diagnostics must distinguish unknown, incompatible, unowned, unauthorized,
   and not established instead of claiming an authoritative rejection.

## Current Gesso correspondence

- `gesso.live.browser.build` records SHA-256 plus a stamp/receipt of generated
  browser artifact bytes; its own contract distinguishes raw emitter publication
  from the supported build path embedding an application-derived manifest.
- `gesso.live.browser.adapter` rejects stale effect generations and treats
  opaque authoritative progression as externally witnessed, not inferred.
- `gesso.assurance.proof.xtdb-gateway-command-outcome-bridge` (v1622) expressly
  limits its result to bounded co-observation/value agreement. It does not
  establish trusted request identity, transaction causality, replay permission,
  or browser settlement.

`req-logical-physical-identity` anchor remains unchanged. This audit
