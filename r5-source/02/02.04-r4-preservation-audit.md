# R5.1 Part II — 02.04 Roles, Principals, Actors, Hosts, and Authorities

**Baseline:** R4 `main` Part II section "Roles, principals, actors, hosts, and authorities."
**Candidate:** `r5.1` numbered source section 02.04.
**Status:** one focused normative editorial review; not a formal theorem,
runtime qualification, or completed whole-Part-II reconciliation.

## R4 guarantees retained

- A choreography role is distinct from an authenticated principal, concrete
  actor, physical host, and semantic authority. None is an authorization grant
  merely by carrying an identifier of another category.
- One principal may act through independent tabs, actors, and executions with
  different knowledge; each protected invocation requires appropriate trusted
  bindings rather than inferred privilege from an actor label.
- Hosts are replaceable physical realizations. Neither the same host nor
  different hosts imply sameness or difference of semantic authority.
- Authority is a semantic locus governing facts and permitted transitions,
  not the process executing them or necessarily a single XTDB document.
- Important retry/failover facts survive only through qualified authoritative
  state or admitted evidence, not process-local memory.
- R4's revocation example remains an explicit negative-case requirement:
  identity continuity does not imply continuing permission, and diagnostics
  should report category-specific mismatches.

## R5 improvements preserved

- `:principal-context` can distinguish authentication/session instances for
  the same principal without prescribing one universal session epoch.
- `:actor-host` and `:authority-host` are distinct, as are transport attempts
  and stable semantic command identities.
- Continuity of a named authority across failover or migration is conditional
  on authoritative-state, command-record, issuer and backend compatibility;
  mere reuse of the authority label across database incarnations is inadequate.
- Compatible replay, current disclosure permission, and new incorporation
  authorization are separate questions.

## Changes in this revision

1. **Projected role does not grant authority.** Clarify that actor role
   realization needs an admitted binding, trusted principal admission, and
   dynamic protection at the authoritative incorporation boundary.
2. **Identity fields do not authenticate themselves.** Reports must name the
   issuer and trusted origin of principal, subject, command-argument and
   authority bindings. Equality of caller-provided maps remains structural.
3. **Illustrations are not credentials or supplied APIs.** Identify all
   prebound example fixture symbols and mark `auth/current-principal!` and
   `document-model/save!` as application-owned schematic contracts.
4. **Restore operational negative cases.** Make R4's revocation example more
   precise: revoked new action, concurrent revocation, prior incorporated
   replay, incompatible command reuse, indeterminate responses, and session
   or host changes each require distinct classifications.

## Intentional supersession of R4 presentation

R4 illustrated revocation using a standalone `admit-editor-operation!`
predicate. That demonstrated an important denial case, but a handler-level
check alone cannot establish transaction-current authorization or race-safe
commit behavior. R5's public-model and qualified incorporation contract is
retained instead. The revised section preserves the adverse scenario without
reintroducing an insufficient handler check as a putative proof of protection.

## Implementation correspondence and cross-part obligations

- **Gesso `application-assurance` v1622:**
  `xtdb_gateway_command_outcome_bridge.clj` explicitly does not authenticate
  principals, arguments, or the reported request outcome and does not establish
  transaction causality. The revised normative requirements do not assert
  that this implementation gap is closed.
- **Part IV:** stable command binding, new-incorporation dynamic guards,
  replay/result disclosure, retention, and indeterminate command outcomes.
- **Parts VI–VII:** browser actor/host lifecycle, acquisition rights, real
  application/route/handler/writer coverage and trusted request context.
- **Parts IX–X:** evidence issuer/scoping, typed obligations, physical
  correspondence, backend qualification and explicit unsupported premises.

No R4 normative identity or revocation obligation was intentionally discarded.
The `req-semantic-identities` anchor is preserved. This audit is documentary
and does not prove that application code passes these conditions.
