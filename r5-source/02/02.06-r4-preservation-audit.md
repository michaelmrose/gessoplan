# R5.1 Part II — 02.06 Resource Instance Identity

**Baseline:** R4 `main`, Part II, “Resource instance identity.”
**Candidate:** `r5.1` source section 02.06.
**Status:** one focused normative preservation audit, not a completed
whole-Part-II review or implementation proof.

## R4 requirements preserved

- A logical slot may survive physical resource replacement; a callback owned
  by the retired instance cannot mutate the replacement.
- Resource-instance identity is distinct from protocol execution, logical
  target, authoritative basis, principal, command, artifact, and other
  independently checked semantic coordinates.
- Distinct opaque instances suffice for equality where no ordering is required;
  any scoped counter must not alias a retired instance while late events can
  remain possible. Cross-scope numeric ordering is not automatically meaningful.
- Refresh A returning after replacement by B must be classified as retired,
  even if execution and authoritative basis still match.
- An authoritative basis advance does not itself replace a resource instance.
- The board refresh example distinguishes owner correlation from full
  acquisition admission; event fields alone cannot establish authorization,
  provenance, scope, or installation rights.
- A shared advisory belongs to its subscription/source contract and cannot
  be assigned to whichever private command execution is active.

## Superior R5 design retained

- Admission checks originate from registered acquisition and subscription
  contracts, not a caller-selected `:require` set or an event-provided selector.
- Event class, query/temporal context, visibility, principal context, source
  provenance, progression, and installation rights remain explicit.
- Event data and even a matching owner ID do not establish trustworthy source.
  A shell must recheck owner and installation applicability when effects
  actuate, and an allowed installation is not equated with physical completion.
- Tokenless shared advisories do not invent an authoritative lower bound;
  their supported read/source-fence policy remains a separate obligation.
- Content provenance does not substitute for HTML/content safety.

## Changes in this revision

1. Explicitly require resource/producer registration to ground instance IDs;
   equal values in untrusted event maps are insufficient provenance.
2. In the schematic acquisition example, resolve the contract using trusted
   runtime registration rather than passing the event to contract selection.
3. Mark illustrative acquisition and shared-advisory functions as proposed
   semantic interfaces, not necessarily implemented public Gesso Vars.
4. Add an adversarial race matrix covering retired callbacks, delayed cleanup,
   forged producer or scope, wrong projection/basis, delayed DOM actuation,
   idle shared advisories, and private-to-shared impersonation.
5. Require stale callbacks and cleanup not to disturb a successor's state.

## Implementation correspondence and limitations

The `application-assurance` branch includes a pure
`gesso.live.browser.adapter` transition system with execution and request
generation gates, target retirement, fragment requests, continuity slots,
and optimistic settlement. The imperative `gesso.live.browser.shell` performs
physical effects and asynchronous completion dispatch. The existence of these
components is not proof that every listed race or hostile-browser condition is
satisfied by the current implementation. The registered-producer and actuation
obligations require specific runtime tests and assurance evidence.
