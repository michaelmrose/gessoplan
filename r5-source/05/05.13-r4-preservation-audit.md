## R4 requirements retained

- A browser-side proof sidecar may not supply principal identity,
  current model authorization, an authoritative observation,
  permission to read protected data or subscribe to protected
  Live invalidation sources. Its only runtime purpose is
  optional explanation; server admission remains source-owned.
- Diagnostic data can leak source/policy/private information.
  Production may omit the sidecar while preserving the same
  canonical executable semantic payload and all mandatory
  model/proof/assembly gates.
- Exact plan identity and its associated sidecar alone are
  insufficient for global source semantics, proof applicability
  or shipped browser artifact correspondence. An actual
  physical installed/served path must be covered by the
  promised application closure.
- Sidecar observation is one-way. A corrupted, missing or
  throwing optional observer cannot authorize an otherwise
  forbidden operation or block required semantic work under
  the stated bounded/nonblocking premises.
- R4's canonical runtime is one compact ExecutablePlan.
  The finished design does not depend on optimizing a
  second rich proof-annotated runtime away.
- R4's final requirement is physical/build correspondence
  with the plans actually deployed, not agreement of
  two self-asserted stamps or a passing pure unit test.

## Focused R5.1 improvements

1. **Disclosure boundary:** diagnostic distribution checks
   current principal, Organization/Location or tenant,
   source content, trace values, scope and retention.
   A copied sidecar or prior authorized debug session
   is not permission to disclose again.
2. **No execution authority:** exact diagnostic identity
   cannot grant mutation, model outcome, physical install,
   Live subscription, protected reads or recovery rights.
   Required proof/audit gates remain construction/semantic
   obligations outside optional runtime sidecars.
3. **Installed application closure:** bind the complete
   role/operation inventory, current host-action/route,
   artifact, model trust boundary and actual served/loaded
   build. Static source checks and dynamically inspected
   Hiccup do not cover unexamined alternate entrypoints,
   pre-serialized HTML or later deployment changes.
4. **Independent claims:** Part VII's model correctness,
   closed assembly and independently expected product
   completeness are distinct judgments. Each records
   premises, exact subject, actual evidence, unresolved
   dependencies and counterexamples. None implies another.
5. **Conformance rows repaired:** added diagnostic
   privacy, local/remote adoption, historical Claim versus
   current Reassign, and rejection-all/no-capability
   vacuity to the existing broad negative inventory.
6. **Independent positive product matrix:** seven paths
   cover eligible Authenticate/Create with prompt
   creator-local visibility, Claim/retry, true manager
   Reassign and lifecycle operations, local adopted
   search/continuity, remote R and local S followed by
   one granted Refresh, honest recovery, and separately
   selected response interaction. Part VIII determines
   the expected capabilities, not rendered buttons.
7. **Paired adverse controls:** positive cases require
   real operation/physical completion; negative tests
   must reach the intended boundary, not pass due to
   invalid fixtures or absent UI. Conditional policy
   unavailability is not a substitute for a required
   eligible positive witness.
8. **Precise evidence status:** pure JVM/Node semantics,
   finite proof, Chromium/HTMX physical behavior,
   server/XTDB write/readback, exact deployment identity
   and user-facing product outcome remain separately
   qualified. Unknown budget, provider or asset evidence
   is inconclusive, not accepted.
9. **Separate whole-Part-V reconciliation:** completion
   of all thirteen sectional audits is necessary but
   not sufficient for Part V acceptance; verify joins
   and R4 preservation before independently deciding.
