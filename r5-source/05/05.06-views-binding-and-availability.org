** Views and UI annotation
:PROPERTIES:
:CUSTOM_ID: req-view-operation-binding
:END:

Views declare semantic intent and render prepared presentation. They do not
redefine choreography, duplicate domain authorization policy, or independently
assemble transport/protocol parameters for a managed operation.

The ordinary path is:

1. a public semantic operation and choreography declare the behavior;
2. application assembly resolves its plan, transport, acquisition, settlement,
   server capabilities, and artifact requirements;
3. preparation binds per-render arguments and admitted observation context;
4. the view supplies element choice, labels, classes, layout, and accessibility;
5. the renderer derives a complete managed realization from the admitted binding.

A view may use a prepared binding directly or a concise declaration normalized
through the same preparation boundary. Multiple convenient authoring forms must
not create multiple independent meanings of Claim. The preparation result
records both *which semantic operation is intended* and *which actual entry
mode is offered*. An input-collection entry is not an unbound final mutation;
a temporarily unavailable operation is not an incomplete executable action.
The render-time decision expresses qualified, potentially stale presentation
knowledge. It is not a durable grant to execute an operation after changes to
Membership, Organization, RequestAssignment or other protected state.

*** Binding values versus operation-owned policy

The registered operation owns its choreography, supported realization modes,
settlement mapping, provisional derivation, recovery policy, required resources,
and compatibility constraints. Per-render binding supplies only admitted
variable inputs: subject/arguments, observation references, and target context
where the operation permits them.

Those binding fields have a closed schema. A view cannot override an operation's
plan, timeout semantics, principal authority, rollback policy, or result mapping
by inserting an extra key. Presentation options occupy a distinct checked area;
unknown semantic keys fail with a precise error. Preparing a visible action
cannot silently substitute a second semantic operation or drop the required
choreography mode, route, browser artifact, acquisition or settlement contract
because an available binding happens to contain insufficient metadata. Such
a missing/incompatible construction edge is a typed defect, not a product
policy denial. The plan and its trusted server execution route are derived
from the assembled operation; a view-supplied identifier is never an
independent authoritative registry entry.

For example:

#+begin_src clojure
(defn prepare-request-card [trusted-context admitted-card]
  (let [card (observation/value admitted-card)
        claim (actions/prepare
               trusted-context
               {:operation request-choreo/claim
                :arguments {:request-id (:request/id card)}
                :observations {:request-card admitted-card}})]
    {:request {:id (:request/id card)
               :title (:request/title card)
               :status (:request/status card)}
     :actions {:claim claim}}))
#+end_src

This illustrative preparation path verifies that the observation, argument,
operation, principal context, and target scope agree. It obtains availability
through public model/application interfaces. The renderer does not rerun a
second Claim policy in Hiccup. This initial availability judgment is
*qualified to the preparation observation and context*; an enabled button
does not establish that the later transaction-current guard will succeed.
The public model still owns the current guarded Claim and real
RequestAssignment transition. The browser must not turn a stale visible
Claim into either unauthorized execution or a fabricated terminal rejection.

The prepared affordance need not serialize principal credentials, server
capabilities, or proof objects. When the browser returns binding data, the server
re-establishes trusted principal identity and the required semantic bindings.
Canonical command arguments use the same declared mapping as Part IV; a domain
Request ID must not be confused with =:http-request-id= or another transport ID.

*** Availability, input collection, and construction defects

Prepared actions distinguish legitimate product states from broken realization:

| Preparation result | Meaning and permitted rendering |
|--------------------+---------------------------------|
| Available | A complete admitted entry affordance can be enabled. |
| Policy unavailable | Current prepared semantics do not offer the operation; hide or disable under the declared disclosure/presentation policy. |
| Needs input | A declared interaction must collect further user input before final invocation; the offered input-collection entry path itself is complete. |
| Deferred or dynamically unavailable | A declared prerequisite cannot yet be established; show the contracted pending/unavailable state and recovery path. |
| Construction failure | Required operation, plan, binding, capability, route, or semantic input is missing or inconsistent; reject the incomplete enabled realization. |

These classifications have closed payload contracts. Missing or =nil= entries
cannot silently stand for every kind of unavailability. A product may use a
compact representation internally, but the preparation boundary must establish
which meaning it has.

The categories distinguish *product intent* from *realization evidence*:
policy-unavailable is a model/preparation decision under the specified
disclosure context; needs-input is an admitted and complete entry *flow*
whose final mutation requires additional bound input; deferred names the
missing dynamic prerequisite and its recovery/refresh contract; construction
failure identifies a missing or incompatible mandatory assembly/binding edge.
The same absent value cannot be reclassified as whichever of these renders
most conveniently. Legitimate product non-availability does not count as an
implementation defect, but making an intended eligible capability permanently
unavailable cannot satisfy positive whole-application acceptance. A renderer
cannot downgrade a construction failure into a disabled button, nil action,
ordinary HTMX send or reassuring diagnostic-only success.

A missing Reassign helper ID is not inherently a defect if the action is meant
to open an admitted helper-selection form. That entry action is fully specified,
and final Reassign remains unavailable until its required arguments are bound.
If the application tries to emit the final mutation without a required helper
ID, that is a construction failure. The declaration determines which case
applies; the renderer must not guess.

For the eligible HumanHelp manager's genuine Reassign, the entry flow obtains
a candidate helper list under the actual authorized Organization/Membership
and target-selection contract, permits selection and confirmation, and then
prepares the distinct final Reassign command. The selected helper ID is an
untrusted *argument*, not proof of the helper's current eligibility.
The trusted server reestablishes principal, manager permission, selected
target identity and current target eligibility at incorporation; it guards
the actual primary RequestAssignment replacement/history. A successful
self-Claim or an empty, permanently disabled selector cannot serve as this
positive product witness. When the product's separately promised response
interaction has not yet been assigned a meaning, preparation may not simply
invent Claim as that operation to satisfy the expected capability list.

An inspection action set could look like:

#+begin_src clojure
{:claim
 {:availability :available
  :binding-ref claim-binding-ref}
 :cancel
 {:availability :unavailable
  :reason :policy/not-offered}
 :reassign
 {:availability :needs-input
  :entry-binding-ref helper-selection-binding-ref
  :required-inputs #{:helper-id}}}
#+end_src

The references resolve to admitted objects. A plain map with these fields is not
sufficient. Reasons must obey disclosure policy; a disabled button must not leak
a private Membership or Organization fact. Public reasons may be intentionally
coarser than private admission diagnostics; an unauthenticated or differently
authorized observer cannot infer protected membership, role, account existence
or Request visibility by comparing availability reasons across rendered views.
A disabled or busy control is presentation, never the server's anti-replay,
rate-limit, authorization or command deduplication mechanism.

Preparation validates the complete *declared required* action set for that
rendered surface or product state, including actions the view will hide. This
does not require every possible application operation to be offered on every
page; the independent application capability inventory declares which
operations and input-collection flows are expected in which eligible contexts.
A hidden action cannot conceal a malformed *required* binding, and omitting
an entire expected action from both the preparation code and rendered markup
cannot make it disappear from the external acceptance oracle.

Application assembly must close operation identity, browser plan, compatible
artifact, trusted server entry/route, acquisition, result mapping and effect
realization for the enabled path. Rendered-surface inspection checks the actual
dynamic Hiccup produced, including branches that static enumeration misses
when exercised; it cannot prove that every possible Clojure branch was
enumerated. Separate eligible positive and nearby adverse witnesses test the
complete path from independently declared product intent to real installed
control, user input, trusted model mutation and visible outcome. Tests derived
only from buttons that happened to render cannot detect a missing product
action. Nor may a source-derived report promote its bounded rendered-surface
check into a universal whole-application certificate.

*** Paired affordance and availability acceptance cases

These cases require independently declared product intent and real
construction, not copied inspection maps or a catalog inferred solely from
currently rendered buttons.

| Eligible positive path | Adverse or incomplete variation | Required result |
|------------------------+---------------------------------+-----------------|
| Claim is prepared from a qualified Request observation, rendered with its admitted operation/plan/binding, and later checked under trusted current model guards. | A view recomputes Claim policy from a simplified helper field, or the browser's earlier available state is treated as current authorization after Membership changes. | Preserve one public model policy and operation identity; render-time availability never bypasses transaction-current server protection. |
| A manager opens a complete helper-selection entry, chooses a distinct eligible helper and confirms final Reassign. | Missing target input for a *final mutation* is silently treated as a complete action, or a self-Claim stands in for the Reassign workflow. | The entry may be =:needs-input=; final Reassign needs the bound argument and real guarded RequestAssignment transition, with independent product success evidence. |
| A legitimately policy-unavailable action is hidden under permitted disclosure rules, while required actions are still structurally checked. | A missing route, browser plan, capability or binding is disguised as policy unavailability or a =nil= hidden action. | Product policy and construction defects have distinct typed statuses; incomplete managed actions fail closed, not via ordinary HTMX fallback. |
| A deferred action reports an admitted prerequisite and recovery path without pretending the user can invoke it yet. | A permanently deferred/unavailable control is counted as a successful required product capability, or missing admission is relabeled as deferment. | Preserve truthful deferred state but require an independently eligible positive path for capability-completeness acceptance. |
| The renderer exposes only disclosable availability and accessible busy/disabled status, while the server binds the actual current principal. | Distinct private Membership failures are leaked through reasons, or disabled HTML is used as authorization or command deduplication. | Preserve disclosure scope and real server-side validation; visual state cannot confer or revoke model authority. |

This table defines expected finished-system semantics, not a claim that the
present Gesso view helpers already implement every availability category.
