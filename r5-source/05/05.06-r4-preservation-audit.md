## R4 obligations preserved

- Views annotate a model-owned semantic operation and choose its
  visual treatment; they do not define Claim/Reassign business policy,
  participant authority, choreography or transport semantics.
- A trusted preparation boundary may bind operation identity,
  per-render subject arguments, admitted observation and target.
  Client-returned values do not authorize execution; the server
  establishes principal/authority and current model state anew.
- Operation identity and projected-plan/transport realization remain
  joined across rendering. Incomplete managed bindings fail closed;
  a missing plan cannot silently yield a naked HTMX mutation.
- The view may receive prepared actions rather than recalculate
  Membership/Request rules in Hiccup. R4's hidden-action examples
  explicitly reject treating missing plans or bindings as legitimate
  product unavailability.
- R4's prepared capability is not an unforgeable or durable
  server security credential. Semantic operation identity, even
  when encoded or authenticated, does not supply current permission.
- Whole-application assembly must validate required operation,
  route, loaded browser plan/artifact, runtime and model effect
  correspondence; rendered output alone cannot establish full
  product capability completeness or general formal proof.

## Corrections and precise finished-system contract

1. **Entry mode versus final mutation:** preparation selects a
   complete admitted *entry flow*. A Reassign helper picker can
   correctly report `:needs-input= without final `:helper-id=`;
   emitting the final Reassign mutation without the chosen argument
   is a typed construction failure, not a product denial.
2. **Qualified render-time availability:** an enabled affordance is
   a snapshot under a declared observation/context, not permission
   that persists after current Membership/Organization/Request
   changes. The protected server/model always rechecks.
3. **Closed classification:** available, policy-unavailable,
   needs-input, dynamically deferred and construction failure are
   separate meanings with their own reasons and recovery. A missing
   edge cannot be hidden as policy, `nil`, or ordinary HTMX.
4. **HumanHelp's real Reassign:** positive eligible scenario has
   an authorized manager, a selected different eligible target,
   actual helper selection and confirmation, and protected primary
   RequestAssignment transition/history. An unselected independent
   response-flow product meaning must not be invented as Claim.
5. **Disclosure and security:** private reasons require scoped
   presentation; merely disabled/busy markup cannot authenticate,
   authorize, throttle or deduplicate server commands.
6. **Independent expected catalog:** validate all declared
   *required* actions for the selected surface/context, including
   hidden actions, without requiring every operation on every page.
   Separate application acceptance derives expected capabilities
   independently from source-discovered Hiccup/actions to prevent
   omission and reject-all vacuity.
7. **Bounded dynamic-render guarantees:** checked dynamic Hiccup
   surfaces and current assembled route/artifact closure are real
   evidence for inspected occurrences, not a proof that all
   possible Clojure rendering branches have been exercised.
8. **Five paired scenarios:** Claim with changing Membership,
   Reassign input-collection versus malformed final invocation,
   real policy unavailability versus missing construction,
   conditional deferment versus unsupported capability,
   and disclosure/disabled-button security behavior.

The preferred R5 architecture keeps concise Hiccup, ordinary Clojure
model rules and derived browser metadata; it does not require the
view author to write proof wrappers, duplicated plan IDs or
second copies of authorization rules. The normative API names
`actions/prepare` and `gesso/action` remain illustrative, not a
claim that these exact helpers are shipping as displayed.

## Actual Gesso implementation inspected

At `michaelmrose/gesso` `application-assurance`
`1b5e10e7` (v1622):

- `src/gesso/live/optimistic/capability.cljc` constructs closed
  operation-keyed typed optimistic capabilities, including plan and
  optional browser policy. Its own documentation explicitly says
  this is inert binding/configuration rather than authorization;
  the trusted server must independently authenticate and revalidate
  the operation and model state.
- `src/gesso/live/ui.clj` provides
  `with-optimistic-operation-capabilities`,
  `optimistic-action`/attribute encoding, and canonical Hiccup
  Choreo affordance metadata. Unknown or missing action fields
  are typed errors. The resulting encoded action contains no
  trusted principal or command/execution ID.
- `src/gesso/live/application_preflight.clj` checks one
  actual rendered Hiccup surface against current assembled
  operation, browser plan, HTTP method, trusted route and
  physical artifact, including anonymously colliding physical
  requests. Its documentation explicitly limits this to the
  currently checked rendering, not every possible dynamic
  application handler branch or deployment escape path.
- These concrete mechanisms do **not** by themselves prove the
  full finished-state `:needs-input`/deferred availability
  taxonomy, eligible HumanHelp Reassign picker-to-final-operation
  flow, all source-defined product capabilities, independent
  current backend authorization, or general browser refinement.

No Gesso JVM/Node/Chromium/browser tests, XTDB tests, or
formal proof checks were executed. Gesso runtime code was not edited.
