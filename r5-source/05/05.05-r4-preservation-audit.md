# R5.1 Part V — 05.05 R4 preservation and implementation correspondence

**Baseline:** `gessoplan/main`, Part V's Bob/R17 continuity-board
example and sections on local preservation, physical resource identity,
failure separation, cleanup after semantic retirement and Choreo effect
completion, cross-checked with reviewed 05.04 and Part IV adoption.
**Candidate:** `r5.1` section
`05.05-continuity-board-replacement-and-cleanup.org`.
**Disposition:** one bounded semantic revision. This does not accept
Part V as a whole, certify Gesso/browser implementation or prove
physical user-facing completion.

## R4 obligations preserved

- Bob's search, opened R17 details, focus and scroll are local
  continuity values, not domain facts, command success or evidence
  of the new board's authoritative provenance.
- The example retains separate prepare, capture, install, completion,
  restore and release phases, with the admission of a real physical
  installation preceding any claim of adopted visible authority.
- An optional failed focus restoration after a successfully
  installed X31 board does not reject a model operation or justify
  reinstalling a stale board; Promise rejections require the same
  containment as synchronous hook failures.
- R4's I1/O1 versus I2/O2 race is preserved with exact slot,
  capture instance, target incarnation and owner checks rather than
  comparing capture numbers or trusting delayed callbacks.
- Locally captured open-details state may be restored only for R17
  if R17 remains in the *newly authorized* rendering; absent or
  undisclosable records cannot be recreated by continuity.
- Physical resource cleanup follows semantic retirement; an old
  style lock or restore handler retains no semantic authority,
  regardless of whether its handle still exists.
- R4's portable Choreo only sees the declared browser-effect outcome;
  ordinary focus/scroll/selection events are not additional
  authoritative choreography branch discriminators.

## Focused corrections in 05.05

1. **HumanHelp query identity.** The current normative example uses
   local text `cabinet` over a complete authorized board cohort
   selected by Organization/Location, principal, visibility and
   temporal/projection scope. Its `board-query-ref` is that
   authoritative selector. The separately supported server-side
   search variant requires distinct acquisition evidence and cannot
   be inferred from a restored input string.
2. **Actual install versus permit/callback.** Preparation and a
   nominal response do not prove installation. The current effect
   must recheck owner/target, scope, provider progression and
   independently newer adopted card/membership at physical mutation.
   Qualified physical completion drives only the covered adoption
   and advisory-debt discharge.
3. **Late edit and superseding owner.** O1's restore is powerless
   after O2 takes the target, after a different actor/tab obtains
   new rights, or after Bob edits the relevant field, even if no
   second board install occurs. Same DOM key need not imply same
   physical target incarnation.
4. **Separate multi-target and mandatory behavior.** Partial
   card/count/board effects retain their own coverage and repair.
   An optional focus/scroll failure never revokes completed
   installation. A separately declared mandatory pre-install
   user-confirmed draft policy is handled at its own boundary,
   not retroactively interpreted as failed incorporation.
5. **Identical-value height lock race.** An old lock L1 cannot
   safely release a CSS property based solely on the fact that its
   previous `min-height` value still matches; newer L2 could
   have deliberately written the same string. Require actual
   property/lock ownership or justified equivalent. A failed
   ownership check leaves diagnostic cleanup debt, not license
   to overwrite.
6. **Six positive/adverse conformance pairs.** Local versus
   authoritative query, optional failed focus, new owner/edit
   races, independently newer self-card, identical-value lock,
   and rejected Promise with later successful refresh.

The stronger R5.1 source neither adds a second business policy layer
nor requires authors to manage raw browser owner tokens. It defines
the finished framework contract and may be realized through more
efficient implementations than the R4 illustrative host snippets.

## Gesso implementation inspected (source, not runtime tests)

`michaelmrose/gesso` branch `application-assurance` was inspected
at `1b5e10e7` (v1622):

- `src/gesso/live/browser/adapter.cljc`: `after-swap` uses exact
  fragment request correlation, emits `:authoritative/installed`
  separately from `:continuity/restore`; no optional restore
  event is sufficient to fabricate installed authority.
- `src/gesso/live/browser/continuity.cljs`: capture returns an
  opaque physical resource and freezes box restore implementations;
  restore uses an async post-layout boundary; release revokes a
  physical latch before best-effort cleanup. The shell/adapter
  own portable generation and slot identity.
- **Known narrower implementation:** `release-height-lock!`
  currently compares the stored `:applied` CSS string with the
  current `minHeight` before restoring `:previous`. That
  avoids overwriting a *different-value* successor write but
  cannot distinguish a same-value successor lock from L1.
  This is an implementation/design correspondence gap against
  the completed normative ownership contract, **not** evidence
  that the general safety property is already enforced.
- Source-inspected tests cover same-value-free idempotent release,
  changed-value nonclobbering, release before deferred restore,
  and physical restore rejection. In particular,
  `height-lock-release-is-idempotent-and-non-clobbering-test`
  checks a *different-value* successor, not the equal-value
  ownership counterexample.
- `test/gesso/live/browser/chromium_integration.clj` contains
  `continuity-restore-failure-is-local-and-later-refresh-recovers-test`
  for an actual production JS/HTMX/Chromium boundary. That test
  was inspected, not run; it cannot by itself establish all
  same-value lock, field-edit or HumanHelp scope cases.

No Gesso runtime file was edited. No JVM, Node, Chromium, XTDB,
Python assembler or model-checker run was performed in this pass.

## Cross-part and remaining obligations

- **Parts I–II:** exact resource-instance ownership,
  trusted principal, input classification and scoped knowledge.
- **Part IV:** complete board acquisition distinct from local
  search/ordering, separate creator-local S/P19 card adoption,
  per-target physical effect completion and retained obligations
  under one user Refresh grant.
- **Part VI:** physical continuity captures, current-generation
  restores, cancellation, host effects, HTMX after-swap,
  interruption and cleanup need actual realization with
  no equal-value owner confusion.
- **Part VII:** assembled assets/handlers cannot bypass current
  authorization and installed effect admission.
- **Part VIII:** actual HumanHelp board selection, local search,
  open Request and scroll retention, Reassign/Claim, and
  one-Refresh positive acceptance remain separate evidence.
- **Parts IX–X:** finite test vectors and scoped physical
  demonstrations are not universal proofs of correspondence.
