** Test architecture and oracles

The proving application uses complementary test layers. No layer substitutes for
the next merely because it is easier to run.

| Layer | What it must establish |
|-------+------------------------|
| Production domain/model tests | Public rules, input validation, assignments, actor/target distinction, command disposition, and exact authoritative outcomes. |
| Executable semantic tests | Transition invariants, ownership, permission budgets, selective coverage, and outcome mappings under declared finite or proof scopes. |
| Qualified backend integration | Actual transaction guards and atomicity, command exclusion, visibility, recovery records, durable publication intent, and assumption-sensitive cases. |
| Assembly and concrete-render tests | The real application constructor and served representation reject missing or contradictory realization edges. |
| Browser adapter conformance | Actual HTMX/DOM/event behavior refines admitted transitions and reports physical completion/failure honestly. |
| Installed-host tests | The running server adopts the admitted handler, providers, writer gateways, and compatible asset set. |
| Real-browser product acceptance | Users can accomplish every required capability through actual controls and observe the specified authoritative and presentation result. |

Fixture construction must establish valid production Organization, Location,
Users, Memberships, Requests, and assignments. Tests must not persist malformed
shortcuts and then bypass public validation to make them usable. Controlled
invalid database states can test explicit rejection/recovery obligations, but
must be identified as such.

*** Real browser means the real operation path

The acceptance browser loads the generated runtime and the served application,
authenticates, locates the rendered control, supplies user input, and interacts
normally. It does not call the private lifecycle executor from page evaluation,
inject a ready-made command envelope, preinstall a desired settlement, or replace
the runtime with a mock that already knows the expected result.

A test may inspect emitted bindings and diagnostics, control a fault proxy, and
read authoritative state through an independent fixture oracle. Those observation
and fault facilities cannot provide the missing command the real control failed
to emit.

Mutating success needs both a visible settled result and fresh authoritative
verification. A reload/reacquisition then checks that persistence survives outside
the original optimistic DOM. The verification reads Request and assignment facts,
not merely the toast text or the UI's own cached projection.

*** Deterministic concurrency and temporal assertions

Two browser clicks launched together demonstrate concurrent usage, but do not
prove that transaction attempts encountered the intended conflicting prestate.
A backend concurrency test uses a controlled barrier at the qualified preparation/
submission boundary, establishes the relevant preconditions, and releases the
competing attempts under the real guard mechanism. The browser test separately
proves that real users receive the correct outcomes and recovery UI.

Likewise, “R was absent immediately after Alice clicked” is a weak selective-
adoption assertion if Bob has not received the advisory yet. Tests await the
relevant observed milestone, then assert absence and the lack of an unauthorized
acquisition/installation over the controlled event window. Deterministic adapter
traces cover late scheduling cases that arbitrary sleeps cannot establish.

Unknown outcomes are expected only in scenarios that create the relevant evidence
gap. In fault-free competing Claim tests, definitive delivered outcomes are
required. In lost-delivery tests, forcing every branch into accepted/rejected
would incorrectly erase uncertainty.

*** Lifecycle acceptance matrix

Each required mutation has an eligible positive fixture, a meaningful current-
policy rejection, and the applicable replay/uncertainty case. The matrix must
include:

| Scenario | Essential oracle |
|----------+------------------|
| Self-Claim | Authenticated actor becomes primary helper; forged actor input cannot select someone else. |
| Authorized target-helper variant, if exposed | Actor authority and target eligibility are both enforced; they remain distinct identities. |
| Concurrent Claim | At most one new primary assignment; losers and uncertainty follow actual delivered evidence. |
| Membership/policy change during Claim | The protected current dependency prevents an obsolete preparation from committing. |
| Compatible Claim replay after success | The old success is recoverable without another incorporation even though the Request is now claimed. |
| Replay after later Unclaim/Reassign | Historical outcome and current card are distinguished. |
| Incompatible command reuse | Typed failure, no extra mutation, and no unauthorized result disclosure. |
| Unclaim | Correct open state and assignment history; ineligible actor/state rejected. |
| On the way | Correct =:on-the-way= state; obsolete or unauthorized attempt rejected. |
| Complete | Correct =:done= state and required assignment closure from each permitted starting state. |
| Cancel | Correct =:cancelled= state and closure under requestor/current policy. |
| Reassign | Real target selector, legitimate replacement, preserved lifecycle meaning, and no two active primary owners. |
| Target loses eligibility during Reassign | Commit guard rejects the stale selection without a partial responsibility change. |
| Duplicate Create or lost Create response | One incorporated Request per compatible command and usable recovery without inventing a second identifier. |

The authoritative oracle follows model-specific semantics. For example, a
Reassign that preserves Request lifecycle state must not be tested as though it
creates a fresh Claim. A terminal Request with no active assignment must not
regain a Claim control merely because a presentation helper checks for nil.

*** Board and presentation acceptance matrix

| Scenario | Required result |
|----------+-----------------|
| Initial load | Authorized complete bounded cohort or explicitly scoped page, correct defaults, compatible assets, and justified or honestly unestablished subscription continuity. |
| Create without an excluding filter | Creator sees the confirmed Request promptly; another browser gets advisory without adoption. |
| Create under an excluding filter | Creator sees the authoritative result area before changing the filter; current options stay intact. |
| Remote R followed by local S | S is selectively admitted; R remains absent and its board obligation remains pending. |
| Search/options after remote advisory | Only adopted rows change presentation; no new collection acquisition or debt discharge. |
| Both priority toggles | Mine-first is primary, unclaimed-first secondary, then creation order and identity tie breaker. |
| Terminal visibility | =:done= and =:cancelled= appear from the adopted cohort when enabled and are hidden locally when disabled. |
| Remote lifecycle update to visible R | R retains its adopted fields until Refresh or a separately permitted local recovery read. |
| Refresh with later advisory | Discharge reflects actual installed coverage; no unauthorized automatic successor read. |
| Local result wins race with old Refresh | The old result cannot remove or regress the newer justified card/membership. |
| Successful read with failed swap | Adoption debt remains and Retry is usable. |
| Empty/partial/error response | No invented complete absence or removal of unresolved command recovery. |
| Search/options changed during Refresh | Current local options win; old response options are not restored. |
| Details open during replacement | Compatible expansion/focus is restored to current targets; removed targets have a safe fallback. |
| Rapid search/option changes | Stale scheduled callbacks cannot restore an older presentation state. |
| Authority context changes in flight | Old content and callbacks cannot enter the new principal/scope. |
| Reconnect with no event delivery | Continuity gap remains visible until the declared recovery establishes coverage. |
| Duplicate and retired-subscription events | No duplicate effect/adoption and no resurrected ownership. |
| Response interaction | The independently selected contract succeeds; until selected, this row is unresolved. |

Two independent authenticated browser contexts are required for the remote/local
scenarios. Separate pages that accidentally share a mutable authentication fixture
are insufficient. Scope-isolation tests also include different authorized
Organizations or Locations, so an advisory cannot leak a foreign scope.

*** Fault and recovery matrix

| Fault point | What must remain true |
|-------------+-----------------------|
| Before any submission | No mutation occurred; retry/admission follows the declared local failure policy. |
| Submission followed by lost outcome | Participant reports unknown until command-specific reconciliation; no assumed rollback. |
| Known commit followed by failed response render/delivery | Commit remains recorded; invalid output is blocked and recovery can find the permitted result. |
| Crash after commit before publication | Durable intent or the explicitly selected alternative recovery path is exercised, not merely declared. |
| Command result lookup denied | No protected result disclosure and no false claim that the command never committed. |
| Acquisition timeout | Pending obligations remain; grant is not silently renewed forever. |
| Late response after abort/retirement | No stale installation, even if physical cancellation failed. |
| Late rejection after newer installation | No rollback of the newer card. |
| Deployment during suspended work | Obsolete execution cannot resume; compatible command recovery remains separate. |
| Backend assumption qualification failure | Dependent admission/claim is blocked or explicitly downgraded under policy, not reported unchanged. |

Each scenario identifies the injected fault, expected diagnostic class, permitted
requests and outcomes, and authoritative postcondition. Tests reject unrelated
console errors, page errors, failed requests, and HTTP failures. They do not
suppress all 4xx/5xx or every message containing “timeout” to make fault tests pass.
