## Preservation crosswalk and final policy

1. **Selected policy is explicit.** R4 settled remote Create as
   advisory-only but left remote lifecycle adoption an open
   product decision. R5.1 selects explicit Refresh for *both*.
   Current code's different behavior is an implementation
   gap, not an excuse to weaken this finished-system plan.
2. **Live invalidation is not authority.** Scope/progression
   hints cannot directly install Request/helper/terminal
   content, forge actor permission or automatically
   grant an additional protected read.
3. **Local affected-card exception.** The user's accepted
   command, or separately authorized rejected/uncertain
   command recovery, can acquire its own Request
   without granting global board membership or
   discharging unrelated advisory debt.
4. **Current authorization.** Logout, scope changes
   and revocation retire incompatible
   managed projections and deny new protected
   access; previously disclosed bytes in
   offline clients cannot be retracted.
5. **One-use Refresh grant.** A user action fixes
   principal, board/Location scope, owner,
   captured obligations, resource lifetime,
   one logical read, expiry and admissible
   acquisition. A further user click may
   authorize one coalesced successor;
   an advisory or automatic retry cannot.
6. **Physical completion is required.** Backend read,
   HTTP success, OOB response receipt,
   swap proposal and actual physical
   toolbar/list installation are distinct
   stages. Partial batches remain incomplete
   with non-regressing local data and
   visible repair/debt.
7. **Opaque provider progression.** Only a
   qualified XTDB/provider relation proves
   basis comparison and observation
   coverage. A higher-looking token,
   current HTML card or local command
   result does not certify complete
   board membership or historical C42.
8. **No-gap delivery premises.** Gesso
   client OOB channel is ephemeral
   and bounded, with overflow/drop and
   disconnected limits. Stronger
   remote eventual notification or
   multi-node guarantees require
   qualified reconnect/fence/replay/
   acquisition, not invented durable
   delivery from the mailbox.
9. **Real browser races.** Older full
   reads, remote O2 during Refresh,
   local S, stale owner and Location,
   unknown commands, terminal
   hiding and current permission
   have independent outcomes.
10. **Positive/negative tests.** Twenty-two
    source-backed acceptance histories
    explicitly test both *successful*
    user-authorized Refresh and absence
    of unwanted automatic adoption.

## HumanHelp dev current implementation: supported and missing

- `src/net/humanhelp/example/live.clj` excludes
  `:created` change events from its managed
  toolbar/list invalidation graph. The same
  graph still routes `:updated` events
  to both managed fragments. That means
  the selected R5.1 advisory-only **remote
  lifecycle** rule is not established by
  the present source; it needs an
  application-level source/effect/owner
  change, not a weakening of the spec.
- `src/net/humanhelp/example/app.clj`
  `refresh-requests!` performs a real
  POST-driven production-backed board
  query, rerendering toolbar/list via
  OOB fragments and returning updated
  board-state markup. It does not
  visibly implement a source-owned
  one-use read grant, captured
  requirements, qualified stage-six
  installation or retry-lifetime
  coordinator.
- `src/net/humanhelp/example/views.clj`
  `refresh-form` uses a stable POST
  form, `:swap "none"` and current
  board-state inclusion. Client
  advisory replaces an inner
  button/advisory surface rather
  than transferring the recipient's
  CSRF form. The toolbar data
  currently defaults `:stale? false`
  and `:pending-open-count 0`;
  these fields cannot independently
  certify debt discharge.
- `src/net/humanhelp/example/live.clj`
  `send-new-request-advisory!`
  requires creator identity and
  sends non-adopting OOB/Toast to
  connected noncreator browsers,
  avoiding canonical Request-list
  HTML. This is meaningful
  **creation** advisory work.
- `src/net/humanhelp/client_plumbing.clj`
  scopes connected clients by app
  and User, delegating ephemeral
  transport to `gesso.live.client`.
  Gesso's finite mailbox/disconnected
  limits and overflow semantics do
  not constitute durable messaging
  or multi-node delivery guarantees.
- `test/net/humanhelp/example/live_test.clj`
  covers declared production Live
  scope, invalidation and authoritative
  basis; `app_test.clj` covers
  route/model boundary safety.
  `chromium_acceptance.clj` does
  exercise real rendered
  Claim/Unclaim/On-the-way/
  Complete/Cancel/Reassign with
  persisted readback. These are
  selected existing *test sources*,
  not fresh executed proof of
  two-browser one-use Refresh
  or all remote :updated cases.

## Gesso source correspondence, qualification, and next work

- `gesso.live.invalidation` preserves
  authority-provided progression on
  expanded semantic invalidations,
  but does not prove remote browser
  adoption or issue user read grants.
- `gesso.live.htmx` and managed
  fragment runtime implement
  physical wakeup/refresh options,
  independent of HumanHelp's
  selected app-level user policy.
- `gesso.live.progression` treats
  bases as opaque and retains
  distinct requirements unless
  externally qualified evidence
  proves a covering relation.
- `gesso.live.browser.continuity`
  manages physical browser-local
  continuity below semantic
  owner and authorized adoption.
- `gesso.live.client` provides bounded
  ephemeral connected-browser OOB
  delivery, with no global
  transaction/durable outbox proof.
