** Optimistic presentation and command recovery

Optimistic behavior is a declared convenience, never an authority shortcut. A
lifecycle action remains semantically identified whether or not its current
observation supports a provisional projection. Missing optimistic basis does not
produce an anonymous ordinary HTMX mutation.

Each prepared affordance must choose one valid realization: an admitted optimistic
plan with its required data; an explicitly supported non-optimistic semantic plan;
or a disabled/unavailable presentation that provides the declared acquisition or
explanation. The renderer cannot invent a fallback after preparation fails.

The browser adapter admits semantic state before issuing effects. Physical work
is registered to the execution and target instances that own it. Final effect
admission, not only promise-resolution time, checks those rights. Physical
completion determines whether presentation was installed and adopted.

*** Rollback and supersession

An optimistic snapshot can be restored only while its exact rollback rights
remain current. A later authorized card installation, target replacement, owner
retirement, or incompatible context change revokes them. Rejecting an old command
must not restore the card that existed before a newer successful command.

Target retirement cleans up timers, listeners, pending operations, and continuity
resources according to their ownership. It does not erase authoritative command
uncertainty. An unresolved command transfers to its recovery owner before the
presentation scope is released.

*** Unknown is a recoverable knowledge state

The UI distinguishes pending delivery from a confirmed rejection and from an
unknown outcome. It retains the stable command binding and a permitted recovery
reference. Reconciliation uses authoritative command evidence under current
binding and disclosure checks.

A scoped card read can repair what the user sees while the command remains
unknown. It cannot determine that this command committed merely because the
Request is now claimed. The application must not implement “retry” by replacing
the identifier or simulate certainty by rolling back the DOM after a timeout.

Retry/reconciliation is bounded by the selected policy and can expose a visible
user action when automatic attempts stop. The policy states what survives reload,
how the user's command receipt or authenticated recovery index is recovered,
and what happens after the retention horizon. Browser reload is not permission
to forget an operation that may have committed.

The profile may store only minimal recovery references in browser storage, bound
to the relevant authority context; sensitive arguments and outcomes remain behind
trusted disclosure checks. Loss of that storage cannot justify inventing a command
outcome. Recovery availability beyond the chosen retention/discovery contract is
an explicit limit, not a proof failure disguised as rejection.
