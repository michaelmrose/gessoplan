** Board projection and selective adoption
:PROPERTIES:
:CUSTOM_ID: req-humanhelp-selective-adoption
:END:

The board separates authoritative truth from the information this browser has
adopted. A database change does not automatically change a user's visible board.
An advisory reports that the view may need attention; it is neither domain
content nor permission to fetch and install everything currently available.

The selected policy is prompt adoption of the user's own correlated results and
explicit Refresh for remote changes. Search, sorting, visibility options, and
ordinary details interaction operate on already adopted information. These
choices must be represented in application policy, not inferred from incidental
HTMX route or callback behavior.

*** Scope, cohort, and presentation

A board scope includes Organization, Location, authority context, projection
contract, temporal interpretation, and any declared collection bounds. Its
adopted cohort is the set of Request identities admitted into that scope, with
scoped observations and permitted display projections.

The default proving scope is one authorized Location and includes active and
terminal Requests within its declared collection bounds. Terminal visibility is
a presentation option. Reading only active Requests and later making “Show
terminal” issue a fresh collection query would violate that option's contract.

The profile declares finite response/retention limits. If a complete result
exceeds those limits, the server must return a typed scope-too-large result or
use an explicitly declared paging/window contract. Silent truncation cannot
justify complete membership or authoritative absence. A page covers its stated
window, not the whole Organization. Moving to another page or Location is a new
explicit acquisition intent, not a local sort operation.

Local text search and sort options do not change this authoritative collection
scope. They derive a visible subset and order from the cohort. A future remote
search feature must be labelled and specified as a different acquisition policy;
it cannot borrow the “local presentation only” guarantee.

The complete-board acquisition composes Request, assignment, and permitted User
display projections under the same qualified observation context. Repeated reads
against an advancing database are not silently treated as one snapshot. If an
integration deliberately combines observations, it preserves their separate
provenance and proves only the relationships that their evidence supports.
Current disclosure checks also remain distinct from the historical observation
being displayed.

 
*** Initial acquisition, truthful membership and counts

The first rendered =GET /app= obtains an admitted
initial Request cohort and permitted Request,
RequestAssignment and User projection. The
toolbar/list may be server-rendered, but a
fragment's token does not by itself prove
the other fragment has matching membership
or counts. Any relevant change between
initial read and subscription registration
requires a source-owned fence, replay or
authorized reacquisition. Merely connecting
SSE does not establish a no-gap baseline.

A complete cohort result has an exact
authenticated viewer, Organization/Location,
collection and terminal inclusion, projection
schema, temporal/query interpretation,
read basis, finite bounds and completeness
claim. Querying Requests, assignments and
User display fields through successive
reads against an advancing database does
not prove one atomic snapshot. Either
qualify their common context or retain
the distinct provenance of every subread.

Displayed =:total-count=, =:active-count=
and =:terminal-count= refer to this
adopted cohort (or explicitly narrower
adopted visible subset), not to the
current global database. Unsupported,
incomplete, unauthorized or truncated
collections must be marked as such:
empty results do not imply complete
authoritative absence. Disclosing an
old card still requires current
read permission, independent of the
basis at which it was first acquired.

*** State with distinct meanings

An inspection view of the board distinguishes the following records:

| Record | Meaning and owner |
|--------+-------------------|
| Board owner and scope | One active coordinator lifetime, authority context, and applied acquisition scope. |
| Adopted membership | Requests admitted by a complete scoped observation or a permitted selective membership rule. |
| Adopted observations | Per-card and collection evidence actually installed, with provenance and scope. |
| Advisory obligations | Information still requiring acquisition/adoption, including unresolved subscription continuity gaps. |
| Acquisition grant | User or policy permission for particular reads and installations, with scope, budget, and lifetime. |
| Active cycle | Registered request and installation resources with current ownership. |
| Local options and drafts | Search, ordering, visibility, expansion, focus, and bounded unsubmitted input. |
| Provisional overlays | Execution-owned speculative presentation, not authoritative observations. |
| Command recovery records | Unresolved command bindings and permitted reconciliation references that can outlive a card. |

These are not eight unrelated mutable registries. The executable semantic core
owns their transitions; physical adapters report observations and completions.
A presentation cache may store allowed fields, but it is not a second domain
model or a source of write authority.

 
*** Resource identity and admission of physical installation

The board owner, scoped cohort, fragment
resource instance, local option state,
each card's physical DOM instance,
issued acquisition, optimistic execution
and unresolved command each have
distinct identity and lifetime. The
same Request UUID does not make a
replaced DOM card the same active
instance; a delayed callback cannot
borrow the new instance's rights or
reapply a retired provisional marker.

For an observation to become adopted,
its trusted principal, permitted
scope and corresponding Request,
admitted progression/coverage,
current board/execution owner and
physical installation must all agree.
The physical swap must complete;
an HTTP 200 without installation
is not evidence of adoption.
A response prepared before a
newer justified local card update
cannot overwrite that card simply
because it arrived afterward.
Failed/cancelled swaps retain their
unfulfilled read/adoption obligation.

Local filter changes may preserve
focus, caret, scroll and compatible
open =<details>= state across a
managed HTMX replacement. Continuity
does not resurrect an expired
command, stale card owner or old
acquisition grant. A local Create
may admit exactly its correlated
new Request, while a local Claim
may update only its own qualified
card. Neither can claim whole-board
membership advancement through
the new result's later basis.

A schematic inspection value is:

#+begin_src clojure
{:board/owner-ref board-owner
 :board/scope-ref board-scope
 :board/authority-context-ref authority-context
 :membership/adopted-ref membership-evidence
 :cards/adopted-refs card-evidence-by-request
 :advisory/obligations pending-obligations
 :acquisition/grant-ref current-grant
 :acquisition/cycle-ref current-cycle
 :presentation/options {:search ""
                        :created-order :newest
                        :mine-first? false
                        :unclaimed-first? false
                        :show-terminal? false}
 :presentation/result-ref local-result
 :commands/unresolved-refs unresolved-commands}
#+end_src

The references name admitted runtime objects or inspection subjects. Constructing
this map cannot grant admission. In particular, replacing =membership-evidence=
with a newer card's basis does not make the cohort a newer complete snapshot.

*** A concrete HTMX-compatible realization

The primary realization keeps server-rendered cards and a small browser
presentation projection. An admitted observation supplies the card content and
the permitted fields needed for local search, stable sorting, terminal filtering,
and continuity. Local option changes select, order, or hide those already adopted
cards without issuing an authoritative collection acquisition.

The browser projection contains only data the viewer may receive. Search indexes
must not smuggle undisclosed email addresses, phone numbers, or other hidden
fields into page attributes. Client-side display metadata remains untrusted as
input to future server operations.

 
Search metadata is itself a disclosure surface. A match on an
undisclosed email, phone or other restricted identifier can reveal
private information even if it is never printed on a card. Indexes
therefore include only permitted display/search fields and are
retired or redacted when current access is lost. The current
source's index contents are documented in the preservation audit.

HTMX remains the qualified transport and installation mechanism for authoritative
updates. The application-specific local presenter uses declared managed effects
for its own DOM changes; it cannot re-create retired cards, copy old owner
annotations, or make an obsolete callback current. Stable Request identity is
separate from the current physical card instance.

A server-rendered local-options alternative is valid only if it renders a
retained, scope-bound projection without silently acquiring newer domain facts.
Any retained projection handle needs principal/context binding, expiry, resource
limits, and current disclosure checks. A browser-supplied list of Request IDs
neither proves membership nor authorizes reads. The primary browser presenter
avoids requiring this additional server snapshot service for ordinary options.

 
*** Search and options preserve admitted membership

The chosen realization may present an admitted browser projection or
a retained, owner/principal/scope-bound server snapshot. A GET that
requeries current collection membership is an authoritative acquisition,
not a harmless local search. It must have a separately authorized grant;
it cannot silently adopt remote Requests or discharge advisory debt.
If retained data cannot be used, the renderer reports unavailable or
offers explicit acquisition, never an unqualified latest-database
fallback. This is a cohort-adoption rule, not a prohibition on Clojure
or HTMX rendering. The existing requery path is analyzed in the audit.

*** Mixed observations are explicit

A board may retain its cohort from observation Q17, adopt a local result for S at
another qualified observation, and keep an older card for R. It must preserve
those distinctions. There is no scalar board “current revision” that proves all
these cards and membership were read in one database snapshot.

Collection counts are counts of the specified adopted cohort or visible subset.
A separately acquired current count needs its own scope and disclosure contract.
Neither a pending-obligation count nor a progression token is a count of new
Requests. The default advisory label is “Updates available”, not an invented
number of unseen Requests.

 
*** Positive and adversarial board histories

The independent product oracle uses
actual adopted membership, provider-
scoped read evidence and two
browser contexts where remote
actions matter. A test must
observe the remote advisory
*before* asserting that its
Request stayed absent; otherwise
the assertion may pass vacuously.

| History | Required result |
|---------+-----------------|
| The initially served =/app= includes a permitted terminal Request and a live interest is registered afterward. | Record authorized membership and initial coverage; recover or expose a gap for any intervening commit. |
| =show-terminal?= changes from false to true. | Reveal terminal members already in the cohort; neither a new database query nor a new permission is implied. |
| Alice creates R remotely while Bob's board retains Q17. | Bob receives advisory; R and any newer count remain absent until authorized adoption. |
| Bob searches for R's exact title after receiving its advisory. | Search only the admitted cohort; R remains absent and advisory debt survives. |
| Bob changes mine-first, unclaimed-first and newest/oldest after R arrives remotely. | Deterministic order of existing members; no new Request membership. |
| Bob creates S locally at P19 while remote R at P18 still waits. | Adopt only the correlated eligible S and preserve R's outstanding advisory obligation. |
| Bob's current filter excludes newly created S. | The correlated result remains visibly confirmed without silently clearing the filter or adopting R. |
| Bob Claims an already adopted T while R is remote. | Install a justified T observation only, preserving old cohort coverage and R debt. |
| S's card has basis P19 but board membership is still Q17. | Preserve different scope/progression provenance; do not advertise a complete P19 board. |
| Search/options invokes a fresh =requests-for-location= query without Refresh grant. | Classify it as unauthorized additional acquisition for the local-only policy, not an innocent presentation transform. |
| A retained server projection expires or belongs to another principal or deployment generation. | Reject reuse or require a newly granted acquisition; browser-supplied IDs confer no read authority. |
| Request and User display rows were read at different physical positions. | Keep independent provenance unless the selected backend/join evidence establishes their compatibility. |
| A result exceeds configured full-cohort limits. | Return typed incomplete/scope-too-large or a declared window; never silently truncate and claim complete absence. |
| An older Refresh response arrives after a newer local authoritative card was installed. | Keep the newer applicable card and current owner; do not regress via response arrival order. |
| New advisory O2 arrives while Refresh covers only captured O1. | Discharge O1 only after authorized physical adoption; retain O2 pending. |
| A local options rerender replaces an expanded card while search is focused. | Restore compatible =<details>=, focus/caret/scroll without reviving retired action rights. |
| A late callback addresses a Request with the same UUID but an obsolete card DOM instance. | Refuse it as a current owner; no resurrection of provisional view or consumed grant. |
| Viewer loses current Membership to previously adopted R. | Withhold further disclosure and retire/redact the forbidden projection under applicable policy. |
| Search indexes an unauthorized User email/phone value. | Prevent disclosure through match results, DOM fields or retained index, even if visible card text omits it. |
| Advisory UI displays “3 new Requests” based solely on notification count. | Reject unsupported numeric claim; use “Updates available” until a permitted count has been read. |
| User switches Location or explicit collection page. | Require a new authorized scoped acquisition and retire incompatible old cohort; this is not a local sort. |

The existing =example.board= unit tests
exercise source-level presentation
semantics on supplied production rows
and distinguish Live/XTDB observed basis
from Request revision. The existing
Chromium lifecycle test exercises
real browser operations and persisted
outcomes. Neither automatically
establishes this complete selective-
