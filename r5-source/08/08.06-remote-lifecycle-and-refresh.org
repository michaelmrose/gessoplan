** Remote lifecycle adoption policy
:PROPERTIES:
:CUSTOM_ID: decision-humanhelp-remote-lifecycle-adoption
:END:

Selected policy: remote creation and remote lifecycle changes both require
explicit board Refresh for ordinary domain-content adoption. This includes
changes to Requests already visible. An advisory may update the pending indicator
and explanatory status; it does not silently replace a card or its cohort.

This policy is intentionally separate from two permitted local continuations:

- The user's own accepted command may install its declared affected-card/result
  observation and selective membership effect.
- A rejected or uncertain local command may invoke its declared scoped recovery
  read. That read can reveal current state of the affected Request, even when
  another actor caused it. It cannot import unrelated collection members or
  automatically resolve the uncertain command's attribution.

An old displayed Claim button can therefore remain visible after another helper
claims the Request. Clicking it is safe only because the public model enforces
current authority. The resulting rejection and affected-card acquisition explain
the conflict. An advisory may say the view has updates, but must not infer the
winner or current domain state from advisory payload alone.

Authentication loss, explicit scope change, and an established loss of disclosure
rights are separate context transitions. They retire incompatible execution and
installation rights and remove protected projections where the supported client
can do so. They are not delayed merely to preserve a board Refresh preference.
No application can retract information already disclosed to an untrusted or
offline browser; the enforceable guarantee is current checks at subsequent
trusted disclosures and mutations, plus the declared supported-client behavior.

** Explicit Refresh, coverage, and races
:PROPERTIES:
:CUSTOM_ID: req-humanhelp-refresh-coverage
:END:

A Refresh click creates a grant for one logical acquisition of the current board
scope and authority context. It captures the outstanding requirements and the
current non-regression obligations. Its lifetime ends on completion, failure,
expiry, owner retirement, or incompatible scope/context change.

The default has one acquisition and no automatic successor read. It can obtain
a complete current query result that includes changes beyond the captured
requirements. Installation can discharge any current obligation covered by that
actual result within the grant's scope. It does not authorize a second read just
because another advisory arrived.

A new explicit Refresh or Retry can create a new grant. While a cycle is active,
additional clicks are coalesced into at most one user-authorized successor intent
with current captured requirements; they do not create an unbounded queue. A
pending indicator alone never creates that intent. The UI reports whether it is
refreshing, waiting for another explicit action, or unable to refresh.

A deployment may choose a bounded automatic repair/drain policy instead, but that
is an explicit product-policy change with its own budgets, expiry, and acceptance
cases. It is not an adapter optimization invisible to the user contract.

*** Acquisition and adoption are separate stages

1. Register the cycle, transport identity, scope, target owner, and requirements
   before physical dispatch.
2. Authenticate the actual read and validate the query/progression input under
   the qualified provider contract. A hostile or impossible token must not force
   an unbounded wait.
3. Acquire a projection with evidence of actual observation, completeness, and
   applicable authority context. Echoing the requested minimum does not prove
   the read met it.
4. Admit installation against the current owner, target instances, grant, scope,
   compatibility, and non-regression requirements.
5. Perform the qualified physical replacement/merge and report completion.
6. Record adoption and discharge only obligations satisfied at their required
   stage. Render current local options over the newly adopted cohort.

HTTP completion, response receipt, a proposed swap, or a backend read alone does
not complete stage 6. If installation fails, acquired evidence may remain useful
but the adoption/repair obligation remains visible.

Toolbar counts, list membership, cards, and board evidence must refer to the
same declared installation or explicitly identified partial result. The primary
full-board path renders one coherent board projection and coordinates its
affected surfaces as one adoption batch. Where HTMX performs several physical
mutations, admission is checked before the protected work and completion tracks
each required effect; multi-fragment delivery is not claimed to be DOM-atomic.
A partial failure leaves the batch incomplete, prevents a false “up to date”
claim, and exposes repair without rolling back a newer independently admitted
card. Re-fetching toolbar and list independently cannot manufacture a coherent
board observation merely because both responses arrived successfully.

*** Race rules

The default allows a non-regressing complete-query advance even when a stronger
remote advisory remains outstanding. This is partial satisfaction of current
debt, not partial or fabricated completeness of the query result. The remaining
advisory stays visible for a later user action.

| Race or failure | Required result |
|-----------------+-----------------|
| A later advisory arrives during a Refresh. | Preserve it; clear it only if the actual installed observation covers it. |
| The read covers the captured obligation but not the later one. | Adopt the non-regressing result and retain the later obligation; no automatic successor without a grant. |
| A qualified read also covers the later obligation. | Discharge both after successful installation within the permitted scope. |
| A local Create/Claim result is installed while an older board read is in flight. | Recheck the incoming board result against the newer local observation/membership obligations; do not overwrite or remove the justified local result. |
| An older result cannot establish safe replacement. | Decline that installation, preserve the local result and debt, and expose Refresh/Retry. A separately admitted selective merge needs its own coverage argument. |
| A stronger result arrives from a retired request or board owner. | Reject its installation rights; stronger progression does not revive a retired resource. |
| A read succeeds but physical installation fails. | Preserve remaining adoption debt and a usable retry path. |
| Local search/options change during the read. | Install into the same acquisition scope if still valid, then apply the current local options; do not restore obsolete options from the response. |
| Organization, Location, page/window, or authority context changes. | Retire or explicitly transition the owner; the old response cannot populate the new scope. |
| A command remains unresolved when a board refresh completes. | Update permitted presentation without claiming the command succeeded or failed solely from current card state. |

A full-board replacement must not regress any retained observation whose scope
it supersedes. If proof of safe replacement is unavailable, the default rejects
that replacement and requires a new acquisition. It does not silently union an
old complete result with arbitrary newer rows and call the union a complete
snapshot. A mixed selective projection can be valid, but must retain its mixed
provenance and must not claim snapshot-wide properties.

*** Membership removal and authoritative absence

An authoritative query result can remove a cohort member only with the required
coverage and current installation rights. A filtered-out row, a failed read,
missing markup, or an empty partial page is not evidence of domain deletion.
Terminal filtering hides =:done= and =:cancelled= in the default view without
removing their admitted cohort membership.

If an affected-card read establishes that a Request has left the authorized
scope, the UI follows the declared non-disclosing absence/unavailability branch.
It must not reveal whether an inaccessible entity was deleted, moved, or made
private unless policy permits that distinction. Such a read still does not
resolve a prior command's attribution without command evidence.

Pending provisional presence has a resolution owner. It cannot survive every
complete authoritative observation indefinitely, and it cannot disappear with
its command-recovery record merely because a DOM row was removed. Part VI's
separate rules for presentation supersession and command uncertainty apply.
