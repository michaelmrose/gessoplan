** Required user capabilities
:PROPERTIES:
:CUSTOM_ID: req-humanhelp-required-capabilities
:END:

The following obligations are independent of the assembled operation list.
Conditional unavailability under production policy is legitimate; permanent
unavailability or omission of a promised capability is not.

| Capability | Positive user interaction | Independent authoritative or observable result |
|------------+---------------------------+-----------------------------------------------|
| Authentication | Sign in as a real eligible fixture user. | Reads and writes bind to that principal; a second context has a separate session. |
| Create | Enter valid Request content in the real dialog and submit. | One Request in the selected authorized Organization/Location, correlated command outcome, and prompt creator-local visibility. |
| Claim | Eligible helper clicks Claim on an open Request. | Production claimed state and the proper active primary assignment. |
| Unclaim | Eligible current helper releases a claimed Request. | Production open state and assignment termination required by the model. |
| Mark on the way | Eligible current helper acts on a claimed Request. | Production =:on-the-way= state and its required lifecycle facts. |
| Complete | Eligible helper completes a claimed or on-the-way Request. | Production =:done= state and closure of the active assignments required by policy. |
| Cancel | Eligible requestor cancels an allowed active Request. | Production =:cancelled= state and required assignment closure. |
| Reassign | Authorized manager chooses a legitimate different eligible helper and confirms. | Production replacement of primary responsibility and correct assignment history. |
| Refresh | User explicitly adopts current board information. | A qualified scoped observation is installed, with only covered obligations discharged. |
| Search and options | User changes search, creation order, mine-first, unclaimed-first, or terminal visibility. | Deterministic presentation of the adopted cohort without unrelated remote adoption. |
| Details and continuity | User opens details, edits allowed local input, and survives permitted updates. | Correct disclosed information and bounded restoration of compatible local interaction state. |
| Response interaction | User completes the separately selected response-flow contract. | Its independent product outcome, as required below. |
| Recovery | User encounters rejection, uncertainty, disconnect, or stale application state. | An honest status and a usable declared path to recover under the stated availability assumptions. |

The production model owns exact eligibility. These descriptions do not authorize
an actor who lacks current Membership or whose Request state changed. Positive
fixtures satisfy policy through real production relationships; negative fixtures
change one relevant premise and assert the corresponding outcome.

Reassign is not a hidden model function with a permanently disabled button. Its
UI must provide target discovery/selection, visible validation, confirmation,
and a tested eligible path. Target search reveals only permitted User projections
and is revalidated at commit. “Take over” is not silently treated as a synonym
for Reassign; if exposed, its actor and target policy must be explicitly bound.

Additional model operations, including Edit and collaborator management, remain
inside the relevant writer/invariant coverage even when this stage does not
promise dedicated example controls for them. Excluding a control is different
from pretending that the writer cannot affect the shared database.

** Worked vertical slice: Claim

Alice is an authenticated helper with effective Membership in the Request's
Organization. The board has adopted an authorized observation of Request R17 as
open. The prepared Claim control carries its unconditional semantic operation
identity and the concrete realization data its plan needs.

1. Alice clicks the actual control. The admitted browser plan binds command C42,
   its operation/arguments, execution owner, and presentation target. The bridge
   supplies the wire protocol; the test or page author does not handcraft it.
2. A provisional “Claiming…” state may appear. It is owned by that execution and
   does not establish authoritative assignment or disable another user's model
   operation.
3. The installed route resolves the exact admitted server realization. The
   trusted boundary authenticates Alice, validates the command envelope and its
   interface mapping, and invokes the public production operation.
4. Resolve-or-incorporate recovers an existing compatible result or protects the
   complete current guard and atomically incorporates C42. A new Claim cannot
   succeed if the relevant current policy denies it.
5. The outcome mapping settles accepted, rejected, or unknown as justified. An
   accepted result authorizes only its declared card/result acquisition and
   installation, not a fresh whole-board membership query.
6. Physical installation completion records adoption and retires superseded
   provisional rights. Late callbacks from the old target/execution cannot
   restore its speculative card or apply a second settlement.

If Bob concurrently claims R17 with a different command, at most one new Claim
can establish primary ownership from the eligible open state. In a fault-free
run with both outcomes delivered, the other command receives the appropriate
authoritative rejection. When outcome delivery is deliberately lost, unknown is
a valid intermediate participant state and reconciliation is required.

If C42 commits but its response is lost, Alice's retry preserves C42 and its
binding. It does not fail solely because R17 is now claimed. If a later Reassign
has changed R17, a permitted replay can still report C42's historical success;
the fresh card must reflect the distinct current observation.

If the result response fails render validation after commit, the invalid output
is blocked. The commit remains real. Diagnostics and recovery must keep those
facts separate rather than pretending preflight rolled back the transaction.

A checked semantic certificate can justify admitting the Claim plan under its
premises. Separate evidence establishes installed dispatch and current atomic
enforcement. Returning that certificate from the browser creates no Membership,
principal, current Request state, or permission to disclose the command result.
