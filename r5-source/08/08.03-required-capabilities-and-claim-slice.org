** Required user capabilities

The following obligations are independent of the assembled operation list.
Conditional unavailability under production policy is legitimate; permanent
unavailability or omission of a promised capability is not.

| Capability | Positive user interaction | Independent authoritative or observable result |
|------------+---------------------------+-----------------------------------------------|
| Authentication | Sign in as a real eligible fixture user. | Reads and writes bind to that principal; a second context has a separate session. |
| Create | Enter valid Request content in the real dialog and submit. | One Request in the selected authorized Organization/Location, correlated command outcome, and prompt creator-local visibility. |
| Claim | Eligible helper clicks Claim on an open Request. | Production claimed state and the proper active primary assignment. |
| Unclaim | Eligible current helper releases a claimed Request. | Production open state and assignment termination required by the model. |
| Mark on the way | Eligible current helper acts on a claimed Request. | Production =:on-the-way= state and its required lifecycle facts. |
| Complete | Eligible helper completes a claimed or on-the-way Request. | Production =:done= state and closure of the active assignments required by policy. |
| Cancel | Eligible requestor cancels an allowed active Request. | Production =:cancelled= state and required assignment closure. |
| Reassign | Authorized manager chooses a legitimate different eligible helper and confirms. | Production replacement of primary responsibility and correct assignment history. |
| Refresh | User explicitly adopts current board information. | A qualified scoped observation is installed, with only covered obligations discharged. |
| Search and options | User changes search, creation order, mine-first, unclaimed-first, or terminal visibility. | Deterministic presentation of the adopted cohort without unrelated remote adoption. |
| Details and continuity | User opens details, edits allowed local input, and survives permitted updates. | Correct disclosed information and bounded restoration of compatible local interaction state. |
| Response interaction | User completes the separately selected response-flow contract. | Its independent product outcome, as required below. |
| Recovery | User encounters rejection, uncertainty, disconnect, or stale application state. | An honest status and a usable declared path to recover under the stated availability assumptions. |

The production model owns exact eligibility. These descriptions do not authorize
an actor who lacks current Membership or whose Request state changed. Positive
fixtures satisfy policy through real production relationships; negative fixtures
change one relevant premise and assert the corresponding outcome.

 
*** Independent user-capability oracle and positive controls

This table is a *separately selected product requirement*, not a census
of the current browser plans or a generated registry of admitted operations.
Every promised capability has its own positive reachable scenario using the
real selected =/app= surface and public production models. Its fixture
establishes legitimate current User, Membership, Organization, Location,
Request and RequestAssignment relationships without bypassing a guarded
operation. The expected model effect and observable UI are independently
specified; the test does not rewrite the oracle when a handler or button
is removed.

A capability may be hidden, disabled, or rejected in a legitimately
ineligible state. The same operation must remain *usable* in a separate
eligible state. Structural closure, refusal of invalid requests, and
absence of console exceptions cannot satisfy a product capability
whose button never submits or whose state never commits.

The product oracle separates (a) rendered affordance and browser input,
(b) trusted transport and production model operation, (c) committed
Request/assignment and permitted command-outcome evidence,
(d) authoritative acquisition and physical installation,
and (e) relevant local/remote presentation continuity.
An isolated source, server, or browser fixture may establish
some of these; it must report its narrower scope.

The full product acceptance also covers the broader response-flow decision,
real authentication, creator-local Create, multi-client advisory and one
user-Refresh, search/order/filter, details/continuity, and unknown/reconnect
recovery. Passing a six-operation lifecycle gate does not qualify those
other capabilities. The explicitly selected response-flow contract remains
a genuine pending product decision until chosen and independently tested;
the evaluator may not silently accept either absence or a substitute
unrelated workflow.

Reassign is not a hidden model function with a permanently disabled button. Its
UI must provide target discovery/selection, visible validation, confirmation,
and a tested eligible path. Target search reveals only permitted User projections
and is revalidated at commit. “Take over” is not silently treated as a synonym
for Reassign; if exposed, its actor and target policy must be explicitly bound.

Additional model operations, including Edit and collaborator management, remain
inside the relevant writer/invariant coverage even when this stage does not
promise dedicated example controls for them. Excluding a control is different
from pretending that the writer cannot affect the shared database.

 
*** Lifecycle operations share one user-to-model path

For Claim, Unclaim, Mark on the way, Complete, Cancel and Reassign,
the positive case begins at the *actual rendered enabled control*.
The source-owned semantic operation must retain its identity across
the generated plan, loaded browser artifact, HTMX request, trusted
route, public model operation, guarded outcome, settlement, scoped
acquisition and final DOM. A missing optimistic basis, plan or
route rejects the managed action rather than silently converting
it to an anonymous POST. A terminal removal follows authoritative
membership/absence semantics, not a speculative view-side decision.

A present target-helper selector is necessary but not sufficient for
Reassign. Target candidates are permitted User projections with an
explicit target choice and confirmation. Trusted model authority must
separately recheck the current actor's manager role, the target's
Membership/helper/skill eligibility and the protected Request's
current assignment at commit. A dropdown or physical =:helper=
browser role does not grant model permission.

The canonical real Chromium scenario may exercise Claim, Unclaim,
Claim again, Mark on the way, Complete, owner Cancel and manager
Reassign with distinct legitimate fixture Requests. Positive
acceptance additionally checks each operation's negative/concurrent
case and fresh persisted result. One all-green happy trajectory
alone cannot establish the behavior under stale Membership,
competing commands, lost settlement or a permanently unavailable
network. Section 08.12 owns the full independent test architecture.

** Worked vertical slice: Claim

Alice is an authenticated helper with effective Membership in the Request's
Organization. The board has adopted an authorized observation of Request R17 as
open. The prepared Claim control carries its unconditional semantic operation
identity and the concrete realization data its plan needs.

 
*** Admission and observation before Alice clicks

Alice's card has a Request identity =R17=, an adopted authoritative
Request/assignment projection and a scoped XTDB observation frontier
=X17=. The latter is neither the Request's revision nor a guarantee
of database currentness. The page also has a live executable
browser-plan/artifact binding, rendered action and target/owner
identity; a server-issued certificate or metadata copied into
the page does not grant authority.

The test locates the actual enabled Claim control in rendered
=GET /app= and follows the generated script/HTMX path. It
must not manually create, inject or edit
=__gesso_live_optimistic_command=, silently synthesize a
browser command in the HTTP fixture, or use an example-only
Request store. A separately named lower-level HTTP fixture
*may* manufacture the wire command to inspect server/model
behavior, but it is never promoted into proof of this
browser-to-command edge.

The real route binds its normalized Request selector to
the command arguments, rejects a mismatch, and obtains
Alice's authenticated User identity from trusted context.
The physical browser participant =:helper= is not evidence
that Alice has effective helper Membership; the current
production model guard establishes that independently.

1. Alice clicks the actual control. The admitted browser plan binds command C42,
   its operation/arguments, execution owner, and presentation target. The bridge
   supplies the wire protocol; the test or page author does not handcraft it.
2. A provisional “Claiming…” state may appear. It is owned by that execution and
   does not establish authoritative assignment or disable another user's model
   operation.
3. The installed route resolves the exact admitted server realization. The
   trusted boundary authenticates Alice, validates the command envelope and its
   interface mapping, and invokes the public production operation.
4. Resolve-or-incorporate recovers an existing compatible result or protects the
   complete current guard and atomically incorporates C42. A new Claim cannot
   succeed if the relevant current policy denies it.
5. The outcome mapping settles accepted, rejected, or unknown as justified. An
   accepted result authorizes only its declared card/result acquisition and
   installation, not a fresh whole-board membership query.
6. Physical installation completion records adoption and retires superseded
   provisional rights. Late callbacks from the old target/execution cannot
   restore its speculative card or apply a second settlement.

 
*** Distinguish authority, delivery, and a successful browser test

A positive browser Claim test observes the generated command's exact
operation, Request argument, stable logical command identity,
execution/physical target, route and supported observed basis.
It then correlates the trusted production result and any
authoritative progression-bearing response with a permitted
card acquisition and actual installed DOM. A fresh authorized
reread or reload verifies that the Request and *primary*
RequestAssignment persist. A provisional badge alone does
not qualify success; neither does seeing a 200 response
whose body was never installed.

The first eligible claim transition changes the persisted
Request and primary assignment together. A rival new Claim
with another command cannot create a second active primary;
an open-state Request guard without the active-assignment
absence/cardinality assertion is insufficient. A model-defined
rejection for invalid current Membership or an already
claimed Request is legitimate *runtime behavior*, not
application assembly corruption.

There are three distinct settlement contexts: the public
=Request core= result with =:commit/status= and transaction
progression; the trusted current protocol-v3 optimistic
server's =:confirmed= result with a justified projection;
and the finished-system Part IV command taxonomy
=:committed=, =:already-incorporated=, =:rejected=,
=:commit-unknown= with browser =:accepted=, =:rejected=,
=:unknown=. Their mappings are explicit, not inferred
from an HTTP status or equal-sounding strings. In
particular, the present source-backed Claim route does
not establish durable historical replay of C42 merely
by generating a protocol command ID. The Part IV
same-transaction command-record/retention and
disclosure mechanism remains a separate required
implementation and qualification.

If Bob concurrently claims R17 with a different command, at most one new Claim
can establish primary ownership from the eligible open state. In a fault-free
run with both outcomes delivered, the other command receives the appropriate
authoritative rejection. When outcome delivery is deliberately lost, unknown is
a valid intermediate participant state and reconciliation is required.

If C42 commits but its response is lost, Alice's retry preserves C42 and its
binding. It does not fail solely because R17 is now claimed. If a later Reassign
has changed R17, a permitted replay can still report C42's historical success;
the fresh card must reflect the distinct current observation.

If the result response fails render validation after commit, the invalid output
is blocked. The commit remains real. Diagnostics and recovery must keep those
facts separate rather than pretending preflight rolled back the transaction.

A checked semantic certificate can justify admitting the Claim plan under its
premises. Separate evidence establishes installed dispatch and current atomic
enforcement. Returning that certificate from the browser creates no Membership,
principal, current Request state, or permission to disclose the command result.

 
*** Positive and adversarial capability histories

The following histories are acceptance *obligations*, not
assertions that every scenario has passed in the running
application. Each retains the source-owned business
policy and selected product profile.

| History | Required positive or failure result |
|---------+------------------------------------|
| An eligible signed-in helper clicks the actual Claim button on an adopted open Request. | Browser generates C42, trusted production Claim commits one Request and active primary assignment, justified card installation occurs and fresh reload retains the mutation. |
| A lower-level integration test posts a manually encoded valid command while the actual Claim button is disabled or broken. | Credit trusted route/model fixture only; fail independent real-browser positive acceptance. |
| Alice's card lacks a justified XTDB observed basis though Claim is still a semantic operation. | The managed control is unavailable or structural/render validation rejects the missing binding; no anonymous HTMX fallback. |
| Two eligible helpers race to claim the same open Request using distinct commands. | At most one open-to-claimed incorporation succeeds; rejected or uncertain competitors keep typed outcomes and no second active primary. |
| An unrelated XTDB transaction advances X17 to X23 before Alice clicks. | No automatic stale-command rejection; the real model evaluates protected current Request and Membership dependencies. |
| Alice's active Membership is revoked after a valid card was rendered. | Trusted Request model rejects the new Claim with no partial assignment despite the old visible affordance. |
| Claim commits but its response or canonical Hiccup rendering fails. | Model truth remains committed; participant retains unknown/uncertain settlement and authorized command-specific recovery, not fictitious rollback. |
| C42's response is lost; Alice retries with the same binding after the Request became claimed. | The *finished* resolve-or-incorporate path returns a permitted historical result without replaying the mutation; a current implementation lacking durable records must not claim that guarantee. |
| C42 succeeds and a later legitimate Reassign replaces the current helper. | C42's permitted historical replay still reports its old incorporation; fresh authorized acquisition reports current new helper. |
| The browser reports a claimed card optimistically but no authoritative active primary assignment exists. | Do not accept DOM-only success; rollback/supersede provisional presentation and fail the positive product result. |
| Alice Unclaims after a successful Claim and follows the rendered Unclaim control. | End the active primary assignment and reach the model-defined open state, then confirm by fresh authorized read. |
| A helper clicks Mark on the way and later Complete from legal current states. | Verify real production =:on-the-way= and =:done= transitions, required assignment continuation/closure and persisted reload. |
| An eligible requestor Cancels a separate Request. | Confirm the model-defined =:cancelled= result and ended assignments without borrowing helper-only authority. |
| A manager selects a different eligible helper in the real Reassign menu. | Require browser-generated selected-target command, trusted manager/target guards, historical assignment end, new active primary and persisted reload. |
| A nonmanager sees a forged Reassign action or a stale selector includes an ineligible helper. | Rendered options cannot grant permission; trusted Request model rejects unauthorized/ineligible target without partial Reassign. |
| A full lifecycle browser test passes while Create, login, local search, Refresh or details never work. | Preserve the bounded lifecycle success but fail the broader independently selected HumanHelp product profile. |
| A remote connected browser receives advisory after Alice's Claim. | Do not silently adopt new remote data; preserve advisory debt and the separately permitted one-user-Refresh acquisition. |
| A refresh/acquisition returns an older card after a newer justified installation. | Preserve the newer scoped observation and participant owner; late callback cannot overwrite canonical state. |
| An already consumed one-use Refresh grant is paired with a duplicated SSE advisory. | Duplicate invalidation cannot manufacture another user read grant or erase unresolved advisory obligations. |
| Browser session for the helper is absent or forged, despite a syntactically valid C42. | Trusted boundary rejects principal substitution; neither operation metadata nor certificate supplies authentication. |
| A real Chromium test exercises Claim, Unclaim, On-the-way, Complete, Cancel and Reassign with proper browser-generated commands. | Credit the scenarios actually observed, including committed reload and browser diagnostics; no claim of full distributed/fault/response-flow coverage or of test execution without a run. |

These scenarios keep the R4 user-facing test architecture:
unit model checks, Choreo projections, structural preflight,
effective rendered affordance, server integration and
real Chromium/HTMX product acceptance are distinct gates.
No test may create the real browser wire command for it
or treat a report map as authentication. Positive
cases must stay reachable while all negative cases
are correctly rejected or reconciled.
