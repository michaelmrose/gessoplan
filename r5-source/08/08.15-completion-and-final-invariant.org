** Completion gates

Completion means all applicable gates hold for the identified build and qualified
runtime profile. Passing gates for a subset is reported as that subset; an open
product contract or unqualified backend assumption cannot be hidden by a green
aggregate label.

| Gate | Required evidence |
|------+-------------------|
| 1. Production model authority | All example mutations use public production semantics with protected dependencies, command disposition, and correct Request/assignment results. |
| 2. One admitted source | Startup, plans, routes, providers, acquisitions, rendering, inspection, and tests consume the canonical application construction. |
| 3. Actual host adoption | The serving host and relevant writer paths demonstrably use the admitted bindings and selected policy. |
| 4. Browser correspondence | Exact generated runtime/assets are served and used; stale or incompatible bindings are rejected. |
| 5. Claim end to end | A real rendered Claim control reaches persisted production ownership and settles correctly without manufactured protocol data. |
| 6. Lifecycle completeness | Every required lifecycle capability has an eligible successful browser fixture and the applicable negative/recovery cases, including real Reassign selection. |
| 7. Rich board | Creation, immediate local visibility, local search/options, terminal display, details, continuity, and the selected response interaction work. |
| 8. Selective multi-client adoption | Remote changes remain advisory; local results adopt only their permitted scope; unrelated debt survives. |
| 9. Refresh correctness | Explicit grants, actual scoped coverage, race protection, physical completion, and remaining-debt behavior meet this part's contract. |
| 10. Failure recovery | Unknown commands, failed installation, publication crash, reconnect gap, and stale continuation have tested usable paths. |
| 11. Structural enforcement | Controlled malformed assemblies, renders, protocols, assets, and installation bindings fail at their specified boundaries. |
| 12. Semantic evidence | Applicable finite/proof obligations, rule/operation exercise, source bindings, opaque premises, and writer-coverage limits are reported honestly. |
| 13. Qualified substrate | The selected Biff, HTMX, browser, compiler/build, and XTDB profiles meet the assumptions on which the claims depend. |
| 14. Independent browser acceptance | Real controls and sessions produce expected visible and persisted outcomes with no unexplained failures; deleting a promised capability fails acceptance. |

The response interaction at [[#decision-humanhelp-response-flow]] remains a
specific product decision and blocks the corresponding full-completion claim
until selected and tested. The remote lifecycle policy at
[[#decision-humanhelp-remote-lifecycle-adoption]] is selected here and is part of
the required multi-client oracle.

** HumanHelp proving-application invariant

The HumanHelp example is a useful application of production model truth. It has
one admitted construction, an actual installed realization, and independently
specified user capabilities. Its browser controls preserve semantic identity;
its trusted operations enforce current authority and atomic dependencies; its
command outcomes distinguish historical incorporation, rejection, and uncertainty.

The creator can see a correlated confirmed Request promptly without adopting
unrelated remote work. Remote creation and lifecycle changes remain advisory
until explicit Refresh, except for separately admitted local-result/recovery
scopes. Search, sort, visibility, and continuity operate on permitted adopted
information. Refresh records adoption only after safe physical installation and
discharges only the obligations that its actual scope and evidence cover.

Application claims remain proportional to their evidence. Executable semantics,
conditional proofs, backend qualification, installed-path enforcement, and real
browser acceptance support different conclusions. HumanHelp must make their
connections concrete while preserving the assumptions and limits of each.
