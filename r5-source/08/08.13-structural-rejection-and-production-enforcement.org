** Structural rejection and production enforcement

The HumanHelp proving application must demonstrate *selective*,
source-derived rejection: an invalid operation, construction,
rendered action, runtime invocation or physical continuation is
rejected at the first boundary that actually has enough trusted
evidence to reject it, while a nearby legitimate HumanHelp action
remains executable. A clean report is not an execution credential.
Passing a test by rejecting every operation is a failure of the
independent positive product contract.

The finished system does not solve this by maintaining a second
example-owned operation registry, a hand-copied route inventory, or
checker fixtures that silently substitute for the production
application. The production Request model, Request Choreo, concrete
HumanHelp routes, actual server realization, Live acquisition
graph and generated browser artifact are the sources from which the
canonical assembly and its checks are derived. Tests intentionally
damage *one* of those real sources or one installed boundary, then
exercise the same checker, renderer or dispatcher used in service.

*** Admission stages and first enforcing boundaries

The selected assurance policy assigns each check to the earliest
boundary at which its actual evidence is available. Static
construction may decide a missing typed operation or route; it
cannot invent the future authenticated principal or the current
Request/assignment prestate. Concrete rendering can inspect the
supported actual Hiccup/HTMX/native form coordinates; it cannot
prove that an arbitrary future script emits no other request.
The trusted route can bind untrusted input to the selected operation
and real actor; the production model and guarded XTDB transaction
decide commit-time business eligibility. A physical adapter can
deny an obsolete target's effect only while it owns the actual
admission/installation boundary.

| Stage | Evidence and responsible rejection |
|-------+------------------------------------|
| Source/semantic construction | Unknown operation, invalid role or impossible plan, undeclared required recovery, or unclosed operation/source dependency |
| Application assembly | Missing required browser plan, trusted executor, route, provider, publication or authoritative acquisition edge; route/operation ambiguity or contradictory server binding |
| Build and deployment admission | Invalid source→generated-plan→artifact receipt/bytes relation, unsupported compiler/runtime profile, stale or mismatched physically served asset, or incompatible application generation |
| Actual structured-render/serialization | Enabled but unprepared action, missing required observation, anonymous collision with a reserved semantic route, conflicting effective request coordinates, or unsupported output outside the selected enforced profile |
| Trusted HTTP/command ingress | Malformed protocol, method/path/subject/operation mismatch, forged identity, incompatible command binding or denied required disclosure |
| Current model and transaction | Changed Membership/Organization/Request eligibility, conflicting primary assignment, failed current guard, qualified duplicate/exclusion result, or invalid domain transition |
| Browser effect and acquisition | Unauthorized collection expansion, ungranted Refresh, invalid progression, retired subscription/target/execution or stale physical rollback |
| Host installation and execution | Invalid or replaced checked handler, unsupported Biff start order, unmediated writer, mismatched runtime capabilities or discovered coverage gap under a mandatory policy |
| Postcommit observation/recovery | Qualify the actual outcome, preserve unknown and repair obligations, never reclassify an already committed Request as precommit rejection |

A checker must not move a failure earlier by assuming facts it has
not observed. Nor may the application defer a statically detectable
missing route until the first user clicks Claim. If an error
appears after a real commit, the responsible boundary blocks
invalid output or later effects and initiates recovery; it cannot
retroactively deny the successful transaction.

*** Controlled defects in one actual production construction

Each defect fixture starts with the ordinary real HumanHelp
application constructor and its source-owned production Request
Choreo/route/Live declarations. The test removes, substitutes or
changes one declared edge *before* the relevant check, or exercises
a specified post-admission physical replacement. The remaining
sources stay real so failure is attributable to the selected
defect. The test records the original and changed source/generation,
first rejecting boundary, typed diagnostic and prohibited effect;
the paired valid case is run through the same boundary.

| Controlled defect | Required result and positive counterpart |
|-------------------+------------------------------------------|
| Unknown =:request/claime= or valid operation with incompatible role | Source or preparation reports unknown/mismatched operation and originating view; genuine Claim remains admitted |
| Missing Claim browser plan or incompatible plan/role | Assembly reports the exact required realization; no fallback anonymous =hx-post=; matching generated Claim plan works |
| Missing route, method mismatch, duplicate ambiguous route or route points to Cancel | Assembly/installed dispatch rejects the actual unresolved or contradictory operation/route/Request binding; valid Claim route reaches the intended server |
| Missing current-time, trusted actor, transaction, seed or qualified read provider | Statically absent capability fails before serving; a dynamically unavailable provider fails at trusted invocation without unauthorized mutation; supplied valid provider works |
| Missing initial board acquisition, fragment/stream route, settlement or denied-disclosure recovery | Admission reports the missing required path; declared incomplete dynamic condition cannot strand a pending operation; intact acquisition and recovery succeed |
| Missing exact browser artifact, stale plan stamp, wrong bytes or forged receipt | Supported build/start/serve check rejects with expected and actual artifact lineage; rebuilding and serving the actual matching bytes succeeds |
| Enabled action missing required =:observed-basis= or canonical operation identity | Real preparation/rendering rejects or presents an explicitly admitted unavailable/alternate control; a qualified enabled Claim is rendered correctly |
| Ordinary HTMX/native form submits to protected Claim route | Actual supported output scanner catches anonymous method/path collision; trusted route separately rejects missing semantic protocol; normal read-only form and real managed Claim remain legal |
| Form owner/submitter overrides or keyword/string duplicated request attributes | Actual effective method/path and ambiguous attributes cannot evade the selected structured check; equivalent nonambiguous canonical form passes |
| OOB/error/deferred/cached rendering bypasses the guard | Serving boundary rejects unsupported managed output or supplies the same actual serialization check; valid deferred or ordinary response under its declared profile is served |
| Forged browser principal, Request retargeting or valid-plan command on wrong lifecycle route | Trusted route ignores client identity as authority and refuses incompatible operation/subject; correct authenticated command reaches public Request core |
| Incompatible C42 reuse or lost C42 result | Current permitted command resolution rejects binding reuse and preserves unknown delivery; exact permitted replay does not reincorporate |
| Unqualified advisory used to adopt remote R or repeated one-use Refresh | Live/acquisition effect admission refuses unauthorized membership/permission use; a separate genuine permitted Refresh succeeds |
| Stale E1/T1 callback after newer T2 or removed target | Final physical effect gate refuses installation/rollback; current T2 and authorized continuation remain intact |
| Correct preflight report but different Ring handler actually served | Startup/host adoption blocks the selected protected deployment claim; canonical installed handler can serve the valid page |
| Omitted/false read-only background writer or unrestricted XTDB capability | Mandatory writer-coverage claim stays open or deployment blocks; separately issued covered writer succeeds within its admitted scope |
| Source removes Reassign from model, Choreo and generated checks | Independent product acceptance fails even though the reduced declared catalog is closed; eligible real Reassign succeeds in the positive fixture |

A defect that changes several facts at once is not an oracle for
which one should have failed first. The test either isolates them
or reports their causal ordering and the evidence available to
each boundary. A failure at an earlier supported gate can make
later gates inapplicable; it does not demonstrate those later
gates would work or reject correctly. The positive counterpart
is necessary to exclude a permanently disabled or
reject-everything application.

*** Physical rendering and both directions of protection

For HumanHelp managed lifecycle routes, the *producer* and
*consumer* protections are complementary. Supported actual
pre-serialization structured rendering cannot emit a live
anonymous action to a protected route, even when its HTML
looks like an ordinary button. The trusted receiving handler
cannot execute such an action even if a malicious client
manufactures it, the served markup was not produced by
HumanHelp, or a later JavaScript sends it. Neither guard is
permission for the other to be absent from the declared
protection profile.

Rendering checks the actual expanded concrete occurrence,
including conditional affordance selection, target identity,
effective HTMX inheritance, native form owner/action/method and
submitter overrides, supported OOB destinations and plan/basis
preparation. A disabled-looking control with a still-active
request route is not a valid disabled control. Missing
observed basis is not silently converted to a guessed Request
revision, wall-clock time, anonymous normal POST or inferred
authorization. The application selects only an expressly
admitted unavailable/alternative state or rejects the render.

The selected Hiccup/serialization mechanism has a finite
language and a physical boundary. An inspector that receives
canonical Hiccup cannot certify pre-serialized HTML,
arbitrary JavaScript-produced requests, future middleware
substitution, deferred work outside its guard, or bytes
served by a different handler. Those paths require a
connected enforcement mechanism, explicit disallowance
under the admitted profile, or an honestly narrower claim.
A passing snapshot render does not establish universal
dynamic-output coverage. Unchecked raw HTML is not cured
by adding a success-shaped value to the assembly report.

If an output check rejects *before* sending a protected
command, the positive oracle establishes that no protected
mutation was submitted. If it rejects a response after a
previously committed Claim, the mutation remains authoritative:
the correct oracle is blocked invalid output, preserved
command/outcome evidence and permitted authoritative repair.
It is wrong to assert Request remains open merely because
a postcommit response-render guard failed.

*** Trusted actor binding and command disposition

For a routed Claim(R17), the trusted boundary uses the
authenticated current principal and the concrete route's
operation/Request selection. The browser-supplied
=:principal=, target-helper string, role name, client ID,
plan stamp, command identity and reported basis are data
to verify, not an authorization token. Route-selected
Claim cannot perform Cancel, reach R18, invoke an
arbitrary Clojure callable or bypass the current
production Request/RequestAssignment/Organization/
Membership/Location guards.

A malformed command, invalid transport and incompatible
binding can be rejected *before domain invocation*. A
well-formed authenticated command may instead fail a
model-defined current eligibility rule after trusted
execution begins. That is a legitimate domain rejection,
not necessarily an application-assembly fault. A
commit followed by lost outcome remains uncertain to
the participant until qualified command-specific
reconciliation; timeout, denied disclosure and missing
historical lookup are not evidence of model rejection.
A duplicate exact binding is resolved under the
selected durable-command protocol; an incompatible reuse
must not obtain another user's historical result.

The test checks separately for absence of prohibited
model invocation, absence of new transaction
incorporation, absence of unauthorized disclosure,
and absence of stale physical installation. These
are different postconditions. A checked route that
refuses Claim before invocation should not be
credited with proving every conceivable concurrent
database writer obeys the same invariant.

*** Runtime installation, source identity and report integrity

Gesso's canonical managed Biff/Aleph path must install
the actual checked Ring handler *before* admitting
protected HTTP requests. The exact
=application-handler-module= object is part of the
native module collection once; its required qualified
module ID is first in the declared Biff start order.
The startup checker rejects a missing/duplicated
module, a forged module carrying the correct ID,
a non-ID component-function start sequence,
a mismatched current assembly or noncallable
Ring handler. The selected Aleph adapter must
serve the resulting handler, not an older Var or
different unwrapped function.

The host admission evidence is invalidated by later
handler/module/route/asset replacement unless the
replacement is admitted and checked under the new
generation. If a server intentionally uses raw Ring
responses, off-process writers or a separate
HTTP entrypoint, the production policy must
enforce or exclude them explicitly rather than
inherit the canonical wrapper's limited guarantee.
A current in-memory report does not prove which
callable the deployed server actually installed.

ApplicationAssembly and checking reports are
derived from the original source objects, verified
identity and current underlying artifact; arbitrary
Clojure maps are not capabilities. A caller must
not gain authority by copying a passing report and
changing =:valid?=, =:errors=, =:analysis= or an
assembly field, swapping an operation registry,
adding a favorable proof badge or using a stale
content-identical replacement provider. Genuine
reconstruction/rechecking is required when the
selected source, host callable, compiler receipt,
actual served asset or admission generation
changes. Even a well-formed checked report is
descriptive of its stated scope and never by
itself permission to perform a protected effect.

A structural preflight can check known supplied
writers and enforcement edges; it cannot discover
every process with direct XTDB access by
enumerating the registered Biff modules. The
assurance report distinguishes declared,
enumerated, physically observed and proven
restricted paths. An unclassified writer remains
an open mandatory condition or blocks
installation under the selected policy. It
cannot be hidden by relabeling a descriptor as
read-only or reporting an uninspected inventory
as empty.

*** Dynamic failure completeness and recoverability

Static admission does not guess future transaction
results or assume every GET, SSE stream and
subscription will succeed. It must nevertheless
establish an allowed continuation or recovery
policy for each dynamic condition that can strand
a managed command or adopted board obligation:
missing/expired observation, authoritative
rejection, submitted-but-unknown transaction,
unavailable disclosure, lost subscription, failed
fragment reread, partial DOM/OOB installation,
obsolete plan or target, exhausted retry budget,
and unavailable trusted provider.

Each continuation identifies its owner, permissible
current authority/read scope, bounded retry or
user action, release of obsolete physical rights,
and what evidence can terminate uncertainty.
An invalid assembly is rejected if it has no
declared legal recovery route for a required
uncertain branch, even when a particular test
happens to succeed. A permitted explicit
degraded path is named and reflected in the
assurance claim; the system must never silently
turn a semantically protected lifecycle command
into anonymous HTMX or turn participant unknown
into rejected.

Recovery and static safety are reported
separately: correctly preventing an unsafe
stale swap is a safety success, while eventual
convergence depends on declared provider
availability, scheduling fairness, retention
and (for explicit Refresh) permitted user
action. Runtime denial may therefore preserve
visible pending/advisory debt rather than
fabricate completion.

*** Structured diagnostics and acceptance

Each rejection supplies stable machine-readable
category, precise proposition, original source
or physical occurrence, application generation
where relevant, operation/route/target subject,
expected versus actual relation where safe,
first responsible enforcement boundary,
and whether the effect was already submitted
or committed. Diagnostics may report unknown
rather than an invented yes/no; errors from
domain guards and from assembly incompatibility
retain distinct types and recovery contracts.

The diagnostic audience determines allowed
detail. Redact authenticated credentials,
full command bodies, private Request content,
unverified tenant identifiers and protected
read/query results. Useful developer-local
explanations may show source paths, selected
operation names, mismatch categories and
safe route templates; they must not leak
cross-Organization information to a browser
or untrusted requestor.

#+begin_example
Positive and adverse — one real production boundary:
  Good Claim(R17): canonical constructor, installed handler,
    enabled bound control, trusted principal, guarded commit,
    authorized readback and browser settlement all succeed.
  Missing Claim plan: same source construction with only
    required plan removed -> preflight rejection, no fallback.
  Paired valid case still succeeds after restoring the plan.
#+end_example

#+begin_example
Adversarial — anonymous request and forged principal:
  A real Hiccup/native form inherits the protected Claim POST,
    but lacks managed operation/protocol metadata.
  Supported final render check rejects its emission.
  Independently a forged external POST supplies :principal Mallory
    and incompatible Claim/R17 wire values.
  Trusted ingress does not execute as Mallory or mutate R18.
#+end_example

#+begin_example
Adversarial — postcommit output failure:
  C42 validly commits Request R17 + primary assignment.
  A later output renderer fails structural enforcement.
  The invalid response is not delivered, but XTDB commit persists.
  Recovery obtains qualified current state and historical
    C42 outcome separately; the server never reports "not committed"
    merely because its HTML response was blocked.
#+end_example

#+begin_example
Adversarial — startup identity and escaped writer:
  The browser receipt and ApplicationAssembly check successfully.
  HumanHelp supplies a noncanonical Biff module/incorrect order,
    or Aleph invokes a different unwrapped Ring handler.
  Service admission refuses the installed-boundary claim.
  A background raw XTDB writer outside the checked module catalog
    leaves global writer closure explicitly unproved.
#+end_example

HumanHelp's structural rejection gate exercises
the production preflight constructor, actual
rendered responses and installed host path
against controlled defects: unknown operation;
missing/mismatched plan, route or server;
missing provider and initial acquisition;
anonymous native form and HTMX action;
forged/mismatched command; stale asset;
handler/module mismatch; unauthorized
advisory/Refresh; retired effect; hidden writer;
and required capability removal. Each case
has a paired usable positive through the
same enforcing boundary, a precise typed
diagnostic and an appropriately scoped
no-prohibited-effect oracle.

A negative fixture that passes only because
the app never starts, no browser control
exists, all requests are rejected, or a
fake checker is used is insufficient. The
complete product still requires the real
HumanHelp Chromium lifecycle and two-client
board/Refresh behavior of 08.12. Section
08.14 joins connected evidence and operational
limits; this section specifies enforcement,
not a claim that the currently inspected
sources have already passed every test.
