## R4 obligations retained, expanded and qualified

1. **Real authentication is a separate premise.** Genuine sessions,
   multiple independent user/browser contexts, issuance/expiry, current
   production User status and actual installed middleware remain required.
   Gesso's role binding assumes a trustworthy actor source; it does not
   certify that HumanHelp has authenticated the person. Well-shaped
   `:session :uid` alone is not production credential verification.
2. **No browser principal privilege.** A Client/Choreo User ID,
   helper target, Request ID, route, opaque certificate, CSRF token or
   provider basis cannot become the trusted principal. Real Request,
   Organization, Location, Membership and User model dependencies
   are checked where used.
3. **Context provenance must be coherent.** A trusted middleware-supplied
   `:current-user/id` can be valid, but it must agree with the active
   authenticated session or be covered by an explicitly granted
   impersonation policy. Browser/session contexts with conflicting
   principal fields may not silently acquire another user's scope.
4. **Read/disclosure is independent from write permission.** Board
   lists, single details, search indices, target-helper menus,
   command-result lookup and retained projection handles all
   require current permitted disclosure and appropriate timing.
   Unauthorized Request existence and other tenant-scoped facts
   may require a deliberately nonrevealing response.
5. **Recipient-safe connected Live.** A per-user and broad app
   connected-client scope are delivery selectors, not read
   authorization. OOB pending/stream drains must recheck the
   actual recipient, session and generation. Payload content
   and even scoped identity/count metadata must satisfy
   the intended disclosure rule.
6. **Host/HTTP integrity.** Session-bound CSRF, bounded parsing
   and schema validation, route-selected Request identity,
   allowed target-helper versus forbidden principal, escaping,
   script/OOB target constraints and actual Biff middleware
   placement are required before protected effects.
7. **Publication follows commit, never replaces it.** Request/assignment
   state is not copied into a second Live domain store. Direct
   correlated initiator settlement and remote advisory have
   distinct proof and failure paths.
8. **Interest closure includes dependent writers.** RequestAssignment,
   Membership, Organization, Location and permitted User display
   changes can affect board membership/disclosure without an
   immediate Request document update. Registered Request-only
   Live rules do not establish complete physical/writer coverage.
9. **Primary durable intent is conditional on backend qualification.**
   The strong finished-system profile records original command
   incorporation/result binding and required publication intent in
   a physically qualified atomic transaction. Stable at-least-once
   workers and explicit crash/retry/retention contracts recover
   publication intent; duplicate advisories do not duplicate
   domain mutations or grant reads.
10. **Selected weaker profile stays honest.** An application may
    select periodic reconciliation, an explicit reconnect action
    or user Refresh under stated availability premises. A
    postcommit callback or finite mailbox cannot be called
    persistent guaranteed notification.
11. **Initial subscription and reconnect gap.** Subscription/read
    ordering must be source-qualified via an XTDB/provider
    read fence, durable replay or authorized reacquisition.
    SSE client ID, stream cursor and XTDB progression are distinct.
    Reconnect restores advisory continuity without a silent
    remote-board adoption exception or free user Refresh.
12. **Same single/multi-node semantics.** Failover must restore
    interest and coverage, with safe duplicate invalidation or
    qualified fresh acquisition, without promising visible
    convergence while a client is permanently offline.
13. **Positive/adversarial source-to-browser cases.** Twenty-five
    histories cover real login, anonymous reads, spoofed context,
    actor versus target, unauthorized data, cross-user OOB,
    CSRF/encoding, dependency-only updates, crash-before-publish,
    duplicate delivery, lost interests, stale clients, two-person
    scope, no user-grant amplification and independent product
    acceptance. Neither negative-only checks nor a static fixture
    count as complete product proof.

## HumanHelp `dev` source actually inspected

- `src/net/humanhelp/middleware.clj` supplies
  `wrap-signed-in`, checking that session `:uid` has
  an allowed UUID/string shape, and site defaults
  including session/anti-forgery middleware.
  That is concrete protected routing, but
  not end-to-end verification of session
  issuance, expiry, account status or
  every route's middleware order.
- `src/net/humanhelp/example/app.clj` declares
  protected routes under `wrap-signed-in`
  and resolves actor display through
  `client-plumbing/current-user-id`
  and public `user.core/require-user`,
  rather than a separate example User model.
  Public Request Choreo and production
  Request guards still decide protected
  operation authority.
- `src/net/humanhelp/client_plumbing.clj`
  currently prefers `:current-user/id`,
  `:user/id` or `[:user :xt/id]`
  context fields ahead of Biff
  `[:session :uid]`. Those fields
  must have verified trusted provenance
  or correspondence with the active
  session before they can determine
  a protected User/client scope.
  This is a **qualification gap**,
  not proof that an untrusted client
  can currently inject those fields
  through installed middleware.
- The same `client-plumbing` defines
  per-user and app-wide `[:app/all]`
  connected scopes, pending/stream
  routes and recipient-rendered
  OOB delivery. Cross-tenant safety
  and session-bound pending-drain
  need explicit independent checks;
  a client ID is not authority.
- `src/net/humanhelp/example/live.clj` compiles
  production Location-scoped
  Request toolbar/list interests,
  excluding `:created` from
  managed invalidation but admitting
  `:updated`. Thus present source
  is not yet compliant with the
  selected all-remote lifecycle
  advisory-only policy. Additional
  Membership/Organization/assignment
  and User-display interest
  dependencies need complete
  inventory/proof.
- `example.live/send-new-request-advisory!`
  sends a non-adopting OOB/Toast to
  other connected clients, under
  authenticated creator exclusion,
  using app-wide scope. It does
  not deliver canonical Request
  list markup in the advisory.
- `src/net/humanhelp/example/app.clj`
  sends the creator's success response
  and invokes a separate
  best-effort advisory helper.
  If a process fails in that
  interval, source does not
  demonstrate a durable
  same-transaction outbox
  or eventual remote delivery.
- `test/net/humanhelp/example/live_test.clj`
  exercises production-scoped change
  expansion/progression and
  fragment query source.
  `test/net/humanhelp/example/app_test.clj`
  checks route/operation mismatch
  and fixture failure boundaries.
  Their current scope does not
  cover real login issuance,
  forged context precedence,
  client-ID cross-session
  reuse, publication crash
  recovery or two-node
  subscription/interest failover.
  Source inspection is not
  a new passing test run.

## Gesso v1622 correspondence and missing evidence

- `src/gesso/model/tx.clj` composes
  Request `:commands`, guarded
  `:assertions`, observed
  `:changes` and `:emit`
  and calls `live/transact-and-notify!`.
  On success it preserves
  transaction progression and
  `:commit/status :committed`.
  This is meaningful
  model transaction + Live
  integration, not evidence
  of a complete persisted
  command record/outbox
  and crash-resumable worker
  for HumanHelp.
- `src/gesso/live/client.clj`
  explicitly implements ephemeral
  connected client SSE/OOB
  channels, bounded pending
  fragments and disconnected
  mailbox limits. Those are
  app-agnostic physical delivery
  mechanics, not tenant-aware
  permission, durable publication,
  exact Recipient lookup, no-gap
  subscriber inception or
  client DOM adoption proof.
- `gesso.live.progression`
  has opaque provider bases;
  `gesso.live.htmx` and
  `gesso.live.browser.continuity`
  implement fragments/client
  mechanics but do not grant
  HumanHelp read rights or
  automatically prevent
  subscription loss. Typed
  permission/advisory debt
  and source-qualified
  XTDB replay/refinement are
  separate obligations.
