** Routes, concrete rendering, assets, and host lifecycle

The HumanHelp proving application closes one installed application, not
four mutually agreeing diagrams. Its real production Request semantics,
trusted executor, Reitit/Biff routes, browser plan, generated assets,
rendered controls, Live/acquisition paths and running Aleph handler must
correspond to one admitted application generation. Part VII owns generic
assembly and enforcement; HumanHelp supplies its actual production facts,
real user capabilities and independent operational evidence.

*** One route authority, semantic protocol and writer inventory

=example.routes= owns route identity and method/path facts. The active
Reitit router, =example.app= handler selection and the canonical
=example.application-preflight= constructor consume those same facts.
The example may use separate route IDs for Claim, Unclaim, Mark on the way,
Complete, Cancel, Reassign, Create, board reads, fragment acquisition,
Refresh and SSE, but must not maintain a shadow route catalog for tests
or preflight. Normalized path parameters and effective HTTP method must
select the exact declared operation, subject and trusted executor.

A protected lifecycle route accepts the required semantic protocol
only when the decoded command, bound Request, declared operation and
installed server realization agree. =POST /requests/R17/claim= cannot
execute a Cancel command, apply to R18, select an arbitrary Clojure
function from a URL, or treat a client-provided User ID as the trusted
principal. An absent/malformed protocol, operation mismatch, unknown
Request or incompatible command binding rejects before protected
mutation. URL and form selectors are untrusted input, not authorities.

A semantic operation may be implemented by a trusted route before a
particular user can see its eligible control. Supported operation,
physically installed handler, user-facing affordance and current model
permission are separate claims. HumanHelp's complete product contract
requires eligible positive controls for all six lifecycle operations;
the current renderer's inventory cannot define that requirement away.

Ordinary GETs, ordinary non-mutating HTMX, forms and deliberately
admitted non-Choreo operations remain legal. A Create Request or other
route that writes invariant-bearing state is nevertheless a real
authoritative writer and belongs in operation/writer coverage, whether
or not it uses optimistic Choreo. So do imports, fixtures, startup
initialization, administrative work, scheduled jobs, provider callbacks
and other physically reachable mutation paths. Absence of a declared
writer is not proof that none can run. Each reachable writer is either
covered by an explicit rule and interference/effect contract or reported
as an uncovered or unknown boundary, never silently renamed read-only.

Live fragment, initial acquisition, advisory-stream and authoritative
reread routes also share their actual route specifications with the
corresponding source-owned interest, result and adoption contracts.
The serving route may not quietly diverge from the assembled Live route
or publish a transport-success label as authoritative model knowledge.

*** Actual rendered affordances and request coordinates

An admitted assembly is not sufficient if the actual emitted view
selects a different request. The finished HumanHelp serving boundary
checks each concrete enabled rendered occurrence at the last supported
structured-response point before serialization, after component
expansion and preparation. It checks semantic operation identity,
required observed basis, browser plan/artifact compatibility, current
binding, effective request method/path and route correspondence, and
the permitted target/transport/effect shape. An inspected test fixture
does not certify a different branch rendered for a real viewer.

The supported transport profile includes real HTMX =hx-get=,
=hx-post=, =hx-put=, =hx-patch= and =hx-delete= requests, applicable
native forms and submitters, explicit =action=/=method=, form owners,
=formaction= and =formmethod= overrides, disabled controls, inherited
attributes, OOB fragment destinations and semantic metadata needed
by the plan. The final user-visible and physically executable request
coordinates matter; a decorative parent button or omitted =type=
must not hide a native submission path. A disabled-looking button
retaining an active enabled request path is not accepted.

A concrete enabled Claim cannot omit its required command or
observed basis, and it cannot downgrade into an anonymous ordinary
HTMX POST to a reserved lifecycle route. If a target helper or
current observation is unavailable, the renderer exposes the
declared acquisition/input/unavailable state or rejects the invalid
render. It must not invent authority or silently change the operation.
An explicitly admitted ordinary mutation uses its own checked
contract, not a false claim to semantic Choreo coverage.

The check is scoped to the actual supported render/transport language.
String HTML bypassing structured rendering, user-provided raw markup,
dynamic client-generated requests, opaque callbacks, unbounded
JavaScript, and transport features not examined by the selected
profile require an independently enforced boundary or explicit
exclusion from a narrower claim. A scan of canonical Hiccup alone
cannot certify all possible DOM or network behavior. The trust
boundary additionally requires correct escaping, CSRF/session policy,
permitted disclosure, and rejection of unauthorized script or
request-capable markup; a passing route scan does not prove these.

*** Deferred, cached and multi-target response completion

Checking only the synchronous handler return is insufficient for
deferred Hiccup evaluation, streaming HTML, callbacks, cache reads,
alternate response helpers, error views, redirects and OOB payloads.
Each path that can emit a managed affordance carries its admitted
application and current output-check context to the physical
serialization/serving boundary, or is explicitly disallowed by
the qualified profile. A cached fragment is revalidated against
the currently served assembly and recipient policy when required;
a stored "checked" marker from a different generation is not an
unrestricted permit.

Out-of-band updates and multi-target installations have actual
target identities and completion reports. A valid response before
serialization does not prove every requested DOM effect occurred.
Partial OOB completion retains its specific recovery obligations.
A committed Request mutation is not reversed by a later failed
render or incomplete browser installation; the participant must
perform authorized result acquisition or truthful repair.

For ordinary routes returning legitimate raw HTML or other formats,
HumanHelp declares the separate check/escape/serving contract.
For protected managed routes the output boundary must be connected
to the actual installed handler and cannot be bypassed by replacing
the handler after preflight. Application preflight rejects a missing
or incompatible enforcement connection where the selected deployment
profile requires it.

*** Generated browser entrypoint and physical asset identity

The browser declaration and role-local plans come from the same
admitted production Choreo as the server assembly. The supported
build path generates a browser entrypoint embedding the exact
admitted BrowserAssemblyManifest, compiles it with the selected
ClojureScript/compiler configuration and physical realization
options, and records a receipt for the resulting artifact bytes.
Startup verifies the current manifest-to-receipt correspondence
and the receipt-to-bytes correspondence before serving managed
HTML. A matching filename, hand-copied stamp, or receipt for
unrelated JavaScript is not evidence that the browser implements
the admitted plans.

The build claim is conditional on its actual producer, compiler,
linked runtime, dependencies and tested bootstrap contract. A hash
does not prove arbitrary minified JavaScript semantics. The assembled
publication inventory includes the script, its transitive required
assets, styles and any separately supplied HTMX/SSE/browser runtime
whose behavior the plan assumes. Their actual served URLs, bytes,
cache headers, integrity/correspondence mechanism and client load
order are qualified as part of the selected deployment, not inferred
from their existence on disk.

A page admitted with generation A must load assets compatible with
A throughout its supported lifetime, including after a rollout of B.
Identical URLs cannot switch to incompatible bytes under an A page's
feet. Use immutable versioned URLs and coherent publication sets, or
a specified generation-pinning/reload/retirement protocol with an
equivalent correctness argument. A CDN, filesystem, classpath
resource and the active HTTP server may each expose different bytes;
verifying a local build path alone does not verify what the client
actually retrieved.

*** Generation transitions, reload and old clients

Reload and deployment first construct, validate and stage a coherent
candidate B; activation switches the installed route graph, trusted
executor, browser artifact, current assembly and Live/acquisition
interfaces according to an explicit atomicity or compatibility
contract. It may not serve A's routes with B's command plan and a
stale A script as though those independent objects formed a valid
new application. Old pages either continue against a supported
compatible A boundary or receive a specified reload/repair response.

An already issued C42 can be recovered across a deployment only
through a qualified compatible command/disclosure contract. Its
retired local E42 execution, old target instance, pending listener,
HTTP callback or generated browser plan does not resume merely
because C42 remains historically meaningful. Background work,
connected SSE subscriptions, one-use Refresh permissions and
advisory debt are transferred, fenced, or retired under their
separate ownership/recovery rules. A reconnect is not automatic
authorization to adopt remote Request state.

A candidate that fails preflight never becomes an active half-B
generation. A crash between staged assets and application activation
must either leave a valid A available or enter the declared unavailable
recovery state; it must not expose an accidental mixture while
claiming successful service.

*** Qualified Biff, Aleph, HTMX and XTDB host contract

The finished application names an actual supported Biff release and
native lifecycle semantics, Aleph serving integration, HTMX and SSE
extension versions, browser/CLJS compiler and runtime, and XTDB
adapter/configuration. "Final Biff 2" or "the current database"
is not an executable compatibility contract. Changed versions,
configuration or physical topology require requalification of
the assumptions each dependent proof and integration gate uses.

At startup the trusted host initializes configuration, schema and
model transaction providers, database connection and required FX
capabilities, browser artifact, Live/advisory machinery and the
canonical application assembly in the declared dependency order.
It installs the checked actual Ring handler before Aleph admits
traffic. The canonical Gesso application-handler module appears
exactly once and at the required lifecycle position for a profile
using that native startup path. The server must use that resulting
handler rather than a different unwrapped Var or manually bypassed
entrypoint. No unchecked normal production path remains enabled.

Biff explicit FX input/previous-result flow supplies time,
transaction, authenticated principal and other required capabilities
through trusted providers. One request's context is not silently
merged into another's or replaced with browser-provided authority.
Any startup seed or fixture write is an authoritative ingress with
the same coverage obligations. Shutdown and startup failure release
database, Live, thread pools, subscriptions and HTTP resources in
the required order and preserve durable in-flight recovery promises.

Distinct authenticated clients must operate concurrently according
to request- and execution-scoped ownership. A global one-use lease
that serializes every HumanHelp write is not a valid substitute for
per-command exclusion, per-Request conflict resolution or qualified
XTDB atomicity. An intentionally narrow single-request test profile
does not certify the real multi-client service.

Backend qualification follows [[#req-backend-assumption-qualification]].
HumanHelp must establish the required atomic guard/write and
RequestAssignment uniqueness behavior, exact-binding command
exclusion/observation, query completeness and authoritative absence
where claimed, post-commit outcome and visibility guarantees, and
the effect of concurrent writers. The evidence has precise
version/configuration, source and physical execution scope; it is
not a proof of all XTDB behavior. A changed backend assumption
invalidates dependent certification until it is requalified.

*** Positive and adversarial installed-application histories

#+begin_example
Positive — checked Claim through the actual service:
  A production Request operation defines Claim(R17).
  The installed Reitit route selects Claim and trusted Request R17.
  Real rendered Hiccup prepares a valid managed control for helper A.
  The generated current browser artifact forms C42 and HTMX H1.
  The trusted Biff/Aleph handler validates the exact command binding.
  Production Request/assignment guard and transaction commit.
  Qualified settlement and current acquisition install the result.
  A fresh reload sees the authoritative claimed Request.
#+end_example

#+begin_example
Adversarial — valid startup label but wrong installed handler:
  Application preflight verifies an assembly and build receipt.
  An Aleph route starts with a separately wrapped or replaced handler.
  A protected response bypasses canonical render preflight.
  Admission fails for this deployment; a successful static fixture
  does not certify the physical server or its emitted controls.
#+end_example

#+begin_example
Adversarial — stale A page after deploying B:
  The A page still references /js/gesso-live.js.
  B replaces that same URL with incompatible script bytes.
  The page invokes an A plan against B's route/asset context.
  Deployment must pin matching A assets or force qualified reload;
  it cannot silently treat the mixed execution as admitted.
#+end_example

#+begin_example
Adversarial — deferred fragment and native form:
  A cached/deferred fragment materializes after the handler returns.
  A submitter inherits a POST action to the protected Claim route.
  The actual form lacks required semantic command binding.
  The final serving boundary rejects it rather than delivering a
  control that static render snapshots never inspected.
#+end_example

HumanHelp connected acceptance includes paired valid and defective
production-assembly fixtures: missing handler/module, route operation
or Request mismatch, absent plan, stale or forged build receipt,
wrong generated bytes, omitted browser dependency, incorrect served
asset URL, anonymous native form/HTMX collision, deferred unchecked
HTML, rejected B startup, resource leak on failure, writer-inventory
gap, stale A callbacks after B activation and simultaneous authorized
clients. Each fixture identifies the first real enforcing boundary,
asserts no prohibited effect or unauthorized disclosure, and preserves
the independent positive Create/Claim/lifecycle/browser outcomes.
This section describes the finished-system test obligation, not a
claim that present Gesso or HumanHelp already passes the full matrix.
