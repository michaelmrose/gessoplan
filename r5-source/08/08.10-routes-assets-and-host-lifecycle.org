** Routes, concrete rendering, assets, and host lifecycle

An assembled semantic route accepts the declared semantic protocol and maps it
to the exact admitted operation/interface and issued server realization. A
method/path match alone is insufficient. A URL parameter cannot select an
arbitrary callable or override the operation selected by the route.

Ordinary non-mutating routes and local controls remain legal. A route that writes
invariant-bearing state is classified as a writer even if it is not choreographic.
Background tasks, imports, administrative tools, fixture initialization, and other
writers receive the same scope treatment. An uninspected inventory is reported
as unknown, not as an empty list proving complete coverage.

*** Concrete enabled renders are checked

The production render boundary checks the actual expanded structured output,
including prepared action bindings, effective transport, targets, basis data,
plan compatibility, forms, and supported out-of-band effects. It must inspect the
representation that will be serialized, rather than a fixture render unrelated
to the served page.

An anonymous ordinary HTMX POST cannot occupy an assembled lifecycle route.
A missing operation identity, wrong route mapping, or absent required observation
is rejected at the responsible preparation/render boundary. Disabled controls
must not retain an active request path that bypasses their declared state.

Supported forms and browser effects follow the qualified profile. Where static
inspection cannot determine behavior, an explicit host contract and connected
runtime guard are required. The presence of an opaque function does not authorize
a claim that all of its possible output has been statically checked.

Deferred rendering, cached fragments, streaming chunks, and error responses retain
their assembly and output-checking context through the actual serialization
boundary. A synchronous guard around a handler is insufficient for work evaluated
after that guard has returned.

*** Exact browser artifacts and deployment compatibility

The browser plans and bootstrap are generated from the admitted source. The
selected build profile binds their manifest to the produced asset bytes and
compiler/runtime configuration. Startup and serving verify the corresponding
receipt and actual asset set. Copying a manifest label onto unrelated JavaScript
does not establish correspondence.

The claim depends on the generated entrypoint and trusted build process. A checker
cannot infer arbitrary minified JavaScript semantics from a matching external
stamp. Tests distinguish a stale manifest, wrong bytes, and an unqualified
producer rather than claiming one digest check solves all three.

Assets use immutable versioned identities. A page admitted under assembly A must
continue to receive A's matching assets during the supported overlap with assembly
B, or enter a declared compatibility/reload path. Installing B must not cause the
same asset URL to return incompatible bytes to A's page.

A stale continuation cannot cross a deployment simply because its command ID is
stable. Command recovery can continue through a compatible admitted boundary
without resuming an obsolete plan, target instance, or suspended effect.

*** Qualified Biff/HTMX/XTDB profile

The application names the supported Biff host, HTMX and extensions, compiler,
browser runtime, and XTDB adapter/configuration identities. It uses qualification
and conformance evidence for the actual behavior it relies on. “Final Biff 2”
is not an executable lifecycle contract or a durable version specification.

Host startup orders dependency readiness, application admission, installed
handler adoption, and exposure of traffic according to declared requirements.
The model/Live system must exist when a path needs it. Initialization that writes
model state is covered as an authoritative ingress. Shutdown and failed startup
release resources and do not leave a half-adopted application serving traffic.

Reload constructs and checks a new candidate before coherent activation. The
active application must not combine old routes, new plans, an old browser asset,
and replacement callbacks merely because each object was once independently
admitted. In-flight work follows explicit retirement or compatibility rules.

Request-scoped execution and effect ownership permit independent users to act
concurrently. A one-use global lease that rejects every overlapping request is
not an adequate general HumanHelp concurrency model. Narrow single-request
profiles may be tested as such but cannot stand in for this application's
multi-client requirement.

Backend qualification follows [[#req-backend-assumption-qualification]]. HumanHelp
requires evidence for atomic guard/write behavior, command exclusion, relevant
query/absence dependencies, commit-outcome interpretation, and observation
visibility. It does not claim a proof of all XTDB behavior. A version/configuration
change that invalidates one of those assumptions invalidates the dependent claim
until requalified, even if the application still starts.
