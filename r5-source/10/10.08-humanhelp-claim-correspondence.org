*** HumanHelp Claim as a correspondence slice

Claim's public semantic contract, admitted plan, physical transaction, and
participant observation have one connected meaning. The example is the
self-claim case. A separately authorized operation that assigns another helper
must bind and guard that target helper's Membership as well as the actor's
permission; it cannot reuse self-claim assumptions unchanged.

**** Source-owned identities, actor and helper distinction

The *source* of the Claim decision is the current public HumanHelp
production model and the application-selected Claim operation, not a
proof-only Request entity. The correspondence ledger binds the source
generation, actual public model interface versions, normalized Claim
operation, current actor and authority domain, complete original
operation/invariant catalog, role-projected executable plan and
installed executor. Each identity has its own lifecycle: neither
command ID, HTTP attempt, XTDB receipt, model operation ID, browser
resource lease nor proof fingerprint can substitute for another.

The self-Claim principal, helper receiving the assignment and
Request target refer to their own typed identities. They happen to
denote the same person for a genuine self-Claim, but the relation is
proved at the admitted operation, not assumed globally. Manager
Reassign or a separately authorized claim-for-another operation
has a distinct *actor*, *target helper* and existing-primary context.
Its guard includes the actor's authority to select another helper and
the target's independent effective Membership and eligibility.
A source check or UI gesture cannot turn a self-Claim operation
into an authorized manager assignment by swapping a helper argument.

The selected proof projection must name the *representation relation*
from the public Request, RequestAssignment and effective Membership,
Organization and Location records to the abstract model's state and
roles. Derived display labels and cached board cards may stand for
those facts only when the producer, disclosure scope and observation
frontier are known. A single conveniently nullable helper field is
not a second authoritative assignment store; a proof over that
field must account for every primary assignment that contributes
to its meaning. Assertions about actual schema keys must come
from the current public model interfaces, not from illustrative
Clojure data in R4 or Part IV.

**** The command envelope and trusted invocation

The browser sends the domain Request identity and stable
=:gesso/command-id= through the admitted command boundary. A transport may add
=:http-request-id= for this delivery. The latter identifies neither the domain
Request nor the command across retries. The server binds the principal from
trusted context and validates the operation, interface, canonical arguments,
and authority-domain binding of the command.

The formal state projection includes the Request and the relationships relevant
to its primary RequestAssignment, Membership, Organization, and durable command
record. Primary ownership is not modeled by inventing a =:request/helper-id=
field. A projection may summarize these relationships, but its representation
relation must explain how the actual records establish that summary.

The simplified candidate in Part IV illustrates a decision over supplied values.
Using a nullable helper field in such a projection does not change HumanHelp's
storage or authority model. Its production correspondence must still account for
the primary assignment and every guarded relationship on which that value rests.

The authority-domain binding must include the Request and selected
Organization/tenant context at the trusted server/model boundary.
An observed basis can justify some *client presentation* obligations
but it does not establish current backend Request status, Membership
or organization policy. The route maps exact typed operation,
canonical arguments, actor and command binding to the selected
public model contract; it does not promote a client-supplied actor,
role, provenance flag, one-Refresh permission or =:authorized?=
field into trusted authority.

The source/installed correspondence must show that this browser
control actually emits the admitted command envelope and that
the deployed Ring/Biff route, authenticated principal, selected
model callable and gateway share the compatible assembly/host
generation. A manually inserted command attribute or synthetic
successful request is permitted as a *route-level fixture*,
but cannot count as an actual browser-originated positive
product witness. A stale served plan or replaced handler
reopens the relevant installed-realization edge even
when the original abstract proof remains valid.

**** Historical command decision precedes new eligibility

The transition distinguishes these branches:

| Branch | Required decision | Authoritative effect |
|--------+-------------------+----------------------|
| Existing compatible command | Validate its full binding and current permission to disclose its recorded result | Return the permitted recorded result without incorporating again |
| Existing incompatible command | Detect disagreement in operation, arguments, principal, or authority binding | Reject incompatible reuse; do not disclose another binding's result |
| New command with satisfied current guard | Enforce the complete current predicate and command exclusion atomically | Incorporate ownership change, command result, and required outbox intent |
| New command with failed guard | Establish the typed nonincorporation outcome under the command-resolution protocol | No successful claim mutation; retain any separately required rejection record |
| Outcome not established for participant | Preserve uncertainty and the command binding | Reconcile; do not invent a second successful incorporation or rejection |

This decision ordering is a *logical semantic requirement*.
The implementation may combine checks in one protected
transaction or route them through a separate authoritative
read, but the observed behavior must be equivalent to
compatible-history reconciliation before treating the
request as a new command. A command key is *not*
a security capability: its result may be disclosed
only under current authorized disclosure policy,
and a mismatched binding must not reveal another
actor's command existence or stored outcome.

An old command can truthfully have incorporated while
current Request state has been changed by a later
Unclaim, Complete or Reassign. Conversely, a current
claimed card does not attribute incorporation to C42.
A not-found command record at one external pinned
basis does not establish permanent nonincorporation
while a prior attempt may still be pending.
Retention expiration and inaccessible history must
preserve an explicit unresolved/unknown branch
unless stronger authoritative evidence establishes
a different outcome.

The existing-command branch is logically prior to applying the new-command
business guard. A successful retry must not fail merely because the first
incorporation made the Request claimed. It still requires compatible binding
and permitted disclosure. A forbidden lookup must not leak whether a protected
command record exists.

For a new self-claim, the commit guard covers at least:

- the Request exists in the permitted authority scope and is currently open;
- the actor is the authenticated helper and has the required active Membership;
- Membership, Request, and the guarded Organization refer to the same
  Organization through the actual association paths;
- the current Organization policy permits this Claim by this principal;
- the primary-assignment conditions and any absence or uniqueness predicates
  required by the public model contract hold;
- the bound command has not already been incorporated incompatibly or won by a
  concurrent delivery;
- any other declared current policy dependencies are guarded as part of the
  same atomic decision.

**** Real guarded transition, physical race and frame

The original-source invariant is stated against the public model's
actual active-primary RequestAssignment definition. A useful
abstract form is that each permitted Request has *at most one*
currently active primary, but the actual source must define active,
historical/terminal, collaborator versus primary, and any
allowed transition of a Request to and from terminal states.
A proof does not establish *exactly one* primary in every
state: an open or unclaimed Request can legitimately have none.
Source-derived induction must include relevant initializers,
Unclaim, lifecycle transitions, manager Reassign and other
assignment writers, not only the Claim step that is easy to prove.

A new self-Claim must check both the public Request lifecycle
and eligibility/relationship guard *at the actual transaction
conflict boundary*. An external source snapshot, card, client
basis or server pre-read may help prepare the attempt, but cannot
authenticate the transaction-internal prestate. Protect
the absence/uniqueness of another active primary even when
competing helpers create *different assignment document IDs*;
comparing only an existing Request status field is sufficient
only if a qualified shared conflict protocol demonstrably
excludes both incorporations.

The abstract frame and physical footprint are separately
specified. A complete-document PUT can overwrite an unrelated
summary; an assignment status or deletion changes primary
cardinality even without a Request row mutation. Document
replacement, field presence/nil, expected revision,
ABA history, command record, durable outbox intent,
and backend guard/commit semantics retain the exact
10.05–10.07 obligations. A controlled two-helper race
must demonstrate the correct positive winner and actual
nonincorporation of the competing *different* command,
without accidentally eliminating unrelated legitimate
concurrent requests.

Request lifecycle change, primary assignment change, durable command result,
and required publication intent share the promised atomic boundary. An abstract
single-record induction example does not establish this multi-record Claim
contract. If the selected physical adapter supports only one-document updates,
Claim's stronger claim remains unavailable until the complete operation has a
qualified realization or an explicitly admitted implementation premise under a
profile that permits it.

The selected atomicity contract also determines how a guard
failure is *known*. A backend conflict or post-submit
exception may not prove which command incorporated,
and request-local transport failure must not be
reported as a public-model business rejection.
A rejection record, if created, has its own typed
authority and historical disclosure requirements.
A gateway's process-local one-shot capability
prevents a second use of that attempt, not two
separate H1/H2 submissions of the same logical C42.
Durable command binding and exclusion remain
independent model/backend facts.

**** Model, participant and observation outcomes

The outcome mapping is explicit:

| Model outcome | Presentation treatment | Evidence retained |
|---------------+------------------------+-------------------|
| =:committed= | =:accepted= for a successful Claim | Command-specific incorporated result and permitted projection |
| =:rejected= | =:rejected= | Typed rejection justified by the public command-resolution contract |
| =:already-incorporated= | Follow the permitted recorded outcome; a recorded successful Claim is accepted | Historical command attribution, with separate current-state provenance |
| =:commit-unknown= | =:unknown= | Original command binding and unresolved outcome obligation |

An =:already-incorporated= result is *historical* attribution
of the original command to its recorded disposition,
not a new successful domain mutation. If the recorded
outcome was a rejection, the permitted replay presents
that rejection rather than treating every compatible
record as successful Claim. An indeterminate attempt
continues to be =:commit-unknown= until a qualified
authority establishes one of the other outcomes.
The browser's =:accepted= is a projection/presentation
status, not an independent XTDB commit certificate.

The real participant trajectory is separately identified:
the originating button/DOM resource, emitted logical
C42, H1/H2 network requests, settled or unknown adapter
state, current owner/target, permitted authoritative
acquisition, actual target-specific HTMX/OOB completion
and rendered card. An HTTP 200, SSE advisory,
optimistic "Claiming…" badge, event handler call,
source-compatible manifest or readback report does
not establish all of those. A completed domain
transaction remains incorporated when rendering
or DOM installation fails; safe recovery cannot
rewrite that historical fact.

A card reacquisition can restore a current authorized presentation. It cannot
by itself prove which command produced that state. Command-result reconciliation
is a separate protected acquisition. Lost disclosure permission or expired
outcome retention may prevent attribution even while a permitted card read can
supersede the old provisional view. The liveness claim must include the needed
retention and disclosure premises.

**** Correspondence edges and independent physical witnesses

The formalization and assurance apparatus produces a *dependency
record*, not a synthetic proof that every stage occurred. Claim
semantics are owned by the public model, transition and Choreo.
Each physical edge uses the actual source of its authority:

- Original source to abstract proof: exact public interfaces,
  admitted source operation, current normalization, original
  operation/initialization and invariant closure, typed
  rule/projection checks, and checked premise inheritance.
- Proof to issued handler: accepted compatible plan, exact
  model callable and source-owned route, current assembly
  artifacts and required trust contracts.
- Handler to real transaction: current authenticated
  principal and permitted operation/tenant, full atomic
  guard, physical assignment and command-result
  footprint, complete relevant writers and the
  qualified backend isolation/failure semantics.
- Transaction to historical outcome: actual canonical
  command binding and stored result under its retention
  and disclosure contract; H1/H2 receipt and later
  poststate observation are distinct evidence.
- Outcome to browser presentation: actual delivered
  response or allowed authoritative reconciliation,
  current execution/target ownership, scoped
  acquisition, physical DOM completion and
  admitted remote advisory/Refresh policy.

For this slice the correspondence ledger must separately show:

| Obligation | Suitable evidence or explicit premise |
|------------+----------------------------------------|
| Abstract Claim preserves the declared invariant | Checked guarded-transition or induction result over the exact projection |
| Physical records represent that projection | Checked representation definition or scoped trusted mapping |
| Current policy dependencies enter one atomic guard | Constrained lowering plus qualified backend guard semantics, or another justified refinement |
| Physical writes implement only the admitted effects | Complete immutable transaction footprint and frame argument |
| Retry cannot incorporate twice | Atomic command exclusion and durable binding/result contract, including retention |
| Actual invocation uses the admitted plan | Installed entrypoint and gateway mediation evidence |
| Commit and outcome are not confused with delivery | Provider outcome qualification and command-resolution enforcement |
| Required remote notice survives the promised failures | Atomic outbox intent plus the selected dispatch/recovery contract |
| Browser effect follows its permitted result | Explicit outcome mapping and final effect/adoption gates |

The ledger's mandatory evidence categories cannot be discharged by
one generic success flag. It should separately expose a checked
abstract-invariant theorem, admitted operation/projection/plan,
conditional model/public-interface mapping, installed route
and loaded asset identity, physical guarded multi-record write,
durable command/outcome and all-writer qualifications, actual
browser installation and independent eligible user/product
acceptance. Unknown/unsupported checks remain open at
their first responsible boundary; missing positive application
capabilities remain product failures even when source checks pass.

In particular, the v1622 opt-in command-resolution and
XTDB gateway readback components can relate a
source-bound plan, process-local return, pinned command
record and caller-reported outcome in a controlled
scope. That is useful physical *co-observation*.
It does not by itself authenticate an installed
HumanHelp production route, the current user
principal, the submitted transaction's causal
effect, the full physical writer set, or actual
browser command settlement. Their results
must never serve as privileges to retry,
acquire a protected collection or install
a current DOM target.

**** Independent vertical acceptance and failures

The Claim pilot requires a real eligible browser-originated
positive path and discriminating adversarial neighbors:

1. **Eligible self-Claim:** real authenticated Alice sees an
   authorized open Request R17, the issued button generates
   C42 and H1, the trusted server/model accepts and
   atomically incorporates a new active primary, durable
   C42 result and required publication intent, and
   the permitted real card is physically adopted.
2. **Current authority:** after a rendered card but before
   incorporation Alice loses the effective Membership,
   moves outside permitted Organization/Location policy,
   or Request becomes non-open; the actual protected
   write is rejected, not merely the UI disabled.
3. **Two-helper contention:** Alice/C42 and Bob/C43
   have genuinely concurrent protected attempts for
   the same R17; at most one *new* primary is
   incorporated, the loser has a justified typed
   result, and neither leaves a partial assignment.
4. **Historical replay:** C42 incorporates and H1's
   response is lost; a compatible H2 resolves C42
   without a second incorporation or mistakenly
   rejecting it because R17 is now claimed.
5. **Binding/disclosure:** reusing C42 with different
   Request, actor, operation or arguments rejects;
   an unauthorized history query neither reveals
   another principal's outcome nor supplies a retry
   capability.
6. **Distinct actor/target:** a genuine manager-target
   Reassign guards both the manager's and replacement
   helper's effective rights, and does not borrow
   self-Claim assumptions or silently classify
   a takeover as the same operation.
7. **Current state versus history:** an authorized
   later Unclaim/Reassign changes the current
   primary but preserves C42's recorded past;
   current card state cannot stand in for
   historical attribution.
8. **Partial rendering:** domain incorporation
   succeeds but response markup or one OOB
   target fails; presentation stays honestly
   unresolved/partly installed and uses
   appropriate scoped recovery without
   issuing another Claim.
9. **Deferred/stale browser effect:** an old
   execution receives a delayed response
   after the resource/target is replaced;
   physical effect-time rights reject
   its DOM mutation without erasing a
   real committed command.
10. **Remote advisory/Refresh:** Alice's
    creator-local new Request S can
    appear immediately while Bob's
    remote change R is advisory.
    Bob's one user-authorized Refresh
    acquires and adopts only its permitted
    current scope; SSE delivery alone
    cannot force a whole-board read.
11. **Writer bypass:** a raw admin, background,
    migration or other external XTDB path
    capable of creating a second primary
    is constrained, modeled under an
    approved transition, or left as an
    explicit failed/open physical-closure
    premise—not silently omitted.
12. **Evidence provenance:** a bounded pinned
    readback, matching ledger or copied
    proof report is accepted at its actual
    observation scope but cannot assert
    physical causation, universal refinement,
    installed browser identity or product
    completion without the independent
    witnesses those claims require.
13. **Positive product coverage:** legitimate
    Create, Unclaim, Mark-on-the-way,
    Complete, Cancel, manager Reassign,
    board continuity and recovery remain
    independently required; a Claim-only
    proof cannot erase their absence.

Each acceptance case names the original semantic source,
current authority/host generation, selected physical actor,
operation, command, transport attempt, target/asset,
expected first enforcing boundary, positive neighbor,
adversarial mutation and independently observed
domain/history/browser effect. A source-level
rejection does not certify an untested physical
bypass was prevented. A post-effect diagnostic
may identify a violation but cannot retroactively
undo a committed transaction. A timed-out,
uninspectable or privacy-forbidden observation
is incomplete, not a passed physical refinement.

There is no generic call that proves arbitrary Clojure execution refinement
because an implementation Var was named in a map. Each row must identify the
mechanism that actually establishes it, or retain the precise premise. Passing
one Claim scenario is useful integration evidence; it is not a proof of all
concurrent executions.
