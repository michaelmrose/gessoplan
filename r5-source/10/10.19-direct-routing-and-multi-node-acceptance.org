*** Direct participant routing is an explicit extension

An ephemeral feature can have different semantics. For a typing indicator, the
meaningful event may be an admitted participant-message receipt, with no durable
business fact to reread. Its contract must say so instead of borrowing the
Request invalidation protocol.

A minimal typing contract binds sender identity through authentication, resolves
recipients from current authorized collaboration scope, limits payload, defines
message and execution correlation, admits receipt under the recipient's current
resource, and specifies best-effort delivery, duplicate handling, and expiry.
The UI effect still passes its final ownership gate. Loss is permitted by that
best-effort contract; persistent replay is not automatically useful for an
expired typing signal.

If expiry uses clocks across hosts, the contract names the clock and skew
assumptions, or uses a receiver-local lifetime with appropriately narrower
meaning. A timestamp alone does not prove that a remote message is fresh. A
broker's acknowledgment, transport delivery, admitted receipt, rendered indicator,
and domain commit are distinct events.

Stronger direct-message guarantees require explicit persistence, recipient
admission, acknowledgment, deduplication, retry, retirement, and version
compatibility contracts. Infrastructure reuse is allowed; semantic conflation
is not. Direct participant routing must not redefine ordinary authoritative
convergence or bypass protected-data authorization.

*** Multi-node assumptions and acceptance

The root assurance graph includes actual host replacement, backend qualification,
writer coverage, command retention, outbox recovery, dispatch acknowledgment,
interest registration, replay/gap detection, and current authorization contracts.
It also includes old/new assembly compatibility and browser artifact availability
across rolling activation. Merely sharing a database or load balancer establishes
none of these joins.

The multi-node acceptance suite uses real process and transport boundaries and
must include:

- mutation through one host becoming authoritatively observable through another;
- compatible retries through a different host, including concurrent deliveries;
- loss before submission, after possible submission, after known commit, and
  after publication but before dispatch acknowledgment;
- duplicate and reordered advisories with preserved scoped debt;
- initial-subscription and reconnect gaps, including a silent missed notice;
- expired replay retention and explicit recovery without false currentness;
- remote creation and lifecycle change remaining unadopted until permitted
  Refresh, with own-command exceptions exercised separately;
- insufficient progression at the replacement host without false discharge;
- Membership or scope loss affecting reads, command-result disclosure, and
  subscription renewal;
- concurrent independent request contexts without capability or identity leakage;
- incompatible plan or assembly replacement following the declared retirement
  and recovery path;
- eventual successful recovery once the named availability, permission,
  retention, and user-action premises hold.

The report separates safety during interruption from progress once those premises
hold. If current authorization no longer permits result disclosure, the suite
expects nondisclosure rather than assuming eventual command attribution. If
explicit Refresh never occurs, the remote-adoption liveness claim is not enabled.

Persisting arbitrary suspended choreography machines remains a separate facility
with persistence, migration, ownership, and recovery contracts. Ordinary long
waits use durable model state and later short choreographies. Multi-node support
does not require converting those waits into serialized process stacks.
