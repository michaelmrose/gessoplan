*** Formal obligations must return to executable production boundaries
:PROPERTIES:
:CUSTOM_ID: req-formal-obligations-return-to-production
:END:

A formal statement about Gesso's admitted semantics is useful only when
the corresponding implementation responsibility can be found, qualified
and checked at the boundary that can actually make the statement true
or false. Every correctness-relevant *formal assumption*, operation,
initial condition, resource, message, observation and permitted failure
retains a traceable origin in the original semantic source and a
named production realization obligation. This is *reverse
traceability*, not an assertion of reverse simulation, executable
completeness or proof that every formal trace can occur in XTDB,
a real browser or a deployed multi-node application.

Part IX owns original-source proof obligation completeness, checked
derivations, assumption inheritance and issuer-controlled admission.
Sections 10.01–10.04 distinguish the formal theorem, the checked
source and the concrete-to-abstract execution/refinement relation;
10.05–10.08 spell out the actual gateway, guard/frame,
writer-universe and HumanHelp Claim obligations. This section
connects them without inventing a second proof language or
accepting hand-authored formal machinery as a replacement
for the application. Sections 10.10–10.12 later own external
checker metatheory, finite abstraction and reproducible proof
artifacts.

A formal conclusion with an unestablished physical edge can still be
a genuine abstract theorem. Its *production* consequence is conditional,
unsupported or not admitted under the selected strong profile.
A report that says "source checked" or "formal proof passed"
cannot silently promote that edge to current runtime authority.

**** Production-obligation record and first enforcing boundary

For every transferred claim, the trusted source-derived ledger
records the exact following facts, with no empty slot interpreted
as success:

| Obligation dimension | Required interpretation |
|----------------------+-------------------------|
| Original source | Model public interface, typed rule, operation, Choreo declaration, initializer, invariant or selected product policy that actually owns the meaning |
| Formal subject | Generated normalized transition/proposition, selected abstraction and observation alphabet, quantifiers, checker/backend version and exact source-to-translation dependencies |
| Proposition and conditions | Assumptions and premises used, failure/unknown semantics, source-derived coverage and nonvacuity requirements, required selected profile and proof method |
| Production subject | Actual model callable, installed handler/worker, plan, route, generated/browser artifact, backend client and deployment/resource generation where relevant |
| Concrete representation | State/data and event mapping, actor/tenant/command identity, field presence, association, abstract frame and physical write/guard/predicate footprints |
| Responsible first boundary | Source type/preflight checker, trusted ingress, protected model policy, transactional commit/conflict check, backend outcome, transport/browser effect-time gate or product acceptance |
| Qualifying evidence | Genuine issuer-controlled check or independent physical observation, owner, provenance, freshness and supported backend/installation/threat scope |
| Remaining obligations | Open implementation/provider/opaque assumptions, unsupported checks, incomplete observation and independent positive/product gates |
| Change and privacy | Exact invalidation/requalification rule, safe source span and redacted witness appropriate to the authorized reviewer |

This is normative *record content*, not a prescribed public map API.
Source locations and normalized IDs help developers navigate the
report, but neither a Clojure Var name nor a source fingerprint proves
the installed handler uses the checked operation. A source
transaction target may depend on Request, RequestAssignment,
Membership, Organization, Location and command history; flattening
all those to an unqualified "current state" destroys the information
needed to prove atomicity and policy correspondence.

The boundary's role must be classified accurately. A source/type
checker can reject a malformed operation before issuance; an
authenticated model guard can prevent an unauthorized protected
effect only if it truly executes before the effect; a
transaction ledger/readback can diagnose one completed event,
but cannot retroactively prevent an invalid commit.
A browser effect-time permission check can prevent
a stale DOM mutation but cannot undo an already committed
domain operation. Distinguish *prevention*, *post-effect
detection*, *bounded observed correspondence* and
*unestablished universal assurance*.

**** Formal assumptions create independently checkable production debts

Every modeled capability or favorable environment hypothesis creates a
matching physical obligation. Representative cases include:

| Formal construct or premise | Required implementation/enforcement edge | Insufficient evidence |
|-----------------------------+------------------------------------------+-----------------------|
| Authenticated principal or tenant | Trusted server/session/service identity, current Membership and permitted authority-domain binding at actual protected call | Browser role flag, copied identity, preflight shape |
| Atomic authoritative operation | Real guarded transaction or independently justified atomic implementation, current prestate/predicate, frame and all relevant writers | Correct pre-read, submitted plan name, single success response |
| Absent active primary | Protected RequestAssignment cardinality/absence predicate across competing distinct IDs and status-changing writers | CAS on an unrelated Request field without proved shared exclusion |
| Stable logical command and once-only incorporation | Durable C42 operation/actor/target/arguments binding, atomic command result/exclusion and qualified historical replay under retention | One-shot H1 submission handle or HTTP request ID |
| Trusted authoritative observation | Provider-qualified basis, actual scoped read/projection, appropriate disclosure and adoption; incomparability preserved | SSE notification, numeric-looking version or caller-supplied basis |
| Fresh browser resource and permitted effect | Real resource/owner generation, retirement, effect-time authorization, actual target-specific DOM/HTMX outcome | Reused DOM ID, callback-entry check, HTTP 200 |
| Eventual command/recovery/notice | Qualified retention, delivery/replay/gap repair, scheduler/provider/fairness and necessary user-action premises | Timeout, one successful retry or a reachable terminal state |
| Closed original operation catalog | Independently rederived initializations, all relevant operations/invariants and proof dependencies | Developer-selected smaller formal state machine |
| Closed installed writer set | Qualified provider/credential/host enforcement across routes, workers, migration/admin and external writers | A fresh but incomplete host enumerator |
| Portable semantic execution | Supported JVM/CLJS/codec/plan and loaded artifact relation under its tested or proved scope | Matching source hash or JVM-only execution |

Such edges may be justified by a dedicated checked mechanism,
a verified compilation/refinement theorem, an actual enforcing
boundary, a carefully delimited third-party/backend contract,
or an explicit profile-permitted opaque premise. The evidence
classes and their strength are *claim specific*. An open premise
may remain in a useful conditional theorem; it cannot be marked
discharged by attaching a shape-compatible success report.
A strict profile rejects unavailable mandatory evidence while
an explicitly requested weaker profile may admit a different,
honestly conditional claim. Neither changes original business
policy without source-owner approval.

An atomic formal Claim action in particular creates an
atomic *production* obligation. A sequence of correctly
observed pre-reads followed by an unconditional write
does not satisfy that obligation, because Claim's current
Request status, helper eligibility, relationship guard,
active-primary absence and command exclusion must be
qualified at the actual protected conflict boundary.
The real backend may use a guarded XTDB transaction,
an equivalent conditional mechanism or a separately
proved implementation; identical source syntax is not
required, but the same relevant observable transition
and rejected/unknown outcomes are.

**** Correspondence direction, coverage and non-vacuity

The strong safety-transfer claim is directional: *every relevant
actual admitted production execution* under its stated environment
and initial-state relation must abstract to an allowed semantic
transition or trace. The chosen abstraction identifies which real
states, events, stuttering/internal steps, failed/unknown outcomes,
concurrent writers, side effects and browser observations count.
A successful generated formal trace, matched operation name or
one correct concrete execution is not the required universal
quantification.

A converse inclusion—every formal trace is physically realizable—
is a distinct completeness claim if the selected profile needs it.
A correct source-level counterexample can be physically
unrealizable because of a deliberate abstraction overapproximation,
a stronger deployed guard or excluded environment schedule.
The *formal* safety claim still fails in that selected model,
unless a justified refinement of the model or property removes
the spurious behavior. The production claim cannot be declared
false until the concrete relation and realizability are examined.

A different danger is a model that omits a real operation or
declares Init empty, so its invariant is trivially true.
Source-derived original catalog closure, satisfiable/representative
initial state, real eligible Claim and independent HumanHelp
capability positives prevent such vacuous success from satisfying
the claimed application. A universal proof over a carefully
restricted subset is not a proof that the subset describes
all actual source or physical behavior. A complete submitted
DAG is not necessarily a complete *original-source*
obligation ledger.

Progress transfer has additional fairness, execution-continuation,
retention, availability, delivery, quiescence and authorized
participant-action conditions. A safety simulation that allows
indefinite stuttering need not provide progress. Under
HumanHelp's explicit Refresh policy the browser may legitimately
remain unaware of remote changes until its user grants one
scoped acquisition. Modeling the user as eventually refreshing
without a stated premise changes product semantics and
cannot support an unconditional liveness theorem.

**** Generated formal artifacts derive from source; repair the owner

The preferred generation path is:

#+begin_example
actual Gesso and application semantic declarations
                     |
       trusted original-source normalization/checking
                     |
            admitted semantic subject
               /              \
    checked formal           issued production
    translation              plan/operation
          |                        |
 external formal check        real installed realization
          \                        /
       correspondence + named open premises
                     |
        qualified claim and source-level diagnosis
#+end_example

Do not replace it with:

#+begin_example
handwritten Clojure model  --- manually kept in sync ---
                              separately handwritten formal model
#+end_example

A framework-maintained translation to Recife, Quint/TLA+,
Lean or another supported backend is a derivative of the
admitted semantic source. Backend version, translation
rules, checker inputs, selected bounds/abstractions and
actual generated bytes remain identified and reproducible.
The backend can have its own implementation defects or
soundness premises. A proof about the generated model is
not a proof that the *translator* preserved the original
meaning or that production executed that meaning.

Application developers must not have to author, debug
or hand-synchronize such a second formal specification.
They may inspect or request explanations of emitted formal
code. Maintainers may directly repair the framework's
translation as a source-controlled framework change.
Changing a generated invariant in place so it becomes
weaker and a checker turns green is not an application
repair and cannot establish the previously claimed
property. An intentional weakening of the actual
business invariant is a *visible owner-selected
policy change*, requiring corresponding source,
proof, application and product reacceptance.

**** Counterexamples identify the modeled failure, not an invented physical event

Suppose a *candidate defective* Claim model checks Request
=:open= at an earlier observation and fails to require
that status at its commit action. A formal checker may
produce this bounded trace:

#+begin_example
COUNTEREXAMPLE IN THE FORMAL SUBJECT
Property: Claim requires an eligible, open Request at incorporation.
A observes Request R open.
B observes Request R open.
A incorporates Claim for R.
B incorporates another active primary Claim for R without an intervening release.
Scope: the selected candidate model, initial states and exploration bounds.
Physical XTDB execution of this history: not established.
#+end_example

That is a counterexample to the defective *formal candidate*
if its admitted transitions really allow those incorporates.
It is not a counterexample to a correctly guarded formal Claim
action, nor evidence that the real XTDB model actually performed
both writes. If the generated model purported to include
the current-open guard, inspect source normalization,
translation, property and abstraction before attributing
the counterexample to a production bug.

Conversely, a correct abstract guarded model may pass while
an installed writer uses an outdated Request pre-read and
unconditional PUT. Then the source-level theorem may be
valid while the real refinement obligation is open or
refuted. A matching pinned poststate, command ledger
or local transaction receipt can be bounded diagnostic
evidence without authenticating causation or excluding
other physical writers.

A good counterexample/first-blocker diagnostic retains:

- original named property, its semantic subject and current
  source location; the actual original model and operation
  catalog against which completeness was checked;
- the smallest *reproducible and meaning-preserving* trace
  prefix or typed-rule valuation, including actor/command,
  Request/assignment and observation identities only where
  authorized and genuinely relevant;
- selected formal encoding, checker version, abstraction,
  finite bounds, fair/unfair schedule assumptions,
  source-to-generated relationship and exact failure
  classification (counterexample, unsupported,
  exhausted, vacuous, stale or incomplete);
- the exact failing semantic guard, frame, knowledge or
  premise, if supported by the evidence; otherwise
  the plausible alternative model/translation/physical
  owners still under examination;
- the production callable/route/worker, transaction/
  writer or browser effect and its current generation,
  and the first actual enforcement/observation boundary
  to be checked separately;
- which checked propositions remain valid, which
  specific physical bridge is absent, and whether
  an independent *actual* implementation trace
  concretizes the modeled failure.

This is a data and explanation contract, not permission
to expose raw private Request, Membership, command
record, XTDB query or actor identities in a copyable
report. Diagnostics use stable structured reasons
and authorized redacted source witnesses, with
correlation handles interpreted only at trusted
boundaries. A failing downstream artifact blocked
by one missing root premise is not reported as
a collection of independent semantic bugs.

When reducing a counterexample, an automated shrinker
must retain the discrepancy and the declared source
semantics, not merely find a shorter trace with
a different failure. A minimized finite counterexample
is bounded by the generated/tested language and domains;
it does not become a universal proof or a real
production incident by being reproducible.

**** Source-level and production repair are distinct ownership decisions

The supported correction loop is:

#+begin_example
original Clojure/Gesso source and actual product policy
        -> source-checkable admitted semantics
        -> regenerated formal subject and executable plan
        -> independently classified proof/model-checking result
        -> source-located counterexample or missing obligation
        -> identify semantic, translation, provider, or physical repair owner
        -> owner-approved source/implementation/assumption repair
        -> rerun source, proof, assembler, production and product gates
#+end_example

The possible owners are separate:

| Finding | Correct owner and repair | What cannot count as repair |
|---------+--------------------------+-----------------------------|
| Defective admitted model guard | Application/public model owner corrects the actual rule/transition; rebuild proof and issued plan | Only editing a generated TLA+/Quint/Recife guard |
| Incorrect formal lowering | Framework maintainer fixes translation and rechecks semantic correspondence, checker and emitted artifacts | Weakening the formal property to agree with buggy lowering |
| Abstract overapproximation | Review abstraction and property against original semantics; refine within supported meaning with explicit applicability | Suppressing a real abstract counterexample or declaring it physical by fiat |
| Production lacks qualified atomic guard | Model/host/backend owner repairs the actual guarded write and tests concurrent effects; formal source theorem may remain valid | Adding a true statement to a correspondence report |
| Missing original-source operation or physical writer | Restore source completeness or real writer confinement/qualified exception; recheck dependent theorem | Removing the writer from a host enumerator |
| Current business policy differs from intention | HumanHelp owner explicitly changes and independently accepts model policy and product requirements | Letting a proof tool infer user/product intent from prose |
| Unsupported checker/proof fragment | Add a compatible admitted proof mechanism or retain an allowed precise premise/other claim class | Silent downgraded =:kernel-checked=, timeout-as-success |
| Browser effect occurs after retirement | Repair current owner/effect-time permission and real shell behavior; exercise actual DOM completion | Passing a source-only adapter test while the stale callback still mutates |

An assistant or automated tool can propose and explain
these repairs, but it does not acquire business-policy
authority, trusted source issuance, deployed writer
access or checker acceptance. A proposal is not
a certificate. Repairs must preserve the
same original-source requirement or explicitly
announce a changed policy, applicability or
assumption. Re-run the relevant negative mutation
and a *real eligible positive control*; a repair
that simply rejects all Claim attempts is not
HumanHelp acceptance.

**** Acceptance: both directions of explanation and independent evidence

For each production-transferred formal claim, Gesso
must answer two questions without requiring developers
to manually reconcile two source languages:

1. *Which original semantic object, executable
   production boundary and current host/asset
   generation does this formal subject constrain?*
2. *Which actual evidence discharges each
   correctness-relevant assumption used by the
   formal claim, and which remain open?*

The following positive/adversarial pairs are
required at their applicable scope:

1. **Source origin:** a generated Claim model,
   exact original source and emitted plan share
   checked semantics; a hand-modified formal
   model or stale source-ID pair does not pass.
2. **Original completeness:** all declared
   operations/initializers and invariant
   dependencies appear; a pruned Unclaim
   catalog is rejected as complete proof.
3. **Abstract counterexample:** the defective
   pre-read-only Claim candidate yields a
   scoped source-located trace; a genuinely
   guarded candidate is not falsely blamed.
4. **Correct model/incorrect implementation:**
   formal atomic guard succeeds; an
   unguarded deployed writer fails
   execution/refinement rather than the
   correct abstract theorem.
5. **Trusted actor:** current authenticated
   helper/Organization policy authorizes
   eligible Claim; browser role assertion
   does not discharge actor authority.
6. **Absence and uniqueness:** real concurrent
   different-command Claims preserve one
   active primary; two stale pre-reads
   followed by distinct assignment inserts
   cannot count as guarded incorporation.
7. **C42 historical result:** compatible
   H1/H2 recovery returns the qualified
   recorded result; a current Request
   card or missing row at one basis
   cannot invent historical rejection.
8. **Physical witness scope:** one selected
   actual gateway call and pinned readback
   support their reported local facts;
   copied receipt, wrong node or third-party
   intervening writer cannot gain
   universal causal authority.
9. **Stale resource:** current browser owner
   adopts only permitted target content;
   retired callback cannot mutate a
   reused DOM ID even if HTTP 200 arrived.
10. **Notification and permission:** a durable
    advisory with qualified eventual
    delivery/replay may support the named
    progress claim; SSE arrival alone
    cannot grant remote Refresh.
11. **Tool failure:** a finished supported
    proof check can be distinguished from
    timeout, unsupported translation,
    empty finite Init or lost external
    checker; none is success by default.
12. **Counterexample provenance:** a finite
    model trace maps back to exact source
    and explicit open physical question;
    source-located report does not
    invent an actual XTDB incident.
13. **Correct source repair:** changed
    original guard or verified translator
    regenerates all dependencies and
    passes relevant checks; editing only
    the emitted model is insufficient.
14. **Physical repair:** an actually
    guarded deployed writer prevents
    the competing invalid effect;
    a post hoc ledger discrepancy
    cannot be called pre-effect
    prevention.
15. **Product non-vacuity:** an eligible
    self-Claim and required
    Unclaim/Reassign/other Part VIII
    capabilities remain exercised;
    reject-all is not completeness.
16. **Topology:** single-/multi-node
    deployments preserve the same
    abstract Claim meaning, with
    separate routing, credential,
    writer and failure premises;
    node loss is not an
    authority grant or
    unconditional convergence.

Each case states the original source,
profile, positive control, adversarial
mutation, formal abstraction and bound,
first checker/physical enforcing boundary,
and independent relevant observation.
The report distinguishes prevention,
scoped diagnostic detection, proof
counterexample and unobserved uncertainty.
An uninspected route or external
database writer remains open, not
conveniently absent.

The final invariant is that formal
assurance *constrains the implementation
Gesso actually installs and operates*.
It cannot become an independent story
that is true only of generated models,
nor can a real passing test fabricate
a theorem that has not been checked.
