** Formal correspondence and system-boundary invariant

#+begin_quote
A claim applies to production only through its stated representation, checking,
or refinement relation and the continued applicability of its premises. The
executable semantic core, proof kernel, dedicated checkers, external formal
checker, physical gateways, and deployed entrypoints have distinct obligations.
Source-derived coverage, observed execution, trusted backend behavior, and
universal theorems are not interchangeable evidence.

Full host-language implementations remain available through explicit contracts.
Finite checking remains finite unless a justified abstraction transfers it.
Physical guards and writes enforce current authority; certificates do not.
Known commits remain commits despite delivery loss, while participants preserve
unknown outcomes until permitted authoritative evidence resolves them.

Every relevant backend or implementation change triggers the appropriate
qualification and correspondence checks. Multi-node placement changes hosts,
not authority, command meaning, resource ownership, or HumanHelp's adoption
policy. The root report preserves the evidence class, scope, assumptions,
applicable identities, enforcing boundary, and unresolved obligations of each
claim.
#+end_quote

*** Interpret the invariant as a claim-specific transfer judgment

The closing rule is conditional and typed: *claim C about
source subject S applies to installed production subject P
only when each required interpretation, original-source
coverage, admissible proof, implementation refinement,
runtime enforcement and environment assumption for that
exact C,S,P has been established under the selected
scope*. If a mandatory edge is unknown or refuted, the
abstract theorem may still be true; its corresponding
production or completion claim remains conditional,
unsupported or rejected by the selected strict profile.
A matching name, digest, code shape or HTTP response is
never a substitute for the missing edge.

| Claim edge | What must actually be established | What it does not grant |
|------------+----------------------------------+------------------------|
| Original source to obligation | All relevant declared initializers, operations, business invariants, actors, writers and product requirements are represented without silently narrowed coverage | Correctness of arbitrary opaque Clojure or undiscovered deployed writers |
| Source to semantic/formal subject | Versioned normalization, interpretation, abstraction and proof dependencies preserve the precise source proposition | A handwritten convenient specification substituted for HumanHelp |
| Proof or finite result | Genuine issuer/checker run, exact quantifiers/bounds, source premises and an admissible derivation or witness | Universal theorem from a bounded test or a copied successful report |
| Semantic to runtime transition | Directional refinement with stated abstraction, visible events, stuttering/failures, source/effect and message correlations | A converse simulation or liveness property not separately proved |
| Runtime to protected authority | Installed authentic principal, guarded atomic writer, trusted read/disclosure and physical effect-time admission | Authority from browser data, a certificate label or a process-local diagnostic |
| Physical provider and topology | Qualified selected XTDB/backend, codecs, actual installed handlers/writers, host/broker/asset identities and recovery assumptions | All-schedules provider theorem or all external direct writers from one node's observation |
| Client acquisition and adoption | Current scope/permission, genuinely sufficient provider basis, active resource and completed browser installation | Canonical truth from an advisory, echoed token, SSE send or HTTP 200 |
| Release and application acceptance | Every required product capability, independently selected policy, positive/adversarial test and deployment gate for the named milestone | Automatic completion of other milestones or future deployments |

This is an *obligation map*, not a current Gesso map API
or a presumption that the listed checks have passed.
Original-source completeness is judged against the
source's full declared requirements, not the smaller
catalog returned by an elaborator or a conveniently
successful subset of tests. A required obligation
omitted from the assembled application remains owed.
An externally authored proof language is optional
internal framework machinery; normal application
authors continue to use Gesso/Clojure declarations.

*** Evidence remains precise under composition and change

Evidence classes must remain distinct at the root:
proved or checker-admitted conditional theorem,
exact-finite result, tested correspondence,
physically observed enforcement, runtime
assumption, application assertion, unsupported,
unknown, stale and refuted are not interchangeable.
A derived proof inherits every relevant admitted
premise, trusted inference rule, external checker
assumption, backend condition and coverage gap.
The assurance graph does not promote open premises
to proved merely because many other nodes passed.
A copyable report, signed-looking payload, source
fingerprint or issued abstract certificate does not
authenticate the current installed server or replace
its live authorization checks.

For a safety invariant, the claimed quantifier
and transition universe include the necessary
initialization, legal steps, relevant conflicts
and writer/dependency closure. A real execution
may conform through a declared directional
abstraction with hidden local steps; byte-identical
state traces are not automatically necessary.
Conversely, finite exploration, a sampled physical
schedule or one causal-looking readback cannot be
called an unbounded proof of transaction or
browser refinement. Noninterference of optional
observation sidecars is not evidence that mandatory
runtime guards were applied.

Liveness is separate. Any eventual-command,
publication, convergence, participant-message or
HumanHelp adoption conclusion names availability,
fairness, durable retention, connectedness,
current authorization, replay/gap recovery and
the *user's explicit Refresh where required*.
Safety remains required during supported partitions
and delivery uncertainty without pretending the
liveness antecedents hold. A known committed
effect cannot be relabeled rejected when its
response, notice, readback or diagnostic fails.
An indeterminate command remains unknown until
authorized command-specific evidence settles it;
current Request state does not retrospectively
identify the successful command.

A relevant source, invariant, backend implementation,
physical writer, proof assumption, compiler, browser
asset, assembly generation, authenticated context,
transport, retention or deployment topology change
invalidates or requalifies exactly the dependent
claims. An independently checked compatible
replacement can retain valid abstract theorems;
an unchanged byte digest cannot preserve a
claim whose semantic dependency or live boundary
has changed. Failure to *observe* an external
change is a named assurance limitation, not
proof that it did not occur.

*** Proof hardening and multi-node experiments may proceed iteratively

R4's ordering principle remains part of this finished-system
plan: complete multi-node productionization is *not* a
prerequisite for strengthening the executable semantic
core, its proof obligations or source-relative theorems.
Conversely, a small real two-process experiment may
expose an unstated transaction, observation, routing,
identity or failure assumption before the corresponding
formalization is considered mature.

The supported feedback loop is: admit the current
versioned semantic source; check its obligations;
exercise a bounded real deployment; independently
classify observed counterexamples and unsupported
physical edges; repair the actual source semantics,
implementation or assumption contract under its
proper owner; regenerate and rerun the dependent
checks. A finding in the physical realization must
not be concealed by weakening a formally true
requirement, and a changed semantic rule must not
inherit an incompatible old theorem. Small physical
tests remain tested evidence, never proof of all
deployments. The semantic authority is never
derived from the host conducting the experiment.

This iterative development permission does not
collapse the four separate release milestones
below or bypass Part XI's selected candidate,
installation and activation requirements.

*** Four independent completion milestones

R4's closing distinction is preserved explicitly.
A release or progress report must never claim one
milestone solely because a different one succeeded:

| Milestone | Positive scope | Still separate |
|-----------+----------------+----------------|
| Operational application success | The supported real product capabilities and user-visible workflows work under named deployment and test conditions | Compositional certification, external proof and cross-node failure coverage |
| Compositional application certification | The admitted application source, required assembly/contracts, scoped proof obligations and conditional guarantees close under the selected assurance profile | Physical provider and unproved runtime premises, independent external metatheory, unspecified product choices |
| External formal correspondence | The named source-derived formal theorem, its checker/import and necessary representation/refinement bridges are independently established to their stated scope | Current production installation, all business policies, liveness and unrelated formal families |
| Production multi-node completion | The same semantics survive actual host replacement, cross-node command recovery, publication, registration gaps, authorization and browser adoption in tested supported topologies | Unbounded formal proof, other unsupported deployments or missing product capabilities |

A project may legitimately ship a bounded operational
profile before the stronger formal or distributed
milestone. It must label that smaller achievement
and retain its unmet requirements, not relabel
the full goal as complete. Conversely, editorial
acceptance of this timeless design can occur
before these implementation/product evidence
gates pass, because the design specifies
the obligations without reporting them as facts.

Part XI owns candidate admission, actual
installation, activation and milestone release
decisions; Part XII owns realization ordering.
This final Part X judgment supplies their
semantic/physical boundary requirements, not
a second release procedure or a replacement
for current trusted enforcement.

*** Closing positive and adversarial correspondence obligations

| Positive claim-compatible example | Nearby forbidden inference |
|-----------------------------------+---------------------------|
| A source-complete typed invariant is proved under named abstract premises | Source omission or unchecked opaque writer is silently excluded from the universe |
| A genuine closed-kernel derivation is rechecked for the original proposition | A caller-provided proof-looking map or copied report issues authority |
| A sound finite model result is reported at its precise domain and bounds | A timeout or enumerated subset is called universal theorem |
| Qualified physical Claim enforces atomic guards and a complete frame | Handler-only pre-read or successful test map substitutes for real XTDB incorporation |
| Authenticated current principal invokes a protected operation | A browser ID, stale actor, or certificate substitutes for authorization |
| An installed browser plan executes the admitted effect for its current owner | Retired callback or HTTP 200 is counted as an authorized completed DOM adoption |
| Compatible historical command resolves under current disclosure | Lost response triggers duplicate mutation or current state is called command attribution |
| Named outbox/registration recovery closes an eligible advisory gap | Router health, SSE write or silence is called complete delivery |
| Bob's explicit Refresh adopts one coherent authorized board | Remote notice auto-adopts lifecycle content or clears incomparable debt |
| A real mixed-host deployment preserves the same source semantics | Two host labels, shared database alone or broker ack prove distributed refinement |
| A checked compatible artifact preserves exactly its dependent guarantees | Changed Membership, provider or installed assembly inherits stale evidence |
| A release reports each of the four separately evidenced milestones | Operational success, an abstract certificate or editorial approval is called total completion |

These controls are obligations for future independent
conformance and physical tests, not assertions that
the present Gesso implementation has passed them.
The final judgment also preserves R4's negative
lesson: formal correctness of one model,
operational success of one workflow and a
correctly rendered UI can coexist with an
unverified or unsafe production boundary.
