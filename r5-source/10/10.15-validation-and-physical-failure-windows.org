** Validation through the real enforcing boundaries

Formal and concrete evidence are complementary. Retain unit and property tests,
exact finite checks, portable-runtime conformance, real browser integration,
backend qualification, installed-application acceptance, and multi-node fault
scenarios where their claim depends on physical deployment.

*** The validation ladder has independently owned claims

The validation ladder comprises complementary mechanisms, not a
single regression-test success state. A complete release record identifies
which obligation each layer challenges and the original subject from which
that obligation was derived:

- *Unit and property tests* examine value, state transition, elaboration,
  normalization and invalid-input behavior; they cannot authenticate the
  production shell merely by invoking a pure function.
- *Proof checker and model/finite-state runs* establish their precise source,
  inference, finite-domain, abstraction or bounded-counterexample result.
  An incomplete exploration and a genuinely exhaustive finite result are
  different, even if both find no counterexample in visited states.
- *JVM/Node and CLJS portability tests* check actual shared semantics,
  codecs and error classification across the supported runtimes. Matching
  results are tested correspondence for the selected inputs, not universal
  source/physical equivalence.
- *Real Chromium integration* exercises the emitted, verified production
  browser asset, HTMX extension, EventSource, actual HTTP/SSE and DOM effect
  timing; a mocked adapter or synthetic browser event has narrower scope.
- *Actual Biff/XTDB integration* exercises the checked handler, issued
  operation, selected guarded lowering, real provider, authoritative writes,
  durable command record and acquired readback. A locally checked Ring
  object does not establish deployment through the serving socket.
- *Application acceptance* uses the actual HumanHelp public models and
  user-visible Claim, recovery, notification and selective Refresh actions;
  a toy Request, injected browser command or successful HTTP status is not
  a substitute for that vertical composition.
- *Multi-process acceptance* adds independent processes, shared authoritative
  persistence, command-resolution portability, interest routing and the
  selected failure topology. Part X 10.16–10.19 own its concrete design;
  a two-label single JVM is not two physical hosts.

Evidence may be reused only for the exact propositions, versions and
qualified premises it establishes. The reported release outcome separates
admitted semantic theorem, tested implementation correspondence, actual
installed effect enforcement and current backend/host qualification. A
failed test identifies the likely owner of the repair—original rules,
semantic implementation, lowering, build/shell, policy, backend assumption
or application assembly—without altering a theorem to hide an
implementation or environmental defect.


An acceptance case records its admitted assembly and artifact, input and fault
schedule, expected semantic result, first enforcing boundary, actual observation
origin, and remaining assumptions. A negative test must reach the boundary it
claims to test. A test-only wrapper that rejects earlier is not evidence that
the production gateway, endpoint, or browser mutation gate enforced the rule.

*** Evidence fixture, independent oracle, and classification

For each required guarantee the acceptance fixture records the original
Gesso source location and operation/invariant ID; expected state and
allowed outcomes; exact issued assembly and loaded asset; principal,
command and transaction/attempt bindings as permitted by disclosure;
provider and adapter versions; controlled input/fault schedule; first
*real* enforcing boundary; independent observations of both the
authoritative state and any forbidden physical effect; and every open
trust, coverage or fairness premise.

The expected result must come from the declared semantic obligation,
not be reverse-engineered from the same adapter under test. Independent
observations may use a second read path, a controlled database query,
receipt/ledger inspection, forbidden-effect counter, or a browser
user-visible oracle, with the independence and provenance limitations
recorded. A test that asserts a wrapper's earlier rejection cannot
claim the later production gateway rejected; a report computed only
from supplied expected values cannot authenticate the physical
transaction. When a source mutation changes semantics, record the
*first* mandatory boundary expected to refuse it and challenge that
boundary directly.

Run a valid positive control through the same tested boundary, not
merely a separate fixture. A reject-all implementation can pass many
negative cases; it cannot pass the matching positive control. Likewise
a "no forbidden write observed" verdict requires credible coverage of
the actual write surface and observation interval, not an empty
test-local counter with uninspected direct writers.

Outcomes are typed: =passed= under a precise scope, =counterexample= or
=refuted= with an actual witness, =rejected-as-designed=,
=unsupported=, =incomplete=, =unavailable=, =timed-out= and
=commit-unknown= when submission may already have occurred. A
deliberately rejected malformed declaration is not a counterexample
to an admitted model; a finite search cutoff is not a positive theorem;
an unrelated console/network error is not an expected injected
failure. Keep exact counterexample event order, identity, basis,
observation origin and the point where semantic/physical evidence
diverged, while redacting protected inputs and credentials from
public reports.


*** Required mutation and positive-control pairs

| Mutation or failure | Expected enforcing boundary | Positive control |
|---------------------+----------------------------+------------------|
| Change a proof premise or dependency after issuance | Certificate currentness and required-closure admission | Unchanged immutable closure remains reusable |
| Copy a successful report into a new map | Issuer or persistence revalidation | Original source is rechecked and legitimately issued |
| Append a physical write after canonical lowering | Owned gateway payload and footprint check | Exact admitted transaction reaches the provider |
| Change an unguarded field before a replacement write | Qualified frame/guard contract | Independent safe fields are preserved by the selected mechanism |
| Supply a stale principal or Organization association | Trusted invocation and atomic current-policy guard | Authorized compatible self-claim succeeds |
| Retry an incorporated Claim after Request becomes claimed | Binding and permitted recorded-result branch | Same command returns its allowed historical outcome |
| Lose one attempt while another delivery commits | Command-resolution boundary | Outcome remains unknown until sufficient command evidence arrives |
| Replace a resource after callback admission but before mutation | Final physical effect gate | Current owned effect can install and complete |
| Break actual server adoption while retaining a checked router object | Installed production-entrypoint validation | Real request reaches the issued handler and gateway |
| Change provider version or relevant adapter semantics | Qualification applicability gate | Qualified supported configuration admits the same operation |
| Exhaust the finite checker before exploration completes | Evidence result classifier | Completed exhaustive run reports its exact bounds |
| Supply an unsupported host function to a closed rule checker | Closed-language admission | Explicit opaque contract remains usable under a permitted profile |

The mutation corpus covers source obligations and their actual
derivatives independently. Examples include omitted operation or
invariant, mutated guard/read dependency, dropped frame or uniqueness
predicate, stale certificate or source closure, forged issued handle,
changed plan/compiler asset, missing route/writer adoption, and an
unchecked direct or deferred writer. Rejecting an invalid *declared*
proof graph is not proof that a later physical raw XTDB write cannot
bypass a production admission gate.

Where a positive result depends on a callback, do not assume an
opaque Clojure function behaves as its declarative summary. Challenge
the callback at its supported use-site or retain a named conformance
premise. Where an observed result depends on backend behavior,
recheck the selected qualified provider boundary, not a fake return
map. An accepted source claim is not a universal security/availability
claim, and a tested production slice need not refute a valid abstract
theorem when its host implementation fails.


Positive controls establish useful acceptance, not just rejection. The test
suite must also preserve a known formal counterexample, an incomplete exploration,
and an unsupported feature as distinct statuses. “Nothing unsafe happened” is
not enough if the intended operation never executed.

*** Physical concurrency and failure windows

Backend scenarios must include competing commands, repeated delivery of one
command, policy changes between preparation and commit, changed relationship
members, and concurrent writes outside the nominal business fields. The
transaction tests inspect authoritative outcomes and state under the declared
provider contract, not only HTTP status codes.

*** Physical Claim and command failure-window matrix

Tests involving authoritative mutations use concurrent requests that
genuinely reach the selected physical gateway. Force contention with a
barrier *after each request acquires its own prestate and issued
capability* where that is the scenario. Observe what each submission
actually did, which transaction committed or asserted, whether the
document frame survived, and whether the command record and domain
write share the promised all-or-nothing outcome. A post hoc comparison
of two HTTP 200 responses is insufficient.

Required schedules distinguish:

- guard failure and successful same-version conflict control;
- competing Claim and Membership/Organization association changes;
- interleaved unguarded changes outside business fields, including
  absent/nil, whole-record replacement, relationship/absence and
  writer-footprint differences;
- duplicate delivery of *one logical command* versus two genuinely
  different commands and separate submission-attempt identities;
- crash/exception before physical submission, after a successful
  transaction but before the Ring response, and during later
  readback or command-resolution observation;
- already-incorporated compatible replay under current disclosure
  versus new incorporation, revoked permission or incompatible
  argument/target binding;
- a fresh *authorized* request after a resolved conflict versus
  prohibited reuse of the consumed one-shot writer; and
- outbox publication before/after commit, dispatch, receipt and
  retry under the promised delivery/gap-recovery contract.

A lost response after successful submission is not a rejected
transaction; an observation failure cannot request an automatic
second submission. The test independently inspects the durable
physical record to distinguish the *actual test oracle's knowledge*
from what the browser or request caller is entitled to know. A
currently claimed Request does not establish which command caused
the claim, and a matching transaction ledger/readback may be
co-observation without proven causal correspondence. Time/basis,
writer completeness and actual installed-handler scope must be
qualified separately. Even a successful controlled embedded-XTDB
contention test does not certify all backend schedules or external
direct writers.


Browser scenarios include reordered callbacks, duplicate completion, failed
abort, resource replacement, deferred mutation, insufficient observations, stale
plans, and partial installation repair. Expected network or console failures in
fault injection are asserted precisely; unrelated failures still fail the case.
A successful portable test does not substitute for the real HTMX or browser
lifecycle event that the shell normalizes.

*** Browser and user-level delivery schedules

A real-browser fixture must load the same checked runtime bytes and
HTMX/SSE versions selected by the installation being claimed. It
drives actual user actions and physical event delivery instead of
injecting only already-normalized adapter events. Adversarial cases
include SSE duplication, reconnect/loss, delayed or reordered
fragment response, overlapping POST/GET, aborted request that still
completes, stale callback after resource retirement, DOM root
replacement, optimistic settlement after rejection or uncertainty,
a deferred side effect whose owner changes before mutation, and
partial installer failure followed by allowed repair.

Use both semantic adapter traces and observed DOM/network state:
selected item, focus/scroll continuity, pending marker, refresh
affordance, stable behavior-owning root, current/advisory/canonical
progression and actual server-refetched HTML. A browser trace that
retains a stale pending state, silently adopts a remote advisory
revision, sends a second command, or installs an effect under a
retired resource fails the appropriate obligation. Deliberately
expected network/console errors must be identified by type and
fault schedule; new or unrelated failures remain failures. Portable
CLJS tests and mocked HTTP fixtures are useful separate layers, not
evidence that native HTMX lifecycle events were normalized correctly.

For HumanHelp, complete acceptance starts from real production
model operations, routes and protected public policy, covers the
actual Claim/unclaim/take-over/done/cancel life cycle and independent
multi-client visible state, and preserves the distinction between a
creator's immediate result and another viewer's advisory update plus
explicit Refresh. A browser-only demo, a fabricated positive
command, or a reachable-looking checked route does not close this
application-wide guarantee.


Host scenarios include concurrent independent requests and any supported deferred
execution. They must demonstrate that one request's identity, writer capability,
result, or admission limit cannot be silently inherited by another. Thread-bound
APIs that intentionally exclude deferred work must reject it clearly rather than
claiming it was mediated.

*** Independent host isolation and closure limits

Concurrent checked Biff requests must not share request-local writer
issuance, principal context, one-shot permit, current target, result
or admission budget. Test controlled overlap, queue saturation,
timeout/exception cleanup and sibling-request isolation. If a scoped
writer is deliberately synchronous/thread-bound, deferred callbacks
and off-thread use reject before an effect rather than inheriting a
previous request's permit. A post-dispatch host report may detect a
mismatch after irreversible work; it cannot certify that the write
was prevented.

Production adoption is checked separately from an in-process system
map: show that the actual listener dispatches through the final
checked handler, that real HTTP invocations reach their intended
operation and guarded writer, and that the serving JS/fragment/stream
corresponds to the admitted assembly. Deliberate bypass tests should
challenge raw Ring responses, retained pre-mediation handlers,
background/worker/migration/admin writers and separate XTDB
credentials under the application's declared supported universe.
The result may correctly be =open= for uninspectable external
writers; absence from the surveyed host registry is not proof of
absence from the deployment.

Run completion also records negative controls for the test harness
itself: missing backend, never-executed action, empty generator,
untriggered race, absent browser asset, unsupported physical
interface, and timed-out test. These do not pass due to vacuity. A
scope-qualified failed oracle may block production admission if it
is required by the selected assurance profile, without conflating
that gate with optional logging or undoing an already committed
effect.


No single passing history establishes universal refinement. These tests make
premises falsifiable, exercise real boundaries, and provide reproducible
regressions while the report retains their scope.
