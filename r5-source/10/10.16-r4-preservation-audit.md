**Accepted design context:** R5.1 Parts I–IX, Part X 10.01–10.15. The following 10.17 owns durable fact/outbox/interest-registration mechanics; 10.18 owns explicit HumanHelp Refresh and the two-host failure schedule; 10.19 owns opt-in direct participant routing and distributed acceptance.

## Editorial decision

Preserve R5's architectural improvements and restore R4's useful concrete role/host/authority example and optional real-world topology examples without reinstating lengthy fictitious APIs. Make explicit the two separate obligations: *distributed transition semantics refine the same admitted application machine*, and *actual deployed paths and external failure assumptions establish applicability*. Retain exact cross-host command binding/retention, permitted unknown outcomes and current authorization. Treat distributed router interest structures as qualified interchangeable realizations; do not mandate a single bus, graph hierarchy, Valkey, Rust router, broker, or topology-specific application programming model.

The prior conversation's interest in hierarchical interest filters, replicated routers and conservative invalidation redelivery is a possible strategy, not a currently proven Gesso capability. The revised normative contract permits them only if registration freshness, failover, missing-notice recovery and disclosure obligations are established. R5's stronger outbox/registration contracts remain in 10.17, avoiding duplicate authorship.

## R4/R5 preservation and strengthening decisions

1. **Same semantics:** Multi-node realization adds placement, not new Gesso operations, authorities, retry meanings or browser adoption rules.
2. **Two different evidence edges:** Abstract/distributed refinement is separate from physical deployed route/writer/backend qualification.
3. **Roles and principals:** The choreography role, actor realization, principal, host, execution, command, transport attempt and resource identity remain distinct.
4. **R4 visual example:** Preserve the A-to-C host replacement for semantic `[:authority :request R]` with `:request-authority` role, explicitly illustrative rather than an API.
5. **Host is not authority:** An Aleph/Biff process temporarily realizes a projection but cannot acquire permission from a host label.
6. **Host/session rebinding:** Every replacement invocation derives trusted current principal, operation, arguments, target and disclosure at the actual boundary.
7. **Durable command identity:** Preserve the bound command across deliveries, distinguishing HTTP request and backend submission attempts.
8. **No cross-node cache deduplication:** Duplicate suppression and historical outcome require qualified shared, atomic, retained authoritative evidence, not a local callback journal.
9. **Command replay versus new effect:** Compatible recorded commands resolve without another incorporation; a new intent must meet current transactional authorization.
10. **Outcomes remain epistemic:** A lost or ambiguous response cannot be inferred from Request current-state alone or labeled rejection.
11. **Retention horizon:** Command history/tombstones, enforced expiry/reuse exclusion, restoration/incarnation and compatibility define exactly where deduplication applies.
12. **No invented retry by new ID:** A participant with uncertain intent cannot silently generate a different command identity and claim it is resolution.
13. **Simple real topology:** Two physically independent processes, shared qualified authority, distributor, optional cross-host transport and compatibility are necessary to test replacement; separate broker is not a universal prerequisite.
14. **R4 product examples retained:** Aleph, HAProxy, XTDB, Valkey, Redpanda are possible products, not mandatory deployment components or proof of correctness.
15. **Identical API semantics:** Local and cross-node invalidation/operation transports are realizations of one app declaration; another runtime or Rust adapter cannot silently alter those laws.
16. **Mixed-version activation:** Old/new assembly, browser assets, authentication, protocol, source, command record and routing interfaces need directional compatibility or an explicit retirement path.
17. **Serving identity is observed:** A registered in-process handler or supplied node string is not proof of the actual physical listener and database writer set.
18. **Backend freshness at each host:** Shareable backend identity does not imply equal reader frontier, authenticated internal transaction basis or causal proof.
19. **Distinct progression coordinates:** Transaction ID, system time, domain revision, SSE cursor, request and command ID cannot be collapsed into one global sequence.
20. **Invalidation differs from choreography message:** Advisory potential-state change does not create a domain operation, grant protected read authority, or constitute an admitted execution-message receipt.
21. **Routing optimization is optional:** Indexed filtering, replication, hierarchy and conservative redelivery are allowed only under their stated coverage and authorization contracts.
22. **Router failover needs knowledge:** Healthy standby does not imply interest state, registration frontier or replay completeness; silence and local cache emptiness are not evidence of no change.
23. **Lost-notice recovery:** A qualified fence, retained source, replay or gap/recovery path is needed before currentness; re-broadcast without evidence cannot promise recovery.
24. **Overdelivery may be safe but not unlimited:** Duplicate/inexact authorized advisories can be coalesced without violating progression, disclosure and resource limits; they cannot be promoted to authoritative adoption.
25. **Protected topics:** Routing interests and advisory scopes themselves require data minimization, tenant isolation and current authorization.
26. **Real test environment:** Process death, distinct sockets, actual shared backend, changed auth and independent reads are required for physical host-failure claims.
27. **Safety versus liveness:** Partition/reconnect/failed router must preserve safety; progress is conditional on backend/network availability, retention, surviving topology and explicit user action.
28. **No suspended stacks required:** Durable domain state and later short choreographies remain ordinary cross-user rendezvous; optional durable participant machines have separate contracts.
29. **Finite/scoped test evidence:** Two successful hosts or one cross-host retry provide bounded integration evidence, not universal multi-node refinement.
30. **Original source remains canonical:** Authors build normal Gesso applications; no parallel multi-node TLA/Quint/Recife specification or topology-specific business semantics is required.

## Gesso v1622 source-relative evidence and nonclaims

- `src/gesso/live/core.clj` composes model metadata, invalidation expansion, process-local hot source, per-client flow and SSE response transport. This is a useful semantic decomposition but not a distributed interest router or cross-node delivery guarantee.
- `src/gesso/live/invalidation.clj` expands declared primary changes without inspecting database writes; it does not establish production writer completeness, outbox creation, or causal notification.
- `src/gesso/live/source.clj` explicitly identifies itself as an **in-process** indexed subscription source with coalescing. A matching local interest is not a globally acquired router registration.
- `src/gesso/live/flow.clj` builds client-local flows and indexed subscriptions; it does not own a cross-node retained log, gap fence or durable routing protocol.
- `src/gesso/live/transport/sse.clj` formats outgoing SSE/Manifold stream behavior. A local SSE send is not a browser receipt or proof of global subscriber recovery.
- `src/gesso/live/consistency/xtdb.clj` offers explicit per-query consistency/progression primitives and distinguishes ID-only `submit-tx` from `execute-tx` TransactionKey. It neither publishes invalidations nor proves cross-node basis satisfaction.
- `src/gesso/model/command_resolution.clj` constructs a proposed atomic canonical command record and compatible replay under trusted disclosure; it explicitly does not authenticate real principals, all domain guards, real XTDB durability or unbounded linearizability.
- `src/gesso/live/optimistic/server.clj` provides a trusted server operation/settlement facade but delegates business authorization, transaction correctness and actual Live publication.
- `src/gesso/assurance/proof/xtdb_gateway_biff_request_mediation.clj` checks a host-local final handler and scoped writer, not actual server adoption, external writer confinement or a multi-process consistency theorem.
- `src/gesso/assurance/proof/conditional_single_node_refinement_evidence.clj` expressly assumes all contributing operations used **one node** and relies on caller-supplied reports; it cannot be reused as a multi-node certificate.

No real multi-host installed topology, durable outbox/subscriber fence, verified router failover, shared authentication, production incarnation bridge, two-node fault injection, cross-node writer closure or general distributed refinement was observed or executed in this review. These remain *future obligations*, not defects in the timeless normative plan.

## Eighteen positive/adversarial acceptance pairs

| # | Positive case | Adversarial or excluded case |
|---|---------------|------------------------------|
| 1 | Same Claim is admitted with qualified semantics on A or C | Host label cannot alter authorization or create a second domain authority |
| 2 | Retry uses original bound C42 via another process | New C43 cannot silently substitute for unresolved C42 |
| 3 | Compatible durable C42 resolves under current disclosure | Local cache hit/record absence is not proof of commit or rejection |
| 4 | Two same-ID submissions have at most one qualified incorporation | Concurrent hosts cannot each incorporate a fresh copy |
| 5 | New authorized Claim evaluates current Membership at C | Old A session or revoked principal cannot borrow authorization |
| 6 | Retained command record supports its declared replay horizon | Expired or restored DB history cannot silently reuse an old command ID |
| 7 | Real two-process route can survive A death | Two labels in one JVM or dead process both behind one port cannot prove replacement |
| 8 | Shared authoritative write is visibly acquired through C | Successful C query insufficient for required frontier cannot count as authoritative currentness |
| 9 | Qualified old/new version pair interoperates during rollout | Incompatible command/asset/route is blocked or retired rather than silently coerced |
| 10 | Trusted A/C backend and handler identities are acquired | Caller-supplied node/assembly labels are not deployment evidence |
| 11 | Routing sends scoped notice to interested live client | Stale router filter or late registration must not be interpreted as no relevant change |
| 12 | Router failover retains knowledge or triggers qualified recovery | Healthy router with missing interest view cannot silently drop a notice and certify completeness |
| 13 | Authorized duplicate advisory is safely coalesced | Extra advisory cannot disclose protected scope or induce automatic domain adoption |
| 14 | Qualified replay/fence closes initial registration gap | Silent missed notice cannot mark current subscriber as caught up |
| 15 | Own-command response and remote advisory remain separate | Bob's remote Claim advisory cannot settle Alice's command or become Bob's authorized read |
| 16 | Browser explicit Refresh yields authorized sufficient observation | Lagging host or stale client resource cannot adopt current-looking but insufficient state |
| 17 | Durable model state survives host process loss | Lost in-memory choreography stack does not erase committed Request or invent intent |
| 18 | Recovery succeeds under stated availability/permission/user-action premises | Partition, absent record, denied disclosure or missing Refresh cannot be called a violated unconditional liveness theorem |

These are prospective independent acceptance cases. No new JVM/XTDB/Chromium/multi-node test was executed.

## Scope and handoff

10.16 owns physical placement, identities, minimal topology, command continuity and the *obligation* for qualified interest routing. 10.17 owns durable fact/outbox, dispatcher, registration fence, subscriber gap detection and recovery. 10.18 owns HumanHelp's explicit remote Refresh and exact two-host failure schedule; 10.19 owns ephemeral direct-message semantics and full distributed acceptance. 10.20 owns the final system-boundary invariant. The R4 worked durable-Claim vs typing-message contrast is substantively distributed between 10.17 and 10.19, while its A/C identity example and optional topology products are explicitly preserved here.

The cross-section acceptance pass must challenge the R4 preservation and R5 design across these joins, without claiming editorial acceptance equals deployment certification.
