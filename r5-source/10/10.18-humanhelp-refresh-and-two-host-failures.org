*** HumanHelp preserves explicit Refresh across hosts

Part VIII selects explicit Refresh for both remote creation and remote lifecycle
changes to already visible cards. This policy is settled for this plan; only the
separate response-flow product contract remains unresolved there.

Remote advisories may update scoped outstanding debt or indicate a recovery gap.
They do not automatically fetch and adopt a new board. Own-command outcomes and
the specifically permitted local rejection/unknown recovery paths remain the
exceptions defined in Part VIII. Those exceptions do not authorize unrelated
membership changes or clear unrelated remote debt.

*** The selected product contract and distinct permissions

This is a selected *HumanHelp* application policy, not a
general change to Gesso Live's choreography semantics. The
authoritative model may commit remote Create, Claim, Unclaim,
Take-over/Reassign, On-the-way, Complete or Cancel on another
host. The resulting scoped invalidation records potential
outstanding authority that Bob could choose to acquire;
it never grants a domain read or installs a changed card.
Both remote creation and lifecycle changes to a card Bob
already sees require explicit Refresh for ordinary
collection-content adoption.

The two independently permitted local continuations are
narrower than a global Refresh:

- Alice's own accepted command can adopt its *correlated*
  authorized result and the declared selective affected-card
  or membership change, subject to physical installation and
  current ownership. It cannot clear unrelated board advisory
  debt or pretend that a later individual-card observation
  refreshed the whole cohort.
- A rejected or indeterminate local command can perform its
  specifically admitted affected-Request recovery read. This
  can disclose a current state caused by someone else where
  current authorization permits, but cannot add unrelated
  collection members or convert unknown command attribution
  into a historical success/rejection claim.

Initial page acquisition, user Refresh, an own-command result,
and a scoped conflict-recovery read carry different grants
and coverage claims. A browser can still display a stale
Claim button before an explicit Refresh, but its invocation
must pass *current* protected model eligibility and cannot
assume the displayed owner or Membership is authoritative.
The separate HumanHelp response-interaction product choice
in Part VIII remains unresolved; completing this two-host
Claim case does not certify that product journey.


One Refresh grant authorizes one board acquisition under that contract. It does
not schedule an automatic successor read when a newer advisory arrives during
the request. A user action explicitly coalesced under the permitted policy is
accounted for as that action, not invented by the scheduler. An actually newer
qualified observation may discharge additional covered debt where the scoped
progression relation proves it sufficient.

*** Refresh grants, adversarial arrivals, and scoped debt

One permitted Refresh issues one board acquisition with a
stable scope, resource ownership, optional previously observed
progression requirements and a bounded lifecycle. If a newer
advisory arrives while the acquisition is pending, it records
separate or composable scoped debt; it does not silently
schedule a successor GET or confer a new user grant. Only a
new explicit Refresh/Retry action, or user action explicitly
coalesced under the admitted policy, may issue the relevant
additional acquisition. If the *already issued* qualified
read returns a sufficiently newer coherent observation, it
may discharge newer debt that is actually proved covered.
Mere chronological arrival, a greater-looking token or a
matching Request UUID is not such proof.

A command outcome, invalidation, provider read basis, SSE
cursor, board-cohort membership, per-card observation and
successful HTMX installation are distinct evidence. Debt
merging preserves organization/location/projection and
progression-compatibility boundaries; unrelated or
incomparable requirements remain separate. When retention,
coalescing budget or replay coverage is insufficient, report
typed unknown/gap debt rather than dropping it or declaring
the board current.

Search, sort, mine-first, unclaimed-first, terminal-visibility
and card expansion operate on the *adopted* bounded cohort
under Part VIII's local presentation contract. They cannot
trigger an undisclosed remote collection reacquisition just
because the visible board has newer advisory debt. A
successful local action may selectively update the affected
card and legitimate membership without upgrading the entire
adopted-cohort basis.


A board observation must be coherent across Request, primary assignment, and
permitted User projection at its declared provider context. A lagging host that
cannot satisfy the required progression returns insufficiency and preserves
recovery. It must not echo the requested basis as if it had observed it. A
successful HTTP response is not evidence that the required frontier was reached.

*** Qualifying one coherent board candidate

A complete-board acquisition binds the current trusted
principal and allowed Organization/Location, source-owned
cohort and completeness contract, RequestAssignment primary
membership, Request statuses, permitted User projections,
query temporal context and finite collection bounds.
These relations must be observed at one qualified common
provider basis or carry independent evidence sufficient to
justify the advertised coherence. A series of unrelated
reads on an advancing database is not a complete snapshot
because the last response happened to return HTTP 200.

An insufficient or lagging read through C must preserve the
original debt and typed retry/repair affordance. The
server must not fabricate sufficiency by echoing a requested
frontier into its response. A complete authorized current
board can establish current cohort membership; an individual
Request recovery read cannot. A missing Request in an
incomplete, denied, truncated or differently scoped result
does not establish authoritative absence. Counts are facts
about the *adopted* cohort, not the latest global database.

The browser treats the received candidate as *not yet
adopted*. The current resource instance, authenticated
scope, acquisition grant, nonregressing progression and
permitted installation batch must agree. For HTMX OOB
toolbar and collection changes, physical target installation
and batch completion are distinct from HTTP receipt. A
failed or partial swap retains unsettled adoption debt and
uses the declared compensation/repair protocol without
claiming that an older owner regained rights. A delayed
callback, aborted-but-completed request or replaced DOM
resource cannot install a stale candidate, even when its
domain Request ID is still valid.


No acquired board is adopted if its resource is retired, its scope is no longer
permitted, or it would regress newer locally installed authority. Installation
of toolbar, collection, and associated evidence follows the adoption-batch
contract, including repair after partial failure. Reconnect and host replacement
do not waive that contract.

A known authorization-context change retires the affected protected projection
and subscriptions according to their lifetime contract. It cannot erase data
already disclosed to an offline browser. Protected rereads and subscription
renewal still require current authorization at the replacement host.

*** Context changes outrank remote-adoption preference

Logout, switched principal or Organization, revoked read
permission and replacement of the admitted board scope
are trusted context/lifetime transitions, not ordinary
remote Request advisories. They retire incompatible
subscriptions, grants, pending installations, provisional
effects and protected projections according to the
supported-client contract. An in-flight request created
for Bob's prior Organization cannot install its late
response into the new identity's board. Historical
command-result disclosure requires its own *current*
principal and permission; reconnect to a different host
does not inherit Alice's old browser settlement rights.

No framework can retract protected bytes already copied
by an untrusted or offline client. The enforceable boundary
is current server-side read, stream, command, historical
result and recipient/OOB-drain authorization, plus
retirement of controlled client resources. An advisory
topic or count must not reveal otherwise protected
Request, helper or Organization facts.


*** A concrete two-host failure schedule

The schedule's authoritative and browser facts must be
observed at different physical boundaries. In particular,
an outbox publication does not confirm Bob's SSE receipt,
Bob's SSE receipt does not authorize Refresh, and an
authorized acquisition does not prove a DOM adoption.
The Alice/host-A and Bob/host-C flow is the reference scenario. The steps below require a
*qualified* shared backend, distinct running host processes,
actual current sessions, and the installed Gesso/HTMX/SSE
browser path for an end-to-end acceptance claim. A two-host
fixture drawn as one JVM with two labels does not establish
this physical guarantee.


The following schedule exercises distinct facts; it is an acceptance scenario,
not a proof that every deployment execution behaves this way.

| Step | Authoritative or transport fact | Permitted participant conclusion |
|------+---------------------------------+----------------------------------|
| 1 | Alice's bound Claim reaches host A | Submission may proceed; no commit is inferred from arrival |
| 2 | Guarded Request, primary assignment, command result, and outbox intent commit | The authoritative command is incorporated |
| 3 | Host A dies before delivering Alice's response or dispatching the outbox | Alice may still have =:commit-unknown=; the commit remains durable |
| 4 | A dispatcher on another surviving process publishes the retained intent | Notice reaches the declared distribution boundary; browser receipt is separate |
| 5 | Bob receives a valid scoped advisory through host C | Record debt; do not automatically adopt the remote lifecycle change |
| 6 | Alice reconciles or replays the same bound command through host C | After binding and disclosure checks, return the permitted recorded result |
| 7 | Bob presses Refresh and host C obtains sufficient coherent authority | Acquire a candidate observation; current browser admission and installation remain necessary |
| 8 | Bob's current resource successfully installs the admitted batch | Record the permitted adoption and discharge only justified covered debt |

*** Failure cuts, correct negative conclusions and recovery

| Fault point or race | Required observation and forbidden shortcut |
|---------------------+----------------------------------------------|
| A fails before reaching the physical write boundary | No commit inferred from intent; reissue only under the qualified command protocol |
| A submits but the transaction result is lost | Alice keeps =:commit-unknown= until command-specific retained evidence resolves it |
| A commits but dies before HTTP result or outbox dispatch | Durable domain, command result and required publication intent survive; absence of response is not rejection |
| Outbox is forwarded twice or acknowledgment is lost | Bob may see duplicate advisory debt, never a second Claim or automatic board adoption |
| Notice was emitted before Bob's interest became effective | Registration fence, replay or explicit gap/authorized recovery; stream silence is not currentness |
| Router fails with stale interest knowledge | Replacement repairs coverage or records uncertainty; healthy process alone is insufficient |
| Bob's previous Refresh is pending when another notice arrives | Retain uncovered newer debt; do not schedule an automatic successor acquisition |
| C returns a lagging or noncoherent board | Reject insufficiency as a candidate for the claimed scope, even when HTTP succeeded |
| Bob changes Organization or logs out during the read | Retire incompatible owner; drop the old response and recheck server-side disclosure |
| Browser swaps toolbar but fails collection installation | Keep batch/adoption incomplete and repair within current resource lifetime |
| Bob's DOM resource is replaced while an old callback is pending | Old callback/effect cannot mutate the new resource or restore stale continuity |
| Alice resolves C42 through C after concurrent new domain activity | Historical C42 attribution and current Request content are acquired separately |
| C42 cannot be disclosed after Membership revocation | Nondisclosure is correct; never guess rejection or reveal another user's history |
| A Remote Request is created while Bob searches adopted cards | Search changes only adopted presentation; new Request appears only after an admitted Refresh or own-result rule |

The positive control for each case includes a real eligible
operation and, where the policy permits, a subsequent
successful authorized acquisition and installation.
A reject-everything handler, empty subscriber fixture,
untriggered process fault or stale synthetic adapter trace
is not evidence of the relevant production guarantee.
Gesso's underlying model checker can explore abstract
schedules, but physical two-host correspondence also
requires real independent host, provider and browser
observations with their versions, scope and open premises
recorded.


Variants lose the advisory, expire a cursor, duplicate publication, reject a
lagging read, change Membership, or replace Bob's resource between receipt and
mutation. Each variant must preserve its unresolved obligations until the
appropriate evidence and permission exist. Host C's ability to read the current
Request does not by itself attribute Alice's command.
