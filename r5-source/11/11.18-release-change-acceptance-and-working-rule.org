** Acceptance for changes to the release mechanism

The release system itself needs mutation and positive-control evidence. At
minimum, exercise:

- a semantic change invalidating its complete required dependency cone while an
  independent subject stays reusable;
- an implementation-only change retaining a valid abstract theorem while
  invalidating affected physical evidence;
- a forged or corrupted cached report failing at the issuer/re-admission boundary;
- a missing required capability remaining missing despite all exposed operations
  being closed;
- failed, skipped, unsupported, unavailable, stale, and incomplete required checks
  each blocking the claimed decision;
- a disabled stronger policy failing a release intent that requires that policy;
- a valid conditional claim retaining its accepted premises without inventing
  mandatory unmet obligations or erasing the original ledger;
- a tested artifact differing from the served bytes failing correspondence;
- a checked local handler not adopted by the actual server failing or narrowing
  the installed-host claim;
- concurrent activation, partial installation failure, and cleanup preserving
  coherent current bindings;
- a known invalid old premise preventing fallback to an otherwise previously
  admitted assembly;
- compatible rolling directions succeeding and unsupported directions retiring
  or rejecting before incompatible effects;
- unresolved command identity surviving execution retirement without a fresh-ID
  resubmission or false rejection;
- protected recovery honoring current disclosure and HumanHelp's adoption policy.

The test report names the first intended enforcing boundary, actual subject and
artifact, observation origin, fault schedule, and remaining premises. Rejection
of every candidate is not success: ordinary supported positive releases and
reusable unchanged evidence must continue to work.

** Working rule for every semantic or release change

For each changed component, identify the proposition it establishes, the premises
it needs, the evidence mechanism, the actual enforcing boundary, and the dependent
claims that must be reconsidered. If the next layer cannot mechanically check
the required interface and evidence relationship, that portion of the chain
remains an explicit premise or an unmet obligation according to the profile.

The intended result is a framework that knows which claims are proved, checked,
qualified, runtime-enforced, trusted, asserted, or tested; which concrete
realizations those claims concern; and when they stop applying. Conditional
liveness retains its environmental premises alongside its evidence class.

A release is admitted because its declared requirements and applicable evidence
compose through the actual construction and installation path. Completion is
claimed because the required behavior and assurance scope have been established.
Neither conclusion follows from an application merely appearing to start.
