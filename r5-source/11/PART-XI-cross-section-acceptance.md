## R4 preservation and preferred-R5 improvements

The R4 baseline includes the explicit source/checker and implementation
change examples; incremental dependency-cone recheck; the A44/B45
adapter distinction; green cache corruption; candidate integrity;
finite rolling compatibility; C42 unknown-outcome retirement;
the full global non-goal catalog; and separate operational,
compositional, external-formal and multi-node completion milestones.
Those subjects remain owned by 11.01–11.18, not merely mentioned
in a reconstructed table.

The preferred R5 architecture is retained where stronger:
immutable claim-first admission, closed scoped results, four
subject-specific release decisions, exact artifact and issuer
provenance, coherent activation, directional overlap, semantic
versus physical continuation, and separate completion scopes.
The whole-part correction to 11.08 is upheld: its fourth
release *coordinate* is a compatibility **relation**, not a
fourth version identity. No new universal middleware,
storage topology or implementation language has been mandated.

All eight R4 Part XI `CUSTOM_ID` values survive in identical
order. R5.1's longer exposition is justified by explicit
owner/consumer handoffs and falsifiable negative cases rather
than by a larger textual length alone.

## Cross-part acceptance, not cross-part proof

- **Parts I–II:** domain owners and current authority supply original
  requirements and protected semantic meaning. Generated release
  metadata cannot invent a new independent source of rules.
- **Parts III–IV:** Choreo/projection and guarded command incorporation
  have separate proofs, effects and C42-specific historical outcomes.
  Release activation cannot override those contracts.
- **Parts V–VI:** provisional presentation, browser resources, adoption,
  continuity and cleanup need qualified physical and temporal
  ownership; transport success does not establish browser truth.
- **Part VII:** assembly inventory is prior to actual installed host
  correspondence, protected-writer closure and activation.
- **Part VIII:** remote lifecycle/creation remains advisory until
  explicit authorized Refresh, while creator-local correlated
  effects and selected recovery remain scoped. The product-owned
  Response decision remains open and blocks full product completion.
- **Part IX:** checked rule/projection derivations, closed source
  obligations, issuer provenance and nonvacuity are separate from
  inspected/installed backend behavior.
- **Part X:** S0/S1 formal soundness, S2 checker premise, S3 typed-atom
  semantics and S4 production transfer are distinct; actual multi-node
  publication, interest and failover cannot be inferred from a
  single-node proof or a successful finite search.

These joins describe coherent **future obligations**, not
discharged implementation evidence.

## Documentary verification and limits

At acceptance base, all eighteen numbered Part XI Org source files
were fetched at the same branch revision. Their ordered exact
concatenation matched the published canonical Part XI string
(character-for-character, 291,569 JavaScript string code units);
all eighteen separately recorded R4-preservation audits exist.
Its eight `CUSTOM_ID` anchors match the R4 baseline in order,
with no duplicates. Ten Part XI internal anchor-link occurrences
were inspected; their targets resolve to Part XI or to accepted
Parts I, VII, VIII, IX and X. All twelve Org begin/end block
delimiters observed in Part XI paired without nesting errors.

The original R4 Part XI (54,816 characters) and preferred R5
Part XI (69,749 JavaScript string code units) were read as
comparison baselines, not assumed to be identical to the revised
candidate. This separate decision also reviewed the committed
whole-part reconciliation and the independent acceptance ledgers
for Parts VIII–X. The scoped v1622 Gesso implementation
correspondence recorded in the 18 audits was not promoted to
current framework completion.

The present pass was conducted through the GitHub connection.
It **did not** execute `python3 script/assemble_r5.py --check`
in a local Gessoplan checkout, a JVM or browser suite,
real XTDB/Biff listeners, a multi-host failure test, any
external prover, a deployment or an independent human audit.
Editorial validation cannot establish those results.

No normative Part XI Org source needs rewriting for this
editorial decision. The acceptance record and Part XI progress
README are the only intended changes.
