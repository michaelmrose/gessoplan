## Editorial judgment

Preserve R5's stronger claim-first release contract rather than returning to a monolithic all-green build. Make R4's predeclared denominator, mandatory release-gate completeness and incremental evidence reuse explicitly falsifiable against the true source and actual candidate. Separate a *release request*, its *derived gate inventory*, *checked evidence*, and *physical installation/adoption*. An optional stronger assurance family can remain open when the requested narrower milestone permits it, without bypassing the basic structural, runtime security, rendering or artifact gates. Keep the detailed four decision states and result classifications in the already separate 11.02, avoiding contradictory release terminology.

## Twenty-five R4 preservation and strengthening decisions

1. **Preserve R4's first:** Preserve R4's first release requirement: correct source and proof dependency identity with a strong but incremental release discipline.
2. **Keep ordinary construction:** Keep ordinary construction separate from additional optional advanced proof milestones.
3. **State the claim:** State the claim before running tests, deriving proof tasks, deciding the rollout scope or sampling the installed environment.
4. **Original source requirements,:** Original source requirements, selected product capabilities and implementation-discovered operations are independently compared.
5. **A release gate:** A release gate cannot shrink full-completion requirements because a feature is absent from the current executable.
6. **An intentionally smaller:** An intentionally smaller product scope creates a named separate claim with visible exclusion and supported-environment bounds.
7. **The operational milestone:** The operational milestone does not require all external formal or multi-node milestones, but remains subject to mandatory authorization and construction gates.
8. **An advanced strict:** An advanced strict profile cannot silently downgrade to a weaker profile upon failure or checker absence.
9. **Versioned proof profile:** Versioned proof profile and mandatory judgments are distinct from permitted accepted premises.
10. **Canonical requirements, application/source/semantic:** Canonical requirements, application/source/semantic assembly, emitted JS, implementation, provider and installed deployment are different subject identities.
11. **Source-preservation fingerprint and:** Source-preservation fingerprint and matching names do not establish semantic correspondence, physical behavior or serving deployment identity.
12. **Candidate manifest binds:** Candidate manifest binds required evidence to precise selected subject, versions, topology and configuration rather than acting as magical authority.
13. **Proof reuse may:** Proof reuse may survive implementation changes only when affected conformance, backend and artifact evidence is requalified.
14. **Previously passed evidence:** Previously passed evidence cannot bypass current checked applicability, including original source and issuer-controlled admission.
15. **A trusted open:** A trusted open premise can be accepted only when the selected profile permits it; mandatory proof/qualification cannot be hidden in a premise list.
16. **An empty proof/test:** An empty proof/test inventory is nonvacuous only when independent source-coverage and discovery completeness are established.
17. **Unknown applicability, unsupported:** Unknown applicability, unsupported checker, unavailable provider and missing product choice remain different failure owners.
18. **Skipped, stale, incomplete:** Skipped, stale, incomplete or unexecuted required checks never become passing results; 11.02 owns the detailed closed release-result algebra.
19. **Authenticated principal, valid:** Authenticated principal, valid command binding and protected read/write authorization are enforced at actual runtime, not frozen by build-time success.
20. **Checked Biff application:** Checked Biff application construction or a retained in-process report cannot alone authenticate the deployed final handler or a separate writer path.
21. **Browser bundle bytes,:** Browser bundle bytes, compilation/manifest identities and actual served assets require independent correspondence checks.
22. **HumanHelp's explicit remote:** HumanHelp's explicit remote Create/lifecycle Refresh policy survives; its response-flow decision remains open and blocks complete product claims.
23. **Release gate and:** Release gate and physical installation/activation/completion remain separately qualified decisions owned by 11.02 and later Part XI.
24. **Required test and:** Required test and adversarial acceptance fixtures need successful positive controls, not a reject-all or missing-action false pass.
25. **Release intent remains:** Release intent remains a timeless application specification and does not imply present implementation, production certification or all four milestones.

## Actual Gesso v1622 source-relative correspondence and limits

- `src/gesso/assurance/report.clj` builds a source-relative conditional root report. Its own contract denies independent theorem authority, authenticated test-run receipts, installed physical route/writer verification and deployment permission; a report fingerprint only detects changes over supplied/current declared sources.
- `src/gesso/assurance/subject.clj` provides versioned *structural* identity over bounded EDN-like subjects. It neither proves denotational equality nor performs Clojure/runtime implementation checking; a matching semantic ID cannot substitute for actual selected candidate conformance.
- `src/gesso/assurance/proof/application_assurance_report.clj` recomputes original-source conditional evidence and deliberately retains permanent open obligations for proof-kernel soundness, installed application adoption, physical XTDB writer completeness, abstract/physical refinement and browser/HTMX/SSE realization. It does not admit a candidate into production.
- `src/gesso/assurance/proof/certificate.clj` offers narrowly scoped, opaque JVM-local issued conditional proof handles for supported proof classes. Source rechecking is mandatory; these are not portable signed release credentials, physical effect-time authorization or universal full-application certification.
- `src/gesso/live/application_preflight/assurance.clj` describes supplied construction and rendered surface preflight evidence with explicit unproven enumeration and installed route adoption, rather than asserting full runtime closure.
- `src/gesso/live/application_preflight/biff.clj` can wrap a current supplied Biff handler and check rendered canonical HTML, but the file explicitly cannot prove later handler replacement, direct raw Ring response bypass or that a physical listener actually used the returned handler.
- The reviewed current-source modules do **not** establish a single authentic, comprehensive release-intent freeze/gate derivation/admission/installation/activation/completion system. That lifecycle remains a future Part XI design requirement, not a proven v1622 capability.

| # | Positive admitted case | Forbidden nearby inference |
|---|------------------------|----------------------------|
| 1 | Complete HumanHelp requirements derive a full gate inventory | Missing response-flow hidden by the current supported-operation list |
| 2 | A named partial slice is admitted with explicit exclusions | Slice is labeled full HumanHelp completion |
| 3 | Valid normalized semantic proof remains applicable to selected candidate | Copied report or stale dependency reused without checker admission |
| 4 | Accepted candidate binds actual current browser artifact | Old compiled JS reused after modified assembly |
| 5 | Actual installed Biff handler/XTDB writer enforces required gate | Only tested wrapper exists; raw deployed path bypasses it |
| 6 | Operational claim respects required runtime authorization | A missing stronger external proof silently removes auth checks |
| 7 | Stricter formal profile completes required actual checks | Timeout/unsupported mandatory checker is auto-downgraded to tested |
| 8 | Selected backend version qualifies its actual obligations | Expired provider qualification asserted by caller passes |
| 9 | Real positive and negative tests run for required capability | Empty test discovery or reject-all endpoint appears green |
| 10 | The release records all four completion milestone statuses separately | One green build or proof report claims multi-node completion |
| 11 | Current principal can read permitted HumanHelp board on Refresh | Remote notice or stale session bypasses protected scope |
| 12 | Changed implementation triggers scoped conformance and deployment recheck | Unchanged semantic ID retains stale handler/browser evidence |

These are prospective independent source/physical acceptance cases, not passing test results.
