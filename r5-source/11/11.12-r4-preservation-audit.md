## Governing judgment

Restore R4's explicit proof/checker artifact-class, theorem coverage,
TCB, formal correspondence and first-boundary mutation diagnostic
measurements while retaining R5's better denominator and original-source
requirements. A well-formed metric needs a fixed original subject,
predeclared complete inventory and attributable checked evidence.
Generated catalogs may be perfectly closed over their own smaller
inventories, and positive test counts may be large while the
independently specified product is still unusable.

The revised text makes non-displayed mandatory product controls remain
visible, separates the exposed assembly closure metric from original
usable product scope, distinguishes trusted premises from proved
conditions, and prevents an empty/shortened denominator from issuing
100% coverage. It does not create a universal confidence score,
a new proof issuer, runtime gate or second requirements registry.

## Thirty-two R4/R5 preservation and strengthening decisions

1. Progress is not synonymous with revision counts, line volume,
   number of green rows or raw assertion totals.
2. Every metric binds the original independent requirement set.
3. Release scope, selected profile, milestone, subject and environment
   are part of metric applicability and comparisons.
4. Product capability inventory differs from generated exposed routes.
5. Assembly closure measures all genuinely exposed managed
   obligations, not independent missing product capabilities.
6. Original-source dependency completeness is independently established;
   a caller-provided complete-looking graph is insufficient.
7. Legitimate scope changes require a new claim identity and preserve
   the old denominator and documented approval.
8. No silent post-failure downgrade from mandatory proof/test into
   trusted premise, skipped or narrower claim.
9. Empty/unsupported inventory cannot be credited as 100% without
   independently established valid exclusion.
10. Distinguish non-run, missing, incomplete, unavailable, unsupported,
    skipped, stale and failed from genuine passing evidence.
11. Credit passing only when issuing evidence matches exact intended
    subject, scope, configuration and result class.
12. Product success requires eligible real-user positive and applicable
    negative/recovery histories for each required capability.
13. Runtime enforcement is measured at actual installed route,
    writer, output and privileged effect boundaries.
14. Typed semantic coverage is per subject/judgment, not per
    unconstrained Clojure function name.
15. Framework theorem coverage names selected properties,
    proof artifact kinds, boundedness and conditional premises.
16. Finite exploration is not universal theorem proving.
17. Formal-to-production correspondence is separate from abstract
    proof, installed byte match and successful browser behavior.
18. Original application/writer dependency closure retains the
    transitive assumptions and missing sources.
19. Controlled mutation inventory and expected first rejecting
    boundaries are specified independently of what passed.
20. Rejection quality requires a valid paired positive case and
    helpful diagnosis; reject-all does not count as progress.
21. Trusted-base size and accepted assumptions remain audit
    inventories and dependency maps, not scalar confidence.
22. Selected compiler/XTDB/host/adapter/configuration envelopes
    receive separately applicable qualification evidence.
23. Recovery coverage includes unknown commands, reconnect,
    release retirement and failed providers, not just happy path.
24. Rolling-release metrics cover all reachable A/A, A/B, B/A,
    B/B pairings and any proven route exclusions.
25. Incremental reuse is measured by sound dependency invalidation
    alongside valid reused evidence, not reruns avoided alone.
26. A new physical artifact/provider can invalidate correspondence
    without invalidating the corresponding abstract theorem.
27. Parallel test inventory, preflight, worker results and failure
    accounting must be complete before credit is given.
28. Rerunning a nondeterministic failure does not retroactively
    erase the original observation or remove it from the set.
29. Performance results name hardware, dataset, backend, workers,
    topology, resource limits and workload.
30. Fast developer gates do not replace required real Chromium,
    XTDB, formal, physical fault or multi-host execution.
31. Reporting blocker completeness is useful even while all
    current release eligibility claims remain blocked.
32. All measures remain explanatory claim-specific data and
    never gain proof-issuer, runtime-effect or release-admission
    authority from their percentages or emitted shapes.

R4's explicit measurement classes are all retained. R5's stable
denominator, performance and incremental-reuse improvements
remain. No essential R4 requirement is intentionally removed.

## Actual implementation evidence and open work (v1622)

Reviewed source on the application-assurance GitHub branch,
at the commit recorded above:

- src/gesso/assurance/proof/application_assurance_report.clj
  computes a non-authoritative conditional report from original
  source-dependent composition, provenance and observed-writer
  accounting. It rejects the interpretation that copied summaries
  prove hidden-writer absence, XTDB implementation refinement,
  independent kernel soundness or browser behavior.
- src/gesso/assurance/report.clj exposes a root source-bound
  conditional evidence accounting and preserves caller-reported
  observations as descriptions; a reported test outcome is not
  authenticated external test execution.
- src/gesso/live/application_preflight.clj closes specified
  whole-application relations and can describe checked
  assembly/finite-reference observations, but expressly
  does not thereby establish an application-wide theorem or
  actual deployed handler adoption.
- bb.edn identifies separate quick, JVM, formal, browser and
  integration test tasks. The presence of these tasks is an
  inventory of commands, not evidence that the corresponding
  workloads completed for this commit or profile.

These implementation features support selected conditional evidence
and diagnostics. They do not establish a complete original
HumanHelp product denominator, automatic comprehensive live
writer inventory, independently authenticated executed test
receipts, universal proof-to-execution correspondence or one
globally numeric completion measure.

No JVM, real XTDB/Chromium, formal checker, browser integration,
physical deployment, parallel test or HumanHelp test was
executed for this editorial review.

## Twenty paired future measurement controls

| # | Required honest measure | Misleading nearby result to reject |
|---|-------------------------|-----------------------------------|
| 1 | Required six capabilities still count after only four ship | Four of four exposed routes called full product completion |
| 2 | Missing Response decision is explicit | Missing feature removed from denominator |
| 3 | Original-source obligations establish complete assembly | Caller-generated subset counted as all sources |
| 4 | Actual production writers and routes are observed | Test-only wrapper stands in for deployed guard |
| 5 | Checked semantic subset is precisely reported | Arbitrary Clojure execution becomes theorem proof |
| 6 | Trusted assumption recorded as conditional premise | Assumption counted as independent derivation |
| 7 | Finite sample and universal correspondence kept distinct | Small model check sold as physical theorem |
| 8 | Predeclared mutation inventory and paired valid control | Reject-all gets 100% pass rate |
| 9 | Defect fails at first applicable trusted boundary | Crash after protected write counted as early check |
| 10 | Real positive Reassign works through installed controls | Always-disabled button counted as implemented |
| 11 | Relevant compiler/backend/host are actually qualified | Other adapter or fixture supplies production result |
| 12 | C42 uncertainty remains open with recovery | Timeout scored as rejection and resolution |
| 13 | True routing/failover directions included | One sticky session covers entire rollout |
| 14 | Changed physical artifact requalifies physical claims | Cached abstract theorem counts as current browser |
| 15 | Every required parallel worker result accounted | Missing shard treated as success |
| 16 | Performance evidence states exact resource/workload | Quick gate reported as production throughput |
| 17 | New requirement profile has explicit new identity | Failed denominator shrinks invisibly |
| 18 | Unknown source inventory stays blocked | Empty unchecked set produces 100% |
| 19 | Report displays all unresolved required gates | Fabricated passing map issues release |
| 20 | Positive actual browser operation and negative check | Synthetic request-only test called end-to-end |

These cases are *prospective* requirements. They do not prove that
their checks ran. The physical tests must observe actual installed
routing, backend and browser effects under the named profile, and
positive and negative examples must correspond to the same real
enforcement seam.
