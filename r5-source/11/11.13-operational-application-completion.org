*** Operational application completion
:PROPERTIES:
:CUSTOM_ID: milestone-operational-application
:END:

The operational milestone is a usable, structurally closed Gesso application
realized by the HumanHelp proving application and its public production models.
It requires every applicable completion gate in Part VIII, not merely a working
Claim pilot or an error-free startup.

The required evidence includes:

| Area | Completion condition |
|------+----------------------|
| Production authority | Mutations use the public production model contracts, current guarded dependencies, RequestAssignment ownership, and command-resolution semantics |
| Canonical construction | Source, operation catalog, routes, acquisitions, render contracts, plans, and artifacts form one admitted assembly |
| Actual host adoption | The serving path and relevant writers use the admitted handlers, gateway/provider bindings, policy, and output guards |
| Qualified substrate | Biff lifecycle, browser/HTMX behavior, compiler/build, and XTDB adapter/configuration meet the premises used by the claim |
| Browser operation | Actual controls execute the supported canonical plan and effect protocol with no anonymous downgrade |
| Required capabilities | Every capability in Part VIII has an eligible successful scenario and the relevant rejection/recovery scenarios |
| Multi-client policy | Remote creation and lifecycle changes remain advisory until permitted Refresh; own-command exceptions remain scoped |
| Recovery and continuity | Unknown outcome, stale resource/plan, failed installation, publication loss, and reconnect gaps have tested usable behavior |
| Enforcement sensitivity | Controlled defects fail at the intended production boundary and corresponding valid cases succeed |
| Independent acceptance | Real browser sessions establish visible outcomes and authoritative truth through the actual generated/served application |

Creation, details, response interaction, lifecycle actions, local search, sorting,
board options, terminal visibility, advisory feedback, explicit Refresh, selection,
scroll continuity, and protected access are required as defined in Part VIII.
Claim, Unclaim, Mark on the way, Complete, Cancel, and Reassign each need an
eligible positive browser case. Disabling the control in every fixture does not
satisfy the capability. Reassign includes real target-helper selection and the
appropriate manager authority; it is not relabeled self-claim.

The lifecycle model uses =:done= for the completed state. The primary assignment,
Request state, and permitted rendered projection must agree under the public
model contract. A provisional DOM change alone is not authoritative success.
An accepted result uses the operation's qualified authoritative result or
acquisition contract; an extra read is required only where that contract requires
one, not as an unconditional ritual after every commit.

The following product status is canonical:

- Remote creation and remote lifecycle adoption are selected: explicit Refresh,
  with only the admitted own-command/local recovery exceptions in
  [[#decision-humanhelp-remote-lifecycle-adoption]]. Their positive and negative
  scenarios are mandatory.
- The response interaction at [[#decision-humanhelp-response-flow]] still requires
  a concrete product contract and independent acceptance before the full
  operational milestone can be claimed. A placeholder control or an invented
  response meaning does not close that gate.
- Refresh scope, concurrent advisory handling, one-grant acquisition, completion,
  and remaining-debt behavior follow [[#req-humanhelp-refresh-coverage]].

The three claims from [[#req-application-assurance-claims]] are reported separately:
declared closure, actual production enforcement, and required usable behavior.
A server starts, a route returns HTTP 200, or a browser has no console errors
without necessarily establishing any of them.

Acceptance uses actual rendered controls, authenticated contexts, served assets,
trusted routes, public production models, and physical browser lifecycle events.
It must not manufacture hidden protocol fields in a way that bypasses the control
being tested. Multi-client assertions require distinct appropriate contexts.
Provider evidence and command reconciliation establish durable truth; the browser
scenario establishes how the user sees and acts on it.

The operational milestone does not require the later formal milestones. It does
require the ordinary semantic checks and every stronger profile requirement
explicitly selected for that release. An unmet stronger requirement cannot be
ignored while reporting the same requested release admitted.

A partial operational checkpoint names its missing capabilities or decisions. It
cannot redefine the canonical HumanHelp target by dropping the response flow,
Reassign, terminal behavior, or another difficult capability.
