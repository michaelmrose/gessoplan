** Root release evidence and candidate integrity

The root report has machine-readable data and a human-readable explanation of
the same records. It is generated from checked construction and observed evidence;
it is not a second hand-maintained application registry.

*** Required report fields

The report identifies:

1. Release intent, canonical requirements, requested milestone/scope, assurance
   profile, and independent required-capability inventory.
2. Normalized subjects, required dependency closure, original obligation ledger,
   accepted premises, mandatory unmet obligations, and excluded claims.
3. Actual implementation bindings, source/build provenance, provider/configuration
   identities, compiler/runtime versions, and qualification applicability.
4. Issued plans, browser manifest, build receipt, exact artifacts, and the admitted
   assembly generation to which they belong.
5. Every required gate's result, evidence class, evidence reference, subject,
   environment, bounds, and enforcing boundary where relevant.
6. Candidate, installation, activation, compatibility, and retirement decisions,
   including the actual serving-host evidence for the claim made.
7. Product decisions, resource limits, retention contracts, security boundaries,
   and conditional-liveness premises.
8. Completion results for each requested milestone and a change-impact explanation
   relative to any reused evidence.

*** The root report carries a typed claim/evidence ledger

A root report has a stable, versioned representation whose human-readable
explanation is generated from the *same checked underlying records* as its
machine-readable form. It does not reconstruct source or release policy from
the checks that happened to pass, and a user-edited human explanation cannot
update the checked decision. The report is about a specific named release
intent, original requirement denominator, candidate, physical environment,
evaluation window and claimed milestone; it is not a global `certified`
flag on an application name.

Each required claim and capability has a source-derived original requirement
reference and a current disposition: which checked proposition or physical
effect is asserted, what evidence class can support it, who issued or observed
that evidence, what exact subject/configuration was examined, and what the
selected profile requires. A required obligation absent from the emitted
evidence ledger remains *missing*; an admitted narrower scope names the
excluded original requirement and its approval. The ledger preserves
unknown, failed, unavailable, unsupported, incomplete, stale and
intentionally skipped cases according to 11.02 rather than erasing them
from the denominator.

| Report dimension | Must distinguish and bind |
|------------------+---------------------------|
| Original source and coverage | Declared business rules, models, operations, invariants, initial states, roles, protected writers, rendered affordances, all required product capabilities, omissions and source-completeness assumptions |
| Semantic proofs and issue authority | Exact theorem subject, proof family, original derivation/checker source, proof kernel and dedicated checker identities/versions, inference/profile scope, genuine issuer, qualified premises and independent checker-soundness status |
| Assembly and actual implementation | Normalized construction and issued assembly generation, real guarded operation, route, installed handler and writer/worker bindings, source/implementation dependency closure and open physical-refinement edges |
| Browser and build | Plan/manifest, generated bootstrap source, compiler/toolchain/format versions, exact emitted JS identity, receipt, tested bytes, installed/served bytes and client acquisition assumptions |
| Real provider and environment | Selected XTDB/backend profile, transaction lowering and codec, provider configuration/version, host/credential/OS/network/transport and physical qualification envelope |
| Gate observations | Required gate ID and expected boundary, actual test/checker type and result, provenance and execution identity, tested source/configuration, positive/negative oracle, bounds, coverage limitations and allowed premise classes |
| Release decisions and rollout | Separately identified candidate admission, specific installation eligibility, exposure/activation and required overlap/retirement/continuation recovery facts, with requalification triggers |
| Product and milestone | Independently selected product policy, required HumanHelp workflows, positive user-capability evidence, named operational/compositional/external-formal/multi-node milestones and remaining unselected or unmet requirements |

The report also classifies the relevant *trusted computing base* (TCB)
by responsibility: source semantics and normalization, proof/checker,
compiler/build, authenticated application/XTDB writer, installed host,
browser/transport and external environment. For each dependent claim,
it states which pieces have actual checked evidence, which are
explicit trusted premises and which are still unsupported or unknown.
A backend premise may be accepted under a selected profile but cannot
be presented as an independently proved universal property.

A useful evidence graph contains edges from the original obligation
to the admitted semantic/proof subject, concrete implementation,
selected artifact, observed deployed gateway and resulting milestone
decision. Such edges describe the *specific correspondence evidence*
and its limits. Their presence in a report does not establish the
edge's truth: the trusted consumer obtains issued proof or physical
observation from the owning boundary, then validates the resulting
reference and current applicability before any release decision.

*** Identity and provenance are claim-specific

The canonical release subject from 11.01 remains immutable while
evidence is collected. Semantic/proof identities, dependency
closure, issuer identity, implementation identity, exact bytes,
assembly generation, installation and public activation are
distinct coordinates. A Git commit, timestamp, source filename,
shared operation name, matching digest or supplied report status
cannot substitute for any missing coordinate.

A test made against a fixture assembly, old server implementation
or staging host may be valuable evidence *for that stated scope*.
It cannot be reused as production evidence merely because the
current candidate has the same logical operation name. Concrete
test-to-actual-installation correspondence requires an expressly
checked applicability relation, including the compiler, emitted
artifacts, provider, runtime and resource boundaries required by
the claimed behavior.

A built artifact's receipt binds the selected generated bytes to
its declared manifest under the build contract. It does not by
itself prove that the deployed listener serves those bytes, that
a user browser loaded them, or that the browser completed a
permitted DOM effect. Installation and activation evidence from
the actual serving environment belongs to the separate 11.02
decisions and Part VII's physically enforced lifecycle.

An immutable historical release evidence package is useful for
reproducibility, comparison and audit. When source, checker,
policy, provider, credential, served artifact, active host or
retention condition changes, the report must distinguish historical
facts from *currently applicable* evidence. A current release
decision reacquires or revalidates exactly the dependent
observations required by 11.03–11.04, rather than editing an old
successful report to appear current.

*** Root reports are descriptions, not new authority

The reporting process consumes genuine checked construction,
proof-issuer and observation interfaces. A caller-supplied map,
test list, original source graph, physical route inventory,
reported issuer handle or manually assembled root report is
neither a second application registry nor a release authority.
The selected trusted owner must obtain the actual source and
installed observations from their appropriate boundaries, with
unknown physical enumerator completeness recorded as an open
obligation rather than assumed away.

The human and machine presentations may arrange information
differently, but must represent the same claims, evidence
classes, failed or unrun gates, accepted premises, exclusions,
enforcing boundaries, and limitations. A concise summary can
link to checked detailed evidence, but may not call a weaker
status `certified` or omit a blocking gate. The executable
source, proof package and physical installation—not the printed
report—remain the authoritative inputs for the corresponding
decisions.

Proof/diagnostic values must not be fed into runtime semantic
transition decisions, browser effect authorization, Membership
evaluation or XTDB guarded writes. Genuine proof of a conditional
abstract proposition does not convert it into current physical
permission. Runtime guards enforce current authority even when
release reports are unreadable or unavailable.

*** HumanHelp and release-report challenge cases

| Valid root-report statement | Forbidden promotion or omission |
|-----------------------------+---------------------------------|
| The original full HumanHelp capability catalog is named, including unselected response-flow work | The successful Create/Claim/Refresh subset becomes the full completion denominator |
| Claim theorem is admitted under its precise original source, kernel version and remaining premises | A copied proof report becomes universal XTDB/CLJS implementation soundness |
| Selected Biff/XTDB handler and complete current writer inventory have their own physical evidence or open gap | A source-derived route list asserts that every external writer was observed |
| Exact browser manifest, tested built JS bytes and actually served artifact have distinct references | A valid build receipt is presented as proof of real client installation |
| Fixture/browser staging positive and negative tests retain their precise tested subject and environment | A passing staging suite certifies a different production host |
| A named required physical qualification is stale or unavailable and remains blocking | A current human summary hides the failed gate while machine results say `:passed` |
| A strict profile lists accepted source assumptions and separately unmet physical obligations | Accepted backend premise is silently rendered as fully proved |
| Four release decisions and four completion milestones have separate status/subjects | One green root record is interpreted as permission to activate every host |
| A supported remote HumanHelp lifecycle advisory awaits explicit Refresh and current protected read | An SSE send is labeled canonical browser adoption or participant receipt |
| Changed provider or serving handler triggers requalification of its dependent release claim | An old timestamp/digest permanently qualifies the changed deployed gateway |
| A known committed command remains committed after delivery/diagnostic failure | Missing release report turns unknown/committed domain command into rejection |
| Positive valid Claim succeeds under the actual protected gateway, and forbidden attempts are rejected | A reject-everything handler passes solely because its negative tests are green |

These are independent report and physical conformance requirements, not
evidence that the tests have run or that any release is certified. The small aggregation illustration
in 11.06 intentionally checks no such issuance or physical evidence:
its output remains downstream explanatory data.

Every reference must resolve to evidence of the stated subject and scope. A
passing fixture test, an old browser bundle, a supplied route inventory, and an
actual installed handler are different evidence. The report must preserve the
origin and limits identified in Part X rather than combining their green labels
into an unsupported production claim.

The root report is explanatory. An admitted candidate or installation uses the
genuine checked construction result or supported revalidation contract. It does
not trust a caller-edited =:passed= or =:eligible= field. The report never becomes
an authorization capability for Claim or a semantic input to browser transitions.
