*** The tested object must be the activated object

The candidate binds declarations, prepared operations, route/decoder behavior,
providers, selected assurance policy, runtime/render gates, plans, manifest, and
actual emitted bytes through the construction phases in Part VII. Mutable lookup
or post-test replacement cannot substitute a different implementation at activation.

Artifact verification inspects the actual bytes and receipt relation. A filename,
embedded manifest string, matching digest metadata, or build timestamp alone is
insufficient. The normal build path derives the bootstrap from the admitted
application source and uses the qualified compiler/build contract. The compiler
remains a named premise unless stronger correspondence evidence establishes it.

Release acceptance records what the browser and server actually used. A generated
artifact copied into a staging directory but never served is not evidence of
browser correspondence. A minified asset's hash establishes byte identity under
its assumptions, not the semantic correctness of its compiler output.

Relevant differences between test and production environments are explicit
obligations. A tested transaction adapter may be reusable while production
credentials, backend endpoint, server adoption, or topology must be established
at installation. Environment promotion is a checked relation over those facts,
not a blanket assertion that staging and production are equivalent.

*** Coherent activation and failure handling

Installation prepares the final guarded handler, provider bindings, owned workers,
asset references, and response lifecycle under the admitted candidate. Required
checks run before those application paths are exposed. Private initialization of
dependencies may precede admission; an externally usable unchecked mutation path
may not.

Activation uses a compare-and-activate or equivalent checked transition that
prevents an older concurrent candidate from replacing a newer current assembly
without the declared policy allowing it. The binding being activated includes
routes, executors, providers, assurance policy, render/output checks, and artifact
references. Publishing those pieces independently can expose a mixture that was
never admitted.

Coherence is local to the stated activation boundary. A rolling deployment across
hosts may temporarily serve several admitted assemblies under the compatibility
contract below. It is not called a globally atomic switch unless the deployment
mechanism actually establishes that stronger property.

Each invocation captures its immutable assembly and concrete context at entry.
Deferred response bodies, futures, streams, and transferred work retain an
explicit applicable context through their declared lifetime. They must not fetch
whichever mutable registry happens to be current when completion occurs. Assembly
binding does not freeze Membership, authorization, backend validity, or resource
ownership; those premises remain current where the operation requires them.

A failed candidate leaves the old assembly serving only while that assembly is
still valid. If a discovered backend, security, or semantic violation invalidates
a required premise, failure to install a replacement is not permission to keep
using the unsafe claim. The declared response suspends affected work or enters an
explicit restricted mode whose remaining guarantees hold.

Failed installation retires its owned resources in dependency-safe order. It
must not leave an unchecked listener, scheduler, or worker active. Cleanup errors
are reported alongside the primary admission failure without concealing it.
Failed cleanup does not restore retired effect permission.

A gate failure after a command may have been submitted must not invent rejection.
Stopping traffic, retiring an assembly, or aborting a response does not roll back
a durable commit. Command reconciliation and publication recovery follow their
separate authoritative contracts.

*** Rollback is a new checked activation

Reactivating an older artifact does not roll back domain state, command records,
outbox entries, or previously disclosed information. The older code must still
understand the state and protocol it will encounter and must satisfy current
qualification and security requirements.

A release involving schema or state evolution declares forward and backward
compatibility, migration ownership, relevant writer coverage, and the invariant
entry point after migration. A migration is an authoritative writer; it is not
outside the proof boundary merely because it runs once from an administration
script.

Rollback eligibility considers the actual committed migration state, all writers
that can still run, the command-result retention and decoding contract, pending
durable work, and the supported client/server combinations. An irreversible
change may make an older application version ineligible. The remedy is a declared
forward repair or another qualified transition, not an unexamined code rollback.

The plan does not prescribe a universal migration engine. It requires the chosen
mechanism to make these conditions explicit and enforce the claimed boundary.
