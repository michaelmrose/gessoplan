*** The four scopes do not collapse into one status

Completion is a set of *four separately justified milestone judgments*,
not one status called "Gesso complete" or an ordering constraint on
project implementation. The subjects are:

| Milestone | What its complete result actually establishes | Other conclusions that do not follow |
|-----------+----------------------------------------------+--------------------------------------|
| Operational application | All independently required HumanHelp product capabilities work through qualified installed model, host and browser paths within the selected operational profile | Independent kernel soundness, unbounded formal proof or production multi-node resilience |
| Compositional certification | The named source-complete, non-vacuous typed/checker/issuance chain and genuine multi-record Claim pilot meet their selected profile | Every HumanHelp interaction works, the checker is independently proved sound or the real physical backend is universally refined |
| External formal verification | The exact accepted independent formal theorem and qualified S0–S4 correspondence frontier of the selected external profile are established with their premises | Current Request authorization, complete product behavior or arbitrary installed XTDB/browser correctness |
| Multi-node production | The original single-machine semantics survive the selected actual independent-host, router, recovery, compatibility, security and load/fault envelope | An unbounded theorem, all possible topologies or independent proof-kernel soundness |

These milestones have independent *requirement denominators* derived
from Parts VIII–X and 11.13–11.16. Their work can overlap, and
one can be complete before another. They are not aliases for
development stage numbers, a cumulative project percentage,
or automatic implications in either direction. A successful
Claim proof pilot can coexist with missing Response interaction;
a usable operational application can coexist with an unproved
external checker; a physically resilient two-host application
can still have an unestablished semantic theorem.

They are also distinct from the *four release decisions*
of 11.02: candidate admission, installation eligibility,
activation eligibility and completion. A candidate can be
correctly admitted but never installed, installed but not
activated, or active under an allowed smaller release intent
without meeting a separately requested stronger completion
milestone. An abstract completion theorem does not authorize
installation or a live command. A permitted operational
release does not become a failed release merely because
an unselected formal milestone remains unfinished;
conversely, it cannot satisfy an originally requested
strict formal or multi-node release profile by silently
renaming the requested claim.

*** Completion records bind original requirements and actual evidence

A completion record is a *checked result for one named
release intent, milestone, subject and environment*,
derived from a source-complete requirement ledger and
qualified evidence. It is not an independently authored
status word. The root human-readable and machine-readable
views use the same validated underlying records; neither
can issue a certificate, invoke a protected operation or
change a source requirement by editing an explanation.

The record identifies all applicable coordinates:

- *Original subject:* canonical source and independently required
  product/model obligations, their owner, version and complete
  denominator, including separately unresolved product choices.
- *Selected claim:* one milestone or an explicitly requested
  collection of milestones, selected assurance profile,
  required positive/negative histories and predeclared
  release intent before checks execute.
- *Semantic candidate:* source-bound normalized rule/operation,
  Choreo, projected/executable and application-assembly identities;
  admitted artifacts, exact browser manifest and compiler/receipt
  relations, with their relevant generation/versions.
- *Installed realization:* actual selected Biff/Ring handler,
  guarded writers, providers, backend, workers, host/router
  and serving/loaded asset bindings; site, topology, configuration
  and evaluation window to which physical evidence applies.
- *Four release decisions:* separately current candidate,
  installation, activation and completion subjects, evidence
  and applicability. A stale host or newly revoked backend
  premise must not inherit an older activation result.
- *Each required gate:* original obligation ID, exact intended
  proposition or effect, issuer/observer and evidence class,
  original source, environment, physical/semantic boundary,
  checked result, qualified premises, dependencies and
  reproducible or authorized evidence reference.
- *Eight gate-result classifications:* =:passed=, =:failed=,
  =:incomplete=, =:unavailable=, =:unsupported=,
  =:skipped=, =:stale= or =:missing=, used only after
  the corresponding source and evidence record is
  genuinely checked. A different report vocabulary
  may summarize milestones without changing gate truth.
- *Current limitations:* mandatory unmet obligations, genuine
  accepted trusted premises, unselected product decisions,
  unavailable jobs, exclusions, finite proof bounds,
  tested physical fault/scale conditions, unresolved
  command/Live/recovery horizons and explicit liveness premises.
- *Change lineage:* previous claim/evidence subjects, exact
  source and implementation differences, dependency
  invalidation, reused still-applicable evidence and
  separately required requalification.
- *Outcome:* each milestone's computed complete, partial,
  blocked or otherwise accurately limited disposition,
  the first responsible failure boundaries and the
  stronger claims not established.

An explanatory record can display =:partial=,
=:prototype= or =:not-complete=, but those labels
do not replace the eight gate results and are
not proof issuer handles. A complete disposition
requires every *mandatory original gate* in
the selected profile to have genuine applicable
success or a specifically allowed conditional
qualified premise under the predeclared policy.
Mandatory unproved obligations cannot be
reclassified as voluntary assumptions because
their checker failed.

The initial denominator is not whatever a
generated catalog happens to expose. A missing
HumanHelp Response route, an undiscovered
external writer, a proof family omitted by
an elaborator or an unavailable physical test
is still counted when independently required.
The record can separately report closure of
the currently exposed assembly and coverage
of all original required product capabilities;
it may not combine their percentages or
replace the latter with the former. An
approved real change of product scope
creates a new identifiable requirement
subject and retains the old comparison
and authorization for that change.

*** Applicability is current and claim-specific

A historical completed result states what
was established *then*, about the exact
release, source, assumptions and environment
it actually checked. It is not a permanent
property of a repository, branch, application
name, model key, deployment label, digest
or browser cache. An independently proved
theorem can remain mathematically sound
after a runtime configuration change
while its claimed application to the
newly installed runtime becomes stale.

A change-impact computation follows the
dependencies of the exact affected claims.
A change in a source rule, original requirement,
normalization, proof checker, issuer, trusted
premise, production writer, backend incarnation,
provider, Biff handler, emitted browser artifact,
installed router or release compatibility
may invalidate different portions of the
evidence graph. The affected result is
marked stale, incomplete or blocked as
appropriate until independent requalification.
A genuine unaffected theorem, source
relation or valid physical observation
may be reused with its original subject
and current applicability established.
"No need to rerun everything" is allowed;
"keep every green line after a dependency
change" is not.

Known revocation of an accepted principal,
Organization Membership, credential,
model policy or backend safety premise
fences the dependent protected runtime
effect or disclosure at the actual trusted
boundary. A report's historical success
cannot preserve execution permission.
Likewise, an invalid previous assembly
is not safe fallback merely because
a newer installation failed; 11.07
governs current rollback, recovery
and restricted service.

Change status also preserves *what kind
of evidence survived*. A valid abstract
invariant may persist while the
source-to-physical writer coverage is
stale; a complete bounded model check
does not become an unbounded theorem;
a sound external kernel theorem does
not requalify a changed production
parser; an application preflight report
does not prove the running listener
uses the admitted handler; and a
historical successful client does not
authenticate the bytes loaded by a
later sleeping browser.

A change to documentation can alter
the *requirements* and thus the
claimed target, with the usual
requirement-version and denominator
reassessment. Editing documentation
cannot itself establish that code
has passed a newly described test.
The editorial acceptance of a
normative Part is not any of the
four implementation milestone
completion judgments.

*** Worked record: useful progress with four different answers

Consider a **hypothetical** HumanHelp
candidate with some genuinely checked
Create, Claim, board option and
explicit Refresh paths, but without
an independently selected and
accepted Response interaction
contract. It also has useful
conditional proof and two-host
experiments. The correct report
does not flatten these facts
into a single green project result:

| Completion subject | Hypothetical established evidence | Unmet original requirement and permitted conclusion |
|--------------------+-----------------------------------+----------------------------------------------------|
| Operational application | Some actual original production-model and browser capabilities plus installed assembly paths are qualified | Response contract and user scenario remain missing; report a partial operational slice, not the full milestone |
| Compositional certification | Typed Claim/guard, source-bound conditional checks and part of the issued proof chain are qualified | Required broader judgment or source-to-issued-plan obligations remain open; report only the exact checked pilot |
| External formal verification | A bounded derivation or finite exploration has actually been checked | Universal S0/S1 kernel metatheorems and selected S2–S4 production transfer remain open; do not report full external verification |
| Multi-node production | Two genuinely independent processes can access current shared model state and selected limited advisory behavior works | Host-loss, publication/interest gaps, compatible mixed generations and production load envelope remain missing; report a prototype or bounded observation |

The following is *schematic explanatory
data*, not a concrete Gesso API, a
runnable acceptance fixture, an
issued certificate or an executed
test result. All identifiers are
illustrative rather than references
to real checked evidence.

#+begin_src clojure
{:record/kind :illustrative/completion-explanation
 :release/intent :illustrative/humanhelp-operational-intent
 :requirements/original :illustrative/part-viii-required-set
 :candidate
 {:source :illustrative/original-source
  :semantic-assembly :illustrative/assembly-A
  :assembly-generation :illustrative/generation-G
  :browser-artifact :illustrative/exact-bundle-G}
 :installation
 {:host :illustrative/host-H
  :handler :illustrative/guarded-handler-H
  :backend :illustrative/selected-backend}
 :required-product
 {:selected-policy :remote-lifecycle/explicit-refresh
  :open-decisions #{:humanhelp/response-flow}
  :verified-scope #{:request/create :request/claim
                    :board/options :board/explicit-refresh}
  :missing-scope #{:request/respond}}
 :examples-of-gate-results
 {:operation/claim {:status :passed
                    :evidence :illustrative/claim-observation}
  :operation/response {:status :missing
                       :evidence nil}
  :physical/host-loss {:status :missing
                       :evidence nil}}
 :completion-explanation
 {:operational-application :partial
  :compositional-certification :partial
  :external-formal-verification :not-complete
  :multi-node-production :prototype}
 :warning :not-admitted-evidence}
#+end_src

Even in this illustrative record, a
=:passed= label has **no evidentiary
force** without independent issued or
observed matching evidence. The
=examples-of-gate-results= are not
the required complete gate inventory;
the missing entries cannot be
treated as inapplicable. A real root
record must resolve every mandatory
gate and its subject, admitted
issuer/observer, original source,
environment, premises and actual
receipt. The =:illustrative/=
identifiers authenticate nothing.
One actual original-source
Response contract cannot be
replaced by a placeholder button
or a copied result map.

The remote lifecycle policy in the
example is an *already selected*
explicit Refresh rule, not another
unresolved product decision.
Remote advisories cannot be
silently adopted because a new
runtime was installed, and a
recovered own-command outcome
does not confer unrelated board
acquisition authority. If the
Response choice is later actually
selected and all required
operational gates are exercised
and qualified, the same product
may attain operational completion
while the formal and multi-node
milestones remain independently
partial. A release permitted
by its actual operational profile
need not await an unselected
stronger milestone. A release
that originally requested a
strict external proof cannot
obtain permission by changing
the displayed claim label
after the proof failed.

*** Acceptance controls for completion records and applicability

| Required valid result | Nearby false claim to reject or contain |
|-----------------------+------------------------------------------|
| Four milestones retain independent original requirement sets | One green "Gesso complete" status erases missing formal or product obligations |
| Four release decisions name candidate, installed host, activation and completion separately | Valid candidate assembly map becomes proof of actual traffic activation |
| Every mandatory gate has checked evidence or explicit blocking disposition | Missing physical observation disappears because only generated passing rows are counted |
| Accepted conditional proof retains named actual trusted premises | A presumed XTDB/issuer premise is reported as an independently proved theorem |
| Real HumanHelp Response decision is selected and positively exercised before full operational claim | Claim demo or placeholder Response button satisfies full product denominator |
| Selected remote lifecycle explicit Refresh remains current and its grant scoped | An unrequested remote reread is treated as adopted after host replacement |
| Valid old semantic theorem is reused when only physical adapter changes | Reused theorem is presented as new installed handler qualification |
| Changed original rule or required proof checker invalidates dependent evidence | Old certificate handle, report hash or copied status stays green by default |
| New browser bytes or serving host requires its relevant physical checks | An old emitted-asset receipt certifies unrelated currently loaded browser code |
| Known revoked Membership fences protected actions regardless of release badge | Historical completion continues granting old actor new rights |
| Full requested strict release fails when its mandatory stronger milestone is open | A failing proof is reclassified as an optional smaller release with the same claim ID |
| Separately approved narrower preview retains original missing scope | Smaller exposed UI operation inventory becomes full product completion |
| An operational release remains eligible when unselected external work is partial | All four milestones are incorrectly imposed as mandatory for every deployment |
| Real two-host observation is credited only to its bounded topology and test | Shared XTDB and two process names become universal multi-node completion |
| Finite formal result retains its bounds and independent source | One model run or fabricated external report counts as proof-kernel metatheorem |
| Missing command result remains unknown under current disclosure and retention | Cached historical report or Request state is treated as command attribution |
| Valid release change marks only genuinely dependent claims stale | Every edit discards unrelated sound theorem, or no physical recheck is performed |
| Primary gate failure survives cleanup-report processing | A secondary report failure masks the reason the release was blocked |
| Root machine-readable and human summaries derive from the same checked ledger | Human text or serialized EDN status becomes an alternative issuer |
| Prior completed release remains historical with exact environment/provenance | An earlier green completion label is treated as permanent correctness |
| Conditional liveness requires actual availability and user-action premises | Offline user who never Refreshes is counted as converged |
| Genuine positive supported candidate works under the same gate rejecting invalid candidate | Reject-all release mechanism passes only negative controls |

These are prospective first-boundary
and positive/adversarial checks, not
executed acceptance observations.
The record may explain partial
progress while every still-required
gate remains visible. Its value is
that a downstream consumer can
identify *which source proposition
has been checked, for which actual
subject, by whom, under which
premises, through what enforcing
boundary, and what changed since*.
The completed record never becomes
an independent source of business
rules or a command/DOM authority.
