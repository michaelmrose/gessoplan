* Part XI — Release and completion
:PROPERTIES:
:CUSTOM_ID: part-11-release-and-completion
:PART_REVISION: 11-20261108
:END:

This part defines incremental evidence reuse, release admission, activation,
bounded compatibility, and completion. A release claim concerns an identified
application, supported scope, actual artifacts, and declared environment. It is
not established by a successful build, an empty error log, a large test count,
or a report containing a successful status.

Parts I–X define the semantics and enforcing boundaries. This part makes their
acceptance obligations concrete without introducing a second application model.
Part XII owns realization ordering. Operational usability, compositional
certification, external formal correspondence, and production multi-node support
remain four separately reportable completion scopes.

The plan is normative. Examples in this part illustrate release mechanisms and
hypothetical records; they do not declare the present implementation complete.

** Incremental certification, build, and release
:PROPERTIES:
:CUSTOM_ID: req-release-evidence
:END:

The ordinary application constructor performs structural admission and installs
the required production gates. A release profile adds its claim-specific proof,
qualification, acceptance, and deployment requirements. Omitting an optional
stronger proof profile does not disable structural construction, rendered-surface
checking, runtime authorization, or artifact correspondence.

A selected stronger profile must be enforced by the actual candidate and
installation path. Defining a strict checker or obtaining its report in a test
does not establish that production invoked it. A disabled or absent policy
cannot be treated as successful evaluation of that policy.

*** The selected claim is not the generated gate list

The release request is a declaration of *what is being claimed*, not a
summary reconstructed from checks that happened to pass. Its canonical
requirements originate in the actual supported application and independently
selected product obligations. Construction, elaboration, proof generation,
test discovery, and installation *derive* relevant gates from that request;
they cannot redefine the requested claim by omitting source operations,
writer paths, protected read surfaces, deployment roles, or product journeys
that are difficult to establish.

A release candidate has an immutable claim identity during one evaluation.
The release's exact subject, qualifying evidence, and intended runtime
realization are separately identified: a model/source identity is not a
handler implementation identity; an assembly fingerprint is not browser
asset bytes; a test fixture's host is not the actual production listener;
and a source-checked certificate is not a runtime permission. Reusing a
previously admitted result always requires rechecking its declared
applicability to these distinct subjects.

The minimum normal construction contract applies regardless of optional
stronger milestones. A user may request a bounded operational profile
without claiming an external formal proof or multi-node completion. But
the ordinary constructor must still check its mandatory whole-application
closure, generated/runtime artifact agreement, rendered affordance
boundaries and required current-authorization guards. An omitted advanced
proof option is not permission to bypass a necessary server/XTDB gate.


*** Declare the claim before evaluating its gates

A release intent identifies at least:

- the application and canonical requirement-set identity;
- the required product capabilities, independently of the exposed-operation list;
- the requested milestone or explicitly narrower supported scope;
- the versioned assurance profile, mandatory judgments, permitted premise
  classes, and required runtime enforcement;
- the semantic, implementation, artifact, provider, and configuration subjects;
- the intended deployment topology and supported compatibility directions;
- the required test environments, fault scenarios, resource limits, and product
  decisions;
- the admission, installation, activation, and retirement conditions.

**** Freeze the intended requirement denominator

The versioned release intent fixes the canonical requirement inventory and
which selected application/product capabilities count as fulfilled, excluded,
blocked, or unimplemented *before* expensive checking starts. Its denominator
includes obligations that the current implementation fails to discover;
discovery is itself an independently checked coverage relation against the
original declarations. A discovered empty set of proof tasks, zero failing
tests or zero registered business operations is not evidence that the
canonical requirement inventory is complete.

An intentional narrow release is a new identified claim. It names the
excluded capabilities and evidence families, why the narrower claim is
valid for its supported users and environment, and which original
milestones remain unmet. A missing requirement is never relabeled
not-applicable merely because its handler is absent. A profile may
explicitly accept a trusted premise under Part IX's rules; this is not
equivalent to silently deleting a mandatory theorem or physical
qualification from the requested milestone.

**** Bind the same candidate across its evidence edges

A current candidate manifest binds the versioned source/requirement set,
normalized semantic and proof-subject identities, admitted operation and
application assembly generations, implementation/configuration identities,
compiler/codec versions, actual emitted browser artifacts, chosen provider
and topology, required runtime gates, and each mandatory test/proof/
qualification witness. The manifest is an obligation/identity record,
not an invented universal certificate. Physical installation and
activation still need independent observations of the actual running
handler, worker, writer, served bytes and credentials.

Evidence is applicable only if its checked subject and dependency closure
match the *current* candidate within the selected relation. Exact source
equality, structural semantic equality, binary artifact identity,
implementation conformance and installed host correspondence are different
checks. A sound abstract invariant can remain reusable after a compatible
implementation change even while previous physical and browser tests become
stale. A copied successful report or a digest asserted by the subject under
test does not establish these relationships.

The release evaluator must report the origin of every mandatory gate from
canonical requirements or admitted application construction, including
an explicitly justified dynamic/opaque premise when a static catalog is
incomplete. It must record unavailable, unsupported, incomplete and stale
required evidence *without* converting it into success. The exact decision
vocabulary and distinction between admitted, installed, activated and
completed are owned by 11.02, not redefined here.


The release gate derives the concrete obligations from that intent and the
canonical application construction. It joins them to the original obligation
ledger, rather than replacing the ledger with a list of successful checks.
Required capabilities omitted from the implementation remain required.

Changing the requirement set, narrowing a proof domain, removing a capability,
or weakening an assurance profile is an explicit change of release intent. It
produces a distinguishable claim with its exclusions visible. It cannot make the
original full-completion claim pass by shrinking its denominator during gate
execution.

**** A concrete scope-bound counterexample

Suppose the full HumanHelp release still requires a separately selected
response-flow interaction, but the candidate demonstrates only Create,
Claim and explicit remote-board Refresh. Those features can be valuable
positive evidence for an appropriately named partial operational slice.
They cannot produce a completed *full HumanHelp* requirement set by
deleting response-flow from the discovered feature list. Similarly, a
proof of the Claim abstract transition cannot be presented as evidence
for all model operations, installed XTDB writers, real-browser behavior
and independent multi-node recovery.

Conversely, a fully specified response-flow product requirement that has
not yet been implemented is a missing application capability, not an
unsupported proof checker; a checker incapable of evaluating one declared
proof judgment is a distinct machinery gap. The release diagnostics and
repair owner must reflect the real deficiency rather than steering an
application author to rewrite sound product requirements around a tool.


A missing product decision is different from unsupported framework machinery.
Either may block the requested claim, but diagnostics identify the actual owner.
**** Nonvacuous release-intent challenges

| Positive candidate | Forbidden alternative |
|--------------------+-----------------------|
| Complete canonical requirement set produces its source-derived gate inventory | Empty or incomplete discovered operation set is declared complete |
| Named narrow profile explicitly excludes unimplemented journeys | Missing feature is silently omitted while full completion is retained |
| Current semantic proof is admitted for its checked proposition | Proof-looking report, old digest or mismatched dependency grants admission |
| Real source/assembly/artifact identities match the qualifying witnesses | Changed physical handler or served JS reuses stale conformance evidence |
| Actual protected runtime route enforces current admission | Disabled gate or never-installed wrapper is reported as successful enforcement |
| Original model and application requirements yield all required negative/positive tests | Reject-all or never-run test suite is used as readiness evidence |
| HumanHelp remote changes retain explicit Refresh and protected read policy | Successful SSE send is reported as canonical browser adoption |
| Selected stricter profile is genuinely evaluated before candidate admission | Strict failure is silently downgraded to a weaker profile or accepted premise |
| Required backend assumption is qualified within its declared version/scope | Caller-claimed or expired provider status is treated as production proof |
| Accepted operational scope names its four-milestone exclusions | One green build is called formal and multi-node completion |

Each row is a prospective acceptance obligation; it does not assert that the
current Gesso implementation or HumanHelp release has passed it. The real
positive case traverses the named construction and (where claimed) physical
boundary, preventing a reject-everything implementation from passing a
negative-only gate.


HumanHelp's selected remote-adoption policy is already part of Part VIII's
requirements. Its response-flow contract remains a product decision until it is
substantively selected and tested.
