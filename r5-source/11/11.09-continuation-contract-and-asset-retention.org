*** Derive a complete continuation contract

The continuation contract is derived from the admitted semantic objects and
bound physical protocol. It includes the dependencies capable of changing the
meaning or safety of continued work:

- operation meaning, placement, and relevant rule or assumption interfaces;
- command binding, canonical arguments, result records, retention, and disclosure;
- event vocabulary, state-machine transitions, and outcome mappings;
- retry, duplicate delivery, uncertainty, and reconciliation behavior;
- authority, principal, knowledge, provenance, and refinement requirements;
- progression, acquisition, observation coverage, and adoption policy;
- resource ownership, cancellation, retirement, and deferred effect behavior;
- required runtime capabilities and value codecs;
- actual route selection, transport envelope, decoder, encoder, and emitted
  browser runtime;
- persistent-state and durable-work formats the continuation can encounter.

Equality of a complete normalized continuation contract is a useful conservative
baseline for its semantic portion. It still requires actual route/decoder,
artifact, implementation, and qualification bindings to be valid. A matching
contract digest copied into a header establishes none of those facts.

A more permissive directional adapter must establish the required representation
or refinement relation. It names which arguments, events, outcomes, and states
it transforms and what premises it preserves. If the selected profile allows a
trusted implementation premise for that adapter, the premise remains visible.
A claim requiring checked refinement cannot be satisfied by an unsupported
handwritten compatibility flag.

Compatibility does not grant the old principal continuing authority. Current
session, Membership, Organization policy, and protected-disclosure conditions
remain runtime obligations. Semantic compatibility with a new rejection outcome
must be explicit where the old client needs to handle it; it cannot be presumed
because both clients once used the same operation name.

*** Retain assets and endpoints for the promised lifetime

An active overlap requires the exact browser assets, supported decoders and
encoders, reconciliation paths, and provider contracts promised to its clients.
Retaining only the newest JavaScript file under a mutable URL does not satisfy
an old artifact binding. Old assets use their exact versioned identities under
Part VII's serving contract.

Server reference counts do not measure sleeping browsers or offline commands.
The retention policy therefore accounts for the declared maximum continuation
window, recovery path, and command-record lifetime rather than deleting old
resources as soon as the last visible HTTP request completes.

Command reconciliation may need to outlive executable-plan compatibility. A
current protected lookup can interpret a retained command record through a
qualified read-only compatibility path without keeping the entire old mutation
implementation available. It must validate the original binding and current
disclosure permission. Supporting lookup does not imply that replay of the old
command is safe under new semantics.

Asset and route retirement are observable transitions with tests. Outside the
supported window, clients receive the declared typed retirement or recovery
response. An unexplained missing asset or decoder exception is not the intended
compatibility mechanism.
