*** Derive a complete continuation contract

The continuation contract is derived from the *same admitted source*
that owns the operation, Choreo projection and executable client plan.
It is not a second application-authored catalog of convenient version
labels. For an originating continuation and a target realization,
the contract identifies every dependency whose change can alter the
meaning, authority, physical representation or safe completion of
the continuation. An opaque dependency is explicitly an assumption,
a separately qualified implementation contract or an unsupported
boundary; it is never silently omitted from the source-derived
inventory because static analysis cannot inspect its Clojure body.

The normalized contract includes, at the applicable scope:

- original operation, role, placement, rule/invariant interfaces and
  source-derived semantic identity, with the permitted state/transition
  family and any open proof or backend premises;
- typed argument and presence semantics, canonical logical command ID
  binding, deduplication, authority scope, result vocabulary, rejection
  and uncertain-incorporation/reconciliation obligations;
- event, knowledge/provenance and allowed information-flow conditions,
  including which participant may receive or use each observation;
- progression and acquisition source/basis, query and coverage contract,
  advisory versus canonical observation, adoption grants and required
  authorization for collection membership and rendered content;
- selected optimistic resolution, causal outcome ordering, cancellation,
  response ownership and browser effect/resource-incarnation constraints;
- the specific endpoint, route/method/template, transport envelope,
  parameter/codec versions, decoder and encoder, outcome mapping,
  HTML/HTMX semantics and actual emitted browser runtime requirements;
- resource lifetime, transfer and retirement behavior for requests,
  streams, event subscriptions, deferred callbacks, old assets and workers;
- persistent document/state and durable-work encodings that the target
  can encounter, including migration/reader/writer compatibility and
  historical command-record formats;
- provenance of selected providers, installed executors and runtime
  capabilities, plus the declared applicability and invalidation edges
  needed to qualify the physical realization.

This is a *closed and source-derived* relevant-dependency interface
for the selected operation and continuation, not a demand that all
arbitrary host code be proved. If a required dependency or reachable
state/representation is absent, the stronger compatibility judgment
is open or rejected under the requested profile. Treating incomplete
discovery as an empty dependency set would make every plan appear
compatible and is forbidden.

*** Normalize semantic equality without turning hashes into proofs

A conservative compatibility rule compares complete, type-aware
normalized continuation contracts for their *semantic* subject and
checks all remaining current physical and trusted-premise edges.
Normalization has a versioned definition, accounts for defaults,
missing-versus-null fields, role/operation identity and dependent
rule semantics, and excludes diagnostic-only source metadata only
where the source's declared meaning demonstrably does not depend on
it. A digest is a compact identifier for the normalized bytes under
its hash assumptions, not an independent derivation or current
execution capability.

Equality of source names, Git revisions, route strings or a
caller-supplied digest does not establish semantic equality; equal
semantic contracts need not imply equal emitted JavaScript,
transaction adapters, decoder implementation, host installation or
permission to disclose historical results. A changed provider,
implementation, backend or artifact may preserve the abstract
operation theorem but invalidates its dependent physical
correspondence until requalified. A changed current Membership
does not change the semantic Claim contract, yet may prohibit the
particular operation or protected acquisition at effect time.

A more permissive *directional* adapter may translate an originating
plan or protocol into a target representation. It specifies its
domain of admitted origins, target assemblies, operation and
argument/result/state mapping, preservation obligations, error and
unknown outcome behavior, and the point at which the actual
transformation is enforced. Required refinement or simulation
evidence is bound to those exact subjects and assumptions. A
selected profile may explicitly accept a qualified trusted
implementation premise where permitted; it may not silently
replace required checked refinement with a handwritten
=:compatible?= flag. Reversing a proved old-to-new adapter does
not infer new-to-old compatibility.

The selected release evidence reports which rule admitted each
operation-specific direction: exact semantic equality, checked
adapter, explicitly permitted trusted premise, or exclusion.
It ties that rule to exact origin/target identities, current
dependency and implementation qualification, open assumptions
and the concrete first enforcing boundary. A proof-looking map,
human report or old successful compiler stamp cannot act as an
adapter, proof issuer or server/DOM authorization.

*** Bind actual route, artifact and browser realization

An admitted continuation can be enacted only when its origin's
real client artifact and the target's *actually installed* route,
decoder, response encoder and supported runtime form a compatible
physical pair. The build manifest, compiled bootstrap, artifact
receipt, exact built bytes, selected host and actual served/loaded
bytes remain distinct evidence subjects. The actual bytes must
match their qualified identity; their digest alone does not prove
the compiler's behavioral correctness. A retained file at a
build path is not an actually reachable versioned browser asset,
and a valid system-map =:biff.ring/handler= does not prove which
handler a running host invokes.

Versioned asset references are immutable during the promised
lifetime, including all byte-affecting dependencies needed to
execute their admitted plan. A mutable URL such as one that
always serves only the latest JavaScript cannot be relied on for
A's client while B is active unless the release establishes an
independent checked content/compatibility and cache relation.
Proxies, CDNs, service workers, browser caches and alternative
entrypoints are part of the stated actual serving/loading
qualification; an origin that self-reports a manifest ID does
not authenticate what code the client actually runs.

The release policy identifies exactly which admitted server
handlers, route selectors, envelope/codecs, result/command
decoders, subscription endpoints, provider contracts and
browser artifacts must stay available to service each permitted
A/A, A/B, B/A or B/B direction from 11.08. It also names the
mechanism ensuring they remain actually reachable, not merely
present in a deployment folder. The selected code/runtime
compatibility envelope is bounded by a versioned admission
policy; old packages are not kept executable forever solely
because an ancient tab can wake.

A browser returning from sleep, back-forward cache or offline
storage is not assumed still current. Before a protected send,
authoritative adoption or stale callback effect, its current
resource/assembly contract, permitted server pairing and
trusted runtime conditions must be established or the old
execution is retired. A compatible client plan does not freeze
the current actor, Organization Membership, route authorization,
protected disclosure, or DOM target ownership.

*** Specify distinct retention horizons and their owners

The release derives an explicit lifetime and owner for each
required resource and separately records its withdrawal rule:

| Retained subject | Required lifetime/owner relation | What retention alone cannot establish |
|------------------+----------------------------------+----------------------------------------|
| Exact old browser asset and matching dependency bytes | Named supported client execution/overlap window and serving owner, including sleeping-client recovery promise | That any browser actually loaded it, remains authorized or can continue past expiry |
| Old installed route, decoder, encoder and compatible executor | Every permitted origin-to-target operation direction during admitted overlap, under the owning host's current qualification | That an old writer remains safe after schema/authorization changes |
| Live subscriptions and event/reconnect protocol | Declared overlap, replay/fence and current interest/authorization recovery contract | That queued SSE delivery is current protected collection adoption |
| Resource-owned pending browser/request/stream work | Its valid current operation lifetime or checked transfer; retirement may end actuation rights sooner | That a reference count measures every remote sleeping browser |
| Durable command-result and historical decode/reconciliation path | Declared command retention and authorized resolution horizon, potentially longer than executable-plan overlap | That old mutation execution is still allowed or the observed state attributes a command |
| Persistent schema, migration and queued durable work formats | All admitted readers/writers and recoverable work that can encounter the format | That backward read compatibility grants backward write permission |
| Current protected content acquisition and DOM effects | Only the named current knowledge, principal, grant and resource scope | That possession of old data or a cached credential extends disclosure rights |

The overlap horizon, asset availability, command-record horizon,
authoritative state/format support, replay/registration windows
and required recovery horizon need not coincide. They must be
jointly satisfiable for the selected release promise. A release
cannot promise recovery from an old command while retiring
its only permitted decoder or losing its durable retained
record, nor can it call an old browser executable after
withdrawing the only compatible runtime endpoint.

When a horizon expires, the policy defines the reachable
typed refusal, semantic retirement and current authorized
reacquisition path. Expiry must be enforced by a current
boundary; the absence of an HTTP request, a zero process-local
reference count, a successful cache purge or a wall-clock
label does not prove that no old browser exists. A sleeping
client may be safely *refused* at the next contact without
extending its right to perform effects. Physical garbage
collection follows the actual eligible rights and retained
recovery obligations rather than creating a silent gap.

Command resolution often outlives executable-plan compatibility.
A new generation may expose a qualified, protected **read-only**
decoder and resolver for an original C42 command record even
after rejecting A's old mutation implementation. Resolution
validates the bound operation version, canonical arguments and
original target, stable command identity, current authorized
principal/disclosure and genuine trusted historical evidence;
a browser-held ID or a current Request state does not prove
C42 incorporated or identify which attempt caused it.
Where evidence is absent or outside the declared retention
guarantee, the status remains unknown or explicitly blocked;
it is not changed to =:rejected= by expiration or a network
exception. Compatible retry of C42, where separately admitted,
still must use the original binding and deduplication contract
rather than silently creating C43. Part IV owns command truth
and 11.10 owns recovering the old participant's intent.

*** Retention must preserve product acquisition policy

Release reconstruction is not a hidden source of extra
authorization or an automatic grant to adopt unrelated remote
changes. For HumanHelp, remote Request Create and lifecycle
changes remain advisory until Bob's explicitly granted
Refresh, except for precisely scoped own-command outcome and
affected-card recovery. Asset reload, SSE reconnection,
new host selection, plan retirement or recovered command
status does not discharge unrelated advisory debt or create
a new one-use acquisition grant. A newly initialized page
may have its independently declared initial-load grant; it
must be distinguished from a transparent successor read
performed merely because an old asset expired.

Retained local route, filters and an explicitly supported
draft can assist current reconstruction, but none retains old
authority. A valid current read must cover the required
scope/basis, remain discloseable under present policy, and
install only into the new resource's authorized target.
Out-of-window execution artifacts, stale optimistic rollback
callbacks and obsolete plan-private knowledge cannot be
restored by copying bytes from storage. Section 11.10 owns
the exact retirement, debt and participant-facing recovery
dispositions; this section requires the necessary retained
physical paths and evidence to make them feasible.

*** Positive and adversarial continuation/retention controls

| Required positive history | Invalid shortcut or counterexample to reject |
|---------------------------+-----------------------------------------------|
| Complete source-derived continuation inventory includes a real rule and its opaque dependencies | Missing rule or opaque body yields vacuous equal contract hashes |
| Typed normalization preserves missing/present argument meaning | Nil, missing and defaulted arguments are collapsed despite different admission |
| Equal semantic contract requalifies changed adapter and serving host | Unchanged operation digest is used to reuse obsolete physical evidence |
| Directional old-to-new adapter has bounded source/target refinement and effect rule | Handwritten compatibility flag or reversed direction passes without proof |
| Valid old plan uses a genuinely installed compatible route and decoder | Matching URL or handler map hides replaced live server entrypoint |
| Actual A browser bundle is served through its promised immutable reference | CDN/service worker returns incompatible B bytes under A's stable label |
| Physical byte receipt and qualified serving/loaded evidence bind an actual browser client | Build hash alone asserts compiler semantics and actual client installation |
| Sleeping A tab awakens and passes current continuation/resource admission before protected work | Cached old allowed bit or bfcache callback writes to new DOM or domain state |
| All A/B and B/A permitted directions retain needed codecs and endpoints | Old decoder is deleted after last observed server request |
| Released old execution rights are refused at the active boundary after overlap | Successful file purge is mistaken for automatic retirement of sleeping clients |
| Current principal and Membership are rechecked for old-origin lookup | Historical command ID, source proof or cached session grants protected disclosure |
| Genuine C42 historical record resolves via qualified read-only path on B | Readback of current Request is labeled C42 incorporation |
| Retained C42 result decode survives longer than old mutation executor | Resolver is deleted with obsolete writer or old writer revived for lookup |
| Absent command evidence preserves honest unknown and authorized repair | Lost record or expired asset becomes fabricated domain rejection and fresh C43 |
| Migrated state admits only qualified old reader/writer combinations | Schema-compatible old read is taken as permission for an obsolete writer |
| Live reconnect meets declared authorized fence/replay/interest contract | SSE transport acceptance is labeled complete board adoption |
| Remote HumanHelp advisory remains pending through asset reload | Reload auto-Refreshes unrelated remote Create or lifecycle changes |
| A permitted current acquisition installs into present owned DOM and required basis | Stale A callback overwrites newer B card or consumes old Refresh grant |
| Expired plan exposes typed retirement and applicable recovery | Missing JS file or decoder exception serves as the intended retirement protocol |
| Resource and recovery horizons are jointly valid for the release claim | Offline command promised recoverable after last qualified decoder and record expire |

These are prospective test and physical-observation obligations,
not a claim that any deployed release currently satisfies them.
The release gate must challenge real asset/handler adoption and
both valid and invalid runtime paths; a test-only rejecting wrapper,
copied stamp, passive status report or one successful staging
request is not enough.

Section 11.08 owns *which directional pairings are reachable and
admitted*. This section owns *which source-derived contract,
physical realization and retained resources make each pairing
safe and recoverable*. Section 11.10 owns retiring the
execution and restoring only authorized semantic intent.
No separate global compatibility registry, arbitrary suspended
machine migration or universal durable participant-message fabric
is required by these responsibilities.
