** Bounded rolling-release compatibility
:PROPERTIES:
:CUSTOM_ID: req-bounded-release-compatibility
:END:

A rolling release preserves *one admitted application semantics* while
several physical realizations, artifacts, hosts or invocations may remain
alive at once. Compatibility is a checked, potentially *directional*
relation between a particular originating client/continuation and an
admitted target server realization for a specified operation and protocol.
It is not a generic property of an application name, a Git branch, or
two nearby build numbers. A successful compatibility judgment preserves
only its named semantic and physical obligations under its declared
premises; it neither grants present authority nor proves that an
unobserved deployment uses the checked artifacts.

*** Name the four distinct release coordinates

A release decision distinguishes four related but non-interchangeable
coordinates—three identities/realizations and one directional relation:

- the source-derived semantic identity of the operation, projection or plan,
  including the conditions that make its continuation meaningful;
- the exact emitted client/server artifact and protocol realization, including
  actual route/decoder/encoder and browser runtime bindings;
- the admitted application assembly and its concrete installed/activated
  generation at each applicable host and deployment scope;
- the directional continuation/adaptation relation between an origin and
  a target for the operation in question.

A semantic ID may be unchanged while generated bytes, provider behavior,
trusted writer, decoder, installation or security qualification changes.
Conversely, two different generations may support a checked continuation
relation. The fourth coordinate is a relation, not another version identity.
Neither identity equality nor inequality proves that relation
without the relevant source, physical and current-premise evidence.

The normal baseline is a *finite, declared* overlap between the current
activated assembly and a selected predecessor. Another finite window
may be admitted, but it must name the actual eligible assemblies,
origins, target installations, supported operations, duration or
retirement condition, and recovery policy. =N= and =N+1= may illustrate
activation order; their arithmetic is not an assembly identity and
does not itself mean compatible. A third activation does not magically
make every previously served page disappear or its command uncertainty
resolve. The declared retirement boundary must have an enforcing and
recoverable meaning.

Development may build and admit many candidates without activating
them. The relevant predecessor is determined by the selected activation
history and declared rollout topology, not by earlier commit time,
candidate creation order, or a numerical version label. A candidate
that was never activated is not silently treated as a predecessor
serving real clients. Conversely, a still-reachable older host or
sleeping browser cannot be omitted merely because a newer release
was admitted and activated elsewhere.

*** Check every direction the real topology can expose

For a two-assembly overlap A (selected predecessor) and B (selected
current assembly), the release gate accounts for all four pairings.
"Permitted" always means *qualified for the specified operation*,
not unrestricted permission to invoke arbitrary routes.

| Originating client or execution | Target server realization | Required release judgment |
|---------------------------------+---------------------------+---------------------------|
| A client/plan | A server | Continued actual installation validity and supported lifetime of A/A, or enforced retirement |
| A client/plan | B server | Separate old-to-new semantic/protocol compatibility, a checked directional adapter, or typed retirement/recovery |
| B client/plan | A server | Separate new-to-old compatibility, or a physically enforced routing exclusion with safe failure |
| B client/plan | B server | Current-pair admission, actual installation and active runtime qualification |

The pairs are not interchangeable: an A client may issue an envelope
that B's decoder accepts while a B client uses a new field that A's
decoder cannot safely interpret. An operation-compatible Claim
continuation need not imply compatibility for an unrelated board
query, admin writer, Live subscription, or browser effect. Even
within one pair, protected commands, read-only reconciliation,
authorized collection acquisition and advisory delivery may have
different supported directions. Record their individual scopes.

The real reachable matrix is derived from selected deployment/routing
rules *and* the actual ways clients can reach a host: mixed instances
behind a load balancer, sticky-session expiration, retry and redirect,
host loss/failover, reconnecting SSE, stale page assets, service workers,
CDN/proxy behavior, in-flight requests, delayed async responses and
sleeping browser tabs. A routing rule that excludes B-to-A is an
enforced, qualified premise, not a conclusion from an ordinary
happy-path load-balancer configuration. If failover or a direct
endpoint can reach A, that pairing remains reachable unless an
actual checked guard excludes it before the protected continuation.

The release records the true endpoint, installed route and decoder,
selected source and plan identity, actual client artifact, host
generation, required protocol features, enforcement point and evidence
for every permitted or excluded direction. A shared URL, matching
operation keyword, apparent schema shape, source hash, browser-supplied
generation label or caller-edited compatibility map does not establish
the selected target or safe execution. A manifest checked at build
time does not prove that an already-running host actually serves it.

*** Admit compatibility or stop before the effect

A permitted cross-generation continuation must preserve the
source-derived operation meaning and the selected client/server
representation, including its invocation, result and recovery
contract. Its current target must have an admitted installation,
supported decoder/encoder, available browser/runtime capabilities,
and qualified physical execution or read path. A sound complete
normalized continuation contract may support conservative semantic
equality, but the actual physical and authority joins remain
separate checks. A broader directional transformation requires a
stated representation/refinement relation and the evidence or
explicitly allowed trusted premise appropriate to the selected
assurance profile. Section 11.09 owns that contract and the exact
asset/endpoint retention required to realize it.

Unsupported or unqualified skew is detected at the *first boundary*
where the incompatible continuation could otherwise acquire
protected data, perform an authoritative effect, or install a
browser-owned result. The available outcomes are: admitted
continuation under current premises; checked directional adaptation;
semantic retirement with the declared authorized recovery; or
typed refusal where that recovery is unavailable. A silent fallback
to an ordinary unmarked HTMX request, an old anonymous decoder,
discarded semantic metadata or a guessed operation is never an
acceptable fifth outcome.

A refusal is not sufficient merely because some unrelated outer
wrapper blocks a request in a test. For the claimed enforcement
boundary, negative conformance must show the intended guard
rejecting the specific mismatched pairing *before* the protected
physical effect or disclosure, while a valid compatible pairing
succeeds at that same actual gateway. Unsupported work does not
become successful simply because the attempted transport returned
HTTP 200, a browser callback ran, or an SSE message was queued.

An existing request or stream remains tied to the originating
assembly and its admitted resource context during its declared
lifetime. A host switch does not authorize it to fetch an arbitrary
new executor, outcome mapper, provider, response guard or asset.
A checked transfer may deliberately rebind only the dependencies
its compatibility proof covers. Current principal, Membership,
model authorization, backend qualification and browser resource
ownership are not frozen by either the old assembly or a successful
release check. A revoked effect permission is enforced even for an
otherwise compatible old continuation.

A command submitted under A may have committed even when its
response is lost and B is activated. Failing the A-to-B *mutation
continuation* gate must not relabel =:commit-unknown= as
=:rejected= or authorize a new command ID. A qualified
read-only historical reconciliation path may remain usable after
the old mutation implementation is retired; its current principal,
original command binding, result decoding and disclosure checks
are independent of permission to retry. Section 11.10 owns the
retirement/intent recovery contract and preservation of HumanHelp's
explicit remote Refresh policy.

*** Make the overlap an actual release gate

The candidate and activation gates fix the declared reachable
pairings before traffic moves. Installation and runtime qualification
then establish the exact host bindings, routing exclusions, asset
references and compatible protocol implementations on which the
decision depends. A topology or artifact change invalidates the
affected direction even if the semantic continuation contract
is byte-for-byte unchanged. Unavailable or unsupported required
cross-generation checks block that requested overlap profile;
a separately approved narrower rollout may instead impose
independently enforced exclusions. The original requested
strict profile is not silently downgraded.

Rolling releases are not globally atomic merely because one host
uses a coherent compare-and-activate transition. Mixed-host operation
requires its own finite compatible window, exposure/failover
coverage and qualified retirement conditions. For a supported
direction, any claimed progress depends on stated fairness,
availability, retry and retention premises; safety cannot be
replaced by an assertion that a client will eventually reconnect.
When the promised overlap expires, the old execution rights are
retired by actual enforcement and explicitly recoverable intent
is reacquired under the current admitted semantics. Neither
elapsed wall time nor server request reference count by itself
establishes that all sleeping clients have been handled.

*** Positive and adversarial rolling-direction acceptance

| Positive case to establish | Invalid adjacent case that must not pass |
|----------------------------+------------------------------------------|
| A/A invocation stays within A's qualified lifetime | Old A host continues unsafe writes after its provider premise is revoked |
| A/B old-to-new Claim uses qualified decoder, command binding and effect gateway | B accepts old envelope by stripping unknown semantic metadata |
| B/A direction is separately shown compatible where permitted | Success of A/B is incorrectly taken to prove symmetry |
| B/A exclusion is enforced through real dispatch, including failover | Sticky session routes normally to B but error fallback reaches unguarded A |
| B/B current installation serves the exact checked runtime/decoder | Current B build receipt is used while host serves stale A assets |
| Operation-scoped migration allows compatible A-origin read | Safe historical lookup is taken as permission to execute A's old writer |
| Source-equivalent semantic plan changes physical adapter and is requalified | Same semantic fingerprint inherits obsolete provider/host conformance |
| Old A request completes with retained qualified context during B activation | Deferred A body resolves a newer mutable B provider and changes its result |
| Required current Membership is checked for a compatible old command | Stale A principal snapshot authorizes protected B effect or disclosure |
| New B client receives explicit typed retirement on unreachable A decoder | Incompatible B envelope is silently treated as an ordinary anonymous HTMX call |
| Blocked direction is rejected before real protected XTDB effect | Test-only wrapper rejects early while the production writer still accepts |
| Real eligible Claim succeeds beside the required negative skew control | Reject-everything installation passes because only negative checks run |
| C42 committed under A is reconciled under a qualified B read path | Lost response causes invented rejection and submission of new C43 |
| Browser resource is still current before an admitted cross-generation swap | Retired A callback installs into a replaced B DOM resource |
| Reconnect, host loss and sleeping clients satisfy the declared window | Only one happy-path HTTP request is treated as complete topology coverage |
| A third activation enforces A retirement and permitted recovery | Old A client is silently granted indefinite execution through version arithmetic |
| HumanHelp remote board remains advisory until user-authorized Refresh | Reconnect to B automatically adopts unrelated remote updates |
| Excluded or unsupported strict direction blocks the original release claim | Unsupported checker is reclassified after failure to keep green admission |

These are prospective conformance and physical observations, not
automatically satisfied release results. Section 11.07 owns the
coherent candidate/installation/activation transition. This section
owns the *directional reachable-pair decision and its enforcement*.
Section 11.09 owns normalized continuation and physical retention;
11.10 owns semantic retirement, unresolved command intent and
selective recovery. They all preserve the semantic ownership,
conditional proof and real physical-boundary requirements of
Parts IV, VI–VIII and X.
