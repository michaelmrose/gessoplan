* Part VI — Browser realization and recovery
:PROPERTIES:
:CUSTOM_ID: part-06-browser-realization-and-recovery
:PART_REVISION: 06-20261108
:END:

This part specifies how an admitted browser plan becomes physical requests,
DOM changes, subscriptions, timers, and recoverable user interaction. It connects
Part V's portable execution and presentation contracts to Part IV's authoritative
operations, scoped observations, and unresolved commands. Part VII assembles
these contracts before a managed affordance is served.

The browser is an execution environment with delays, duplicate callbacks,
reentrant event handlers, disappearing targets, lost connections, and suspended
pages. These conditions belong in the realization contract. A successful pure
transition, HTTP response, or swap callback does not by itself establish that
the intended application state has been adopted.

Examples use illustrative API names and inspection records. They specify the
intended architecture; they do not assert that a displayed function already
exists. Symbols such as =E42= and =observation-ref= denote values established by
the surrounding construction. Copying their fields does not create an admitted
observation, resource owner, installation permit, or server credential.

The full application language remains available under the
[[#req-full-language-construction][checked construction contract]]. Opaque
renderers, adapters, and other application functions have explicit input/output,
effect, and completion contracts. Unverified behavior remains an assertion or a
named environmental premise. It is not promoted to a theorem because the code
passes through a small runtime interface.

** Browser adapter refinement
:PROPERTIES:
:CUSTOM_ID: req-browser-adapter-refinement
:END:

*** One executable semantic core and a narrow physical shell

Browser coordination is defined by the permanent executable semantic core,
including the browser adapter's transition semantics. A separate proof kernel,
when used, checks evidence about that semantics. The proof kernel does not
become a second runtime interpretation of browser behavior.

The projected Choreo machine owns the role-local trajectory. The browser
adapter owns its admitted invocation, asynchronous admission, fragment
coordination, resource ownership and the conditions under which that machine
may advance. These are composed responsibilities within *one executable
semantic interpretation*, not competing copies of the machine. The browser
shell, HTMX integration, timer callbacks and view components do not keep
independent semantic answers to which execution is current, whether a
command committed, whether rollback is legal or whether a presentation
is authoritatively adopted.

For an admitted plan and normalized event, the adapter computes a next semantic
state, a selected transition identity, and abstract effect descriptions:

#+begin_src clojure
(adapter/step admitted-plan adapter-state normalized-event)
;; => {:state next-state
;;     :transition-ref selected-transition-ref
;;     :effects effect-descriptions
;;     :diagnostics diagnostic-values}
#+end_src

This is an *illustrative* inspection shape, not a required signature or claim
about the current adapter API. The exact return representation is an
implementation choice. A selected-transition reference, if supplied for
inspection or evidence, must be derived from the actual transition and its
admitted source, not from a parallel diagnostic simulation or an independently
chosen branch. Its absence from a runtime API does not excuse missing
transition/effect correspondence where the application claims that assurance.

The following boundaries are required:

- The transition does not perform HTTP requests, mutate DOM, register listeners,
  read wall-clock time, or invoke an uncontrolled effectful observer.
- Nondeterministic inputs enter as explicit normalized values with their required
  provenance. Reading a clock or generating an identity is an admitted boundary
  operation, not an invisible dependency of a supposedly pure step.
- Semantic state contains portable identities, ownership, knowledge, obligations,
  and effect lifecycle records. DOM nodes, XHR objects, functions with mutable
  closures, and physical cancellation handles remain in the shell.
- The shell interprets abstract effects and supplies their actual completion or
  failure events. It cannot silently decide a different semantic successor.
- Opaque local computations use the declared execution boundary from Part V.
  Their inputs, results, failure behavior, and premises remain inspectable even
  where the computation itself has not been proved.

The normalized event contract distinguishes the event's *reported fields* from
its *admitted origin*. Correlation is attached when an admitted physical
resource is created or registered, and carried through its lifecycle. Merely
parsing an execution ID, source identifier, command ID or apparent basis from
client bytes cannot authenticate the event, bind a current owner, establish
a trusted authoritative observation or authorize a server mutation. The
supported browser realization identifies the source, schema, owner, resource
instance and generation admitted for each event class. Execution-private
callbacks and shared fragment invalidations use different admission contracts:
a shared invalidation is not rejected merely because it did not originate
from the currently selected local command.

One logical dispatcher owns semantic state for a runtime instance. Applications
may have several isolated runtime instances, but two mutable copies must not
both claim to own the same execution, coordinator, or resource instance. Shared
resources have an explicit shared owner and protocol. A later event observes
one committed predecessor transition, not an arbitrary interleaving of two
partially updated copies. Each accepted event has a linearized semantic
disposition; physical effects and their callbacks occur after that state
transition is committed. If a physical effect synchronously calls back into
the dispatcher, the callback must see the newly committed semantic owner,
generation and obligations. The interpreter cannot apply an obsolete pending
effect from the prior transition to a newly owned resource merely because the
effect was already emitted. Where multiple host tasks can dispatch concurrently,
the implementation needs an admitted serialization/ordering mechanism; an
unprotected read/modify/write cycle is not sufficient.

The required relationship is:

#+begin_example
registered physical source
  -> normalize and admit source/identity/event
  -> compute semantic transition and abstract effects
  -> commit next semantic state / retire obsolete rights
  -> interpret admitted physical effects through narrow shell or HTMX gate
  -> report actual completion/failure as a new normalized event
#+end_example

HTMX remains responsible for ordinary declared requests, parsing, supported
swaps, OOB handling and settlement. Gesso may gate a lifecycle action *before*
a protected physical mutation when its invariant requires intervention; it
must not perform a forbidden mutation first and ask the adapter afterward.
The exact supported HTMX lifecycle contract, including other physical
mutation paths, is specified in the following sections, not presumed from
the mere existence of a =beforeSwap= callback. The shell likewise must not
reimplement HTMX's native request/swap machinery to create a second,
unexamined execution path.

An effect request is not evidence of effect completion. Emitting
=:htmx/allow-swap= does not certify that a target was installed; a successful
request does not establish a committed Claim; and recording a tentative
presentation does not establish current RequestAssignment state. The
appropriate owner must admit actual, correctly scoped physical completion
before advancing adopted presentation knowledge. Timer cancellation, aborted
requests and listener cleanup may fail or race. Semantic retirement first
revokes stale callback rights, while physical cleanup remains a separate,
possibly incomplete obligation.

Optional diagnostics observe actual selected transitions without choosing
different outcomes or supplying missing permission. Their resource and
failure isolation must be established under declared bounds; a throwing or
unbounded same-process observer is not magically harmless merely because
its return value is ignored. Mandatory semantic checks and application
admission are not optional sidecar observers.

The event/physical boundary also has a trust asymmetry. A hostile browser
can skip the adapter, alter attributes and submit requests directly. Current
principal, Organization/Membership and RequestAssignment eligibility, as well
as the actual transaction and disclosure rules, remain with trusted server
and model authorities. Browser admission protects browser-coordination
guarantees, not server authorization.

physical behavior is claimed, instrumented host effects. An inspection
map with the expected keys is not a substitute for the relevant event source.

*** Distinct identities serve distinct purposes

The browser preserves identity through every boundary at which a callback,
effect, recovery attempt or physical mutation might otherwise be attributed to
the wrong work. Identity has a declared allocation authority, namespace,
incarnation or generation, comparison relation, lifetime, and permissible
transfer. An equal-looking string, a reusable DOM selector or a compatible
plan version is not by itself evidence of the same current owner.

| Identity | Meaning and lifetime |
|----------+----------------------|
| =:runtime-instance/id= | One admitted browser runtime lifetime in a page or worker context; a replaced, resumed or concurrently loaded runtime does not inherit physical rights merely because it carries the same logical application ID. |
| =:authority-context/ref= | Reference to the admitted principal, tenant/Organization and relevant policy context at the specified trust boundary; never a browser-issued credential or permission to reuse stale authorization. |
| =:execution/id= | One local execution of an admitted role-projected plan; an execution has its own generation and may retire while command reconciliation survives. |
| =:gesso/command-id= | One semantic command under Part IV's immutable intent, actor/authority, operation, arguments and compatible replay contract; distinct from delivery and local presentation. |
| =:resource-instance/id= | The concrete incarnation of a timer, listener, subscription, continuity capture, transport handle or managed physical owner, under a declared parent. |
| =:effect-instance/id= | One issued effect and its completion, cancellation, failure or uncertainty protocol; issuance does not mean the physical result has occurred. |
| =:transport-request-id= | One attempted HTTP or other transport exchange; a retry of C42 may receive a new attempt identity while retaining the command identity. |
| =:target-instance/id= | One physical DOM target incarnation and ownership generation, distinct from a reusable selector, logical view slot or domain entity ID. |
| =:coordinator/id= | One scoped Live acquisition coordinator and its ownership lifetime; its in-flight requests have their own attempt/generation identities. |
| =:assembly-deployment/id= | The pertinent installed application or deployment incarnation for artifact and continuation admission, not a self-authenticating source stamp. |
| =:executable-identity= | The exact projected executable identity from Part V, distinct from a semantic-compatibility judgment or a proof certificate. |

This vocabulary does not require every host API to use these exact keys,
allocate a separate UUID for each row, or expose implementation-only handles
to applications. Where two identities share an underlying value, the admitted
contract must establish that they identify the *same physical instance* for
all operations relying on that alias; equality of their representation alone
does not establish the claim. Generations belong to a named allocator and
owner. Counters can be reused only when their full identity also prevents
an old callback being confused with a new incarnation. A local generation
never orders different actors' commands, deployments, or opaque XTDB bases.

A HumanHelp domain Request =R= remains a model-owned subject, such as
={:arguments {:request-id R}}=. It is not an HTTP request ID. The
authoritative actor/Organization/Membership and current
=RequestAssignment= eligibility are established by trusted server/model
enforcement, not by a copied =:authority-context/ref=, plan digest or
=:gesso/command-id= on a browser element. Browser-side admission may
bind the same semantic intent C42 across H1 and H2, but it does not thereby
prove either attempt incorporated, that E42 is still current, or that an
observed card is physically installed.

*** Identity allocation, currentness and retirement

An admitted resource or effect record binds its issuer, semantic owner,
runtime/plan context, generation, expected source and completion contract
*before* physical issuance. The shell carries the resulting correlation
through the physical handle or a registered mapping; later callbacks
cannot reconstruct authority from today's DOM ancestry, URL, selector or
"active execution" variable. The runtime checks both the reported identity
and the admitted origin and still-current record when the event arrives.

Distinct lifecycle subjects retain distinct end conditions:

- C42's command history and unresolved incorporation/attribution survive
  transport timeout or E42 retirement until Part IV's qualified resolver,
  retention and terminal-exclusion rules dispose of that obligation.
- E42's execution and its private timer, transport, rollback and target
  rights end or transfer through explicit semantic retirement; a new E43
  does not receive E42's callback rights merely by continuing C42.
- H1 and H2 are different physical attempts. H1's completion cannot
  settle H2's pending transport effect, even if both refer to C42.
  Compatible command replay is determined by the authoritative boundary,
  not by the browser picking the response it prefers.
- A logical target may remain =:request-card R= while the actual DOM
  instance changes from B1 to B2. The old element's listeners, continuity
  snapshots and deferred mutations cannot act on B2 without newly admitted
  rights, even if both elements have the same =id= attribute.
- Shared Live invalidations follow their declared fragment/coordinator
  ownership rather than an unrelated execution-private identity.
  Revoking E42 must not accidentally erase a separately retained,
  legitimately scoped Refresh requirement or subscription obligation.
- A suspended tab or newly served deployment re-enters compatibility and
  source-admission checks before resuming old work. Semantic command
  recovery may be possible while old physical continuations remain
  irrevocably retired. Sections 06.08–06.09 own the detailed protocol.

Currentness is not solely a structural test on a copied map. A transition
must establish *who issued* the resource, which runtime and generation
presently own it, which host source actually emitted the callback, and what
semantic event is permitted in the current machine state. Invalid or missing
correlation fails closed for protected actions; an already late, otherwise
well-formed callback is classified stale/duplicate where the admitted event
vocabulary allows it. A malformed event, a stale event, an unsupported host
profile and an unknown authoritative command outcome are not interchangeable
diagnoses.

*** Commit semantic state before issuing physical work

The shell validates and commits the selected next state before interpreting
effects. This includes the effect issuance records and retirement of any
superseded local rights. An immediate completion callback must observe
the effect's current issuance and owner rather than a physically existing
resource absent from semantic state.

Committing first does not settle reentrancy. A handler can synchronously
submit another event, retire E42, replace B1, or begin a newer effect before
the outer transition's remaining effects run. The interpreter therefore
checks each protected effect's *current* issuance, owner, generation,
target and permitted mutation footprint immediately before the last
controllable physical act. A previously emitted batch is not an
irrevocable blanket permit. No delayed physical mutation may rely on
a permit that has ceased to be applicable, even if its later completion
would be correctly rejected as stale.

The check must distinguish effect kinds. A retired execution may still
require best-effort cancellation of its own old physical handle, a
non-mutating diagnostic, or transfer of durable recovery debt. Such
cleanup is not permission to restore old presentation or cancel a
successor's identically named resource. When a physical action has
already partly occurred, the system records actual completed, failed
and indeterminate outcomes and follows its declared compensation
contract instead of pretending a pre-action check made it atomic.

A conforming dispatch sequence is:

1. normalize the raw event and admit its actual source, owner and legal state;
2. compute and validate the next transition without physical side effects;
3. commit the next state, issuance records, retirement and transfer obligations;
4. offer an immutable record of the *selected* transition to bounded diagnostics;
5. interpret each effect subject to its current actuation gate, with no
   unadmitted transport or DOM action between the check and controlled mutation;
6. admit actual host completion, partial failure or uncertainty as another event.

One logical dispatcher owns semantic state for an admitted runtime. Nested
dispatch must see the newly committed state; the outer frame cannot overwrite
changes made by the inner dispatch when it returns. A serialized event queue
may be used for events that do not need a synchronous host decision. If
multiple worker or host entrypoints can mutate one semantic state, their
admission/commit order requires a real linearization mechanism. A mere
read-then-write or matching timestamp does not supply it.

Diagnostic observation is not a second semantic dispatcher. Observer failure
may be isolated through bounded buffering or a suitable failure-isolation
mechanism, but recording the selected event cannot block a mandatory effect,
replace a transition, or leak protected observation data. Promises and
callbacks initiated by supposedly observational code must also obey the
declared noninterference contract. This does not assert zero diagnostic cost
or a sandbox for arbitrary same-process code.

*** Synchronous lifecycle decisions need a synchronous gate

Certain supported HTMX/browser hooks require an allow/veto decision before
returning to the host. The supported integration profile identifies the
*actual last cancellable boundary* for each protected physical request,
swap, secondary mutation and follow-on effect. A deferred Promise, event
queue, later observer or eventual rollback cannot retroactively veto a
request already sent or a DOM mutation already performed.

At such a gate the currently admitted semantic dispatcher computes a
synchronous decision from the available admitted state, including its
source/attempt/target generation and required prerequisites. If the source
is uncorrelated, the applicable permit has expired, required knowledge is
unavailable, the dispatcher cannot commit safely, or the handler fails,
the protected operation is prevented before that act or is rejected as an
unsupported realization. Fail closed is a *physical outcome*, not just
a logged =:rejected= status while HTMX proceeds. A host profile that cannot
actually suppress the protected action is not certified by calling
=preventDefault= at an ineffective point.

The gate may direct a separate, explicit reacquisition or retry flow.
That flow owns its own attempt identity, checks authority and required
progression again, and retains C42 only if it is a compatible retry of
the same still-admitted intent. An unknown result must not be silently
relabelled rejected or replaced by a fresh Claim intent. A prepared
=:needs-input= or deferred affordance is not evidence that a previously
unadmitted physical send was allowed.

Synchronous decision-making does not imply that a handler is free of
later physical consequences. Timers, Promises, custom-element reactions,
animation callbacks, extension activity and queued work require their
own correlation and last-actuation safety. Section 06.03 specifies the
HTMX response and mutation surface; 06.05 and 06.10–06.11 specify actual
installation, effects and async admission.

*** Paired identity and lifecycle histories

These cases require independently sourced identity/host evidence, not an
inspection map fabricated to match the expected fields.

| Eligible history | Adverse history | Required classification or result |
|------------------+-----------------+----------------------------------|
| C42 remains one admitted Claim while H1 times out and a permitted H2 retries under the same immutable command binding. | H1's late response is interpreted as H2's transport completion, or timeout is treated as proof C42 was rejected. | Preserve separate H1/H2 effect ownership and command-specific uncertainty; resolve actual incorporation only from qualified Part IV evidence. |
| E42 issues effect F1 to B1; the shell commits issuance before a synchronous callback re-enters dispatch. | A callback reads pre-commit state, or the outer dispatch overwrites a newer nested state. | One linearized owner history; completion sees the committed predecessor and cannot regress later semantic state. |
| A newer E43 owns B2 at the same DOM selector after E42 retires; an old queued DOM effect checks current target and stops. | The old effect mutates B2 because its earlier allow decision or matching selector is reused, even though its later callback would be rejected. | Prevent the stale *act* at the last controllable boundary, not merely its completion; preserve any independent cleanup debt. |
| A supported HTMX before-request gate has an admitted current permit and allows the exact attempted send. | The source is uncorrelated or admission throws, but the handler merely reports a typed error and lets the actual request proceed. | The protected send is physically vetoed or the host profile rejected; report failure without manufacturing an authoritative command outcome. |
| A scoped Live invalidation arrives during E43 while a private E42 timer also fires late. | The runtime rejects the shared invalidation for not belonging to E43, or permits E42's timer to resume E43. | Admit legitimate shared coordinator work; classify the private stale timer without granting it new execution rights. |
| A sleeping page re-admits compatible current assets and recovers C42 through a qualified resolver. | It resumes an old effect/target handle solely because a stored plan digest or runtime ID matches. | Separate command recovery from suspended physical continuation; require deployment/source/owner compatibility and a new physical admission. |

The finished framework must support ordinary useful HTTP/HTMX and
Clojure application paths alongside these gates. Missing mandatory
correlation rejects the incomplete *managed* path, not all raw HTMX
or every unrelated ordinary handler. Browser event admission guards
local realization; trusted server/model policy still guards actual
RequestAssignment mutations and protected reads.
*** HTMX remains the declarative transport and swap owner

For a declared HTMX integration, HTMX owns its supported ordinary request,
response-processing, swap, out-of-band (OOB) and settle lifecycles. Gesso
binds protected actions to admitted semantic plans, applies narrow allow/veto
and correlation gates where necessary, and accounts for their actual effects.
It does not reimplement HTMX's ordinary transport and DOM behavior or secretly
issue a second physical request/swap while pretending the HTMX action was
the one controlled. Explicit unmanaged HTMX remains legitimate under its
own server-enforced policy; weaker transport behavior is never a silent
fallback from a failed managed operation.

The supported *browser integration profile* identifies an actual running
combination, not merely a dependency name. It includes:

- the installed HTMX and extension versions, configuration, response handling,
  custom swap strategies, history/navigation behavior and loaded application
  assets, with the applicable browser/host assumptions;
- the permitted request modes, form/submitter overrides, targets, swaps,
  response statuses, headers, OOB fragments, scripting and extension paths;
- documented lifecycle events and the *actual last controllable boundary*
  for each request send, response-driven action, target mutation and
  deferred effect, including which decisions are synchronous and cancellable;
- adapter-issued attempt, source, owner, request generation and physical
  target-incarnation correlation carried by supported host events;
- permitted action and target footprint, effect ordering/partial results,
  and the evidence required to establish real completion, failure,
  cancellation or an indeterminate physical result;
- positive and adverse conformance tests for that exact profile, with
  version-compatibility, escape and unsupported-mode dispositions.

A matching library version string does not prove an extension, alternate
startup path or runtime configuration obeys the same gates. A custom HTMX
extension is not required in principle. If a particular supported behavior
cannot be safely realized through the ordinary documented hooks, the
framework may provide a separately specified wrapper/extension/alternate
realization with its own host correspondence evidence, or reject that
combination. It may not claim protection from a hook that cannot veto the
relevant physical action. Changing an external HTMX event name should
not change Gesso's underlying Choreo/browser semantic requirements.

The integration must account for the request's effective method, URL,
form/submitter parameters, headers, target, swap and entry binding,
rather than trusting only a generated annotation or its initial DOM
shape. An application may render a valid managed affordance and later
replace it, inherit unexpected attributes or use an alternate submitter;
the *actual admitted physical request* must still correspond to the
protected operation and trusted route. Neither client-side checking
nor a copied execution/command ID supplies server authorization.

For every managed response or host action, the profile answers:

| Boundary | Required qualification |
|----------+------------------------|
| Before physical send | Which actual request, owner, correlation, binding and synchronous gate permit this irreversible attempt? |
| Before response-driven effects | Which result bytes and metadata are admissible, which secondary behaviors may run, and what happens if they cannot be contained? |
| Before each protected mutation | Which target incarnation, scope, permitted representation and still-current physical actuation right cover it, including deferred or reentrant work? |
| After the physical act | What actually completed, for which target/effect instance, and what remains failed, partial, indeterminate or unobserved? |
| Across replacement/recovery | How are old element owners, pending events, subscriptions, continuity and fragment coordinator obligations retired or reconstructed without silently losing debt? |

The request gate and mutation gates are not interchangeable. A successful
=:htmx/before-request= decision permits at most the corresponding attempt;
it cannot authorize arbitrary response headers or later targets. A
=:htmx/before-swap= decision is not evidence that every OOB, script, history
or extension effect has already been controlled. A callback named
=:htmx/after-swap= is an observation whose correlation and actual completed
scope must still be checked; it cannot establish a command's incorporation
or a whole-board adoption by its name alone.

For a supported cancellable lifecycle hook, a failing normalization,
missing source identity, expired permit or throwing semantic gate must
physically prevent the protected action. An asynchronous decision returned
after the request or mutation starts does not provide the required veto.
No application can claim a stronger browser safety invariant when an
unexamined response path can mutate that same protected state outside
its admitted footprint.

*** Response data, response effects, and content safety

A response may convey a command-specific historical result, an
authoritative observation, replacement HTML, response headers,
OOB fragments, browser events, navigation/history instructions or
active content. These are different *subjects of admission*.
Authorizing one does not authorize the others. A browser-visible
HTTP status or response body is neither a trusted business-rule
decision nor evidence that the user's display was installed.

For HTMX 2's ordinary =hx-swap="none"= behavior, suppressing the main
target insertion does *not* imply a response without browser effects:
OOB content and applicable response headers can still be processed.
A managed command-response endpoint using that mode must explicitly
admit, isolate or exclude such effects. For example, a response that
reports C42's result may still carry an OOB replacement of a Request
card or a response-triggered event; neither gets permission from the
mere fact that C42's command outcome was admitted. A registered
side effect must have its own owner, disclosure scope, target and
completion contract. A malformed or unauthorized additional effect
is rejected or quarantined *before* its protected mutation. A
typed error recorded after unintended DOM replacement is too late.

The profile inventories the applicable response and extension mechanisms,
not just the primary HTML swap. Depending on the qualified HTMX version
and configuration, these include OOB swaps, response-specified retargeting
and swap overrides, client-side events, redirects/location changes,
history updates, script processing, native form behavior, and
extension-defined mutations. Response-triggered events can themselves
cause further requests or application actions; a declared effect chain
must either be admitted through its own entry gate or excluded.
A configured =HX-Trigger= header cannot silently become an
unexamined mutation capability. Likewise a response carrying
=HX-Retarget= or =HX-Reswap= cannot enlarge a previously admitted
mutation footprint without a new effective check.

A protected main-target permit does not grant all OOB targets. Each
secondary target requires a valid current instance, authorized
content/disclosure scope and mutation permission. One multi-target
permit is possible if the complete footprint and intermediate
physical behavior are genuinely covered; otherwise individually
scoped permits and completion records are needed. Sequential
DOM writes are not automatically physically atomic. A later failed
target does not undo earlier physical changes, and observed partial
completion must retain the required repair/adoption debt. Section
06.05 owns the detailed scoped installation contract.

An application may safely choose a restricted response profile
(e.g., permitting only one known inert fragment and prohibiting
unexpected response effects), but restriction has to be enforced at
the *actual response-processing boundary*. Merely expecting the
server to return a harmless shape is insufficient if any other
reachable path, cache, extension or response override can produce
an unreviewed mutation.

Authoritative provenance and HTML/content safety are separate.
A qualified XTDB observation does not make arbitrary user-supplied
HTML, JavaScript, =hx-*= attributes or event handlers safe for
insertion. Rendering declares escaping, sanitization where
untrusted markup is intentionally supported, allowed active
content, script/CSP policy, HTMX attribute processing and
extension behavior. The trusted construction and serving path
must prevent client-supplied content from manufacturing managed
actions or protected subscription/command bindings. Rendering
into an inert container can be a useful preparation step, but
later activation and execution are separate physical effects.

The actual checked fragment must preserve the relationship
among its protected data, operation binding, target/coordinator
instance, authoritative observation and accepted protocol version.
Copying an old =:choreo/op= annotation onto a newly generated
button does not provide admission. Replacing a stable Live/HTMX
behavior-owning root without re-establishing its declared
connection, trigger, current-owner and continuity hooks can
silently end all subsequent refreshes. An admitted replaceable
inner fragment may change while its owner remains stable; if the
root itself is replaced, the new owner and subscription lifecycle
must be explicitly reconstructed and checked.

*** Transport and response conformance histories

Each positive case must exercise the real supported HTMX processing
path and the expected source/owner bindings; negative cases must
reach the relevant physical boundary rather than fail on an unrelated
malformed fixture. The table specifies finished-system tests, not
claims that Gesso v1622 already satisfies every row.

| Eligible positive path | Adverse or incomplete path | Required conclusion |
|------------------------+----------------------------+---------------------|
| An admitted managed Claim H1 receives a qualified C42 settlement through a command-response with =hx-swap="none"= and no unadmitted secondary effect. | The same-looking response contains an unauthorized OOB card replacement or a response event that submits a second operation. | Historical C42 disposition may be recorded independently; the extra mutation is blocked before actuation or the response/profile is rejected, without asserting that the card adopted. |
| A protected acquisition swaps the current target B2 under an admitted permit and reports actual completed installation. | An OOB replacement targets a different or retired B1, or a response retarget/override escapes the approved footprint. | Only the actually covered target may change and discharge its scoped adoption; the other target is denied or recorded as separate incomplete/repair work. |
| A supported cancellable pre-send hook binds actual form method, route, arguments and owner to the admitted operation. | A submitter override, inherited HTMX attribute, thrown gate or uncorrelated physical request changes that binding but the network send proceeds. | Fail physically closed at the effective pre-send boundary; do not silently downgrade to unmanaged HTMX or mark the command rejected from a failed attempt. |
| A permitted HTML fragment escapes untrusted Request text and preserves its validated data/operation bindings after replacement. | User content introduces executable =hx-*= attributes, handlers or scripts that initiate protected effects outside the admitted construction path. | Prevent unsafe activation/processing under the declared content profile; possessing an authoritative observation does not authorize injected code. |
| A complete authorized refresh replaces the inner fragment while stable root owners, Live subscriptions and continuity resources survive or are deliberately re-established. | A whole-root swap silently drops the SSE listener or attaches new events to the retired owner's target, while tests check only the first refresh. | Reject the incomplete managed realization or perform the admitted owner handoff; later refresh and owner-bound callback tests must remain positive. |
| A scoped installed result and a separate current command readback establish their own qualified propositions. | An HTTP 200, a generic =afterSwap= event, or the presence of a matching digest is reported as universal current RequestAssignment state and whole-board adoption. | Preserve command, read, installed target and board-cohort evidence separately; absent physical completion is unresolved, not success. |

Ordinary raw HTMX interactions continue to work on legitimate routes
under ordinary trusted server authorization. Managed stronger promises
apply only when the exact selected rendering, transport, response,
target and deployed integration paths have been admitted. Part VII
must verify the actual application closure for those paths; Part VIII
requires nonvacuous eligible HumanHelp Create/Claim/Reassign and
one-Refresh product behavior, not merely passing negative fixtures.

*** Worked example: Claim followed by protected acquisition

Alice sees HumanHelp Request R in a qualified, authorized observation of the
currently selected Organization/Location. The rendered Claim affordance binds
one public model-owned operation and typed arguments. It does not mint a trusted
principal, establish current Membership, or authorize the write merely because
the browser displays =Claim=. The observed pre-read may report an =:open=
Request with no active primary =RequestAssignment= under its stated coverage;
that is not an atomic, transaction-current eligibility decision.

The example uses these distinct subjects:

| Subject | Meaning |
|---------+---------|
| R | HumanHelp's model-owned Request identity; not an HTTP request. |
| C42 | Stable semantic Claim command intent and protected binding, allocated before the first possible submission. |
| E42 | One local browser Choreo/optimism execution with separately revocable physical rights. |
| H1, H2 | Distinct physical transport attempts that may carry a compatible retry of C42. |
| B1, B2 | Physical incarnations of the Request-card target, not merely the same DOM selector. |
| O1 | An admitted card observation, with its own source, covered scope and qualified progression. |
| P1 | A runtime-issued installation permit for an exact representation, target and effect instance. |

The values are illustrative. A later execution may continue permitted C42
reconciliation, but does not inherit E42's retired transport, timer, target
or actor-local branch knowledge. Two requests that reuse C42 are not
automatically interchangeable in their transport-result correlations.
The command's immutable semantic intent is bound to its operation,
arguments, actor/authority context and compatible replay contract under
Part IV. A copied ID in a request header is not that admission.

The following trajectory is a supported *design*, not a claim that
these names are already the public browser API:

| Stage | Required semantic/physical correspondence |
|-------+-------------------------------------------|
| Prepare | Admit the current view binding and relevant scoped observation. Establish a stable C42 intent and local E42/target owner before any possible send, preserving required actor, operation and argument bindings. |
| Provisional | Derive and install only the locally admitted provisional presentation; failed physical installation is reported as such and never fabricated into command rejection. |
| Request construction | Bind an exact H1 physical attempt, current execution/generation and effective HTMX method, route, inputs and send footprint. HTMX retains native transport ownership. |
| Send admission | At the supported synchronous hook, verify the projected send state, still-current attempt/target owner, complete physical request binding and source. No missing projector, correlation or plan silently downgrades to ordinary HTMX. |
| Trusted Claim | Authenticate the actual principal and guard current Request, Organization/Membership/actor and active primary RequestAssignment facts through the real model-owned transaction and backend contract. A browser pre-read or self-asserted plan cannot replace the transaction guard. |
| Outcome observation | Admit binding-scoped C42 command evidence from the qualified response or permitted readback. Distinguish incorporation, terminal rejection, compatible replay and unknown delivery; do not translate network failure or an HTTP status into a domain result. |
| Acquisition | Independently admit permission to read the current authorized card or board cohort, its required query/scope and progression. A historical C42 result alone does not yield a current O1 observation. |
| Installation | Derive a prepared representation from the admitted O1 observation and acquire a current P1 covering its actual target instance, physical action and allowed mutation footprint. Recheck P1 at the last controllable act, including delayed/reentrant work. |
| Completion/adoption | Admit actual completed physical effect/postcondition for the matching O1/P1/target. Discharge only its covered presentation/adoption obligations; do not call a whole board refreshed after installing one card. |

Part IV owns the *authoritative* Claim transaction and historical command
knowledge, Part V the local provisional derivation/settlement treatment,
and Part VI the browser's actual effect and installation boundary.
These are composed responsibilities, not competing interpreters.

A permitted =:committed= result, or a qualified
=:already-incorporated= result for C42, establishes the specified
historical incorporation, subject to the authoritative source and
binding contract. It may permit an =:accepted= presentation status;
it is not an assertion that today's primary helper is Alice, that a
particular HTML fragment installed, or that the board cohort changed.
A terminal =:rejected= command outcome requires its own qualified
exclusion evidence. =:commit-unknown= remains unresolved until an
admitted resolver establishes more. The browser's generic optimism
=:confirmed=, =:reconciled=, =:failed= and timeout dispositions are
not substitutes for the public model outcome vocabulary.

Two independent histories make this distinction unavoidable:

- H1 may have incorporated C42, then the network response was lost.
  The browser can retire H1/E42's physical resources, recover the
  current card through O1, and still lack C42-specific historical
  attribution. It must retain or transfer the command-resolution
  obligation rather than asserting that the new card proves H1
  succeeded or failed. Retrying C42, if permitted, must preserve
  immutable command binding without executing a second incorporation.
- C42 may have successfully installed Alice's primary assignment,
  followed by a manager's authorized Reassign to Bob. A historical
  C42 result and a newer qualified Request/RequestAssignment
  observation are simultaneously true. An old settlement callback
  cannot reinstall Alice over Bob; a current Bob card does not turn
  C42's earlier success into rejection.

Claim's response and card acquisition may use separate physical HTMX
requests, which is a particularly clear realization. A combined result
and observation is also possible, but each proposition must pass
its own source, disclosure, scope, and completion gates. An
=hx-swap="none"= command response must still satisfy section 06.03's
OOB/header/secondary-effect contract. Its success cannot be counted
as a card swap. A raw =afterSwap= callback is not automatically
physical proof of installation in an unrelated or retired target.

When provisional derivation requires asynchronous computation but the
chosen HTMX gate requires a synchronous allow/veto, that derivation must
complete *before* entering the gate or be deferred to an admitted
re-entry/reacquisition path with a new physical attempt. The gate
cannot allow the send on hope of eventual projection. Failed,
missing or incompatible managed realization remains an explicit
typed failure; authored raw or non-optimistic alternatives keep
their independently complete authorization and recovery contracts.

HumanHelp's board has an additional adoption distinction. Alice's
correlated local Claim may update her own card promptly after the
relevant qualified outcome/observation and actual installation.
Other actors may receive only a scoped Live advisory until their
explicit Refresh grant. Local text search, sorting, selected card,
open details and scroll state remain continuity of an already adopted
authorized cohort, not proof of a new server query. A creator-local
newer S must not be overwritten by an older whole-board R snapshot;
one explicitly granted remote Refresh must satisfy its stated
scope without silently acquiring an extra cohort. The detail of
these policies belongs to Parts IV–V and 06.05–06.07, not to
an ad hoc Claim listener.

*** Browser FFI contracts are small but substantive

The browser FFI is the physical interpreter of *adapter-issued*
effects, not another source of command meaning, business rules
or Choreo branch selection. HTMX owns its native request/response
and supported swap behavior; a Gesso-owned effect handler may
intervene at admitted HTMX gates or perform distinct Gesso-owned
timer, provisional DOM, continuity, subscription and cleanup work.
It may not quietly duplicate an HTMX request or swap.

Every supported physical effect handler has a registered contract:

- **Input and binding:** typed effect kind, implementation and
  protocol/asset identity, closed required inputs and admitted
  normalized source; unsupported inputs fail explicitly.
- **Ownership:** exact runtime, semantic effect instance, resource
  incarnation, current owner/generation, target incarnation,
  representation and allowed physical footprint.
- **Actuation:** synchronous/async classification, actual
  last-controllable permit check, required serialization with
  protected mutation, and any possible host reentrancy.
- **Outcomes:** actual completion postcondition, correlated effect
  and target, failure, cancellation, partial/indeterminate
  mutation, duplicate delivery, and unknown physical result.
- **Cleanup/recovery:** registration before issue, handling of
  immediate callbacks and handles returned after retirement,
  exact-resource release, stale callback no-op, observable
  residual debt and any necessary compensating/reacquisition path.
- **Premises/evidence:** supported host/HTMX version, external
  behavior relied on, test/proof scope, and unproved opaque or
  third-party effect assumptions.

A handler returning a syntactically successful envelope does not
establish a physical action. The completion contract must identify
what the host actually accomplished, or classify its result as
unknown/partial. An absent, throwing or misbound mandatory handler
must not silently satisfy the projected semantic obligation.
A sidecar or observer callback cannot supply the missing effect.

The shell's physical registry maps adapter-issued references to
actual opaque host objects. Correlation is established at issue or
registration and carried through callbacks, not rediscovered by
whatever element currently matches a selector. A timer cancellation
cannot remove the successor owner's identically named timer.
A delayed DOM write cannot act on B2 using a revoked B1 permit
merely because the eventual callback would be rejected. If the
host supports a guarded last-actuation section, its check and
mutation must preserve current ownership under the declared
serialization/reentrancy contract. If it does not, the selected
physical realization is unsupported for that strong guarantee.

The current semantic transition is installed before issued effects
are interpreted. Immediate physical callbacks must therefore see
committed ownership and effect state. A nested callback may retire
the outer owner before its remaining effects run; every remaining
protected effect must recheck current permission. Concurrent
dispatchers need a genuine serialization mechanism rather than
two mutable competing copies of the same semantic state.
The FFI may retain physical handles, but cannot choose a semantic
successor or transfer authority as a shortcut around that protocol.

Ordinary application code and third-party browser libraries can
mutate the same DOM and trigger network work. For a protected
footprint, those actions must participate in the admitted host
profile, be prevented from interfering, or remain an explicit
noninterference/trust premise with corresponding limits on the
claim. Full-language Clojure application development does not
eliminate physical or opaque effect obligations.

*** Scoped authoritative installation
:PROPERTIES:
:CUSTOM_ID: req-runtime-scoped-authoritative-installation
:END:

Part IV distinguishes an authorized observation from the act of acquiring
it and from a participant's subsequent adoption. Part V distinguishes
authoritative presentation from provisional overlays, continuity, and
historical command outcomes. The browser must preserve those separations
across the *actual physical effects* of HTMX and the Gesso-owned shell.
A result about one card, field, or complete query cohort cannot be
promoted to a claim about every other visible or required scope.

| Stage | What is actually established | What remains unestablished |
|-------+------------------------------+-----------------------------|
| Acquisition permitted or requested | The current owner may start, or has started, a specified read within a declared grant. | No response, qualified observation, installation, or adoption is implied. |
| Observation acquired | An admitted source establishes particular data, coverage, authority context and qualified progression. | The represented view has not necessarily been changed. |
| Installation prepared | A proposed representation and target/mutation footprint have been derived from that observation. | The proposal may still fail validation, owner checks, or actual DOM mutation. |
| Installation permitted | The semantic runtime has issued a currently valid, precisely scoped right to attempt that physical act. | The act has not necessarily begun or succeeded. |
| Installation reserved or in progress | The host has entered the specified guarded actuation protocol. | Partial or interrupted physical effects and reentrancy remain possible. |
| Installation completed | A correlated physical postcondition is established for each covered target/effect instance under the supported host profile. | Uncovered targets, other projections and unrelated command attribution remain open. |
| Observation adopted | The participant's semantic state records qualified completed installation for the precise covered scopes. | Neither all advisory debt nor a whole aggregate query is discharged without its separate requirements being satisfied. |

These are semantic distinctions, not a requirement for seven different
public callbacks or an extra persisted record per DOM node. An
implementation may combine stages whose premises are established
together. It may not erase the stage or invent its evidence. An
HTTP 200, response parsing, =htmx:beforeSwap=, permitted swap,
generic =htmx:afterSwap= callback, or matching plan digest is not
by itself a whole-application or whole-board adoption witness.
The selected supported host profile must explain what each callback
actually establishes, including its limitations for OOB, nested,
deferred, missing-target and extension effects.

For example, a complete authorized Request-board observation with
membership scope Q may establish information about the board cohort
while a correlated newer Request-card observation establishes the
current presentation of S independently. Conversely an acquired
card alone does not establish the absence of R from an open-request
collection, or that every card in Q came from one snapshot. The
browser must represent both qualified facts and the obligations
each one has or has not satisfied. Neither the identity of a
database basis token nor the act of swapping a DOM subtree alone
settles the comparison.

**** Installation permits bind the intended physical act

An installation permit is a *runtime-issued semantic right for a
physical operation*, never a credential for a server-side domain
write. It must bind the decision to exactly the realization it
permits, including:

- the admitted runtime/assembly and relevant authority-context
  references, with their freshness and disclosure premises;
- the current execution, coordinator or declared shared owner,
  its generation and the actual effect instance;
- the observed data's source, semantic scope, query/cohort and
  qualified progression or coverage references;
- the prepared representation's content-sensitive identity,
  render/binding contract, version and supported host profile;
- the actual target incarnation(s), intended actions and complete
  mutation footprint, including secondary/OOB effects if admitted;
- the physical actuation/serialization and completion postconditions,
  partial-failure disposition, cleanup and recovery obligations.

One illustrative inspection shape is:

#+begin_src clojure
{:permit/ref installation-permit-ref
 :runtime-instance/id runtime-id
 :assembly-deployment/id installed-assembly-ref
 :authority-context/ref context-ref
 :owner/ref board-coordinator-ref
 :effect-instance/id installation-effect-id
 :observation/ref qualified-observation-ref
 :scope/ref covered-query-and-projection-ref
 :representation/ref prepared-content-ref
 :targets [current-board-target-instance]
 :action :dom/replace-children
 :host-profile/ref qualified-htmx-profile-ref
 :completion-contract/ref checked-postcondition-ref}
#+end_src

The record illustrates a permit *already selected and registered by
the semantic runtime*. A matching client map, repeated digest,
copied DOM attribute or proof sidecar does not mint one. Neither
a browser permit nor a completed DOM effect grants authority to
call a protected server model operation.

Permits have explicit issuance, reservation/physical commitment,
completion, failure, revocation and retirement semantics. An
issued but unconsumed permit can be revoked. A physical act that
has crossed its defined commitment point cannot be treated as
unexecuted merely because semantic ownership subsequently changes.
A duplicate completion cannot replay the physical act, adopt the
same evidence twice or consume a successor's permission. A
successor target at the same CSS selector or HTML =id= is not
the same physical incarnation.

**** Final admission covers delayed, reentrant and secondary effects

Expensive or arbitrary application rendering occurs under its
declared full-language/effect contract before the last protected
actuation where possible. The runtime verifies that its result
still matches the observation, permitted representation and
current target. It must not install a once-authorized stale
render merely because rendering completed successfully.

Immediately before every protected physical mutation, the shell
or admitted HTMX integration verifies the still-current permit,
owner, effect instance, target incarnation, representation and
scope. Checking a captured =allowed?= bit at request time and
then rejecting only the *late callback* does not protect a
later DOM act. The final check and the physical commitment
point require a stated serialization protocol; if user code,
custom elements or the host can reenter during mutation, the
protocol must identify reservation, suspended conflicting
transitions, partial effects and exact failure recovery.
One JavaScript event loop does not make a multi-target swap
an atomic semantic transaction.

An old E42 effect may have been admitted for B1 and scheduled
for later execution. In the meantime, another authorized
installation replaces B1 with B2 and revokes E42's permit.
The queued effect must not mutate B2 even though B2 has the
same selector and Request R. Its late physical completion or
failure may be observed for cleanup, but cannot restore B1's
obsolete representation. A recognized stale permit is
suppressed at actuation, not mislabeled as successful install.

For HTMX-owned effects, section 06.03's version/configuration
profile must supply an actually effective pre-mutation gate
for the entire protected footprint. A main-target
=:htmx/allow-swap= does not license an unexamined OOB target,
response header, extension mutation or reentrant follow-on
request. If a supported host profile cannot control the
protected act at the required boundary, it must use a
separately qualified realization or fail admission before
the unsafe effect, not declare success from a later callback.

**** Actual completion determines adoption

The completion evidence identifies the issued permit and
effect, actual resource/target instances, admitted source,
realized representation and physical postcondition. The
host profile may accept a sufficiently correlated lifecycle
event, a checked DOM predicate, or a stronger instrumented
mechanism, but must say which concrete mutation paths it
covers. A generic event with the right name is not proof
that an unrelated target's contents, owner or required
accessibility/interaction bindings were installed.

Admission of a completion event checks its current semantic
owner, target incarnation and source as well as any
intervening installations and observed physical effects.
A physically completed *older* act may remain historical
diagnostic evidence without advancing today's adopted
frontier. If completion reporting is lost or ambiguous,
the browser cannot manufacture adoption from matching
text in the DOM. It retains an explicit reconciliation
obligation: inspect under a qualified physical predicate,
reacquire/reinstall an allowed scope, or use another
declared compensation or recovery mechanism.

An installation can succeed in one target and fail in
another. The runtime records completed, failed, pending
and indeterminate per-target outcomes with their respective
observation, effect and owner bindings. A completed card
does not justify marking the board's membership cohort
fully adopted; a completed board shell does not establish
all internal card/action bindings merely because the
outer element exists. If the product requires all-or-nothing
presentation, the physical mechanism must actually provide
that atomicity or the declared compensation protocol must
specify its observable intermediate states. Ordinary
sequential DOM mutations do not satisfy that promise.

A partial or inconsistent realization must not expose
enabled semantic affordances whose guarded bindings no
longer correspond to their visible content. The runtime
may quarantine the affected target, preserve valid
independent scopes, or perform declared reconstruction.
It cannot quietly downgrade a managed action into
unprotected HTMX or use an old provisional snapshot as
a universal "undo". Actual model incorporation is not
reversed by a local DOM failure.

Optional focus, scroll or disclosure restoration is a
separate local continuity operation. Failure to restore
such optional state after a successfully admitted
authoritative install does not annul the command or
that installation. If a mandatory user-draft barrier
was declared before replacement, its own preparation
contract determines whether replacement was authorized;
it cannot retroactively veto an already completed
authoritative operation. Physical resource cleanup
remains owner- and instance-relative even when an old
owner and its successor set the *same* CSS property value.

**** Progression, coverage and selective supersession

An installation can supersede provisional presentation or an
older authoritative projection only where its scope and
qualified progression/provider judgment authorize that
replacement. Opaque XTDB bases do not acquire a total
order through numeric-looking labels. The browser must
preserve actor/authority context, projection, selected
query, collection membership, fields, temporal
interpretation, target ownership and observation source.

The satisfaction relation is obligation-specific.
An acquired entity card may satisfy an entity-information
requirement but not a complete filtered board query.
An observed collection absence requires the proper
authorized cohort coverage; it is not proved by a missing
node or a locally hidden item. Advisory obligations whose
required discharge stage is *adoption* persist after
fetching the response until the corresponding physical
scope actually installs. Obligations that arrive while a
read is in flight remain if that read does not cover them.

A whole-board R response can overlap a separately newer,
correlated creator-local S card. The correct result may
adopt the board membership from R while preserving S's
more advanced Request-card representation. That requires
a *qualified scope-aware merge* or other admitted policy,
not a fabricated claim that the mixed view is one XTDB
snapshot. If a safe merge cannot be justified, the runtime
rejects/reacquires the conflicting scope, retains
independently valid presentation and its unsatisfied
obligations, or follows an explicit recovery strategy.
It must not erase S merely because the whole-board
response was initiated later.

Likewise a remote actor's advisory may establish new
Refresh debt without granting a new read. One explicitly
granted Refresh binds the applicable query/context and
read budget, and may discharge only the obligations
satisfied by its one qualified acquisition and actual
installation. An implementation may offer a different
declared automatic-drain policy, but one granted read
cannot silently become unlimited successor acquisition.
Sections 06.06–06.07 own that coordinator protocol.

Each positive history needs an eligible authorized
source, actual host execution and a checked target-specific
postcondition. Each nearby negative case must reach the

an unrelated malformed fixture.

*** Fragment coordination
:PROPERTIES:
:CUSTOM_ID: req-fragment-coordinator
:END:

A fragment coordinator is the single semantic owner of acquisition,
installation, advisory debt and relevant scheduling decisions for one
*admitted logical scope during one owner-instance lifetime*. That
scope binds the authoritative applied query, tenant/Organization and
actor disclosure context, projection/cohort contract, required
progression and relevant deployment/target ownership. It is not a
global mutex for every view of the same domain Request; nor may two
coordinators independently claim the same current physical target
or acquired/adopted obligation without an explicit sharing protocol.

An invalidation is information that a relevant authoritative change
*may require* acquisition or adoption. It is not itself a database
observation, a trusted command outcome, permission to read protected
data, or proof that another participant has adopted that change.
Advisory delivery and user-visible Refresh availability can coexist
with independently newer local authoritative presentation. The
coordinator, not an arbitrary SSE callback, decides how each
requirement enters its scoped obligation state.

The coordinator distinguishes these independently owned subjects:

1. **Obligations:** source-qualified advisory or gap requirements,
   their scope, origin, coverage relation, and required discharge
   stage (acquisition, actual installation/adoption, or recovery).
2. **Policy permission:** whether, by whom, for what query and how
   many times an acquisition or installation may be initiated;
   it is distinct from trusted server read authorization.
3. **Active cycle:** one admitted logical acquisition/installation
   lifetime, with its captured requirements, current request
   generation, physical attempts, target/permit identities and
   qualified completion or repair state.
4. **Successor scheduling:** at most one coalesced scheduling slot
   under the default policy, containing a *possible next cycle*,
   not an unconstrained right to submit more requests.
5. **Evidence:** independently qualified acquired observations,
   actual installed/adopted scopes, progression judgments and
   unresolved comparison/repair obligations.
6. **Recovery/resources:** failed or indeterminate effects,
   subscription continuity, retained debt, semantic retirement,
   pending physical cancellation and bounded cleanup policy.

The default coordinator promises at most one active *logical*
acquisition/installation cycle and one coalesced successor slot
for its admitted owner and scope. A cycle ordinarily lasts through
physical installation completion or a terminal cycle disposition,
not merely until the HTTP response arrives. If a realization
separates the network-read slot from installation, it must
state and check separate bounds on outstanding prepared and
physical installations. Bounding in-flight network requests
alone does not establish one coherent current DOM mutation.

#+begin_example
active logical cycles for one admitted coordinator <= 1
successor scheduling slots for that coordinator <= 1
#+end_example

This is a *logical scheduling bound*, not a claim that an aborted
request ceases to exist physically, that all callbacks have
returned, or that retained debt uses constant memory. Physical
remnants from earlier generations can coexist with the active
request. They have no installation authority and must have
their own release, instrumentation, backpressure and boundedness
contract. A single successor slot may represent arbitrarily
many incomparable requirements unless the supported requirement
domain supplies a sound finite abstraction or an explicit
overflow/recovery policy.

**** Advisory debt is not permission to acquire

A new invalidation first passes source, subscription/interest,
current owner and scope admission. It then adds an obligation
or produces a *justified* combination with existing obligations.
An advisory that says "newer information may exist" but gives
no authoritative minimum-read token still represents debt when
the product's contract requires future reconciliation. Absence
of a token is not permission to discard it. Conversely a
duplicate of an *exact already-covered* requirement need not
create new work if a qualified coverage judgment establishes
that the active read or adopted result already satisfies it.

The obligation-to-observation satisfaction relation comes from
Part IV's declared progression/coverage provider. The
coordinator does not infer ordering of opaque XTDB tokens,
timestamps, SSE sequence labels or request-generation integers.
Combining distinct requirements by keeping only the numerically
largest-looking basis is not an admitted implementation of
that relation. Where requirements are incomparable, each
independent condition must survive or be summarized by an
explicitly sound provider-supplied representation.

A product may select one of several *declared* policies:

- **Explicit user Refresh:** remote advisories update debt and
  presentation (for example a Refresh glow) but do not initiate
  acquisition. A qualified user action grants an exact read and
  adoption policy for the applied query and captured obligations.
- **Bounded automatic refresh:** a particular declared scope
  permits one acquisition on an admitted invalidation, possibly
  with bounded coalesced successors and explicit backpressure.
- **Deferred or gated refresh:** work waits for edit completion,
  reauthorization, connection recovery, foreground activity,
  or another declared prerequisite, without erasing the debt.

The product must not silently switch among these policies because
an HTMX trigger happened, a queue slot became free, or a callback
saw a nonempty obligation set. A managed automatic-fetch policy
can be useful, but it is not the universal semantics of Live.
A disabled or pending managed affordance remains honest about
its retained obligation; an ordinary raw HTMX path may have
a different, explicitly admitted contract.

An explicit one-Refresh grant binds its current owner, principal/
authority context, applied query and authorized cohort, captured
requirement snapshot, allowed physical acquisition count,
installation/adoption policy, validity interval and expiry or
handoff conditions. For example:

#+begin_src clojure
{:grant/ref refresh-grant-ref
 :owner/ref board-coordinator-ref
 :authority-context/ref context-ref
 :query/ref applied-query-ref
 :requirement-snapshot/ref captured-debt-ref
 :reads {:initial 1 :successors 0}
 :observation-policy :current-complete-query
 :adoption-policy :install-if-current
 :expiry-policy/ref current-expiry-ref}
#+end_src

This record illustrates an already admitted grant; a fabricated
map from client code cannot create an authorization. A permit
to *schedule* a read is not the server's permission to disclose
Request or RequestAssignment data. Each actual request still
passes trusted principal, tenant and current read policy.

The read budget is consumed on the defined admission of the
*actual physical acquisition*, not by setting a boolean in a
completed handler. An unstarted queued successor cannot spend
an expired grant later. Whether a failed attempt consumes the
read budget, and whether a permitted retry is the same attempt
or an additional read, are explicit grant-policy questions;
they are not silently decided by HTTP error timing.
A scheduled successor with no remaining permission is blocked,
not dispatched; its requirements remain. The provider may
return a qualified observation stronger than the captured
minimum, satisfying additional debt without consuming
another read. Satisfaction does not retroactively authorize
a second acquisition.

Grant expiration and page suspension are interpreted under
a declared clock and lifecycle source. Delayed timers do not
extend permission. A resumed page must revalidate current
authority, applied query, deployment and owner as required;
holding the old grant reference is insufficient.

**** Coordinator state and transition obligations

The following is an *inspection model*, not another mutable
store that application authors maintain next to Gesso's
semantic adapter:

#+begin_src clojure
{:coordinator/id board-coordinator-id
 :owner-instance/ref board-owner-ref
 :scope/ref applied-authoritative-query-ref
 :authority-context/ref context-ref
 :obligations outstanding-scoped-debt
 :permission current-grant-or-none
 :active-cycle active-cycle-or-none
 :successor-slot successor-intent-or-none
 :acquired-evidence acquired-scoped-evidence
 :adopted-evidence adopted-scoped-evidence
 :continuity subscription-and-gap-state
 :physical-remnants bounded-cleanup-records}
#+end_src

Each obligation identifies what was learned, by which admitted
source/interest or continuity recovery event, for which
authority/query/projection, and what stage qualifies as discharge.
Coalescing is permitted only if the replacement representation
preserves all required facts or records what remains unknown.
For incomparable provider requirements, a bounded scheduling
slot cannot itself guarantee bounded retained-data size.
Limits and overflow behavior must be specified separately,
including whether progress can block, degrade to a conservative
reacquisition, or require a new user grant.

| Event or boundary | Required semantic result |
|-------------------+--------------------------|
| Authorized scoped invalidation while idle | Record or soundly combine its obligation. Start a cycle only if the currently selected acquisition policy and effective grant permit it. |
| Invalidation while an acquisition is active | Retain any requirement not proven covered by the active/captured read; coalesce scheduling without treating callback arrival as progression. |
| Duplicate or already satisfied requirement | Suppress redundant scheduling only under a valid exact/scope-aware coverage judgment; do not erase unrelated debt. |
| Explicit user Refresh | Admit the current applied query, authority context, requirement snapshot and read budget; issue or schedule exactly the work permitted. |
| Physical request constructed/issued | Register the logical cycle and its exact attempt/generation, source, query, captured obligations and target ownership before sending through HTMX. |
| Authorized observation acquired | Admit the actual provider's coverage and progression. Clear only those obligations whose *acquisition* stage is now satisfied. |
| Installation proposed/permitted | Bind current representation and physical target permit; retain adoption-stage debt until actual completed installation. |
| Installation completed or partially failed | Advance only physically completed qualified scopes; retain per-target failure, ambiguity and repair debt. |
| Request failed or transport outcome unknown | Retire the appropriate attempt without claiming its covered facts; preserve unmet debt and follow declared retry/grant policy. |
| Active cycle finishes | Re-evaluate current obligations and current permission; start at most the admitted successor, otherwise retain blocked/deferred debt. |
| Applied query, actor, owner or deployment changes | Revoke obsolete private resource rights; transfer only proven-compatible scope/debt to an admitted new owner. |
| Subscription or connection continuity breaks | Record continuity as unestablished and the required fence/reacquisition obligation, even if no further advisory is delivered. |
| Coordinator retires | Revoke scheduling/installation rights before physical cleanup; retain/transfer surviving obligations under the declared recovery policy. |

A coordinator must not conflate physical completion with
a response having passed a =:htmx/after-request= callback.
An acquired, but uninstalled, board is not an adopted board.
An advisory received while one read is in flight is
discharged only by an actually qualified observation and
its required adoption stage, not because the response happened
to arrive later.

Consider O1 requiring a complete authorized board observation
and adoption under its applied Organization/query. Bob presses
Refresh, granting exactly one read A1. While A1 is in flight,
another relevant advisory O2 arrives. If the actual result
satisfies only O1, O2 remains even when A1 installs correctly.
If the result independently satisfies both requirements and
its required scopes really install, both may clear without
another request. If A1 fails, both relevant unsatisfied
requirements remain; no ungranted successor may start.
If A1's observation is valid but its DOM installation fails,
acquired evidence and outstanding installation debt coexist.
Section 06.07 gives the expanded same-case table and
subscription-gap recovery.

A failed cycle with no queued successor is not proof that
its debt disappeared. The implementation must preserve
unmet requirements independently of its queue slot, even
when it has exhausted automatic retries or cannot currently
schedule work. Conversely, installing another admitted
observation that provably satisfies the debt may discharge
it without initiating a redundant read. Logical success,
unsatisfied obligations and retained physical cleanup are
different state dimensions.

A late A1 response after A1's owner retires cannot install
into A2's target just because its basis looks stronger.
The physical attempt, current source, effect and target
incarnation must still be admitted. A valid old observation
may be reused only under a separately admitted current
read/installation policy with qualified progression and
disclosure. It cannot revive A1's expired actuation permit.

**** Boundedness, fairness and correspondence obligations

The default one-active/one-successor invariant must be
checked on the *entire* semantic coordination cycle,
including outstanding installation, not only on the
number of in-flight HTTP requests. A stronger application
may use a declared parallel strategy with explicit
independent target ownership and equivalent safety/
resource bounds, but it must not silently claim the
default single-flight theorem.

A sound checker or exact-finite abstraction must cover
admitted/stale owner generations, source-qualified advisory
arrival, incomparable obligations, grants and budget
consumption, actual acquisition and installation success/
failure, page suspension, late physical requests, and
retirement/handoff. Tests that merely call a local
:fragment/refresh effect and see one HTTP request prove
neither non-loss of obligations nor eventual convergence.

Safety claims require that no obsolete request can
install, no unqualified requirement can be discharged,
no read begins without the selected permission, and no
independently newer adopted scope is regressed by an
older board. Liveness claims additionally depend on
user action where explicit Refresh is required, provider
availability, fairness, retry budgets, storage retention
and a working subscription-gap recovery path. A finite
state diagram with a terminal arrow is not proof of
termination or convergence.

Multi-node deployments must realize the same scope,
interest, obligation, authorization and recovery
semantics as single-node ones. The coordinator cannot
infer that silence from a distributed router proves
no relevant changes occurred. Interest installation,
router failover and missed-delivery reconciliation
require named physical guarantees or a qualified
reacquisition/fence. This section does not prescribe
a prematurely proved router algorithm; 06.07 and the
deployment/correspondence parts own those details.

**** Paired fragment-coordinator acceptance histories

The finished design requires both a real eligible
successful path and a nearby adverse/ambiguous case
that reaches the particular boundary under test.

| Eligible positive history | Adverse or ambiguous history | Required conclusion |
|---------------------------+------------------------------+---------------------|
| Bob receives O1, retains advisory debt and presses one Refresh to admit A1 under the applied board query. | The same advisory automatically triggers an ungranted fetch in the explicit-Refresh product policy. | Debt exists independently of acquisition permission; no physical read occurs without its declared grant. |
| O2 arrives while A1 is in flight; A1 installs a qualified observation satisfying only O1. | A1 completion clears O2 merely because it happened after O2 arrived, or loses the requirement by resetting a queue slot. | Discharge O1 at its required stage, preserve O2 and any unmet continuity/adoption debt. |
| A1's real qualified complete query observation covers both O1 and O2 and installs all required scopes. | The adapter assumes arbitrary numeric token ordering or silently discards an incomparable requirement to claim coverage. | Discharge both only on provider-justified satisfaction and actual adoption; no second read needed. |
| A1 fails or its physical installation is partial; no successor read is permitted. | Failure ends the cycle and erases the only O1/O2 records, or a queued slot initiates A2 without a new grant. | Preserve unsatisfied debt and partial-effect repair; expose blocked/deferred state without hidden automatic acquisition. |
| A1 logically retires, A2 is admitted later, and a late A1 response arrives after an unsuccessful abort. | The late response mutates A2's DOM by matching selector or a stronger-looking basis token. | Reject stale actuation, retain bounded physical cleanup debt and current owner evidence. |
| One full-cycle coordinator finishes acquisition and admitted installation before starting its next logical cycle. | It counts only open HTTP connections and allows overlapping untracked DOM installations, while claiming single flight. | Require one-active/one-successor bound for the declared logical cycle or separately prove the alternate installation bound. |
| The user changes the authoritative applied Organization/query while retaining a local text-search draft. | The old owner installs its earlier query response into the new applied cohort, or local draft changes silently reidentify the server read. | New owner/authorization and scoped transfer check; local presentation draft is not the authoritative applied query. |
| A subscription disconnect is detected and a recovery fence/read is admitted under its policy. | No more SSE messages arrive and silence is treated as proof of continuity, including after router failover. | Preserve an unestablished-gap obligation; recovery needs qualified source coverage rather than assumed delivery. |

No valid path is accepted merely because all managed
actions were disabled. The product acceptance oracle
comes from independently required HumanHelp behavior,
including active Claim/Reassign, creator-local results,
remote advisory without premature adoption and one
explicitly granted Refresh where that policy is selected.
A fabricated basis map, self-asserted source tag or
matching plan digest is not evidence of completed
provider acquisition or physical board installation.

**** Worked example: two obligations during one Refresh

Bob has adopted a qualified, complete HumanHelp Request-board observation
for applied query Q and authority context K at provider position P17.
An admitted Live advisory O1 establishes an outstanding requirement for
compatible Q coverage satisfying provider condition P18. Under this product's
*explicit-user-Refresh* policy, O1 creates advisory debt and a visible
Refresh affordance, not automatic permission to fetch or adopt another board.
Alice may independently create or Claim a Request while Bob is viewing Q.

Bob presses Refresh once. The admitted action creates grant G1, capturing
the applied Q/K scope, O1 and a budget of one physical acquisition with no
automatic successor. A1 is the admitted logical acquisition/installation
cycle; its physical HTMX attempt, installed target and resource generation
have distinct identities. During A1, a separate admitted advisory O2
arrives with a requirement associated with P20. No ordering or
satisfaction relation follows merely from the labels P17/P18/P20.
The relevant progression provider must establish it.

#+begin_src clojure
;; Illustrative already-admitted inspection values, not authority grants
;; created by supplying these maps from an arbitrary browser.
{:grant/ref G1
 :owner/ref board-owner-B1
 :authority-context/ref K
 :query/ref Q
 :captured-requirements [O1]
 :reads {:initial 1 :successors 0}
 :adoption-policy :qualified-scoped-install}

{:cycle/ref A1
 :grant/ref G1
 :query/ref Q
 :captured-requirements [O1]
 :request-instance/ref H1
 :owner/ref board-owner-B1
 :status :acquiring}

{:obligation/ref O2
 :source/ref admitted-live-interest
 :query/ref Q
 :required-stage :adopt
 :progression/ref P20}
#+end_src

These maps display distinctions; they do not implement
:advisory/satisfied-by?, create a trusted provider observation, or
justify any physical DOM installation. In particular, a field
named =:progression/ref= is not an assertion that P20 is
comparable to, or later than, P18.

When O2 arrives, the coordinator adds it to the current obligation
set. It does not modify the historical snapshot captured by G1,
silently expand the read budget, or assume that A1's already
constructed request includes O2's minimum-read requirement.
The *actual returned observation* may nonetheless independently
satisfy O2. Discharge is calculated against the current outstanding
obligations and their required stages, not against only G1's
originally captured list.

| Qualified A1 result and actual permission | Required result |
|-------------------------------------------+-----------------|
| A1 returns a complete authorized Q observation O18, provider-proved to satisfy O1 only; the current target installs it successfully. | Record O1's required adoption, retain O2 and its visible advisory debt; no hidden A2. |
| A1 returns O18 satisfying O1, but HTML or DOM installation fails or remains indeterminate. | Retain relevant acquired evidence where valid; keep installation/recovery debt for O1 and O2 as their stages require. Do not claim adoption from HTTP success. |
| A1 returns an independently admitted O21 for Q and the provider establishes that it satisfies both O1 and O2; all required physical scopes install. | Discharge both requirements with the one authorized read, without inventing a second request. |
| A1 fails before obtaining admitted current evidence. | Preserve O1 and O2, classify failure and expose a new user action or permitted declared retry. |
| A1 returns an observation that covers O1 but has no comparable judgment for O2. | Keep O2 even if a token looks numerically larger; a conservative result is not incorrect over-retention. |
| G1 authorizes exactly one acquisition; a queued successor intent remains after A1. | Do not start A2 without a new valid grant. The successor slot is scheduling intent, not independent permission. |
| A different declared policy explicitly grants one bounded drain-debt successor. | Start no more than the admitted successor while its current owner, source, expiry, and read budget remain valid. |
| Another qualified physical installation already satisfies O2 while A1 is active. | Remove only the now-proved satisfied obligation; avoid a redundant read or overwriting newer adopted evidence. |

If A1's response has a provider progression satisfying both
O1 and O2, *but* its actual physical footprint covers only one
card, adoption-stage board obligations remain until the declared
board cohort postcondition is established. Conversely a separately
qualified newer local card S may remain adopted while Q's board
membership is adopted from an older compatible response R.
That selective merge cannot be described as one atomic backend
snapshot; it must preserve each source, coverage and physical
representation relationship under the policy of 06.05.

The original R4 examples used X17/X18/X20/X21 to make the two
possible outcomes concrete. These labels remain useful examples,
but editing a fixture's =:basis= field from X18 to X21 does
not issue a new admitted observation or prove the provider's
satisfaction relation. Test witnesses must come from the actual
qualified source, an explicitly modeled provider or a sound
fixture generator, with separate installation completion evidence.
No unconditional comparison such as =X21 > X20= is permitted.

A1 may be retired while an attempted physical abort fails.
A later response carrying an apparently stronger provider token
cannot write into the new A2 owner/target or discharge its
obligations using A1's revoked permit. If that observation is
still useful, its source/authority and progression must be
readmitted under a *new* applicable owner and permitted
installation path. A later physical callback cannot resurrect
a retired logical acquisition.

An explicit one-Refresh test needs an actual authorized eligible
board and a counted physical request budget. It must positively
show the first permitted request, then prove no ungranted
successor was sent, while remaining debt stays visible. A
test that merely disables the button or intercepts all fetches
does not establish the required positive product behavior.

**** Applied query identity, local drafts and owner changes

The coordinator's authoritative scope is the *applied* server
query and its authorized cohort. It binds tenant/Organization,
principal/actor and current disclosure context, projection,
relevant server-side filters, selection criteria, temporal
interpretation, and required coverage/progression semantics.
A sort order is included when it changes the server query or
meaning of the returned representation; pure local rearrangement
of the same acquired cohort remains a presentation choice.

Typing in a local live-search field need not initiate a new
server query: it may filter an already acquired authorized
cohort while retaining the same applied Q. Local search draft,
sort preference, selected card, open details, scroll and
compatible input drafts are presentation/continuity data.
They cannot create trusted collection membership or rewrite
the acquisition's authorized scope. Conversely, if a filter
*is applied* to the server query, a previously in-flight
response for Q1 may not be installed as if it answered Q2.

A normal applied-query change admits a new coordinator owner
and target generation, revokes the old owner's private
resource and installation permits, and creates or transfers
the newly applicable obligations under a checked coverage
and authority judgment. Compatible independent observations
may be retained, but a merely copied query key, DOM selector
or subscription ID is not evidence of such a transfer.
The old subscription may briefly coexist physically with
the new one during handoff without remaining semantically
authorized to install into its successor.

Authority-context transitions require the same explicit
re-admission. A logout, Organization switch, Membership
change, or altered disclosure rule invalidates assumptions
attached to the earlier principal/context. The browser
must not retain protected old content, subscription interests
or acquisition permissions as if they belonged to the new
context. The trusted server independently checks every read,
stream subscription and write, including those submitted
by a hostile client that bypasses the browser adapter.

Continuity restoration may preserve an authorized local
draft, focus or scroll under its owner policy. It may not
reinstate an old *applied* server filter, older Request card,
outdated operation annotation, unapproved user draft, or
subscription owner as though those were harmless UI state.
An optional failed focus restoration after an admitted
installation is a local fault; it does not revoke the
authoritative observation or authorize obsolete rollback.

HumanHelp's remote actor who has O1 sees an advisory and
Refresh glow, but no hidden acquisition under the
explicit-Refresh policy. Alice's own correlated new
Request S can be installed locally after its qualified
operation and card observation, without requiring every
remote participant to adopt it. When Bob finally grants
one Refresh, it must preserve a separately newer locally
installed S in a compatible scope rather than blindly
overwriting S with older board R. The product's positive
behavior includes actual enabled Claim, Unclaim, Done,
Cancel and manager Reassign where eligible, not only
correct rejection of deliberately invalid commands.

**** Initial load and subscription recovery close the same gap

Initial server rendering is also a qualified acquisition
and physical installation. Its projection, applied query,
trusted disclosure scope, coverage, installed asset/plan
compatibility and physical owner must be related to the
subsequently admitted Live subscription. An HTML fragment's
mere presence on page load is not proof that its
authoritative baseline and subscription are coherent.

Consider an initial authoritative board observation B taken
at provider position P17. The stream/interest that should
report later changes may not be effective until after B.
A relevant write W can occur in that interval. If no
subsequent event is delivered for W and no other fence is
established, the browser cannot infer that its initial
B remains current. Establishing the stream after rendering
is not, by itself, a coverage proof.

A supported provider/transport realization closes that
hand-off gap by an explicitly justified mechanism, such as:

- registering the durable interest/stream before capturing
  the baseline, buffering or replaying admitted invalidations,
  then reconciling against a proved overlap/fence;
- an atomic or otherwise qualified subscription/read fence
  that establishes all changes up to a declared provider
  position are reflected in the baseline or replay set;
- durable cursor/replay with explicit retention, delivery,
  source, ordering and gap detection semantics;
- an admissible post-interest current-state read whose
  provider/stream protocol proves coverage of the relevant
  gap, including authorized query and applied-scope identity;
- bounded periodic reacquisition with an explicit staleness/
  liveness contract, where continuous no-gap knowledge is
  *not* claimed without stronger evidence.

The same question arises when a router first learns of a
node's interest, when a browser reconnects, or when a
standby router takes over. An invalidation that no router
formed or retained cannot be reconstructed merely by
resending the messages still available to a recovering
router. Idempotent redelivery is useful for messages that
*were* generated and may have been lost; it is not a proof
that every write inside an interest-registration race was
ever represented. A qualified baseline/fence, replay
contract or reacquisition is still required to establish
the promised current-state coverage.

If the system provides only best-effort SSE notifications,
the safe contract retains continuity as *unestablished*
across the gap. It may warn that the view may be stale,
offer an explicit Refresh, or use a separately authorized
reacquisition policy; it must not assert a successful
subscription handoff because no more messages arrived.
The ordinary refresh may legitimately happen after an
advisory without providing a precise global stream-order
witness; the assurance claim must name what the provider
actually establishes.

Disconnect, =online=, restored =pageshow=, foreground
=visibilitychange=, server restart, subscription replacement,
tab suspension, live-root replacement and router failover
can all create or expose a continuity gap. These triggers
are *opportunities to detect or repair*, not authoritative
progression evidence or unconditional permission to fetch.
A lifecycle wakeup with no progression token still creates
the required reconciliation/unestablished-continuity
state when the selected contract demands it.

For a product selecting explicit user Refresh, a recovery
gap may create visible debt without consuming an
ungranted read. If a strong subscription invariant
requires an immediate fence/read, application construction
must either explicitly authorize that bounded bootstrap
or recovery acquisition, declare a weaker live guarantee,
or reject the incompatible combination. It may not
quietly bypass the user's one-Refresh grant while
claiming that the same grant covered two reads.
Mandatory safety or privacy revocation may require
separate immediate local invalidation under its
security policy; that is not permission to fetch new
protected data without trusted authorization.

Stream event IDs, XTDB basis values, HTTP request
generations and distributed router sequence numbers
serve different purposes. They are not interchangeable,
and their numeric-looking forms establish no universal
order or durable replay property. Every admitted
identifier needs a declared source, scope, epoch/
incarnation and provider relation. Duplicate, late
and reordered messages are ordinary protocol cases;
the coordinator preserves independently valid debt
and ignores stale *installation rights* without
discarding a current, genuinely scoped advisory.

Current-state views can recover from a missed sequence
of invalidations by obtaining a qualifying current
observation, without replaying every intermediate
write, provided the provider's read and authorization
semantics establish the promised resulting state.
A workflow promising delivery or execution of *every*
event requires a separate durable event-processing
contract: refreshing a board cannot prove that each
intermediate event was consumed.

Interests themselves have semantic and physical
lifetimes. A shared SSE connection may serve several
fragments and survive replacement of one card, but a
retired card interest cannot continue authorizing
callbacks or disclosures for that target. Owner
replacement and new stream registration preserve
or deliberately reestablish live trigger bindings
and cleanup resources by exact instance identity.
A physically lingering old connection is cleanup
debt, not a second semantic owner.

**** Paired Refresh and subscription-gap acceptance histories

These are obligations for the *finished* system and
its declared provider/host profile. A positive path
must use an eligible authorized read and actual
installed result; a nearby negative must exercise
the relevant boundary without being rejected for
an unrelated malformed fixture.

| Eligible positive history | Adverse or incomplete history | Required conclusion |

The complete HumanHelp product criterion remains independent:
eligible Claim, Reassign, local search, creator-local immediate
presentation, remote advisory, one granted Refresh and physical
continuity must be observed through real model and browser paths.
Source-level state-map equality or reject-all construction
cannot satisfy those positive requirements.
** Projected-plan identity, deployment, and stale continuation recovery
:PROPERTIES:
:CUSTOM_ID: req-stale-plan-recovery
:END:

A browser may keep a page open while Gesso's executable plans, application
operations, public-model policy, served assets, wire contracts, or trusted
server deployment change. A suspended page may later be restored from
browser history, the back/forward cache, a service worker, a local persisted
record, or a long-running tab. The successful decoding or presentation
of that old state does not authorize its continuation.

The finished application admits a resumed execution only for the *actual
subject and boundary* for which required compatibility is established.
A version label, shared source name, matching DOM attribute, copied plan
digest or still-available JavaScript object is not itself a compatibility
judgment. The implementation must preserve the difference between
identifying the exact object installed, deciding whether two subjects may
interoperate, and establishing the current permission for a protected act.

Parts IV–V own historical command incorporation, immutable intent,
executable subject identity, model authorization and provisional
presentation. Sections 06.01–06.07 establish physical owner/target
rights, actual installation, advisory debt and subscription continuity.
This section joins them at startup, resume, deployment and compatibility
boundaries. Section 06.09 handles the subsequent retirement, obligation
transfer and recovery protocol; it is not a license to keep old browser
effects alive.

*** Compatibility is a collection of scoped judgments

An admitted application construction identifies separately:

| Subject | Required question at the applicable boundary |
|---------+------------------------------------------------|
| Executable interpretation | Can this *actual loaded* browser runtime execute the exact projected-plan payload and all required bound implementations under its stated semantic contract? |
| Local continuation | Can this particular execution state, pending effects, generations, ownership and provisional work safely resume, rather than merely be parsed? |
| New operation invocation | Are the current generated binding, operation meaning, argument schema, route and application authority context still admitted for a *new* command? |
| Existing command resolution | Can a trusted resolver still interpret a previously submitted command's immutable operation/actor/argument binding and produce a qualified historical outcome? |
| Compatible command repetition | Is another transport attempt for the *same* still-unresolved command admitted by its original deduplication/replay contract, rather than by today's potentially changed operation meaning? |
| Observation and rendering | May the current authenticated reader acquire the required scope and may the installed renderer/host profile represent and physically adopt that particular observation? |
| Wire and transport | Can the deployed peer decode and interpret the precise request, settlement, progression and subscription contracts in both directions? |
| Physical realization | Do the actually loaded HTMX, SSE extension, Gesso adapter, shell, browser handlers, scripts and response paths match a supported effect and lifecycle contract? |
| Authority and disclosure | Do current principal, tenant, Membership, protected scope, session and policy conditions permit the proposed read, mutation, restoration and disclosure? |
| Deployment/assembly closure | Does the actual served and loaded artifact set correspond to the admitted assembled application and the versioned semantics/checker subject whose guarantees are claimed? |

These judgments can have different outcomes. A new deployment may refuse to
resume an old browser machine while still servicing a qualified resolver
for commands that the old machine submitted. A freshly loaded plan may be
safe for new Claim commands while an older C42 needs a retained operation
schema and readback contract. A byte-identical old script may nonetheless
lack current permission to expose a previous user's data. An accepted
semantic compatibility relation never confers current server authority.

Choreography representation, plan payload, semantic operation meaning,
wire protocol, command identity, local execution, effect generation,
assembly/release generation and deployment placement are separate
coordinates. No single global monotonically increasing version integer
is required. Deployment rollout identity also does not imply that all
servers, cache layers, service workers and currently connected browsers
are serving the same asset set. Mixed-version compatibility requires
explicitly supported intersections and a defined safe behavior when a
request reaches an incompatible peer.

Equality is sufficient only where the stated subject actually demands exact
identity *and* that equality is established from its admitted source.
Interoperation and controlled migration may use a weaker equivalence relation
if it states which invariants, observation interpretations, commands and
effects remain valid. Conversely a blanket =compatible=true= or
successfully decoded EDN value is not such evidence. A claimed digest
must name its canonicalization and equivalence domain, provenance,
collision premise, and the actual bytes/implementations to which it binds.
A proof/sidecar digest does not replace the mandatory runtime
or authorization checks.

*** Resume admission precedes protected physical work

An application states where it obtains current compatibility evidence and
which boundary events require revalidation: initial page startup,
browser-history or bfcache restoration, tab wake, foreground transition,
service-worker takeover, a long-lived socket reconnect, application/asset
replacement, and server or policy change where observable. The mere receipt
of =pageshow=, =online= or an SSE open event is *advisory*; it does not prove
that old code is compatible with the current server or that missed changes
have been replayed. Conversely a tab cannot assume that no change occurred
because no such callback ran during suspension.

Before any protected subsequent physical send, DOM effect, subscription
update or machine continuation, the supported realization has to possess
current, applicable admission for that operation's identity, owner and
effect generation. If compatibility cannot be established at the supported
boundary, the protected act is blocked and the declared recovery path
begins. A stale async continuation cannot acquire new rights by reading
today's global "current plan" or a successor DOM element with the same
selector. A queued effect must check its current permit at the last
controllable physical act, even if its origin was compatible when issued.

A realization may cache compatible judgments with a scoped lease, trusted
invalidation or renewal policy instead of re-proving its entire application
on every keystroke. It must qualify expiry, observation of policy changes,
counterparty version selection and what happens during network isolation.
A stale local lease cannot replace trusted server-side current principal,
Membership, RequestAssignment or other protected policy checks.
Failing to reach the server cannot automatically mean an old grant remains
valid forever.

The re-admission protocol distinguishes:

1. **Known current compatible continuation:** the required interpretation,
   runtime resources, authority context, and progression/continuity
   conditions remain valid, so the exact current execution may advance.
2. **Recognizable but incompatible continuation:** old private execution and
   physical actuation rights are semantically retired before a fresh,
   admitted plan is instantiated; its durable command obligations survive
   under a separate recovery owner where promised.
3. **Malformed or untrusted retained state:** decoding or source admission
   fails. Do not reinterpret malformed bytes as a compatible plan or grant
   a stale callback permission; record the declared recovery/error state.
4. **Compatibility indeterminate or temporarily unavailable:** fail closed
   for protected old effects, preserve unresolved commitments and required
   display/subscription obligations, and follow bounded retry, reload,
   reauthorization or manual recovery rather than guessing a branch.

These classifications do not collapse =unknown command outcome= into
=invalid plan= or =authoritative rejection=. The current user may recover
a card or an authorized board without recovering the history of a
particular old C42, and vice versa. A renderer becoming usable does
not prove the earlier write incorporated.

On account logout or protected context change, the runtime removes or
quarantines old locally displayed protected state and revokes old
subscription/transport/owner permissions according to the selected
privacy/display contract. This is a requirement on the honest
application's future presentation, not a claim that already-seen
information can be erased from an adversarial browser or a person's
memory. Trusted handlers still authorize each read, subscription and
write independently of any browser-side plan stamp.

*** Served assets and physical version correspondence

The installed browser execution is determined by more than the nominal
plan file. It includes the *actual* fetched/executed scripts and modules,
registered handler implementations and their closures, compiled build
configuration, HTMX/SSE versions and extensions, served fragments,
service-worker caches, startup paths, response modes, and browser host
behavior on which protected effects depend.

An application may choose a content-addressed bundle, build manifest,
compatible artifact set, capability negotiation, or a similarly strong
scheme. Whatever scheme is chosen must relate the inspected or certified
semantic artifact set to the real resources subsequently served and
loaded. Merely including an assembly digest in generated HTML is not
a proof that the host executed those bytes or that a stale service
worker and new server agree on the protocol.

A release or rolling deployment can deliberately support more than
one version. Its advertised compatibility is then a scoped matrix of
allowed client/server/route/projection combinations and migration
rules, rather than a vague "both versions supported." Old pending
commands require a resolver horizon independent of how long their
old browser JavaScript is allowed to execute. An offline user whose
browser crosses that horizon requires a truthful unknown or manual
disposition, never a fabricated terminal rejection.

When asset, profile or protocol admission fails, a current authorized
reload/reconstruction is the conservative default. The application
may preserve independently authorized local input or draft state
through a declared migration, but it need not preserve arbitrary
suspended machine locators, timers, DOM snapshots, closures or
untrusted persisted permission maps. A scoped migration is
admissible only with explicit semantic correspondence, identity
and resource transfer rules, noninterference constraints and
actual post-migration validation.

*** Recover command bindings without resuming stale machinery

A historical command's recovery contract retains or permits trusted
lookup of at least its immutable semantic command identity, original
operation and schema, actor/authority binding, canonical arguments,
outcome-evidence provenance, deduplication/replay relation,
retention horizon, resolver owner and allowed disclosure. Sensitive
arguments may remain only server-side behind an authenticated
opaque lookup reference; persisting them in browser storage is not
required. All client-persisted records are untrusted on return.

C42 is not a bearer credential and its ID is not sufficient to
establish the original command's actor, inputs or permitted result.
Changing its arguments or applying new operation meaning while
retaining the ID is not compatible replay. Assigning a new ID to
escape an indeterminate result can cause duplicate incorporation.
Where the original write may already have occurred, a qualified
read-only resolver or safe deduplicated repetition is used under
Part IV; each path retains the current server's authorization and
disclosure checks.

The recovery contract separates *survival of semantic obligations*
from the *retirement of private physical rights*. An incompatible
E42 loses timer, provisional rollback, target and transport callbacks.
An admitted recovery owner may resolve C42 and acquire a new current
Request card under its own rights. It cannot execute E42's old
pending DOM effect, reuse its physical request instance, or
pretend that a visible card is sufficient historical attribution.
Section 06.09 specifies the exact transfer and durable recovery
lifecycle; this subsection specifies what must be compatible
before the transfer is attempted.

*** Paired compatibility and resume acceptance histories

Each positive witness must exercise the actual selected runtime
and trusted boundary where the guarantee is claimed; each adverse
case must reach the intended incompatibility boundary rather than
fail solely because of a malformed, unrelated fixture.

| Eligible positive history | Adverse or incomplete history | Required outcome |
|---------------------------+-------------------------------+------------------|
| A suspended P7 execution resumes on a peer proved compatible with its exact plan, host and current authority-context contract. | P7 remains parseable, but operation semantics, handler implementation or installed asset contract has changed incompatibly. | Only the justified continuation advances; recognizable incompatibility retires the old execution before protected work. |
| A P7 command C77 was sent before deployment D8. Its admitted historical resolver remains available while P7's browser execution is retired. | The new P8 attempts to replay C77 under a changed operation meaning or chooses a new ID without resolving possible earlier incorporation. | Preserve immutable historical command binding, qualified readback/replay and independent current-state acquisition; never infer rejection from incompatible continuation. |
| An offline browser restores from bfcache and obtains current compatible executable, resource, authority and subscription admissions before mutation. | A stale timer or callback sends or writes against a successor target using a saved allowed bit or a new global plan name. | Block stale actuation, retire old instance rights and reestablish compatible current sources before any protected effect. |
| A rolling deployment declares and tests compatible old/new client-server protocol combinations, including loaded HTMX and registered effect handlers. | A service worker serves old JavaScript against a new handler/route while a matching HTML digest is treated as proof that the loaded runtime matches. | Require actual served/loaded asset closure or reject/reload the unsupported combination; nominal digest equality is insufficient. |
| A principal/Organization change re-admits any allowed current data under the new context and retires old protected subscriptions. | Old browser markup, command callbacks or cached policy labels continue disclosing earlier account data under the new principal. | Honest-client future display and effect admission fail closed, with independent trusted server authorization; no impossible retroactive secrecy claim. |
| Compatible command recovery is available but current result disclosure is denied; the resolver returns the declared nondisclosing status. | The browser reuses a stored command ID or old session token to expose the historical result without present read permission. | Preserve semantic uncertainty and privacy boundaries separately; authorization is never inferred from possession of an ID. |
| An application explicitly proves a specific supported retained-draft migration across P7→P8 and validates its new binding. | Arbitrary DOM, pending timers, opaque machine locators and rollback rights are heuristically restored as if they were equivalent. | Only the declared, verified migrated scope survives; obsolete physical continuations remain retired. |
| A suspended client cannot reach a compatibility authority, so it preserves unresolved C42 and enters bounded blocked/recovery state. | It claims compatibility from silence, retries indefinitely, or treats unresolved delivery as terminal rejection. | Fail closed on protected effects and retain truthful unknown/recovery obligations under stated availability and retention bounds. |

The finished design does not require the application author
to manually write an external proof language or reconstruct
all the internal artifact relationships. Gesso's application
assembly and assurance pipeline generates the needed
correspondence obligations from the declared operations,
plans and deployment profiles. Its guarantees must still
name the trust premises, actual installed subjects and
boundaries of any opaque Clojure or browser behavior.
*** Retirement transfers surviving obligations before cleanup

A stale or incompatible browser execution must lose its private semantic
rights before any of its physical resources can affect the current view or
operation. Semantic retirement and *survival of unresolved obligations* are
separate properties: revoking E7's timer, send, rollback and target authority
does not establish that C77 was rejected, that a server transaction stopped,
or that the application may forget how to resolve a possibly incorporated
command.

The retiring owner and a current recovery owner participate in one declared
handoff contract. For obligations promised to survive, the handoff must
establish both their continued ownership and the old execution's revocation.
An implementation may establish the durable recovery record before revocation
or use an admitted atomic handoff. It may not first erase the only recoverable
command binding, then claim that a later best-effort callback will recreate it.
If an atomic handoff cannot be performed, the runtime fails closed on old
private effects, retains or reconstructs the obligation from a separately
qualified durable source where available, and exposes any unresolved
recovery failure. It cannot keep an unsafe old execution running simply
to wait for successful physical cleanup.

| Subject | What retirement changes | What may still survive |
|---------+-------------------------+------------------------|
| E7 local execution and projected machine | Revokes machine progression, private send, rollback, timer, target and restoration rights. | Historical diagnostic facts, with source and retention bounds. |
| H1 physical HTTP attempt and old timers | Requests best-effort abort/cancellation and rejects callbacks under the retired owner. | Physical remnants and uncertainty about whether H1 reached or incorporated on the server. |
| C77 immutable command intent | Does not rewrite C77's operation, actor, arguments or historical evidence. | An authorized resolver, compatible replay/deduplication contract, unknown-outcome obligation and command-specific retention. |
| Current authoritative entity/collection | Does not change trusted model state. | A newly acquired and installed Order/Request view under current disclosure/coverage rules. |
| Continuity and provisional presentation | Expires obsolete restore/rollback permits and old target ownership. | Deliberately selected compatible local drafts or newer independently justified presentation under a new owner. |
| Live and fragment coordination | Revokes retired private interest/target rights, retaining any owned shared connection according to its explicit protocol. | Subscription-gap, advisory and refresh debt transferred or re-established at the current applied query. |
| Deployment/runtime identity | Refuses to continue unsupported machine or effect implementations. | A new admitted plan/host and resolver that intentionally supports an old historical command contract. |

Logical retirement must precede or be committed independently of physical
cleanup. The adapter invalidates execution/resource generations and exact
target ownership; the shell attempts cancellation and release of its *captured*
physical handles afterward. A failed abort, late XHR response or thrown
cleanup hook is physical debt, not a resurrection of E7. A later callback
may be admitted only as cleanup evidence, or under a separate surviving
owner with independently justified semantics. Its old execution-private
rights never transfer by implication.

This ordering also constrains recovery failure. If the new page or resolver
cannot be loaded, E7 remains retired. A handler that throws, a storage quota
failure, an unavailable browser location, or a failed timer cancellation
must produce a typed visible/diagnostic state at the applicable boundary,
not re-enable old effects or interpret the last command as rejected.
A newer owner may begin safe independent work only while runtime-wide
resource and isolation premises remain satisfied.

*** Durable command recovery has an explicit failure domain

The assembly declares which interruptions its recovery promise actually
survives: a local execution replacement, page reload, tab process loss,
device restart, offline interval, deployment rollover, account change,
backend failover, or retention expiry are different failure domains.
A recovery promise across page destruction cannot rely solely on an
in-memory JavaScript closure or a pending Promise. It requires an
appropriate durable client record, trusted server discovery/intent
ledger, durable command-idempotency record or another specified
surviving mechanism. These mechanisms have different privacy,
availability and retention properties.

At the command boundary, the application must preserve or permit trusted
reconstruction of:

- the exact C77 semantic command identity and original operation/schema;
- authenticated actor/Organization context and immutable arguments or a
  protected resolver reference sufficient to check the original binding;
- the authoritative write/deduplication semantics under which another
  attempt could be compatible, including the possible-incorporation interval;
- existing qualified settlement, retry and readback evidence with its
  source, scope and temporal interpretation;
- a designated current recovery owner and trusted resolver entrypoint;
- which retention/expiry conditions permit a strong answer, leave
  uncertainty, or require manual reconciliation;
- present disclosure authority and the current authorized projection,
  which are re-established independently of the original actor.

A semantic command ID alone is not a credential, an original binding,
or proof that the operation was accepted. Persisted browser bytes
remain attacker-controllable input. They must not carry unconditional
read permission or override the current principal, Membership,
tenant or transaction rules. Sensitive canonical arguments may
remain server-side; a browser may retain only an opaque lookup key
whose use is authenticated and appropriately scoped.

If retention is bounded, the framework must specify what evidence survives
expiry and whether the original authoritative effect may still be pending.
An expired deduplication window cannot silently be treated as permission
to repeat an unknown non-idempotent operation. A missing resolver record
is not necessarily a terminal rejected command: it can mean
=:commit-unknown=, denied disclosure, unsupported old schema,
expired history, or an actually proven non-incorporation, which
have distinct consequences. A promise of eventual automatic resolution
requires realistic fairness, provider availability, retention and
scheduling premises; otherwise a truthful blocked/manual state is valid.

A selected plan may be retired while the recovery ledger remains useful
for multiple later deployments. The current plan's operation interface
does not automatically define the old command's meaning. A surviving
resolver must understand the exact original command and its committed
transaction/evidence scope; compatible replay requires a named
authoritative deduplication/repetition contract. A new command ID
cannot be allocated just to evade an unknown C77 result and produce
a duplicate Order or assignment.

*** Worked example: a sleeping checkout crosses deployment

An authorized browser running executable plan P7 prepares and submits
the =place-intent!= operation with semantic command C77 through one
physical attempt H1. The trusted transaction may have created Order
O900 in =payment-pending= state and atomically admitted durable payment
work. That is not the same as asserting that the later payment completed.
The network response is lost. The browser knows only that the
historical C77 disposition is unresolved, while E7 may still hold
a provisional "submitting" presentation and a pending retry timer.

Deployment D8 makes P7's continuation incompatible with the installed
plan P8. Alice's tab wakes after a long suspension. The supported
runtime checks current plan/host compatibility and present
authority context before allowing another protected send, timer
continuation or DOM act. An =online= or =pageshow= callback is a
wakeup opportunity, not compatibility or authorization evidence.

The default safe sequence is:

#+begin_example
recoverable C77 binding/lookup is already durable,
or its survival is established by an admitted handoff
        |
P7 continuation found incompatible
        |
retire E7 and revoke H1/timer/rollback/target rights
        |
attempt best-effort physical cleanup
        |                  (physical failure may remain debt)
admit current P8/runtime + current principal/authority
        |
resolve historical C77 under its old operation contract
        |                 separately
acquire authorized current Order O900 observation
        |
install the qualified current presentation
        |
continue durable payment/workflow monitoring independently
#+end_example

The handoff of recovery obligations and retirement of unsafe local
rights form a safe semantic transition; physical cleanup need not
finish before authoritative recovery can proceed. The diagram's
steps need not impose an artificial total order between independent
readback and current-state acquisition. A current Order may be
known when C77 attribution remains unresolved, or C77 may be
historically incorporated before a current Order card can be
read or installed. Each result retains its own owner/source evidence.

The trusted resolver identifies the original operation/actor and
deduplication context, checks the current requester's permission
to learn the result, and returns only the proposition its evidence
supports. For illustration:

| Trusted evidence and current read | Allowed presentation/recovery |
|-----------------------------------+-------------------------------|
| C77 is qualified as incorporated; an authorized current read shows O900 still =payment-pending=. | Show current pending Order and separate admitted payment-progress/recovery affordance; do not claim payment succeeded. |
| C77 is incorporated and later independently qualified payment completion is observed. | Show the authorized completed state; the later workflow result is not inferred from C77's original outcome. |
| The old command was authoritatively rejected and disclosure is currently permitted. | Present its qualified rejection and the admitted next action; do not claim the Order was created by C77. |
| An authorized read finds O900, but no qualified causal attribution to C77 exists. | Display O900 if permitted while preserving C77's unresolved historical incorporation; similar state is not command readback. |
| Neither incorporation nor rejection is established after H1's lost response. | Retain =:commit-unknown= and the declared resolver/backoff/manual reconciliation path; do not assign a fresh ID for blind replay. |
| The principal changed or disclosure is denied. | Quarantine old protected display and give only an authorized nondisclosing status; no implicit C77 rejection. |
| The original operation resolver/schema is unavailable or its retention horizon elapsed. | Block incompatible repetition, report the precise unavailable/expired/manual disposition, and avoid fabricated terminal results. |
| P8 cannot be loaded or current resources/transport are temporarily unavailable. | Leave E7 retired; use a bounded reload/retry or safe blocked state without silently falling back to P7. |

This example is deliberately about a durable business process. A
payment-pending Order can advance while the browser is closed
because the trusted workflow owns it; an old browser timer
does not. The same principle applies to HumanHelp's Claim:
a protected RequestAssignment may have incorporated even if
the browser lost the response and its old provisional
presentation was retired. A subsequent manager Reassign
does not retroactively reject the original Claim. Trusted
historical command resolution and permitted current card
acquisition remain distinct.

No part of this example creates a universal runtime
=order-model/resolve-command= function or a concrete public
Clojure API by implication. Actual operation admission,
resolver schema, durable payment progression and evidence
must be supplied by the declared application model and
the assembled Gesso interface.

*** Recovery is bounded, observable, and non-privileged

A branch described as recoverable must state its recovery owner,
required inputs/evidence, current authorizations, executable
next actions, retry/expiry policy, progress conditions and
terminal or manual alternatives. It cannot be satisfied merely
by labeling a catch block =:recoverable=. Recovery must have
a real path for eligible positive users as well as explicit
failure states.

The policy covers incompatible executable assets or protocol
schemas, failed authenticated readback, revoked Membership,
subscription/interest gaps, missing or stale target instances,
partially completed DOM effects, exhausted retention, browser
storage loss, server-side resolver unavailability, and network
partitions. Each branch preserves the distinction between:

- physical resource cleanup and logical execution retirement;
- a historical command result and the currently acquired entity;
- acquired data and physically adopted representation;
- a still-pending durable business workflow and its prior
  admission/command result;
- uncertain command delivery and proven terminal exclusion;
- a current recovery plan and an obsolete suspended machine;
- permission to initiate recovery acquisition and permission
  to disclose its protected result.

Restart/reload, readback, reacquisition and reinstallation do
not automatically erase outstanding Live interest/Refresh debt.
An initial-load or reconnect gap must be covered by the
applicable 06.06–06.07 source/fence/admission contract.
A fresh initial authoritative read may be separately permitted
as a new-page bootstrap under its declared product policy;
it may not be billed invisibly against an exhausted prior
one-Refresh grant.

Failure to acquire a current artifact or observation may stop
safely in =:blocked=, =:unknown=, =:read-only=, or
=:manual-reconciliation= with an explicit reason and next
admitted action. Automatic retries require bounded budgets,
backoff, cancellation and fairness assumptions. A failed
reload cannot simply schedule another unbounded reload,
and expiry of a retry timer cannot reauthorize the stale
execution. If the resource budget for lingering physical
effects is exhausted, the runtime may require a stronger
reset while retaining truth about unresolved commands.

Current-state views need not replay every missed UI event
after a long offline interval when a qualified current
observation establishes the promised state. Systems that
promise durable per-event processing must separately
retain and process those event obligations. The browser
cannot manufacture completed payment, Claim attribution,
or an entire event history from one freshly rendered card.

*** Paired retirement and recovery acceptance histories

Each positive witness must exercise an eligible real application
path and the relevant current trusted authority/physical boundary.
An adverse case must reach the intended failure/recovery point
rather than being rejected for an unrelated malformed fixture.

| Eligible positive history | Adverse or incomplete history | Required conclusion |
|---------------------------+-------------------------------+---------------------|
| C77's immutable binding survives before or atomically with E7's incompatible-plan retirement; its resolver remains available under a declared retention promise. | E7 is destroyed first, the only C77 binding was an in-memory closure, and a later reload claims the command is recoverable. | Recovery has a genuinely surviving owner or a reported loss/manual state; retirement never fabricates command rejection. |
| E7 is semantically retired, its timer/transport/target rights revoked, and physical cleanup succeeds. | Timer cancellation throws, then an old callback fires or a physical request completes after P8 starts. | Old private effects remain powerless; cleanup failure is bounded physical debt and cannot restore E7. |
| A resolver proves C77 created pending Order O900; another qualified source later proves payment completion. | Payment success is inferred solely from =:committed= for =place-intent!= or from an optimistic checkout label. | Command incorporation and durable payment-workflow progression are separate trusted propositions. |
| P8's current authorized Order read succeeds while historical C77 attribution remains unknown. | The presence of O900 or matching order text is taken as proof that C77 committed, or unknown is renamed rejected. | Present the current Order if permitted while retaining unresolved command attribution. |
| A compatible replay of C77 is admitted through its original deduplication/operation schema during the retention horizon. | A new command ID is used after H1 timeout, or C77's arguments are silently reinterpreted under changed P8 operation semantics. | Permit only qualified original-binding repetition or readback; no duplicate non-idempotent incorporation. |
| Alice's tab wakes as Bob; the current trusted resolver denies disclosure of Alice's old protected command. | Bob recovers the old result by copying a browser command ID, cached view or retained stale session label. | No unauthorized historical disclosure; keep the appropriate nondisclosing/unknown status independently of server truth. |
| A full reload reconstructs current plan and an authorized board/read without an ungranted second remote Refresh. | A reconnect/reload secretly consumes an expired G1 one-Refresh budget or treats SSE silence as subscription continuity. | Bootstrap/recovery acquisition has explicit permission, scoped adoption and a qualified continuity fence or retained debt. |
| A resolver is unavailable and an authorized user follows bounded retry or manual reconciliation. | The runtime enters an unbounded reload loop, silently uses P7, or converts lost history into terminal command rejection. | Stop safely with truthful blocked/unknown/manual state and declared retention/fairness premises. |
| A supported target migration preserves permitted local draft state and rebinds its current owner. | Arbitrary old DOM capture or provisional rollback is restored after the newer authoritative target installed. | Preserve only explicitly compatible local state; never revive obsolete restoration rights. |

The finished-framework behavior may require stronger durable command
storage, server idempotency, plan retention and recovery UI than the
present Gesso implementation. Those are normative targets and
separately owed implementation, assembly and certification evidence,
not reasons to weaken the required result.
** Browser managed effects
:PROPERTIES:
:CUSTOM_ID: req-browser-managed-effects
:END:

A managed effect is physical work whose ownership, permitted footprint,
completion, and retirement behavior are part of the admitted plan. Effects may
create resources, alter presentation, initiate transport, or request another
owned action. They do not acquire server authority by being called managed.

*** Classify effects along independent dimensions

A single effect can be asynchronous, allocate a resource, and provisionally mutate
DOM. These are not mutually exclusive categories. The contract records the
relevant dimensions separately:

| Dimension | Examples of the distinction |
|-----------+----------------------------|
| Footprint | Transport send, listener registration, timer, scoped DOM mutation, local storage. |
| Semantic purpose | Provisional presentation, authoritative-observation installation, continuity, command reconciliation, diagnostic output. |
| Owner/lifetime | Execution-private, coordinator-owned, shared subscription, durable recovery owner. |
| Completion | Synchronous postcondition, correlated asynchronous completion, externally indeterminate result. |
| Repetition | One-shot local mutation, repeatable cleanup, replay-safe read, deduplicated command attempt. |
| Retirement | Abort physical work if possible, revoke future rights, detach an interest, transfer unresolved obligation. |
| Compensation | No compensation, permitted local restoration, or a separate authoritative command with its own checks. |

Installing authoritative data is a browser realization of an admitted observation.
It does not make the DOM an authoritative domain model. A local rollback is not
an atomic undo of a server operation.

*** One root effect scope per execution, with explicit children

Each active local execution has one root ownership scope. Child scopes may
separate a provisional card, a presentation deadline, and other resources whose
lifetimes differ. Coordinators and shared connections have their own named
ownership scopes. No effect is ownerless simply because several executions may
benefit from it.

Resource references include actual incarnation identity. Retiring one timer or
transport cannot retire another resource that later reused the same registry key.
Ownership transfer is an admitted semantic transition, not two unrelated writes
that briefly leave the resource uncontrolled or doubly controlled.

Shared-resource release distinguishes detaching one interest from closing the
underlying connection. A reference count can implement the policy, but the
semantic contract must define which interests are current and how duplicate
attach/detach events behave.

*** Register before issuing; reconcile late physical handles

The runtime commits an effect/resource issuance record before calling the host
API. This permits a synchronous completion to be matched to real issued work.
It also handles the opposite race: retirement may occur before the host API
returns its cancellation or listener handle.

A physical registry therefore needs states such as awaiting-handle, live,
retired-awaiting-handle, and released. When a late handle arrives, the shell checks
whether the corresponding owner and resource instance are still current. If they
are retired, it immediately performs the permitted release and never publishes
the handle as a live resource.

A completion that arrives during registration follows the same admission gate
as any later completion. The implementation must handle completion-before-handle,
retirement-before-handle, duplicate completion, and exceptions after partial
registration. A handler that promises cleanup must expose enough information to
clean up any work it actually created.

Local effect issuance and remote operation incorporation are different protocols.
One-shot execution of a DOM permit does not provide exactly-once network delivery.
Remote retries rely on the command binding and authoritative deduplication contract
from Part IV.

*** Semantic retirement precedes physical cleanup

Retirement first invalidates semantic rights. Physical abort, listener removal,
timer clearing, and temporary-node cleanup follow. Safety cannot depend on those
physical operations succeeding immediately.

A late callback from a retired resource may report cleanup progress or provide
evidence through a separately admitted surviving owner. It cannot regain the
retired execution's right to send, settle, roll back, or install. A callback
carrying a newer observation does not bypass this rule.

Cleanup is idempotent for the same issued resource instance. It uses the captured
physical handle or an equivalently strong binding, rather than searching the DOM
for whichever current node matches an old selector. Deleting a temporary node or
removing a style by comparing its current value is unsafe when a later owner may
have written an identical value. Ownership and incarnation, not value coincidence,
control cleanup.

The runtime can continue semantic recovery while best-effort cleanup remains
outstanding, subject to resource limits. If physical remnants exceed the admitted
budget, it may suspend new work or require a stronger reset. The debt remains
observable; a failed abort cannot be counted as successful resource release.

*** Rollback and continuity rights have bounded lifetimes

A reversible presentation effect carries a scoped restoration right. That right
expires when its owner retires, the target is replaced, authoritative installation
supersedes the affected scope, or the declared concurrency policy revokes it.

Continuity capture is bound to its actual capture implementation and matching
restore contract. A later registry change cannot silently interpret an old
capture using a different restoration function. Captures may preserve permitted
focus, selection, scroll, or local draft state; they do not preserve obsolete
authoritative content or arbitrary old HTML as a privileged snapshot.

Authoritative supersession may retire one provisional overlay while leaving an
unresolved command's reconciliation owner alive. Competing presentation timers
lose their settlement rights immediately when their branch settles or is
superseded. A separately owned command-resolution deadline may remain necessary.
Cancelling every timer associated with the command would conflate those lifetimes.

*** Fault containment preserves the original failure and uncertainty

A failure in a pure step before state commitment has not partially performed its
abstract effects. The implementation retains the last committed state for
diagnosis and follows the declared containment path. Where the affected owner
cannot safely continue, it is retired through the trusted failure mechanism.

A failure after physical work begins is different. Some effects may have occurred,
and remote incorporation may be unknown. The shell records the actual stage and
partial work, revokes unsafe rights, preserves unresolved obligations, and runs
best-effort cleanup. It must not rewind semantic state and blindly reissue the
whole effect batch.

Cleanup failures are secondary diagnostic events linked to the primary fault.
They do not replace its cause, manufacture an authoritative rejection, or erase
command uncertainty. Independent owners may continue only if their isolation
premises still hold. Corruption of a runtime-wide registry may require retiring
the whole runtime instance rather than one execution.

** Async event safety
:PROPERTIES:
:CUSTOM_ID: req-browser-async-admission
:END:

Every asynchronous entry point normalizes and admits its event before causing a
semantic transition or protected physical action. This includes network outcomes,
HTMX callbacks, subscriptions, timers, animation callbacks, promises, worker and
cross-tab messages, observer callbacks, and delayed continuity restoration.

The gate is owner-relative. An execution-private completion, a shared subscription
advisory, and a command-resolution result have different owners and applicability
conditions. Requiring an execution ID on every event would misrepresent genuinely
shared work; accepting all events without an execution ID would bypass admission.

*** Event class comes from the registered source

The trusted local adapter registration establishes what kind of event a source
may deliver and which correlation fields it carries. An arbitrary payload field
such as =:event/class :command-evidence= cannot choose a more permissive admission
path.

Normalization binds the actual source resource to its permitted schema and owner
class. Payload values are validated within that binding. A worker or another tab
can provide useful information, but its message is not automatically authoritative
because it arrived through a browser API. The assembly declares how any claim in
that message obtains provenance.

An admission record can include:

#+begin_src clojure
{:source-registration/ref registered-source-ref
 :resource-instance/id source-resource-id
 :owner/ref admitted-owner-ref
 :effect-instance/id issued-effect-id
 :event-kind :transport/completed
 :correlation {:transport-request-id T1
               :gesso/command-id C42}
 :payload decoded-payload}
#+end_src

The registration constrains the record. Constructing the map is not the check.
A malformed or conflicting payload cannot overwrite the source's bound owner or
transport instance.

*** Admission checks both identity and legal state

The gate establishes, as applicable:

1. the source registration exists and permits this event kind;
2. the runtime, owner, and resource instance are current for this path;
3. correlation agrees with the issued effect, transport attempt, command binding,
   and target scope;
4. the event is well-formed and its claimed evidence has the required provenance;
5. the current plan state admits this completion or settlement;
6. duplicate/replay policy permits the intended consequence;
7. any resulting physical action receives a current permit of its own.

A valid identity does not make every event legal in every state. A completion
cannot settle an effect never issued, and a timeout cannot reverse an already
resolved branch merely because its execution record still exists.

Disposition and diagnostics distinguish at least:

| Condition | Meaning and treatment |
|-----------+-----------------------|
| Unknown correlation | No applicable issued work is known; do not guess an owner from nearby DOM. |
| Stale resource/owner | The event belongs to an earlier incarnation or retired scope; suppress its former rights. |
| Duplicate | The same admitted occurrence/result has already been handled; apply its declared idempotent disposition. |
| Incompatible | The applicable plan, message, context, or retained-operation contract does not admit interpretation. |
| Malformed | The event violates its input schema or bound correlation. |
| Illegal state transition | The source is known but this event cannot legally advance its current state. |
| Unestablished evidence | The supplied information does not justify the claimed fact or outcome. |
| External/physical failure | The issued work failed or has an indeterminate result under its contract. |

These are runtime classifications, not additional domain statuses or substitutes
for =:committed=, =:rejected=, =:already-incorporated=, and =:commit-unknown=.
Expected stale/duplicate events can be ignored semantically while still producing
bounded diagnostics. Conflicting evidence or broken invariants require the
specified fault/reconciliation path.

*** Worked example: three different owners

E42 submits command C42, then its card presentation retires. A board subscription
S9 remains active under shared owner B3. Command recovery owner K8 now holds C42's
unresolved obligation.

| Incoming event | Required interpretation |
|----------------+-------------------------|
| E42's old presentation timeout fires. | Its resource/branch is retired; it cannot reject C42 or restore the card. |
| E42's delayed provisional DOM callback fires. | Its permit and target rights are stale; no mutation is allowed. |
| Current subscription S9 emits a relevant board advisory. | B3 may record scoped debt under its subscription contract; E42's retirement is irrelevant. |
| Retired predecessor subscription S8 emits a callback. | S8 cannot use S9's rights merely because the endpoint and payload look the same. |
| K8 receives permitted resolver evidence that C42 was incorporated. | It may resolve the command and request an authorized current acquisition; it cannot revive E42. |
| An old transport callback labels itself shared command evidence. | The label does not change its registered source path; any evidence reuse needs an explicitly admitted handoff. |

This permits useful late knowledge without reopening stale physical authority.
A new execution E43 repeating the same command C42 also has distinct private
resources. Equality of command IDs does not make E42's callbacks valid for E43.

*** Duplicate delivery does not erase evidence distinctions

A transport delivery identity, a semantic command identity, and an authoritative
result/effect identity answer different questions. Deduplicating one layer does
not automatically deduplicate the others.

When an event/result ID is stable across repetitions, admission also checks the
binding and permitted payload equivalence. Conflicting payloads under the same
ID are a protocol/evidence fault, not harmless duplicates. The system cannot
silently keep whichever result arrived last.

Known authoritative incorporation is not downgraded to unknown because a later
transport attempt times out. Conversely, two similar successful-looking payloads
do not prove incorporation without admissible outcome evidence. The reconciliation
rules preserve established knowledge within its actual scope and disclosure
permission.

Deduplication and retirement records have a declared retention/compaction policy.
Unbounded tombstones are not the only solution, but compaction must prevent old
callbacks from being mistaken for newly issued work. Fresh runtime/resource
identities, retained fences, and explicit acceptance horizons can provide that
separation. Reusing an identifier after deleting its history is not sufficient.

** Authoritative absence
:PROPERTIES:
:CUSTOM_ID: req-authoritative-absence
:END:

An authoritative observation can establish that a particular entity or membership
is absent within a specified authorized scope. That is a positive evidence claim
about absence, not the lack of a successful response.

The browser distinguishes:

- an entity absent under a qualified entity lookup;
- an entity excluded from a particular query or collection membership;
- a field absent under the projection's field contract;
- information unavailable, undisclosable, or not covered by the observation;
- a missing physical DOM target.

These conditions need different continuations. A network error is not absence.
A permission denial need not disclose whether the entity exists. A card not found
in the DOM does not establish anything about the authoritative model.

*** Absence requires the appropriate coverage evidence

For absence inferred from omission, the observation must establish the closed
coverage needed for that inference. A paginated page, partial response, filtered
subset, or redacted projection cannot silently claim complete collection absence.
The membership question must also be within the query universe actually covered.

An explicit authoritative membership-exclusion result can provide narrower
sufficient evidence without reading a whole board. Its contract binds the entity,
query, context, progression, and exclusion meaning. The requirement is evidence
for the claimed absence, not a mandatory full-collection transport format.

The runtime preserves absence with its scope and admitted evidence just as it
preserves presence. It can represent this through a complete observation,
scoped exclusion record, or checked compact summary. It need not create a permanent
tombstone for every entity that could theoretically be missing.

*** Worked example: Request R17 leaves an open-request board

Alice's applied board query selects open Requests in Organization O. An earlier
admitted observation includes R17. Another operation changes R17 so it no longer
matches that query. A current acquisition can establish different facts:

| Observation | What the browser may conclude |
|-------------+-------------------------------|
| Complete admitted membership observation for the same query, with sufficient progression, excludes R17. | R17 is absent from this board membership at the observation's declared basis. |
| Admitted explicit exclusion for R17 under this query and context. | The covered membership is absent, without asserting complete board contents. |
| A different page of a paginated result omits R17. | No exclusion follows unless the paging/coverage contract establishes it. |
| A card lookup shows R17 in another domain state. | Board removal requires the admitted predicate/coverage relationship, not a guessed filter rule. |
| The user loses permission to view this board. | Apply the display-revocation policy; do not assert that R17 was deleted. |
| The request fails or returns incompatible data. | Preserve unavailable/unknown and the required recovery debt. |

A permitted removal is an installation effect. Its permit binds the affected
membership/target scope, current owner, and actual target instances. The runtime
records adopted absence only after the declared removal postcondition is
established.

If the target is already physically absent, an admitted no-op completion may be
valid when the removal contract can establish the required postcondition for the
same current owned scope. A generic target-not-found error cannot supply that
proof. A missing or replaced board root may instead require owner reconstruction
or full reacquisition.

The adopted absence is qualified by the observation's basis. It does not claim
that no concurrent future operation can reintroduce R17 into the board. Later
relevant changes follow the same advisory/acquisition contract as later presence
changes.

*** Provisional presence does not override authoritative coverage

Suppose execution E99 provisionally displays new Request R30 while creation
command C99 remains unresolved. A board acquisition omits R30. Several questions
remain distinct:

1. Does the observation establish exclusion from the relevant query, with the
   required coverage and temporal/progression meaning?
2. Does that evidence and the presentation policy authorize removing or replacing
   this provisional overlay now?
3. Does any evidence establish the authoritative disposition of C99?

An observation taken before a still-pending command incorporates may correctly
omit R30 while C99 remains unknown and may later commit. Even a sufficiently
current board observation need not establish attribution to, or rejection of,
C99. The application must not turn absence into a fabricated rejected command.

The presentation policy can retain a labeled pending overlay, remove it under a
declared supersession rule, or present it outside the authoritative membership
view. Its choice states the evidence/horizon it requires and keeps provisional
content visibly distinct from adopted authoritative membership.

If the overlay is removed, its stale rollback/continuity rights expire. The
command's surviving recovery obligation remains with its declared owner. Removing
one scoped presentation is not permission to retire all resources associated
with C99 or to discard its recovery record.

*** Absence participates in progression and convergence

An absence observation can satisfy an obligation only within its admitted scope
and required discharge stage. Entity deletion, query exclusion, authorization
loss, and a partial projection are not interchangeable.

A later compatible presence observation can legitimately replace earlier absence
when the provider's progression and model contracts permit it. The runtime must
not make absence an irreversible browser tombstone. It must prevent a stale
presence callback from resurrecting a removed card under revoked ownership.

Display revocation has a separate reason and postcondition when current policy
requires clearing sensitive content. It may remove presentation without claiming
that authoritative domain absence was established. Its future acquisitions and
reconciliation paths still enforce current authorization.

** Failure, liveness, and convergence

Safety, progress, and recovery are separate claims. The runtime must remain
truthful when it cannot make progress. A blocked acquisition, unknown command,
or unsupported continuation can be a correct safe state, provided its required
handling path is present and its presentation does not imply success.

*** Failures preserve authoritative commit truth

The application distinguishes at least:

| Failure class | Required semantic treatment |
|---------------+-----------------------------|
| Local input/admission rejection before send | Report the local condition without claiming an authoritative model rejection. |
| Authoritative operation rejection | Carry the permitted typed outcome under Part IV's binding and disclosure rules. |
| Transport loss after possible send | Preserve command uncertainty unless authoritative evidence resolves it. |
| Post-commit advisory/delivery failure | Preserve incorporation and the required delivery/recovery debt. |
| Acquisition failure | Preserve unmet observation requirements; do not invent presence or absence. |
| Installation failure | Preserve the distinction between acquired evidence and unestablished adoption. |
| Stale/incompatible continuation | Retire its rights and enter the admitted compatibility/recovery path. |
| Physical cleanup failure | Record resource debt without restoring retired semantic rights. |
| Runtime invariant failure | Contain affected owners and preserve evidence/uncertainty for diagnosis and recovery. |

A UI timeout means that a particular local waiting policy expired. Its meaning is
not automatically the operation's authoritative result. The timer contract names
its owner and whether it governs provisional display, transport waiting, command
reconciliation, or some other work.

*** Safety targets

Under the named semantic, implementation, and environmental premises, the browser
realization must establish:

- no protected physical effect proceeds without a current applicable issuance
  record and permit where required;
- a retired owner cannot regain private rights through a late or duplicate event;
- identity and provenance are preserved across normalization, effect issue, and
  completion rather than silently erased or substituted;
- adopted state reflects actual admitted installation within the claimed scope;
- progression and absence judgments use their qualified provider contracts;
- provisional presentation and local continuity cannot manufacture authoritative
  knowledge or revive superseded authoritative content;
- unknown commit is not converted into rejection or success by local timing;
- server authority never depends on obedience by the browser runtime.

These are conditional claims. An unverified renderer, host profile, progression
provider, or evidence extractor remains a named premise in claims that depend on
it. Passing tests must not silently remove that premise.

*** Progress needs explicit fairness and availability assumptions

A graph containing a path to a terminal state does not prove that an execution
will take that path. A liveness claim names its scheduling, delivery, availability,
permission, resource-budget, and user-action assumptions.

For example, eventual adoption of relevant board state can be claimed under
conditions such as:

1. the relevant authoritative state and query/context eventually stabilize;
2. the progression provider can supply a sufficiently strong authorized observation;
3. the required acquisition and installation permissions are eventually granted;
4. the scheduler, transport, and selected browser profile eventually complete
   enabled work within the promised failure model;
5. failed attempts retain debt and the declared retry/recovery policy continues;
6. no unresolved higher-priority overlay or incompatible ownership condition
   permanently blocks the required installation.

The conclusion is scoped convergence of the promised participant state, not
processing of every intermediate change or agreement with undisclosed data.
An explicit-refresh product may provide eventual convergence conditional on a
later Refresh action rather than unconditional background convergence.

Continuous changes, permanent denial of access, exhausted recovery budgets, or
an unavailable backend can prevent convergence without violating the safety
contract. The runtime exposes the resulting debt or blocked state. It must not
label the view current merely to make a progress metric succeed.

*** Boundedness is specified independently of single flight

The assembly declares budgets and overflow behavior for active cycles, successor
slots, unsatisfied obligations, retained command recovery, deduplication history,
physical remnants, and diagnostic buffers. These are different resources.

Checked coalescing or stronger reacquisition can compress advisory obligations
when the progression/coverage contract permits it. Otherwise the system needs
backpressure, a declared resynchronization state, or a visible capacity failure.
Dropping arbitrary obligations because the queue is full is not a valid bound.

A browser with one logical request per coordinator can still leak DOM captures,
failed-abort transports, or stale callback records indefinitely. Physical registry
and retention checks therefore accompany the logical scheduling bound.

** Refinement, correspondence, and conformance evidence

*** Observe actual transitions and actual physical work

The implementation records the transition selected by the actual adapter step,
its admitted identities, and the abstract effects it issued. The shell separately
records correlated physical issue/completion events where the claimed assurance
requires them. These records preserve their origin and scope.

| Evidence | What it establishes at most |
|----------+----------------------------|
| Selected pure adapter transition | The executable semantic step selected this successor/effect description for these inputs. |
| Abstract transport-send effect | The semantic machine requested a send; physical delivery is not yet established. |
| Physical send/completion evidence | The selected transport performed the reported stage under its qualified contract. |
| Authoritative command evidence | The trusted operation/resolver established the permitted command outcome. |
| Admitted observation evidence | The acquisition established the declared facts and coverage. |
| Matched installation completion | The declared physical postcondition was established for that issued installation. |
| Participant adoption record | The participant admitted that completed installation within its scope. |

The trace must not conflate these into one event called success. A useful adapter
observation may be source-relative to actual local transitions while still lacking
a proven connection to global choreography, physical delivery, or authoritative
incorporation. Its assurance label states that limit.

Diagnostics use exact executable identity and the actual emitted transition
mapping from Part V. They do not recompute a transition from source names or
reconstruct physical success from the effect that was intended.

*** Adapter refinement is conditional trace correspondence

The browser refinement claim relates concrete shell/browser traces to admitted
semantic traces under the selected profile. The relation preserves relevant event
order, ownership, identities, evidence, physical commitment/completion boundaries,
and externally observable actions.

A useful formulation is:

#+begin_example
Given an admitted initial relation and the named profile premises,
each concrete transition either:
  - realizes an allowed semantic transition with its bound observations/effects; or
  - is permitted internal work that preserves the relation and protected invariants.

Every protected concrete action is accounted for.
Every claimed semantic physical completion has matching concrete evidence.
#+end_example

Internal stuttering steps cannot hide an unadmitted mutation, duplicate send,
wrong-target installation, or lost obligation. A safety correspondence alone
does not exclude infinite internal stuttering; liveness needs the additional
assumptions and progress argument stated separately.

The relation includes failures and partial effects. A model that includes only
successful swaps cannot justify the implementation's behavior on target loss,
callback exceptions, or retirement races.

A trace-alignment checker can establish that a particular observed sequence fits
an independently constructed semantic witness. It must match actual occurrences,
not just similar payloads: no reuse, omission, or reordering of relevant events,
and no substitution of command, resource, target, or observation identities.
Where multiple matches are possible, the accepted witness and its premises remain
explicit.

Constructing a model witness with the same output values is insufficient if the
extractor could invent those values or omit the bad physical action. Trace origin,
extraction completeness for the claim, and the concrete-to-abstract binding are
part of the assurance boundary. A checked finite trace is evidence about that
trace, not a universal theorem about every possible schedule.

*** Execution isolation and shared effects

Execution-private events and effects may change only the state and physical
footprint allowed by their owner and declared interactions. A late callback for
E42 cannot settle E43, even when both concern the same entity or command.

Shared coordinators, authoritative installation, and resource-pressure policies
can legitimately affect several executions. Their affected scopes and revocation
rules are explicit semantic transitions. An isolation statement must not exclude
those intended interactions from the model and then claim stronger independence.

Where two effects share a physical target, the assembly supplies a serialization,
merge, or supersession policy. Merely assigning distinct execution IDs does not
make their DOM mutations independent.

*** Authoritative installation and resource invariants

For each accepted installation, the proof/test obligations include:

1. the observation is admitted for the current context and claimed scope;
2. the installed representation is bound to that observation and permitted
   provisional/continuity policy;
3. the current permit covers every protected target and effect;
4. obsolete restoration rights are revoked at the declared boundary;
5. physical completion is correlated to the issued installation;
6. acquired/adopted frontiers and discharged obligations reflect only what was
   actually established.

For each resource lifetime, the obligations include registration-before-issue,
current-owner checks, explicit transfer where permitted, idempotent release,
late-handle handling, bounded retention, and the absence of private rights after
retirement. A logically terminal presentation need not imply that its command
has resolved; surviving recovery ownership is part of the invariant.

*** Adversarial-browser authority boundary

A user can bypass the browser adapter, alter markup, forge local records, choose
command bytes, replay requests, or invoke server endpoints directly. Browser
correctness therefore concerns the admitted implementation's behavior; server
security must remain valid without assuming that behavior.

The trusted operation boundary authenticates, checks current authorization,
validates typed arguments and command binding, guards current model dependencies,
and controls disclosure of prior results. Browser certificates, installation
permits, sidecars, and correlation records do not supply those premises.

This separation permits strong local execution guarantees while keeping domain
authority at the boundary that owns it. It also prevents an adapter proof from
being presented as a proof of backend transaction semantics or of arbitrary
client honesty.

*** Required conformance scenarios

The suite combines pure transition/property tests, trace correspondence checks,
and physical integration tests for each supported profile. Pure tests explore
semantic schedules; physical tests exercise hooks and effects that a simulated
event sequence alone cannot establish.

At minimum, the admitted realization covers the following cases, with positive
controls showing that valid work still completes:

| Scenario | Required observation |
|----------+----------------------|
| Immediate completion during effect registration | The completion finds the issued semantic record and is handled once. |
| Retirement before a cancellation handle returns | The late handle is released and never becomes a current live resource. |
| Synchronous callback retires an owner during an effect batch | Remaining protected effects recheck and cannot use the captured stale permission. |
| Required lifecycle gate cannot decide synchronously | The protected host action is prevented; no delayed default-allow path occurs. |
| Missing or throwing physical handler | Required work fails visibly rather than being reported completed. |
| Delayed swap after target replacement | The old permit cannot mutate the new target instance. |
| Secondary-target or response-driven action outside the permit | The profile prevents it or refuses the unsupported response path. |
| Partial multi-target installation | Only independently established subscopes may be adopted; repair debt remains. |
| HTTP success followed by installation failure/lost completion | Acquisition and adoption remain distinct; installation debt persists. |
| Advisory arrives during a one-read grant | Debt is retained without inventing permission for a successor request. |
| Failed refresh with no queued successor | Unsatisfied obligations remain recoverable. |
| One stronger actual observation covers several obligations | Checked coverage discharges them without redundant reads. |
| Older board content conflicts with a newer adopted card | Reacquisition or the admitted scoped-merge policy prevents regression. |
| Connection returns after missed advisories | Gap recovery runs even if no new event is delivered. |
| Old and replacement subscriptions overlap | Source-instance admission prevents retired ownership from being reused. |
| Unknown command crosses deployment or page restart | The retained binding resolves under current disclosure rules without incompatible replay. |
| Principal/tenant changes with retained private data | Future display/use and resolution follow current-context admission. |
| Provisional creation is absent from a board read | Presentation policy applies without inventing command rejection. |
| Duplicate event ID carries conflicting evidence | The conflict is diagnosed/reconciled rather than treated as a harmless duplicate. |
| Cleanup encounters a new owner's identical CSS value or reused selector | It does not remove or restore the new owner's state. |
| Diagnostics are absent, corrupted, slow, or throwing | Required semantic work is unaffected within the declared resource/fault boundaries. |
| An arbitrary client forges adapter/certificate fields | Trusted operations still enforce their own authority and binding checks. |

Model-based generation should vary event ordering, duplicate deliveries,
retirement, query/context changes, failure stages, and resource incarnations. It
must distinguish a tested schedule from a proof over the unbounded state space.
Test doubles that simply return the requested progression token or always report
successful installation cannot establish the corresponding real provider or
browser premise.

Profile qualification records the actual runtime/library/configuration and relevant
implementation identities, tested properties and coverage, known limitations,
and remaining assumptions. A changed dependency is assessed against those
assumptions and requalified where applicability changes. Conformance tests are
valuable for detecting assumption violations; they are not a proof of all browser,
HTMX, renderer, or storage behavior.

*** Assembly obligations and the browser realization invariant

Before a managed affordance is served, assembly checks the declared path from
its admitted operation and observation through the projected plan, physical
handlers, target/coordinator ownership, outcome mapping, and recovery continuations.
Required handler registration and supported hook coverage are obligations, not
optional diagnostics after the application appears to start.

Static preflight need not predict dynamic facts such as target disappearance,
network delivery, future permission changes, or which transaction wins a race.
It may and must require declared handling/recovery paths for dynamic conditions
that can strand an operation. Runtime admission then establishes the premises
available at the actual boundary.

The resulting invariant is:

#+begin_quote
Every managed browser action has an admitted semantic purpose, a current owner,
and a declared physical interpretation. Its consequences are attributed to the
actual issued work and evidence. Supersession and retirement revoke obsolete
rights before cleanup is trusted. Unknown outcomes and unfinished acquisition,
installation, delivery, or recovery work remain explicit until the appropriate
evidence or declared policy resolves them. Authority remains with the trusted
boundary that owns the relevant facts.
#+end_quote
