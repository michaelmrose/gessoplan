* Purpose

The canonical Gesso r4 design is structurally strong but often reads as a dense
semantic specification before the reader has seen the concepts operate inside a
recognizable application.

The explanatory-example pass exists to make the document easier to understand,
easier to challenge, and more useful as a design probe.

The goal is not to rewrite the design, simplify away distinctions, or freeze a
public API prematurely.

The goal is to preserve the canonical normative plan while adding substantial,
integrated examples that show:

- what a concept means in a real application;
- why the distinction exists;
- what goes wrong when two concepts are conflated;
- what plausible Gesso application code could look like;
- what Gesso should derive rather than force downstream code to repeat;
- where an example reveals an API-shape problem;
- where an example reveals an actual semantic problem requiring discussion.

The examples are therefore explanatory, adversarial, and exploratory at once.

* Governing rule: explanation, not redesign

This pass does not change the canonical semantic plan merely because an example
would be easier to write under a different architecture.

The default rule is:

#+begin_quote
Preserve the normative design exactly and explicate it through examples.
#+end_quote

If an example reveals something that appears genuinely wrong, contradictory, or
unworkable in the design, stop before changing the normative text.

Record the issue, explain why the example exposes it, and discuss the proposed
semantic change first.

Only after explicit agreement should normative design text be changed.

Awkward illustrative syntax, on the other hand, is not by itself a normative
design defect. It may simply reveal an API-shape problem.

* Hard additive-transform invariant

Unless a separately discussed semantic correction is approved, every enriched
part must be a strict additive transform of its corresponding canonical source.

That means:

- every original line is preserved exactly;
- every original line remains in the same order;
- no original line is deleted;
- no original line is rewritten;
- no original line is moved;
- additions are inserted only between original lines;
- the original beginning boundary remains intact;
- the original final boundary remains intact;
- no example is appended after the original final boundary;
- no extra top-level =* Part ...= heading is introduced;
- Parts II-XII do not introduce document-wide metadata;
- Part I retains the sole document-wide metadata;
- existing =CUSTOM_ID= anchors remain unchanged;
- existing cross-part references remain valid.

The desired property is:

#+begin_quote
Any subset of the twelve enriched files may replace the corresponding canonical
source files, and the assembled Org remains the same canonical document with
only additional explanation in the replaced parts.
#+end_quote

This makes the enrichment pass incrementally installable and robust across
conversation handoffs.

* Structural validation required after every replacement

Every produced full-file replacement should be mechanically checked for:

- original-line subsequence preservation;
- unchanged original final boundary;
- valid Org heading hierarchy;
- balanced Org blocks;
- unique =CUSTOM_ID= values;
- preserved existing anchors;
- no accidental new document-wide metadata in Parts II-XII;
- Pandoc Org parse success when available.

The assistant should report the original line count, enriched line count, and
inserted-line count.

* Revised example standard

** Major examples should contain substantial code

A major example should normally contain approximately 25-80 lines of plausible
Clojure/ClojureScript or declarative Gesso code.

Some examples may exceed 80 lines when the semantic point genuinely requires a
small composition of declarations, projected behavior, runtime checks, and
recovery.

The goal is not an arbitrary line count.

The goal is that the reader should be able to see enough code to ask:

- what does the application author declare?
- what does Gesso derive?
- what does the trusted side re-establish?
- what knowledge does each participant possess?
- where does authority enter?
- how is the operation projected?
- what happens at failure or retry?
- which identities survive which transitions?
- what code would accidentally bypass the intended semantics?

Three-line toy fragments are still useful as local contrasts, but they no longer
count as the principal explanatory payload of a major section.

** Examples should resemble partial applications

Examples should be incomplete in breadth but complete enough in the semantic
slice under discussion.

A useful example may define:

- schemas;
- semantic categories;
- rules;
- public model operations;
- operation declarations;
- choreography;
- projections;
- view bindings;
- trusted-side realization;
- outcome settlement;
- progression/recovery requirements;
- browser ownership guards;
- proof/certificate dependencies.

It need not define:

- CSS;
- complete HTML;
- authentication boilerplate unrelated to the point;
- full XTDB transaction syntax;
- complete route infrastructure;
- production logging;
- every possible error;
- deployment configuration.

** The syntax is still provisional

Substantial code does not make the syntax normative.

Each part should make clear, either locally or by relying on Part I's explanatory
convention, that the code is the best current guess at a good application-facing
Gesso API.

The examples may deliberately pressure that API.

The semantic structure matters more than the exact spelling.

** Examples should include derived/projected consequences when useful

A declaration becomes much more informative when the reader can see what follows
from it.

For example:

#+begin_example
application declaration
        |
        +--> normalized semantic operation
        |
        +--> projected manager machine
        |
        +--> projected browser binding
        |
        +--> trusted-side obligation
        |
        `--> release/preflight obligation
#+end_example

When useful, show both:

- what the application author writes;
- what Gesso could derive, project, or check.

** Bad examples should be plausible

A bad example should not be intentionally ridiculous unless the point is simple
type misuse.

Prefer mistakes that a competent developer could plausibly make:

- same-shaped untrusted data substituted for an authoritative observation;
- a browser projection branching on a fact that only the server knows;
- a retry accidentally acquiring a new semantic command identity;
- a stale callback accepted because target name matches;
- a hand-written route bypassing the declared semantic operation;
- a cached certificate reused under the wrong assembly;
- an advisory notification treated as authoritative adopted state.

The best counterexamples should look like code that might appear to work.

* Integration style

Examples should be part of the argument, not boxes pasted after it.

The preferred flow is:

#+begin_example
normative concept
        |
prose introduces a concrete application situation
        |
substantial code / state / sequence example
        |
prose walks through what the code means
        |
contrast or failure case where useful
        |
prose returns to the general semantic rule
#+end_example

Small examples should normally be woven directly into prose.

Medium examples may use a descriptive lead-in.

Major examples may receive a real subheading when the example itself is a
significant conceptual unit.

Do not create repetitive headings of the form:

#+begin_example
*** Example -- ...
*** Example -- ...
*** Example -- ...
#+end_example

merely to mark every inserted illustration.

Heading structure should continue to reflect real conceptual hierarchy.

builds familiarity while the architecture is tested across different domains.

* Expanded example shape

A major example should normally have several layers.

For example, an Expense approval slice may include:

** Domain representation

#+begin_src clojure
(defschema Expense ...)
(defschema ApprovalPolicy ...)
#+end_src

** Semantic rule

#+begin_src clojure
(defrule manager-may-approve? ...)
#+end_src

** Semantic operation

#+begin_src clojure
(defoperation approve-expense ...)
#+end_src

** Choreography

#+begin_src clojure
(defchoreo submit-and-approve-expense ...)
#+end_src

** Projection

#+begin_src clojure
;; manager projection
...
#+end_src

** Failure or contrast

#+begin_src clojure
;; tempting but wrong:
;; manager browser branches on a fact it never learned
...
#+end_src

The document need not label these with literal headings every time. They are the
semantic layers the example should expose when useful.

* Example-derived design pressure

Every substantial example should be read as an API design probe.

Classify discoveries as follows.

** Explanation problem

The semantics are sound.

The prose or example is unclear.

Action:

Improve the explanation.

** API-shape problem

The semantics are sound, but ordinary downstream code must manipulate too much
framework-internal machinery.

Examples of suspicious requirements:

- manually allocate command identities;
- manually allocate execution identities;
- manually track resource-instance identities;
- repeat route/plan/wire names;
- construct proof terms directly;
- construct certificate dependency graphs manually;
- manually copy progression metadata through unrelated view code.

Action:

Do not change normative semantics.

Flag the API pressure and prefer a declaration-first sketch in which Gesso
derives the machinery.

** Semantic problem

A realistic application cannot be expressed coherently under the current
normative design, or two examples expose incompatible requirements.

Action:

Stop.

Describe the problem and discuss the semantic change before editing normative
text.

* Preferred authoring style

The examples should bias toward ordinary downstream code that expresses semantic
intent directly.

A desirable sketch often looks conceptually like:

#+begin_src clojure
(defoperation place-order
  {:actor :customer
   :requires [...]
   :does order/place
   :optimistic submitting-view
   :recover outcome-unknown})
#+end_src

rather than:

#+begin_src clojure
(with-certified-semantic-operation-context ...
  (bind-admitted-resource-instance ...
    (allocate-command-id ...
      (register-transport-correlation ...
        ...))))
#+end_src

The second form may resemble internal implementation machinery, but it is poor
evidence of a good application-facing design.

* Acceptance criteria

The example-enriched r4 is complete only when all twelve parts satisfy the
following.

** Additive compatibility

Any subset of enriched parts may replace the corresponding original parts and
the assembled document remains coherent.

** Explanatory depth

Major abstract concepts are accompanied by substantial application slices, not
only short toy snippets.

** Integrated flow

Examples are introduced, interpreted, and connected back to the surrounding
normative argument.

** Semantic fidelity

Examples do not silently alter, weaken, or strengthen normative requirements.

** API usefulness

Examples show plausible declaration-first application code and reveal where
framework internals should be derived rather than repeated downstream.

** Genericity

The example set collectively exercises:

- HumanHelp selective adoption;
- checkout/external-effect uncertainty;
- approval/role/knowledge semantics;
- reservation/race/progression behavior;
- ephemeral participant messaging;
- explicit resource ownership and retirement.

** Reviewability

A reader can distinguish:

- normative rule;
- explanatory prose;
- illustrative code;
- provisional API guess;
- intentionally bad example;
- unresolved design pressure.

** Structural validity

Every part continues to parse and compose as valid Org, and all original
canonical source lines remain intact unless a separately discussed semantic
change was explicitly approved.

* Desired final character of the document

The final document should no longer feel like a specification that occasionally
contains examples.

It should feel like a specification whose abstract claims are repeatedly forced
through recognizable application code.

The recurring rhythm should be:

#+begin_example
semantic rule
        |
real application situation
        |
substantial declaration / operation / choreography / projection
        |
concrete success and failure behavior
        |
return to the general invariant
#+end_example

The examples should make the design easier to understand and harder to fool
ourselves about.

They are not an API freeze.

They are executable thought experiments for the architecture.
