## Editorial decisions

R4's worked failed release was more than a gate table.
It showed locally plausible passes: a working abstract
Claim proof, old compiled browser bytes, claimed
server capabilities, a forged client role, fabricated
lost-command attribution, automatic reconnect
adoption, an omitted Reassign requirement, and
old unrelated formal/browser evidence. It also
illustrated the full repair path from source-owned
assembly through trusted providers, dynamic
recovery, admitted proof and real Chromium
before selected release. The original R4
called those Clojure-looking API calls
*illustrative*, not verified implementations.
Retaining them as if shipped APIs would be
an accuracy regression.

The new normative section therefore preserves the
specific P23/P24 incompatibility, absent clock
plus anonymous HTMX fallback, authority-shaped
untrusted browser input, C42 timeout/current-card
false attribution, selective remote policy,
incomplete HumanHelp operations, mismatched
certification and unsupported future-network
assumptions. It uses one explicitly schematic
EDN example rather than fictitious live API
invocations. A longer defect table adds
transaction-internal prestate, unrelated-field
frame loss, unseen writers, double primary
assignment, partial OOB, last-effect
ownership, late subscriber, dispatcher
failure, post-preflight handler replacement,
Response decision and external S2–S4
correspondence. Those are the strengthened
R5.1 contracts already independently
accepted in prior parts and gates.

The previous R5 table was useful but had no
explicit *selected release profile* or
distinct four-decision accounting. That
left room to claim a broken candidate
wasn't currently installed and thus
all physical tests were somehow passed
by being unreachable. The new version
explicitly separates statically stopped
construction from controlled eligible
runtime-fault variants and demands a
nonvacuous positive at each targeted
boundary. Part XI result classes
remain distinct from command business
outcomes: a correct rejected mutant
can pass its negative *test* without
making the rejected operation admitted
or proving its installed source path.

One already incorporated C42 cannot be
retroactively made rejected merely
because its response, publishing host
or HTML render later failed. Equally,
a prior process-local receipt cannot
authenticate every other host attempt.
The accepted repair sequence binds
original immutable command history
and current disclosure independently
from current Request state. Automatic
remote Bob adoption is forbidden even
after receipt of a genuine advisory;
a separately selected Creator-local
exception is not a broad permission.

A complete rejected release should be
explainable as actual independent
causes, not merely one catch-all
`:failed` bit. A correct
repair does not adjust a status map
to fit: it changes original source,
physical realization or
product-owner requirements and
rechecks affected dependency cones.
It cannot downgrade mandatory formal
or product requirements without
a newly declared separate release intent.

## Newly explicit faults and why they belong here

R5.1 Parts IV, VI, VII, IX, X and XI
already require the following stronger
counterexamples; including them in
the final worked release example is
preservation of the *current accepted
architecture*, not invention of
a new framework feature:

- An ordinary optimistic/read
  prestate or checked ASSERT shape
  does not establish the actual
  transaction-internal XTDB guard,
  complete RequestAssignment
  uniqueness, changed-field
  frame or every relevant writer.
  An added write after inspecting
  the pre-plan changes the
  physical footprint and must
  invalidate the claimed
  correspondence.
- A correct local build receipt
  does not prove an actual
  serving Biff listener adopted
  the checked handler, nor
  that old clients load the
  expected artifact after
  directional rolling change.
- Retired execution permission
  cannot be restored by
  fallback cleanup or a
  callback that was valid
  when first queued. Actual
  last physical mutation
  remains gated.
- Missing routing-interest
  propagation, dispatcher
  recovery and actual
  authorized acquisition
  cannot be disguised as
  a successful SSE send.
  The selected HumanHelp
  remote policy still
  requires an actual user
  Refresh.
- Product completion is
  independent of what the
  generated registry exposes:
  manager-target Reassign,
  all six lifecycle operations,
  Response choice and fourteen
  separate real positives
  cannot be silently removed.
- Independent mathematical
  S0/S1, Clojure checker S2,
  typed atoms S3 and
  current installed transfer
  S4 remain separate;
  pasted certificate/report
  identity is never current
  issue authority.

## Prospective first-gate and repair acceptance cases

The revised source table
contains twenty-four distinct
counterexample classes. The
test method for each is:
a real eligible positive
baseline; one controlled
mutant; a declared first
enforcing owner and
expected reason; observation
of the actual forbidden
physical effect with a
qualified method and
window; correct
classification of
unsupported, incomplete,
stale or unrun checks;
and repair at the original
owning source. Merely
getting an exception
elsewhere is inconclusive
for the selected gate.

A corrected candidate
must show both assembly
admission and an
independently qualified
installation and
activation path before
public release, with
the named completion
milestone passing
only when its original
requirements have
actually been met.
Failure of the full
HumanHelp product
does not erase
valid reduced Claim
or abstract proof
subjects; those
narrower subjects
are separately reported
and cannot be
used to override
the original
stronger request.

The specific postcommit
counterexample is
critical: if C42
incorporated under
a valid prior
generation but
the HTTP response
and publisher
later failed,
a repaired release
must preserve
canonical command
truth and any
unresolved notice
debt. No release
failure is an
XTDB undo.
A newer Request
state cannot
identify C42;
a new C43 is
not the same
logical retry.
Unknown outcome
remains until
qualified historical
evidence or a
selected terminal
exclusion policy
establishes it.
