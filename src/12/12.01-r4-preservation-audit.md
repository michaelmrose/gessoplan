## Editorial decision

Retain R5's best idea: develop a *single useful vertical Claim path*,
then strengthen the same source-owned objects and explicitly scoped
evidence. A roadmap is neither a strict stage queue nor a claim that
a checker-shaped fixture or a deployment-shaped report completed the
original product.

The revised opening restores essential R4 obligations that became too
implicit when R5 moved Biff substrate and host construction later in
its 18-stage navigation: no supposedly runnable integration can be
served through an unchecked listener, unsupported FX dataflow, or
unqualified protected writer. The earliest true application path
needs real source, enforcement, installed-route and browser
boundaries, even while the comprehensive future checker remains
unfinished. This is *not* a demand that all later theorems be proved
before a useful bounded pilot is built.

A stage's supported subset must be independently reconciled against
the original required product inventory, not derived solely from
whatever routes, rules, or examples the current assembler happens to
find. A successful Claim does not silently discharge HumanHelp's
Response interaction, the other lifecycle actions, or the selected
remote advisory/explicit-Refresh contract.

## Material changes and retained design freedom

The revised normative text adds: a five-way reading of delivery dependencies;
an explicit eligible, physically grounded first Claim path and adjacent
failure histories; a real Biff startup/preflight seam; the protected
original product denominator; authority, deployment, publication and
adoption duties at their earliest boundaries; separation of the four
release decisions from four completion subjects; and stronger scoped
stage-report rules.

It intentionally does **not** restore R4's old allocation of “Stage 1”
to the entire final Biff substrate or its entire old sequence. The
preferred R5 18-stage semantic order and the upcoming 12.02–12.10
stage names remain unchanged. The physical substrate requirement
is pulled forward as a prerequisite of a *claimed runnable slice*,
not a mandatory global implementation chronology. A small router
prototype, additional proof or independent formal check may be
worked on early without earning production acceptance.

The first path deliberately does not mandate a particular broker,
Rust router, global CRDT, universal proof language, database-portable
implementation, or unconditional liveness. It demands only the
selected semantics, qualified physical subjects and named residual
premises. Arbitrary Clojure remains usable behind explicit
contracts without acquiring unchecked semantic authority.

## Actual Gesso source correspondence (not a passed runtime test)

The provided `application-assurance` v1622 tar was inspected
locally for the following current evidence:

- `src/gesso/model/core.clj` exposes conventional Malli-backed
  model descriptor compilation, Graph projections, generated
  single-document operations and Biff 2 module assembly. Its own
  namespace documentation keeps complex FX/Graph workflows as
  application code on shared model primitives. This does *not*
  independently prove public HumanHelp Claim/RequestAssignment
  policy or inventory all application's physical writers.
- `src/gesso/model/command.clj` describes commands and expected
  version checks shared across generated and hand-written FX.
  Its documentation explicitly says generic version mechanics
  do *not* themselves confer authorization semantics.
- `src/gesso/live/application_preflight.clj` defines assembly
  preflight and an actual Biff handler/lifecycle integration
  path. Its documented guarantee is limited to the canonical
  startup and covered HTML response boundaries; unobserved
  deployment, arbitrary `:biff.ring/handler` replacement and
  pre-serialized bypasses remain unproved.
- `src/gesso/assurance/claim.clj` describes closed *unadmitted*
  assurance claim data and explicitly disclaims premise
  discharge. `src/gesso/assurance/report.clj` checks a
  source-bound reporting boundary, not test-runner receipts,
  theorem soundness, production authorization or deployed
  listener adoption.
- `src/gesso/choreo/semantics.cljc`,
  `src/gesso/choreo/project.cljc` and
  `src/gesso/live/browser/adapter.cljc` provide real
  semantic/projection/browser transition machinery, but their
  presence does not certify that the same complete HumanHelp
  production path is installed in a running browser.
- `bb.edn` declares JVM, formal, Node and Chromium targets.
  Named tasks and source test namespaces do not establish that
  this chat executed them or that their future applicability
  to the revised Part XII has been proven.

No JVM, XTDB, Playwright, HTMX or multi-node tests were run for
this editorial revision. The presence and source documentation of
these concrete namespaces are implementation-context evidence,
not authority to claim final stages complete.

## Positive/adversarial acceptance pairs for future implementation

| Eligible positive witness | Nearby forbidden shortcut or fault | Earliest owner and required disposition |
| --- | --- | --- |

| Real Biff handler serves an admitted route only after preflight has passed | An unverified listener or replacement handler serves the same path despite green assembly data | Installed Biff lifecycle/handler boundary must reject or explicitly name unsatisfied deployment applicability |
| Complete C42 incorporates and qualified historical command evidence resolves it after lost response | A timeout is treated as rejection, or retry silently creates C43 | Command-specific resolver retains unknown until sufficient evidence; no invented incorporation or exclusion |
| Alice's committed Create may adopt her scoped local result | Bob's remote Create or lifecycle notice automatically replaces adopted board without Refresh | Live/acquisition/browser selection gate retains advisory debt and only honors one authorized one-use Refresh |
| A real eligible Claim crosses generated plan, rendered affordance, trusted route, actual XTDB write and observed browser result | A single-document fixture or injected browser envelope passes and is reported as complete production Claim | Claim slice remains partial until original multi-document, installed-path and positive acceptance close |
| A scoped proof legitimately reuses unchanged source/premises | Changing protected adapter A44→B45 reuses obsolete physical evidence because abstract theorem stays valid | Dependency and physical installation gate requalify affected implementation without discarding unrelated valid proofs |
| A staged candidate installs exact checked assets, starts safely and accepts a useful operation | Successful build receipt conceals different loaded browser bytes or skipped Biff startup preflight | Release/installed-host verification blocks stronger claim; positive eligibility retained |
| A supported narrow profile explicitly reports unimplemented Response and distributed milestones as open | Auto-discovered operation set omits Response, turning a smaller report green | Original product and claim-denominator owner keeps mandatory missing requirement visible |
| A physical backend fault after commit preserves true incorporated status and unresolved publication debt | Failure to publish is classified as failed Claim transaction | Transaction/notice authority distinguish durable commit, outbox and delivery result |
| Early two-host experiment exposes missing interest-registration fence and informs single-node design | Prototype's successful SSE delivery is claimed as eventual all-node knowledge | Multi-node/Live owner records premises, repairs design and defers full milestone evidence |

These are proposed acceptance oracles for the finished framework,
not test results from this revision. Exact product-interface syntax
and implementation choices remain subject to their owning contracts.
