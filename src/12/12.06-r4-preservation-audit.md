## Editorial finding

The R5 architecture is retained: Live is an advisory and
authoritative-acquisition coordination mechanism, not a
separate domain database, and the ordinary application
is constructed through one source-owned admission graph.
R4's commitments are stronger than simply exposing a
fragment endpoint and a working structural checker.
The actual semantic path joins original model change,
durable notice obligation (when selected), delivery,
interest registration, protected authorized read,
coverage/progression, physical DOM install and current
participant knowledge, with each result separately
reported. A cache hit, stream event or successful HTML
return cannot silently discharge the remaining steps.

The principal R4 risk recovered here is the *silent gap*:
a subscriber or failover router can learn an interest after
a notice is processed. Neither best-effort SSE nor a
durable writer outbox alone proves later interested clients
will know that earlier committed state exists. The selected
profile needs an admitted initial observation and
registration fence, qualified replay/gap recovery, or an
explicitly weaker acquisition contract that makes the
uncertainty visible. HumanHelp's already selected remote
lifecycle policy also forbids turning such a notice into
an automatic remote board read or DOM replacement.

At application assembly, the key R4 preservation point
is the *actual deployed boundary*. Source-level admission,
a generated browser artifact and an installed handler
must be related by checked or separately observed
physical correspondence. The independent original
product capability denominator and all relevant writers
cannot be inferred from the graph's currently discovered
nodes. Dynamic handling remains structural at startup
and current at the actual invocation/render/transaction
boundary; a failed postcommit response is not a rollback.

## Actual Gesso source correspondence and boundaries

The implementation comparison used the following real
source modules from `application-assurance` v1622:

- `src/gesso/live/core.clj` is a public orchestration
  facade composing invalidation, flow, SSE, fragment
  rendering, progression, XTDB acquisition and
  optimistic UI; it does not independently establish
  a durable cross-host publication protocol.
- `src/gesso/live/invalidation.clj` expands declared
  primary changes into scopes while preserving
  original progression metadata. It explicitly does
  not inspect DB writes, infer old/new state or
  prove durable notice delivery.
- `src/gesso/live/progression.cljc` models opaque,
  orderless basis requirements and explicit
  provider-supplied progression relations. It
  validates the witness shape, not its truth.
- `src/gesso/live/fragment.clj` provides bounded
  optional singleflight/cache rendering keyed
  by caller-supplied scope/progression dimensions;
  it has no subscription interest or route authority.
- `src/gesso/live/acquisition_preflight.clj`
  checks selected Live fragment/stream route
  declarations and a source-derived invalidation
  acquisition graph. Its own documentation
  labels actual Ring/Biff routing declarations
  as trusted physical facts, not handler-body
  inspection or proof of actual dispatch.
- `src/gesso/live/oob.clj` constructs Hiccup OOB
  attributes and does not implement physical
  HTMX swap, subscription, browser authorization
  or actual DOM installation.
- `src/gesso/live/application_preflight.clj`
  assembles operation, plan, route, artifact,
  settlement, Live and acquisition relations
  and enforces a supported canonical HTML
  pre-serialization boundary. It explicitly
  does not prove that the deployed server
  adopted the checked handler, that later
  Clojure did not replace it, or that arbitrary
  pre-serialized responses are inspected.
- `src/gesso/live/application_preflight/biff.clj`
  wraps canonical Biff HTML responses with a
  current assembly/render check, but notes
  unqualified later handler substitution,
  alternate serving paths and actual host
  adoption as separate evidence subjects.
- `src/gesso/live/application_preflight/semantic_audit.clj`
  derives limited operation cards, overlaps
  and opaque conformance requirements from
  a freshly checked preflight report. It
  expressly cannot enumerate arbitrary
  model Clojure predicates/atomic guards
  and marks those source categories
  *not inspected*, rather than green/empty.
- `src/gesso/live/browser/adapter.cljc`
  maintains abstract fragment ownership,
  advisory requirements, progression and
  installation states, not true provider
  ordering or the permission of a remote
  HumanHelp board Refresh.
- `src/gesso/live/consistency/xtdb.clj` and
  `src/gesso/live/progression/http.clj`
  supply the selected XTDB/HTTP progression
  boundary, not a universal total order
  for arbitrary providers.

These are concrete implemented source paths
with bounded behavior and stated limitations.
They do not demonstrate all-node interest
fencing, strong atomic outbox delivery,
independent real installed Biff adoption,
all writer/host closure, complete policy
inspection, production product acceptance
or a universal proof. No new JVM,
Chromium, XTDB, multi-node or formal
tests were run for this editorial revision.
