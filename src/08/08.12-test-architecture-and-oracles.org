** Test architecture and oracles

HumanHelp is a proving application only if its tests exercise the real
production Request models and the actual Gesso/HTMX/Biff/XTDB realization.
The test architecture is a collection of independently meaningful
judgments, not one green build, a second hand-authored application, or an
unqualified claim that a rendered page proves a database invariant. The
accepted requirements describe the finished Gesso/HumanHelp system without treating a narrower implemented test subset as complete evidence.

*** Independent test layers and evidence owners

| Layer | What it establishes | What it cannot silently establish |
|-------+---------------------+-----------------------------------|
| Production domain and model | Request/RequestAssignment schemas, current actors and targets, Organization/Membership dependencies, exact lifecycle rules, guards and outcome classes | Real browser command construction or a fully qualified installed XTDB writer boundary |
| Projected choreography and semantic machine | Typed role-local plans, knowledge/continuations, provisional/status ownership, finite or inductive propositions with declared state/operation coverage | Correct business intent, arbitrary opaque host callbacks or actual deployed physical effects |
| Qualified XTDB/FX integration | Actual guarded Request/assignment transaction, relevant dependency/absence assertions, returned progression and persisted readback under the tested backend configuration | Every writer, unbounded concurrent schedules, genuine browser-to-command binding, or all XTDB configurations |
| Application assembly and rendered output | Real source-owned operation/route/Live/browser closure; concrete effective HTMX/native-form requests; fail-closed diagnostics | That this exact handler or JavaScript artifact was physically installed or that a protected request committed |
| Physical adapter and browser conformance | Real HTMX/SSE/DOM event behavior, effect ownership, continuity, output/swap and failure paths against admitted transitions | HumanHelp product policy or trusted current Request authorization |
| Installed host and publication | Actual Biff/Aleph startup, checked Ring handler, current asset bytes and dependency/provider lifecycle, including denied/stale startup | Correctness of all outside writers or all future rolling deployments |
| Real-browser product acceptance | A genuine logged-in user can complete required HumanHelp tasks through rendered controls and sees the correct settled, authorized result | Universal formal safety, all temporal traces or complete external-system qualification |

A useful test names the exact operation, source/application generation,
actor and target, provider/version assumptions, reachable starting
state, injected fault if any, real enforcement boundary, authoritative
postcondition and expected diagnostics. Results retain which parts
were genuinely observed, constructed, assumed or untested. The same
test should not use a private mock to produce both the behavior under
test and the supposedly independent oracle.

*** Valid fixtures and independent product requirements

Normal fixtures establish real public User, Organization, Location,
Membership, Request and RequestAssignment facts through the selected
public production model and admitted initialization path. They bind
distinct actor, requestor, helper, candidate target and manager
identities to genuine authentication/session contexts; generated
UUIDs, a crafted =:session :uid= map, or browser identity fields alone
do not demonstrate authentication. Fixtures preserve actual
progression/transaction receipts and test each authorized read at
its intended scope. Deliberately malformed database state may be
introduced only for an explicitly labeled corruption/rejection test;
it must not become the conveniently seeded positive case.

The independent product oracle requires Create, Claim, Unclaim, Mark on
the way, Complete, Cancel and Reassign, with a genuinely eligible
positive for each and meaningful negative/changed-policy cases.
Search, board sorting and terminal options, remote advisory-only
presentation, one-use explicit Refresh, selective creator-local
adoption, details/continuity, reconnect and the independently selected
response-flow behavior are separate requirements. Removing a required
capability from both the production catalog and its generated tests
does not make the product complete. Required positives must not be
satisfied only by constructing a disabled action or by a mock
executor that always reports rejection.

A test can use isolated public-model seams to investigate a narrow
Request aggregate, provided it calls the result a *seam-qualified*
test and separately tests real Organization/Membership persistence,
concurrency and disclosure at the relevant connected boundary.
One invalid foreign-model stub cannot be used to certify the entire
authenticated HumanHelp application.

*** Browser-originated Claim and lifecycle acceptance

The installed product test launches the supported generated Gesso
browser artifact, authenticates a real test principal, navigates to
the actual served =/app= page and locates the real eligible Claim
control. It clicks the control as the user would. The actual browser
runtime, not test code, constructs its protocol-v3 command, local
execution identity and HTMX request; the trusted route binds that
command to Claim and the selected Request. Production Request
model/FX commits the real guarded transition, the response carries
truthful settlement/progression, and current authoritative
acquisition and physical completion install the settled card.
A fresh reload and independent model read establish persisted
Request and primary assignment truth.

#+begin_example
Claim positive oracle:
  authenticated helper A -> served Claim(R17) control
  real browser -> semantic command C42, transport H1
  actual checked HTTP route -> public Request Claim
  qualified XTDB guards + Request/assignment writes
  authoritative outcome + permitted readback
  physically installed settled card -> page reload
  public Request/RequestAssignment query agrees with the result
#+end_example

A server unit test may deliberately manufacture a well-formed wire
command to test trusted decoding or Request routing; it cannot
be counted as this browser-originated positive. Likewise page
evaluation must not call the private lifecycle executor, inject
=__gesso_live_optimistic_command=, swap a prebuilt success body,
or silently replace the generated client with a test implementation
that already knows the expected outcome. Observation-only browser
instrumentation and controlled network faults are legitimate when
they do not supply the missing action, settlement or authority.

Every exposed lifecycle operation repeats the appropriate installed
control-to-model-to-physical-result path with the real operation
identity and necessary user input. Reassign must include a legitimate
target-helper choice and must preserve the production transition's
actual Request state and assignment history; it is not another
Claim with a different label. Unclaim returns to the model-defined
open state and ends the selected primary participation; Mark on the
way establishes =:on-the-way=; Complete and Cancel establish
=:done= and =:cancelled= respectively with their specified
assignment closure and terminal visibility. Each eligible positive
is accompanied by appropriate policy denial, malformed-binding,
stale-state and replay cases. A terminal Request cannot regain an
enabled Claim merely because its display row has no active helper.

The oracle is not "DOM contains Claimed" or "HTTP was 200":
it checks the transaction-related Request/assignment facts from a
qualified fresh read, exact current actor/target, the committed
operation's semantic outcome, authorized user-visible settlement,
absence of obsolete provisional presentation, and persistence
after reload. A response-render error after a valid commit is
not retroactive domain rejection. Unexpected page/console errors,
failed HTTP requests, missing command, absent model mutation,
unhandled asynchronous errors and mismatched artifacts fail the
scenario rather than being swallowed by the green status.

*** Deterministic concurrency, causality and negative knowledge

Two Playwright clicks at nearly the same time are a useful user
experience test, not proof that two XTDB transitions competed over
the same protected prestate. The backend test uses a controlled
barrier after both real contenders have acquired the relevant
preparation/guard snapshot and before their submitted guarded
effects become mutually ordered, under the named backend profile.
It confirms both reached the intended contested boundary and
that at most one incompatible new primary is incorporated. It
checks the losing request's actually delivered model outcome,
rather than assuming all losing transports must report a
particular HTTP code. If the barrier changes the guard mechanism
or prevents the tested real submission, its result cannot
qualify the physical concurrence claim.

An authorized manager Reassign racing target Membership revocation,
a simultaneous Complete and reassignment, and compatible/
incompatible C42 replay are separate concurrency or command tests.
Atomicity and non-partial result must be read from the actual
persisted Request and assignment set, not from an in-memory
precomputed transaction plan or the last browser card alone.

Negative assertions need a completed, causal observation window.
For example, to establish that remote R was not automatically
adopted, the test first observes R's committed authority and
that the intended already-connected B received the relevant
advisory (or qualified gap/debt). It then records B's adopted
membership and monitors the actual forbidden acquisition and
installation paths until a defined synchronization milestone.
A momentary count of zero before B receives any event cannot
show the policy was respected. A single sleep cannot exhaust
all possible late callbacks; deterministic adapter exploration
and instrumented physical events cover the specified schedules.
Claims beyond the observed window retain a liveness or fairness
premise, never an invented absence proof.

Positive outcome delivery and unknown delivery have distinct test
branches. A competing Claim with healthy confirmed transport
must produce the supported definitive delivered outcome; a
controlled lost response after submission may legitimately leave
C42 unknown. A current claimed card cannot attribute the exact
historical command. Each fault case documents precisely which
transaction outcome is observed, which is uncertain, and which
subsequent authorized command-specific recovery is permitted.

*** Lifecycle, model and command acceptance matrix

| Scenario | Independent decisive observation |
|----------+----------------------------------|
| Self-Claim | The authenticated helper, not a forged client actor, becomes the only active primary when eligible |
| Claim under competing helpers | At most one new primary survives the real guarded conflict; delivered loser status and history reflect actual evidence |
| Preparation followed by policy/Membership change | Commit-time dependency guard prevents the obsolete transition; no partial Request/assignment result |
| Helper claim on behalf of another target | Only explicitly authorized actor/target variants succeed; target identity never substitutes for principal |
| Compatible C42 replay | One incorporated command; same binding yields only the authorized historical result without a second Claim |
| Incompatible C42 reuse | Changed Request, arguments, principal or operation rejected without mutation or unauthorized historical disclosure |
| Replay after Unclaim or Reassign | Historical incorporation of C42 does not falsely describe the current primary |
| Unclaim | Eligible actor returns Request to =:open= with correct ended assignment and preserved history |
| Mark on the way | Correct =:on-the-way= state and active assignment; disallowed starting states reject |
| Complete | Model-defined permitted starting states yield =:done= and correct ended responsibilities |
| Cancel | Authorized requestor/current policy yields =:cancelled= and correct assignment closure |
| Reassign | Legitimate current target selector, policy check, ended old primary and one new primary; lifecycle status follows model |
| Changed Reassign target policy | Commit-time guard rejects stale/ineligible replacement without partial ownership change |
| Duplicate Create/lost Create response | Where the selected command profile promises it, one incorporated new Request and a permitted recovery path |
| Missing operation capability | Removing a required positive from both Choreo and model cannot make independent HumanHelp acceptance green |

*** Board, Live and presentation acceptance matrix

The selected HumanHelp policy is **remote advisory without automatic
adoption**, including changes to already-visible Requests. Remote
notifications may alert, but an unpermitted remote change does not
replace current adopted fields; explicit one-use Refresh or a
separately authorized local result is required for adoption.

| Scenario | Required user and physical outcome |
|----------+------------------------------------|
| Initial page | Genuine authenticated principal, authorized cohort/scope, meaningful defaults, correct generated asset and honest initial subscription/observation coverage |
| Create ordinary | Creator's confirmed R appears promptly; a separate already-connected viewer gets advisory/toast/Refresh signal but not auto-adoption |
| Create under excluding filter | Creator sees authorized local result/confirmation while search/options and prior adopted cohort remain unchanged |
| Remote R, then creator-local S | S is selectively adopted for the actor; remote R remains outside that actor's adopted cohort and its advisory debt persists |
| One-use Refresh | An explicit permitted click triggers one corresponding authoritative acquisition/adoption; duplicate/synthetic triggers do not acquire extra membership |
| Advisory during Refresh | A later uncovered advisory remains outstanding after earlier captured requirement returns |
| Local result races older Refresh | Old board/fragment response cannot remove or regress a newer justified card or newer local membership |
| Read succeeds but swap fails | Adoption and notification debt are not falsely cleared; visible repair remains available |
| Scope-limited/empty/error response | No invented complete absence, removed authorized rows or resolved unknown command |
| Search/options after remote advisory | Only adopted entries change local presentation; no implicit server-side collection requery or debt discharge under the selected contract |
| Newest/oldest, mine-first and unclaimed-first | Actual stable order: mine-first primary, unclaimed-first secondary, creation order then identity tie breaker |
| Terminal visibility | =:done= and =:cancelled= are hidden/shown within adopted membership without changing database state |
| Details/focus/scroll | Compatible same-identity replacement preserves declared continuity; target retirement or lost read permission cannot resurrect private DOM |
| Rapid input, stale callbacks | Later local edits and justified installations dominate stale search/option/continuity callbacks |
| Remote lifecycle change to visible R | Existing adopted R fields remain until the specified user-approved Refresh or authorized actor-specific read |
| SSE disconnect/reconnect | Lost interest/coverage is reported and recovered within the selected mechanism; reconnect never silently grants remote adoption |
| Duplicate/retired events | No duplicate protected effect, obsolete target resurrection or foreign recipient disclosure |
| Response flow | The independent response interaction product contract must be selected and passed; an unresolved decision remains an acceptance blocker |

All remote/local cases use at least two independently authenticated
browser contexts, preferably distinct principals, with independently
verified sessions, permission scopes and actual network connections.
A pair of pages sharing one mutable auth fixture is not enough.
Cross-Organization and cross-Location tests challenge both payload
disclosure and metadata/count/interest leakage. The test distinguishes
a user-local option from a server-side query change: where a
new authoritative collection query is actually required, it needs
its own authorization and scoped read/adoption permission; it
cannot be smuggled in as mere presentation search.

*** Fault, recovery and environmental qualification

| Fault or changed premise | Required evidence and safe result |
|--------------------------+-----------------------------------|
| Failure before actual submission | No new authoritative effect; typed local failure and permitted new admission |
| Submission with lost result | C42 remains unknown until exact authorized command-specific evidence; current card read alone cannot attribute C42 |
| Known commit, failed rendering/transport | Persistent transition remains; invalid output blocked and actor has qualified acquisition/recovery |
| Crash after commit before Live publish | Transaction-coupled durable publication intent or the explicitly chosen tested alternative closes the declared recovery path |
| Live delivery gap or reconnect | Interest/grant fencing, scope and basis recovery; no accidental automatic adoption |
| Result lookup denied/expired | No protected disclosure; denial/retention expiry is not evidence of rejection |
| Fragment read timeout/partial/error | No invented complete authoritative absence, and no false Refresh-debt discharge |
| Partially installed OOB/multi-target response | Per-target physical completion and repair rights; no claimed atomic multi-target adoption |
| Older network/optimistic callback | Retired E42/T1 cannot overwrite newer justified installation or restart old plan |
| Deployment A to B while client A persists | Matching assets/compatible protocol or declared reload/retirement; no mixed-generation actuation |
| Wrong installed Biff handler or receipt | No protected service with unsupported assembly; paired valid startup still succeeds |
| Membership/Organization change in flight | Proper current guards, read/disclosure revocation and usable permitted recovery |
| Unknown/extra physical writer | Coverage obligation remains open; it cannot borrow the declared operation's proof |
| Changed XTDB/HTMX/compiler qualification | Dependent proposition requalified, blocked or honestly reported unsupported, never silently left certified |

Fault injection records the exact boundary and ordering: before send,
after send/before transaction, after commit/before response, after
commit/before publication, read-success/swap-failure, owner retirement
and browser reload. It must not replace a real backend/handler with a
fake transition while claiming physical refinement. Fault-free tests
must not tolerate synthetic unknown outcomes; fault tests must not
convert unknown to rejection. Automatic retry budgets, retention
horizons, user recovery affordances and resource cleanup are
separately observed.

Unexpected console/page/network failures and unrelated non-2xx
responses fail the test. The fixture may accept an *expected* typed
fault only in the case that injected it, with exact operation/subject,
first enforcing boundary, permitted outcome and current poststate.
Blanket suppression of 4xx/5xx, all timeouts, or all exceptions
would conceal a broken product path. Negative cases pair with
a valid, eligible positive so "reject everything" cannot pass.

*** Evidence ledger, suite composition and completion

The finished HumanHelp acceptance report connects the real
production assembly, generated browser manifest/build receipt,
physically served asset, authenticated sessions, rendered controls,
browser-created commands, installed Ring route/handler, XTDB
transaction/readback evidence, actual SSE/HTMX/OOB effect events,
current adopted frontier and independent product outcomes. Each
reference has its source, version, trust boundary, observation
scope and limitations. It must not use a copy of one green
preflight result as evidence of all these independent edges.

The suite reports distinct statuses for domain/model, bounded
semantic checking, backend qualification, declared and actual
writer coverage, structural/render rejection, installed-host
adoption, real browser lifecycle, full two-client board/Refresh,
failure/reconnect, and independent response-flow requirements.
A partial pass is reported as partial. A missing positive
capability, unqualified real writer, untested physical join, or
still-unselected response-flow contract prevents full HumanHelp
product acceptance, even when every available test passes.

A future strengthened Gesso checker can produce more of the
required oracles automatically from one source-owned application,
but it cannot silently generate the independent HumanHelp
business intent or prove physical causality from unchecked
report-shaped maps. Part IX owns compositional certification;
Part X owns the proof/refinement correspondence conditions.
Section 08.13 details deterministic structural rejection,
while 08.14–08.15 join deployment evidence and final
acceptance gates. Their work remains open until demonstrated,
not declared complete by this section.
