** Connected evidence and operational limits

HumanHelp is useful as evidence for Gesso only when its real
production model, assembled semantic operation, browser command,
installed host, authoritative effects, Live advisory and adopted
presentation can be related without inventing unobserved edges.
The completed application exposes connected evidence for at least
Claim, Create with selective adoption, Reassign with genuine target
selection, and explicit one-use Refresh. It does not construct a
parallel example-owned witness registry that could agree with
itself while the running application uses different sources.

Connected evidence does not mean that one large success map,
identical operation names, a common digest or passing tests
automatically prove causality. Every link states which
source-owned relation, verified construction, qualified physical
observation, authenticated receipt, or still-open premise
supports it. The claim remains no stronger than its weakest
required, unestablished connection.

*** Claim-specific evidence and its ownership

Each end-to-end report identifies its *subject*: exact HumanHelp
source and ApplicationAssembly generation, Request/actor scope,
selected operation and assurance policy, physical runtime and
backend qualification, observation interval, and the independently
required product outcome. An audit view is derived from those
subjects; it is not a credential, an execution grant, or a
surrogate for verifying the present caller and protected effect.

| Link in the chain | Required provenance and boundary |
|-------------------+----------------------------------|
| Production source | Exact public Request/RequestAssignment operation, relevant Organization/Membership dependency declarations, owned transition and contract version |
| Admitted application | Choreo/plan, checked operation/route/acquisition construction, known missing or opaque edges, and application-generation identity |
| Actual served control | Authenticated viewer and permitted scope, concrete rendered command identity, effective action/target and inspected supported HTML form/HTMX transport |
| Browser execution | Generated/served asset identity, C42 user intention, local execution E42, transport attempt H1, target T1 and applicable resource generations |
| Trusted ingress | Actual installed Ring/Reitit handler and trusted principal, selected Request/operation, protocol/binding validation and capability providers |
| Domain incorporation | Guarded Request/assignment transition, qualified XTDB transaction evidence, exact command record where the durable profile promises it, and truthful committed/rejected/unknown outcome |
| Publication and delivery | Source-derived invalidation or transaction-coupled intent, authorized scope, publish attempt, recipient subscription/receipt or a specifically visible evidence gap |
| Acquired authority | Scoped read permission, actual basis and completeness, operation-specific observation and any qualified absence |
| Physical settlement/adoption | Issued install permission, current target/generation, actual swap/continuity completion, adopted membership and fields, and remaining Refresh/command obligations |
| Assurance conclusion | Each established proposition, evidence mechanism, physical/test scope, accepted premises, untested boundaries and current applicability |

This report is a directed, typed chain, not a chronology guessed
from log timestamp order. A browser HTTP 200 cannot authenticate
a model transaction. An XTDB readback at a later basis cannot
by itself identify which command caused its values. A matched
command-record value does not establish that every outside
writer was observed; a returned command outcome does not prove
the browser installed it. A Live publish receipt cannot prove
recipient delivery or adoption. Independent evidence must
actually join across the selected edges.

When a test or diagnostic sees only an in-process callback or
caller-reported observation, the report says so and preserves
the original trust boundary. In particular, a checked Gesso
report/fingerprint is not a transferable proof certificate,
and an observation attached to a copied Request/actor map
does not become authenticated by the map's shape. Claims
involving uninspected external writers, compiler semantics,
hidden data sources or opaque policy functions remain
conditional or open under the selected assurance policy.

Reports for developers and operators retain useful
diagnostic context but redact sessions, private Request
content, credential/command bodies and tenant-scoped
identities unless their audience is specifically authorized.
Correlators and structural fingerprints do not themselves
grant result disclosure. A principal or access-policy change
may invalidate further acquisition even when the historical
command remains incorporated.

*** Connected HumanHelp journeys

Claim establishes a positive route from a real eligible
button through browser-generated C42 and trusted route to
production Request and primary assignment incorporation.
It separately establishes permitted current reread and
a physically installed settled card after provisional
ownership retires. A lost H1 response is not negative
transaction evidence: its participant branch remains
command-outcome unknown until exact authorized historical
correlation, while a fresh Request read may independently
repair visible state.

Create/selective adoption establishes that local creator S
receives its own correlated authoritative result while
already-connected viewer B learns of remote S only as
advisory debt. If B has an earlier remote R pending and
creates its own local T, T may be adopted without R or
R's pending debt being silently consumed. The evidence
records the actual creator-specific transaction and
reread, each viewer's independent session, authorized
advisory scope, and the before/after adopted cohort.
It does not call a broadcast or toast an authoritative
card installation.

Reassign establishes legitimate distinct actor and
target-helper identities, current relevant Membership,
Organization/Location and Request guards, model-defined
ending of the previous primary assignment and creation
of exactly one new primary. It then connects the real
target selector, browser command, trusted route, transaction,
qualified readback and displayed result. An old candidate
who loses eligibility between display and commit must
not be counted as a valid successful Reassign.

Explicit Refresh establishes the one-use action/grant
that permits a scoped remote acquisition, the captured
required advisory obligations, the actual read result,
qualification of the returned progression/scope and
physical installation of the admitted projection. Only
requirements actually covered by that successfully
adopted result are discharged. A newer advisory,
uncovered scope, failed read, partial OOB installation,
obsolete response or lost permission retains its
specific obligation or justified unknown status.
No self-perpetuating successor read or passive SSE
event inherits a fresh grant merely from a previous
Refresh attempt.

#+begin_example
Positive — four connected journeys:
  Helper A clicks rendered Claim(R17) -> browser C42 / E42 / H1.
  Trusted Request model commits guarded Request+assignment.
  Actual authoritative reread and installation settle R17.
  Creator A adds S; viewer B receives advisory but not S's card.
  Manager M selects eligible target H2 and reassigns R17.
  B explicitly Refreshes; only the qualified acquired scope
    installs and only actually covered debt is discharged.
  Each edge retains its distinct source and physical witness.
#+end_example

These histories are independently testable but not one
universal serial execution. Joined claims require actual
identity, scope, predecessor/successor and temporal
relations; four individually plausible snapshots do not
automatically form a contiguous physical history.

*** Safety, uncertainty and progress are distinct claims

The following are safety properties: no double primary
assignment under the specified guarded writer set;
no unauthorized command or scope disclosure; no
anonymous lifecycle route downgrade; no unpermitted
automatic adoption; no retired E42/T1 continuation
overwriting a newer installation; no loss of uncovered
Refresh obligations through a successful-looking HTTP
response. Their evidence can be finite, conditional
inductive, runtime enforcement or bounded observed
physical behavior, but those mechanisms are named
separately.

Progress propositions have different conditions. If
Live transport is available with the declared fairness
and recovery strategy, relevant advisory may eventually
reach an interested active browser. If the authoritative
provider is available, permitted Refresh may acquire
current data. If the user never takes the explicitly
required Refresh action, a stale adopted board is
allowed indefinitely; the UI must still explain the
pending condition and expose the action. A transient
unavailable provider, denied disclosure, expired
command record or permanent network partition does
not falsify a promise whose *premises* explicitly
exclude that situation; it does prohibit claiming
unconditional eventual convergence.

A publication failure after committed Request mutation
does not reverse the mutation. The primary durable
publication profile requires transaction-coupled intent
recorded with the business transition and an
at-least-once worker/recovery protocol with stable
work identity, duplicate-safe delivery, restart,
backoff, retention and a visible escalation policy.
A simpler selected user-Refresh/periodic-reconciliation
profile makes a narrower liveness claim and tests its
actual recovery conditions. An in-memory callback,
successfully registered subscription or best-effort
postcommit push cannot claim the stronger durable
crash-to-publication guarantee.

Similarly a stable C42 identity is not guaranteed
historical exactly-once behavior unless the chosen
backend profile provides qualified atomic
command-record/domain-effect incorporation and
exact-binding replay. Current Request state and C42
historical attribution are different acquisitions.
Transport timeout, missing lookup, expired retention
and unauthorized disclosure remain unknown or
undisclosable where appropriate. A cleanup function
cannot turn that uncertainty into rejection.

*** Resource limits, backpressure and debt accounting

The installed application publishes actual resource
budgets and owners as part of its named deployment
profile rather than implying unbounded queues or
infinitely retryable work. At minimum its limits cover:

| Resource | Required capacity and overload semantics |
|----------+-------------------------------------------|
| In-flight fragment acquisitions | Per logical fragment/request-generation bound; allowed coalescing and obsolete-transport cancellation; no duplicate ungranted remote Refresh |
| Pending successor requirements | Bounded representation retaining scopes, covered/unknown knowledge and joinability of actual progression; incomparable bases cannot be ordered by timestamp or max ID |
| Advisory debt | Per-viewer/scope bounded storage or safe compaction to a coarser "updates/continuity unknown" obligation, never silent forgetting of missed distinct requirements |
| Publication intent and delivery | Queue size, worker ownership, retry/backoff, retention, failed-work escalation and durable handoff where promised |
| Command outcome recovery | Receipt/index retention, context/disclosure restrictions, retry rate/work horizon and honest expired/undeterminable result |
| Browser-owned effects | Bounded live timers, listeners, transport handles, installed optimistic generations, retained continuity snapshots and retired-but-not-yet-cancelled resources |
| Local presentation | Board cohort/page size, number of visible cards, detail/focus/scroll captures, drafts and permitted in-memory history |
| Diagnostic evidence | Bounded, redactable and access-controlled records with useful provenance retained long enough for the selected claim, not unlimited raw browser/transaction logs |

Resource limits are not solely performance goals. An
exhausted acquisition slot must not silently authorize
an extra read; an overflowing advisory queue must not
discard the only evidence of remote change; and evicting
an unresolved command receipt must not invent a known
terminal outcome. Safe coalescing may combine equivalent
obligations or use a qualified coverage join. Where
requirements cannot be safely joined, the runtime retains
a bounded coarse unknown/debt state with a permitted
full-scope repair path and visible explanation. One
queue slot bounds stored work, not the semantic number
of unfulfilled obligations it represents.

Overflow handling identifies its effect on safety,
fairness and progress. Repeated hot scopes cannot
indefinitely starve an unrelated permitted Refresh
or a queued authoritatively correlated local result
under a claimed fair profile. Dropped jobs report
their loss/unknown coverage through the designated
owner. If the selected profile has no durable queue,
the evidence must not pretend pending in-memory work
survives process restart.

#+begin_example
Adversarial — advisory overload:
  Distinct remote R1 and R2 requirements accumulate while
    viewer B is offline; the fine-grained budget fills.
  Coalescing may retain a scope-wide "possibly changed" debt
    and require explicit authorized complete Refresh.
  It may not erase R1, declare B current after R2 delivery,
    or install remote cards without an explicit grant.
#+end_example

*** Resource retirement and ownership transfer

Cleanup first *revokes semantic permission* for the old
execution, request, target, subscription, grant or
continuity slot; it then attempts physical abort,
listener removal, timer clearing, XHR/SSE release
and continuity snapshot disposal. Physical abort is
best effort. An old asynchronous callback that
arrives after cleanup cannot regain rights because
its generation has been retired, even if the browser
or network library cannot cancel it.

Release is idempotent under duplicate completion,
nested removal, aborted transport, unsuccessful
cleanup and application shutdown. Exact owners are
registered, so removing one card's interest does
not accidentally close a shared SSE connection
still serving another authorized subscriber.
Partial cleanup failure is diagnosed and bounded;
a detached DOM node or callback is not silently
treated as harmless if it retains a reachable
protected effect capability.

An uncertain C42 result, pending durable publish
intent or unfulfilled Refresh/advisory debt may
outlive its original physical card/target. Before
disposing the old owner, the runtime transfers
the still-valid semantic obligation to a declared
recovery owner (possibly an authorized server-side
index). That transfer preserves only the minimal
qualified command reference and scope; it does
not resume E42, re-grant a one-use Refresh, preserve
disallowed private content, or override a new
principal's access restrictions. Expired retention
produces an honest recovery limit.

Startup, shutdown, rolling generation replacement,
logout, permission revocation, browser navigation
and disconnect all have declared retirement and
handoff behavior. Cleanup must be testable both
after a normal successful operation and after
each partial failure path. A clean empty pending
resource map is insufficient evidence of no
leaked native listener or wrong-installed
physical target; the test checks the actual
supported shell/host resource boundary.

#+begin_example
Adversarial — late physical completion:
  E1 uses T1 and an in-flight H1; then a newer
    authoritative card installs into T2.
  Semantic retirement revokes E1/T1 installation rights.
  H1's abort fails and callback eventually completes.
  The runtime drops E1's now-unauthorized effect; it
    cannot restore T1, change T2 or clear unrelated debt.
  If C42 remains unknown, the recovery owner retains
    its qualified historical inquiry independently.
#+end_example

*** Connected fault evidence and failure attribution

The application exercises at least these ordered
negative histories against its actual boundaries:

| History | Safe conclusion and observation |
|---------+---------------------------------|
| Invalid pre-submit operation | No protected command submitted; construction/route diagnostic names the first real rejection boundary |
| Submitted C42, lost HTTP result | Historical outcome unknown to browser; no fabricated rollback or new C43 replay; authorized command-specific recovery remains |
| Commit, then response-render failure | Request/assignment truth persists; invalid output rejected; permitted reread and historical result are distinct |
| Commit, then publication crash | Durable intent replays under the selected primary profile or an explicitly weaker alternate recovery path is exercised; no false "delivered" claim |
| Advisory received but no permission to adopt | User sees pending indicator; no unauthorized remote collection acquisition/installation |
| Refresh returns partial or stale coverage | Only actually installed, qualified covered obligations discharge; newer/uncovered debt remains |
| Reassign with policy change in flight | Current guard prevents obsolete target incorporation; no partial primary-assignment transition |
| Installed T2, late E1 rollback | No stale physical restoration even if transport cancellation fails |
| Restart with old A page and new B | Incompatible effects retire or request qualified reload; old C42 may be reconciled independently under current authorization |
| Unenumerated raw XTDB writer | Physical-writer coverage remains unknown/open or fails selected admission; declared catalog cannot conceal it |

The report distinguishes "expected rejection occurred",
"no forbidden effect was observed through the
qualified mechanism", "qualified absence established",
and "not observed or still unknown". Lack of a log
line, a passing timeout assertion or a successful
build receipt is not a proof of non-execution.
A bad browser response cannot undo a previously
successful transaction. Fault injection exposes
the precise point before submission, after
submission, after commit, before publication,
during acquisition or during physical install;
it does not mock away the real effect and then
claim physical correspondence.

*** Retiring obsolete migration state and classifying defects

The final HumanHelp proving surface uses production
=net.humanhelp.site.model.*= semantics and the
single admitted example construction. It has no
parallel demo Request store, competing example
authorization state machine, alternate "visible
revision" treated as XTDB authority, duplicate
route/operation catalog, anonymous lifecycle
fallback, stale CSS producer, or compatibility
code that silently changes the supported
Choreo/Biff/HTMX contract. Legitimate
presentation-local option/draft state remains;
it is not a competing source of Request truth.

Removing obsolete files, tests and resources
happens only after the replacement path and
required positives are established. Repository
history and a short reason/replacement record
make the removal auditable without making a
temporary cleanup checklist part of the
timeless product semantics.

When HumanHelp testing discovers a problem,
the evidence identifies its ownership:
a missing reusable representation/closure
property is a *generic Gesso gap*; wrong
example routes, assets, or application
composition are *HumanHelp integration
defects*; wrong lifecycle/Organization
policy is a *production HumanHelp model
defect*; changed XTDB, HTMX, Biff,
browser or network behavior is an
*external/runtime premise failure* requiring
requalification. A generic framework rule
is introduced only when the discovered
need is reusable, not merely because the
example exposed a bug.

Completion evidence is generation- and
profile-specific. The HumanHelp app's
positive behaviors, negative enforcement,
resource bounds, durable or weaker recovery
profile, live publication, physical writer
coverage and open premises are reported
separately. Part VIII §08.15 specifies
their joint completion conditions. Parts IX
and X own the broader compositional proof
and implementation-refinement claims; their
open premises cannot be silently discharged
by a connected HumanHelp trace.
