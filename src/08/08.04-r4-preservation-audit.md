## R4 obligations preserved

1. **Scoped adoption instead of global maximum.** A newer
   card (S at P19), an earlier full cohort Q17 and pending
   remote R advisory P18 are different states. Neither
   Clojure/HTMX rendering nor an apparent higher basis
   implies complete board acquisition.
2. **Separate membership, object facts, advisory,
   provisional and local options.** One semantic owner
   coordinates them. Multiple registries or universal
   per-object revision counters are not required.
   Command and browser resource identity remain distinct.
3. **Initial baseline and no-gap interest.** Real initial
   Request/assignment/User read, scope and current
   authorization must be established before calling
   the page adopted. Subscribe/read races require
   replay/fence/reacquisition or explicit open debt.
4. **Truthful scope and counts.** Organization/Location,
   viewer, terminal coverage, bounds, temporal and
   query interpretation determine complete membership.
   Incomplete/truncated/paged/unauthorized collections
   cannot prove absence or a current global count.
5. **Presentation-only search/options.** Local live
   search, oldest/newest, mine-first, unclaimed-first
   and terminal visibility must transform the
   *already adopted* cohort. Terminal Requests belong
   to the baseline even when initially hidden.
   The response must not accidentally include
   remotely new Requests awaiting Refresh.
6. **Server-rendered alternative.** HTML/HTMX is not
   deprecated. A server may re-render from a retained
   scoped authorized cohort with principal binding,
   expiry, finite resource limits and current
   disclosure; on expiry it cannot silently query
   latest authority as if the result were local.
7. **Physical admission and continuity.** Current
   owner, fragment/card instance, original Request
   identity, acquisition and provisional execution
   are not interchangeable. Late responses and
   callbacks cannot overwrite newer justified
   cards. Successful HTTP alone is not
   completed physical DOM adoption.
8. **True disclosure.** Search indexes, count fields,
   hidden DOM metadata and display User phone/email
   may reveal information. Only permitted
   projection fields may be retained or searched;
   revocation can require redaction without
   waiting for optional Refresh.
9. **Advisory semantics.** An SSE signal is not
   adopted data or a new acquisition grant.
   Pending/advisory count is not a justified
   number of unseen Requests; “Updates
   available” is the default honest text.
   Refresh debt is discharged only by
   sufficient authorized observed installation.
10. **Positive/adversarial histories.** Twenty-one
    scenarios preserve R4's remote R/local S,
    filter/options nonadoption and refresh
    races alongside terminal, initial
    subscription, mixed reads, stale
    owner/DOM, pagination and security
    cases. Two independent browser contexts
    are required to test remote nonadoption.

## Source correspondence and identified gap

- `src/net/humanhelp/example/board.clj` is
  production-backed read composition, not
  a duplicate model. `request-rows-for-location`
  resolves Location->Organization via
  public production APIs and calls
  `request/requests-for-location` with
  `:include-terminal? true`.
  It composes RequestAssignment/User
  display and implements useful
  `visible-rows` search, terminal
  filter, sort and viewer-relative
  presentation preferences.
- `src/net/humanhelp/example/views.clj`
  `search-control` submits an HTMX GET
  and the board-options dialog submits
  another form with current options.
  `src/net/humanhelp/example/app.clj`
  `search-requests` and
  `apply-board-options` render
  response fragments using
  `board-fragments`.
- `src/net/humanhelp/example/live.clj`
  `request-list-query` uses
  `board/board-data`, which currently
  executes `request-rows-for-location`
  again. Consequently the current
  server side search/options path
  can read newly created remote
  Request membership even when
  the user has not pressed Refresh.
  The tests show valuable sort/
  filter semantics, but **do not**
  establish the required local-only
  adopted-cohort behavior. This is
  a concrete source/design
  correspondence gap requiring
  future implementation repair.
- `example.live/compiled-live` excludes
  `:created` from ordinary managed
  fragment invalidation, using
  app-owned advisory for remote
  creation, but `:updated`
  changes still invalidate
  toolbar and list. Full
  remote-lifecycle adoption
  policy is owned by 08.06
  and must be tested separately.
- `board/searchable-row-text` includes
  production Request text and display
  User names, email and phone.
  The specification requires
  viewer-specific authorization
  for each search field, including
  hidden indices and metadata;
  this is a needed audit, **not**
  a demonstrated disclosure breach.
- `test/net/humanhelp/example/board_test.clj`
  tests source presentation operations
  and authoritative Gesso Live
  observed-basis handling. The
  existing Chromium acceptance
  source tests real lifecycle
  browser commands and persisted
  effects. Neither alone
  proves P17/P18/P19 two-client
  selective board adoption.
- Gesso provides Live fragments,
  progression, browser runtime
  ownership and managed refresh
  foundations. A complete
  viewer-bound retained cohort
  and no-remote-acquisition
  guarantee must be assembled,
  proved and exercised for
  this selected HumanHelp
  policy, not assumed from
  the existence of HTMX.
