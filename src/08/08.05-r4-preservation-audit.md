## Preserved R4 normative obligations

1. **Real production Request creation.** The example owns the
   dialog and HTTP extraction; `request.core/create` and
   `request.fx/plan-create-request` own trusted authenticated
   User, operational Organization/Location, content validation,
   clock/seed, transaction and persisted Request semantics.
   Neither the form nor fixed example Location grants tenant
   or requestor authority.
2. **Mandatory FX checks before interaction.** Knowable
   missing `:biff.fx/now`, `:biff.fx/seed`, generated
   ID, transaction or public handler dependency must
   fail canonical assembly/admission before the
   user can submit a doomed Create dialog. A test
   providing fixture keys directly does not prove
   real Biff handler FX availability.
3. **Correlated authoritative creator result.** Successful
   production commit/progression can justify an
   allowed affected-Request read and visible card.
   HTTP 200, speculative row, modal closure and
   toast do not alone prove committed persistence
   or completed physical adoption.
4. **Selective scope, not an implicit all-board reread.**
   Committing S at P19 does not grant admission
   to remote R at P18. Local Request identity
   and read-your-writes are not new authority
   to query or install unrelated collection
   members. Mixed membership/card/count
   provenance remains explicit.
5. **Filtered-out local success remains visible.**
   The selected finished product has a dedicated
   accessible “Your new Request” result surface
   for S when its own search/visibility
   excludes it. The active filter stays intact;
   reveal changes only local options. If S
   is outside selected cohort bounds,
   show an appropriately scoped result
   with explicit navigation rather than
   inventing complete-board membership.
6. **Preserve pending and multiple commands.** A
   second local successful Create can replace
   the result *presentation*, not delete
   prior eligible adopted Requests or
   unresolved earlier command-recovery
   bindings. A stale target cannot
   reassert presentation rights.
7. **Distinct commit, response and notification.**
   Model incorporation does not guarantee
   rendered/received/installed creator
   HTML, nor delivery to remote subscribers.
   A postcommit render exception
   cannot rewrite committed Request
   truth as rejection; blind retry can
   duplicate logical Create without
   durable same-command resolution.
8. **Creator exclusion and advisory-only remotes.**
   Remote recipients get a separate
   non-adopting notification; no Request
   list/card is smuggled into the
   advisory. Missing creator identity
   fails closed. A fanout failure
   does not roll back Create.
   Durable intent/replay is a stronger
   necessary guarantee if the
   product claims no-gap notification.
9. **Real two-client R/S test.** Await R's
   observable advisory to Bob, retain
   his original search filter,
   verify S's visibility *before*
   filter changes, then verify R
   absent until Bob performs an
   explicitly permitted Refresh.
   A test clearing search first
   is not this acceptance case.
10. **Twenty-one positive/adversarial histories.**
    Include eligible creation, validation,
    missing FX, forged requestor,
    filtered result, out-of-scope
    result, remote R/local S, stale
    count, broad OOB response,
    response or fanout failure,
    lost delivery, duplicate C19,
    revocation and lifecycle
    ownership; positive success
    is independently required.

## HumanHelp dev source observations

- `src/net/humanhelp/example/app.clj`
  `create-request!` extracts the signed-in
  User, requires creator User ID
  before mutation, validates content
  via the production public Request
  API and executes `create-request-machine`
  calling `request.core/create`.
- `src/net/humanhelp/site/model/request/fx.clj`
  `plan-create-request` builds a real
  User-owned Request with active-user
  and Location dependencies plus
  transaction/clock/seed prerequisites.
  `src/net/humanhelp/site/model/request/core.clj`
  `create` commits the model plan
  and returns canonical Request
  and transaction `:commit/status`
  and optional `:progression`.
- `app.clj` `create-request-success-response`
  composes the committed progression
  then calls `board-fragments`.
  `views/create-request-success` returns
  toolbar/list OOB fragments and a
  "Request created" toast; the
  success message says the Request
  is now on the board.
  Those fragments execute fresh
  `board/board-data` reads. They
  demonstrate actual creator
  read-your-writes but **do not
  establish selective-only adoption**
  when remote R is pending.
- The present example also lacks
  proven distinct “Your new Request”
  result surface for a newly created
  S excluded by local search.
  A filtered-out card may be absent
  from list despite a success toast;
  this is a concrete product
  acceptance gap, not a reason
  to discard R5's superior design.
- After successfully constructing
  the creator's response, the route
  calls
  `send-new-request-advisory-best-effort!`.
  It logs fanout errors and
  preserves the constructed success
  response without inventing
  a failed commit. If rendering
  fails before this call, the
  new Request may have committed
  even though neither creator
  response nor separate advisory
  was established. The finished
  contract requires honest
  owner/recovery/notification
  classification.
- `src/net/humanhelp/example/live.clj`
  excludes `:created` from
  automatic managed fragment
  invalidation, and its
  `send-new-request-advisory!`
  requires authenticated creator
  identity and sends only
  refresh OOB/stale presentation
  plus a toast to other clients,
  never the canonical Request list.
  Delivery is app-owned
  best effort here; future
  durable interest/notification
  proof is not implied.
- `test/net/humanhelp/example/app_integration_test.clj`
  includes a real XTDB-backed
  create route case asserting
  committed progression, persisted
  Request with correct public
  Organization/Location/requestor
  and immediate HTML containing
  title/details/User projection.
  It also tests a subsequent
  real fragment reread. These
  are valuable bounded source
  cases, **not** fresh runs
  or the remote-R/local-S
  two-client acceptance.
- `test/net/humanhelp/example/chromium_acceptance.clj`
  currently documents a
  browser-generated lifecycle
  Claim/Unclaim/On-the-way/
  Complete/Cancel/Reassign
  trajectory. Its existence
  does not establish real
  Create-with-excluding-filter,
  nor two-client no-remote-adoption
  behavior. No Chrome
  run was performed here.
