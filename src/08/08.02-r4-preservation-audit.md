## Original R4 requirements preserved

1. **Production model owns truth.** Request state, independent
   RequestAssignment history, Organization/Location, User,
   Membership and public authorization/projection boundaries
   remain in `net.humanhelp.site.model.*`; the example
   and Choreo never implement substitute policy. State
   vocabulary retains `:open`, `:claimed`, `:on-the-way`,
   `:done` and `:cancelled`, not a new persisted
   `:completed` alias from display copy.
2. **Public model before distributed projection.**
   `request.choreo` calls the real `request.core` operation,
   not a copy of guard rules. Choreographic `:helper`
   is one browser participant, not a trusted actor
   or Membership role; `:request-authority`
   is a logical role, not a particular Aleph node.
3. **R4's Claim basis X17 retains its meaning.** It is
   a scoped previously observed authoritative frontier,
   not a Request revision, global state, guarantee
   of currentness or automatic stale-command rejection.
   Unrelated commits need not make Claim invalid;
   actual changed dependencies must be guarded.
4. **Complete relevant atomic dependencies.** Request
   and relevant active assignments, the scope/Location
   state, actor's current authority where required,
   target's Membership/role/skill, and exclusion/
   absence of active assignments require the
   selected physically qualified guard/assertion
   mechanism; pre-read values alone are not
   sufficient against interference.
5. **Actor and target distinct.** Basic Claim means
   claim for the current authenticated actor;
   manager-assisted Claim can select a different
   eligible helper only with the model's exact
   supervisor/admin policy. Reassign likewise
   rechecks manager and target separately.
   Browser labels, field values and roles cannot
   authenticate a principal or authorize
   either relationship.
6. **Stable command identity across attempts.**
   A command ID binds original principal, operation,
   arguments and interface; a retry at another
   web node is the same logical intent under
   that binding, not automatically a new mutation.
   A copied ID with incompatible arguments
   cannot confer another user's authority.
7. **Historical result and current state differ.**
   Replaying a previously successful Claim does
   not become rejected because a later Reassign
   changed the current card. Current protected
   result-disclosure permission is separate
   from old invocation authority. An absent
   command record without a sufficient lookup
   is not a rejection or safe reexecution.
8. **Model commit precedes participant success.**
   The Request/assignment transition can commit
   while response rendering, Live notification,
   settlement transport or browser adoption fails.
   Authoritative `:committed`, protocol
   `:confirmed` and participant
   `:accepted` are distinct layers.
   An unadopted provisional DOM card is
   not production truth.
9. **No incomplete writer-proof promotion.**
   Public Request Edit, collaborator,
   Organization/Membership and raw
   background writes may affect Claim's
   safety even if absent from the example
   browser operations. A finite abstract
   model and one real transaction fixture
   do not prove complete physical writer
   control or backend refinement.
10. **Positive and negative cases.** R4's
    actual browser Claim and concurrent
    Claim examples remain acceptance
    targets. This 08.02 revision supplies
    eighteen source/physical/binding
    histories spanning eligible Claim,
    competing claims, role revocation,
    missing-set assertion, forged actor,
    retry and disclosure, postcommit
    failure and DOM-only success.
    Section 08.03 still owns the
    complete worked browser slice.

## R5 architecture retained and extended

The R5 section already strongly distinguishes
Request aggregate truth, atomic dependency
sets, principal from selected helper,
command ID from transport/execution identity,
resolve-before-recheck behavior and four
authoritative outcome categories.

The revision adds:
- explicit Request plus separately persisted
  RequestAssignment aggregate and real
  active/ended primary/collaborator history;
- source-to-physical differences between
  `:commands`, `:guards`, `:assertions`
  and postcommit `:changes`;
- location-scoped supervisor/admin and
  target helper/skill dependencies with no
  assumed implicit role hierarchy;
- source-relative assertion/absence versus
  physical XTDB transaction evaluation,
  concurrency and unregistered writers;
- precise distinction between real model
  `:commit/status`, optimistic protocol-v3
  `:confirmed`, intended durable
  Part IV incorporation and browser
  `:accepted` / `:unknown`;
- explicit experimental status of Gesso's
  command-record construction and missing
  finished HumanHelp durable replay evidence;
- evidence-qualified historical command
  retention, disclosure, cross-node retry,
  result expiry and unknown recovery;
- eighteen positive/adversarial model and
  presentation boundary histories.

## HumanHelp `dev` implementation actually inspected

- `src/net/humanhelp/site/model/request/core.clj`
  is the stable public Request API. It
  exposes production Request and
  RequestAssignment reads, aggregate
  snapshots, guarded dependencies,
  model planners and public Create,
  Claim, Unclaim, mark-on-the-way,
  Complete, Cancel, Reassign,
  Edit/collaborator methods.
  `claim` calls `plan-claim-request`
  and `model.tx/transact!`, returning
  model `:commit/status` and, when
  available, `:progression`.
  It does **not** itself manufacture
  the choreography command ID or
  promise same-command durable replay.
- `src/net/humanhelp/site/model/request/fx.clj`
  constructs `plan-claim-request`.
  It obtains the Request aggregate
  via `require-request-snapshot-dependency`
  (request/active-assignment guards),
  an Organization/Location scope
  dependency, an effective helper
  dependency and optional exact
  manager/supervisor privilege.
  It creates one Request update and
  one primary RequestAssignment,
  and uses `assert-no-active-assignments`
  to guard the absence of other
  active assignments; semantic
  `:request` changes are provided
  for the existing Gesso Live path.
  The matching absence assertion
  matters beyond guards on records
  already present when the plan
  was prepared.
- `src/net/humanhelp/site/model/membership/core.clj`
  provides the public role/guard
  APIs, and
  `src/net/humanhelp/site/model/organization/core.clj`
  provides scope dependencies;
  Request FX calls them through
  those public boundaries.
  The manager helper checks exact
  supervisor or admin permission,
  with no generic role hierarchy.
- `src/net/humanhelp/site/model/request/choreo.clj`
  delegates to the public
  `request.core`, requires committed
  model outcome and progression,
  and produces optimistic protocol-v3
  `:confirmed` authoritative
  projections. It explicitly does
  not turn infrastructure failures
  into semantic rejection or
  treat a browser basis as an
  unconditional stale veto.
- `test/net/humanhelp/site/model/request_claim_integration_test.clj`
  contains clean XTDB-backed coverage
  for one committed Claim with an
  active primary assignment and
  a subsequent rejected independent
  second Claim with no partial
  aggregate change. The tests
  do **not** demonstrate a
  command-record-bound retry of
  the identical C42 across
  interrupted network delivery
  or multi-node contention.
  This audit inspects test source;
  it does not assert a fresh run.

## Gesso v1622 correspondence and nonclaims

- `src/gesso/model/tx.clj`
  defines canonical model plans with
  `:commands`, version `:guards`,
  XTDB `:assertions` for
  cardinality/absence, and
  `:changes` for postcommit Live
  publication. These are
  transaction mechanics, not
  HumanHelp authorization semantics.
- `src/gesso/model/command_resolution.clj`
  is explicitly **experimental**
  source for adding a typed
  command-result document to the
  same transaction plan. Its
  `incorporation-plan` and
  `reconcile` functions depend
  on authoritative record reads,
  exact binding and externally
  trusted current disclosure.
  Its declared assurance scope
  leaves domain authorization,
  record immutability, durable
  notification debt, unknown
  delivery liveness, actual XTDB
  physical correspondence and
  unbounded concurrency unproved.
  It is not installed HumanHelp
  end-to-end exactly-once recovery.
- The selected actual XTDB backend,
  assertion/runtime semantics,
  unclassified writer inventory,
  command ID retention, authenticated
  historical readback, browser
  continuity and actual deployment
  remain separate evidence/proof
  subjects under Parts IV, VII,
  IX and X. Source inspection cannot
  certify those connections.
