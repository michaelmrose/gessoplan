# R5.1 Part III — 03.10 Operation Admission and Diagnostics

**Baseline:** R4 `main` Part III “Availability is not authorization,”
“Malformed operation type versus wrong business policy,”
“A valid rule may still be inadmissible at a distributed program point,”
and “Operation declarations should remain inspectable data.”
**Candidate:** `r5.1` source unit 03.10.
**Status:** focused R4 preservation audit; not whole-Part-III acceptance,
proof of arbitrary host-Clojure type safety, or deployment certification.

## R4 obligations preserved

- Operation registration, structural choreography eligibility, current
  principal authorization and rendered affordance are distinct; none
  grants another without the applicable trusted admission.
- A syntactically/type-invalid business rule should fail where the
  checker actually supports the language; a well-typed but humanly
  mistaken policy is not inferable from ordinary type correctness.
- Intrinsically well-typed predicates can be unusable at a role-local
  program point because required facts, provenance, trust, presence
  refinement or authoritative acquisition are absent there.
- Elaborated semantic declarations remain inspectable, normalized,
  projectable, fingerprintable and diagnostic; source syntax and
  convenience macros must not secretly define a second semantics.
- Source locations and diagnostic spans can explain errors without
  becoming a different semantic identity. The compiler may not
  manufacture trusted knowledge or assertions to satisfy a checker.
- Statically established contradictions should be rejected early;
  current dynamic business-state changes require trusted runtime
  guards and outcome handling.

## R5's stronger design retained

- Valid source-level operation typing is not physical assembly,
  authenticated authority, or installed-handler correspondence.
- The knowledge model distinguishes globally available protocol values,
  role-local must-knowledge and definitely authoritative observations.
- Command-specific unknown outcomes retain reconciliation and do not
  become negative domain facts after a transport timeout.
- Evidence is scoped to its actual checker, issuer and program point,
  including unsupported language and opaque physical premises.

## Changes in 03.10

1. Clarify the difference between structural operation eligibility,
   authorization by the current model, and proof of deployed physical
   realization; missing independent evidence remains explicit.
2. Qualify the sample comparison as an *illustrative Clojure expression*:
   Gesso's current typed assurance rules use a deliberately closed AST
   with explicit readers, not an analyzer for arbitrary Clojure.
3. Strengthen the program-point rule: global availability, one
   favorable branch, or a shape-valid claimed basis does not satisfy
   definite role knowledge, refined optional presence, or actual
   authoritative observation.
4. State diagnostic source identity and reporting requirements without
   putting source locations into semantic identity.
5. Introduce seven specification-level diagnostic classes:
   invalid, unsupported, open premise, runtime required, runtime
   rejected, indeterminate and product-policy mismatch.
6. Add seven concrete acceptance cases exercising their distinctions;
   require that unsupported and indeterminate checks cannot be
   converted into positive verdicts by accidental omission.

## Current Gesso correspondence and limits

- `gesso.choreo.verify` checks structural/terminal paths,
  definite-value, role-local knowledge, required sender/receiver
  communication knowledge and definitely authoritative provenance
  within its portable core. It does not authenticate authority,
  verify optional sender fields, or prove browser execution, runtime
  ownership and liveness.
- `gesso.assurance.rule` defines a closed pure rule AST with declared
  readers, literals, boolean operations, comparisons and set membership;
  it explicitly does not type-check arbitrary host-language callbacks.
- `gesso.assurance.rule-type` checks the supported nominal scalar
  and enum types, presence/nullable refinements and short-circuit
  semantics. This makes malformed enum/numeric use rejectable in that
  *specific* admitted rule language; no product-intent proof follows.
- `gesso.assurance.proof.typed-rule-admission-correspondence` compares
  source admission with branch-sensitive independent semantics on
  three synthetic partial states; it is diagnostic, bounded evidence,
  not a universal theorem or a certificate.
- `gesso.live.application-preflight.assurance` distinguishes supplied
  surface and backbone checks from actual deployment adoption,
  dynamic HTML completeness and deliberate raw-response bypasses.
- The exact diagnostic class keywords added here are target
  specification language, not all existing public API statuses.
