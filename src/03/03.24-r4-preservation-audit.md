# R5.1 Part III — 03.24 Durable Rendezvous and Deployment Compatibility

**R4 baseline:** `main` Part III, “Durable model state is the normal
rendezvous point” and “Deployment compatibility remains explicit.”
**R5 candidate:** equivalent R5 unit, with the status example changed
from `:request/completed` to `:request/done`.
**Disposition:** focused R4 preservation and finished-system design
audit; not whole-Part-III or installed-release certification.

## Normative R4 requirements preserved

- Actors working on a long business process may rendezvous by
  authoritative model observation without direct peer communication
  or one resident server-local workflow machine.
- Durable business state is distinct from command-specific historical
  evidence and from a later actor's fresh authentication, knowledge
  and authority.
- A pending fact is not an unconditional progress guarantee. The
  application declares an eligible opportunity for discovery/action
  and its required runtime-condition and recovery behavior.
- Domain-owned leases, reassignment, cancellation and successor
  rules preserve model authority rather than being delegated to
  arbitrary browser or process-local timers.
- Domain state may outlive its producing executable plan, while
  suspended runtime execution compatibility is separately checked.
- A plan redeployment does not implicitly migrate the model's
  persisted representation or semantic meaning.

## Superior R5 treatment retained

- R5's compact status example and two separate conceptual contracts
  are preserved; the `:request/done` status remains illustrative
  and model-owned, not an invented privileged Gesso keyword.
- The target architecture does not force every cross-user workflow
  to use a durable suspended machine or global actor-routing directory.
- Section 03.23 keeps the detailed Expense command history, and
  03.22 keeps short-execution handoff and optional persisted-machine
  continuation. This section focuses on rendezvous and deployment.

## Focused improvements in 03.24

1. Require subject/workflow/command/execution identities to remain
   separate and qualify current status observation by scope, source,
   basis and disclosure rather than implying historic command attribution.
2. Clarify durable pending-work discoverability, reconnect and
   missed-advisory repair, recovery ownership, and the environmental
   premises required for liveness.
3. Keep lease/fencing and replacement worker semantics model-owned;
   an expired lease or lost notification is not definitive evidence
   of failure or non-incorporation.
4. Specify independent compatibility boundaries for domain records,
   command/outcome and recovery ledger, projected executions,
   physical client/server directions, and exact assurance evidence.
5. Define safe typed retirement/new-execution reconstruction versus
   checked continuation migration without silently creating a new
   command or retaining an old principal's capability.
6. Align directional rolling-release semantics with Part XI,
   including actual route and codec availability, offline clients
   and unsupported pairing rejection.
7. Keep domain migration as an authoritative checked writer activity,
   not a side effect of loading a new browser plan or rolling back.
8. Add twelve negative acceptance cases for lost discovery,
   borrowed authority, invented history, failover, effect uncertainty,
   obsolete plans, bidirectional rollout, sidecar drift, stale ledger,
   model migration and selective adoption.

## Current Gesso correspondence (audit only)

- `gesso.choreo.project` distinguishes recognizable incompatible
  plan formats from malformed input, but explicitly excludes semantic
  operation, wire and deployment compatibility from that narrower
  version check.
- `gesso.choreo.machine` uses that portable format check for
  executable-plan admission. Format compatibility is not a
  security/permission decision or a business-state migration.
- `gesso.choreo.artifact` keeps non-executable proof/diagnostic
  sidecars bound to exact emitted runtime plans by digest.
- `gesso.live.browser.preflight` validates a statically assembled
  browser manifest without claiming that the browser already ran
  JavaScript or installed a DOM change.
- `gesso.choreo.correspondence` supplies scoped concrete runtime
  witnesses, not a universal compatibility theorem or live rollout
  certification.
- These observations inform feasibility. The canonical 03.24 text
  remains the future, complete Gesso contract rather than a record
  of current implementation progress.

## Cross-part joins and future reconciliation

- Part I: runtime-condition/recovery, explicit property claims,
  contingent actor progress and admissible assertions.
- Parts II–IV: distinct identities, authoritative observation,
  command outcome/replay, durable work, disclosure and progression.
- 03.22–03.23: durable handoff, newly admitted short executions,
  recovered original command intent and model-owned deadlines.
- Parts V–VIII: runtime ownership, browser installation,
  HumanHelp-specific selective adoption, and application closure.
- Parts IX–X: exact artifact evidence, proof premises and physical
  correspondence. No compatible-plan label promotes an old sidecar.
- Part XI: bounded rolling pairs, direction-specific routing,
  retained command lookup after asset retirement, model migration,
  and checked rollback activation.

No substantive R4 obligation is intentionally discarded. The
canonical plan describes finished Gesso without imposing this code
snapshot as a limit on future capabilities.
