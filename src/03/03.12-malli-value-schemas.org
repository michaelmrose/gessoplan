** Malli as the value-schema substrate
:PROPERTIES:
:CUSTOM_ID: req-value-schema-boundaries
:END:

Malli provides the ordinary value-shape layer underneath choreographic
types. Its supported schemas describe data and runtime value obligations; the
model and Choreo remain the owners of business meaning, knowledge, authority,
and legal transitions. A schema reference is not a separate semantic registry
that can redefine the owning operation's contract.

A choreographic value may conceptually carry:

#+begin_src clojure
{:schema ClaimCommand
 :known-by #{:helper :request-authority}
 :agreement #{#{:helper :request-authority}}
 :provenance :communicated}
#+end_src

or:

#+begin_src clojure
{:schema RequestProjection
 :known-by #{:helper}
 :provenance :authoritative
 :basis AuthoritativeBasis}
#+end_src

These are conceptual interface sketches, not self-authenticating runtime
envelopes or necessarily literal Malli schema expressions. The schema
references and the =:known-by=, =:agreement=, =:provenance=, and =:basis=
claims have different semantic owners. Malli can check their declared shape;
trusted admission, derivation, communication, authoritative acquisition, and
agreement must establish the corresponding claims. Copying the map, adding a
tag, or passing Malli validation cannot upgrade any of them.

Malli is responsible for questions such as:

- is this a UUID?
- does this map contain the required keys?
- is this settlement one of the allowed values?
- does this intermediate machine context have the promised shape?

Malli is not responsible for questions such as:

- did this value come from a trusted actor rather than merely having a valid
  shape?
- may this helper claim this Request?
- is this Organization currently open?
- does this principal have authority?
- is this stale basis still semantically compatible with the operation?
- did communication actually establish knowledge?
- did an authoritative observation justify the actor's knowledge?
- does this branch satisfy the global choreography?

Those remain domain, FX, Choreo, or authority/progression concerns.

Runtime validators are compiled and reused for the admitted schema and
effective registry definitions whose identities they reference. Their
applicability includes the relevant schema form, registered references,
closedness and refinement options, custom predicate contracts, and target
runtime semantics when these affect validation. A stable schema name, an
unchanged source filename, or a cached compiled function is not sufficient
evidence that the same contract remains in force.

If those bindings belong to an admitted assembly generation, validator use
remains coherent with that generation. A changed schema, registry entry,
extension, or predicate realization requires an appropriately recompiled or
independently established compatible validator before relying on it. A
canonical description may name and compare known semantic dependencies; it
does not pretend that arbitrary host-language functions can be proven
equivalent by hashing their names or serializing them. JVM/CLJS or other
runtime realizations may need separately qualified predicate semantics.
Validator correspondence does not depend on a browser execution identity or
resource-instance counter.

The admitted application validates important runtime boundaries in production,
including:

- externally supplied choreography inputs;
- message payloads;
- authoritative observation/projection envelopes where they cross a runtime
  boundary;
- FX input/output boundaries;
- projected-machine state transitions;
- settlements;
- provisional/canonical protocol payloads.

The successful path uses compiled boolean validators where applicable. Rich
Malli explanations are constructed on failure or explicit diagnostic request.

These validations remain enabled in production. Optimizations based on
measurement may remove redundant work only where an equivalent check has
already been established at a trusted admission boundary and the binding,
value, schema contract, and consumer scope remain valid. No optimization may
drop a required check where untrusted or dynamic values can enter.

*** Schema-boundary acceptance cases

| Tempting shortcut | Required behavior |
|-------------------+-------------------|
| A browser sends a shape-valid principal and authoritative-basis map | Admit the shape only; authentication, observation provenance, and basis progression require their trusted semantic evidence |
| Two schema references have the same name but different registered enum sets | Use the admitted effective registry for the consuming artifact; a cached validator from the old contract cannot silently accept the new boundary |
| A custom predicate changes behavior while retaining its registered keyword | Preserve a changed or unresolved predicate-dependency premise; a matching name or hash of its name is not semantic equivalence |
| A JVM predicate is unavailable or behaves differently in CLJS | Require a supported target realization or explicit qualified premise; do not infer portable meaning from a JVM validator |
| A closed command has an extra field that later code would interpret | Reject the undeclared semantic field or apply an explicitly admitted extension contract; do not merge it into trusted machine knowledge |
| A value was validated under an old assembly but enters a different operation after deployment | Revalidate under, or establish compatible evidence for, the receiving contract; prior validation alone is not transferable authority |
| An implementation disables a required boundary validator after a benchmark | Preserve an equivalent trusted check and its applicability, or reject the optimization; speed does not discharge a runtime premise |

These are finished-system acceptance obligations. They do not claim that
plain Malli validation itself certifies source-to-runtime correspondence,
trust, or the correctness of arbitrary custom predicates.
