# R5.1 Part III — 03.01 What a Choreography Is

**Baseline:** R4 `main`, Part III introduction and opening of
“What a choreography is.” **Candidate:** `r5.1` source unit 03.01.
**Status:** focused first-unit preservation review; Part III is still
under review and no whole-part acceptance or implementation proof is claimed.

## R4 obligations retained

- A choreography is a global description of a distributed state machine with
  N roles; independent role-local machines are verified/projected from it.
- The design does not require one omniscient global runtime interpreter to
  coordinate every local step. The global machine specifies the admitted
  behaviors and provides a checking reference.
- Under stated entry, environment and realization assumptions, distributed
  executions must refine the global semantics under an explicit observation
  relation; this is not an unconditional claim about hostile browser behavior.
- The intended vocabulary includes local work, communication, branching,
  authoritative operations and observation, environment events, provisional
  state, resource ownership, failures, timeouts, settlement and convergence.
- Role-local knowledge, provisional display and authoritative state are
  distinct. Distributed actors need not change state atomically or agree on
  the whole world at every point.
- A conceptual workflow may be realized by short-lived executions
  coordinated through durable model authority, without requiring a
  permanently suspended server process.
- The R4 expense-review walkthrough that follows this introduction has
  been reorganized in the candidate into adjacent Part III units, beginning
  in 03.03. Its detailed example preservation belongs to those later audits.

## Superior R5 distinctions preserved

- Role instance, concrete actor, authenticated principal and semantic
  authority have explicit participation/admission relationships; role
  names are not credentials.
- Concurrent executions and aggregate roles must not be interpreted as one
  omniscient actor or as automatic protection of shared model invariants.
- Full-language Clojure remains supported through named semantic contracts;
  portable choreography is a coordination interface, not a replacement
  application programming language.
- Projection and runtime cooperation are distinct from trusted-side
  authoritative authorization and model enforcement.
- The semantic claim identifies supported language, observation alphabet,
  internal steps and its environmental assumptions.

## Changes in this revision

1. Specify the correspondence target as a relation between admitted global
   semantic and distributed role-local executions under the declared
   environment, delivery and fault contract.
2. Make explicit that semantic `:communicate` and sender emission are not
   equivalent; a physical send does not alone establish a matching receive
   or receiver knowledge.
3. Separate structural verification, a concrete witness replay and the
   intended all-schedules refinement/liveness obligations.
4. State that local role completion is not evidence that the participant
   knows the global authored terminal outcome.
5. Preserve independent model-guard/commit and environment/recovery
   obligations instead of implying projection serializes every concurrent
   authoritative effect or ensures eventual message delivery.

## Current Gesso implementation correspondence

- `gesso.choreo.semantics` owns an executable global machine with six
  primitive operation families and the canonical distributed observation
  alphabet; its abstract global communication differs from physical
  sender-emission and transport.
- `gesso.choreo.realization` drives independent projected role machines
  in a deterministic CLJC harness with explicitly controlled delivery,
  local/authoritative outcomes and environment events. It is not a
  network/XTDB/browser implementation or a refinement theorem.
- `gesso.choreo.correspondence` checks explicit concrete lockstep and
  weak schedule witnesses. The implementation disclaims all-schedules
  refinement, fair-transport liveness and physical trace correspondence.
- `gesso.choreo.verify` checks structural and role-local availability
  properties, not general runtime authority, browser behavior or liveness.
- Current evidence therefore supports specified bounded implementation
  and checking claims, not the unqualified end-state refinement property.
