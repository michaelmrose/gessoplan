# R5.1 Part III — 03.12 Malli Value Schemas

**Baseline:** R4 `main` Part III, “Malli as the value-schema
substrate,” under `req-value-schema-boundaries`.
**Candidate:** R5.1 source unit 03.12.
**Disposition:** focused preservation and improvement review; the
canonical text describes finished Gesso, not an implementation snapshot.

## R4 preservation conclusion

R4 and the original R5 text of this particular unit were byte-identical.
The revised design retains every R4 normative obligation in the unit:

- Malli owns ordinary value-shape validation but does not authenticate
  provenance, authorize operations, confer knowledge, decide Choreo legality,
  or establish authoritative progression.
- The conceptual ClaimCommand and RequestProjection examples continue to
  illustrate separate shape, knowledge, agreement and provenance claims.
- Validators are compiled and reused against the effective schema/registry
  contract rather than accepting obsolete cached validators.
- Input, message, observation, FX, machine, settlement and
  provisional/canonical boundaries retain production validation.
- Boolean validation stays on the common successful path and richer
  diagnostics on failure; a performance optimization cannot remove a
  required runtime premise.

## Improvements made to the finished-system specification

1. Make the existing Malli role a definite contract, without making schema
   metadata another owner for domain or choreography semantics.
2. State that the example maps are conceptual interfaces, not automatic
   authority, knowledge, or agreement certificates; no public constructor
   is implied by the illustration alone.
3. Qualify validator reuse by effective registry, referenced schemas,
   closedness/refinements, predicate semantics and target runtime when
   relevant; unchanged names are not enough.
4. Explain that unknown arbitrary host-function equivalence is an explicit
   premise, not something a source name or digest can prove.
5. Preserve required boundary validation during optimization while allowing
   equivalent trusted admission evidence to avoid redundant checks.
6. Add seven concrete negative cases for forged shape-valid claims, stale
   registry definitions, custom predicate changes, target portability,
   extra semantic fields, stale assembly validation and removed enforcement.

## Relationship to the current implementation

The inspected `gesso.choreo.type` in `gesso/application-assurance`
implements a small named Malli shape registry with compiled schema and
validator maps, fail-closed unknown schema keys, and on-demand
explanations. Its namespace documentation explicitly separates shape from
authentication, authorization, knowledge, basis ordering and refinement.
These observations inform the design, but the canonical Org text makes no
implementation-status claim.

## Cross-part and later-unit obligations

- 03.13 owns shape versus semantic certification and the default closed
  semantic payload contract; 03.14 owns diagnostic disclosure, runtime
  premise preservation and compatibility of changed schemas.
- Parts I, II, VII, IX and X own source/contract identity, evidence issuer,
  selected application assembly, rule-type elaboration, proof assumptions
  and actual physical boundary coverage.
- Every target-platform realization must identify which predicates and
  registry bindings it actually supports; unresolved custom-function
  equivalence cannot be promoted to a universal theorem.

The original `req-value-schema-boundaries` anchor survives unchanged.
No R4 normative behavior is intentionally removed. R5.1 remains the
timeless design target, not a test or implementation progress report.
