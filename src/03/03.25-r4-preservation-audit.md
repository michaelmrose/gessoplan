# R5.1 Part III — 03.25 Semantic Acceptance Obligations

**R4 baseline:** the normative obligations distributed across the
R4 `main` Part III sections (not a standalone final acceptance matrix).
**R5 baseline:** the separate final “Semantic acceptance obligations”
matrix containing eighteen cases, plus requirements for meaningful positive
acceptance and honest limitation of test evidence.
**R5.1 candidate:** revised unit 03.25.
**Disposition:** focused preservation and extension review. This is
not the independent whole-Part-III reconciliation or a claim that
current Gesso implementation passes the full future acceptance target.

## Preservation: R4 normative semantics

- Keep the source/role-local knowledge separation, mandatory sender
  knowledge, authenticated authority, legal projection, causal
  communications and no unearned global branch discriminators.
- Keep executable local runtime guards distinct from the proof/diagnostic
  explanation of those guards.
- Maintain real authoritative operations, distinct model outcomes and
  persistent cross-execution workflow meaning without pretending
  in-process state is durable business truth.
- Keep private facts subject to visibility and disclosure contracts,
  plus runtime correlation and resource-ownership rules.
- Retain the difference between finite structural reachability and
  conditional liveness, genuine projected behavior and a given trace
  witness, and exact versus compatible executable identity.

R4 had no separately titled Part III “Semantic acceptance obligations”
section. The R5 acceptance table was a design improvement and is retained.

## Superior R5 design preserved

- All eighteen original R5 case/result pairs survive verbatim.
- The independent selected assurance policy governs admitted opaque
  host-language functions. Valid actions are not rejected solely because
  their implementation cannot be proved by a closed semantic checker.
- A test result is scoped to its subject and profile, not promoted to
  a universal projection/implementation theorem.
- Rejected mutation fixtures must fail for the intended semantic
  obligation, not because of an unrelated malformed input.
- Positive viable application constructions remain essential:
  rejecting all difficult applications is not a valid certification strategy.

## Improvements made to the timeless specification

1. Bind every case to its actual semantic subject, assurance profile,
   authority/trust premises and intended claim, distinguishing admitted,
   rejected, unresolved and out-of-profile outcomes.
2. Add sixteen conformance cases reflecting learned Part III join
   obligations: forged authoritative claims, changed schema predicates,
   open-transport isolation, unauthorized message elimination,
   transport-vs-receipt, occurrence duplicate handling, causal barriers,
   advisory scope, actual physical adoption, typing sequence replay,
   durable execution handoff, Expense manager choice, historical
   command attribution, directional deployments, exact sidecar identity,
   and the limits of concrete witness evidence.
3. Specify typed coverage metadata: subject, proposition, scope,
   result, origin and evidence type. Preserve the difference between
   ordinary test, finite model check, structural checker,
   concrete witness, conditional proof and installed-realization check.
4. Require source-to-projection and converse observable-origin
   preservation under the property being claimed, rather than
   relying only on successful examples.
5. State that physical tests/assurance cover their actual registered
   handlers, routes, assets, writers and trust providers, never all
   deployment entry points by implication.
6. Add ten positive constructions for opaque managed code, locally
   equivalent branches, open extensions, replay, independent
   interleavings, authoritative acquisition, creator updates, ephemeral
   loss, fresh durable-workflow execution and diagnostic-only plan changes.
7. Keep generated assurance and validation interfaces useful to
   downstream Gesso authors without requiring them to write Quint,
   TLA+, Recife or a second verification DSL.

## Implementation correspondence (audit only)

- `gesso.choreo.verify` performs definite global-value, role-knowledge
  and authoritative-provenance flow analyses. Its own namespace
  documentation correctly limits its claims about actual authority
  authenticity, runtime owner guards and general refinement.
- `gesso.choreo.project` preserves semantic origin mappings separately
  from executable role-local plans; successful compilation itself is
  not a universal projection proof.
- `gesso.choreo.proof` owns narrow machine-checkable finite
  structural properties and explicitly distinguishes them from
  all-schedules simulation, runtime correctness and liveness.
- `gesso.choreo.correspondence` replays selected concrete/weak
  schedules against global and role-local semantics, with scoped
  witness results and observable differences.
- `gesso.choreo.realization` models independently projected machines
  with a controlled in-memory message queue and explicit drop,
  duplicate and delivery operations; this is a harness, not a
  physical network or universal refinement proof.
- `gesso.choreo.type` provides shape validation under Malli,
  not authenticated identity or authoritative truth.
- These observations inform the normative target without limiting
  the completed design or claiming present runtime conformance.

## Cross-part and acceptance joins

- All 03.01–03.24 units contribute obligations to the final matrix.
  The 03.25 matrix is not a substitute for their detailed contracts.
- Parts I, II and IV–VIII: application model ownership, command
  integrity, identity and source admission, browser adoption,
  durable handoff, and HumanHelp-specific acceptance.
- Parts IX–X: exact property/assumption provenance, formal and
  implementation correspondence, proof soundness and honest gaps.
- Parts VII and XI: whole installed assembly and accepted release
  topology, direction-specific plan compatibility, physical tests
  and owner-retirement recovery.
- Part XII: dependency-aware implementation order and completed
  system acceptance without requiring runtime artifacts to be
  the same thing as static proofs.

No R4 or R5 normative requirement in the compared scope is
intentionally discarded. This completes a focused editorial
review of all twenty-five Part III source units, but a separate
whole-part reconciliation remains required before Part III
is accepted as coherent and complete.
