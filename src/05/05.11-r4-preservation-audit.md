# R5.1 Part V — 05.11 R4 preservation and Gesso correspondence

**Baseline:** `gessoplan/main` Part V `Executable projection and
diagnostic sidecars`, especially the canonical ExecutablePlan/sidecar
separation, exact executable identity versus semantic/compatibility
identity, emitted compiler locators and packaged build relationship.
**Candidate:** `r5.1` section
`05.11-projection-and-payload-identity.org`, joining accepted
Parts I–IV and reviewed Part V 05.01–05.10.
**Disposition:** one bounded semantic review. It is neither
whole-Part-V candidate acceptance nor proof/deployment certification.

## R4 obligations preserved

- R4 keeps one canonical projected `ExecutablePlan` as the
  production runtime artifact and the *same plan* in pure and
  diagnostic/proof-enabled tests. The browser does not need an
  `AnnotatedPlan`, verification DAG or a second semantic machine.
- Compiler/sidecar products remain separate from executable
  transition meaning. Guards, successors, runtime event contracts
  and required semantic inputs belong to plan/runtime; source
  locations, derivations and proof explanations belong to
  sidecar/compiler correspondence products.
- A diagnostic sidecar is bound to the exact emitted executable
  content, not an approximate name, timestamp, state count or
  compatibility class. Runtime coordinates may legitimately
  change between compilations.
- Semantic/source identity, proof-obligation identity, runtime
  locator, exact executable identity, runtime compatibility
  and packaged artifact identity are non-interchangeable.
- R4's example sidecar/digest expressions are illustrative;
  the finished contract is reproducible, type-aware canonical
  identity and an exact build binding, not a requirement that
  printed EDN or source code stamps are sufficient proof.
- The old illustrative observer recomputed the runtime transition
  locator; the stronger reviewed 05.12 boundary retains the
  original *intent* while requiring the actual selected locator.
  Replaying guard selection is not trustworthy diagnostic evidence.
- A digest may be used for exact correspondence, but is never
  by itself an authentication credential, proof theorem,
  guarantee of semantic equivalence, or trusted client input.

## Focused improvements

1. **Exact plan versus global semantic subject.** Several distinct
   global choreographies may project to identical role-local
   executables while differing in an unprojected terminal
   proposition. Exact plan matching therefore does not
   authenticate an authored global source or its proof.
2. **Whole role-set binding.** Build/sidecar and admitted assembly
   record every intended role-to-plan binding, including
   presence/absence and assembly generation. A browser-only
   digest is insufficient when a server role changed.
3. **Dependency and implementation separation.** Normalized
   transitive semantic dependency identity from Part I,
   admitted global-to-plan correspondence, proof proposition,
   and actual host-action closure remain distinct from a
   payload digest. Rebinding opaque functions under equal
   plan bytes can invalidate assurance.
4. **Canonical encoding requirements.** The digest input
   defines a tagged, unambiguous, type-preserving,
   ordering-independent domain for supported map/set/scalar
   values, with explicit numeric and string/byte semantics.
   Unsupported scalar/host values fail rather than relying
   on arbitrary `pr-str` or stringification.
5. **Domain separation and semantic exclusions.** Distinguish
   one plan, role-keyed set, semantic subject, proof obligation
   and actual asset bytes. Excluding irrelevant source
   metadata must not exclude an executable guard, successor,
   event contract or interpretation dependency.
6. **Exact packaging chain.** Assert and check the relationship
   among admitted plan/role set, opaque implementation/runtime
   closure, emitted bundle and deployed/served browser
   entrypoint. Source stamps and copied manifests alone
   cannot bind real physical bytes.
7. **Diagnostic failure isolation.** Exact sidecar match is
   necessary for locator use but not proof of sidecar
   authenticity or checked claim status. Wrong sidecar
   disables explanation, not an otherwise admitted
   semantic execution.
8. **Five paired positive/adverse histories:** deterministic
   canonical equivalence, source/global divergence, fake
   sidecar with matching digest, compatibility versus exact
   identity, and stale shipped asset/implementation binding.

These are timeless finished-system obligations, not a
demand that every current JVM hash function already
implements a general JVM/JavaScript canonical serializer.

## Actual Gesso code and tests inspected

Gesso `michaelmrose/gesso` `application-assurance`
at `1b5e10e7` (v1622):

- `src/gesso/choreo/project.cljc` emits canonical
  current-format `ExecutablePlan` maps containing compact
  runtime locators and checks the closed plan/state shape,
  successor links and reachability. `compile-role`
  generates actual runtime-origin/semantic continuation
  correspondence for synthetic and compacted states.
- `src/gesso/choreo/artifact.clj` is explicitly JVM-side:
  it emits sibling executable and diagnostic artifacts,
  computes SHA-256 over a recursively tagged map/set/
  vector/list/seq representation rendered using
  `pr-str`, and checks the sidecar's *entire role
  set* of executable digests. This demonstrates existing
  deterministic JVM artifact identity but is not by
  itself a specified cross-host canonical-byte codec
  for every future supported value.
- The same artifact code re-projects the verified
  choreography for exact artifact correspondence
  evidence. A witness-level lockstep/weak result
  is not a universal all-schedules projection theorem.
- `src/gesso/assurance/subject.clj` separately
  defines a typed/versioned canonical digest for a
  bounded declarative semantic *subject*, explicitly
  marked structural and unadmitted. Its identity
  differs in domain from the executable-plan digest.
- `test/gesso/choreo/artifact_test.clj`
  includes `executable-digests-bind-only-the-exact-runtime-artifact`,
  `sidecar-is-bound-to-every-emitted-executable-plan`,
  and
  `identical-executable-plans-cannot-hide-different-global-terminal-semantics`.
  The latter directly demonstrates why plan digest equality
  alone is insufficient for source/global-terminal claims.
- `test/gesso/choreo/project_test.cljc` covers
  deterministic compact locators, map insertion order,
  generated runtime origins, collapsed receive
  alternatives and exact compiler provenance.
  These are source-inspected tests, not results
  produced by executing the suite in this pass.

**No Gesso code was edited. No JVM/Node/Chromium/XTDB,
Python assembler, deployment or formal proof tests were
executed during this documentation revision.** Existing
source-derived evidence does not certify loaded bundle
bytes, every opaque implementation, all compiler/runtime
platforms or an independently proved general refinement.

## Cross-part residual obligations

- **Part I:** keep normalized semantic dependency
  identity, assumption scope and claim proposition
  distinct from literal plan/content identity.
- **Part III / 05.12:** preserve source-to-compact
  compiler mapping, actual role-local branch
  knowledge and selected transition locator;
  a sidecar must never rerun guards to guess it.
- **Part IV:** a command-result reference and
  actual adopted observation remain independently
  bound; the plan digest is not authorization or
  physical installation evidence.
- **Part VII:** include exact role/action/runtime/asset
  inventory and every served entrypoint in
  installation-correspondence closure, with
  re-admission on relevant deployment changes.
- **Part VIII:** actual HumanHelp Claim/Reassign
  capability and RequestAssignment semantics
  are not certified by a matching browser plan.
- **Parts IX–X:** checker issuer, evidence applicability,
  exact semantic/implementation subject, premises,
  weak/lockstep witness scope and kernel soundness
  remain separate certification obligations.
