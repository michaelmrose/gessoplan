# R5.1 Part V — 05.01 R4 preservation and implementation correspondence

**Baseline:** `gessoplan/main`, R4 Part V, especially its opening
Optimism requirements and subsequent `Optimism is typed provisional
knowledge`, `Provisional state cannot confer authority`, `Settlement
and authoritative observation are complementary`, and resource /
no-silent-downgrade examples.
**Candidate:** reviewed `r5.1` 05.01, retaining the stronger R5
foundational architecture.
**Disposition:** one focused substantive section review. This is not
whole-Part-V acceptance, runtime certification, or a machine proof.

## R4 preservation and intentional supersession

- R4 requires optimism to be part of semantic choreography, not an
  untracked DOM trick. A provisional projection carries a command,
  admitted observed premises, owner and a declared terminal/recovery
  contract; it never forecasts a guaranteed XTDB result.
- R4 distinguishes authoritative observation, provisional local state,
  qualified authoritative absence, and unknown/unavailable evidence.
  Matching map shapes and browser fields do not supply trusted admission.
- R4's Claim example preserves separate command C42, execution E42 and
  owned physical resource identities. Later settlement and authorized
  reread can resolve different knowledge questions.
- R4 explicitly rejects provisional authorization, silent ordinary-HTMX
  downgrade, invented terminal rejection, and expired owner callbacks.
  The substantive detailed paths remain distributed across R5.1
  05.02–05.03, Part IV and Part VI rather than copied wholesale here.
- R4's universal wording about a pre-existing authoritative basis
  does not force the new R5 design to demand an existing entity card
  for an optimistic *create*. Its admissible collection/policy
  observation, local draft and temporary identity are legitimate
  premises without a false nonexistent-row witness.
- R4's older `:request/helper-id` optimistic example describes
  visual tentative help but does not redefine HumanHelp's production
  `RequestAssignment` model. R5.1's separation of view-level
  `:display-helper-id` from domain status is retained and clarified.

## Changes in 05.01

1. **Separate three knowledge/effect dimensions.** The source now states
   explicitly that semantic observation, command disposition and
   installation/adoption are not interchangeable. A provisional DOM
   installation is local presentation, not committed Claim or an
   authoritative adopted progression. Conversely a valid command result
   can precede the current card's acquisition or physical installation.
2. **Constrain derived protected information.** Local drafts can display
   the author's inputs without proving entity existence, collection
   membership or third-party visibility. A mixed-source derivation must
   preserve the exact authorized scope and provenance of each premise.
3. **Reject helper-label authority.** Clarified that the schematic
   optimistic `:display-helper-id` is not a persisted primary
   `RequestAssignment` or a transaction-current eligibility guard.
4. **Add paired positive/adverse histories.** Checked conceptual cases
   cover genuine admitted Claim versus copied observation markers,
   legitimate create preview versus fabricated entity uniqueness, and
   admitted C42 success versus premature provisional-to-authoritative
   DOM promotion. Each case names what would establish the stronger
   conclusion and what must remain unestablished.

## Accepted R5 improvements retained

- The complete host language remains available through checked/declared
  contracts, including opaque callback assumptions without pretending
  everything is a closed formal DSL.
- Provisional presentation is an admitted local derivation while a
  command is unresolved, *not* a counterfeit authoritative state
  assembled under a `:request/status :claiming` domain enum.
- Different admission evidence may support optimistic creation,
  model-projected data and user drafts; not every operation must have
  one previously existing Request observation or one universal basis.
- The eight-entry derivation contract includes source inputs, scopes,
  owner/resource identity, local concurrency, settlement/retirement
  and physical adoption, without requiring application authors to
  maintain a second command authority registry.

## Gesso source and tests actually inspected

Gesso `application-assurance` at `1b5e10e7` (v1622):

- `src/gesso/live/browser/adapter.cljc` is a pure portable
  `AdapterState × NormalizedEvent -> AdapterState × AbstractEffects`
  core with owned optimistic effects and separate authoritative swap
  decisions; it does not itself execute DOM or XTDB effects.
- `src/gesso/live/browser/optimistic.cljs` documents that semantic
  settlement does not upgrade provisional DOM. Its `:await-authority`
  and `:authoritative` terminal effects leave any still-provisional
  marker intact pending the distinct canonical Live/HTMX path.
- `src/gesso/live/browser/observation.cljc` separately classifies
  `:provisional-presentation` versus `:authoritative-view-installation`.
  Its observed transition is not itself XTDB commit evidence.
- `test/gesso/live/browser/optimistic_test.cljs` includes
  `confirmed-settlement-cancels-timeout-and-awaits-authority-test`,
  which expects the DOM to remain explicitly marked provisional after
  semantic confirmation, and
  `provisional-render-failure-does-not-fabricate-command-failure-test`.
  These are source-inspected tests; **they were not run in this pass**.

This provides concrete implementation precedent for the normative
separations. It does **not** establish general browser-host
correspondence, current Membership/Organization authorization, all
source-to-XTDB transition refinement, real positive HumanHelp product
completion, or the stated formal checker guarantees.
