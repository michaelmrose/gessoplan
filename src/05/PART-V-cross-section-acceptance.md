# R5.1 Part V — independent whole-part candidate acceptance

**Baseline:** Gessoplan `main`, Part V (3,105 newline-split lines),
with R5 `r5` Part V (1,392 lines) as the preferred architecture.
**Reviewed candidate:** Gessoplan `r5.1`, thirteen numbered Part V
Org units, their thirteen R4-preservation/Gesso-correspondence audits,
the assembled 2,361-line publication, and the separate
`05-whole-part-reconciliation.md`.
**Disposition:** **ACCEPT Part V as the reviewed R5.1 candidate
"Provisional State and Executable Presentation"**, conditional on
the explicit cross-part obligations below. No blocking internal
normative contradiction was identified after the reviewed corrections.
This is an editorial design-document judgment, **not** proof of the
finished framework, a Gesso v1622 implementation certificate, a
HumanHelp production acceptance, or approval of all twelve parts.

|----------------|-------------------|---------------------------------------|

These are joined *normative* decisions about the finished framework. Each
requires its own physical, source or proof evidence before declaring a
particular application implementation conformant. In particular, a command
may incorporate without its card installing, a current card may install
while the earlier command's attribution remains unknown, and one actor
may retain remote R as advisory while showing a newer correlated local S.

The independent review considered all thirteen sectional
`05.xx-r4-preservation-audit.md` records and the distinct whole-part
reconciliation. All seven original R4 Part V `CUSTOM_ID` anchors
survive the published candidate:

- `part-05-provisional-state-and-executable-presentation`
- `req-optimistic-projection`
- `req-provisional-resolution`
- `req-continuity-boundary`
- `req-view-operation-binding`
- `req-portable-execution`
- `req-executable-plan-sidecar-boundary`

The audits preserve R4's provisional knowledge, settlement,
restoration, concurrent-resource ownership, continuity, portable
execution, nonauthoritative sidecars and physical/build correspondence.
R5's stronger single executable semantic plan, full-language Clojure
construction and evidence-scoped operation model remain preferred.
Older verbose example functions and simplified one-field helper/Claim
sketches have been deliberately superseded by qualified
RequestAssignment, actor, operation and physical ownership contracts;
they are not silently omitted requirements.

This is a substantive editorial preservation judgment, not a
mechanical proof of R4/R5/R5.1 semantic equivalence. Anchor and line
counts alone cannot establish the judgment.

## Cross-part and implementation obligations retained

- **Parts I–IV:** retain independent product intent, the public model's
  business-rule authority, principal/actor/role knowledge, protected
  RequestAssignment/current authorization, exact command attribution,
  trusted observation scope, durable publication/recovery and acquired
  versus actually adopted evidence. Earlier accepted candidates remain
  reopenable if a later concrete counterexample requires it.
- **Part VI:** define and qualify real HTMX/browser effect identity,
  completion, post-swap DOM truth, stale timer/Promise/callback rights,
  multi-target partial application, cleanup and continuity. In the
  inspected Gesso v1622 `release-height-lock!`, checking only whether
  the CSS value equals the earlier applied value does not distinguish
  a newer owner writing *that same value*. The finished design's
  owner-relative protection remains an implementation/physical
  correspondence obligation, not a reason to weaken its specification.
- **Part VII:** cover the actual assembled application, authorized
  source reads/disclosure, rendered dynamic paths, Biff/Ring handlers,
  workers/FX/write ingress, protected routes, browser plan/runtime and
  actual built/served entrypoints. A successful canonical wrapper test
  alone does not prove every unexamined or subsequently changed entry
  path closed.
- **Part VIII:** independently establish the complete production
  HumanHelp acceptance catalog, including positive eligible
  Create/Claim/Unclaim/lifecycle/Reassign, local/remote board behavior,
  one-Refresh adoption, accessible continuity and failure recovery.
  The meaning of the separately required response flow is a product
  selection to be made explicitly, not inferred from an existing button.
- **Parts IX–X:** keep actual proof subject, checker/kernel assumptions,
  finite versus unbounded claims, implementation refinement, backend
  isolation/transaction causality, completeness of evidence and
  meaningful counterexamples distinct. A plan digest, pinned readback,
  structural report or finite trace is not a universal theorem.
- **Parts XI–XII:** preserve deployed asset/version/semantic-compatibility
  closure, schema migration, release gates, physical multi-node
  invalidation/recovery and dependency-ordered completion. Multi-node
  must realize the same application semantics as single-node; no
  unqualified routing algorithm is prescribed as a theorem.
- **Liveness, resource and trust premises:** qualify progress under
  declared fairness, user action, provider availability, retention,
  backpressure, permitted disclosure and actual host/transport behavior.
  No opaque same-process observer is magically isolated merely because
  its diagnostic return value is discarded.

These are separately owned assurance, future implementation, product,
deployment or cross-part duties. Their existence does not make a
timeless *target-system* requirement invalid or convert this
editorial acceptance into implementation certification.
