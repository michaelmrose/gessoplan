## Preserved R4 requirements and R5 improvements

- **Scoped data versus visible adoption:** the actual authorized observation
  may have entity/card or whole-query coverage. R4 forbids upgrading one
  scoped result to complete aggregate adoption, and distinguishes acquisition
  from actual installation and satisfaction of adoption-stage obligations.
  R5 supplies a more precise permit/effect-stage model; this revision retains
  both without introducing a universal per-object revision number.
- **Independent newer evidence survives:** a complete board observation
  may coexist with separately newer Request-card state. A permitted
  scoped merge must retain that provenance, not fabricate a common snapshot
  or discard the newer card. Unsupported combinations require
  rejection, reacquisition or declared recovery.
- **Physical failure is not authority reversal:** rendering failures,
  partial DOM mutations or optional continuity failure cannot turn an
  incorporated domain command into rejection or authorize stale rollback.
  A coherent but incomplete view retains explicit installation/repair debt.
- **Current physical permit at last actuation:** R4's E1/E2 counterexample
  requires preventing an obsolete queued mutation, not merely rejecting
  its later callback. The permit belongs to an exact owner, effect
  instance, target incarnation and prepared representation, with
  serialization/reentrancy obligations.
- **Retained advisory/Refresh obligations:** a read may satisfy only the
  obligations actually covered at their required discharge stage.
  An advisory arriving while the read is in flight survives if uncovered.
  One explicit Refresh grant remains one declared read budget, not
  implicit authorization for unlimited successor reads.
- **Real physical completion and cleanup:** completed installation is
  a distinct source/host claim with exact per-target postconditions;
  resource retirement and later cleanup cannot usurp the successor
  owner, even for identical physical property values.

The preferred R5 source remains the architectural basis. Older R4
listener diagrams and illustrative DOM function APIs are not revived
as another runtime semantic interpreter. The stronger target-system
contracts are timeless, not assertions that all Gesso code already
implements them.

## Focused improvements to 06.05

1. Extended the stage table to distinguish grant/request, acquired
   observation, prepared representation, issued permit, reserved
   actuation, actual physical completion and qualified semantic adoption,
   with explicit propositions *not* established at each stage.
2. Bound permits to the installed assembly/profile, source/cohort,
   current authority context, effect/owner generation, exact
   prepared representation and permitted target/OOB mutation footprint.
   No copied browser map or digest mints those rights or server authority.
3. Specified last-actuation checks and the permitted host reservation/
   reentrancy behavior, including a separately controlled HTMX secondary
   effect and B1/B2 incarnation reuse at an identical selector.
4. Made real, correlated per-target physical postconditions and loss of
   completion evidence first-class, with no universal inference from
   HTTP 200, decoded HTML or an unqualified afterSwap callback.
5. Required explicit completed/failed/pending/indeterminate results
   and repair for partial multi-target writes; rejected imaginary
   physical atomicity and inconsistent enabled managed affordances.
6. Distinguished optional continuity faults from failed mandatory
   preparation, preserving successful authoritative installation
   and exact-owner cleanup even under same-value CSS ownership races.
7. Joined Part IV progression/coverage, Part V continuity/optimism,
   and one-Refresh scoped advisory rules without claiming a mixed
   R/S view came from one coherent backend snapshot.
8. Added seven paired positive/adverse histories demanding real
   source and physical witness paths rather than success-shaped maps.

## Actual Gesso v1622 source consulted

Inspected the user-provided Gesso application-assurance archive at
commit 1b5e10e71c00e7784b019dee7dc1198a96fd03f6.

- In src/gesso/live/browser/adapter.cljc, before-swap checks a current
  fragment request/generation and a structurally valid authoritative
  candidate with scope, basis and optional exact progression witness.
  A nonmatching progression relation cancels that swap. This is a
  scoped adapter precursor, not an attested general progression-provider
  comparison or signed trusted observation.
- The same adapter's after-swap path, for a still-current fragment,
  records the candidate's scope/basis in the local :authoritative map
  and emits an :authoritative/installed *observer* effect. Its input
  event contains fragment ID, request generation and request ID.
  The source-level transition does not independently check arbitrary
  DOM target contents, OOB effects, mixed cohort membership or a
  general per-target physical postcondition at that step.
- src/gesso/live/browser/core.cljs binds beforeSwap and afterSwap
  to an active managed physical HTMX request and dispatches the
  normalized correlated event. That establishes meaningful host
  correlation for the selected integration; a documented callback
  alone does not certify every possible host mutation path.
- src/gesso/live/browser/shell.cljs explicitly treats
  :authoritative/installed as an observer effect, stores next
  semantic state before running effects, and keeps owned
  continuity resources separate from semantic admission. It
  does not by itself establish arbitrary multi-target atomicity.
- Source-inspected tests in
  test/gesso/live/browser/adapter_test.cljc include
  first-authoritative-basis-installs-without-ordering-assumption-test,
  distinct-authoritative-basis-requires-exact-progression-witness-test,
  malformed-authoritative-candidate-fails-closed-test,
  accepted-before-swap-captures-continuity-once-test, and
  stale-after-request-cannot-retire-newer-request-generation-test.
  test/gesso/live/browser/shell_test.cljs includes
  newer-fragment-swap-revokes-old-physical-resource-before-allowing-new-swap-test
  and duplicate-before-swap-does-not-revoke-current-physical-resource-test.
  These are test *sources* inspected, not executed in this revision.

This is concrete evidence of existing generation checks, scoped basis
handling, HTMX correlation and physical continuity-owner discipline.
It does not certify complete real browser postconditions, partial
OOB behavior, current RequestAssignment model policy, independent
positive HumanHelp product acceptance, all installed application
entrypoints, or universal proof of physical host refinement.

- **06.06–06.07:** fragment coordinator ownership, bounded logical
  cycles, retained incomparable advisory debt, authorization for
  acquisitions, applied query identity and one explicitly granted
  Refresh need an independently checked end-to-end history.

  must enforce the exact permit and postcondition relationships here.

  acquired-versus-adopted evidence, provisional status and local
  continuity remain distinct. A whole-board adoption cannot
  regress a separately newer adopted creator-local card.

  eligible production Create/Claim/Reassign/Refresh interactions
  need physical evidence, including multi-target and failure cases.

  bounded tests, hardware/browser/HTMX premises and implementation
  refinement. An emitted permit map is not an application certificate.
