## R4 preservation and intentional supersession

- **Separate command, execution and transport identity:** the R4
  worked Claim example distinguishes C42 from E42 and the physical
  H1 transport resource. The revised section retains that contract
  and also requires explicit binding of the current source, owner,
  effect issuance, target incarnation and deployment where needed.
  It does not resurrect R4's illustrative state-map or pretend that
  a particular emitted example is today's public Clojure API.
- **Correlation is established, not rediscovered:** R4 requires
  opaque installed identities for timers, transport and continuity
  rather than DOM ancestry or current globals. The revised section
  also requires allocating authority, namespace and lifetime to
  prevent ABA/reused-selector errors.
- **Semantic owner uniqueness and ordering:** the adapter owns
  coordination while projected execution owns role-local state,
  without conflicting shell/listener state machines. The state
  transition and issuance must precede physical effects, including
  callbacks that complete synchronously. A reentrant outer
  dispatch cannot overwrite the inner state.
- **Veto before irreversible work:** R4's documented HTMX gate
  must be genuinely synchronous and effective at the selected
  supported lifecycle point. The revised text makes source/permit
  failure a physical fail-closed requirement rather than an
  optimistic assumption about event names.
- **Stale effects versus stale callbacks:** R4 explicitly bars
  an expired effect from mutating the physical target even when
  its eventual callback would be rejected. The revised section
  makes a last-actuation check distinct from callback admission,
  preserves cleanup rights only for the correct old resource, and
  classifies partial physical actions.
- **Private versus shared work:** command/attempt/execution
  resources remain private, while scoped authoritative Live
  invalidations and retained Refresh obligations follow their
  separately declared fragment/coordinator protocol.
- **Hostile browser and trusted server:** a browser-supplied command,
  actor, plan or authority-context reference is never enough to
  authorize the actual Request/RequestAssignment operation.

R5's more precise identity vocabulary, one executable semantic
interpretation, pending-effect records, synchronous gates and
future-compatible plan boundaries remain the preferred architecture.
A R4 diagram is not copied into a second executable interpreter.
The new 06.02 adds lifecycle precision without taking over the
HTMX response, physical installation or durable command-resolution
subjects owned by other sections.

## Focused improvements

1. Defined each identity's allocation/namespace, owner/lifetime,
   expected source, comparison and retirement obligations. Equal
   strings, selectors or recycled counters do not establish
   equal *incarnations*. Separate identity values need not always
   be separate UUIDs when a stronger alias contract exists.
2. Distinguished command preservation across attempts from
   execution-private callback rights. Unknown H1 delivery cannot
   be treated as C42 rejection or H2 completion; historical
   command resolution needs qualified current attribution.
3. Required an effect-level current issuance and last-controllable
   actuation gate, particularly when a callback starts E43 before
   the outer E42 effect batch finishes. Cancellation and stale
   callback filtering alone do not prevent the prior bad act.
4. Preserved reentrant state-first dispatch and required a genuine
   linearization contract where concurrent entrypoints can mutate
   the same semantic owner.
5. Required physical fail-closed behavior at documented synchronous
   HTMX hooks. Exceptions, unavailable knowledge or unsupported
   profiles cannot silently allow the send/swap. A later async
   decision cannot undo an already irreversible mutation.
6. Distinguished legitimate shared invalidations from stale
   execution-private callbacks and kept local presentation,
   subscription and advisory debt separately owned.
7. Qualified diagnostics, resource-budget premises, partially
   completed physical effects, and deployment/recovery identity.
8. Added six paired eligible/adverse histories with independent
   expected classification; they are not satisfied merely by a
   self-described event map.

## Inspected Gesso implementation and evidence limits

Inspected the supplied Gesso `application-assurance` v1622
source snapshot, commit
`1b5e10e71c00e7784b019dee7dc1198a96fd03f6`:

- `src/gesso/live/browser/adapter.cljc` defines a closed event-key
  vocabulary, execution generations, effect generations, separate
  `:timer/fired`, `:transport/succeeded` and
  `:htmx/before-request`/`:htmx/before-swap` event shapes.
  `current-execution-or-ignore` distinguishes missing/retired
  from stale generations; fragment requests use their own
  `request-generation` and `request-id`.
- `src/gesso/live/browser/shell.cljs` commits `next-state`
  before interpreting effects, allowing synchronous callback
  reentry to see committed state. Its synchronous-required
  effects include HTMX cancellation, fragment refresh and
  continuity capture, with separate optional observer handling.
  This does not alone demonstrate that *every* effect in a
  reentrant batch validates a still-current permit immediately
  before an arbitrary subsequent DOM mutation.
- `src/gesso/live/browser/core.cljs` binds a physical request
  ID during `on-before-request!` and uses the corresponding
  active correlation for `on-before-swap!`. Both handlers
  catch exceptions and call the physical event cancellation
  hook before rethrowing. This is meaningful fail-closed
  source evidence under its supported host profile, not proof
  that all HTMX modes, OOB targets or future extensions are
  protected by the same hook.
- Source-inspected tests include
  `synchronous-local-completion-reenters-after-transition-state-is-installed-test`,
  `stale-before-request-is-cancelled-by-physical-handler-without-shell-semantic-guessing-test`,
  `stale-transport-success-cannot-complete-a-retried-send-test`,
  `stale-request-generation-is-cancelled-before-htmx-work-test`,
  and `later-htmx-phases-require-a-request-id-previously-accepted-by-before-request-test`.
  These names and fixture assertions were inspected in source;
  the tests were not run in this revision.

Current v1622 source therefore supports the one-state-owner and
generation-aware approach, but does **not** by source inspection
certify all deferred effect mutators, cross-deployment resume,
HTMX host lifecycle variations, browser physical completion,
trusted RequestAssignment policy or a general proof of all
executions.

## Later obligations and handoff

- **06.03–06.04:** reconcile actual HTMX request/send, response/OOB,
  protected Claim, target-instance and browser FFI paths against
  last-controllable mutation boundaries. Different HTMX
  profiles may require different, explicitly admitted gates.
- **06.05–06.07:** prove qualified physical installation and
  per-scope adopted knowledge, one user Refresh, retained
  advisory debt and initial interest/acquisition recovery.
- **06.08–06.11:** verify deployment/plan compatibility, revived
  command but retired physical continuation, managed effect
  issuance, stale/duplicate async admission, resource cleanup
  and reentrant effect-batch behavior.
- **Parts IV–V:** retain current trusted RequestAssignment
  authorization, historical command attribution, provisional
  presentation and owner-relative continuity as distinct subjects.
- **Parts VII–X:** prove/qualify actual installed route, worker,
  browser asset and writer closure, real HumanHelp eligible
  Create/Claim/Reassign/Refresh behavior, source correspondence
  and formal assurance assumptions. The local adapter step is
  not a certificate for those systems.
