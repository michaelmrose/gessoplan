** Rendered affordances and concrete response closure

*** Minimal semantic intent in views

The view selects an admitted operation, supplies concrete arguments and required
observations, and chooses presentation/availability. Prepared bindings from Part
V derive the plan, transport, encoding, and other realization details from the
assembly. A view should not manually copy browser registries, authority roles,
command envelope formats, or artifact digests.

A prepared action is not current authorization. The trusted model boundary still
checks the principal, Request, Membership, Organization policy, and other
commit-time dependencies. Rendering an action establishes neither a permanent
permission nor a promise that a later attempt will succeed.

An action can be deliberately unavailable under its UI contract. Its semantic
identity and reason remain inspectable, and no effective transport survives that
unavailability. A missing required basis cannot be repaired by discarding semantic
metadata or forging a browser observation record.

 
The authored view may be a Request card rendered for an eligible helper, a
manager with an admitted Reassign target, or a participant who lacks the
required authoritative basis. Those produce different concrete controls,
but the underlying semantic operation does not change to satisfy a template.
A rendered enabled Claim/Reassign action is *structurally usable* only if its
selected operation, typed arguments, basis/observation obligation, actual
browser plan, required physical transport and return path close together.
That observation need not promise current authorization: a competing Claim
or Organization policy change can invalidate the action before commit.

Positive product acceptance remains independent: a perfectly well-formed
permanently disabled Reassign button does not demonstrate that a manager
can reassign an eligible Request. A rendered affordance is also not an
authorization token; client-supplied metadata cannot substitute for the
trusted principal and current guarded model operation.

*** Check the effective action, not one attribute

The render profile defines the HTML/HTMX subset whose effective behavior can be
checked. It accounts for all supported request sources and their composition,
including:

- generated semantic bindings and ordinary explicit request attributes;
- form action/method and submitter overrides;
- form association, including detached controls;
- applicable inherited attributes and explicit inheritance controls;
- relevant defaults, relative URLs, document/base context, and current path;
- supported boosting, extensions, response triggers, and navigation behavior;
- string/keyword or other attribute spellings that the serializer treats alike;
- conflicts between authored and generated transport, target, and protocol fields.

The profile must follow the actual selected browser/library behavior. It cannot
assume every attribute inherits, ignore a supported default action, or accept
silent last-write-wins merging where effective dispatch becomes ambiguous.
Duplicate IDs, invalid nested forms, conflicting attribute spellings, and browser
repair of malformed markup are rejected or explicitly handled where they affect
the claim.

 
*** Derive the effective request under the selected HTML/HTMX profile

The checker and actual browser must agree on the action of the *activated
control*, not merely on attribute names present in one Hiccup vector.
A detached submitter's =form= owner may be elsewhere in the document; a
button may default to submit; its =formaction= and =formmethod= can override
the parent form; an ordinary form may default to GET. Explicit
=:hx-post= and a native submit path can coexist and may have different
effective actions. Duplicate keyword/string spellings can serialize as
two physical attributes, so deterministic selection of one Hiccup map key
does not establish unambiguous HTML behavior.

A checker for the current selected profile must enumerate *all*
supported actions that can cause relevant semantic transport, including
the activation path of each submitter, not just the primary button or one
handpicked =hx-*= attribute. If the same DOM node offers a valid managed
Claim =hx-post= *and* an additional unadmitted protected native form
submission, the valid action cannot exempt the second one.
Conflicting transport, argument, target and observation selectors reject
unless the profile supplies an explicit, independently checked resolution.

The physical route match uses the same supported method, path decoding,
base URI, precedence and normalization as actual installed dispatch, or
a qualified correspondence to it. A plain GET search that happens to share
the path text of a semantic POST is not silently transformed into Claim.
Conversely a concrete =/requests/R/claim= POST does not become ordinary
because its metadata disappeared. Rewriting and inheritance outside the
supported profile must be classified as unsupported or explicitly constrained;
they cannot be counted as checked merely because the scanner did not find them.

A fragment can depend on a form or inherited context outside the returned tree.
Its assembly/rendering contract supplies the necessary host context or constrains
it to a self-contained composition. If required context is unknown, the checker
reports unsupported/unestablished behavior; it does not declare the fragment
complete because the missing ancestor was outside its scan.

 
The target's scoped identity and composition environment are first-class
inputs where needed: document/base URL, HTMX inheritance rules, owning
form, submitter, current route coordinates and authorized target/fragment
ownership. A standalone fragment can be preflight-closed *relative to its
declared self-contained host contract* without claiming that a future
uncontrolled parent element will preserve that contract. If an out-of-band
replacement, boosted navigation or cache insertion can change those
coordinates, the selected output/installation integration must check the
changed effective context or retain the corresponding external premise.

An ordinary effective action targeting an assembled semantic route must carry
that route's required semantic realization. Moving the action to an ancestor or
substituting concrete path parameters does not make an anonymous semantic request
legal. Conversely, an ordinary read/search route remains ordinary when it meets
its declared acquisition and effect contracts without a command choreography.

Arbitrary client JavaScript can alter the DOM or send requests directly. Render
checking establishes the trusted output's supported realization, not honesty of
a hostile browser. Server admission remains independent. Effects of ordinary
scripts within protected browser footprints follow Part VI's ownership and
noninterference contract.

*** The final structured value is the checked value

Dynamic rendering is checked after the application has produced the concrete
structured output and before prohibited output is delivered. Checking a prepared
view model and then running an unchecked renderer is insufficient: the renderer
can introduce a malformed control after the check.

The normal response path is:

1. retain the request's admitted assembly and response-context binding;
2. perform view preparation and component expansion under their declared contracts;
3. materialize the concrete structured tree and effective-action context;
4. validate semantic bindings and all supported effective actions against that
   assembly;
5. serialize that same checked value through the admitted serializer;
6. apply only response transformations whose correspondence contract preserves
   the checked properties, or recheck after a relevant transformation;
7. release the response through the admitted delivery boundary.

Lazy values, component callbacks, mutable references, and serializer-time code
must not be evaluated once during checking and again with different results during
serialization. A supported implementation can materialize a bounded immutable
tree first, or use a serializer with an equivalent checked occurrence protocol.
It must state the actual mechanism and resource/failure limits.

 
A pre-serialization guard that receives the *same top-level Hiccup reference*
does not by that fact ensure that lazy descendants, custom components or
a mutable reference produce the same expanded HTML twice. The supported
render profile must identify which values are inert, which must be fully
realized before checking, how custom renderer callbacks are constrained,
and whether serializer-time transformation invalidates the check. A
materialized exact occurrence is preferable when feasible; where a
paired inspect/emit protocol is used, its semantics, effect containment,
failure behavior and implementation assumptions are explicit. A
counterexample discovered after some output is already streamed can
block further delivery and demand repair, but cannot retract sent bytes.

When validation fails, the response producer must not silently invoke
a different unchecked serializer, return a pre-rendered copy, or use
a privileged raw HTML fallback to keep serving the control. The
fallback is itself within a qualified minimal-output protocol, which
must fail safely without unbounded recursion or accidental disclosure.

This is structural/effective-action checking, not automatic HTML sanitization or
proof of arbitrary renderer purity. Content safety and active-content policy are
separate contracts, as in Part VI. A renderer that has already performed an
external side effect cannot have that effect undone by rejecting its output.

*** Systemic enforcement covers deferred and alternate responses

The canonical application handler installs the guard once for all supported
structured responses. Nested guards compose without disabling the outer guard.
Application authors need not remember a manual validation call at every render.

A dynamically scoped guard can implement the synchronous path, but an asynchronous
response may be completed after that dynamic scope has ended or on another
thread. The response completion carries an explicit assembly/guard context or
uses another qualified propagation mechanism. Absence of the required guard at
a managed serialization boundary is a failure, not a silent return to legacy
unchecked behavior.

 
The ordinary Gesso/Biff synchronous handler integration can use a
dynamically bound guard around =gesso.http/html-response=. That mechanism
does not automatically cover a response serialized after the handler returns,
a future completed on another thread, a raw pre-serialized Ring body,
a server module replacing the checked handler, or a server that never
uses the wrapped =:biff.ring/handler=. Such a path is not magically
checked by the existence of a valid ApplicationAssembly or by an earlier
test of =check-rendered-surface=.

The finished managed application contract identifies how the guard reaches
each admitted producer and final response emission: captured generation
and currentness validation, explicit propagation to deferred continuations,
and a startup/installation gate that actually adopts the protected
serialization boundary. The policy may explicitly exclude an ordinary
unmanaged response whose effects are disjoint from its managed claims,
but it must refuse a whole-managed-surface guarantee if the omitted
response can emit protected operations. An opt-in unit checker cannot
prove the checked production path was used.

The supported response profile covers or explicitly classifies:

| Response path | Required treatment |
|---------------+--------------------|
| Ordinary structured page/fragment | Check the actual final structured occurrence before serialization/delivery. |
| Deferred/asynchronous response | Preserve the admitted assembly and guard through completion, timeout, cancellation, and error handling. |
| Streaming output | Check each delivered managed portion under a compositional context or buffer the required scope; acknowledge that already-sent bytes cannot be withdrawn. |
| Cached structured fragment | Preserve semantic binding and applicability; check the concrete occurrence in its current context where needed. |
| Cached/pre-serialized HTML | Establish a separate admitted output correspondence and context/authority policy; a previous check does not authorize disclosure to another principal. |
| Error response after handler failure | Use the same supported output boundary or an explicitly admitted minimal error protocol. |
| Redirect/navigation/secondary-target response | Check its declared effect and target/protocol behavior, not only the main HTML body. |
| Raw HTML/custom renderer | Admit a separate realization contract or exclude it from the specific structured-output claim. |

Naming an escape hatch does not satisfy a requirement that all application
managed surfaces are covered. A policy requiring that coverage rejects an
uncovered managed path. Static assets or truly unmanaged output can be explicitly
outside that claim, provided their effects do not invalidate its premises.

A response cache key is not just a URL when its contents depend on tenant,
authorization, query, semantic contract, or assembly instance. The cache contract
states the partition, freshness, revocation, and revalidation behavior needed for
its claims. Returning a cached checked card to an unauthorized user is still a
disclosure failure.

 
Cached output has at least two independent questions: *was the stored
structured occurrence checked against the generation that produced it?*,
and *is disclosing and executing it valid for this recipient, context and
current generation?* Cached HTML cannot inherit indefinite permission
from an earlier checked render. Invalidation and reacquisition are
separate from permission to disclose a cached body; an old card can be
structurally coherent yet expose an operation no longer available to
the current principal. A cache hit that bypasses the admitted checking
or authorization boundary must be classified as such.

*** Worked example: a render-time defect after a valid Claim

Startup admits the Claim operation and its return path. For a particular request,
the trusted model incorporates command C42 successfully. While preparing the
resulting card, a bug creates a Cancel affordance without its required Request
argument.

The output guard rejects that concrete card before delivery. It does not change
the authoritative Claim outcome to rejected. The trusted request boundary retains
its known result and follows the admitted response-failure protocol.

| Evidence available to the participant | Required treatment |
|---------------------------------------+--------------------|
| A permitted, correlated committed outcome is delivered through the supported error/settlement channel. | Preserve known incorporation; present response/installation failure separately and offer the authorized recovery path. |
| The server knows incorporation, but its response is lost or the browser cannot admit the payload. | The browser remains unknown until its resolver supplies admissible evidence. |
| A later card read shows the current claimant without command attribution. | It can establish current state at its scope; it does not by itself resolve C42. |
| The malformed response concerns an operation rejected before submission. | Preserve that actual disposition; do not route all response failures through a committed-only handler. |

The error protocol defines the actual HTTP/transport representation and the
browser hook that can decode it, including non-success status handling where
used. A map containing settlement metadata is not enough if the selected HTMX
profile never exposes that metadata to the runtime.

The fallback response itself must be valid and bounded. It must not recursively
invoke the same failing renderer forever or expose privileged diagnostics. A
minimal typed response or a later authenticated resolver may be more reliable
than trying to render the full card again inside the error handler.

 
The error path must preserve the distinction between the *server's known
authoritative result* and *the browser's participant-relative knowledge*.
For example, the server may know that Claim C42 committed and that the
Cancel action in its response is malformed. If a correlated, authorized
settlement is actually delivered and admitted by the selected browser
HTTP/HTMX error protocol, the client may learn the incorporation and
separately report presentation failure. If the error response is lost,
the client retains =:unknown= until the durable command resolver supplies
admissible attribution. A current Request card is insufficient proof of
which earlier Claim command won.

A bad result renderer may also have run *after* the protected transaction,
and its failure cannot retroactively veto that transaction. Conversely,
a rejected pre-effect command remains rejected when rendering its error
body fails. The fallback must not opportunistically invent another
domain write or refresh authorization under the pretext of recovery.
The next section owns the complete authoritative outcome, acquisition and
propagation mappings.

Tests distinguish no malformed output was delivered from no protected mutation
occurred. The former is the render guard's responsibility; the latter requires
an earlier command/model gate. Both need a positive control showing that valid
requests remain usable.

 
*** Positive and adversarial rendered-response histories

Each test uses the selected source-owned assembly, *actual* relevant
production response boundary, and where applicable the real browser
control. Supplying an already successful report or constructing a
valid protocol command in place of a broken control is insufficient.

| History | Required disposition and evidence scope |
|---------+-----------------------------------------|
| An eligible helper renders a well-formed Claim button, activates it, and an admitted plan submits the command to the protected route. | The concrete enabled control and its supported effective request close against the assembly; model execution and actual browser completion need separate evidence. |
| A manager sees an eligible Reassign affordance with typed Request and target Helper IDs. | Preserve its semantic identity, complete arguments and original required observation; do not claim that rendering grants lasting authority. |
| The Reassign renderer omits =:helper/id= on one conditional card while startup's registry is correct. | Reject that concrete enabled affordance before checked output serialization; a static route/plan success cannot excuse it. |
| A Claim button lacks basis and is marked visually disabled, but its enclosing form retains an active semantic POST. | Reject the effective request or suppress every active transport while preserving the unavailable semantic identity. |
| A marked Claim button emits the certified =hx-post= and an additional unadmitted protected =hx-put=. | Reject the extra executable action; valid metadata for one route does not authorize a second route. |
| A detached submit button overrides a search form to the Claim POST route. | Resolve its real =form= owner and =formaction=/=formmethod=; reject anonymous protected transport while allowing unrelated ordinary search. |
| A keyword and string Hiccup key both serialize a relevant physical request attribute. | Reject ambiguity instead of relying on one key chosen by a scanner. |
| A form uses the browser's implicit action/current document URL, which the selected analyzer cannot reconstruct. | Demand a qualified host/default context or report the behavior outside proven coverage; do not accept on absence of explicit =action=. |
| A fragment is valid in isolation but gains a protected inherited action after installation in another parent. | Check the host composition or retain a named compatibility premise; standalone fragment evidence is not parent-independent. |
| A lazy child renders safely when inspected but emits a different protected action on the serializer's second evaluation. | Reject the unsupported nonrepeatable producer or use a qualified single-materialization/check-and-emit protocol. |
| An asynchronous task serializes Hiccup after the dynamically scoped handler guard has ended. | Require captured, generation-bound response enforcement or reject managed output; synchronous guard installation alone is insufficient. |
| A cache serves a previously valid Request card to a different principal or retired generation. | Enforce recipient disclosure, freshness and generation context; a prior artifact/render success cannot authorize this cache hit. |
| A valid Claim C42 commits, but a malformed Cancel affordance is discovered while building its response. | Block malformed HTML, retain the known committed result at the server, and provide a declared correlated settlement/recovery path without fabricating command rejection. |
| C42 commits but its render-failure settlement is lost or ignored by the selected HTMX error lifecycle. | Preserve client-side unknown command knowledge and resolve it through the admitted command resolver; current card alone is not command attribution. |
| A renderer fails before a prohibited protected write would be initiated, and the guard catches the malformed page. | The malformed output is blocked; whether a write was prevented must be established from the actual pre-effect gate rather than inferred from a rendering exception. |
| A handler returns raw pre-serialized HTML while the canonical Hiccup wrapper would otherwise be installed. | Declare an alternate independently qualified output path or explicitly exclude it; no whole-managed-render claim arises from a guard that never sees the body. |
| A real valid ordinary HTMX search form uses a nonsemantic GET route. | Admit its own read/acquisition contract without fabricating a Choreo operation or treating shared path text as a protected POST. |

Controlled-defect tests distinguish source mismatch, effective physical
request, response producer, delivery and postcommit recovery. An application
that disables every action or turns every server result into HTTP 500
does not satisfy independent positive HumanHelp product acceptance.
The fact that Gesso can check one current Hiccup occurrence is not
by itself a claim that the deployed server checks *every* possible
rendering path or that the browser interprets it correctly.
