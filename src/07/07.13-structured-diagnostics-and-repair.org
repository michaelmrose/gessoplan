** Structured diagnostics and repair

Diagnostics identify the failed obligation and its actual owner. Human-readable
messages are rendered from stable structured data; tools should not parse prose
to discover whether the missing edge was a route, provider, asset, or recovery
continuation.

 
*** Diagnose the original proposition and its legitimate detection stage

A diagnostic is a source-bound *explanation of a failed or unfinished
proposition*. It is not a new application semantic fact, a replacement
operation, a trusted executable or a certificate. The ordinary diagnostic
surface derives from the current canonical assembly and actual checker
result; it cannot accept an arbitrary successful caller map as proof that
the inspected source or installed handler is current.

The framework distinguishes a candidate that could not be admitted,
an admitted but not installed construction, a failed actual invocation,
a known post-effect contradiction, and a participant-facing outcome
that remains uncertain. A single generic =:error= or HTTP 500
cannot safely express all of them. In particular, a browser's
reported =:unknown= after Claim settlement loss is not a failed
preflight, an authoritative =:rejected=, or evidence that the
transaction was rolled back.

A stable diagnostic identity includes a *kind* and a scoped
obligation/subject identity. Its generation, semantic source,
route/plan/asset, original command or observed resource
identity, evidence and checker version, and relevant deployment
profile are separately retained when applicable. A copied diagnostic
is valid information about its former subject, not automatically
about a freshly changed generation. Diagnostic vocabulary is
versioned so tools can distinguish renamed public keys from
actually changed failure semantics.

A diagnostic includes, where applicable:

- the error kind and detecting phase;
- operation, projection, route, resource, or claim subject;
- assembly/installation and relevant executable/artifact identities;
- source location that introduced the obligation and source responsible for supply;
- expected relation and actual observed/bound values, within disclosure limits;
- rejected, unsupported, inconclusive, contradicted, or inapplicable status;
- remaining premises and whether any protected effect already occurred;
- mechanically known repair alternatives without automatic substitution.

 
A report also states *which relationship was actually checked*,
which original source supplied each expected condition,
which independent observation (if any) supplied the actual value,
the checker or host trust boundary, and whether the failure
disposition is =rejected=, =open=, =unsupported=,
=inconclusive= or =contradicted= at the specific proposition.
Unobserved means unobserved, not false; copied source declarations
cannot authenticate their own physical adoption.

When a checker emits multiple issues, a deterministic
=first-blocker= is a navigation aid with an explicit priority
rule, not a claim that no other obligations are open. The
full explanation retains the applicable open/assumed/dependent
obligations, subject identity, and whether discovering another
fault requires repairing the first. Stable sort order and
machine-readable paths make diffing repeated diagnosis possible
without creating executable authority.

An illustrative provider error is:

#+begin_src clojure
{:error/kind :incompatible-capability-provider
 :phase :assembly/admission
 :assembly-instance/id candidate-id
 :operation/id :request/claim
 :obligation/id :claim/commit-time-input
 :introduced-by claim-source-ref
 :supplied-by server-binding-source-ref
 :expected {:input-path [:execution-context :biff.fx/now]
            :value-contract :time/instant}
 :actual {:input-path [:execution-context :clock]
          :value-contract :clock/zero-argument-function}
 :suggestions [{:kind :explicit-binding-adapter
                :contract/ref sampled-invocation-time-ref}]}
#+end_src

The suggestion does not install that adapter. Source correction and admission
establish the new binding. Likewise, an unknown =:request/claime= may suggest
=:request/claim= diagnostically but must never be corrected automatically for
execution.

 
The provider example must be interpreted at the *consumer's input
path*. A named =:clock= capability that returns a zero-argument
function is not the =Instant= required at =:biff.fx/now=.
A diagnostic can propose a source-owned sampled-time adapter
when the adapter contract is mechanically known; it must not
invent an implementation, assume the clock is trustworthy,
silently provide a default time, or modify Claim's transaction
semantics. If the provider genuinely failed only at invocation,
the diagnostic identifies that runtime fact rather than
retroactively claiming the builder proved its behavior.

*** Source-local repair is a separate, re-admitted action

Diagnostics describe *candidate actions*, not repairs that have
occurred. Every suggested source correction names the owner
of the declaration that must change, the exact broken relation,
the known alternative interface (if any), the verification
and deployment stages that would need rerunning, and the
extent of evidence that the suggestion itself has. A human
or coding agent may separately choose to edit the source
under normal authorization and version-control rules.
A rebuilt assembly, browser artifact, route and assurance
report then require fresh checking of the changed dependencies.

A repair tool must not treat a near-match operation string
as permission to dispatch it; rewrite a protected role,
tenant or Request selector; add an anonymous HTMX fallback;
substitute a new executable merely because a report names it;
or automatically retry a possibly incorporated command.
Where a domain *compensating operation* is legitimately
needed, it is separately admitted and authenticated under
its own current guards, command identity and effect contract.
No diagnostic callback gains the runtime rights needed to
perform that operation.

A proposed fix can have multiple legal implementations.
The checker explains what is established and what is
unknown rather than guessing a unique implementation from
a plausible name. After source change, it rechecks the
canonical assembly and all dependent generated, installed
and runtime evidence; it cannot simply edit the old
closure report's =:status= field to green.

*** Stable diagnostic families

| Family | Representative distinctions |
|--------+-----------------------------|
| Semantic construction | Unknown operation, duplicate identity, invalid interface, contradictory transition, incompatible realization. |
| Plan/build | Missing plan, wrong plan/operation, stale manifest, asset-byte mismatch, incomplete asset set, unestablished build correspondence. |
| Dispatch/execution | Missing/ambiguous route, selector conflict, wrong issued executor, unsupported route semantics, unclassified writer. |
| Provider/effect | Missing provider, incompatible value or origin, invalid actual candidate, wrong target, unsupported lifetime. |
| Rendering | Missing arguments/basis, anonymous semantic route, implicit downgrade, conflicting attributes, unknown effective context, unchecked response path. |
| Recovery | Missing continuation, incompatible outcome mapping, absent owner/trigger, unsupported retained command contract, unmet acquisition/installation requirement. |
| Installation/lifecycle | Missing gate, wrong actual handler, premature exposure, assembly-instance mismatch, invalid dependency, failed activation/cleanup. |
| Assurance | Unsupported fragment, inconclusive budget, counterexample, inapplicable evidence, unaccepted premise, insufficient coverage. |

These families need stable public identities without requiring this document's
exact keyword spellings. A missing resource and an existing incompatible resource
should not be indistinguishable. Dynamic authorization denial retains its model
outcome and privacy policy; it is not reported as a corrupt assembly.

 
*** Concrete R4 error distinctions remain mandatory

A conforming diagnostic surface can explain the
following independent facts, without requiring
these illustrative keyword spellings as its public API:

| Diagnostic subject | Required distinction and useful evidence |
|--------------------+-------------------------------------------|
| Unknown semantic operation | Original rendered view/source and unknown identifier; admitted operation IDs and safe near matches, with no automatic correction or execution. |
| Missing browser plan | Admitted operation and its exposing role/view exist; the required projected plan is absent. Show candidate plan/manifest scope without claiming semantic rejection. |
| Stale generated artifact | Current source-derived manifest versus actual emitted bytes and current receipt/sidecar. Report exact mismatch and responsible rebuild boundary, never filesystem timestamps as identity. |
| Transport/route mismatch | Differentiate no route, method/protocol mismatch, overlapping/ambiguous route, wrong decoded Request selector and unadopted installed handler. The check uses or qualifies real routing semantics. |
| Anonymous protected HTMX action | Effective concrete method/path, matched semantic route, originating Hiccup/control, and missing operation/basis binding; an unrelated plain GET remains legitimate. |
| Missing or wrong capability | Source operation and consumer input contract (including =:biff.fx/now=), selected actual provider/handler, expected type and observed/declared incompatibility. |
| Missing initial/current acquisition | Logical fragment/owner, required authoritative projection, progression lower bound, permitted trigger and available sources; an SSE route alone supplies neither current knowledge nor a read grant. |
| Missing recovery continuation | Original uncertain command or failure class, required owner/trigger/input, exact resolver/acquisition path and retained uncertainty rather than a fabricated reject. |
| Lifecycle or deployment mismatch | Candidate versus installed generation, actual Biff module/handler, served asset binding, failed gate/cleanup and which physical serving proposition is still unknown. |
| Unsupported or inconclusive assurance | Exact obligation, checker/budget or unsupported language, retained premises and known witness if any; no invented counterexample, passed proof or universal certificate. |

An unavailable, wrongly typed or ambiguous resource must not
be silently classified as merely absent. A known physical
violation must not be relabeled an open proof obligation.
Likewise, an authorization denial for a current
principal and Request remains a typed model outcome,
not evidence that the application graph is corrupt.

A diagnostic must not claim semantic verification succeeded merely because it
reached a later code path. It reports only established evidence. Source summaries,
artifact stamps, and provider declarations can be useful repair facts without
being proofs of their implementations.

 
*** Disclosure, sidecars, and diagnostic noninterference

Source-level internal diagnostics and user-visible response
errors may contain different details under distinct disclosure
policies. A public failure must not leak another principal's
command history, Membership/Organization contents, private
Request identifiers, session material, tokens, executable
handles or unrestricted host source paths. Redaction preserves
explicit =unavailable=/=redacted= markers and the
non-sensitive identity needed to correlate a permitted repair;
it cannot infer that a hidden obligation is absent.

Browser diagnostic sidecars must correspond to the *exact*
generated executable plan and artifact before a source
location or trace is treated as authoritative diagnostic
provenance. An old sidecar with matching operation names
is not a valid map for a changed bundle. Browser
debugging observers are non-authoritative: enabling,
disabling or throwing from the observer cannot change
the semantic trace, adapter effects, resource ownership,
settlement, execution continuation or permission to
perform physical work.

Optional diagnostic probes may be bounded and opt-in
where they execute expensive model checks. Their
failure or timeout is not permission to weaken a
mandatory startup gate, abort an unrelated admitted
command after incorporation, fabricate a passed proof
or suppress a critical runtime error. A diagnostic
system may fail safely while the application's
underlying admitted behavior and obligations remain
as specified.

*** Positive and adversarial diagnostic histories

Acceptance checks stable machine-readable failures
against the actual relevant source/physical
boundaries. A correct looking test report by itself
is not sufficient evidence of installed enforcement.

| History | Required diagnostic or repair disposition |
|---------+------------------------------------------|
| A source-owned Claim has all required plan, HTTP route, typed provider, issued executor and authorized acquisition edges. | Explanation identifies the checked graph and original owners; no failure is invented, and positive usability is tested separately. |
| A rendered control references =:request/claime= while the catalog contains =:request/claim=. | Reject the unknown operation at its legitimate boundary; report known IDs/near match without auto-correcting the invocation. |
| A plan exists for Claim but the current source-derived manifest omits it. | Report missing browser realization, not semantic operation invalidity or an unproven runtime failure. |
| A receipt belongs to the previous generated bundle, though its filename and operation name match the current asset. | Report exact manifest/byte/sidecar mismatch; never trust the stale mapping for source attribution. |
| A route is installed with the wrong method or matches two operations under the actual router's precedence rules. | Distinguish incompatible versus ambiguous route and retain the actual route/source identities. |
| A native form submits anonymously to the protected Claim POST route. | Report effective method/path, semantic-route collision and rendering source; do not turn it into permitted ordinary HTMX. |
| A Claim provider lists =:clock= but the handler requires sampled =:biff.fx/now=. | Report source-owned requirement and incompatible value/input path; a suggested adapter is not automatically installed. |
| A managed fragment has no initial observation or permitted authoritative reread. | Report acquisition owner, required projection/progression and missing permitted trigger; do not call an SSE connection an acquisition. |
| An unknown command has a read-only resolver but no retained ID, authorized trigger or disclosure contract. | Identify the missing continuation binding and preserve unknown incorporation; no generic HTTP error can settle the command. |
| A current authenticated helper loses Membership immediately before Claim. | Preserve successful structural preflight; report the current trusted model rejection without calling it assembly corruption. |
| The real server ignores the checked Biff handler and serves an older raw renderer. | Retain local handler-check evidence but mark deployment adoption/output enforcement unestablished or contradicted where observed. |
| One checker times out while another finds a concrete counterexample. | Preserve the independent inconclusive and contradicted proposition statuses; no single green or generic failed flag erases them. |
| A first-blocker summary names a missing clock, while a second plan/acquisition problem also exists. | Show deterministic first navigation and the remaining open obligation scope; never claim there was only one defect. |
| A copied green report claims physical write coverage and an agent proposes reusing it after provider reload. | Refuse report-as-admission and show invalidated source/implementation dependencies; source must be corrected and re-admitted. |
| A browser observer throws while a valid local execution is running. | Preserve execution effects and resource ownership; observer failure cannot rewrite command outcome or DOM rights. |
| A low-privilege browser receives a diagnostic whose internal version mentions another user's protected command record. | Redact the forbidden record/subject; retain truthful limited scope without leaking prior-result attribution. |
| A Claim has already committed, but response rendering fails on a malformed Cancel action. | Distinguish blocked output from historical incorporation and participant unknown/lost settlement; suggest repair of the renderer, not undo of Claim. |
| A remediation suggestion proposes a replacement handler, while a required external dependency or callable remains opaque. | Show the limits of the suggestion and require source/physical requalification; no fabricated guaranteed fix. |

These histories retain R4's requirement that structured
errors are genuinely actionable. They also reject
"helpful" automatic changes that could silently alter
authorization, operation identity or command repetition.
A source-derived explanation can support both human
and coding-agent repair, but the subsequent edit,
build, admission, deployment and tests remain
ordinary independently authorized work.
