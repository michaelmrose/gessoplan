** Static preflight and required dynamic handling

Static preflight is mandatory construction/startup work for the managed application.
It consumes the actual canonical construction and artifact products, rather than
a manually reconstructed preflight-only registry. It runs at the earliest stage
with enough information and produces structured obligations/results.

 
The supported managed constructor owns the admission sequence. Application
authors must not remember to invoke a separate optional checker before
starting an otherwise unchecked server. A narrower low-level or legacy
startup path may exist, but it does not inherit the checked-managed policy,
its issued executor rights, or production enforcement claims.

A successful *structural* preflight records the exact application generation,
source-owned operation and failure catalog, selected evidence policy,
constructed executable/asset products, and still-unmet installation,
invocation, runtime and external premises. It cannot claim that the
network listener adopted the guarded handler merely because a candidate
assembly was checked. Installation, activation and serving adoption are
distinct mandatory gates where the policy requires them.

The preflight checker rejects *known missing* mandatory edges, while
preserving separate classifications for unsupported, inconclusive and
externally assumed obligations. An opaque =:recovery-exists? true= field,
copied success report or abstract terminal state is not a checked
continuation. A proof checker that cannot model a required recovery
transition must not relabel its inability as structural success.

*** Failure belongs at the earliest legitimate boundary

| Boundary | Representative checks |
|----------+-----------------------|
| Semantic construction | Malformed interfaces, contradictory roles/knowledge, invalid transition terms, unsupported declaration structure. |
| Assembly/build | Missing operation realization, incompatible provider, wrong plan/route binding, incomplete required recovery, stale asset set. |
| Installation/activation | Wrong actual handler/executor, missing policy gate, unsupported lifecycle ordering, incorrect server/asset adoption. |
| Concrete rendering | Missing bound argument, anonymous semantic route, unavailable action retaining transport, unsupported effective-action context. |
| Request/effect admission | Malformed envelope, contradictory selectors, stale assembly/resource binding, invalid actual candidate or effect target. |
| Authoritative incorporation | Current permissions and dependencies, atomic guard failure, command binding/replay/disclosure rules. |
| Completion/recovery | Actual outcome, acquisition/installation evidence, unresolved delivery, partial effects, cleanup and retry conditions. |

A valid assembly can receive a rejected Claim because Membership changed after
render. That is not assembly corruption. Conversely, a known missing clock
binding should not be deferred until the first Claim throws a missing-input
exception.

 
A different failure layer can become relevant *after* the previous layer
succeeded. For example, a Claim route and its required sampled
=:biff.fx/now= provider can be structurally closed at admission,
yet the trusted principal may lose Membership before incorporation.
The earlier check remains valid for its actual proposition; the runtime
must still reject the now-unauthorized command under the model's
current-state guard and preserve its real typed outcome.

A malformed Claim command envelope can be rejected at trusted request
admission even if its rendered control previously passed Hiccup checks.
An actual DOM target can retire during acquisition even if the response
was correct. A post-commit response-render failure blocks the invalid
output but never proves the earlier authoritative write failed. The
diagnostic identifies the earliest *legitimate* boundary with the needed
information without confusing a later detection with prevention at
an earlier boundary.

*** Required handling coverage
:PROPERTIES:
:CUSTOM_ID: req-preflight-dynamic-handling-coverage
:END:

Preflight need not predict dynamic facts. It must check declared handling/recovery
paths for supported dynamic conditions that could strand an operation. A happy-path
provider or reachable terminal node is insufficient.

The obligation identifies the condition, source contract, continuation input,
owner, required resources/evidence, trigger, and permitted outcome. Construction
checks the corresponding graph edges and type/binding compatibility. An opaque
statement saying recovery exists cannot replace an available structural check.

 
*** Derive recovery obligations from the operation, not a second catalog

The source owner declares the selected operation's failure/outcome classes,
delivery and recovery expectations, and admissible continuation semantics.
Application construction derives a *coverage relation* for those classes
through its installed route, physical providers, browser projection, Live
and acquisition sources. A separate hand-authored recovery registry
that repeats operation names is not independent coverage evidence.

Each required continuation is inspectable as a typed edge with:

| Evidence dimension | Required content |
|--------------------+------------------|
| Original condition | Which operation phase/failure/outcome class creates the obligation, and its source/version. |
| Trigger and permission | The real event, timer, explicit user action or retained work that may initiate continuation, including whether it has an unspent grant. |
| Current owner | Command/work identity, assembly generation, principal or authorization scope, resource lifetime and transfer/retirement rule. |
| Inputs and evidence | Typed prior result, original command binding, current authorized observation, progression lower bound or error/unknown discriminator actually available at that point. |
| Physical realization | An actually constructed and installed resolver, route, worker, provider, browser effect or explicitly qualified external mechanism. |
| Continuation contract | Which outcomes may be reported, what can be retried, what remains unknown, which effects or targets are forbidden and whether partial completion survives. |
| Applicability and failure | The preflight evidence mechanism, required premises, unsupported opaque behavior, boundedness and fallback disposition when continuation is unavailable. |

An edge is not covered merely because a function with a matching name
exists. The expected result type must match the actual continuation input,
and its owner must be able to invoke that continuation through a
permitted live path. A required =:commit-unknown= resolver that
can never retain the original command ID has no usable input; a
valid GET acquisition endpoint without an authorized trigger cannot
satisfy a user-mediated one-Refresh contract.

For opaque Clojure callbacks, a checked interface can establish the
declared input/output and provenance relation only to the extent of
the actual mechanism. It does not prove every callback return value,
side effect or eventual completion. Required stronger properties need
their own contract checks or named assumptions. A declaration whose
supported checker cannot establish a mandatory relation remains
unsupported/open under the selected policy, rather than green by
unchecked assertion.

| Condition | Required declaration and realization |
|-----------+--------------------------------------|
| Provider fails before submission | A typed local failure/retry path that does not claim authoritative incorporation or rejection without evidence. |
| Delivery is lost after possible submission | Unknown command disposition, retained binding, and a valid reconciliation owner/path. |
| Prior result cannot be disclosed | A permitted nondisclosing continuation without false rejection or information leakage. |
| Acquisition cannot establish required scope/progression | Retained debt and a declared stronger read, retry, defer, or blocked state. |
| DOM installation is partial or completion is lost | Repair/reconciliation without premature adoption. |
| Continuity restore fails after adoption | Local continuity failure without undoing authoritative installation. |
| Subscription misses changes | Gap recovery independent of receiving a fresh advisory. |
| Plan/operation version becomes incompatible | Retirement/transfer and retained command resolution under a compatible contract. |
| Recovery budget or retention expires | Truthful deferred/blocked/manual handling with no fabricated authoritative disposition. |

These checks cover the declared supported conditions. They do not prove that
arbitrary external software has no additional failure modes or that recovery will
eventually succeed. Unexpected failures enter an explicit containment boundary
that preserves evidence, uncertainty, and surviving obligations.

 
*** Recovery states must preserve the kind of uncertainty

Some operational outcomes can be distinguished at one boundary but not
at another. Before an authoritative attempt is initiated, a trusted
provider failure may be a local no-submission result under the contract.
After submission might have occurred, a network timeout, callback
exception or publication loss cannot be converted into the same
no-submission result unless actual command-specific evidence
establishes it. An existing command-record resolver may prove a
disclosed replay without proving current permission to issue a new
write. Current-state reacquisition may show a new claimant without
identifying an earlier Claim command's incorporation.

Each continuation therefore states whether it is:
a guard that *prevents* an effect; a settlement based on authoritative
evidence; a read-only reconciliation; permitted acquisition; a
participant-local presentation/continuity repair; or a compensating
*new* admitted operation. These cannot substitute merely because they
share an exception handler. Failure after successful DOM installation
cannot retract the installed observation; a failure of continuity
restoration keeps a separate continuity obligation.

For an optimistic Claim, a structurally sound required unknown-delivery
path retains the command's original argument/version binding, records
a durable or explicitly qualified recovery owner, checks disclosure
before returning prior results, and allows a separately granted
readback only when its progression and browser-target rights hold.
Neither a generic HTTP 500 nor an optimistic =:rejected= toast
is sufficient handling for unknown incorporation.

A path to a terminal node is not a termination theorem. Liveness depends on the
stated availability, scheduler, permission, resource, and user-action premises.
The application explanation shows those premises next to its progress claims.

 
The application need not promise that an unavailable provider, uncooperative
user or partitioned router will inevitably recover. It must instead
make its liveness contract conditional and testably explicit: which
fairness or availability premises it needs, how long recoverable
command/evidence material is retained, which obligations remain when
those premises fail, and the authorized manual/deferred disposition.
A timeout cannot be used to assert proof of termination, to discard
a prior durable submission, or to make a permanently disabled
required product capability count as completed acceptance.

*** Controlled-defect and positive-path qualification

Construction-time controlled defects deliberately remove *one*
required edge from the actual source-owned assembly and expect a
stable failure at the earliest applicable boundary. A corresponding
valid assembly and fault-injection scenario must exercise the real
continuation and the preservation of authority, uncertainty or
physical installation. Tests that invoke only a helper checker
cannot claim that the deployed managed startup or returned browser
response actually enforces it.

| History | Required earliest legitimate outcome |
|---------+--------------------------------------|
| A valid Claim model, plan, route, sampled time provider and authorized resolver are assembled and successfully exercised. | Admit the candidate; separately show actual effect, participant settlement and physical adoption for product acceptance. |
| Claim requires =:biff.fx/now= but only a differently shaped clock provider is registered. | Reject the construction/provider edge before serving rather than defer a known missing input to the first request. |
| The browser plan requires an unknown-command resolver, but the selected operation assembly has no resolver or retained original binding. | Reject required recovery closure; a present-state card GET is not an automatic substitute for command attribution. |
| A resolver exists but has no real authorized trigger, available owner, or compatible continuation input. | Reject unusable continuation wiring instead of accepting a named function. |
| A valid rendered Claim is attempted after the helper's Membership is revoked. | Preserve structural assembly success, then reject on the current trusted model/transaction guard; do not misdiagnose application preflight failure. |
| A Claim submission might have committed but HTTP settlement is lost. | Preserve =:unknown= and real command binding; continue through qualified reconciliation rather than invent a failed mutation. |
| The durable command record is nondisclosable to the current principal. | Return the admitted nondisclosing outcome; do not leak prior result or relabel it rejected. |
| A granted Refresh was consumed, and another Live advisory arrives. | Preserve new advisory debt; the prior one-use acquisition permission cannot be reused. |
| The acquisition route exists but returns an observation below the required scoped progression. | Do not discharge debt or adopt merely from HTTP success; retry, defer or explicitly block under the declared policy. |
| A fragment subscription is established after a relevant missed change, but nothing new is published. | Require the declared reconnect/fence/replay/reacquisition trigger; a handler waiting only for a future advisory is incomplete. |
| The DOM adoption finishes, then continuity restoration fails. | Report local continuity repair debt; preserve installed observation and authoritative mutation. |
| A valid Claim commits but its response renderer generates a malformed Cancel action. | Reject output delivery at the rendered boundary, not the earlier committed Claim; retain settlement or unknown recovery as appropriate. |
| One required recovery handler is replaced after installation without new admission. | Invalidate affected construction and execution evidence; reject unsupported generation crossing or re-admit the changed path. |
| Recovery queue budget is exhausted while a command may remain incorporated. | Enter typed blocked/deferred/overflow handling and retain applicable evidence; do not discard unknown work as rejection. |
| A checker hits its resource limit without completing a mandatory structural/proof obligation. | Report inconclusive, not established or contradicted, and apply the selected assurance policy. |
| All invalid commands are rejected, but a valid eligible Claim or Reassign is permanently unavailable. | Fail independent positive product acceptance even if negative structural enforcement is correct. |

Negative cases must identify the exact source-declaration change,
expected error/obligation ID, actual production entrypoint or qualified
unit-check boundary, observed absence of a prohibited effect/output,
and recovery/blocked behavior. A rejected build may still own
cleanup of already prepared resources, but it cannot activate an
unchecked candidate.

*** Resource policies are part of admission

Construction and runtime declare limits for model exploration, graph size,
render materialization, response buffering, active executions, recovery queues,
physical remnants, and evidence retention where those resources matter. Limits
have typed outcomes and handling paths.

A resource limit cannot turn an unfinished proof into a successful check, a dropped
advisory into discharged debt, or a lost command record into a rejected command.
Static checking validates the declared policies; runtime enforces their actual
budgets and preserves the appropriate scope of uncertainty.

 
Resource policy also owns work after an HTTP response or assembly generation
retires. The contract specifies whether a command resolver, Live interest,
deferred structured response, worker and physical target is cancelled,
transferred, retained for bounded recovery or reported as unavailable.
A process-local handle cannot silently survive restart as a durable
certificate. Resource exhaustion must never leak an unbounded queue,
promote a stale grant, retry a possibly committed external effect
without an idempotence contract, or expose partially installed
application operations.

A managed profile may select conservative limits to remain usable in a
small deployment and more capable limits for a larger host. It must not
convert a resource-limited checker into a different theorem, omit required
operation/failure classes, or silently weaken the user's chosen
application assurance policy.
