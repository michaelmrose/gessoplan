## R4 requirements preserved

1. **Canonical, source-derived BrowserAssemblyManifest.** The exact
   required executable plan set is derived from the same semantic
   ApplicationAssembly as preflight; browser build, application
   checking and tests must not maintain separate hand-typed lists.
   Required operations, role, feature/transport profile and exact
   plan identities stay source-bound. Missing, duplicate and
   incompatible required plans fail.
2. **Exactness is stricter than protocol compatibility.** R4 explicitly
   distinguishes the newly admitted application's current manifest
   from whether an older browser can safely continue after deployment.
   Reassign added in B cannot be waved through with A's stale bundle
   because A still has a compatible Claim plan.
3. **Build-generated, not self-certified, artifact identity.** R4's
   BrowserArtifactStamp and actual byte digest are distinct
   semantic/physical facts. Receipt values cannot establish
   source-generation, correct compiler behavior, or genuine plan
   inclusion just by duplicating expected manifest digests.
4. **Acyclic identity.** The manifest cannot contain the digest of
   the final bytes that themselves contain that digest without a
   specifically justified cycle break. A detached signed or
   independently authenticated receipt may serve as evidence under
   its declared provenance; a raw copied receipt cannot.
5. **No test-only surrogate as production proof.** A fake stamped
   bundle may isolate a checker test. The real startup/acceptance
   path requires the generated runtime and the same physical
   asset/receipt checks used in production.
6. **Reject stale assets before external service.** Missing, stale,
   mismatched, incomplete or unverified generated assets must
   fail the selected strong admission/startup profile before
   protected browser behavior is exposed.
7. **Publication and deployed serving are distinct.** Checked bytes
   at local build time are not necessarily the actual bytes later
   served by Aleph, a reverse proxy, CDN or service worker.
   The runtime needs an immutable serving correspondence or a
   qualified check at the boundary where it actually matters.
8. **Old clients and rollout safety.** A page rendered under assembly
   A needs A-compatible assets even if B activates before the
   browser downloads them. Older command-resolution, resource
   retirement and plan compatibility are Part VI contracts, not
   excuses to skip exact B admission.

The R4 illustrative `gesso.application/normalize`,
`browser/derive-manifest`, `cljs-build/inspect-emitted-plan-registry`
and `check-browser-artifact-currentness` helpers are examples of
required relationships, not promises that these exact names are
current public APIs. The smaller R5 generated-entrypoint design
remains preferred; the material R4 distinctions are retained.

## R5 strengths and R5.1 additions

R5 already supplied a Gesso-owned generated bootstrap, a typed
physical-realization options surface, explicit compiler-fidelity
premises, receipts for physical bytes, transitive assets,
isolated staging, immutable serving sets and old-client
compatibility.

The revision makes their acceptance consequences more explicit:

- A plan inventory covers required, optional/shared and truly
  inactive plans, with exact semantic/role/transport and
  physical-handler requirements rather than blanket one-plan
  per app.
- Independently chosen compiler, runtime, realization Var,
  bundler/options and dynamic imports are identified as
  implementation dependencies; a literal `current` version
  label cannot keep stale evidence valid.
- A low-level arbitrary emitter can establish only the narrowed
  receipt/bytes relationship; the normal source-generated build
  establishes more *under a named compiler premise*.
- An emitted registry claim is only as strong as its independent
  extraction or audited producer binding; copying expected
  plan digests does not prove inclusion.
- Actual served resource closure includes dynamic chunks,
  workers, relevant scripts, cache controls and other resources
  whose meaning affects admitted behavior.
- A pair of per-file atomic moves is not a transactional release
  of the bundle and receipt. Failed receipt publication may
  invalidate the candidate and disturb an earlier mutable
  location. The finished design must stage immutable *sets*
  and switch their serving reference as one admitted generation.
- A/B rollout, concurrent fetches, CDN/service-worker caches and
  long-lived browsers demand generation-specific asset bindings
  and a retention/recovery profile.
- Fourteen positive and adversarial histories distinguish:
  real successful build/load, missing Reassign, extra plan,
  arbitrary stamped bytes, mismatched receipt, changed
  realization code, stale dynamic chunks, compiler failures,
  partial publication, A/B URL substitution, CDN drift,
  old unknown command, fake test artifact and unsupported
  compiler qualification.

## What Gesso v1622 implements, and what it does not

Inspected files in the supplied local v1622 checkout:

- `src/gesso/live/browser/entrypoint.clj`: canonical declaration
  resolution and browser-preflight compilation from source-owned
  plans; only selected fields may be qualified JVM Var references,
  with restricted build-time evaluation.
- `src/gesso/live/browser/artifact.clj`: pure closed
  `BrowserArtifactStamp`, plan-digest inventory, role, feature,
  transport and bootstrap correspondence; **not** actual emitted
  JavaScript inspection or runtime behavior proof.
- `src/gesso/live/browser/build.clj`: actual
  `build-application-artifact!` embeds the admitted manifest
  in a generated CLJS entrypoint and advanced-compiles it.
  `build-generated-artifact!` allows arbitrary emitters under
  narrower premises. `verify-generated-artifact!` compares
  the current manifest stamp and actual file digest/size with
  an on-disk receipt, failing closed for missing/stale/mismatched
  files.
- The v1622 publisher stages bytes but then moves the emitted
  JavaScript into its target and writes the receipt separately.
  Its verification fails closed if publication is interrupted,
  but the code does **not** itself implement a versioned,
  atomically activated multi-asset serving set or guarantee
  uninterrupted availability of the old generation after a
  partial publication. The finished architecture must retain
  that stronger requirement.
- `src/gesso/live/application_preflight.clj` checks the
  current browser artifact against the nested manifest when
  requiring ApplicationAssembly, including on the canonical
  checked rendered-response boundary. This is not independent
  proof that a deployed server always serves the checked path.
- Relevant tests include
  `test/gesso/live/browser/build_test.clj` (stale stamps,
  wrong bytes/receipts, emitter failures, generated entrypoint
  and compiler integration when available),
  `test/gesso/live/browser/artifact_test.clj`,
  `test/gesso/live/browser/entrypoint_test.clj`.
  Their code and presence were inspected locally; no fresh
  JVM, browser or XTDB test run is claimed in this review.

The current implementation's concrete one-output receipt shape
and narrow physical publication are not treated as restrictions
on the final architecture, which may require chunk bundles,
workers, CSS and deployed cache/asset coordination.
