## R4 preservation decisions

1. **One canonical source-owned composition.** R4 explicitly refused
   independent browser-build, preflight, startup, rendering and test
   registries. This requirement survives unchanged. Each producer owns
   its facts; assembly derives repeated identities and checks physical
   choices rather than copying an operation string into six maps.
2. **Concrete Claim decomposition.** R4 illustrated operation/Choreo,
   request-card affordance, HTTP method and Request path mapping, trusted
   handler, provider capabilities, Live card acquisition and browser
   manifest with separate namespace owners. R5.1 now includes a
   concise schematic source-owner composition plus a concrete
   Claim correspondence/counterexample table. The exact old helper
   spellings are not treated as implemented or mandatory APIs.
3. **Actual capability shapes.** R4's important
   `:clock -> :biff.fx/now` integration and typed Instant contract
   must be checked in the *actual* operation context. A named
   `:clock` provider is not evidence the executor receives it.
   Current principal, Request, RequestAssignment, Membership and
   Organization remain governed by the trusted model.
4. **Closed-world error cases.** Unknown operations, plans, routes,
   acquisitions and executors are rejected when their declared
   registry is closed. R5.1 also distinguishes a declared closed
   registry from a complete physical ingress/writer inventory.
5. **Identity and phases.** R4 distinguished semantic assembly identity,
   artifact bytes, admitted generation and deployment placement;
   it prohibited self-referential artifact hashes, stale evidence
   under changed Vars and silent in-place generation mutation.
   R5.1 retains that contract and expands dependency-specific evidence
   invalidation, construction/activation gates and retirement.
6. **Test/prod correspondence.** R4 required tests to consume the
   production constructor under explicit fixture configuration.
   A fixture-scope pass cannot prove the production handler, provider
   or asset binding.
7. **No duplicate product acceptance.** R4's example named Create,
   Cancel and other undeclared modules illustratively; it explicitly
   said omitted owners still had to exist. Claim-only closure cannot
   satisfy independent Create, Unclaim or manager Reassign acceptance.

## R5 features retained and improvements

The preferred R5 Section 07.02 already specifies ordinary full
Clojure/CLJS usage, source-owned derivation, checked opaque interfaces,
closed registries, acyclic construction phases, immutable admission,
typed semantic/manifest/asset/assembly/deployment identities,
per-use currentness and copyable diagnostics versus opaque issuance.

This revision strengthens that design rather than reverting to a
giant implementation-specific assembly map:
- Source inventories carry completeness, provenance and honest unknowns
  rather than treating omitted routes, workers or conditional renders
  as absent.
- A worked actual-Claim *contract*, not invented executable API, makes
  independent path/argument, executor, clock, loaded asset and
  acquisition choices checkable.
- Opaque callbacks have explicit purity, budget, effect and failure
  contracts; report generation cannot self-certify source behavior.
- Closed registries are qualified by source, profile and effect scope.
  Plugin installation and hot reload require fresh admission.
- Actual installation and activation checks are separate from a
  candidate's report, with cleanup of partial physical effects.
- Same-name or same-digest evidence is insufficient across different
  handler implementations, deployments or permission scopes.
- Retiring HTTP, subscription and background work retain their own
  generation rights; current model authorization and target ownership
  cannot be inferred from a frozen assembly.
- Ten concrete positive/adverse histories cover different Request
  targets, missing FX shape, conditional HTML, unlisted writers, hot
  reload, retired callbacks, fixture mismatch, server non-adoption
  and finite checker exhaustion.

R4's long example definitions of `request.choreo/claim`,
route/provider maps and proposed `gesso.application/*` functions are
preserved as *semantic obligations*, not copied as normative public
Var spellings. R5.1 retains the stronger architecture and makes the
lost concrete failure cases explicit.

## Current Gesso implementation correspondence

- `src/gesso/live/application_preflight.clj` has a current
  ApplicationAssembly via `require-application-assembly!`, nesting
  OperationAcquisitionAssembly, physical browser artifact/receipt
  verification, optional rendered Hiccup snapshots, and derived
  operation summaries and explanations. This is substantial
  closed-backbone implementation, but not all conceivable runtime
  writers or application entrypoints.
- `src/gesso/live/application_preflight/biff.clj` and the public
  wrapper/module/startup path check canonical Gesso HTML before
  serialization when actually installed. Explicit raw Ring HTML,
  direct Biff startup, later handler replacement and servers that
  do not use the wrapped `:biff.ring/handler` are named escape or
  deployment boundaries, not silently certified.
- `src/gesso/live/application_preflight/relational_definition.clj`
  has an opt-in one-source relational constructor, in-process handle,
  bounded exploration and executor-bound comparison. It does not
  generally prove Clojure callback purity, global writer completeness,
  full physical installation, universal model correspondence or
  complete product policy.
- Relevant actual test source files include
  `test/gesso/live/application_preflight/assembly_test.clj`,
  `biff_test.clj`, `rendered_response_test.clj`,
  `relational_definition/admission_and_exploration_test.clj`
  and `test/gesso/assurance/application_induction_mutation_test.clj`.
  Their repository presence was inspected; they were **not rerun**
  as part of this GitHub-only editorial change.

These are version-specific source observations, not current
application/deployment certification. Additional source-owned
inventory coverage, installation proof, opaque effects, all-writer
completeness and HumanHelp acceptance remain separate obligations.

## Cross-part boundaries and next work

Parts I–III retain independent structural, production and positive
behavior claims, source authority and choreography meaning. Part IV
retains model-controlled guarded XTDB Claim, RequestAssignment,
durable command identity and current principal rights. Parts V–VI
retain physical/browser source ownership, current asset identity,
one-Refresh authorization, Live recovery and obsolete continuation
retirement. Sections 07.03–07.15 must establish the exact
proposition/evidence closure, admission policy, route/FX/runtime
coverage, startup adoption and positive HumanHelp demonstration
without circularly trusting the assembly's own claims. Parts
VIII–XII and whole-plan reconciliation remain future work.

**Structural validation:** intended exact replacement of 07.02
in the published Part VII, unchanged nine CUSTOM_ID anchors,
balanced Org blocks, and source/readme/audit consistency.
GitHub-only work does not assert a local `assemble_r5.py --check`
or Gesso JVM, Node, Chromium, XTDB or formal test run.
