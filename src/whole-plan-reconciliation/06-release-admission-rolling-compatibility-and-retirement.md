## The question to resolve

A release can pass source checking and still fail in production if its admitted handler was replaced after checking, a server serves the wrong JavaScript, an A-origin browser calls an incompatible B route, B clients can reach A after a partial rollout, a stale callback mutates the new DOM, a running worker performs an effect using retired rights, or the attempted rollback reactivates an old adapter incompatible with the new database. Conversely, a failed old *execution* may leave one original logical command incorporated, whose authorized historical disposition must remain recoverable after the old writer is retired.

The cross-part requirement is neither "same version means safe" nor "every upgrade restarts everything." Gesso's normative design permits scoped, explicitly qualified continuity when the **source-owned meaning, current physical pair and runtime authority** justify it. Otherwise the correct behavior is a typed stop, safe retirement, and declared recovery—not silent downgrade, invented rejection or a stale protected action. A release is judged against an independently selected scope and original product/assurance denominator, not the subset of gates that happened to pass.

The original R4 Part XI already required incremental valid evidence reuse, actual browser artifact correspondence, no shrink-to-pass release, and four independent completion scopes. Preferred R5 retained that architecture while spelling out candidate/installation/activation and bounded rolling compatibility. R5.1 Part XI's eighteen reviewed sections make directionality, resource ownership, real host adoption, evidence provenance and adverse histories explicit. This review also challenges their joins with browser/Choreo, guarded commands, source-relative proof, Live and the implementation roadmap.

## Do not collapse identities, decisions or milestones

**Identity/evidence coordinates:**

| Coordinate | Meaning and qualified owner | Forbidden promotion |
| --- | --- | --- |
| Original claim and requirements | Product/release authority freezes scope, operation denominator, assurance profile, environmental assumptions and positive/adverse gates | Removing Reassign/Response or a physical writer after a failed check makes the same claim pass |
| Source-owned semantic subject | Exact normalized business operation, rules, public model contract, Choreo and supported interpretations | Same name or serialized source hash proves that a new Clojure implementation enforces it |
| Emitted realization and artifact | Exact browser/server protocol, decoder/encoder, CLJS bundle, source-dependent manifest, byte receipt and qualified toolchain | Filename, build receipt or bytes alone establish that the currently serving host/browser uses them |
| Assembly and installed host generation | Selected actual Ring/Biff handler, routes, executors, providers, workers, protected writers, credentials and assets | A tested local system map proves live server adoption or excludes all alternate writers |
| Directional continuation relation | One source/operation-specific **origin → actual target** mapping and required supported behavior/effects | The direction is symmetric, a fourth version identity, or valid for every operation |
| Runtime command/execution/resource | Immutable C42 intent, separately identified A1 attempt, live resource/DOM owner and current authority | Retiring an A browser proves C42 rejected or makes its old callback eligible for B's target |
| Proof and release record | Original-source-required proposition, trusted current checker/issuer, premises, actual host/environment and selected gate status | Copyable green report, cached derivation or earlier staging result authorizes protected work |

The release process has **four subject-specific decisions**: *candidate admission*, *installation eligibility*, *activation eligibility* and *completion claim*. A coordinated implementation may combine them procedurally while retaining distinct judgments and independent evidence. A candidate can pass without ever being installed; installation can be correct before public exposure; activation does not imply success of later individual domain actions or all requested milestones. A staging installation is not automatically a production installation.

The release gate has **eight mutually distinguishable required-result classifications**: `:passed`, `:failed`, `:incomplete`, `:unavailable`, `:unsupported`, `:skipped`, `:stale`, `:missing`. Only an actually applicable, independently validated `:passed` may discharge a required gate. These are not model outcome keywords, proof types or runtime admission credentials. A timeout does not prove falsehood; an unsupported theorem does not downgrade the originally selected strong profile.

The design also names **four independent completion milestones**: operational HumanHelp application, compositional certification, external formal verification with its stated S0–S4 transfer frontier, and actual multi-node production qualification. These are not the four release decisions and are not stages of one monotonically increasing generic `:certified` bit. An operational scope need not await unselected external-formal work, but a release originally requesting external-formal or multi-node completion may not silently remove those requirements.

## The reachable rolling matrix is directional and operation-specific

For activated predecessor **A** and selected new assembly **B**, source section 11.08 names **three identities/realizations plus one directional relation**, not four different versions. Which of the following is reachable depends on actual routing, browser assets, failover and already-started work—not just the intended load-balancer rule.

| Origin → server | Eligible behavior | Required adverse/fail-closed behavior |
| --- | --- | --- |
| **A → A** | Current still-activated A service handles a supported old plan under actual retained host/asset, resource, decoder and permission conditions. | A's browser plan persists past its real retirement/unsupported horizon and attempts a protected old effect. |
| **A → B** | Qualified exact-compatible or checked A-to-B adapter carries the original operation meaning, request/result representation and allowed recovery. | B parses a familiar-looking old envelope but silently changes Claim authority, command inputs, outcome semantics or Refresh grant. |
| **B → A** | Explicitly qualified new-to-old protocol *or* physically enforced routing exclusion prevents that target from being selected. | B's new field can reach A on fallback/redirect or stale sticky-session and A silently ignores it while executing a protected action. |
| **B → B** | B's actually installed and activated current plan, route, writer and asset prove the named current pairing. | Correct candidate manifest exists but the real server runs A's handler, decoder, policy or JS. |

Compatibility is checked **for each selected source operation or protected acquisition**. Claim mutation, read-only historical C42 reconciliation, collection Refresh, Live stream and browser effect have different requirements; compatible Claim does not imply compatible Reassign, board subscription or protected admin write. A successful A-to-B translation cannot be inverted to prove B-to-A.

If the deployment claims B-to-A is unreachable, that is an **enforced physical exclusion premise**. It must withstand stale clients, redirects, load-balancer changes, host failure, service-worker caches, old tabs, retries and any reachable alternate endpoint. Otherwise test and qualify the B-to-A pair or reject it before the first protected effect/disclosure. A load-balancer intent file or identical URL is not an observed exclusion. The default finite two-generation overlap can be widened under an explicit declared supported history; the predecessor is defined by *activation history*, not the preceding Git commit or a never-activated candidate.

A compatibility ruling admits no new principal, current model fact or browser physical mutation right. Every cross-generation invocation rechecks its applicable installed route, supported codec, current trusted authentication and authorization, protected model preconditions, selected provider/host, and resource-instance ownership. An old successful proof report or matching plan name cannot exempt those checks. An unsupported continuation has a typed stop/recovery outcome, **never** an unmarked ordinary HTMX downgrade or a guessed operation.

## A coherent release lifecycle, including non-atomic multi-host overlap

1. **Predeclare the release claim.** Fix original required capabilities, selected stage/milestone and proof profile, environmental qualifications, positive/adverse test set and intended topology. A change to scope/profile is an explicitly new claim. Preserve individual `:missing`, `:incomplete`, `:stale` and `:unsupported` blockers rather than collapsing them to a single boolean.
2. **Prepare an immutable candidate and admissible proof/build products.** Normalize exact semantic source/assembly, selected dependencies, compiler/normalizer/checker versions, generated plans, server wiring and actual browser bytes. Reject an unsupported required judgment. A previous valid certificate is *candidate reusable evidence* only after checking current original-source obligations and exact dependency applicability.
3. **Qualify installation at the actual intended host.** Verify current emitted asset/receipt and real handler, route, provider, worker and credential selection; include service-worker/proxy/alternate-writer premises where relevant. Prevent listener or background-worker *protected* activity before required effect gates are established. A system map checked locally is not a deployed-server witness.
4. **Admit and activate one coherent new-entry generation per installation scope.** Use an actual compare-and-activate/fence or justified equivalent, including expected predecessor and its current applicability. Avoid independently swapping dispatcher, writers, authorizers and HTML response guards so traffic sees a combination no candidate admitted. Per-host atomic selection does not imply a globally atomic rolling rollout.
5. **Enforce selected overlap and retention.** Identify all genuinely reachable A/A, A/B, B/A and B/B pairings; retain only necessary versions of endpoint, operation decoder, response/result codec, browser bundle, current issuer binding and historic C42 resolver for declared horizons. Do not treat a resource's mere presence as permission to execute it.
6. **Retire obsolete execution rights before stale physical actions.** A browser P7 or worker A may lose permission to submit, mutate a DOM target, consume a Live grant or send a privileged effect even if an external callback continues. Carry forward only independently justified command history, authorized draft/acquisition obligation or durable publication work. Retirement is not evidence of command rejection.
7. **If activation fails, perform a separately checked rollback/stop.** A now-old A candidate can be activated again only under current backend schema, domain state, protocol and writer/asset qualification. Rollback is a *new* controlled activation, not reversal of already committed Request domain history. If A cannot safely resume, fence or degrade through a declared separately supported recovery/availability path without exposing unchecked effects.
8. **Issue only the earned milestone record.** Candidate, installation, activation and product/formal/multi-node completion use different evidence. Keep the externally observed release and actual fault/scale/test scope, current open premises, denied operations and independently owned Response choice visible.

The source/implementation identity relation is subtle: a server-only model policy change **may leave some emitted CLJS bytes unchanged** and a physical adapter change **may leave an abstract proof still valid**. Neither permits stale dependent evidence. Revalidation follows *affected dependency edges*, not a rule that every edit changes every byte or that every reused hash transfers every qualification.

## Old command C42 survives without resurrecting A's execution

A's browser plan P7 submits Claim **C42**, physical attempt A1, to an actual host A. The request may commit but the browser loses the response while B is activated. There are at least four independent truths:

- the **historical command** C42 with its immutable original principal/authority scope, operation version, Request target and canonical arguments;
- the **physical attempt** A1 and its possibly lost/unknown response (which does not determine which attempt incorporated C42);
- the **current domain** Request/RequestAssignment after possible later Reassign or other change;
- the **browser execution** P7's resource/effect permit, which may already have retired.

P7's old callbacks, optimistic rollback rights, SSE owner and DOM target permissions can be revoked without erasing C42. B may provide a *read-only historical resolver* when it can authenticate the caller, validate original binding/version and retention, apply current result-disclosure policy and safely decode a qualified command record. This is not a right to run A's old Claim writer, perform an unchecked retry, conclude from a current Request card that C42 committed, or disclose a protected result to a caller who lost permission.

A compatible *same-command* retry, if the operation supports it and both original binding and current submission/retention gates permit, preserves C42; it does not invent C43 as a substitute. Failed A1, absence of a row at an insufficient basis, removed A assets, canceled stream and rollback to A are not sufficient terminal exclusion evidence. If no safe current resolver or retry remains, the honest result is unresolved/blocked/unavailable at that scope, with only declared authorized recovery and no false `:rejected`.

C42 retention/exclusion horizon, physical attempt retry horizon, result-decoder availability, old-plan/asset lifetime, outbox/invalidation recovery horizon and browser acquisition/Refresh grants may differ. One TTL or one release-generation marker cannot govern them all unless the design proves that shared policy sufficient. A retained durable command fence must prevent late old attempts from becoming new incorporations after payload erasure. A reused DOM selector or browser plan name must not restore old mutation rights.

For HumanHelp, rolling compatibility must also preserve the independently selected remote advisory-only, **one-use user Refresh** rule. An old client reconnecting on B does not acquire an automatic second board GET. Historical C42 settlement may authorize its **affected-Request** read but not an ungranted unrelated whole-board Refresh. Actual current Membership changes can require immediate protected denial despite the user's choice to defer otherwise ordinary remote lifecycle adoption.

## Requalification after change and defensible reuse

The correct evidence delta is proposition-specific:

| Change | Evidence that may be reusable after dependency checking | Evidence that must be requalified for affected claims |
| --- | --- | --- |
| Only commentary/diagnostic prose changes | Unchanged normalized semantic theorem, emitted bytes and installed path if truly independent | Diagnostic/privacy/display policy when it depends on changed text/source locator |
| Claim model guard or original product contract changes | Unrelated proof/source nodes after exact impact closure | Affected Claim semantic judgments, original required cases, browser/route bindings where depended upon, product positives, active gates |
| Browser compiler or emitted JS bytes change | Independent abstract Claim theorem if its source/interpretation unchanged | Artifact bytes/receipt, loaded browser asset, physical adapter/HTMX behavior, applicable A/B pairs |
| Trusted XTDB writer adapter or provider changes, abstract Claim unchanged | Source-level theorem under unchanged premises if issuer verifies it still applies | Actual transaction-internal guard/frame, writer capability, backend provenance, installed host correspondence |
| Deployment topology, router, credential or load-balancer rule changes | Unaffected abstract semantic/proof claims | Reachable A/B directions, protected entrypoint/current principal, router/fault/physical qualification and activation evidence |
| Backend schema migration or rolling rollback | Only evidence proven invariant under the changed schema/state/implementation boundary | New initial-state / transition mapping or migration proof, old/new writer compatibility, recovery decoder/retention, activation eligibility |
| Cached proof/report copied to another host | Copyable data may be inspected as a *candidate*, then checked under valid current subject/premises | Trusted current issuer, host/installed applicability, no hidden writer, current user authority and physical observation |

**Proof issuance is not a deployment capability.** Even a genuinely checker-backed JVM-local certificate is an abstract or conditional result for its admitted proposition, not a transportable signing key, authenticated browser role, semantic command grant or promise of exact deployed XTDB refinement. A serialized root report and cached evidence remain untrusted until a current consumer independently checks source-derived obligations and its specified issuer/evidence boundary. Unknown or unsupported evidence is kept visible, not laundered through a familiar digest.

## R4 preservation and substantive R5.1 reconciliation result

The R4 requirements retained are incremental rechecking rather than pointless world rebuilds; exact generated-artifact dependency; original requested release profile and no shrink-to-pass; failed/stale cache exclusion; real installed route/browser effect enforcement; tracked command/knowledge uncertainty; and four independently evidenced completion scopes. Preferred R5 source-first normalized semantics and composable release checks remain superior to a flat status manifest.

R5.1 resolves four areas where the joined contract needed greater precision: (1) the fourth “release coordinate” is a **directional relation**, not a fourth version identity; (2) locally coherent activation and globally rolling topology have different evidence; (3) execution/asset retirement, command historical disposition and application selected user Refresh are separately recoverable rights; and (4) certificate, cache, source-equal implementation and physically active host are distinct evidence classes with distinct requalification triggers.

**Editorial determination:** No blocking contradiction was found in the inspected source-to-release-to-retirement join across Parts I–XII. In particular, an abstract source-equivalent change may preserve a theorem while invalidating physical/host evidence, and a retired A execution may preserve C42's uncertainty without retaining A's ability to execute it. A failing required strong profile remains blocked while an independently approved narrower profile may progress under a different honest claim.

**No numbered Org source or preservation-audit edit is justified by this bounded review.** This editorial ledger cannot repair an undiscovered future normative contradiction. The original user-provided local source archive passed `python3 script/assemble_r5.py --check` for all twelve published Org parts; exact assembly integrity does not establish semantic or runtime correctness.
