** FX value flow and lifecycle

FX should make value dependencies and effects inspectable while remaining usable
from ordinary Clojure. Pure calculations consume explicit values and return
explicit values. Effectful steps declare their inputs, outputs, failure classes,
and effect boundary. A context is a capability-bearing environment, not a
hidden bus into which every step writes arbitrary intermediate state.

*** Context and values have different roles

The context may contain admitted database/acquisition capabilities, a trusted
principal binding, clocks or randomness with declared semantics, tracing, and
scoped backend interfaces. Intermediate Request data, candidate decisions,
prepared transitions, and outcomes should normally flow as explicit arguments
and results.

This permits the system to explain which value justified a step and to detect
missing or mismatched inputs. It also reduces accidental use of stale ambient
data. The machine's original invocation argument and its subsequent state
outputs are distinct value categories. A later step must receive needed
invocation values explicitly, through a declared retained-value binding or
other admitted value path; it cannot assume that the ambient context silently
accumulated them. The same applies to graph or multistate resolvers.

A capability's presence in context does not extend its lifetime or widen
its authority. Authentication state captured at entry does not freeze mutable
authorization unless that temporal policy is explicitly part of the contract.
The trusted invocation boundary owns capability provenance: an untrusted input
map may not overwrite a principal, clock, database handle, or other privileged
context binding through an incidental map merge. Missing required capability
bindings known at construction must be rejected before invocation; effective
runtime authentication, availability, expiry and current policy still require
their appropriate dynamic checks.

Graph or multistate implementations obey the same rule. They may provide a
convenient evaluation strategy, but hidden mutable cells must not become an
untracked second model of operation state. Pure dependency nodes and effectful
nodes require distinct semantics, including recomputation and retry behavior.
Passing a client value through a trusted FX step does not upgrade it into an
authoritative fact. A query result passed to another step does not become
knowledge of a remote choreography participant until its admitted communication
or acquisition path actually establishes that knowledge.

*** Ordering and completion are explicit

An ordered effect description specifies what each step waits for, how values
flow, and what happens after failure. Merely placing effects in a vector is not
enough if the interpreter may run them concurrently or treat enqueue as
completion.

An illustrative descriptor could distinguish:

#+begin_src clojure
{:fx/type :sequence
 :steps [:admit-command
         :resolve-or-prepare
         :incorporate-authoritative-transition
         :construct-response]
 :failure-policy :phase-aware}
#+end_src

The registered step definitions supply types, branches, capability requirements,
and completion semantics. The map alone is not an executable operation. In
particular, an effect's vector-valued argument is not implicitly an ordered
list of effects. An effect-order edge only orders execution as specified; it
cannot itself establish transaction atomicity, durable completion, or remote
receipt. The public operation advertises typed inputs, outcomes, authority,
pre/postconditions, effect classes and failure semantics without requiring
Choreo to inspect its private FX state graph.
Independent publication work may proceed separately once durable intent exists;
it need not delay an otherwise justified commit response unless the public
contract explicitly promises that stronger acknowledgment.

Exceptions are interpreted by phase and evidence. A failure before submission,
an ambiguous failure during submission, a post-commit publication failure, and
a response-rendering failure are different events. A generic catch that turns
all four into =:rejected= violates the operation contract.

| Phase and available evidence | Permitted conclusion |
|------------------------------+----------------------|
| Preparation fails before any possible submission. | The attempt did not submit; this alone is not a durable terminal command disposition. |
| Submission or response is lost without conclusive incorporation evidence. | The command disposition remains unknown pending admitted reconciliation; no blind new-command retry. |
| Commit is established, but publication or dispatch fails. | Preserve committed domain and command truth, classify the delivery failure, and retain required recovery debt. |
| Commit is established, but rendering or reply delivery fails. | Preserve the command outcome; the participant may lack settlement knowledge and needs its permitted resolution path. |

A later compatible command replay, a delivery-work retry, and a browser's
fresh acquisition are different operations. Retrying notification must never
re-execute the original authoritative mutation merely to make an observer
current.

Every submitted effect path—including an exceptional fallback, deferred FX
continuation and worker retry—must be admitted for the **actual complete**
transaction and its trusted caller/worker authority. A registered step graph
does not establish which callbacks or transaction options were used by the
installed runtime. The selected checker can derive the effect before issuing
an executor, enforce a final gate immediately before backend submission, or
admit a qualified opaque implementation premise. It cannot claim full
transaction correspondence merely because the initial step order is valid.
Likewise, a worker's legitimate recovery of a publication item authorizes the
promised delivery effect, not an unrelated replay of the earlier domain write.

Retryable backend callbacks must not contain unprotected external effects.
Clock and random values used in semantic decisions need declared sampling and
retry semantics. A clock or randomness facility is an ambient capability; its
particular sampled value is a semantically relevant result whose origin and
reuse across retries must be explicit. Ordinary Clojure functions and macros
may implement these steps, but any opaque effect footprint remains an explicit
contract premise.

*** Post-commit delivery debt
:PROPERTIES:
:CUSTOM_ID: req-post-commit-recovery
:END:

Once a command commits, failure to notify, render, or deliver does not uncommit
it. Required later work becomes explicit delivery or recovery debt. The
operation contract identifies what must be durable, who owns it, how it is
retried, and what counts as completion.

For a durable publication requirement, the domain transition and publication
intent must share an atomic boundary or an equivalently qualified discovery
mechanism. A commit followed by an unprotected best-effort publish can leave a
permanent gap if the process dies between those actions.

The intent binds the authoritative effect, relevant subject/query impact,
progression requirement, and stable delivery/work identity. It need not capture
every currently connected subscriber. A durable change log or outbox can feed
later routing and interest matching. The required impact must be derivable from
admitted source-owned change meaning and the selected application contract,
not solely from the subscribers known to one process at commit time. Matching
later-installed interests to that retained impact, or instead closing the
initial-read/subscription gap through a qualified acquisition fence, must
satisfy the promised awareness and recovery scope. This does not require
persisting a per-subscriber acknowledgment for every broadcast or retaining
every unrelated database change forever. Delivery semantics must state whether
duplicates are possible and how consumers recognize compatible repetition.

An in-memory list of local interests is not proof that all affected participants
will learn a change. If publication is conditioned on known interests, the
design must cover remote interests, subscription races, disconnects, and router
failover to the extent that its convergence claim includes them. Otherwise that
claim must be limited explicitly. The particular routing topology belongs to
the transport design; the no-lost-required-work obligation belongs here.

In particular, losing the process between authoritative commit and the first
in-memory publication must be covered whenever automatic notification is
promised. A durable change log, work intent, qualified reconciling acquisition,
or another declared mechanism may satisfy the relevant obligation; a live SSE
connection alone cannot. On subscription inception or reconnect the observer
must have an admitted way to acquire a sufficiently qualified state or recover
missed interests. If the only repair is user-initiated Refresh, the convergence
claim is explicitly conditional on that action.

Publication completion also has a scope: queued, durably recorded, accepted by a
broker, delivered to a connection, admitted by a participant, and adopted by a
projection are distinct milestones. The contract names the milestone it can
observe and retains downstream obligations where required. A work item may be
retired at a narrower milestone *only if* remaining promised obligations have
qualified independent owners, coverage or recovery. Replaying a publication
work item must not repeat the domain transaction whose impact it announces.
The same rule applies to a provider-result incorporation that creates new
publication impact: payment-work completion, local receipt incorporation and
Order-view dissemination are distinct settlements.

Recovery failure may leave debt visible and unresolved. It must not manufacture
success, discard the command record, or turn the committed domain operation
into a rejection. If an effect is intentionally best effort, its omission and
the resulting weaker guarantee must be part of the public contract.

*** Paired FX and recovery acceptance cases

| Admitted construction or history | Adverse or unsupported counterpart | Required judgment |
|-----------------------------------+------------------------------------+-------------------|
| A generated FX machine receives the invocation input in its first step and passes declared results to later steps. | A later step reads a previous result or the original input from accidental mutable context accumulation. | Admit explicit value flow; reject or expose the untracked dependency. |
| A trusted context supplies a declared principal and transaction capability. | Client parameters overwrite that capability or the required binding is structurally absent. | Reject privilege shadowing or knowably missing construction inputs; retain runtime authentication premises. |
| A pure query step returns a typed value with source provenance. | A subsequent step treats that value as current authority or remote participant knowledge without an admitted path. | Preserve provenance and role-local knowledge rather than upgrading a value by transport through FX. |
| Effect sequencing waits for the declared completion boundary. | A vector-valued argument is executed as a sequence, or enqueue is reported as authoritative completion. | Enforce the registered effect interpreter's actual ordering and completion semantics. |
| Submission fails before any possible incorporation, or an ambiguous submission is reconciled. | All thrown exceptions are mapped to durable business rejection or trigger blind resubmission. | Distinguish local attempt failure, unknown command disposition and admitted authoritative evidence. |
| Commit succeeds and a subsequent publication fails; the original command result is retained. | A catch rolls back the reported command truth, retries the domain mutation, or discards necessary propagation. | Classify post-commit delivery debt independently and recover only the appropriate effect. |
| A required scoped change intent survives process loss before any in-memory invalidation emit, and a successor or qualified reader reconciles it. | A successful domain commit relies solely on a later unprotected async dispatch, so crash erases the only recovery path. | Admit an atomic work intent or equivalent discovery/fencing guarantee; a post-commit error tag by itself is not durable debt. |
| A source-owned change impact is recoverable for a late or remote subscriber under the declared guarantee. | The commit-time emitter generates work only for interests visible at one router, omitting all late or remote interests without a read/subscription fence. | Cover the late-interest gap or weaken the stated awareness promise; do not demand per-recipient broadcast acknowledgments as the only design. |
| A disconnected participant returns through qualified acquisition or its declared Refresh path. | A missed SSE notification is assumed to arrive eventually with no retained work, inception coverage or recovery trigger. | Admit precisely the supported eventual-freshness claim; reject unconditional convergence. |
