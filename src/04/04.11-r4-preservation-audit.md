**Section:** `r5-source/04/04.11-authoritative-basis-and-xtdb.org`  
**Disposition:** eleventh substantively reviewed Part IV candidate section.
This is editorial semantic review of the finished-system specification,
not a deployed backend certificate, proof of all XTDB behaviors, or whole
Part IV acceptance.

## R4 requirements preserved

R4's “Authoritative basis and XTDB” and “Progression is visibility
provenance, not domain identity” distinguish a trusted AuthoritativeBasis,
an untrusted browser ObservedBasisClaim, and a scoped ProgressionRequirement.
Their concrete encodings need not be distinct public types, but the
meaning and admission boundary cannot be conflated.

R4 allows an intentionally XTDB-specific implementation rather than
inventing a portable global revision overlay. Domain revisions, command
identity, execution resources, XTDB basis, valid/effective time and
actor knowledge remain independent semantic coordinates.

The worked X17→X23 Request/Claim example is restored in a compact form:
unrelated database advances cannot invalidate a command by themselves;
an intervening competing Claim changes relevant business facts.
Submission carries an observed-basis *claim*, not authority or proof
the browser installed an observation.

R4 also requires read-after-commit consistency, meaningful acquired
scope, refusal to weaken unsatisfied minimum requirements, trusted
token origin, and explicit treatment of database version changes,
backend qualification and potential unknown incorporation. Proof of
an issued observation is not proof of delivery, installation, human
acknowledgement or current permission. All are retained.

## Stronger R5 design retained

R5 already provides a sharper contract for:
- Separate atomic publication, predicate/dependency protection,
  representation/frame, command exclusion, result interpretation,
  read visibility, durable recovery and writer coverage premises.
- Qualified adapter version/build, value codec, temporal options,
  supported transaction/SQL semantics and installed realization.
- The difference between an external pinned prestate, an actual
  transaction-internal read state and a later poststate; no universal
  requirement for a backend-internal prestate token.
- No false promotion of co-observation, ledger matching, guarded
  construction or source-bound result equality to general causality.
- Exact acquired basis versus requested minimum, query/authorization
  scope and both valid-time and system-time selection.
- Counterexamples and qualification failure propagating to dependent
  claims without marking uncertain commands rejected.

The revision retains this architecture; it does not force a new
backend-neutral token algebra or claim complete XTDB verification.

## Focused normative changes

1. State XTDB-first adapter specialization and explicitly distinguish
   AuthoritativeBasis, ObservedBasisClaim and ProgressionRequirement.
2. Explain why structurally valid or previously server-issued tokens
   from a browser do not authenticate delivery, installation,
   acknowledgement or authorization.
3. Require conformance coverage for lost/unknown outcomes, malformed
   scope, field/frame, temporal choices, cross-document/absence
   dependencies and concurrency, not only a dependency version string.
4. Clarify whole-document writes, incomplete guards and unenumerated
   writers as independently visible refinement premises.
5. Distinguish returned submission IDs, committed transaction keys
   and pinned command-record observations by their actual evidence
   provenance and exact claimed subject.
6. Restore the X17/X23 Claim example with RequestAssignment as the
   correct source of primary-helper truth.
7. Add eight paired positive/adversarial cases covering trusted basis,
   current dependency admission, complete guards, command causality,
   scoped reads, pinned snapshot limits, backend changes and database
   incarnation.

## Current implementation correspondence (Gesso application-assurance v1622)

`src/gesso/live/consistency/xtdb.clj` provides XTDB2 query/transaction
wrappers and closed portable basis/progression representations. Its
documented `execute-tx!`/TransactionKey path obtains tx-id and system
time for read-consistency metadata; `submit-tx!` alone supplies less
information. The request-frontier helper binds one latest-completed
basis and fails closed on an incompatible stronger requirement.
These are concrete implementation supports, not proof that every
browser-provided basis or deployed read path is trustworthy.

`src/gesso/model/tx-refinement-xtdb.clj` explicitly describes
before/after acquisition as separate pinned observations under a
controlled no-intervening-writer diagnostic premise. It does not
establish transaction-internal prestate, full external-writer closure
or universal refinement.

`src/gesso/assurance/proof/xtdb-guarded-prestate-acquisition.clj`
constructs bounded prewrite ASSERTs from an external read, but does
not itself submit the result or attest internal snapshot/coverage.
`xtdb-gateway-complete-guard-execution.clj` tightens one-document
top-level field and count protection; it does not protect arbitrary
nested attributes, related documents or nonparticipating writers.
`xtdb-gateway-monotonic-revision-execution.clj` adds conditional
revision constraints with an explicit all-writers premise.

The v1616 readback gateway and v1622 command-outcome bridge join an
original local return and same-basis physical observation, but both
explicitly decline transaction-causality, independent authentication,
complete writer coverage, general refinement and browser settlement
claims. These improvements must be preserved without being presented
as an already complete Gesso certification of XTDB.

These source statements were inspected through the GitHub connector.
No XTDB tests, concurrency checks, browser runs or actual backend
qualification were executed for this document revision.
