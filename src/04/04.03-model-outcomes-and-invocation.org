*** Model outcomes and invocation errors

The operation interface uses the following model outcomes:

| Outcome | Required meaning |
|---------+------------------|
| =:committed= | Qualified affirmative physical evidence attributes incorporation of the bound command to the reported admitted submission (or an equivalently justified invocation-specific mechanism). It does not mean that later propagation or presentation succeeded. |
| =:already-incorporated= | A compatible retained command record establishes that the command was incorporated; this resolution path returns the permitted historical result without another incorporation. The record alone does not attribute the winning physical attempt or prove incorporation predated an earlier ambiguous submission. |
| =:rejected= | The declared authoritative rejection/closure policy establishes that the bound command is terminally rejected within its promised scope; one failed preparation or physical attempt is insufficient. |
| =:commit-unknown= | Available evidence does not establish a permitted definitive command disposition. The command may or may not have incorporated, even when one particular physical attempt is known not to have committed. |

Outcome variants have closed discriminants and variant-specific payload schemas.
A successful variant carries command binding and result evidence; a rejection
carries its permitted reason and disposition evidence; an unknown variant
carries the admitted reconciliation reference and uncertainty classification.
Fields are not made optional merely to allow every variant through one loose
map schema.

A model outcome, a physical *submission-attempt* result, the historical
semantic command disposition, and a participant's *permitted knowledge* of
that disposition are different subjects. A positive, correlated backend
acknowledgment can justify an invocation-specific =:committed= result under
the qualified adapter contract. A later read of the durable command record
can establish incorporation of the command while leaving open which of two
attempts performed it; that read supports the compatible recovered-result
path, not invented evidence that the immediately preceding submission
succeeded. Physical submission receipt, transaction acknowledgment, actual
authoritative incorporation, result disclosure, Live delivery, and browser
installation are not one terminal event.

An invocation-specific =:committed= result requires qualified physical
evidence tying the *actual complete submitted effect*, its command binding,
trusted principal/authority, and affirmative outcome to the reported
submission or invocation. Co-observing a transaction key and retained command
record at one compatible pinned basis can establish narrower facts; it does
not by itself identify the attempt that caused the record. Abstract transition
proof does not supply that missing physical causality.

Conversely, a compatible retained command record can justify the historical
=:already-incorporated= recovery path without naming the winning attempt.
Qualified binding-scoped terminal closure, not a failed guard or absent row,
is required for stable =:rejected=. Otherwise a physically failed attempt,
timeout, incomplete result or unestablished backend premise leaves the command
unknown or supplies only a narrower typed attempt/invocation failure. These
classifications cannot be strengthened by exchanging report-shaped maps.

An authoritative readback must preserve its *own* observation scope, basis,
completeness and trusted origin. If a command record is not observed after
a timeout, absence at one insufficient or stale read is not evidence of
non-incorporation. If a command record *is* observed, matching the stable
ID alone is insufficient: its full bound operation, authority, principal,
canonical arguments and compatible interface must be checked before
returning a recorded result. When the present principal is no longer
authorized to learn it, disclosure can be unavailable despite known
incorporation. An observation of a Request's present =:claimed= state
cannot replace this bound command evidence.

Rejection has a similarly exact boundary. A failed authorization precheck
may prevent *this entry attempt* from proceeding; an explicit backend
assertion failure may establish that *this transaction attempt* did
not incorporate. Neither necessarily proves that a concurrent compatible
attempt did not or will not incorporate the semantic command. A terminal
=:rejected= outcome requires its promised authoritative exclusion/closure
evidence, or a specifically narrower declared rejection policy that
does not masquerade as permanent command closure. Otherwise use the
appropriate typed invocation failure, physical attempt result, or
unresolved command disposition. Do not manufacture a durable rejection
record from a transaction which definitely aborted without storing one.

Malformed inputs, unsupported interface versions, incompatible reuse, invalid
credentials, disclosure denial, and backend qualification failure require typed
handling. They are not all domain rejections. For example, an unauthorized
caller must not be able to create a terminal rejection record for somebody
else's command. A disclosure denial must not falsely say that the command was
never incorporated. Privacy policy may require an intentionally indistinguishable
unavailable response for several underlying conditions. Likewise, a caught
exception, a failed post-commit advisory, or a delivery timeout cannot be
reclassified as a domain rejection. A known incorporated command remains
incorporated despite failure in a separately owned publication/response
stage; if the physical outcome is genuinely indeterminate, preserve unknown
until qualified evidence resolves it.

The outcome recorded for replay is a historical operation result. A Request
projection freshly acquired alongside it has a different meaning: it describes
state at that acquisition's scope and basis. The API must distinguish these
values. It must not imply that a recorded successful Claim guarantees the
Request is still assigned to that helper now.

This distinction is also a *role-local branch knowledge* obligation. A
continuation about whether the historical command C42 incorporated may use
qualified, currently disclosable C42 result evidence if the authored
choreography admits that acquisition path. A continuation about who is
currently primary helper may instead use a scope-complete authorized
Request/RequestAssignment observation at its own basis. These are different
propositions, even when their rendered values happen to agree. A role
requiring one cannot substitute the other, nor infer that another actor
received an approval message merely because the authority recorded C42.

An alternative authoritative observation may satisfy the *knowledge
premise* of a differing branch without a dedicated message. It does not
automatically replace a globally required send/receive action, its
acknowledgment, causal ordering, waiting semantics or failure path.
The authored protocol must declare the alternative or a qualified
refinement must preserve those effects. The local actor obtains the
evidence before its first differing behavior, with current owner,
subject, scope, source, permission, temporal and command/decision
correlation. This joins the
[[#req-projection-branch-knowledge][projection knowledge rule]]
without introducing a second operation/outcome type system.

Presentation mapping is explicit:

| Model evidence | Presentation settlement |
|----------------+-------------------------|
| Permitted committed success | =:accepted= for the bound presentation operation. |
| Permitted already-incorporated success | The same accepted successor, without a new incorporation. |
| Authoritative command rejection | =:rejected= through the declared rejection branch. |
| Commit unknown | =:unknown= until admissible reconciliation evidence resolves it. |

A model may define successful results other than Claim success, and rejection
details may be undisclosable. Assembly must check the actual variant mapping,
disclosure requirements, and permitted presentation effects. A new command ID
is not an acceptable way to disguise an unresolved retry. Presentation
settlement additionally requires that the evidence be admissible to the
*current* bound execution and resource owner. A correct model outcome
cannot resurrect a retired browser execution, justify unrelated remote
adoption, or discharge a required physical installation that never happened.

*** An explicit invocation sequence

The following logical phases may be implemented by one FX pipeline or several
cooperating components. The semantics must survive either arrangement.

| Phase | Responsibility | What it does not establish by itself |
|-------+----------------+-------------------------------------|
| Admit | Validate inputs, operation/interface identity, trusted principal, and capability. | Permission to commit after mutable authorization changes. |
| Resolve or prepare | Recover a compatible prior result, or acquire data and compute a candidate. | A pre-read is not the atomic command-existence guard. |
| Incorporate | Protect semantic dependencies and atomically establish the domain transition, command record, and required durable intents. | A submitted request is not necessarily a committed transaction. |
| Propagate | Attempt publication or arrange durable recovery according to the operation contract. | Delivery success to all participants. |
| Respond | Return only the outcome and observation evidence the invocation can justify and disclose. | A browser has received, installed, or adopted the response. |

Replay does not blindly rerun notifications or other effects. A recorded durable
intent may remain unfinished and be resumed by its declared recovery owner, but
it retains its original work identity. A compatible replay is not a new reason
to create a second notification or charge.

Each phase may run on the same host or on a later compatible application
node. The semantic command binding, trusted model rules, durable disposition
and presentation/adoption policies do not change with host placement.
Cross-host reads still need qualified sufficient progression; neither
local cache agreement nor the fact that both hosts use the same logical
database automatically establishes this.

*** Outcome and invocation acceptance cases

| Case | Required judgment |
|------+-------------------|
| A fresh Claim receives a qualified affirmative transaction acknowledgment bound to the actual submitted attempt | Report justified =:committed= for that invocation; record durable notification debt separately from advisory/browser delivery |
| A Claim submission loses its acknowledgment, then a compatible command record is acquired authoritatively | Return the permitted recovered historical result; do not claim the readback identifies which attempt performed incorporation |
| Two concurrent physical attempts share one compatible command ID, and one has a confirmed assertion failure while the other incorporated | Preserve the unsuccessful *attempt* and the successful *semantic command* as separate facts; do not report terminal =:rejected= from the failed attempt |
| An input is malformed or the caller lacks an authenticated principal before any submission | Return the corresponding typed invocation failure without inventing a terminal command-rejection record |
| A terminal command rejection is promised, but an abort did not record a binding-scoped exclusion and another attempt may still commit | Do not report stable =:rejected= without a qualified closure/fence; preserve uncertainty or a narrower explicitly scoped failure |
| A known incorporation is followed by a failed Live publish or missing browser settlement | Preserve committed authoritative state and any outstanding propagation/adoption obligations; do not turn a post-commit failure into business rejection |
| An authorized read finds a compatible command record and a newer RequestAssignment state after later Reassign | Disclose the historical Claim result separately from the qualified current projection; do not assert that the previous primary helper still owns the Request |
| A helper continuation explicitly permits learning C42's historical disposition from a qualified command-record observation | Admit the branch only after the recipient acquires the exact disclosable C42 result with its plan/decision correlation; a later Request status is insufficient. |
| A choreography requires an authority-to-helper approval message and no read alternative or qualifying refinement was declared | Do not erase the message/receipt or synthesize its causal history merely because an authorized reread reports =:claimed=. |
| An old command record is found but the current principal lacks permission to disclose its outcome | Preserve the authoritative fact internally while returning only the permitted unavailable/indistinguishable result |
| A replacement browser execution receives valid evidence about an old command | Admit it only through its current authority, ownership, resource and presentation mapping; the retired execution does not regain installation rights |
| A host retries an unresolved command on another web node using the original immutable binding | Preserve the same resolve-or-incorporate rule, current backend/progression qualification and disclosed outcome contract; node placement does not create a new command |
| Concurrent same-binding attempts A1 and A2 target C42; A1 aborts while A2 commits, and a qualified read finds C42. | Admit the historical compatible recorded result; never infer A1 committed or that the command was terminally rejected by A1's abort. |
| A completed transaction key and command record are co-observed but the full-submission causal bridge is not established. | Preserve bounded physical evidence and historical recovery, but do not report invocation-specific =:committed= solely from coincidence. |
| A terminal rejection fence and a pending incorporation attempt contend under the qualified command namespace. | Only established binding-scoped exclusion permits =:rejected=; an isolated failed guard or absent-record read does not. |
