**Section:** `r5-source/04/04.06-command-identity-and-incorporation.org`
**Disposition:** sixth reviewed sectional R5.1 Part IV candidate. The

## R4 preservation and R5 architectural improvements

R4 Part IV `Command identity and execution identity`, `Semantic
command identity survives physical retry`, `Command identity is
not idempotency policy`, and the later distinctions from operation
and projected-plan identity require:

- independent command, operation, execution, transport, principal,
  capability and resource-instance identity meanings;
- survival of a semantic command across HTTP retries, web-host
  replacement and compatible plan replacement, without reviving
  retired local execution rights;
- explicit model-owned durable replay/deduplication policy rather
  than an implication from a UUID;
- complete semantic binding checks and authorized disclosure;
- an atomic command uniqueness guard jointly protecting the domain
  effect, not an unguarded pre-read followed by result recording;
- continued authorization and qualified reconciliation across
  host replacement and lost responses.

R5 already improved on R4 with canonical argument and interface
versions, source/implementation binding, per-attempt evidence,
postcommit uncertainty, retention horizons and scoped replay.
This revision retains those stronger obligations and restores
more explicit physical namespace, cross-host and race behavior.
It does not impose one database schema, a single global ID type
or a particular Gesso helper name.

## Gap 1 — physical command namespace versus public identity

The authoritative lookup key must represent the *declared*
command namespace and stable ID without aliasing two legally
different commands from separate tenants/authorities. A record
key locates a candidate but does not prove binding compatibility
or provide authentication. Current permission to disclose the
historical result is a separate admission judgment.

Canonicalization across omitted/default fields, numbers,
collections and schema revisions must be versioned when its
meaning matters. A compatible upgrade may explicitly carry
an older command into a newer interface. An incompatible
upgrade cannot silently bind the old ID to a new action
or mistake a new projected execution for a new command.

These conditions make one semantic command a durable,
recoverable *intent* rather than a transport or host token.

## Gap 2 — physical absence, concurrency, and two exclusions

The read-before-plan resolver is not the linearization point:
two callers can both see a missing record. A negative lookup
at a stale or wrong scope is not a reliable absence
observation, and even a correctly scoped absence read
does not exclude a concurrently pending incorporation.

For Claim, the protected backend decision needs both
command uniqueness and the independent production
RequestAssignment active-primary uniqueness/lifecycle rule.
A duplicate command can be suppressed while two *different*
command IDs still try to claim the same Request. An
unprotected command-result write after a domain mutation
does not give exactly-once incorporation.

The new positive/adversarial matrix covers eleven cases
including compatible replay, overlapping identical and
incompatible attempts, distinct tenant namespaces,
two-command Claim contention, stale/lagging read, post-Claim
Membership changes, nondisclosable record, upgrade collision,
and out-of-band writer bypass.

## Actual Gesso source observed at v1622

Inspected the `application-assurance` branch:

- `src/gesso/choreo/identity.cljc` defines distinct tagged
  identity categories such as principal, actor, authority,
  host, semantic command and execution, but deliberately
  does not authenticate users or define command durability.
- `src/gesso/model/command_resolution.clj` has an
  experimental *closed* four-key command binding:
  `:command-id`, `:principal`, `:operation`,
  `:arguments`. It uses the command ID raw value
  as the record key in `:gesso_commands`, and adds one
  command-result record creation to the *same* normalized
  model transaction. Its assurance scope does not establish
  tenant-scoped command keying, full business authority,
  all domain guards, outbox work or universal concurrency
  correctness.
- Its `reconcile` uses a separately trusted disclosure
  predicate, returns unresolved when no record is observed,
  unavailable on denied disclosure, incompatible on an
  observed mismatched binding, and replay on a disclosed
  compatible record. It does not by itself perform an
  authoritative read or schedule retries.
- `src/gesso/model/resolved_operation.clj` implements a
  trusted submit/reconcile wrapper. It checks a retained
  record before building another transaction, injects
  an actual command-record write, and rereads on ambiguous
  submission. The wrapper's optional construction/target/
  predicate/outcome contracts are checked subsets, not
  a declaration that every deployed writer or tenant
  namespace is covered.
- `test/gesso/model/command_resolution_test.clj` and
  `test/gesso/model/resolved_operation_test.clj`
  contain positive/negative regression cases for
  exact binding, duplicate result creation, stale
  Membership guards, incompatible records, disclosure,
  lost acknowledgment and real XTDB observations.
  Tests were inspected, **not executed** in this revision.

The current raw-ID command record is a documented bounded
implementation, not an implied promise that it provides
namespaced multi-tenant idempotency. The finished-system
requirement leaves open globally unique IDs or safely
namespaced physical keys under a qualified authority
and compatibility policy.

## Cross-part and adjacent sections

- **04.07:** terminal rejection scope, record retention/
  expiry and upgrade compatibility need their independent
  adversarial review; a rejected *attempt* is not a
  terminal *command* closure.
- **04.08:** a lost-response reconciliation must recover
  C42 without attributing which attempt won, fabricating
  current RequestAssignment state or reactivating an old
  browser execution.
- **04.09–04.10:** durable command uniqueness does not
  establish exactly-once external provider work or
  notification delivery; these need separate effect
  identity, compensation and recovery.
- **04.11–04.16:** authoritative basis/visibility,
  freshness and correct browser adoption need separate
  qualification. A host-local cached negative result
  cannot certify command absence.
- **Parts VII–VIII:** the actual production model,
  tenant/actor authority, RequestAssignment writers,
  installed handlers and real durable-work policy
  must close the source-to-physical correspondence.
- **Parts IX–XI:** finite tests, semantic-model proofs,
  backend adapter premises and installed production
  evidence are different assurance subjects.
- **Parts X/XII:** running the same application on
  several web nodes does not change its command/
  Claim semantics. Router assignment/replay and any
  Rust acceleration are physical realization choices.
