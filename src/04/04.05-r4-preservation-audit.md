R4 Part IV's `Preparation may be rich without weakening atomic
publication` described compatible Request/Membership/Organization
observations, a separate trusted actor, a pure Claim candidate decision,
command resolution before treating a new-command precheck as final

## Corrected production RequestAssignment meaning

The old candidate rejected Claims by testing
`(some? (:request/helper request))`. The revised illustrative
Clojure function instead consumes a distinct model-owned
`assignment-observation` of active *primary* RequestAssignment
facts, separated from collaborator assignments. It requires
a scope-complete read for the exact Request, with qualified
provenance/basis and authorization independently supplied
by the actual acquisition boundary.

A complete empty active-primary result may support a pure candidate;
a partial empty page, absent field, failed read, or out-of-scope query
does not prove there is no primary helper. More than one active
primary reports invalid observed state, not false eligibility.
A terminal Request without an active primary is not automatically
claimable. All of these are candidate classifications, **not**
authoritative command dispositions.

The selected backend must still protect absence/uniqueness against
concurrent primary-assignment insertion, current
Membership/Organization policy, Request lifecycle and proper frame.
It atomically establishes the Request, RequestAssignment,
bound command result and durable work for the Claim example's
selected publication profile. A Request-only version guard or a
caller-crafted `:observation/coverage :complete` map is inadequate.

## Capability and representation review

A copied inspection map, structural admission report and
request-local capability are not interchangeable with a
production mutation authority. A one-shot capability
can exclude competing use of *that instance*, but cannot
durably deduplicate independent invocations of the same command.
Retired capabilities are not revived by remote replay; a durable
worker needs its own admitted execution right and retained work
identity. This remains one semantic model in single-node and
multi-node deployments.

The R5 provisions for physical field mapping, omitted versus nil
values, whole-document stale overwrite, revision discipline,
and non-repetition/ABA history remain unchanged. The negative
RequestAssignment query adds a concrete correctness-relevant
query-coverage case beyond those field-level distinctions.

## Positive and adversarial acceptance

Nine explicit cases cover positive complete/eligible observations,
partial empty pages, collaborators, misleading Request helper
absence, stale Membership or assignment insertion, stale
whole-document replacement, copied cross-host capability,
racing one-shot consumption, and legitimate later durable
worker processing. These paired cases preserve usable positive
capability, not merely a reject-all gate.

## Implementation evidence inspected

Gesso `application-assurance` v1622:

- `gesso.model.core` derives Malli-backed schemas, Graph
  projections and simple FX; complex relationships remain
  application-owned.
- `gesso.model.command` implements generic version/check
  representation without independently proving business authorization.
- `gesso.model.tx-refinement` treats XTDB's top-level nil
  omission explicitly, but does not prove nested transformations,
  observed truth, physical isolation or complete policy input coverage.
- `gesso.model.tx-refinement-xtdb` executes controlled XTDB
  comparisons using pinned before and after read phases, with
  open assumptions about real transaction-internal read scope
  and unrelated writers. No universal refinement theorem follows.
- `gesso.assurance.admission` uses in-process structural
  handles and explicitly excludes production authorization
  and cross-process transfer as guarantees.
- `gesso.choreo.realization` is a portable deterministic
  realization harness, not the physical web/server/XTDB
  execution layer.

These sources inform the normative design, not a claim that
production HumanHelp Claim, query-completeness and worker
issuance are already certified. No runtime test was executed.
