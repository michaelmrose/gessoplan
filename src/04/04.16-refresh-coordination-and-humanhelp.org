*** Worked example: two advisories during one refresh

Let B denote one complete authorized HumanHelp board acquisition for the
selected Organization and Location, declared collection bounds, projection
version, visibility context and temporal policy. These authoritative query
properties are fixed for this example; local text search, sorting, priority
ordering and terminal visibility are *presentation* over the adopted cohort
and may change independently while a read is in flight. The board owner and
target are one admitted resource instance. The board has adopted an
observation at P17.

The provider establishes that an observation through P18 includes the change
announced by O1, an observation through P20 includes the change announced by O2,
and P21 covers both requirements in this compatible scope. It also establishes
the advancement relations used below. These are admitted provider judgments,
not arithmetic inferred from the names.

Advisory O1 creates an acquire-and-adopt obligation for B through P18. The user
chooses Refresh. That action grants one logical acquisition under HumanHelp's
declared scope and lifetime, not indefinite permission to fetch or install
later remote changes. The coordinator allocates a fresh acquisition resource A1
under the managed lifecycle and issues the read for O1's requirement. Its
identity is not merely a reusable request number; reuse would need a separate
admitted instance discriminator. The grant binds the current principal, board
owner, authorized Location/Organization, selection, acquisition scope,
progression requirements and permitted adoption transition.

While A1 is outstanding, advisory O2 creates a further obligation for B through
P20. The coordinator must retain O2. Completing A1 must not restore an old copy
of the obligation set captured before O2 arrived.

Assume the application permits adoption of a non-regressing partial advance
while stronger advisory debt remains visible. The sequence is:

| Event | Adopted board | Retained acquire-and-adopt debt | Required action |
|-------+---------------+--------------------------------+-----------------|
| Initial admitted state | P17 | None | No refresh required. |
| Receive O1 | P17 | O1 through P18 | Offer or schedule acquisition under the product policy. |
| Start A1 for O1 | P17 | O1 | Record current acquisition ownership and requirement. |
| Receive O2 | P17 | O1 and O2 through P20 | Retain O2 while A1 remains outstanding. |
| A1 completes with admitted B observation at P18 | P17 | O1 and O2 | Validate coverage; prepare a permitted installation. |
| Installation is allowed but has not completed | P17 | O1 and O2 | Keep adoption debt; permission is not completion. |
| Installation of P18 completes and is admitted | P18 | O2 | Adopt the covered advance and discharge O1 only. |
| Later permitted acquisition and installation covers P20 | At least the required frontier under provider evidence | None of these two obligations | Discharge O2 using its actual coverage and completion. |

If A1 instead returns an admitted B observation at P21 and its installation
successfully completes, that evidence can discharge both O1 and O2. The
coordinator checks the latest obligation set at completion, not only the set
that happened to start A1. The acquisition's actual evidence can be stronger
than its requested minimum.

If installation fails, neither acquire-and-adopt obligation is discharged by
that attempt. The acquired observation may remain available as evidence under
its lifetime and disclosure contract, but the visible board has not thereby
adopted it. An HTTP success response or HTMX swap permission is not completion;
any partial physical update or lost completion requires qualified inspection,
repair or reacquisition under the current owner.

If a different permitted path already adopted P21, the late P18 response must not
roll the board backward. The existing adopted P21 evidence may already satisfy
O1 and O2; that is a separate justification for discharge. Rejecting the late
installation does not mean the coordinator must keep debt that independently
admitted adoption evidence has already fulfilled.

An application may instead require an acquisition to satisfy all current board
debt before adopting anything. Under that policy, P18 is retained or discarded
as acquired evidence and the coordinator requests enough evidence for P20.
Either policy is valid when declared; the framework must not switch between
them accidentally according to response timing.

For the HumanHelp proving application, the selected policy permits the P18
non-regressing partial advance but keeps O2 visible. One user Refresh grants
one logical board acquisition and does *not* silently grant an automatic
successor read merely because O2 arrived in flight. A separate explicit
Refresh/Retry, or an independently declared bounded repair grant, is required
for the next physical read. Repeated user clicks while A1 is active can be
coalesced only under the specified bounded successor-intent policy; they do not
create an unbounded automatically draining queue. The generic browser adapter's
physical scheduling strategy must be qualified against this policy rather than
being treated as the policy itself.

*** The coordinator's semantic obligations

The example is implemented through admitted transitions, not direct mutation by
arbitrary transport callbacks. A useful transition decomposition is:

1. =advisory-received=: admit source and scope, then add or soundly combine debt.
2. =acquisition-requested=: validate or allocate the current acquisition grant,
   allocate the managed owner/resource, and bind the authorized query, requested
   scope, progression, grant budget and lifetime to a declared effect.
3. =acquisition-completed=: admit the effect completion and observation, then
   determine which requirements its evidence can cover.
4. =installation-requested=: propose only the permitted effect for the current
   target and owner; preserve obligations still awaiting adoption.
5. =installation-completed=: admit actual completion, update justified adoption,
   and discharge only obligations fulfilled in the current state.
6. =acquisition-failed= or =installation-failed=: retain unresolved obligations,
   release or retire resources according to policy, and select the declared
   recovery continuation.

These are semantic phases, not a mandatory source-file layout. Part VI specifies
their browser realization and the refinement between DOM effects and semantic
adoption. The permanent executable semantic core owns the transition meaning;
proof artifacts explain why the admitted realization preserves it.

Every completion checks current owner, resource-instance, acquisition-grant
and target correlation. A response for an obsolete server-side query
selection, principal context, Location, Organization, page/window, route or
target instance must not install merely because its database basis is recent.
Changing only HumanHelp's local search, sorting or terminal-visibility controls
does *not* make an otherwise compatible full-cohort acquisition obsolete. The
completed board may be installed under current ownership and rendered with
the *current* options; response-time display options must not overwrite those
newer local choices. A change to Organization, Location, declared window,
principal or authority context does change the acquisition scope and requires
an appropriately new owner/grant. Evidence may be usable through another
declared admission path, but cannot resurrect a retired execution's rights.

The same principal may operate multiple HumanHelp board actors, each with
its own installed cohort, advisory debt, Refresh grants, search options
and physical target. One tab's P20 installation or explicit Refresh does
not become another tab's adopted knowledge or acquisition consent.
A later command resolver may legitimately disclose a historical result to
another authorized actor, but does not thereby transfer the original
execution's branch knowledge, optimistic overlay or DOM rights.

Logout, principal/Organization switch or established loss of disclosure
retire incompatible subscription, acquisition and pending installation
rights under the supported browser policy. Alice's late HTTP/SSE response
must not become Bob's current board content after account switch.
Protected server reads, mutations and disclosures remain independently
authorized; client cleanup cannot retract data already seen by a malicious
or offline browser. Durable command and work records survive under their
own binding and recovery policy without disclosure to the new principal.

The obligation set is updated from current state. Removing O1 must not remove a
newer obligation with a superficially similar key, overwrite a concurrently
added scope, or clear a global dirty flag representing several independent
requirements. Sound coalescing may replace the representation, but must preserve
the combined meaning.

*** HumanHelp's selective adoption policy

HumanHelp can use these generic contracts to show the creator's own committed
Request immediately through a correlated admitted result, while other viewers
receive an advisory and explicitly refresh board membership. Remote creation
and remote lifecycle changes to already visible Requests both follow explicit
Refresh for ordinary board adoption. A user's own confirmed Create, Claim,
Unclaim, Reassign or other admitted operation may update only its declared
correlated Request-card or selective membership scope, provided the operation
and current trusted disclosure permit that result. The policy must state which
scopes a correlated operation result can update and how that update relates to
the existing board selection. An SSE advisory cannot carry authoritative
Request status, current helper ownership or permission to silently install it.

A card outcome can update an already adopted Request without proving a complete
new board query. The currently active primary RequestAssignment, not a cached
helper field or provisional card label, establishes authoritative Claim
ownership under the source-owned model. An operation that introduces or removes
a visible row needs an explicit membership-adoption rule. Filters, sorting,
retained selection, scroll continuity, and optimistic overlays must not cause
that scope distinction to disappear. A card conflict reread may correct that
one Request without adopting unrelated board membership or proving that an
outcome-unknown command incorporated.

*** Interleaved Refresh and newer local Request evidence

Bob begins one explicitly granted board Refresh A1. Its complete Location
cohort is read at P18. Before A1 installs, Bob's own confirmed Create S
incorporates and its authorized correlated result installs at P19, selectively
admitting S to the cohort. A1's P18 read may still cover its board *acquisition*
requirement, but physically installing that older board must not erase S, its
selectively adopted membership, or the accessible "Your new Request" result.
The combined P18 cohort and S/P19 card are not one complete P19 board snapshot,
and S's later basis cannot clear O2/P20 or import remote R.

The authorized physical realization may install the P18 base cohort while
retaining the independently adopted S/P19 evidence, or it must decline/defer
an incompatible replacement and keep the relevant adoption debt. A later
reacquisition needs its own explicit grant or declared bounded repair
continuation: HumanHelp's one-Refresh policy is unchanged. A complete newer
acquisition can supersede both when its current scope, provider progression,
permissions and actual installed effect establish that relationship. The
creator-result surface has its own declared lifecycle and cannot be silently
retired by an unrelated older board swap.

The framework does not hard-code HumanHelp's particular choice. It provides
checked acquisition, ownership, progression, installation, and obligation
mechanisms from which the application declares that choice.

*** Worked HumanHelp sequence: remote R, local S, and an excluding filter

Bob has adopted authorized board cohort Q17 at P17. Alice creates remote
Request R at P18; Bob receives a valid advisory for the board but does not
adopt R. Bob then successfully creates Request S at P19. Bob's current
local search filter matches R but excludes S.

The correlated *authorized* Create result for S can selectively admit S
under Bob's current board-scope membership rule without importing R.
Because the current filter excludes S, the UI presents S in an accessible
"Your new Request" result area with an explicit way to reveal it in the
ordinary board. It does not silently clear Bob's search or introduce R.
Local search, sorting, show-terminal and other presentation changes operate
over the already adopted cohort; they cannot acquire remote R as a side
effect. The outstanding advisory for R remains visible.

Only Bob's subsequent explicit Refresh, followed by a complete authorized
board acquisition and qualified installation, can adopt R under this
policy. An observation with a later basis for S is not evidence that the
complete board was read at that basis, and its adoption does not discharge
R's scoped obligation. If Bob has an unrelated outcome-unknown command,
that command's attribution remains independently unresolved even after
a board reread shows its present Request status.
