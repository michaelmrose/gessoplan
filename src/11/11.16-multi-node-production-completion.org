*** Multi-node production completion
:PROPERTIES:
:CUSTOM_ID: milestone-multi-node-production
:END:

This milestone qualifies the *same admitted application semantics*
across actual independent processes, physical host replacement
and the declared production topology under
[[#req-multi-node-realization]]. It does not define a second
distributed business-rule system. Source-owned operation
meaning, current principal and Organization authorization,
stable command identity, knowledge/progression, optimistic
settlement and browser acquisition remain the same on one
host or several. Distribution adds physical placement,
routing, shared-authority, publication, interest,
retention and failure correspondence obligations.

The milestone is distinct from operational application
completion, compositional certification and external
formal verification. A two-process prototype may be
useful while those other scopes remain open, but no
report may promote a shared database plus a load
balancer into a complete distributed production
claim without the required real fault and recovery
evidence. The claimed envelope names actual hosts,
backend, network, clients, routers, build generations,
traffic, resource limits and tolerated failures.

*** One semantic contract, several physical owners

A *choreography role*, authenticated actor, principal,
domain authority, command, HTTP attempt, host process,
router, installation generation and browser resource
are distinct identities. Host A's failure and host C's
replacement do not transfer Request authority by
process name. C may serve the same qualified public
operation only by authenticating its current invocation,
selecting the admitted operation/executor, validating
the authoritative model guard, and demonstrating the
selected backend and physical writer contract.

The requested production envelope accounts for
the following as separately qualified physical
subjects:

| Physical subject | Required completion evidence |
|------------------+-----------------------------|
| Installed hosts and ingress | At least two genuinely independent application processes, actual routing/failover, deployed handlers and assets, host loss/replacement and current activation scope |
| Original source and writers | Exact managed operation/initializer, administrative/migration, scheduled/background and external privileged writer coverage, with any open physical paths disclosed |
| Shared authority | Qualified selected backend/adapter transaction semantics, visibility, concurrency and read/progression relations across distinct hosts |
| Command incorporation | Same canonical binding and logical ID on every host, atomic guarded transition and deduplication under declared retention, truthful recorded outcomes and current result disclosure |
| Required publication | Durable intent coupled to the qualifying authoritative write where promised, surviving dispatcher ownership/retry and separate distribution acknowledgments |
| Router and interest state | Authorized interest discovery, effective registration, filter/update/failover coverage and observed gaps or conservative recovery |
| Subscriber/browser continuity | Initial and reconnect fences, replay/retention or re-acquisition, transport/advisory separation, current resource ownership and installed adoption |
| Mixed-generation deployment | Real A/A, A/B, B/A and B/B directions, enforced exclusions, retained assets/codecs, old execution retirement and rollback against actual state |
| Capacity/fault envelope | Measured concurrency, queues, outstanding debt, bounded replay/retention, backpressure, overload and safe degraded behavior |
| Qualified evidence | Independently observed positive/negative histories, source and environment identities, root claim dependencies and the exact limits of each result |

The production implementation may use one or several
routing processes, replicated/coarse or hierarchical
interest filters, redundant worker assignments,
conservative invalidation redelivery, and qualified
external brokers. Those are possible physical
realizations, not a mandated vendor, routing language
or universal distributed participant fabric. Router
work can first use Clojure and later another
implementation if its wire, failure, authorization,
subscription and recovery contracts remain checked.
Multi-node placement must not require application
authors to describe a new business operation or
adoption policy for each physical deployment.

*** Preserve authoritative command identity across loss

A bound Claim C42 sent through A retains its *one
logical command identity* if a later permitted
attempt arrives at C. The new HTTP/transport attempt
has its own identity and authentication context.
The actual authoritative transaction and durable
command record, not an A-local cache or C's
interpretation of the current Request, decide
whether the original command incorporated and
which recorded outcome can be disclosed.

The selected operation supplies a real atomic
incorporation or separately justified equivalent
of its domain transition, command identity/binding
and required result history under the qualified
backend. Two concurrent hosts cannot both produce
a new primary assignment in violation of the same
source model, nor may competing retries of C42
create independent authorized business actions.
The original required public-model and external
writer inventory is considered during proof and
physical correspondence. A test of one successful
HTTP route cannot attest all XTDB or administrative
writers.

A replacement host checks original operation,
target, canonical arguments, principal and
authoritative binding before compatible retry or
historical result lookup. Current authenticated
scope and disclosure policy are checked again;
the old host or client-supplied command ID grants
neither submission nor result access. Expiration
of the supported deduplication window is enforced
through retained record/tombstone or another
admitted reject/reuse policy; deletion cannot
silently turn an old ambiguous ID into fresh
intent. Loss of a response after possible commit
is =:commit-unknown= until adequate historical
evidence supports another outcome. An ordinary
current-state read cannot attribute C42 to A or C.

The following fault windows have different
observable duties:

| Fault window | Required classification and retained obligation |
|--------------+------------------------------------------------|
| Before any trusted submission | No incorporation may be invented; valid unsent intent can be admitted only as a new authorized action |
| After possible submission, before trusted result | Preserve original C42 binding and unknown incorporation; do not infer rejection or allocate C43 |
| After authoritative commit, before durable publication | Retain promised atomic publication intent or proven equivalent; domain commit survives lost response |
| After distribution, before dispatcher completion acknowledgment | Permit duplicate advisory dispatch without duplicate domain mutation, unintended recipient adoption or false publication completion |
| During HTTP/SSE result delivery or host failure | Preserve truthful command and publication debt independently of receipt and browser installation |
| During replacement/expired record retention | Maintain exact permitted reconciliation horizon or typed blocked/unknown resolution without invented command history |

A valid command-positive test must reach the
actual protected gateway and authoritative
backend, alongside forged, duplicated,
concurrent and unqualified cases at that
same boundary.

*** Make required publication recoverable without coupling it to live interests

A model change, a required durable publication
intent, a Gesso Live invalidation, router
forwarding, transport delivery and browser
adoption are distinct events. An authoritative
writer may generate required durable intent
from its original declared semantic change and
notification scope without knowing every
ephemeral recipient currently interested in
the data. A writer-local interest cache is
not the authoritative list of every current
or future subscriber, and failure to observe
a particular browser during commit cannot
silently cancel a promised recovery notice.

Where the selected operation promises
recoverable publication, its domain effect,
durable command result when applicable and
outbox intent are incorporated together under
the selected backend's qualified atomicity,
or via a separately justified equivalent
that cannot lose required intent after
commit. A best-effort advisory may have
different loss rules only where its original
declared weaker contract permits loss.
Published transport data must contain only
the authorized minimal notification scope,
not a protected Request snapshot that
bypasses current read permission.

A surviving dispatcher claims pending intents
under a qualified ownership/lease or equivalent
concurrency policy. Failure before/after
send or acknowledgment does not strand
required work in the dead process. Dispatch
may be conservative and at least once to
its *named acknowledged boundary*; no
unnecessary per-recipient permanent success
ledger is imposed when duplicate authorized
advisories and bounded replay/recovery
suffice. That choice does not license
unbounded duplicate amplification, false
completion acknowledgments or lost required
notification semantics.

The release evidence separately records
authoritative commit, retained outbox
intent, dispatcher claim, broker/router
acceptance, selected interested host,
SSE frame attempt, client receipt,
authorized acquisition and physical
DOM adoption. Neither a broker acknowledgment
nor an SSE write demonstrates that every
subscriber received or adopted the change.
A duplicate invalidation may ask a
permitted client to recheck current state;
it never creates a second Claim or grants
permission to adopt a remote board.

*** Close interest-registration and router-failover gaps

An initial subscription races with
authoritative changes. A committed change
may precede an interest being effectively
known to the router; a host-local filter
may have learned a client the replacement
router has not yet learned. The selected
protocol must establish a registration
fence, replay/gap record, qualified
comparison frontier or conservative
authorized re-acquisition sufficient
for the claimed subscription semantics.
The system cannot infer currentness from
silence on a stream.

Effective interest, retained publication
interval and covered authoritative basis
must be related by an independently
qualified coordinate or checked bridge
when they use different token schemes.
A token echoed from the request, a
router-local "seen" bit, or a healthy
backup process is not evidence that an
interested recipient's interval was
covered. Loss, reordered registration,
expired replay cursor, changed filter
or routing cutover must either preserve
the intended coverage or expose an
unresolved gap that blocks the stronger
currentness/delivery claim.

A distributed interest filter is an
optimization over an authorized
notification candidate set. A
partitioned or hierarchical filter
cannot exclude a recipient solely
because its local view is incomplete.
Replica/filter completeness,
version exchange, stale-router fencing,
fall-back fanout and bounded
conservative redelivery are eligible
mechanisms when their own capacity,
leakage, deduplication and coverage
premises are met. A failed router
may be recovered by re-sending more
notices than necessary; correctness
does not require remembering every
earlier successful destination if
that larger delivery is safe and
its work bound is justified.

Overdelivery may still leak tenant
membership, Request existence,
participant activity or routing
metadata. Current authorization
at dispatch, subscription and
protected read remains obligatory;
"conservative" does not mean
broadcasting protected data to all.
A receiver cannot claim delivery
of a required invalidation that
never reached it merely because
another router had a compatible
Bloom/vacuum filter or a host
reported itself healthy.

After an observed gap, the system
may refuse to claim current
coverage and retain advisory or
recovery debt until a current
permitted read at sufficient
provider basis discharges the
specified scope. It cannot turn
an unobserved missing event into
a fictitious positive stream
receipt or silently clear debt.

*** Preserve source progression, authorization and selective adoption

A replacement host reads under a
qualified provider, transaction
basis and query scope; the
frontier must be a real observed
provider fact and sufficient for
the required original semantic
progression. Transaction time,
valid time, domain revision,
command causality, stream cursor,
interest-frontier and browser
knowledge are not exchangeable
scalars. A lagging read or
unsupported provider option
returns a typed insufficient/
unavailable state rather than
reporting that the requested
basis was attained.

Each host and router reestablishes
current authenticated principal,
Organization Membership,
operation eligibility, protected
subscription, result disclosure
and query coverage at their
actual trusted boundaries.
An old connection, host ID,
serialized certificate, source
digest or stale permission
snapshot cannot authorize a
new effect after revocation.
A replacement process may
retain valid command evidence
while properly denying an
ineligible principal the
result.

For HumanHelp, Alice's own
qualified committed Claim can
settle her scoped pending
action. Bob's remote Request
lifecycle change remains
*advisory* until his
explicit user-authorized
Refresh, subject only to
the separately declared
own-command and affected-card
repair exceptions. A new
router, host, websocket/SSE
reconnect, asset reload or
backfilled invalidation never
manufactures a Refresh grant.
The permitted read must
cover the required cohort
and progression; an old
callback cannot install into
a new DOM resource or erase
incomparable newer advisory
debt. Withheld authorization
requires nondisclosure,
not fabricated convergence.

Direct participant-message
features may have independently
specified ephemeral or
durable delivery semantics.
A best-effort typing
message is not a recoverable
domain-state invalidation.
No universal global actor
directory, durable suspended
choreography engine or
router language is necessary
for ordinary Request
interactions; if a selected
direct-message feature
promises stronger receipt
or persistence, its own
protocol and tests remain
mandatory.

*** Establish real mixed-release, resource and fault evidence

The release profile fixes the
actually reachable A/A,
A/B, B/A and B/B client/server
directions from 11.08,
complete source-derived
continuation contracts and
retained assets from 11.09,
and semantic retirement/
command recovery from 11.10.
A safe per-host activation
does not prove an
all-host atomic cutover.
Host replacement and
failover must exercise
compatible request and
browser asset paths,
pending work ownership,
old/new schema reader
and writer safety,
stale client/stream
retirement and current
credential/authorization
conditions.

The physical acceptance suite
uses independently isolated
application processes and
the actual selected XTDB,
transaction adapter,
router/broker boundary,
installed Ring/Biff handlers,
real browser/transport assets
and representative authenticated
users. Test setups which
share in-JVM process state
where independence is claimed,
intercept only a test wrapper
or label two local maps
as two hosts cannot establish
this milestone. A negative
case is credited only when
the intended *real*
enforcing boundary rejects
the invalid action, and
a related eligible positive
case succeeds through
that same gateway.

A production performance and
failure envelope identifies
host/router/dispatcher count,
process and queue limits,
interest/filter cardinality,
outstanding outbox/debt,
event rates, retention,
replay pressure, failover
latency, load-balancing
strategy, target/browser
population, backend
consistency/availability,
network partitions and
supported recovery duration.
It measures capacity,
isolation, overload,
queue backpressure,
misrouting and leak-free
retirement under those
specific conditions rather
than quoting only peak
successful request rate.
Unbounded memory, queued
callbacks, publication debt
or retained assets do not
become acceptable because
a short throughput test
passed.

Recovery/progress evidence
names when backend and
network service return,
router/filter knowledge
converges, durable records
remain available, current
authorization permits
disclosure, and a participant
actually performs any
required Refresh.
Without those premises,
safety and honest blocked/
unknown status remain the
required result; unconditional
eventual browser convergence
is not promised. Revoked
Membership may make correct
outcome nondisclosure rather
than success. The selected
release's stricter progress
claims need appropriate
fairness and anti-divergence
evidence, not just successful
finite examples.

*** Multi-node positive and adversarial production histories

| Required qualifying history | Nearby invalid result or claim |
|-----------------------------+--------------------------------|
| Independent A and C processes exercise one original production Claim meaning | Two process labels share one process-local registry while claiming host independence |
| Real XTDB model guards permit one of two competing helpers to become primary | Cross-host stale reads permit two active primary assignments |
| C receives C42 original binding and authorized replay or historical result | C creates fresh command C43 merely because A's response was lost |
| C preserves truthful =:commit-unknown= until sufficient command evidence exists | Current Request state or missing record is falsely attributed to C42/rejection |
| Committed Request, command result and required publication intent survive A loss | A dies after commit and sole in-memory callback loses notification debt |
| Surviving dispatcher safely repeats an unacknowledged advisory | Failed acknowledgment doubles the authoritative Claim |
| Broker/router acknowledgment is labeled only for its real boundary | SSE send or broker success is claimed as every browser's receipt |
| Subscription registration is fenced with read/replay coverage | Commit between initial read and effective interest is silently missed |
| Replaced router covers stale or unknown interest via checked recovery | Healthy backup with stale filter silently drops required notice |
| Conservative authorized redelivery repairs uncertain routes under resource bounds | Replayed event exposes other Organization's protected Request metadata |
| Expired replay cursor produces typed gap and permitted re-acquisition | Stream silence or echoed cursor is reported as current authorized observation |
| C performs sufficient provider-basis read or reports insufficiency | Lagging snapshot is installed as satisfying a newer progression frontier |
| C authenticates current principal before protected command/result read | Old A session or source digest reauthorizes revoked Membership |
| Bob gets remote advisory, then explicitly refreshes authorized covered board | Cross-host notice or reconnect automatically adopts new remote rows |
| New owned browser resource installs current result under justified basis | Retired A callback overwrites B's DOM or clears newer debt |
| Genuine compatible mixed A/B client-server routes remain enforced | Sticky routing test misses failover to unsupported old writer/decoder |
| Supported rollback respects actual schema, pending durable work and assets | Prior passing binary is activated against incompatible migrated state |
| True router or host loss is injected and independently observed | Crash simulation does not terminate claimed process or real link |
| Real positive protected Claim succeeds beside adversarial rejection | Reject-all handler passes negative-only tests |
| Bounded queued/debt/filter work recovers after declared overload | Unbounded memory/worker leak hidden by short throughput sample |
| Unauthorized ephemeral typing is discarded under current recipient rights | Best-effort message is treated as durable Request incorporation |
| Root ledger records open physical writer/host premises and exact topology | Local report, copied status or two-host demo is called universal deployment proof |
| Required liveness progresses once declared fairness/availability/user-action conditions hold | Offline Bob with no Refresh is said to have adopted every update |
| After principal revocation, safe nondisclosure is observed | Repair/replay leaks protected historical command result to old session |

These are *prospective* physical,
source-semantic and deployment
tests, not observations that
an implementation presently
satisfies this milestone.
A successful two-host pilot
may satisfy selected bounded
cases while failing the
required production load,
failure or route/interest
envelope. The complete
claim retains the original
selected requirements and
every missing mandatory
case; it cannot shrink
the denominator to
successful observed paths.

*** Milestone decision and remaining scope

The multi-node production
milestone is admitted only
for its exact specified
topology, authoritative
backend/adapter, installed
source and artifact
generations, selected
fault and resource
envelope, exposed routing
directions, current
security assumptions and
authentic observed tests.
It verifies that the same
Gesso/HumanHelp operation
semantics survive the
claimed host movements,
publication and interest
gaps, command uncertainty,
authorized acquisition
and release overlap, with
all required external
premises transparently
qualified.

The root result identifies
original-source required
coverage, actual installed
host/writer/dispatcher and
router evidence, selected
provider qualification,
positive and negative
fault oracles, load and
retention bounds, completed
gates, still-open
assumptions and any
unsupported profile
requirements. Source
theorems, formal proof
issuance and current
runtime/operation authority
retain their own named
claims: neither production
resilience nor successful
fault injection proves
general semantic
soundness or independent
kernel meta-soundness.

A safer, narrower deployment
may be separately admitted
where its independently
selected profile and
actually enforced routing/
recovery restrictions
permit it. A failing
strict multi-node claim
cannot silently be reported
as complete under a
different profile. The
same semantic machine
remains the target of
one-node and many-node
implementations; later
routers, brokers, Rust
optimizations or new host
layouts are physical
replacements requiring
their own appropriate
correspondence and failure
qualification, not a
second application policy.
