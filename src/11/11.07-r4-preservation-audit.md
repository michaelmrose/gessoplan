## Editorial judgment

The R5 target is stronger than R4's short candidate-identity paragraph.
Retain its immutable subject, exact asset/receipt relation, private
installation, compare-and-activate transition, deferred work, current
authorization, selective failure handling and rollback requirements.
Make their actual release subjects and independence explicit rather than
repeating Part VII's entire lifecycle or implying that an admitted
ApplicationAssembly authenticates production serving. Keep an accepted
candidate distinct from an installed host, activated traffic and a
completed original product/assurance milestone.

The key strengthened join is that installation evidence must describe
the *actually used* protected entrypoint, provider and assets; a
candidate or staging report is not a bearer permission. New and old
effects have distinct active lifetimes and current trusted premises.
Migration is an authoritative writer, not an exception outside the
model/assurance boundary. Rollback can fail for state/protocol reasons
despite historically successful code. None of these facts forces a
universal migrations library or globally atomic multi-host switch.

## R4 / R5 preservation and improvement decisions

1. **Canonical original source:** admission binds the exact original
   source-derived requirement set; a truncated generated catalog cannot
   shrink it.
2. **Four release subjects:** candidate, installation, activation and
   milestone completion retain distinct evidence and decision scopes.
3. **Immutable candidate:** the tested realization cannot be replaced
   by a mutable registry, copied report or later source redefinition.
4. **Deterministic identities:** stable normalized identity may support
   reuse under its assumptions; byte-affecting inputs need separate
   physical identity.
5. **Exact emitted bytes:** inspected actual browser bytes and a
   qualified receipt bind the selected generated manifest.
6. **Compiler premise:** hash equality does not prove compiler semantic
   correctness; selected toolchain correspondence remains qualified.
7. **Real host adoption:** an installed Biff system map does not prove
   which handler a live listener selected.
8. **Route/output bypass:** later handler changes, alternative servers
   and pre-serialized HTML need actual coverage or explicit limits.
9. **Current deployment scope:** staging proof or test cannot
   authenticate distinct production credentials, endpoints or assets.
10. **Current physical writers:** protected non-HTTP writers,
    initialization effects and privileged migrations enter coverage.
11. **Private initialization:** early listener/worker preparation must
    fence protected effects before the actual activation point.
12. **Effectful init exception:** a durably effecting initializer needs
    its own independently admitted operation, not retroactive approval.
13. **Coherent active binding:** routes, executors, providers, guards,
    policy and assets change as one checked new-entry selection.
14. **Concurrent activation:** compare-and-activate resists stale
    predecessor/ABA and late candidate races under declared ordering.
15. **No invented global atomicity:** local selection alone does not
    certify coordinated routing across load-balanced hosts.
16. **Long-lived requests:** futures, streams, callbacks and jobs carry
    their original admitted context until completion or checked transfer.
17. **Current rights:** old assembly handles do not freeze
    authentication, authorization, backend trust or resource ownership.
18. **Semantic retirement first:** an invalidated old generation loses
    effect rights even if physical cleanup is delayed or fails.
19. **Valid old-service fallback:** rejection of B leaves A serving only
    while A itself remains qualified; otherwise fence or restrict.
20. **Partial resource ownership:** cleanup accounts for effects and
    acquisitions even when initializer completion was not recorded.
21. **Primary/secondary failures:** diagnostics retain original gate
    failure separately from socket, worker or cleanup failures.
22. **Shared lifetime:** a failed candidate cannot retire another
    admitted generation's shared provider or durable transferred work.
23. **Committed and unknown outcomes:** release failure cannot turn
    possibly committed Claim into rejection or permit new command IDs.
24. **Rollback is re-admission:** old artifact reactivation needs
    current evidence, host binding, premise and directional eligibility.
25. **No durable-state reversal:** Request, command records, outbox,
    disclosed information and browser installations survive code change.
26. **Schema/migration authority:** administration migrations are
    actual writer transitions requiring invariants, guards and coverage.
27. **Writer-direction asymmetry:** compatibility can admit an old
    reader while excluding an old writer under current migration state.
28. **Forward repair option:** irreversible state and protocol changes
    make old execution ineligible without forcing a migration engine.
29. **Historical reconciliation:** a retained command lookup may be
    authorized read-only even after its old writer is unsafe.
30. **Independent positives:** an actual eligible operation must work
    under the same protected gate challenged by its negative test.
31. **No proof by UI report:** activation and rollback use actual
    qualified evidence, never an editable status-shaped root record.
32. **Owner boundaries:** Part VII owns lifecycle mechanics, 11.08–11.10
    compatibility/retirement, Part IV command truth, Part X physical
    correspondence; 11.07 owns release selection and rollback qualification.

R4's useful candidate-generation identity, reproducibility and bounded
predecessor examples are preserved. R5's richer phase separation is
retained and strengthened. R4's schematic generation arithmetic is
not imposed as a universal ID or unconditional compatibility rule.
There is no intentionally dropped essential R4 guarantee.

## Implementation correspondence and honest limits (v1622)

- `src/gesso/live/application_preflight/biff.clj` checks the supplied
  current ApplicationAssembly, expected canonical handler module,
  Biff module start ordering and local handler wrapping for Hiccup
  responses. Its own namespace contract expressly leaves direct
  Biff startup, later handler replacement, raw serialized HTML and
  server modules ignoring `:biff.ring/handler` outside that guarantee.
  It does not issue an observed production traffic-activation receipt.
- `src/gesso/live/application_preflight.clj` owns current assembly
  recognition and supported Biff startup; local preflight/report
  semantics do not themselves authenticate every protected host path.
- `src/gesso/live/browser/build.clj` binds a generated manifest
  stamp to exact emitted JavaScript bytes and a receipt; the lower
  emitter cannot itself prove arbitrary generated JS implements its
  stamped manifest, and a built file does not establish client loading.
- `src/gesso/assurance/proof/installed_route_provenance.clj` has a
  deliberately narrow in-process Ring routing/dispatch witness,
  leaving actual Biff deployment, URI rewriting, external writers,
  credential and physical XTDB causality open.
- `src/gesso/assurance/proof/application_assurance_report.clj` and
  `src/gesso/assurance/report.clj` retain claim-scoped conditional
  reporting; report-like data is not an activation permit.
- `test/gesso/live/application_preflight/lifecycle_integration_test.clj`
  exercises local Biff module/handler use and failure cases.
  `test/gesso/live/application_preflight/assurance_integration_test.clj`
  explicitly tests that startup does not mutate an ApplicationAssembly
  into a deployment attestation and records real escape hatches.
  These test sources are not evidence of executed physical deployment.

The reviewed source does **not** establish a universal active-host
generation registry, atomic multi-host release coordination,
complete deployed writer/handler inventory, reliable cancellation of
arbitrary external effects, qualified schema rollback, or real browser
asset adoption. Those belong to the target contract and its named
physical acceptance layers. No test suite, XTDB integration, JVM
checker, actual Biff listener, Chromium, HumanHelp, two-host release,
or migration was executed for this editorial revision.

## Sixteen positive/adversarial conformance pairs

| # | Positive requirement | Counterexample that must be rejected or contained |
|---|----------------------|---------------------------------------------------|
| 1 | Actual checked JS bytes are served | Staging receipt authorizes unrelated deployed bytes |
| 2 | Live listener consumes admitted guarded handler | Biff system map has correct handler but listener bypasses it |
| 3 | Early init remains effect-fenced | Worker writes protected XTDB state before preflight |
| 4 | Real valid Claim passes and invalid Claim is blocked | Reject-all or test-only wrapper appears green |
| 5 | New requests use coherent B routes/assets/providers | Half-published B combines old incompatible A parts |
| 6 | A-to-B activation checks expected predecessor | Late C overwrites B using stale A condition |
| 7 | Old stream completes under retained valid context | Deferred A body looks up new B provider/guard |
| 8 | Failed B preserves safe A and its shared resources | Cleanup of B destroys A's provider |
| 9 | Revoked A effect right is fenced | B failure allows known-unsafe A writer to continue |
| 10 | Failed partial init accounts for real socket | No result map is misread as no acquired resource |
| 11 | Primary admission and secondary cleanup failures both reported | Cleanup error masks reason for rejection |
| 12 | Lost C42 result reconciles original bound command | Release restart creates C43 on uncertainty |
| 13 | Old target safely reads actual migrated state | Pre-migration test is treated as rollback qualification |
| 14 | Irreversible migration forces forward repair/restricted mode | Unqualified old writer corrupts new required state |
| 15 | Current Membership limits A-origin continuation | Old assembly or certificate freezes authority forever |
| 16 | Actual mixed-host and sleeping-client overlaps are checked | One host switch is called globally atomic |

These pairs are *prospective, separately observable* checks; they are
not results of newly executed tests. The same subject and real
protected effect boundary must be used for applicable positive and
negative paths. Where external constraints require trust, the
selected release profile records the assumption and current
qualification rather than silently treating it as verified.
