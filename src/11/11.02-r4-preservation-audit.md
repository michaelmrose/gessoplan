## Editorial judgment

Retain R5's improved four distinct architectural phase decisions, eight gate-result meanings and predeclared accepted-premise classes. Clarify the *actual subject and trusted observation* required for each of admission, installation, activation and completion, instead of collapsing them to an all-green status. Strengthen provenance, source-required gate enumeration, applicability/exclusions, fail-closed stronger profiles and distinguishing tests/proofs from runtime/domain outcomes. R4's useful operational deployment path is preserved without treating advanced milestones as unconditional prerequisites.

## Twenty-eight R4/R5 preservation decisions

1. **R4's operational milestone:** R4's operational milestone need not await optional later compositional or external formal milestone completion.
2. **R5 keeps distinct:** R5 keeps distinct candidate, installation, activation and completion decisions, without requiring four functions.
3. **11.01's original source:** 11.01's original source requirements and fixed release intent define the required gate inventory before checking.
4. **Passing a conveniently:** Passing a conveniently reduced generated operation/test subset does not certify complete original product requirements.
5. **Candidate admission binds:** Candidate admission binds actual source, assembly, proof profile and exact built asset under its own evidence scope.
6. **Installation eligibility is:** Installation eligibility is a qualified physical host/handler/writer/provider/credential/asset observation.
7. **Actual activation requires:** Actual activation requires current exposed traffic, compatible overlap, in-flight command and continuation recovery.
8. **Completion is a:** Completion is a separate claim over the selected original product milestone and supporting evidence.
9. **Passing staging tests:** Passing staging tests does not authenticate an actual distinct production installation.
10. **The eight R5:** The eight R5 result types remain closed and noninterchangeable; unavailable or incomplete never counts as passing.
11. **Passing expected rejection:** Passing expected rejection is a *negative test* result, not an admitted invalid business operation.
12. **Negative tests must:** Negative tests must challenge the first intended real protected boundary, with a positive passing counterpart.
13. **Gate evidence has:** Gate evidence has original requirement, subject, issuer, input, proof/test kind, scope and current applicability.
14. **Source fingerprint and:** Source fingerprint and report-shaped EDN are not proof objects, runtime authorization or deployed adoption credentials.
15. **Gate applicability/exclusion is:** Gate applicability/exclusion is separate from its result and needs prior approved narrower scope.
16. **Unknown applicability, missing:** Unknown applicability, missing required check or incomplete source/writer closure prevents the stronger claim.
17. **Strict certification cannot:** Strict certification cannot be silently downgraded to operational profile after failed/unavailable checks.
18. **Trusted or asserted:** Trusted or asserted premises remain claim-scoped and only permitted by the preselected evidence policy.
19. **Mandatory failed proof:** Mandatory failed proof obligations cannot be moved into accepted assumptions post hoc.
20. **Required backend premises:** Required backend premises need current qualification and cannot be treated accepted if known false.
21. **Current principal, target,:** Current principal, target, permission and command binding are checked at real effect time rather than frozen at build.
22. **Changed implementation/provider/asset/host/credential invalidates:** Changed implementation/provider/asset/host/credential invalidates dependent decisions without erasing unrelated abstract proofs.
23. **Post-submit diagnostic failure:** Post-submit diagnostic failure is not evidence of rejected business transaction or authority to resubmit.
24. **R4 missing required:** R4 missing required preflight, stale JS, raw handler bypass and false proof/diagnostic authority remain prohibited.
25. **HumanHelp response-flow product:** HumanHelp response-flow product decision remains open even though remote Create/lifecycle Refresh policy is selected.
26. **Reports distinguish concrete:** Reports distinguish concrete counterexample, infrastructure failure, unsupported checker, and unexecuted required test.
27. **Accepted conditional abstract:** Accepted conditional abstract proof never claims complete physical writer closure or deployed browser semantics.
28. **Part VII owns:** Part VII owns installed lifecycle, Part IX scoped proof issuance, Part X actual correspondence and Part XI separate release decisions.

## Current implementation source correspondence and nonclaims

- `src/gesso/live/application_preflight/assurance.clj` describes actual canonical rendering/affordance checks and openly states it cannot independently attest deployed serving handlers, current physical routes or complete rendered application surfaces.
- `src/gesso/live/application_preflight/biff.clj` owns part of canonical Biff handler installation, but deliberate direct/raw Ring bypass, later handler replacement or servers not using the canonical key fall outside that observed enforcement.
- `src/gesso/live/browser/build.clj` verifies selected browser assembly manifests and emitted JS bytes with receipts. It does not automatically establish which JS bytes each real client loaded or their physical effects.
- `src/gesso/assurance/report.clj` is a source-bound report with *caller-reported* tests; its fingerprints are not proof credentials, independent test execution attestation or release admission.
- `src/gesso/assurance/proof/application_assurance_report.clj` explicitly retains independent metatheory, installed application, writer closure, universal refinement and browser/HTMX/SSE evidence as open. Structural coherence is not a completed installation.
- `src/gesso/assurance/proof/certificate.clj` issues limited JVM-local, source-dependent checked proof handles with open premises; it does not grant runtime authorization or full-release completion.

These sources show real implementation work, not a complete current production four-stage release issuer, physically authenticated deployment, independent kernel theorem or universal complete HumanHelp acceptance. This editorial revision performed no live tests or backend qualification.

## Twelve positive/adversarial acceptance controls

| # | Positive control | Adversarial control |
|---|------------------|---------------------|
| 1 | Complete candidate source gate list | Missing required original capability vanishes from generated checks |
| 2 | Staging source/artifact qualifies tested host | Staging evidence copied to unrelated production host |
| 3 | Production handler/provider/asset actually installed | Pre-install system map or stale receipt called enforcement |
| 4 | Traffic exposure respects compatible active generation | Install pass counted as activation on old route |
| 5 | Original full HumanHelp requirements and tests satisfied | Claim-only demo called full product milestone |
| 6 | Invalid operation rejected at first protected effect gate | Test-only wrapper refusal counted as production test |
| 7 | Valid positive operation succeeds at same boundary | Reject-all implementation passes via negative-only cases |
| 8 | Finite exploration completes and reports exact finite bound | Timed-out or truncated exploration called theorem |
| 9 | Approved preview declares excluded capability debt | Required strict checker retrospectively made optional |
| 10 | Backend premise current and qualified within its claim | Stale or known-false premise counted as passing |
| 11 | Lost response retains unresolved command state | Post-submit observer error treated as domain rejection |
| 12 | Changed provider/asset rechecks affected active gates | Earlier success map becomes permanent release credential |

The cases are *prospective* and require current first-enforcing physical boundary and positive-operation evidence where that guarantee is claimed.
