* Part VII — Whole-application construction
:PROPERTIES:
:CUSTOM_ID: part-07-whole-application-construction
:PART_REVISION: 07-20261108
:END:

This part specifies how one source-owned application definition becomes an
admitted construction and an actual serving application. It joins executable
Choreo projections, trusted model operations, Clojure/ClojureScript handlers,
server routes, generated browser assets, rendered controls, Live interests,
authoritative acquisition, recovery, and the physical lifecycle. Parts I–VI
define the meaning and ownership of those components; Part VII establishes
that the required *connecting edges* are present and are enforced in the
realization that actually runs. Parts IX–X provide the stronger proof and
implementation-correspondence arguments and preserve their evidence scope.

Gesso applications retain ordinary Clojure, ClojureScript, server rendering,
HTMX, and application-specific effects. The framework does not require all
business logic to be written in a formal language or every local operation to
use Choreo. Instead, construction identifies the interfaces, effects,
producers, consumers, runtime dependencies, trusted premises, and observable
boundaries on which each selected guarantee relies. A sound declaration of
an opaque effect remains a named contract or assumption until its relevant
implementation correspondence is established; calling it application code
does not make its effects disappear.

Examples use illustrative operation and assembly names. A valid-looking
inspection map, plan digest, source label or success report does not issue a
runtime permission or trusted transaction credential. Present execution
conditions, including the authenticated actor, current authorization, model
facts, resource incarnation and installation permit, are checked at their
proper runtime/model boundaries rather than inferred from construction.

** Whole-application realization and preflight closure
:PROPERTIES:
:CUSTOM_ID: req-whole-application-closure
:END:

A valid choreography, model transaction, compiled browser plan or Ring route
can be correct in isolation while the combined application is broken. A
rendered Claim button may not emit its declared operation; its shipped plan
may be absent; a correct browser send may reach a different physical route;
the trusted route may lack its required execution provider; the command may
commit while no permitted authoritative acquisition or repair can establish
the resulting display. Each local component can pass its own tests.

*Whole-application closure* requires every effect and observation edge needed
by the selected application construction and assurance contract to have a
compatible, source-owned realization. This checks the composition of the
actual submitted application, not merely whether several independently
constructed registries look plausible. The supported construction is an
inspectable semantic/physical artifact with an identity, selected capabilities,
trusted premises, supported host/deployment profiles, and specific closure
and enforcement obligations.

Closure is *not* a second choreography. Choreo states which distributed
behaviors are admitted; projection derives executable role-local behavior;
application assembly establishes that each required concrete/browser/server
realization is supplied. A route cannot legalize an invalid Choreo trajectory,
and a valid plan cannot manufacture a missing route, model operation,
subscription or generated asset.

The required edges depend on the kind of work:

| Admitted application behavior | Realization that must be closed | Edges that are not invented |
|-------------------------------+---------------------------------+-----------------------------|
| Managed browser command such as Request Claim | Rendered affordance, projected plan, loaded browser/HTMX host, issued send, trusted method/route, guarded model operation, qualified outcome, acquisition and adopted presentation or declared recovery. | A fictitious global exact-once transport guarantee or a second runtime semantic interpreter. |
| Server-owned operation or background task | Registered event/worker, trusted operation and providers, applicable publication, durable intent/retry and readback or error policy under its own owner. | A browser plan and button for a task with no browser role. |
| Ordinary read-only HTMX or search route | Actual HTTP/read source, current disclosure authorization, declared query/coverage, rendered response/target and relevant Live or cache obligations. | A Choreo command solely because HTML is swapped. |
| Local draft/filter/focus interaction | Current local state owner, presentation and continuity permissions, effective physical effects, expiry and privacy boundaries. | A database transaction solely because the user types or changes a local filter. |
| Explicit ordinary mutating endpoint | Its declared model writer, authenticated input and current transaction guard, output/disclosure, invalidation and effect coverage. | Automatic exemption from invariants because the endpoint has no Choreo annotation. |

No semantic metadata is required on irrelevant static assets. However, a
managed route or physical writer whose effects can invalidate an invariant
must belong to that invariant's coverage argument or remain an explicitly
trusted and bounded environment premise. The application cannot claim
whole-writer safety while a reachable unaccounted raw route changes the
same RequestAssignment state behind its guarded Claim.

*** Three application claims remain independent

The authoritative [[#req-application-assurance-claims][Part I application-assurance claims]]
retain distinct evidence subjects:

| Claim | Required positive evidence | What the claim does not establish |
|-------+----------------------------+-----------------------------------|
| Declared structural closure | Every required operation, route, source, artifact, capability, observation, effect and recovery edge in the *declared application scope* has a compatible current binding; unsupported requirements are rejected or retain an explicitly allowed weaker profile. | That omitted business capabilities were intended or implemented; that arbitrary Clojure render states were statically enumerated. |
| Actual production enforcement | Real installed handler/startup paths, issued transport and renderer/HTML/HTMX boundaries perform the required checks *before* their protected send, trusted operation or response; the served/loaded asset and declared host are the ones checked. | The correctness of all future authority facts or an unobserved deployment merely because an assembly report passed. |
| Independent behavioral completeness | Eligible users can perform the required product operations using actual controls, trusted model effects, permitted acquisitions and physically installed results; nearby adverse and recovery cases also exercise those paths. | A universal proof of every execution from one positive browser example, or success when the relevant capability was intentionally disabled. |

The three claims can be simultaneously true, false or not yet established
in different combinations. A closed application can omit a required manager
Reassign control. Production may bypass its checked response wrapper even
though the assembly was valid. A test may manufacture C42 by calling a
helper directly even when the real Claim control emits no command. These
are distinct failures and cannot be flattened into one =:verified?= flag.

Application construction always requires its selected mandatory structural
and real admission boundaries. Stronger proofs and finite-model campaigns
are selected by an explicit assurance policy, not silently necessary for
every ordinary use. Omitting an optional theorem cannot disable required
route, actor, artifact, source or physical checks. Selecting an ambitious
proof does not make a disconnected checker an enforcing gate; only an
actual installed, correctly scoped boundary supplies enforcement.

*** Coverage follows effects, not the presence of Choreo metadata

Coverage is relative to the properties, security and product claims made.
The assembly identifies the admitted ingress, egress and state-changing
effects through actual HTTP routes, model functions, background work,
queues, scheduled tasks, administration, imports, initialization,
migrations, Live publication, external systems and browser/local writers
that may affect those claims.

An ordinary search endpoint can be the declared current authoritative
acquisition for a board without being a command choreography. A preference
update can use a simple guarded model operation. An explicitly raw HTMX
endpoint may remain legitimate under its own complete authorization and
effects contract. None obtains a silent right to bypass a selected
whole-application invariant because it lacks =:choreo/op= metadata.

A sound assembly represents *known writers*, their model-affecting
footprints, operation and route identities, required providers, publication
and observation obligations, and any explicitly scoped external writers.
Declared coverage is not a proof that a dynamically loaded plugin,
unobserved scheduler, hidden route or unbounded external system is absent.
Where discovery is incomplete, the report must distinguish an *unknown*
inventory from an actually enumerated empty one. A stronger closed-world
claim may require controlled registration, an enforced runtime boundary,
independent deployment inspection or an explicitly qualified assumption.

The closure graph has positive obligations for commands that succeed:
trusted incorporation must have the declared settlement, affected-scope,
publication, acquisition, adoption or repair path. Live interest without
a permitted first acquisition cannot establish a current initial view;
Live invalidation without a supported registration-gap recovery cannot
promise complete continuity. A command path that is perfectly guarded yet
always lacks its provider, or an entire screen that can never adopt its
observation, is not a realized product capability.

*** Construction-time knowledge and current-world authority

The finished assembly validates every requirement whose meaning and
inputs are available at construction, build, preflight or installation.
For example, it can check a declared missing plan, absent trusted route,
incompatible method/template, unsupplied required provider, stale browser
artifact/receipt, ambiguous physical realization, uncovered output,
unregistered source or undeclared recovery branch without waiting for a
real user to encounter the defect.

Some properties cannot be decided when the application is assembled:
the eventual Claim winner, the current principal, RequestAssignment
eligibility at transaction time, the outcome of an uncertain send,
the arrival of an SSE advisory, or the physical existence of a target
after another execution supersedes it. Each belongs to its current
trusted or physical admission boundary. A dynamic condition is acceptable
only where a specified enforcement and recovery/rejection path handles
it; it is not permission to replace a protected action with raw HTMX.

A production path is considered enforced only while the checked
construction is still the one being used. The checked callable must
be the installed callable, the verified asset must be served/loaded,
and the actual response must pass the required pre-serialization
or protected physical gate. Rebuild, handler replacement, route
override, alternate response encoding, stale service worker and
third-party extension paths must be closed by the qualified deployment
or remain named unsupported/assumed profiles. Successful compilation
or a copy of the expected report is not proof of these installed facts.

An application with arbitrary Clojure rendering cannot claim that a
finite catalog of sample Hiccup values enumerates every future
conditional control. It can still admit a current route/operation
backbone and enforce the required Choreo/physical request check
at every *actual canonical render*. Other response producers
need their own guard, an enforced shared serving boundary or
a weaker explicitly scoped claim. The absence of an observed
unauthorized control in a small snapshot is not completeness evidence.

*** Assurance vocabulary describes the checked proposition

The report retains what was checked, for whom, where, under which
version/coverage and what remains conditional. Useful distinctions
include:

| Evidence state | Interpretation |
|----------------+----------------|
| =preflight-closed= or =assembly-verified= | A specified declarative graph/construction was checked for its listed obligations at an identified current assembly and artifact identity. |
| =production-enforced= | Evidence ties the actual installed handler, physical effect, route or output boundary to the selected required check in the stated profile. |
| =runtime/model-enforced= | Present authentication, authorization and guarded model transitions are checked by their trusted current sources, not by a browser assertion. |
| =behaviorally-demonstrated= | An eligible end-to-end product case exercised real user, backend, transport and presentation paths within the stated test/environment limits. |
| =formally-proved= or =finite-checked= | Only the precisely defined theorem or finite model subject and its assumptions are discharged; neither term is a synonym for deployment correctness. |
| =inconclusive=, =unsupported= or =open= | A required premise is not established, the selected realization is unsupported or more evidence is needed; none is silently rewritten as success. |
| =contradicted= or =rejected= | A concrete observed violation or applicable construction fault was identified, at its own evidence boundary; not necessarily a trusted business command rejection. |

For instance, one application report may state that Choreo semantics
are proved for a named finite/symbolic subject, the browser artifact
correspondence is assembly-verified, the authenticated principal
is runtime-enforced, and actual HTMX behavior is covered by tested
host assumptions. It must not summarize those subjects as a single
unqualified "verified Gesso application." A diagnostic label,
digest or report has no power to authorize a business transition.

*** R4 preservation: broken compositions and positive controls

The following adjacent histories describe eligibility *and*
the failure mechanism. They are not merely tests that all requests
can be rejected:

| Eligible application history | Broken composition or adverse history | Required construction/enforcement conclusion |
|------------------------------+---------------------------------------+---------------------------------------------|
| A rendered authorized Request Claim control has a bound plan, shipped current runtime and trusted POST route. | The view emits the same POST without its managed operation identity, or the plan is absent. | Fail before protected send/HTML delivery under the relevant supported boundary; do not silently downgrade. |
| The current generated browser asset and receipt match the installed assembly and selected host profile. | A stale browser bundle, alternate script entrypoint or service worker supplies an incompatible plan after preflight. | Construction/build or actual serving/currentness gate rejects the stale realization. |
| A guarded Claim route has the required authenticated principal, clock/transaction provider and model-owned operation. | A missing =:biff.fx/now= or otherwise required execution provider becomes apparent only on click despite a knowable missing binding. | Reject the missing declared capability early; runtime still checks genuinely dynamic provider validity. |
| A qualified C42 incorporation produces covered publication/acquisition and physically adopted card or honest repair. | The command commits, but no permissible authoritative acquisition or installation path exists. | Reject the structurally missing continuation or declare an explicit recovery/blocked path; never fabricate adoption. |
| An initialized Live interest has a permitted baseline and reconnect/interest-fence recovery. | A board subscribes only to future invalidations but has no initial knowledge or permitted read. | Do not claim initial/current Live agreement; close the initial acquisition or expose the weaker contract. |
| A canonical guarded Biff/HTML path validates the actual rendered control before serialization. | A later handler replacement or hand-built serialized Ring response bypasses that guard while an app claims universal response coverage. | Actual installation/served-route enforcement must cover the alternate path or explicitly narrow the guarantee. |
| An ordinary read/search HTMX endpoint is correctly authorized and responds as an ordinary route. | The same raw route mutates protected RequestAssignment state outside the claimed writer inventory. | Preserve ordinary HTMX as a supported mode; account for its real write effects and transaction guard. |
| A manager uses an eligible real Reassign control; another helper's competing Claim is rejected at the trusted model boundary. | Tests build a coherent shadow registry or submit synthetic commands although the production Reassign button is absent. | Distinguish production assembly from test surrogates and require independent positive product acceptance. |
| The assembly accounts for named background, scheduled, migration and administration writers affecting Request state. | A known external writer is omitted so a formally checked operation invariant ignores its reachable transitions. | State explicit source coverage, trusted external contract or an honest weaker claim; do not hide the writer. |
| An application enables stronger finite/proof assurance with its own checked subject and runtime gates intact. | The checker is not connected to the admitted artifact, or a finite pass is used as proof that all routes and browsers are correct. | Retain source-bound assurance scope and actual enforcement; neither proof presence nor absence changes runtime semantic authority. |

Part VII's later sections specify the ApplicationAssembly shape,
closure graph, concrete routes, renderer, artifact manifest, Live
and recovery mechanics, lifecycle and diagnostic surfaces. This
opening section establishes the admission *scope* and its three
independent success conditions; it does not provide a second
implementation of those later checkers.

Part VIII must exercise nonvacuous positive HumanHelp Create, Claim,
Reassign, Done/Cancel, creator-local presentation, remote advisory with
exactly one explicitly granted Refresh, and local search/selection/
scroll continuity as appropriate to the selected product contract.
Parts IX–X must relate admitted declarative edges and physical
occurrences to their actual formal and implementation evidence.
** Application definition and ApplicationAssembly
:PROPERTIES:
:CUSTOM_ID: req-application-assembly
:END:

One source-owned application definition composes the declarations that their real
owners export. Its normalized realization is the conceptual
=ApplicationAssembly=. It is a graph of typed subjects, bindings, obligations,
and evidence, not a collection of unrelated success flags.

The public authoring surface should remain small. Source owners declare genuine
choices once; construction derives repeated identities and verifies independently
chosen physical correspondences. Applications should not maintain separate
operation registries for browser compilation, preflight, startup, rendering,
model checking, and tests.

*** Source ownership and derivation

| Source owner | Authored facts | Derived or checked products |
|--------------+----------------+-----------------------------|
| Domain/model module | Typed operation meaning, guards, dependencies, transitions, outcomes, command/recovery contract, opaque premises. | Model interfaces, candidate obligations, operation catalog, rule/audit views. |
| Choreography module | Distributed roles, permitted knowledge flow, coordination, local recovery choices. | Role-local plans and compiler correspondence. |
| View/component | Selected operation, concrete arguments/observations, presentation, availability choice. | Prepared action binding, effective transport annotation, render obligations. |
| Route/ingress module | Supported physical dispatch and input mapping. | Installed dispatcher, route index, selector-consistency checks. |
| Trusted execution adapter | Public model delegation and actual implementation/provider binding. | Issued callable, invocation gate, outcome encoder. |
| Acquisition/Live module | Projection/query scope, observation contract, subscription and refresh policy. | Acquisition bindings, coordinator requirements, advisory/recovery edges. |
| Runtime/build profile | Compiler/runtime, physical handlers, assets, supported host behavior. | Browser manifest, generated bootstrap, build receipt, qualification obligations. |
| Application composition | Selected modules, configuration, assurance policy, lifecycle/deployment profile. | One admitted application and its explanation. |

An exported declaration is not accepted solely because it came from a namespace
with the right name. Construction validates its semantic category and required
source/implementation correspondence. A raw declaration, an admitted operation,
an issued executor, and a copyable report can use similar host representations
without being interchangeable.

A schematic composition might be:

#+begin_src clojure
(defn application-definition [config]
  {:application/id :humanhelp/example
   :domains [request/definition
             organization/definition]
   :flows [request-flow/definition]
   :surfaces [request-card/definition request-board/definition]
   :ingress (routes/definitions config)
   :execution (server/execution-bindings config)
   :acquisitions (live/acquisition-definitions config)
   :providers (server/provider-bindings config)
   :browser-profile browser/profile
   :lifecycle (system/lifecycle-definition config)
   :assurance-policy assurance/managed-application-policy})
#+end_src

Each referenced module exports its actual owned declarations; the example does
not stand in for omitted definitions. The composition does not retype operation
IDs, argument schemas, settlement variants, or plan digests already determined by
those declarations. Independent physical route selection and provider selection
remain real choices that must be checked.

Tests instantiate this constructor with declared fixture configuration. They can
replace a clock or storage provider for a scoped test, but must identify that
substitution and avoid transferring its evidence to an unexamined production
provider. A hand-built shadow assembly is not production-closure evidence.

*** Checked construction supports opaque application code

An ordinary Clojure function can implement a rule, renderer, projection, candidate
builder, or input conversion behind a declared interface. Construction establishes
what can be checked and retains a named premise for the rest, under
[[#req-admission-assurance-policy][the admission policy]].

For a candidate builder, the actual returned targets, assignments, frame,
command binding, and supported effect footprint can be checked before submission.
That instance check does not prove that the builder had no hidden earlier effect
or that it produces valid candidates for every input. Effect containment and
functional conformance remain separate enforcement or assumption obligations.

Normalization must not silently execute arbitrary application work to discover
its meaning. Functions invoked during construction have an explicit purity,
determinism, totality/failure, and resource contract. Compilation, dependency
resolution, and model exploration use their declared budgets. An effectful
builder cannot be called repeatedly by inspection or diagnostics as though it
were inert data.

A canonical admitted construction should derive execution and checking products
from the same semantic subject wherever possible. An independently supplied
reference model remains useful, but its relation to the production operation is
an explicit obligation. Agreement between two copies of the same mistaken policy
is not evidence that the intended business rule was correct.

*** Closed registries and explicit extension boundaries

Registries declared closed reject unknown, duplicate, ambiguous, or incompatible
members before use. Extension points identify how new modules, routes, operations,
or providers become a newly admitted construction. Dynamically loading a plugin
must not mutate an admitted registry while retaining old closure evidence.

Unused declarations can be available for composition without being exposed or
active. They are labeled accordingly. A generated executable or installed writer
that claims a role in the active application must have a corresponding source
and coverage classification; it cannot disappear from the graph as unused merely
because no UI currently invokes it.

*** Construction phases and admitted assembly identity
:PROPERTIES:
:CUSTOM_ID: req-assembly-construction-phases
:END:

Construction has an acyclic dependency order. It may expose several internal
products without asking application authors to maintain several definitions.

| Phase | Product and admission responsibility |
|-------+--------------------------------------|
| Normalize | Resolve source-owned semantic declarations, physical choices, configuration, and explicit opaque contracts. |
| Derive | Produce required role plans, interfaces, closure graph, proof obligations, and the browser build manifest. |
| Build/check | Generate assets and correspondence products; run applicable semantic, closure, qualification, and assurance checks. |
| Admit candidate | Bind accepted evidence and retained premises to an immutable candidate realization under the selected policy. |
| Install | Construct actual router, wrapped handler, providers, worker entrypoints, and asset serving from that candidate. |
| Activate | Verify the required installation relationships and permit external application service. |
| Retire | Revoke or transfer owned rights/work, drain permitted users, and release resources under the lifetime contract. |

Some installation facts cannot exist before installation. The lifecycle therefore
allows private preparation and a final activation gate, while preventing unchecked
application operations from becoming externally available. A report saying a
candidate is structurally closed is not a report that its server was activated.

The identities used in these phases identify different objects:

- normalized semantic/realization input identity;
- concrete implementation closure and qualification-profile identity;
- exact executable plan identity;
- browser manifest identity;
- emitted asset content identity;
- checker result/evidence identity with its applicability;
- admitted assembly instance, optionally described as an assembly generation;
- deployment instance/placement identity.

An assembly generation is a scoped application-construction lifetime. It is not
a universal freshness number, browser execution ID, resource incarnation, command
ID, or database progression token. Examples use =:assembly-instance/id= when
referring to that admitted lifetime.

A digest recipe specifies the object, canonical encoding, schema, relevant
compiler/provider dependencies, excluded self-identifying fields, and collision
premise. Formatting-only source changes need not alter semantic identity, but a
changed opaque implementation can invalidate implementation evidence even when
its public contract is unchanged. Part V's exact plan and asset distinctions
apply here.

The final asset digest cannot be an input to the same bytes containing that
digest without an explicit cycle-breaking construction. Detached receipts and
content-addressed asset locations provide a straightforward solution.

*** Immutable admitted bindings and scoped revalidation

An admitted assembly binds the actual implementations, providers, policy,
qualification profiles, route semantics, rendering contract, and artifact set
on which its claims depend. A request captures that assembly instance at entry.
Its later callbacks, rendering, and response completion preserve that reference.

An immutable map containing mutable Vars or registries is not automatically an
immutable realization. The supported construction captures applicable callable
bindings, uses assembly-owned registries, or detects and re-admits relevant
replacement before dependent use. An ordinary reload is a declared construction
transition, not an arbitrary mutation excused by development mode.

Construction evidence may be cached by its complete dependency identity and
applicability conditions. There is no requirement to recompile plans, explore a
finite model, or hash every asset on every response. The runtime must preserve
or re-establish the relevant binding at the boundary where it is used. A mutable
asset path or live registry needs a concrete stability/invalidation mechanism;
a cached green report cannot supply one.

Admission handles can be opaque process-local values; explanatory reports remain
copyable data. A private issuance registry can prevent accidental substitution of
a copied map for an issued executor. Object identity alone is not durable proof,
remote attestation, or a sandbox against hostile code sharing the JVM. Process
restart reconstructs local admissions from their actual sources and any
independently checkable durable evidence.

** Whole-application closure graph and evidence

The graph represents semantic interfaces and actual realization relationships.
It must expose enough structure to locate a failure without forcing a reviewer
to reverse-engineer many namespaces. The runtime need not carry the entire graph
on every request; it uses admitted bindings derived from it.

*** Operation-specific edges

| Edge or obligation | Required correspondence |
|--------------------+-------------------------|
| Affordance to operation | Concrete arguments, observations, selected realization, and availability implement the named operation. |
| Operation to choreography/projection | Required role-local behavior follows the admitted coordination and knowledge contract. |
| Plan to executable artifact | The generated runtime contains the intended admitted plans and bound implementation/profile dependencies. |
| Executable plan to physical handlers | Every reachable required effect has a compatible handler and completion/failure protocol. |
| Transport to ingress | Method, route semantics, encoding, selectors, correlation, and protocol agree. |
| Installed ingress to executor | Actual dispatch invokes the selected issued/admitted callable, not a metadata-equivalent substitute. |
| Executor to public model operation | The trusted operation binding implements the declared model interface and preserves its command/authority obligations. |
| Operation to providers | Required typed resources resolve to compatible providers with the right origin and lifetime. |
| Candidate to authoritative realization | Checked targets, guards, assignments, frame, and effects reach the admitted lowering/submission boundary. |
| Model outcome to participant settlement | Each supported outcome maps explicitly without collapsing incorporation, rejection, repetition, and uncertainty. |
| Required propagation to recovery | Publication/durable work, progress requirements, and missed-delivery recovery have actual owners and paths. |
| Observation to presentation | Scope, progression, authorization, representation, target ownership, and physical completion support the claimed adoption. |
| Application policy to enforcement | Mandatory checks are invoked at the actual construction, installation, request, effect, and output boundaries. |
| Product capability to acceptance | Independent promised behavior is exercised through the admitted application; closure alone does not establish it. |

Not every operation needs every edge. The operation's admitted interface derives
its obligations. A read cannot require a fictional mutation just to fit a universal
pipeline, and a mutation cannot omit recovery because it looks like an ordinary
POST.

*** Evidence is attached to a proposition, not a prestige label

A checked edge records its subject, expected relation, actual binding, source
ownership, mechanism, premises, coverage, applicability, and result. These are the
[[#req-assurance-classification][assurance dimensions]] from Part I.

An illustrative inspection row is:

#+begin_src clojure
{:obligation/id :claim/installed-route-to-executor
 :subject {:assembly-instance/id assembly-id
           :route/id :route/request-claim
           :operation/id :request/claim}
 :expected {:executor/ref admitted-claim-executor-ref}
 :observed {:installation/ref route-installation-ref}
 :mechanism :issued-dispatch-construction-check
 :evidence/ref checked-binding-evidence-ref
 :status :established
 :scope :this-installed-dispatcher
 :premises [server-adopts-dispatcher-premise
            implementation-closure-premise]}
#+end_src

The checker derives this result from the relevant construction/installation.
Writing =:status :established= into a map does not satisfy the obligation. A
handler's operation name proves neither its body nor adoption by the real server.

A report distinguishes unresolved structural edges from retained runtime or
external premises. Structurally arranging a trusted principal provider can close
an edge; the actual principal's current authorization remains a runtime/model
condition. The report must not list every future authorization decision as an
unfinished build task.

*** Checked, unsupported, inconclusive, and contradicted are distinct

The admission policy identifies which obligations are mandatory, which require a
particular evidence mechanism, and which may remain named assertions. A missing
route, mismatched executor, invalid schema, wrong authority source, or missing
required recovery cannot be excused by adding a trusted flag.

Unsupported proof fragments and exhausted checking budgets do not establish
falsehood or success. They receive explicit dispositions under the policy. A
known counterexample to the same scoped claim cannot be relabeled an accepted
assumption to make admission green. Correcting an abstraction, narrowing a claim,
or fixing implementation requires a new explicit check of the changed subject.

Claims such as assembly-verified, runtime-enforced, exact-finite-checked, and
proof-kernel-checked describe different evidence at different scopes. They do
not combine into an unexplained percentage or one universal verified Boolean.
The permanent executable semantic core remains distinct from the proof kernel
and from dedicated correspondence/conformance checkers.

*** A Claim realization closes more than its happy path

For HumanHelp Claim, the source-owned model operation protects current Request
state, helper Membership, Organization policy, and their association under the
Part IV command protocol. Assembly must connect that operation to all required
browser and trusted-server paths.

| Concrete requirement | Failure it prevents |
|----------------------+---------------------|
| Generated Claim binding includes typed Request arguments and the admitted observation context. | A visually enabled control lacks the input/basis its realization requires. |
| The actual browser asset loads the matching plan and physical handlers. | Startup succeeds but clicking the button cannot execute the plan. |
| The real request carries the selected command envelope and stable =:gesso/command-id=. | A working =hx-post= reaches the route without the required command. |
| Path Request selector and decoded command argument are checked for agreement. | The URL selects one Request while the command targets another. |
| Installed route invokes the bound public operation through its admitted executor. | A similarly named handler performs a different transition or bypasses command records. |
| Provider binding supplies sampled time in the representation the executor consumes. | A declared clock exists but the required context value is absent. |
| Model outcomes have explicit participant mappings and disclosure checks. | Repetition after a successful commit is mistaken for a fresh failed Claim. |
| Unknown has a current reconciliation owner and compatible resolver path. | Lost response strands the command or provokes a duplicate new command. |
| Scoped acquisition and physical installation close the presentation path. | HTTP 200 is counted as a current card despite no successful swap. |
| Required Live propagation and reconnect recovery close remote participant behavior. | The initiating user succeeds while other interested boards can never recover. |

The explanation derives these rows from the admitted construction and its evidence.
A shorter example that omits the resolver, physical completion, or publication
recovery must identify its narrower scope instead of being labeled a complete
application proof.

** Application assurance policy and operation coverage

The application definition contains one explicit assurance policy used by
construction, installation, and activation. Stronger finite, inductive, or
correspondence checks may be optional under one policy and mandatory under
another. Their selection is visible in the admitted subject and explanation.

A low-level compatibility API may preserve an unassured legacy path, but that
path cannot inherit the managed application's enforcement or theorem claims.
The ordinary managed startup path does not silently treat an omitted policy as
permission to skip required checks. It applies the declared default policy or
rejects a missing required selection.

*** One construction owns the semantic catalog and its checking products

A useful construction binds:

- the admitted application assembly;
- the exact relevant operation catalog and semantic definitions;
- rule/invariant declarations with their source ownership;
- actual executor/handler implementations;
- finite model families or inductive evidence where requested;
- the comparator and observation contracts used for implementation evidence;
- required exercise/coverage gates and their budgets;
- the installation and startup path consuming that construction.

Later comparison cannot accept replacement model callbacks or an unrelated
catalog while retaining the old admission handle. Diagnostic inspection reports
the already checked subject and results; it does not rerun user callbacks to
invent a fresh explanation.

This unified construction is an ownership discipline, not a requirement for one
large function or public record type. Layered internal constructors can provide
separate products while preserving their common sources and dependency bindings.

*** Finite operation families and non-vacuous coverage

A finite exploration may expand registered operations over declared principals,
arguments, states, and choices. The expansion must preserve the mapping from
each modeled occurrence to its actual operation contract. Synthetic model IDs
are diagnostic coordinates, not production command or execution identities.

The report records the declared bounds, resource budget, visited states or state
occurrences as appropriate, attempted transitions, remaining frontier, and whether
the requested exploration completed. A depth bound can define the intended finite
problem; exhausting a computation budget before exploring that problem is
inconclusive. Completing a depth-limited exploration does not establish unbounded
invariant preservation.

Coverage dimensions remain separate:

| Coverage question | What satisfying it establishes |
|-------------------+---------------------------------|
| Every relevant registered operation has a family. | No catalog member was omitted from that family mapping. |
| A rule matches a source in an explored state. | The rule's modeled domain was exercised at least there. |
| An operation has an enabled attempt. | The model's enablement relation selected an attempt; its incorporation guard may still reject it. |
| A required committed/rejected branch occurs. | That modeled outcome was exercised within the declared exploration. |
| A modeled path preserves an invariant. | The checked path/model satisfies the stated proposition at its scope. |
| A real observed invocation matches a modeled step. | The admitted comparison establishes its stated local correspondence, with retained premises. |

A policy can require particular rules, operations, and outcomes to be exercised.
These gates prevent vacuous green reports, but do not establish product usability,
all predicate branches, representative domain completeness, or production
execution. A rule with no matching modeled source is reported as unexercised;
it cannot be counted as a substantively tested business policy.

Application authors should not write separate theorem-prover programs simply to
use these checks. Gesso derives supported model/checking inputs from its semantic
construction. Explicit reference callbacks or external models remain possible,
with their translation and correspondence premises visible.

*** Induction is scoped to a catalog and its realization

A conditional application invariant requires an admitted initial-state argument
and preservation by every relevant transition in the scoped catalog. Adding a
new operation or writer can change that obligation even if no existing operation
body changed. The evidence dependency graph records the actual catalog, rule,
backend, and implementation subjects.

An abstract catalog proof is not automatically a physical database proof. Applying
it to production also requires the stated initialization, writer coverage,
input/state mapping, atomicity, frame, and transition-correspondence premises.
Part IV defines the authoritative realization obligations; Parts IX and X define
how stronger evidence composes.

A selected strict assurance policy must be invoked at the real candidate admission
and installation boundaries. Calling a checker in a test or exposing an optional
function named require-policy does not enforce that policy in production. The
installation result identifies which gates actually ran and which checks remain
required at invocation time.

*** Evidence must retain original subjects and provenance

An issued executor can be bound to a checked semantic source and its actual
implementation. An issued handler can then be constructed to call exactly that
executor after trusted request conversion. This provides stronger structural
correspondence than attaching an operation name to an arbitrary function.

The binding does not prove the correctness of opaque request conversion, output
rendering, backend behavior, or arbitrary extra effects. Those contracts remain
explicit. A wrapper around an issued executor does not automatically inherit its
issuance identity or all its guarantees; supported composition records the new
wrapper's role and effects.

A report copied from a genuine check is still a report. Admission consumes the
required original source/issued product or independently verifies a durable
certificate under its declared checker. It does not accept a caller's success
map as a substitute. Evidence about one callable cannot be transferred to another
because their names or displayed metadata agree.

*** Writer coverage includes routes and non-route work

The coverage graph joins the semantic catalog, admitted executors, installed
ingress, and actual effect providers. It distinguishes at least:

1. declared operations and their permitted effects;
2. registered/issued executor implementations;
3. installed HTTP and non-HTTP entrypoints;
4. observed invocation paths at the stated scope;
5. physical submission capabilities and any independent writers.

Matching operation ID sets is useful but does not prove semantic equivalence.
A host-provided inventory is evidence about what it enumerated, not proof that
it omitted nothing. Independent observations and effect containment can strengthen
coverage; the remaining exhaustiveness premise stays explicit.

The graph must not require every writer to be used by an HTTP route. Queue
consumers, scheduled jobs, migrations, and initializers have legitimate entrypoints
and different lifetimes. Each relevant writer has an admitted owner/path or an
explicitly classified external role. Conversely, a route can invoke several
admitted operations if its choreography/effect contract permits that composition.
The operation graph is not a universal one-route/one-writer bijection.

An unclassified writer blocks a claim requiring closed writer coverage. Under a
policy that permits a limited claim with external writers, their permitted
interference and its effect on dependent invariants are named premises. A generic
label saying external must not conceal a known contradictory mutation.

*** Request-scoped and work-scoped submission

The normal managed path gives candidate code the resources needed for preparation
and gives the admitted submission boundary the scoped effect capability. A raw
XTDB client need not be available to every handler merely because the application
uses XTDB.

A request has its own invocation identity, current principal binding, selected
assembly instance, issued effect resources, and completion/retirement protocol.
Fresh grants are issued for subsequent requests. A one-use observation or writer
handle must not become a production route that works once and then rejects every
later valid invocation.

A process-wide mutable slot that installs one request's callback and rejects
unrelated concurrent requests is not the general concurrency architecture. The
normal design uses request/work-local contexts or an equivalent isolated registry
with explicit ownership. A qualified serial controller can remain a supported
limited profile where the limitation is intentional and visible.

Asynchronous handlers, worker tasks, and durable workflows need explicit context
propagation or ownership transfer. Merely retaining a thread-local binding does
not establish their lifetime. Work that survives an HTTP response acquires its
own admitted owner; it cannot borrow the retired request's capability indefinitely.

Cancellation and cleanup first revoke further local use. They do not undo a
transaction already submitted or prove its rejection. Cleanup must not overwrite
an intervening registry change, and failure after dispatch retains command/effect
uncertainty and the required recovery owner.

One-use physical grants and semantic command deduplication remain separate.
Compatible retries preserve =:gesso/command-id= and its binding while receiving
new invocation/transport resources. Backend retries or repeated transaction
function evaluation obey the provider's declared contract and cannot silently
multiply external effects.

*** Observation after execution is not a pre-effect guard

A correspondence observer can detect that an installed route invoked the wrong
writer or that an actual result differs from its model. If that check runs after
dispatch, it is evidence and diagnosis; throwing from it cannot prevent or undo
writes that already happened.

Mandatory safety checks run before the protected effect, with commit-time
conditions enforced by the authoritative boundary. Post-execution observation
may add evidence, flag a broken premise, or trigger containment and recovery.
The explanation states which role each check plays.

A sequence of observed results matching a model path does not by itself establish
physical chronology or uninterrupted state continuity. Occurrence identities,
ordering evidence, captured state scope, and unobserved interference remain part
of the correspondence argument. Equal before/after documents do not prove that
no intervening writer ran.

** Transport, installed routes, and trusted execution

*** Preserve operation identity through physical realization

Once an action is declared to mean a semantic operation, later bindings preserve
that identity. Missing observation basis, plan, transport, or handler causes a
construction/rendering rejection or an explicitly unavailable action under its
UI contract. The system cannot erase the semantic tag and emit an ordinary POST
to keep the control clickable.

Alternate realizations are legal when each is independently declared and checked
for the same operation, and the selection rule is explicit. An optimistic path,
a non-optimistic command path, and a server-only path may have different
requirements. Choosing one is not permission to invent a weaker interpretation
at runtime.

An unavailable rendering preserves the operation and reason while suppressing
its effective executable paths, including form-level and inherited actions.
Styling alone does not disable a transport. A permanently unavailable required
capability still fails independent product acceptance.

*** Dispatch and checking share route semantics

The route constructor supplies both the installed dispatcher and the checker
projection, or establishes their correspondence through a qualified integration.
The checker must use the actual method/path interpretation, parameter decoding,
base path, route precedence, and discriminator rules that select the handler.
A guessed regular expression over a URL is insufficient if it disagrees with
real dispatch.

A supported routing profile declares its analyzable subset. Literal paths and
simple segment parameters are a useful initial subset. Unsupported patterns,
rewrites, wildcard dispatch, or content-based selection are explicitly rejected
for that profile or admitted through another qualified contract. Prototype
restrictions do not define the whole framework's eventual route language.

Overlapping routes are either rejected or have a deterministic precedence relation
that both checking and dispatch use. Merely forbidding every overlap is one
possible narrow profile, not a universal requirement. Routes serving several
operations use an admitted discriminator and closed registry; they do not execute
browser-supplied machine state or select by fuzzy names.

Method/path matching uses the effective request after the declared trusted
normalization chain. Proxy rewriting, host/base-URL rules, query selectors,
method overrides, and content negotiation are included where relevant. Unknown
or conflicting selectors fail explicitly rather than allowing one layer to
silently override another.

*** The installed callable is the checked callable

The construction should issue or compose the actual route handlers and dispatcher,
then install those products. A separate map claiming that route R uses executor E
is weaker evidence than constructing R to invoke E and checking the actual
installation's binding.

The installation check distinguishes:

- a declaration naming a handler;
- a constructed dispatcher bound to that callable;
- a system map holding the wrapped dispatcher;
- the actual server instance accepting requests through that wrapped dispatcher.

Each is a different evidence boundary. Inspecting a caller-selected system map
does not prove what a running server captured earlier. The supported server
constructor must consume the admitted handler directly or establish its actual
adoption through an equivalent qualified mechanism.

Ordinary middleware remains possible. Its composition preserves the required
routing, principal, request, response, and effect contracts. A middleware stage
that rewrites an operation selector or replaces the handler changes the relevant
binding and cannot inherit the previous report without checking.

*** Trusted command admission

The transport contract defines the real wire field/encoding, supported protocol,
operation/interface identity, command binding, argument codecs, and outcome
channel. The browser transports the stable command ID before any possible send.
=:transport-request-id= identifies an attempt and is not the domain Request ID.

At the trusted ingress boundary:

1. decode and validate the actual supported envelope and typed arguments;
2. resolve the operation through the admitted server registry;
3. require agreement between operation and subject selectors in the route,
   envelope, query, and trusted dispatch context where the contract duplicates them;
4. obtain principal/tenant context from its trusted provider;
5. bind the current invocation to the admitted public model operation;
6. enforce command repetition, disclosure, and atomic current-state guards as
   specified in Part IV;
7. encode only the permitted result and observation evidence.

Browser-supplied principal IDs, role labels, basis tokens, plan references,
certificates, or assembly IDs do not grant current authority. A basis carried by
a browser is protocol context unless its particular provenance/use contract
establishes more. Part II's observation-evidence distinction applies.

Where cookie-based or comparable ambient credentials make cross-site invocation
relevant, the selected transport/authentication profile includes the required
origin/request-integrity defenses. Structural route closure and typed decoding
do not substitute for that security contract.

*** Required execution providers are typed bindings

A requirement is more precise than a member of a set such as =#{:clock :db}=.
It identifies the input/output contract, origin, invocation scope, lifetime,
ordering/dependency constraints, and supported failure outcomes of the provider.

For example, a Claim executor may consume a sampled instant under
=:biff.fx/now=. A zero-argument clock function under another key does not satisfy
that requirement until a declared adapter samples and binds it at the intended
boundary.

#+begin_src clojure
{:requirement/id :claim/commit-time-input
 :consumer {:operation/id :request/claim
            :input-path [:execution-context :biff.fx/now]}
 :value-contract :time/instant
 :provider/ref trusted-clock-provider-ref
 :binding-adapter/ref sampled-invocation-time-ref
 :lifetime :invocation
 :failure-continuation/ref time-unavailable-ref}
#+end_src

The example is a construction binding, not proof that a clock is accurate or
that the value is transaction time. The operation names the temporal meaning it
requires. Retry semantics state whether a sampled value is preserved or replaced
and how that affects command binding and guards.

Providers include authentication, transaction execution, authoritative reads,
progression comparison, clocks, identity generation, publication, and external
services as needed. Missing, ambiguous, incompatible, or wrongly sourced supply
is rejected where statically knowable. Runtime unavailability follows its
required declared handling path. Having a transaction capability does not
authorize the transaction's business operation.

** Browser assembly manifest and physical artifacts
:PROPERTIES:
:CUSTOM_ID: req-browser-assembly-manifest
:END:

The browser build consumes the admitted semantic/build inputs of the same
application definition. Its manifest identifies the exact admitted plan set,
operation-to-plan correspondence, executable identities, interpretation/profile
contracts, required physical handlers, and relevant implementation/toolchain
inputs. It does not contain a digest of bytes that do not yet exist.

The admitted plan inventory must cover every required operation realization and
identify any deliberately included shared or currently unused plans. Missing,
duplicate, incompatible, or undeclared executable entries fail the applicable
inventory contract. Bundling an explicitly admitted extra plan is not intrinsically
wrong; letting an unexamined executable enter the claimed closed registry is.

*** A concrete generated-entrypoint construction

The normal build uses a Gesso-owned generated bootstrap source. It embeds or
imports the exact admitted manifest/plan payloads and invokes the canonical
runtime bootstrap. Application code supplies typed physical realization options;
it cannot replace the manifest-owned operation registry or plan resolver through
those options.

A concrete build sequence is:

1. Resolve the application definition once into the candidate semantic inputs and
   selected browser realization.
2. Derive the manifest and exact executable payloads from that construction.
3. Generate the bootstrap entrypoint and explicit imports for the admitted
   physical realization implementations.
4. Compile with the declared toolchain, dependency versions, options, and inputs.
5. Record the generated-input correspondence and digest the actual emitted assets.
6. Verify the staged manifest/receipt/asset set before publication.
7. Admit an immutable asset location set and bind it to the candidate assembly.

A low-level emitter accepting arbitrary JavaScript plus a copied manifest is not
equivalent to this construction. It may remain a testing or integration API with
a narrower guarantee.

There is no requirement for a magical parser that extracts all semantic plans
from arbitrary optimized JavaScript. Source-generation correspondence, compiler
fidelity under a named premise, and exact emitted-byte binding provide a concrete
argument. Stronger independently checked compiler/artifact correspondence can
replace the relevant premise when available. A runtime registry probe can add
conformance evidence, but a self-reported registry is not independent proof of
all code executed by the bundle.

*** Receipts bind provenance and bytes separately

A detached build receipt records the manifest identity, generated input/plan
identities, compiler/runtime/implementation closure, relevant build options, and
the exact digest/size/location of each emitted asset. Its evidentiary value depends
on provenance from the admitted build/checking boundary, not on the receipt's
own claims. It conveys no permission to perform a domain operation.

Verifying a digest establishes equality with recorded bytes under the digest
premise. It does not establish that those bytes implement the intended semantics.
Conversely, trusted compilation from the correct source does not establish that
the server later serves those same bytes. Both relationships belong in closure.

The asset set includes dynamic chunks, workers, imported runtime libraries, and
other resources whose behavior affects the claim. Relevant CSS or configuration
that can suppress or redirect an affordance also has a declared dependency or
qualification role. Diagnostic-only sidecars retain their separate noninterference
contract from Part V; they do not become executable semantic inputs.

Build inputs include opaque physical implementation changes where their behavior
matters. Reusing the same named =current= toolchain/runtime label across changed
implementations cannot preserve evidence applicability. Deterministic compilation
is useful but not a prerequisite for naming actual emitted bytes: a receipt can
bind one actual output even when another valid build yields different bytes.

*** Publication and serving preserve the checked binding

Candidate builds use isolated staging locations. A failed build or rejected
candidate cannot overwrite assets still served by an admitted assembly. Atomic
replacement of one file is insufficient if readers can observe a new bundle with
an old receipt or a mixture of old and new chunks. Publish a verified immutable
asset set, then switch the admitted serving reference.

The concrete serving strategy must prevent or detect substitution between check
and use. Content-addressed/versioned immutable assets are a useful default. An
open immutable resource handle, qualified store, or equivalent serving contract
can also work. Reading a mutable file once at startup and trusting its path
forever is not exact serving correspondence.

A page generated under assembly A must reference assets bound to A even if
assembly B activates before the browser requests them. A mutable logical URL that
now serves B can break that relationship. Versioned URLs or a qualified
assembly-specific asset selection protocol close it. Cache, CDN, service-worker,
and old-client behavior follow the selected deployment/profile contract.

The currentness check asks whether the assets intended for this admitted assembly
match its required build. It does not demand that every sleeping browser already
runs the newest deployment. Older continuations follow Part VI's compatibility
and recovery rules, including retained command resolution.

Tests of startup/currentness use the same verification mechanism and actual
artifact path as production. Synthetic stamped files can test a narrow checker,
but cannot stand in for the real generated runtime in application acceptance.

** Rendered affordances and concrete response closure

*** Minimal semantic intent in views

The view selects an admitted operation, supplies concrete arguments and required
observations, and chooses presentation/availability. Prepared bindings from Part
V derive the plan, transport, encoding, and other realization details from the
assembly. A view should not manually copy browser registries, authority roles,
command envelope formats, or artifact digests.

A prepared action is not current authorization. The trusted model boundary still
checks the principal, Request, Membership, Organization policy, and other
commit-time dependencies. Rendering an action establishes neither a permanent
permission nor a promise that a later attempt will succeed.

An action can be deliberately unavailable under its UI contract. Its semantic
identity and reason remain inspectable, and no effective transport survives that
unavailability. A missing required basis cannot be repaired by discarding semantic
metadata or forging a browser observation record.

*** Check the effective action, not one attribute

The render profile defines the HTML/HTMX subset whose effective behavior can be
checked. It accounts for all supported request sources and their composition,
including:

- generated semantic bindings and ordinary explicit request attributes;
- form action/method and submitter overrides;
- form association, including detached controls;
- applicable inherited attributes and explicit inheritance controls;
- relevant defaults, relative URLs, document/base context, and current path;
- supported boosting, extensions, response triggers, and navigation behavior;
- string/keyword or other attribute spellings that the serializer treats alike;
- conflicts between authored and generated transport, target, and protocol fields.

The profile must follow the actual selected browser/library behavior. It cannot
assume every attribute inherits, ignore a supported default action, or accept
silent last-write-wins merging where effective dispatch becomes ambiguous.
Duplicate IDs, invalid nested forms, conflicting attribute spellings, and browser
repair of malformed markup are rejected or explicitly handled where they affect
the claim.

A fragment can depend on a form or inherited context outside the returned tree.
Its assembly/rendering contract supplies the necessary host context or constrains
it to a self-contained composition. If required context is unknown, the checker
reports unsupported/unestablished behavior; it does not declare the fragment
complete because the missing ancestor was outside its scan.

An ordinary effective action targeting an assembled semantic route must carry
that route's required semantic realization. Moving the action to an ancestor or
substituting concrete path parameters does not make an anonymous semantic request
legal. Conversely, an ordinary read/search route remains ordinary when it meets
its declared acquisition and effect contracts without a command choreography.

Arbitrary client JavaScript can alter the DOM or send requests directly. Render
checking establishes the trusted output's supported realization, not honesty of
a hostile browser. Server admission remains independent. Effects of ordinary
scripts within protected browser footprints follow Part VI's ownership and
noninterference contract.

*** The final structured value is the checked value

Dynamic rendering is checked after the application has produced the concrete
structured output and before prohibited output is delivered. Checking a prepared
view model and then running an unchecked renderer is insufficient: the renderer
can introduce a malformed control after the check.

The normal response path is:

1. retain the request's admitted assembly and response-context binding;
2. perform view preparation and component expansion under their declared contracts;
3. materialize the concrete structured tree and effective-action context;
4. validate semantic bindings and all supported effective actions against that
   assembly;
5. serialize that same checked value through the admitted serializer;
6. apply only response transformations whose correspondence contract preserves
   the checked properties, or recheck after a relevant transformation;
7. release the response through the admitted delivery boundary.

Lazy values, component callbacks, mutable references, and serializer-time code
must not be evaluated once during checking and again with different results during
serialization. A supported implementation can materialize a bounded immutable
tree first, or use a serializer with an equivalent checked occurrence protocol.
It must state the actual mechanism and resource/failure limits.

This is structural/effective-action checking, not automatic HTML sanitization or
proof of arbitrary renderer purity. Content safety and active-content policy are
separate contracts, as in Part VI. A renderer that has already performed an
external side effect cannot have that effect undone by rejecting its output.

*** Systemic enforcement covers deferred and alternate responses

The canonical application handler installs the guard once for all supported
structured responses. Nested guards compose without disabling the outer guard.
Application authors need not remember a manual validation call at every render.

A dynamically scoped guard can implement the synchronous path, but an asynchronous
response may be completed after that dynamic scope has ended or on another
thread. The response completion carries an explicit assembly/guard context or
uses another qualified propagation mechanism. Absence of the required guard at
a managed serialization boundary is a failure, not a silent return to legacy
unchecked behavior.

The supported response profile covers or explicitly classifies:

| Response path | Required treatment |
|---------------+--------------------|
| Ordinary structured page/fragment | Check the actual final structured occurrence before serialization/delivery. |
| Deferred/asynchronous response | Preserve the admitted assembly and guard through completion, timeout, cancellation, and error handling. |
| Streaming output | Check each delivered managed portion under a compositional context or buffer the required scope; acknowledge that already-sent bytes cannot be withdrawn. |
| Cached structured fragment | Preserve semantic binding and applicability; check the concrete occurrence in its current context where needed. |
| Cached/pre-serialized HTML | Establish a separate admitted output correspondence and context/authority policy; a previous check does not authorize disclosure to another principal. |
| Error response after handler failure | Use the same supported output boundary or an explicitly admitted minimal error protocol. |
| Redirect/navigation/secondary-target response | Check its declared effect and target/protocol behavior, not only the main HTML body. |
| Raw HTML/custom renderer | Admit a separate realization contract or exclude it from the specific structured-output claim. |

Naming an escape hatch does not satisfy a requirement that all application
managed surfaces are covered. A policy requiring that coverage rejects an
uncovered managed path. Static assets or truly unmanaged output can be explicitly
outside that claim, provided their effects do not invalidate its premises.

A response cache key is not just a URL when its contents depend on tenant,
authorization, query, semantic contract, or assembly instance. The cache contract
states the partition, freshness, revocation, and revalidation behavior needed for
its claims. Returning a cached checked card to an unauthorized user is still a
disclosure failure.

*** Worked example: a render-time defect after a valid Claim

Startup admits the Claim operation and its return path. For a particular request,
the trusted model incorporates command C42 successfully. While preparing the
resulting card, a bug creates a Cancel affordance without its required Request
argument.

The output guard rejects that concrete card before delivery. It does not change
the authoritative Claim outcome to rejected. The trusted request boundary retains
its known result and follows the admitted response-failure protocol.

| Evidence available to the participant | Required treatment |
|---------------------------------------+--------------------|
| A permitted, correlated committed outcome is delivered through the supported error/settlement channel. | Preserve known incorporation; present response/installation failure separately and offer the authorized recovery path. |
| The server knows incorporation, but its response is lost or the browser cannot admit the payload. | The browser remains unknown until its resolver supplies admissible evidence. |
| A later card read shows the current claimant without command attribution. | It can establish current state at its scope; it does not by itself resolve C42. |
| The malformed response concerns an operation rejected before submission. | Preserve that actual disposition; do not route all response failures through a committed-only handler. |

The error protocol defines the actual HTTP/transport representation and the
browser hook that can decode it, including non-success status handling where
used. A map containing settlement metadata is not enough if the selected HTMX
profile never exposes that metadata to the runtime.

The fallback response itself must be valid and bounded. It must not recursively
invoke the same failing renderer forever or expose privileged diagnostics. A
minimal typed response or a later authenticated resolver may be more reliable
than trying to render the full card again inside the error handler.

Tests distinguish no malformed output was delivered from no protected mutation
occurred. The former is the render guard's responsibility; the latter requires
an earlier command/model gate. Both need a positive control showing that valid
requests remain usable.

** Authoritative outcome, acquisition, and propagation closure

*** Model outcomes and presentation settlements are explicit mappings

The authoritative command protocol uses Part IV's =:committed=, =:rejected=,
=:already-incorporated=, and =:commit-unknown=. Domain result payloads and browser
presentation settlements are separate types.

A Claim presentation may use =:accepted=, =:rejected=, and =:unknown=. Assembly
checks the explicit mapping, including a permitted recorded success from
=:already-incorporated=, incompatible command reuse, nondisclosable prior results,
and unresolved evidence. It does not substitute an assortment of transport
labels such as confirmed or superseded for the model outcome contract.

The trusted boundary checks permission to disclose a prior outcome. A successful
replay lookup does not confer disclosure authority on the caller. A local timeout,
HTTP 500, missing command row under an insufficient lookup, or present-state card
cannot be wired as unconditional proof of command rejection.

A direct response, durable resolver, and current-state acquisition have different
claims. Assembly closes the paths required by the operation rather than assuming
one route serves all three purposes.

*** Recovery includes an owner, trigger, and retained binding

A declaration that names a resolver endpoint is incomplete if nothing can invoke
it or the command binding is lost when the local execution retires. Required
recovery states identify:

- the work/command and sufficient retained binding or protected recovery reference;
- the current owner and lifetime, including transfer on retirement;
- the evidence needed to resolve the condition;
- current authorization and disclosure requirements;
- the actual trigger and permission for the next action;
- bounded automatic retry/backoff where permitted;
- behavior when plans, contracts, providers, or retained records are unavailable;
- the explicit terminal, blocked, deferred, or manual-reconciliation state.

Part VI's cross-deployment command recovery applies. A new plan cannot reinterpret
old arguments under changed operation semantics while keeping the old command ID.
The assembly identifies retained resolver/compatibility support independently of
new invocation support.

*** Progression remains scoped through the return path

The mutation, command record, publication/durable intent, acquisition, renderer,
and browser coordinator must agree on the meaning of their progression and
coverage requirements. Generic assembly code validates compatible provider
contracts; it does not calculate a universal maximum over unrelated tokens.

Acquisition requests carry the required scope and lower bound under the provider's
semantics. Returned evidence reports the actual established observation. An
installation uses that observation and the browser's current target/owner rights.
Adoption and debt discharge require the applicable physical completion, as in
Part IV and Part VI. HTTP completion is not a substitute.

A query membership obligation may require different evidence from a card-content
obligation. Initial server-rendered content is also an acquisition path with
provenance and coverage. An empty managed fragment needs a permitted acquisition
path and a truthful loading/unavailable state; absence of both initial knowledge
and acquisition is a structural defect.

*** Required publication and durable work have recovery semantics

When operation semantics or product convergence requires publication, it belongs
in application closure. Naming a publisher function does not establish that it
runs after commit or survives a crash between commit and publication.

The assembly binds the chosen Part IV recovery strategy: durable publication/work
intent with a worker, a qualified replay stream, periodic reacquisition, explicit
Refresh under its conditions, or another declared mechanism. It identifies the
failure domain and liveness premises. There is no universal promise of event
delivery merely because an SSE connection exists.

A lost settlement or publication leaves incorporation intact and creates or
preserves the relevant delivery/recovery debt. Worker acknowledgment and retries
must agree with the durable work contract. External effects such as payment or
notification are not undone by browser retirement or response failure.

*** Live closure includes subscription continuity and adoption policy

The Live declaration binds the authoritative query/projection, relevant interests,
initial observation, subscription owner, progression provider, acquisition route,
and coordinator policy. The stable logical owner and replaceable physical target
have distinct identities and reconstruction rules.

The application closes the baseline/subscription gap and reconnect gaps using a
qualified fence, replay, buffering, polling, or reacquisition strategy. A process
that publishes changes only for interests known locally must justify how remote
or newly registered interests avoid missed updates. Absence of a locally known
interest is not proof that no other participant needs the change.

Shared subscriptions retain per-interest ownership and authorization. Connection
replacement, authorization-context changes, and lost continuity produce the
required recovery work even when no new advisory arrives. Coarse routing/filtering
can optimize delivery only under a contract that preserves the required coverage
or has a compensating recovery path.

Advisory debt, acquisition permission, and adoption permission remain distinct.
HumanHelp may announce remote changes and wait for explicit Refresh. A newly
arriving advisory does not silently inherit an expired one-read grant. Closure
checks that the declared policy has a real trigger, retained debt, and a viable
path to the promised scoped adoption.

** Static preflight and required dynamic handling

Static preflight is mandatory construction/startup work for the managed application.
It consumes the actual canonical construction and artifact products, rather than
a manually reconstructed preflight-only registry. It runs at the earliest stage
with enough information and produces structured obligations/results.

*** Failure belongs at the earliest legitimate boundary

| Boundary | Representative checks |
|----------+-----------------------|
| Semantic construction | Malformed interfaces, contradictory roles/knowledge, invalid transition terms, unsupported declaration structure. |
| Assembly/build | Missing operation realization, incompatible provider, wrong plan/route binding, incomplete required recovery, stale asset set. |
| Installation/activation | Wrong actual handler/executor, missing policy gate, unsupported lifecycle ordering, incorrect server/asset adoption. |
| Concrete rendering | Missing bound argument, anonymous semantic route, unavailable action retaining transport, unsupported effective-action context. |
| Request/effect admission | Malformed envelope, contradictory selectors, stale assembly/resource binding, invalid actual candidate or effect target. |
| Authoritative incorporation | Current permissions and dependencies, atomic guard failure, command binding/replay/disclosure rules. |
| Completion/recovery | Actual outcome, acquisition/installation evidence, unresolved delivery, partial effects, cleanup and retry conditions. |

A valid assembly can receive a rejected Claim because Membership changed after
render. That is not assembly corruption. Conversely, a known missing clock
binding should not be deferred until the first Claim throws a missing-input
exception.

*** Required handling coverage
:PROPERTIES:
:CUSTOM_ID: req-preflight-dynamic-handling-coverage
:END:

Preflight need not predict dynamic facts. It must check declared handling/recovery
paths for supported dynamic conditions that could strand an operation. A happy-path
provider or reachable terminal node is insufficient.

The obligation identifies the condition, source contract, continuation input,
owner, required resources/evidence, trigger, and permitted outcome. Construction
checks the corresponding graph edges and type/binding compatibility. An opaque
statement saying recovery exists cannot replace an available structural check.

| Condition | Required declaration and realization |
|-----------+--------------------------------------|
| Provider fails before submission | A typed local failure/retry path that does not claim authoritative incorporation or rejection without evidence. |
| Delivery is lost after possible submission | Unknown command disposition, retained binding, and a valid reconciliation owner/path. |
| Prior result cannot be disclosed | A permitted nondisclosing continuation without false rejection or information leakage. |
| Acquisition cannot establish required scope/progression | Retained debt and a declared stronger read, retry, defer, or blocked state. |
| DOM installation is partial or completion is lost | Repair/reconciliation without premature adoption. |
| Continuity restore fails after adoption | Local continuity failure without undoing authoritative installation. |
| Subscription misses changes | Gap recovery independent of receiving a fresh advisory. |
| Plan/operation version becomes incompatible | Retirement/transfer and retained command resolution under a compatible contract. |
| Recovery budget or retention expires | Truthful deferred/blocked/manual handling with no fabricated authoritative disposition. |

These checks cover the declared supported conditions. They do not prove that
arbitrary external software has no additional failure modes or that recovery will
eventually succeed. Unexpected failures enter an explicit containment boundary
that preserves evidence, uncertainty, and surviving obligations.

A path to a terminal node is not a termination theorem. Liveness depends on the
stated availability, scheduler, permission, resource, and user-action premises.
The application explanation shows those premises next to its progress claims.

*** Resource policies are part of admission

Construction and runtime declare limits for model exploration, graph size,
render materialization, response buffering, active executions, recovery queues,
physical remnants, and evidence retention where those resources matter. Limits
have typed outcomes and handling paths.

A resource limit cannot turn an unfinished proof into a successful check, a dropped
advisory into discharged debt, or a lost command record into a rejected command.
Static checking validates the declared policies; runtime enforces their actual
budgets and preserves the appropriate scope of uncertainty.

** Lifecycle, installation, and supported startup
:PROPERTIES:
:CUSTOM_ID: req-application-lifecycle
:END:

The supported application startup path composes native lifecycle modules under a
qualified integration contract. For a Biff application, that contract names the
selected Biff module/system behavior and the server's handler adoption behavior.
The design does not depend on an unspecified future release automatically
performing Gesso's checks.

Every lifecycle owner has a stable qualified identity, dependencies, start/init
semantics, owned resources, and cleanup behavior. Duplicate IDs, unknown required
IDs, incompatible shared ownership, and required dependency cycles are rejected.
A module is not accepted merely because it uses the expected ID while replacing
the required implementation with a different function.

*** Preflight and installation precede application exposure

The required partial order is:

1. obtain and validate the source/configuration and private resources needed for
   construction;
2. close semantic, build, provider, and selected assurance obligations;
3. construct/install the admitted router, response guard, execution/provider
   bindings, workers, and asset references;
4. check their actual required installation relationships;
5. activate the application-serving boundary.

A particular framework may have separate init and start phases. All phases must
respect the exposure rule. Starting an application listener during an earlier
init callback cannot be excused because the named preflight module later appears
first in a start-order list.

There is no universal requirement that preflight be the first module in every
system. Its real dependencies may need private initialization. There is a universal
requirement that no managed application operation is externally available before
its required admission and enforcement bindings are ready.

Health or administration endpoints can have separately admitted scope. They
must not expose unchecked application behavior under a health-check exception.
A listener bound privately or returning only a separately admitted unavailable
response is different from a ready application listener; the profile states its
observable behavior precisely.

*** The ordinary constructor installs the guarded handler

The application start function derives or enforces the required modules and
ordering. Application authors do not manually remember a preflight ID, wrap one
test handler, or maintain separate checked-dev and unchecked-production entrypoints.

A schematic API sequence is:

#+begin_src clojure
(let [definition (application-definition config)
      candidate (application/prepare! definition)
      installation (application/install-private! candidate host-profile)]
  (application/activate! installation))
#+end_src

The contracts of these calls are substantive:

- =prepare!= admits the semantic/build candidate under its policy; it does not
  report that a server has started.
- =install-private!= consumes that candidate, constructs the actual bindings,
  records owned resources, and runs the relevant installation checks without
  exposing unchecked application operations.
- =activate!= consumes the genuine current installation and completes the declared
  exposure transition; it does not trust a caller-edited accepted flag.

Implementations can combine these calls behind a smaller public interface.
Their phase obligations still hold. A constructor that merely returns an accepted
map without installing the required path does not satisfy the contract.

The final server receives the exact admitted wrapped handler, or a qualified
wrapper composition preserving its contracts. The application can inspect the
actual server/installation relationship to the extent promised by the profile.
Local system-map adoption, observed invocation, and deployed-service adoption
remain separately scoped evidence.

*** Request lifetime spans asynchronous completion

At entry, an invocation captures its assembly instance and concrete context. It
resolves route, executor, providers, outcome encoding, render guard, and assets
through those compatible bindings. Asynchronous completion carries this context
explicitly rather than consulting whichever registry became current meanwhile.

An invocation's completion, cancellation, timeout, and transferred work determine
when its assembly/resource references can be released. A handler returning a
future is not necessarily a completed invocation. Streams and workers have
separate declared lifetimes.

Old assembly bindings do not freeze current business authority. Each operation
still checks the current trusted model/authentication premises required by its
contract. If an old assembly or provider profile is revoked, its continued use
requires the declared retirement/compatibility policy, not indefinite reliance
on the fact that a request once acquired a reference.

*** Reload builds a candidate before activation

Development reload and deployment use the same coherence rule. A candidate is
constructed and checked separately from the current admitted assembly. Activation
switches the appropriate new-entry bindings as one admitted transition, using a
compare-and-activate or equivalent mechanism that prevents concurrent reloads
from replacing a newer instance with an older candidate.

The transition covers routes, issued executors, providers, assurance policy,
render checking, asset references, and other relevant realization bindings. It
cannot expose new routes with stale browser assets and an unrelated old report.

In-flight work remains bound to its still-valid assembly or follows an explicit
checked transfer. New invocations use the new instance. Old assets and resolver
contracts remain available for the lifetimes promised by the compatibility and
recovery policy; reference counts alone do not account for sleeping browsers that
are no longer represented by a live server request.

A rejected candidate may leave the prior instance serving only while that instance
remains valid. If a security, backend, or semantic premise has invalidated the old
instance, failed replacement is not permission to keep using it. The application
suspends affected work or follows a declared restricted mode.

Relevant change invalidates dependent evidence. An incremental implementation
can reuse unchanged checked subgraphs and artifacts, but must recheck their joins
into the new root. Cache reuse is justified by complete dependency/applicability
bindings; it is not an assertion that the source looks similar.

*** Cleanup preserves ownership and primary failure

Each lifecycle module owns the resources it acquires and any explicitly shared
references. Failed startup retires completed private installations and accounts
for partial acquisition, in dependency-safe order. Cleanup errors are retained
as secondary diagnostics; they do not replace the primary admission failure.

No failed candidate leaves an unchecked application listener or worker active.
Work already transferred to a durable admitted owner remains governed by its
contract. Cleanup cannot erase a committed transaction, acknowledge unfinished
durable work as complete, or cancel a replacement assembly's shared resources.

Shutdown and replacement preserve uncertain command/work obligations through
admitted transfer or durable recovery. Best-effort physical stop follows semantic
retirement; failure to close a socket or release a registry handle does not retain
the old owner's authority to initiate work.

** Production-path enforcement evidence
:PROPERTIES:
:CUSTOM_ID: req-production-path-enforcement
:END:

Checker correctness and production integration require different tests. A checker
can reject malformed input perfectly while the actual application never calls it.
The supported construction therefore provides observable seams for controlled
faults at the real startup, route, effect, and response boundaries.

Each enforcement case records:

- the admitted source/configuration and actual entrypoint under test;
- the controlled defect and the subject/edge it breaks;
- the earliest boundary with enough information to reject it;
- the expected structured diagnostic or typed disposition;
- the prohibited output or physical effect whose absence is observed;
- any already-performed effect or surviving uncertainty that must be preserved;
- a corresponding valid case showing the path remains usable.

A test-only wrapper that rejects before the real entrypoint does not establish
production enforcement. Removing the actual enforcement connection must make the
appropriate integration test fail. The test must distinguish prevented effect,
detected violation after effect, and inability to establish either.

*** Controlled defects exercise actual construction and installation

| Controlled defect | Boundary and required result |
|-------------------+------------------------------|
| Required plan omitted from the source-derived browser build | Build/admission rejects the missing realization. |
| Correct receipt paired with different asset bytes | Asset admission rejects; the candidate does not serve that pair. |
| Correctly named route installed with a different executor | Installation/invocation gate rejects the mismatched binding. |
| Required provider name exists but returns/binds the wrong shape | Static contract mismatch or concrete provider admission rejects at the applicable boundary. |
| Required assurance policy is selected but its gate is omitted | Managed installation/activation fails; a standalone checker test cannot mask it. |
| Render guard removed or an outer guard shadowed | Concrete malformed output cannot pass the managed delivery boundary. |
| Deferred response loses assembly/guard context | Completion rejects or uses the declared safe failure path; it cannot serialize unchecked. |
| Final renderer introduces an anonymous semantic action | Final structured-output checking detects it even if preparation was valid. |
| Post-check middleware changes the protected action | The transformation is rejected, rechecked, or lacks the claimed admission. |
| Undeclared writer appears in the actual covered inventory | Required closed-coverage admission fails; otherwise the affected claim is explicitly limited under its policy. |
| Candidate activation changes only routes and leaves old assets/providers | Coherence check prevents partial activation. |
| Post-commit rendering fails | Malformed output is withheld while incorporation/participant uncertainty remains truthful. |

These defects use isolated fixtures and the supported production constructor.
They do not alter a real user's live data to test failure. The corresponding
assertions observe the actual server/effect/output seam relevant to the claim.

*** Real browser acceptance starts from real controls

Top-level browser acceptance loads the actual generated runtime and operates the
application's rendered controls. It observes the emitted protocol, selected route,
trusted model result, returned evidence, physical installation, and subsequent
authoritative read as required by the capability.

It must not repair a missing command field by injecting a valid envelope or
manually dispatching the event the button failed to produce. Such setup is useful
in a lower-level protocol test, whose claim is deliberately narrower.

Acceptance includes valid repetition and concurrent activity, not just the first
successful request. Request-scoped issuance must allow later requests and the
admitted degree of concurrency. Out-of-order completions must preserve separate
invocation/command/target ownership. A one-shot test harness cannot establish a
reusable production route.

Expected fault diagnostics are asserted specifically. Broadly ignoring console,
page, or request errors would hide the integration failure this layer exists to
catch. Conversely, a deliberate network-loss test need not pretend no diagnostic
should occur.

** Application explanation and semantic audit
:PROPERTIES:
:CUSTOM_ID: req-whole-application-semantic-audit-surface
:END:

The application exposes a structured, read-only semantic audit derived from its
actual admitted sources, construction products, and evidence. It supports review
of the correctness-relevant policy without treating a large implementation as
an undifferentiated body of code.

The audit is not a second editable policy registry. Business-rule prose, operation
cards, diagrams, and evidence summaries are projections of the same admitted
subject. Prose explains meaning and rationale; it does not gain mechanical force
by appearing beside a checked predicate.

*** Required audit views

| View | Information and required limits |
|------+---------------------------------|
| Business-rule catalog | Stable rule identity, meaning/rationale, formal or opaque contract, source, affected operations, authority, enforcement, and actual evidence. |
| Operation card | Typed inputs, principal/authority dependencies, guards, transition/frame, outcomes, command repetition/disclosure, effects, and recovery. |
| Authorization/disclosure | Current authority sources and policies for invocation, reads, subscription, and prior-result resolution. |
| Domain lifecycle | Actual admitted states and transition relation, generated from semantic definitions rather than guessed from route names. |
| Realization path | Exposed surfaces, plans, assets, routes, actual handlers/executors, providers, acquisition/installation, and serving bindings. |
| Rule/evidence dependencies | Claims affected by a changed rule, operation, implementation, backend profile, or accepted premise. |
| Writer/entrypoint coverage | Declared, installed, observed, classified, excluded, and still-unestablished paths at their actual scope. |
| Opaque-premise report | Each retained premise, its owner/reason, applicability, available tests, and dependent claims. |
| Assurance and exercise | Exact finite bounds, rule/operation/outcome exercise, conditional induction, runtime gates, conformance results, and gaps. |
| Recovery/continuity | Owners and triggers for unknown commands, failed adoption, missed publication, subscription gaps, and version incompatibility. |

A domain lifecycle view uses the operation model's actual enum. It must not rename
HumanHelp's states to superficially similar completed/cancelled labels or infer
terminality from a UI caption.

*** Unknown inventory is not an empty inventory

If a model adapter exposes only a public operation name, the audit cannot infer
its internal predicates or atomic dependency protection. It reports those bodies
as not inspected with their explicit conformance premise. An empty business-rule
list would misleadingly suggest there were no relevant rules.

The same distinction applies to writers, side effects, publication, and policy
branches. Zero unresolved declared edges is not proof of complete human intent
or absence of undiscovered behavior in arbitrary host code.

Enriching the application with source-owned relational rules or checked transition
terms adds concrete audit coverage. It does not retroactively establish that
uninspected callbacks contain no extra policy. The view distinguishes complete
coverage of a supported construction subset from registered opaque boundaries
and unexamined external behavior.

*** Declared Live overlap is not a transaction dependency proof

Two operations may publish the same topic or affect the same board while touching
different authoritative records. Conversely, two opaque operations may share a
transaction dependency not present in their declared Live topics.

The audit can display topic/fragment overlap as declared presentation impact.
It must not relabel that result a business-rule dependency, complete read/write
footprint, or conflict graph without evidence supporting that stronger relation.
Part IV's guard and footprint contracts determine authoritative dependency meaning.

*** Explain one operation end to end

A useful explanation of Claim identifies:

1. the exact semantic source, rule dependencies, and operation interface;
2. exposed controls and their selected realization alternatives;
3. projected roles, executable identities, physical handlers, and asset bindings;
4. route/input correspondence and the actual installed executor;
5. provider contracts, invocation gates, and current authoritative guard obligations;
6. model-to-presentation outcome mapping, including repetition and unknown;
7. acquisition, propagation, installation, and recovery paths;
8. assembly/installation identity, policy, evidence applicability, retained premises,
   and unresolved or excluded claims.

The output may show a local issued-handler binding as established while leaving
backend transition refinement conditional on its qualified provider. It may show
finite rule exercise without claiming that every production predicate branch was
executed. Those distinctions are useful information, not deficiencies to hide
behind a single green label.

*** Inspection does not execute or authorize

Explanation reads admitted results and immutable/redacted trace values. It does
not invoke operation callbacks, submit transactions, rerun model builders,
mutate runtime registries, or repair missing edges. Expensive fresh checking is
an explicit separate action whose result has its own identity and scope.

No diagnostic output needs to expose live executor handles, credentials,
principal-sensitive data, or unrestricted command arguments. Redaction reports
what is unavailable rather than fabricating a replacement explanation. Internal
repair detail and client-facing errors can have different disclosure policies.

The explanatory surface can show an incomplete candidate's rejected/open
obligations without making that candidate executable. A stale sidecar or trace
mapping must not explain a different executable plan by matching similar names;
Part V's exact correspondence rules apply.

** Structured diagnostics and repair

Diagnostics identify the failed obligation and its actual owner. Human-readable
messages are rendered from stable structured data; tools should not parse prose
to discover whether the missing edge was a route, provider, asset, or recovery
continuation.

A diagnostic includes, where applicable:

- the error kind and detecting phase;
- operation, projection, route, resource, or claim subject;
- assembly/installation and relevant executable/artifact identities;
- source location that introduced the obligation and source responsible for supply;
- expected relation and actual observed/bound values, within disclosure limits;
- rejected, unsupported, inconclusive, contradicted, or inapplicable status;
- remaining premises and whether any protected effect already occurred;
- mechanically known repair alternatives without automatic substitution.

An illustrative provider error is:

#+begin_src clojure
{:error/kind :incompatible-capability-provider
 :phase :assembly/admission
 :assembly-instance/id candidate-id
 :operation/id :request/claim
 :obligation/id :claim/commit-time-input
 :introduced-by claim-source-ref
 :supplied-by server-binding-source-ref
 :expected {:input-path [:execution-context :biff.fx/now]
            :value-contract :time/instant}
 :actual {:input-path [:execution-context :clock]
          :value-contract :clock/zero-argument-function}
 :suggestions [{:kind :explicit-binding-adapter
                :contract/ref sampled-invocation-time-ref}]}
#+end_src

The suggestion does not install that adapter. Source correction and admission
establish the new binding. Likewise, an unknown =:request/claime= may suggest
=:request/claim= diagnostically but must never be corrected automatically for
execution.

*** Stable diagnostic families

| Family | Representative distinctions |
|--------+-----------------------------|
| Semantic construction | Unknown operation, duplicate identity, invalid interface, contradictory transition, incompatible realization. |
| Plan/build | Missing plan, wrong plan/operation, stale manifest, asset-byte mismatch, incomplete asset set, unestablished build correspondence. |
| Dispatch/execution | Missing/ambiguous route, selector conflict, wrong issued executor, unsupported route semantics, unclassified writer. |
| Provider/effect | Missing provider, incompatible value or origin, invalid actual candidate, wrong target, unsupported lifetime. |
| Rendering | Missing arguments/basis, anonymous semantic route, implicit downgrade, conflicting attributes, unknown effective context, unchecked response path. |
| Recovery | Missing continuation, incompatible outcome mapping, absent owner/trigger, unsupported retained command contract, unmet acquisition/installation requirement. |
| Installation/lifecycle | Missing gate, wrong actual handler, premature exposure, assembly-instance mismatch, invalid dependency, failed activation/cleanup. |
| Assurance | Unsupported fragment, inconclusive budget, counterexample, inapplicable evidence, unaccepted premise, insufficient coverage. |

These families need stable public identities without requiring this document's
exact keyword spellings. A missing resource and an existing incompatible resource
should not be indistinguishable. Dynamic authorization denial retains its model
outcome and privacy policy; it is not reported as a corrupt assembly.

A diagnostic must not claim semantic verification succeeded merely because it
reached a later code path. It reports only established evidence. Source summaries,
artifact stamps, and provider declarations can be useful repair facts without
being proofs of their implementations.

** Acceptance, qualification, and change impact

*** The application is usable as well as closed

Independent product acceptance specifies promised user capabilities and outcomes
without copying the framework's route/operation registry. Removing a required
capability must fail that acceptance even when the smaller assembly remains
internally consistent.

For HumanHelp, a coherent disabled Claim control does not satisfy a milestone
requiring helpers to claim Requests. A board that never acquires anything is not
complete because no malformed swap occurred. Positive paths, authorized rejection,
uncertainty/recovery, and relevant multi-client behavior are all part of the
appropriate capability acceptance.

This independence does not require independent duplicate implementations of
business policy. The product oracle describes intended observable behavior;
the semantic construction remains the source of executable operation meaning.
A disagreement prompts review of the specification, implementation, or oracle,
not automatic rewriting of one to match the other.

*** Conformance is bound to actual subjects

Evidence records the source/implementation identity, assembly/configuration,
provider and browser profiles, test/checker version, exercised paths, bounds, and
known limitations. A passing fixture with mocked providers is not evidence that
an unexamined production transaction or subscription implementation conforms.

Each backend profile names the assumptions required by dependent claims, including
atomic dependency protection, command-record incorporation, outcome interpretation,
read progression, retention, and failure/retry semantics where used. A current or
future backend version is qualified against those same assumptions. Detecting a
violation invalidates or blocks the dependent claim; it must not be hidden by a
version update or a stale successful receipt.

Conformance tests can expose an assumption violation without proving the entire
backend. That is a useful and intended contract. Unknown qualification after a
relevant upgrade remains unknown until the selected admission policy establishes
sufficient applicability; a changed version number is neither proof of failure
nor proof of continued correctness.

*** Required verification scenarios

The verification strategy covers semantic construction, production enforcement,
and product behavior with appropriately scoped evidence. At minimum, relevant
application profiles exercise:

| Scenario | Evidence sought |
|----------+-----------------|
| Same canonical definition feeds build, startup, render, and tests | Removing or changing an owned declaration affects the actual consuming paths. |
| An opaque builder returns an invalid candidate | The actual candidate is rejected before submission without claiming all builder behavior was proved. |
| Finite exploration reaches its declared bound or exhausts its resource budget | Scope-complete finite results remain distinct from inconclusive computation and unbounded claims. |
| Rule/operation/outcome exercise is vacuous | Required exercise gates reject; the report does not inflate attempted or disabled operations into commits. |
| A copied report or metadata-equivalent function replaces an issued product | Admission rejects the substitution or explicitly establishes a new binding. |
| The server captures an earlier handler while the system map later changes | Installation evidence detects or limits the server-adoption claim rather than trusting the later map. |
| A worker writes state outside the HTTP catalog | Its path is classified and covered, or the dependent closed-world claim fails/remains explicitly conditional. |
| Two valid requests overlap and complete in reverse order | Their scoped capabilities, outcomes, and rendering contexts remain separate and reusable. |
| A deferred/streamed/cached response bypasses the synchronous guard | The selected response contract prevents unchecked managed output or reports the unsupported path. |
| A fragment's effective form/action depends on outer context | Checking uses admitted context or rejects the unestablished interpretation. |
| Old HTML requests assets after a new assembly activates | It receives the bound compatible asset set or follows the declared compatibility failure/recovery path. |
| Artifact, handler, policy, provider, or backend premise changes | Dependent evidence is invalidated/rechecked without mutating an old admission in place. |
| Startup or activation fails after acquiring resources | No unchecked application exposure remains; cleanup and surviving work are accounted for. |
| The response fails after authoritative incorporation | Server knowledge and participant uncertainty remain distinct and recoverable. |
| A disconnected subscriber misses relevant changes | Initial/reconnect acquisition closes the required gap without needing a new advisory to arrive. |
| A required user capability is removed while the remaining graph closes | Independent product acceptance fails. |

Formal checks, controlled-defect tests, observed execution correspondence, and
real-browser acceptance are complementary. A unit test of a report shape cannot
replace evidence that the actual handler or browser edge is used. A successful
request cannot establish every route or every possible schedule.

The suite includes positive controls for each rejection gate. Rejecting all
requests, never exposing a control, or disabling concurrency universally is not
an acceptable way to satisfy the intended application's behavioral requirements.

** Whole-application security and construction invariant

Preflight establishes the stated structural relationships and selected assurance
conditions. It does not confer a principal, disclose a protected result, authorize
a transaction, or establish that a mutable world still satisfies a prior guard.
Those premises are checked at the trusted boundary that owns them.

The browser can forge local metadata, operation names, command bytes, certificates,
and assembly IDs. Trusted ingress and model operations remain secure without
assuming that the browser follows the admitted implementation. Conversely, server
construction controls accidental misuse by trusted host code; a hostile JVM with
reflection or arbitrary bytecode replacement is outside that claim unless an
additional isolation mechanism is explicitly supplied and qualified.

A structural report, artifact receipt, process-local handle, proof certificate,
and runtime observation each has a defined role. None silently acquires the
others' authority. Production evidence is applied only to its actual subject,
scope, assumptions, and current applicability.

The whole-application invariant is:

#+begin_quote
One source-owned definition yields an admitted semantic and physical realization
under an explicit assurance policy. Every required operation, effect, output,
observation, and recovery edge has a compatible current binding, and the actual
installed paths enforce the required checks before their protected actions.
Construction, artifact, installation, invocation, and physical-completion facts
remain distinct. Missing structural edges reject rather than silently weaken
meaning; opaque application logic retains explicit contracts and premises.
Admitted assembly instances remain coherent through build, serving, asynchronous
work, reload, and retirement. Declared closure, production enforcement, and
independent product completeness are separately evidenced, and authority remains
with the trusted runtime/model boundaries that own the relevant current facts.
#+end_quote
