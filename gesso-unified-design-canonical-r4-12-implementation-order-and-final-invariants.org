* Part XII — Implementation order and final invariants
:PROPERTIES:
:CUSTOM_ID: part-12-implementation-order-and-final-invariants
:PART_REVISION: 12-20261108
:END:

This part defines a construction order for the system specified in Parts I–XI.
It starts from the required semantics and observable application behavior, then
connects their implementation, checking, qualification, and release evidence.
It is a design from zero, not a report of completed work or a migration checklist
for a particular repository snapshot.

Eighteen stages organize the work. Their numbers are navigation and a useful
reading order, not a requirement to finish every lower-numbered stage before
beginning a higher-numbered one. The dependency table identifies the branches.
The four completion scopes remain those of Part XI; a stage number is not a
milestone badge and a sophisticated proof fixture is not a usable application.

Stage order is a *contract dependency and delivery priority*, not a serial
project-management lock. Distinguish a semantic prerequisite, a normally earlier
implementation task, exploratory feedback that may be obtained sooner, optional
early hardening, and a completion dependency for a named claim. Later work may
expose a missing earlier contract; repair that contract at its actual owner and
reconsider only the dependent evidence. A prototype can inform the design
without borrowing the acceptance status of a completed stage.

** Delivery discipline

*** Construct one useful path and strengthen the same objects

The first integrated path is a real HumanHelp Claim using public production
models, the canonical application construction, the generated browser plan,
the actual trusted invocation and transaction boundary, and an admitted visible
result or recovery path. Build only the supported breadth needed for that path
before generalizing, while keeping its missing obligations explicit.

The path must include RequestAssignment ownership, current policy dependencies,
command identity and replay, and unknown-outcome recovery from the beginning.
A single-document demonstration can qualify a narrower mechanism. It cannot be
renamed as the completed Claim path while those relationships are absent.

The integrated witness must include an eligible actor authorized by the current
trusted model, an actual Request and RequestAssignment with the guarded
one-primary relationship, a stable logical command, the installed route and
trusted writer that submit the actual effect, and a scoped authoritative
observation for the outcome or its unresolved recovery. A declared operation,
a generated route, a browser fixture, an optimistic card, and a committed
Request are not interchangeable evidence that this complete path worked.
Where real backend or application behavior has not yet been observed, the
record names the still-open physical or product claim.

Pair that eligible success with nearby failures: a competing Claim, an expired
Membership, a missing or incompatible effect capability, a request that may
have committed before its response was lost, and a callback from an obsolete
browser execution. Reject each defect at its first legitimately informed
boundary, or retain uncertainty and the explicit recovery obligation when
the boundary cannot decide. A later visible card alone cannot reconstruct
which earlier logical command incorporated.

The Claim path is the first integration slice, not the whole HumanHelp product.
The independent capability inventory in Part VIII remains fixed while the rest
of the application is constructed. Removing a difficult operation from the
exposed registry cannot make its requirement disappear. A still-unselected
HumanHelp Response interaction likewise remains an explicit product-owned
requirement, not a plausible behavior inferred from the working Claim slice.
The selected remote-board policy remains advisory until an authorized
scope-limited, one-use Refresh or an explicitly narrower local exception;
Live delivery and automatic DOM swap do not silently grant adoption.

The ordinary construction must remain useful for arbitrary Clojure and
ClojureScript behind explicit contracts. Closed proof languages establish
supported properties; opaque implementations retain named premises and their
runtime enforcement. There is no second unmanaged application architecture for
code that the prover cannot analyze. A supported opaque Clojure function may
carry named, checked-at-use runtime obligations; its opacity must not be
treated as an implicit proof, automatic exclusion from the source inventory,
or permission to bypass the application's admitted execution path.

*** Establish the real serving boundary before calling a slice runnable

A declared first path requires a compatible, actually installed host substrate.
The selected supported Biff lifecycle and FX contracts, the application
assembly, its stable startup/preflight gate, and the effective Ring/HTMX routes
must be qualified for the path actually served. In particular, a listener must
not expose a supposedly admitted operation before the required preflight and
startup checks have passed. Startup failure fences newly acquired resources
rather than leaving an unchecked handler serving.

This does not demand the final universal closure checker or all later formal
theorems before any useful application work begins. It demands a genuine
enforcing seam for the selected scope and an honest account of what it does
not yet inspect. A green assembly map, successful compilation, manually
invoked handler, or test fixture does not by itself show that the deployed
listener, active writer, loaded browser asset, and Biff execution flow are
the ones whose contracts were checked.

The exact supported Biff and backend profiles are selected and qualified as
implementation subjects; they are not extra business-rule owners. Changes to
an FX invocation contract, initializer, protected writer, browser bundle,
served route or provider configuration trigger reconsideration at the
affected physical boundary even if the abstract rule is unchanged.

*** Start cross-cutting obligations at their first boundary

The following work accompanies construction throughout the roadmap:

| Concern | Begins when | Required discipline |
|---------+-------------+---------------------|
| Source ownership and identities | The first semantic object is declared | Derived objects retain their actual source and interpretation dependencies |
| Obligation and premise accounting | A claim is made | Preserve the original obligation and distinguish checked evidence from accepted premises |
| Positive and negative tests | A boundary can admit or reject | Exercise a useful valid case and the relevant defect at the intended boundary |
| Physical correspondence | A semantic action first reaches an effect provider | Bind the issued plan, actual invocation, physical operation, and observation origin |
| Diagnostics | A checker or runtime boundary can fail | Identify the failed obligation, scope, source, and repair owner |
| Artifact and release integrity | A candidate is built or served | Verify the actual plan, manifest, bytes, installed bindings, and selected profile |
| Resource and recovery limits | Work can wait, retry, queue, or outlive its owner | Bound retained work and preserve unresolved obligations honestly |
| Backend qualification | A claim uses provider semantics | Name the exact assumption and applicable adapter/version/configuration envelope |
| Original capability inventory | A product or application scope is chosen | Preserve independently required actions and the full denominator even when assembly discovers fewer routes or features |
| Actor, disclosure, and current authority | A request can observe or change protected facts | Bind the authenticated principal, model-owned guards, scope and actual trusted read/write boundary; never derive them from browser metadata |
| Actual application admission | The first handler, worker, or browser artifact is installed | Check the real covered path and retain the uninspected or bypassing effect inventory as an explicit obligation |
| Publication and command continuity | A commit, notification, retry, or host loss is possible | Separate durable incorporation, notice intent, transport, authorized resolution, and participant knowledge; state the selected recovery premises |
| Selective presentation adoption | A remote update can reach a client | Distinguish advisory interest, authorized acquisition, one-use user Refresh, physical adoption, and outstanding visibility debt |

Later stages expand these mechanisms. Their existence does not permit earlier
work to ship with placeholder checks, silent fallbacks, or unclassified proof
claims. Static preflight checks the declared handling paths for dynamic failures;
it does not predict that the network, Membership, or database will remain valid.
A dynamic permission change must still be enforced by the authoritative
operation or qualified read at the time of use. A failed after-commit
notification must not retroactively turn a committed transaction into
rejection; the selected publication profile must either retain its durable
intent or name the weaker recovery and availability assumptions.

For example, Alice's eligible Claim may incorporate at the trusted transaction
boundary while the HTTP result disappears. Her original command remains
unresolved to the client until qualified command-specific evidence permits
settlement; an arbitrary retry under a new command identity would be a new
intent. Bob's Live notification is merely an advisory about a remote change,
not automatic authority to replace his adopted board. These obligations
begin at the first Claim and first subscription, not at a later roadmap
stage devoted to recovery or multi-node deployment.

*** A stage result is a scoped evidence record

A stage record names its supported subset, source and artifact identities,
original obligations, selected profile, accepted premises, actual enforcing
boundaries, acceptance results, and unresolved requirements. It distinguishes
implemented machinery, exercised behavior, and a completed claimed scope.

A supplied map or a successful-looking report is not an admitted artifact. A
checker-issued local object is not durable authority. A test observation is not
an unbounded theorem. The evidence classes in Part I and result statuses in Part
XI apply without reinterpretation.

The record separates the original required capability set from the supported
subset, the chosen conditional or stricter profile from unmet mandatory gates,
and source-derived evidence from actual installed enforcement. It names
successful eligible witnesses as well as adversarial exclusions. A partial
stage can be useful and truthfully complete for a deliberately narrower
claim, but it does not make a missing product action, unknown physical writer,
unresolved premise, or unexecuted test disappear from the stronger requested
claim. Four Part XI release decisions and four independent completion
milestones remain different result subjects.

The next useful task is the earliest unmet obligation on the selected delivery
path whose prerequisites are available. A physical failure is repaired at the
owning boundary, then dependent evidence is reconsidered. Adding another report
layer without closing a required boundary is not progress toward that path.
Early exploration of a future proof, different provider, or multi-node router
is appropriate when it exposes a real missing contract. It must feed that
finding back to the original semantic or physical owner, not produce a
second architecture whose success is then counted as the missing original
application guarantee.

** Construction stages

*** Stage 1 -- Semantic ownership, identities, and claim contracts

Establish the vocabulary and construction interfaces shared by runtime code,
checkers, application assembly, and evidence reporting. This is the foundation
of the permanent executable semantic core, not a promise that all physical
behavior has already been formalized.

The source-owned semantic subject includes the actual actor, target, relationship,
operation and policy dependencies, not just a friendly function name. A real
HumanHelp Claim refers to public Request and RequestAssignment meaning, the
current principal and Membership/Organization relation, one-primary
responsibility, protected observation and atomic effect. Choreo describes
coordination and knowledge; views select affordances; checkers assess named
judgments. None of those consumers may create a second, subtly different
Claim rule or infer current model authority from its metadata.

Stage 1's semantic-first position does not waive the earlier R4 physical
substrate obligation. The actual Biff lifecycle/preflight, model FX
invocation, trusted writer and installed host path must be established at
the first *claimed runnable* scope, as stated in the delivery discipline;
their complete coverage is elaborated in the later host and operation
stages. The permanent executable semantic core is neither the small proof
kernel nor an invented second runtime for unsupported Clojure code.

Deliver:

- single ownership of domain rules, public operations, choreography, projection,
  runtime transitions, and application declarations;
- distinct semantic-subject, implementation, artifact, assembly-generation,
  command, execution, transport, authority, and resource-instance identities;
- versioned claim and judgment records with subject, proposition, scope,
  assumptions, required dependencies, and evidence mechanism;
- an immutable original obligation ledger with separately derived dispositions;
- contracts for opaque host-language functions and their proof-relevant input,
  output, authority, state footprint, effects, and failure behavior;
- the independent product-capability inventory and semantic-policy audit shape;
- stable structured diagnostics and a minimal source-derived inspection surface.
- an explicit source-to-consumer mapping for business rule, nominal value,
  reader/relationship, actor authority, guarded effect and observation-basis
  dependencies, including which are checked, opaque, asserted or still unknown;
- a source-independent product requirement inventory whose denominator cannot
  shrink to currently declared operations or currently generated routes;
- the distinction between semantic subject, source syntax, normalized
  interpretation, checker result, issuer handle, physical implementation,
  generated asset, deployed host and current execution authority.

The independent HumanHelp requirements retain Create, Claim, Unclaim,
other lifecycle operations, real Reassign, and the still-unselected
product-owned Response interaction. A proof of one Claim conjunct or a
closed but reduced application registry may satisfy a narrower named
profile; it may not be reported as the complete product or as coverage
of obligations never discovered by the generator.

Acceptance requires that same-shaped objects from different subjects cannot be
silently substituted, a premise remains attached to its dependent claim, and a
missing product capability remains visible even when the smaller declared graph
is internally closed. An unknown inventory is not an empty complete inventory.

Canonical interfaces must be small enough to compose, but must include every
meaning-changing dependency used by the consumer. A declaration's name or source
location is provenance, not a proof of its semantics or implementation.

For instance, a structurally well-formed description or digest can identify
a semantic *interface* without proving its meaning, its source-to-implementation
correspondence or a safe effect at the trusted physical boundary. A copied
certificate-shaped map, a same-shaped Request from another Organization,
an old issuer status and an unbound client actor label must fail to
substitute for a qualified current subject and evidence. The original
source and its true dependency footprint determine required checking;
a missing inventory is *unknown*, never an empty complete set.

A correctness-relevant policy may also be well typed and nevertheless be
the *wrong intended policy*. The public model's auditable semantic surface
retains explanation, intended actor/target binding and independent product
approval. Human or heuristic review may detect an error and propose repair,
but cannot manufacture a proof or authority. Ordinary Clojure and
ClojureScript functions remain available: unsupported or hidden reads,
effects, time dependence, partiality and provider behavior become named
opaque obligations or independently enforced exclusions, not silently
omitted duties.

*** Stage 2 -- Typed semantic rules and executable judgments

Implement the closed rule language and the versioned judgment contracts of
[[#req-certified-rule-language]] and Part IX. The rule interpreter and checker
operate on the same admitted meaning used by operations and their proofs.

Stage 2 makes four claims distinct: closed *syntax* with an exact reader
footprint, intrinsic *typing* under named reader types, *evaluation* over
one admitted immutable binding, and *use-site admissibility* with justified
knowledge and current authority. Passing one does not discharge the next.
The baseline certifiable expression language consists of bounded literals,
declared reads and presence tests, strict Boolean negation, ordered
short-circuit conjunction/disjunction/implication, typed equality and
ordering, and finite-set membership. Its exact arities, input decoding,
failure behavior and resource limits are part of the versioned meaning.
It does not include arbitrary function calls or EDN reader evaluation.

The full R4 target still includes typed relationship and field access,
nominal variant discrimination, exhaustive closed match/case,
deterministic derivations and independently specified extension
primitives. These are explicit future extensions with their own syntax,
type, evaluation, source mapping, effect and proof/premise contracts;
they are not secretly certified by the small baseline grammar.
Supported application Clojure may be elaborated to the closed term under
a checked source-translation contract, or represented by a named
opaque dependency. Merely copying an equivalent-looking term is not
evidence that it realizes the original public rule.

Deliver:

- closed AST forms, exact reader footprints, operator arity, and semantic types;
- the supported scalar, nominal-enum, optional, and nullable value contracts;
- strict Boolean interpretation and left-to-right short-circuit semantics;
- presence and null refinements scoped to the paths and subjects that justify them;
- conservative normalization that preserves evaluation and access order;
- explicit value codecs and target-runtime limits for portable evaluation;
- typed interfaces for opaque policy or relational extensions, with unproved
  properties retained as premises;
- executable typing, evaluation, and rule-use judgment definitions with source
  diagnostics and stable interpretation versions.
- exact separation of absent, present nil, present false and present zero:
  presence and non-nil are different justified refinements;
- reader/type identity bound to the source, observation subject and
  evaluation path, with incoming-path joins retaining only shared facts;
- source-to-AST elaboration and conservative interpretation-preserving
  normalization, with no silent short-circuit reordering or omitted
  source-meaning dependencies;
- distinct interpretation and proof obligations for JVM/CLJS numerical,
  codec, overflow, range and external-reader behavior, where selected.

For example, the following rule about one supplied optional, nullable
integer binding requires each guard to dominate its dependent read:

#+begin_src clojure
{:readers #{:case/score}
 :expression
 [:and
  [:present [:read :case/score]]
  [:not= [:read :case/score] [:literal nil]]
  [:>= [:read :case/score] [:literal 10]]]}

{:case/score {:type :integer :optional? true :nullable? true}}
#+end_src

This is illustrative rule and reader-type data, not a complete policy,
a production read or a certificate. Moving the final comparison before
the presence/non-nil guards is a type error, not ordinary predicate
false. Replacing a conjunction with a disjunction may express a *different*
well-typed business policy. The interpreter, type checker and any future
proof/translation must agree on the actual left-to-right evaluation paths.

Acceptance pairs well-typed successful evaluation with wrong-type, missing-reader,
absent/null, invalid enum, unsupported-operator, and malformed-shape cases.
A coherent but product-wrong policy remains representable. Typing does not prove
its truth, and evaluation to true does not establish current server authorization.

A rule that is intrinsically valid can still be unusable at a choreography point
because the role lacks its inputs, provenance, refinement, or authority. Stage 7
composes those distributed judgments; Stage 2 does not invent them from schema
acceptance. Arbitrary host functions remain available through their contracts.

Acceptance also distinguishes positive eligibility from reject-everything
success: valid typed expressions must evaluate over supported nonvacuous
bindings while wrong enum, absent/nil, undeclared read, unsupported
operator, malformed AST, overflow/codec mismatch and unsafe
refinement-order cases receive exact diagnostics. A timeout, resource
limit or unsupported construct is neither a Boolean false nor a
successful theorem. A rule may be typed but violate the product's
independently selected policy; a true evaluated rule may rely on
stale, fake or unauthorized bindings. These are separate failures.

Normalization may disregard specified irrelevant map/set ordering or
equivalent mathematical integer notation, but must preserve nominal
domains, reader IDs, optionality, nullability, operator and operand
order, failures, interpretation versions and binding identity.
A stable abstract rule fingerprint after a provider or installed-browser
change cannot reuse stale physical enforcement evidence. The eventual
proof kernel, source-elaboration checker, authority gate and physical
correspondence tests retain independent responsibilities and premises.

*** Stage 3 -- Small proof kernel and guarded proof mechanisms

Build a small, inspectable *proof-checking* foundation alongside the
permanent executable semantic core. These are different components:
the semantic core supplies runtime transition meaning; a propositional
kernel checks derivations of its own closed logic; dedicated transition,
initial-state and induction checkers establish their specified conditional
judgments. Proof-producing elaboration proposes derivations but cannot
create an inference rule or issue authority by calling a trusted-looking
function. The proof stage is a prerequisite for claims that need its
judgments, not a universal requirement that every useful application
operation await independent mathematical formalization.

*** Close the initial propositional checking boundary

Use the original, versioned proposition source with an exact subject,
nominal variable environment, declared premises, step graph and final
goal. The initial calculus has only seven inference-rule families:

- premise use;
- truth introduction;
- implication reflexivity;
- conjunction introduction;
- conjunction elimination;
- implication elimination;
- disjunction introduction.

The checker independently parses and typechecks every source proposition,
validates rule-specific arities and exact conclusions, and requires each
referenced step to precede its use. A derivation claiming a stronger goal,
using the wrong subject/nominal atom, inventing a step, hiding a required
premise or relying on an unsupported rule fails. Every required original
obligation remains visible independently of the supplied derivation.
The supported source format may additionally require every declared
premise/step to be used; that completeness discipline does not itself
prove that an original application rule or physical writer was inventoried.

There is no initial axiom asserting an arbitrary atomic predicate,
unrestricted excluded middle, arithmetic/SMT solving, hypothetical premise
discharge, arbitrary host Clojure evaluation or transactional authority.
A conditional derivation establishes a conclusion *assuming* its admitted
source premises; it does not establish that those premises hold in the
current Request, browser, database, or installed application. A checked
derivation and its report are not a signed authorization or issuer handle.

*** Derive guarded consequences without enlarging the logical kernel

Represent a selected typed guarded transition with pre-state and input,
current guards, simultaneous post-state assignments and an explicit frame
for untouched fields, including presence as well as value where relevant.
A dedicated proof mechanism may derive exactly supported guard,
assignment, frame, conjunction and equality-substitution consequences.
It checks original transition source and matching-relation assumptions.
It cannot generalize a one-document assignment to a multi-record
RequestAssignment invariant, silently infer hidden external writes, or
turn a postcondition into evidence that a particular XTDB effect ran.

For conditional induction, freeze one *original-source* operation catalog,
its initial condition and every required invariant. Each invariant needs
a justified initial condition and preservation argument for *every*
declared operation; a missing operation, malformed guard, changed frame,
omitted invariant, unsupported consequence or falsely discharged premise
keeps the stronger judgment open. Every claimed operation and initializer
also faces independent source/physical completeness challenges. A finite
set of tested initial constructors establishes coverage only of its
declared finite catalog, not that every physical initializer satisfies
the initial predicate. The selected model must retain eligible initial
states and meaningful enabled positive operations, rather than pass an
unreachable or reject-everything machine.

Do not confuse an induction obligation with an issued universal proof.
Successful checker-local reasoning may remain conditional on original-source
coverage, initial-state existence, operation-catalog completeness, abstract
transition semantics, checker soundness and source-to-installed-effect
correspondence. Scoped checking of the complete declared set does not
establish the completeness of all potentially bypassing physical writers.

*** Keep proof, issuance and formal transfer independently accountable

Elaboration and search can construct candidate proofs or finite witnesses,
but must submit their *source* to the relevant independent checker.
Malformed derivations, stale subjects, step/reference mistakes,
unsupported substitutions, skipped branches, result-map forgery and a
mutant elaborator must not obtain a stronger accepted claim. Exhaustion,
incompleteness, a timeout and an unproved premise are not success
statuses. Nearby eligible positive derivations and useful transitions
must still pass; a mechanism that rejects everything cannot earn
completion for a functional Claim path.

Certificate admission separately binds the checked source, dependency
closure, original obligation denominator, issuer scope, validity
conditions and unclosed assumptions. A copyable report, old certificate
description or fabricated fingerprint cannot mint a current capability.
Logical facts in a derivation may be reused under logical inference
rules; one-use physical effect rights and resource ownership are not
duplicated merely by duplicating a proposition.

Independent mathematical soundness of the kernel, the production checker
acceptance implication, typed-atom semantics and actual physical
application correspondence remain distinct later formal and release
claims. In particular, a sound theorem about a seven-rule abstract
calculus does not by itself prove the concrete JVM checker, issuer,
Biff/XTDB writer, generated browser plan or deployment. Keep every
unproved bridge as a named obligation and never promote finite model
checks, successful unit tests or source inspection into such a theorem.

Acceptance of this stage is the precise scoped checking of positive
and adverse *source-bound* proofs, guarded consequences and induction
candidates with their remaining premises honestly recorded. Complete
cross-namespace certification, independently established kernel
soundness and production effect qualification remain separate milestones.

*** Stage 4 -- Qualified host, lifecycle, and invocation context

Select and qualify the *actual* Biff, Ring/Aleph, runtime, XTDB,
compiler and browser/HTMX versions and interfaces used by the
application. “Final Biff 2” is not an API, compatibility contract or
reason to wait for an unspecified release. A selected host profile
names concrete dependency identity and configuration, effective
request/FX value flow, lifecycle semantics, handler adoption,
backend behavior and the implementation assumptions on which a
claim depends. These are implementation subjects, not new owners of
domain rules.

*** Install the real application boundary before exposing traffic

Deliver:

- explicit current invocation input and prior-output value flow for
  generated and handwritten Biff/Graph/FX construction; no accidental
  assumption that previous output is implicitly merged into context;
- stable native module identities, declared resource/dependency owners,
  correct phase ordering, acquisition, initialization, start and cleanup;
- private candidate construction, required preflight/assembly checks,
  current handler installation and a qualified admission boundary before
  the selected application behavior is externally reachable;
- an exact relation between the checked candidate, concrete module,
  installed Ring handler, server's actual adopted handler, active routes
  and served/loaded browser artifacts, with unqualified bypasses reported;
- actual protected principal, model, request and transaction context
  assembled at the trusted boundary, not supplied by client metadata;
- independent concurrent request scopes and explicit supported transfer
  of a qualified context to deferred responses, streams, workers and
  subscriptions, with generation/owner-bound retirement;
- selected backend/HTMX/compiler qualification, real valid/invalid
  conformance tests, and honest residual assumptions for other host paths.

A host may have multiple physical lifecycle phases. In a selected Biff
integration where all module initializers run *before* the ordered
start phase, putting preflight first in start order does not prevent an
earlier initializer from opening a socket, publishing a worker or
performing a protected write. Every such initializer must be separately
classified, safely private/fenced, or admitted before its relevant
effect. The final guarded application must not be exposed through an
unchecked listener under startup failure, missing provider or later
handler replacement. Safe resource cleanup follows revocation of
active effect rights; failed or partial cleanup does not restore them.

*** Preserve concurrency, asynchronous ownership and real observability

Application admission and a physically installed handler do not
automatically qualify every dynamic render, alternative Ring response,
migration, external writer, worker or browser entrypoint. An HTML
serialization gate covers the canonical responses actually sent
through it; a pre-serialized or substituted handler remains an open
bypass unless independently instrumented or excluded by a real
enforcing boundary. The actual server must be shown to use the
guarded handler and asset set before physical correspondence is
credited; a staging report or matching handler key is not such proof.

Each request, command, execution, stream, delayed callback and browser
resource has its own relevant scope and retirement rules. A single
process-wide, one-use writer lease, thread-local dynamic binding or
global request context is not a sufficient model for concurrent
requests and retained asynchronous effects. A context transferred
to a worker needs a declared owner, authority basis, permitted effects,
lifetime, cancellation and post-retirement behavior. Current protected
reads and writes still require trusted checks at their use points;
a formerly admitted request context is not everlasting Membership.

Acceptance challenges startup from a genuine valid candidate as well
as missing/misordered modules, an initializer effect before start,
host handler substitution, failed preflight after resource acquisition,
duplicate module identity, concurrent request cross-talk, stale
deferred writes, unsupported context transfer, and asset/route mismatch.
The check observes the first real physical effect/serving boundary,
not only a helper report claiming the boundary would have blocked it.
Eligible normal requests and authorized deferred completions must still
work under the selected profile, with observed cleanup and bounded
resource behavior.

This stage supplies scoped lifecycle, invocation and enforcement
interfaces. It does not assert Stage 10's complete whole-application
closure, Stage 11's production release admission, or independent
formal/physical correspondence. A health or private probe may use a
separately declared and actually enforced narrower scope; it cannot
quietly expose ordinary unchecked application routes.
*** Stage 5 -- Public authoritative operations and command resolution

Construct public model operations with explicit preparation, guarded incorporation,
and after-commit work. Choreography and views consume their public contracts
rather than private model internals. HumanHelp's public Request, Membership,
Organization, and RequestAssignment contracts own the relevant business truth;
application assembly and the executor cannot define a second Claim policy.

The *source-owned transition* is the original subject. For Claim it includes
authenticated actor/target binding, current helper Membership and protected
Organization association, eligible Request lifecycle, absence or uniqueness of
the primary RequestAssignment, every guarded write and its frame, and the
disclosure contract for the returned or later recovered result. A server
pre-read may prepare a proposal, but is not itself a current commit-time
authorization or a certificate that the write protected all dependencies.

*** Bind one logical command without confusing it with an attempt

The public operation is declared before any particular command exists. A
logical command receives its identity and immutable binding before the
first possible transmission; a request, retry, execution, host, transaction,
transport attempt and browser resource each have other identities. The
trusted ingress must establish the authenticated principal, selected
operation and target, canonical argument semantics and allowed authority
scope. A client-supplied command ID is a correlation value, never proof
of permission, incorporation, current Membership or result disclosure.

The complete binding is retained with the command's authorized historical
disposition. A compatible retry or resolution consults that history *before*
testing new-incorporation business guards: a successfully incorporated Claim
can legitimately leave its Request no longer open. It must be possible
to report that original success without executing Claim again or falsely
rejecting the historical command. Reusing the same ID for changed arguments,
principal, operation or scope is a typed incompatibility, not a new intent.

A newly incorporable command must atomically protect its current business
conditions, complete multi-record effects and required durable command
outcome. Where the selected reliability profile requires durable notice
intent, its record belongs in the same suitable atomic authoritative
boundary; asynchronous SSE publication is a subsequent delivery step.
Separate after-commit attempts must not make an already incorporated
domain transition appear rejected. A command record is not a permission
to disclose private history to an unauthorized resolver.

Deliver:

- typed inputs, current authority requirements, guarded dependencies, write and
  frame contracts, result/disclosure contracts, and durable-work obligations;
- stable =:gesso/command-id= binding before first possible send, covering operation,
  interface, canonical arguments, principal, and authority scope;
- compatible existing-command lookup before applying a new-command business guard;
- atomic command exclusion, authoritative mutation, result recording, and required
  publication intent;
- model outcomes =:committed=, =:rejected=, =:already-incorporated=, and
  =:commit-unknown=, with explicit presentation mappings;
- protected command reconciliation, retry, retention, and expiry behavior;
- public composition of cross-model constraints without pretending that separate
  transactions form one atomic operation;
- a source-complete ledger of permission, relationship, existence, uniqueness,
  guarded change, command-result, disclosure and publication requirements,
  including independently required actions not yet implemented;
- explicit separation of attempt-local transport outcomes, authoritative
  command incorporation/exclusion, historical recovery, and actor-visible
  presentation or Live advisory progression;
- canonical outcomes with qualified origin and scope, preserving unknown
  incorporation after a possible send rather than inferring failure from
  connection loss, read timeout, absent command record or abort of one attempt;
- the independent server read and authorization required to disclose a retained
  command result, including retained history, expiry and compatible old-client
  recovery under a changed host generation.

A command is not safely retryable merely because a new physical attempt is
possible. Retained identical command binding and appropriate authoritative
resolve-or-incorporate exclusion are needed to prevent duplicate effects;
on indeterminate evidence the contract must say who retries, rereads,
reconciles or waits, and under which availability and retention premises.
A failed individual attempt does not exclude a concurrent other attempt.
Nor does current Request/assignment state by itself attribute success
to one particular earlier command.

*** Admit the complete source effect, not a convenient document fragment

Claim's domain mutation, primary RequestAssignment creation or reassignment,
canonical command-result creation and required publication intent are one
declared authoritative effect where that strong profile is selected.
A sequence of individually successful writes is not equivalent to an atomic
multi-record transition. Other source-owned operations, including Unclaim,
Reassign and terminal transitions, need their own eligible and adversarial
execution paths; a successful Claim neither implies their correctness nor
shrinks the independent HumanHelp capability denominator.

Outcomes =:committed=, =:rejected=, =:already-incorporated= and
=:commit-unknown= remain model/command-level claims with qualified evidence.
The browser's provisional/accepted/rejected/unknown presentation does not
constitute a database transaction result. A known committed outcome may
still have undelivered Live advice or an unadopted remote presentation;
a successful SSE send does not grant remote collection Refresh. A
postcommit publication failure never retrospectively invalidates the
authoritative result. Preflight may reject structurally unsupported
operation/effect shapes early, while changing current domain predicates
must be rechecked at their trusted incorporation boundary.

Acceptance pairs a genuine successful Claim with typed guard rejection,
compatible historical replay, incompatible command reuse, changed Membership
or association, simultaneous competing Claim, stale server pre-read, lost
response after possible submission, and recovered command truth after a
later lifecycle mutation. It also challenges a forged principal, missing
RequestAssignment write, omitted command record or outbox requirement,
unknown outcome incorrectly marked rejected, and a retry under a new
identity. The first boundary with sufficient legitimate evidence must
reject or retain the exact uncertainty; no reject-everything candidate can
count as a completed usable operation.

The Claim scope guards Request state, helper Membership, Organization policy,
association and primary-assignment conditions together with its writes. A
pre-read or a self-asserted eligible flag cannot establish those current facts
at incorporation. Replaying C42 after an Unclaim or other later event requires
authorized *command-specific* historical evidence, not merely a currently
claimed Request. Stage 6 separately qualifies the actual backend, guard
semantics, transaction-internal prestate and all physical writing paths.

*** Stage 6 -- Physical transaction mediation and provider qualification

Bind the authoritative plan to the actual physical submission boundary.
The supported implementation may use a narrow mechanically checked lowering
or an explicit opaque adapter whose remaining assumptions cannot disappear.
For a selected strong claim, the admitted source, complete guarded plan,
lowered immutable transaction vector, issued executor, exact one-shot physical
submission, authenticated authority context and observation provenance must
refer to the *same* execution subject. The selected provider/backend profile,
transaction options, encoding and trusted host route are distinct identities.

*** Protect prestate, write footprint and the exact frame

The canonical abstract transition evaluates its guards against a declared
pre-write state and applies its supported assignments atomically. A concrete
XTDB implementation must show that its ASSERT predicates and transaction
operations faithfully implement that transition under the selected API
semantics. For a supported ASSERT-before-write lowering, checking ordering
and transaction-vector shape is a useful prerequisite, not proof that the
provider's *transaction-internal* prestate equals a separately pinned
external read. A snapshot token, ledger row, transaction key or later matching
card cannot authenticate an unseen internal guard evaluation.

Guard and write footprints are different. A guard may depend on Request
status, helper Membership, Organization policy, a relationship's absence or
uniqueness, and command history while the admitted writes touch a different
set of documents. An opaque predicate or external writer can invalidate
the proof unless the selected mechanism establishes its coverage or retains
a named premise. Every mutation, effective transaction option, hook, and
update/replace semantics must be accounted for.

Whole-document replacement can erase a concurrently added field even
when all previously visible values compare equal. A sound frame contract
must protect **presence and value**, including newly introduced and
deleted fields, using an admitted complete field-count/footprint guard,
monotonic history-sensitive revision, suitable partial update operation
or other independently qualified mechanism. Full-value comparison alone
does not eliminate ABA (A→B→A); if forbidden intervening history matters,
the chosen identity/revision/transaction-history discipline must actually
exclude it, including bypassing writers.

Absence, uniqueness, cardinality and one-primary RequestAssignment are
predicate/relationship obligations, not merely a cached false value.
Their physical realization must survive two concurrent attempts and every
admitted writer. No pre-read test or synthetic concurrency schedule is
a substitute for a real protected physical contention case.

Deliver:

- immutable admitted plans and complete physical transaction derivation/checking;
- one submission owner that cannot accept appended raw writes or a substituted
  backend client/callback through its normal interface;
- guard footprints separate from write footprints, including absent/unique
  relationship predicates and all effective transaction options or hooks;
- frame preservation for whole-document replacement, with complete comparison,
  a justified revision discipline, or a qualified alternative update mechanism;
- local attempt and provider-return observation correlated to the issued invocation;
- provider-qualified outcome, read-basis, progression, and atomicity interpretation;
- a real writer inventory and mediation contract covering routes, jobs, imports,
  maintenance, migrations, and external write credentials where the claim requires it;
- explicit backend-assumption qualification and invalidation from Part X;
- one source-to-physical and target-bound submission relation: the caller
  cannot append raw SQL, alter the protected table/target, change transaction
  options or swap the backend callback after the admitted plan is issued;
- transaction-internal prestate and actual guard/action correspondence, or a
  precise conditional premise and reproducible real-provider tests where
  the provider exposes no independently authenticated internal witness;
- complete protected physical frame and presence/write-footprint evidence,
  including caller-supplied actual values, absent relationships, monotonic
  revision policies and history-sensitive conflict assumptions;
- independently qualified process/request/execution/host context, preserving
  parallelism while limiting individual submit capabilities to the intended
  one-shot attempt and retiring stale physical effects;
- separate submitted-operation provenance, provider return, ledger/commit
  status, authoritative command record, read basis, scoped progression,
  actual actor readback and browser adoption, without treating agreement
  between two observations as causal proof;
- independent source/assembly and host-observed writer inventories plus
  mediation or explicitly admitted external writer assumptions for
  migrations, background tasks, maintenance clients, extra processes
  and directly credentialed XTDB connections.

*** Challenge real submission, concurrent writers and evidence limits

Acceptance uses actual backend concurrency and failure windows. It requires
at least one eligible physical success and controlled negatives for stale
Request status, revoked/changed Membership, changed association, competing
primary insertion, duplicate command, additional field erasure, ABA,
loss of command record, unauthorized writer, provider exception after
possible submission, insufficient read progression, and changed adapter
or configuration. The actual transaction's lowered operations and protected
targets must agree with the original plan. Supported values distinguish
absence, null, false, collections, and physical encodings under selected
runtime codecs.

Physical evidence has several independently limited layers. A plan-shaped
checker result proves construction of a *form*, not that it ran. A
process-local one-shot callback or captured return proves only its
correspondingly scoped observation; it is not a cryptographic, durable
command record. A pinned poststate and ledger observation may be
consistent with the returned key without proving which physical writer
caused the observed domain state. A genuinely authenticated protected
physical writer, complete internal-guard coverage and actual submission
can establish stronger bounded claims; a universal refinement theorem
still requires the stated semantics, source completeness and
independent proof/correspondence premises.

The selected strong application profile must survey *all relevant writers*
rather than only HTTP routes or Gesso-issued operations. Independent
host/process/credential coverage is needed before treating a source
registry as a physically closed world. Where the environment cannot
enumerate or constrain an external writer, the stronger no-bypass
claim remains unestablished even when the registered local callbacks
all agree. Deployment changes invalidate the appropriate old physical
evidence while possibly preserving an unrelated sound abstract theorem.

A pinned external pre-read is not a transaction-internal state witness; later
matching post-state is not proof of causality; local return observation is not
a universal refinement theorem. Complete field comparison without history
does not exclude ABA. The required external behavior, physical prestate
relationship, and closed-writer premise remain named and testable.

The stage reports exactly which physical forms, provider versions, writer
paths and authority scopes are supported. One-document coverage cannot
satisfy HumanHelp's multi-record Claim contract. A host-supplied writer
enumerator cannot prove that undisclosed direct XTDB writers are impossible,
and a registered one-shot callback need not be the one a deployed route uses.
The release and cross-layer checker may claim only the smaller supported
subject until actual installed submission, open writer effects,
unknown-command recovery, retained publication and protected readback
are covered by qualified evidence and nonvacuous testing.

*** Stage 7 -- Portable choreography, distributed admissibility, and projection

Construct the global and local semantics around public operation contracts.
Admitted projections preserve the declared global/local relation for the supported
subset and generate the canonical executable plan.

Deliver:

- explicit roles, actors, principals, hosts, authorities, and placement;
- closed message, state, and operation boundaries with runtime value validation;
- knowledge from declared inputs, communication, authoritative observations,
  deterministic derivation, and explicit premises;
- provenance, authority, path-refinement, and scoped-agreement judgments at use;
- behavior-sensitive branch discrimination, terminal states, and required failure
  or recovery successors;
- projection and lowering subject bindings, format versions, and correspondence;
- JVM/Node/Chromium conformance for the actual supported portable value subset.

Acceptance rejects branches without justified discriminators, invented payload
knowledge, premature output use, authority escalation, and unsupported constructs
presented as checked. A named opaque operation remains usable through its admitted
interface; projection does not pretend to translate arbitrary JVM code into a
browser.

For the same admitted plan, initial semantic state, and event stream, the portable
semantics agree within their declared representation. This does not promise
identical external schedules or prove physical browser effects. Certificates can
strengthen these judgments through Stage 13 without introducing a parallel runtime.

*** Stage 8 -- Browser semantics and physical effect enforcement

Use a pure transition core over adapter state and normalized events, with explicit
abstract effects and a narrow physical shell. Qualify the actual HTMX lifecycle
and browser behavior used by that shell. No invented or merely convenient hook
can stand in for the real request, swap, settle, or deferred mutation boundary.

Deliver:

- owner-relative admission for execution-private and shared resource events;
- fresh resource instances, effect identities/phases, retirement, and cleanup;
- bounded active/queued acquisition slots plus separate metadata and physical
  remnant limits;
- typed provisional projections, rejection, settlement, supersession, and unknown
  outcome handling;
- actual effect permission checks immediately before physical mutation;
- completion checks before recording authoritative adoption and debt discharge;
- authoritative presence/absence and partial-installation repair;
- continuity independent of domain truth, including local options and scroll;
- stale-plan compatibility and recovery without retaining revoked effect rights.

Acceptance exercises deferred mutation after resource replacement, duplicate
completion, failed abort, late rollback, stale plan, partial installation, and
continuity failure in real Chromium as well as the portable model. A callback
admitted earlier cannot carry a cached Boolean permission into a later resource.

A Create projection need not invent an authoritative basis for a nonexistent
entity. Its intent and enclosing known facts follow the operation contract.
Current-state supersession may repair presentation while command attribution
remains unknown. Retiring the browser execution cannot silently erase that
separate command obligation.

*** Stage 9 -- Live publication, observation coverage, and selective adoption

Close commit-to-publication-to-acquisition behavior without confusing an advisory
with domain content or permission. Use actual provider progression and projection
coverage rather than a universal integer revision.

Deliver:

- durable publication intent where promised, with dispatcher ownership, retry,
  acknowledgment scope, retention, and duplicate behavior;
- authorized advisory payloads and interest scope;
- initial observation/subscription fences, replay or gap evidence, and reconnect;
- explicit acquisition grants and policy-controlled adoption;
- scoped composition and discharge of outstanding progression requirements;
- coherent acquisition of all records contributing to a declared projection;
- authoritative absence and recovery when an advisory is lost completely;
- bounded debt representation, backpressure, and honest continuity-unknown state.

Acceptance includes crash after commit before dispatch, duplicate and reordered
notice, silent initial-registration or reconnect gaps, insufficient or incomparable
observations, and a successful explicit Refresh when no advisory was received.
A successful HTTP read cannot echo a requested token as proof of sufficient basis.

For HumanHelp, remote creation and remote lifecycle updates remain advisory until
explicit Refresh. One Refresh grant permits one acquisition; a later advisory
cannot silently create a successor read. A qualified newer observation may discharge
additional covered debt without granting another acquisition. Own-command and
local recovery exceptions remain scoped under Part VIII.

*** Stage 10 -- Whole-application construction and actual installed closure

Make the normal application path consume one source-owned construction through
build, preflight, installation, rendering, invocation, and inspection. Structural
closure, installed enforcement, and required product capabilities are separate
checks with separate evidence.

Deliver:

- the operation/view/plan/artifact/transport/route/model/outcome/acquisition graph;
- required and supplied provider contracts, routing uniqueness, and full declared
  handling/recovery coverage for supported dynamic conditions;
- generated browser bootstrap, canonical manifest, qualified compiler receipt,
  and verification of the actual served bytes;
- issued handler/executor bindings and enforcement at the actual serving boundary;
- supported rendered HTML/HTMX contracts and validation through deferred output
  where applicable;
- current invocation and gateway bindings plus declared non-route writer paths;
- an independently supplied required-capability inventory;
- generated policy, authority, lifecycle, dependency, and assurance inspection.

Acceptance removes or substitutes each required edge and verifies rejection at
its earliest appropriate real boundary. An unknown route, missing plan, stale
asset, wrong target, missing required invocation context, or omitted provider
cannot fall back silently. Ordinary non-Choreo HTMX remains supported under its
own contract.

An inspected system-map slot is not evidence that the live server captured that
handler. The supported installation must establish its actual handoff. Neither
an opt-in checker left uncalled nor an unknown writer inventory can satisfy a
production-enforcement claim.

Known structural contradictions block construction. Facts knowable only at render,
invocation, transaction, or mutation time are checked there. A later output failure
does not undo an earlier valid commit. Semantic policy beyond the inspected subset
remains an explicit implementation premise, not an empty “no escapes” result.

*** Stage 11 -- Release integrity, reuse, and bounded compatibility

Implement the release decisions in [[#req-release-evidence]] and
[[#req-bounded-release-compatibility]] for the admitted application scope. This
stage integrates and expands mechanisms already required by the first served
candidate; it does not introduce basic artifact or lifecycle safety for the
first time.

Deliver:

- immutable candidate binding and distinct admission, installation, activation,
  and completion decisions;
- source-derived required gates and the closed result-status vocabulary of Part XI;
- dependency-driven reuse separating semantic theorems from physical evidence;
- safe cache decoding and re-admission, with genuine local issuance where required;
- coherent compare-and-activate behavior and cleanup of failed private installations;
- directional old/new client-server compatibility and actual routing exclusions;
- retained assets, supported decoders, command reconciliation, and explicit expiry;
- state/migration-aware rollback eligibility;
- machine-readable and readable root reports preserving accepted premises and
  mandatory unmet obligations separately.

Acceptance includes missing/skipped/stale/incomplete evidence, a disabled required
policy, substituted served bytes, post-check handler replacement, concurrent
activation, revoked backend qualification, and unresolved command recovery after
plan retirement. Positive valid releases and reusable unchanged results must work.

A failed replacement can leave an old assembly serving only while its premises
remain valid. Activation, retirement, or code rollback never reverses durable
business commits. A command lookup may outlive execution compatibility without
keeping the old mutation implementation executable.

*** Stage 12 -- Complete HumanHelp proving application

Finish the independent Part VIII capability set using public production models
and the canonical construction. The initial Claim path provides feedback during
Stages 5–11; full application completion requires the rest of the product too.

Deliver:

- Create, details, the selected response interaction, and all six lifecycle
  capabilities with eligible successful browser scenarios;
- real Reassign target-helper selection and manager authorization;
- immediate scoped creator visibility, including creation outside a current filter;
- local search, sorting, mine/unclaimed options, and terminal visibility over the
  adopted projection without hidden collection rereads;
- coherent Request, primary assignment, and permitted User projections;
- explicit Refresh for remote creation and lifecycle changes, with retained debt
  and no unauthorized adoption through local-result exceptions;
- continuity, known authorization-context loss handling, and protected reads;
- unknown-command reconciliation, publication-loss, reconnect-gap, stale-plan,
  insufficient-observation, and failed-installation recovery;
- all fourteen Part VIII completion gates on the actual installed application.

Acceptance uses real rendered controls, protocol generation, assets, routes,
authenticated sessions, and backend truth. Tests cannot fabricate missing hidden
command fields in place of the control being tested. Disabled controls, an HTTP
200, and a provisional DOM change are not substitutes for an eligible positive
capability and authoritative result.

Remote lifecycle adoption is already selected as explicit Refresh. The response
interaction at [[#decision-humanhelp-response-flow]] remains a specific product
contract that must be selected and tested; the framework must not invent it to
close a gate. An unfinished response flow blocks the full operational claim but
need not block a scoped Claim proof or a useful integration checkpoint.

*** Stage 13 -- Source-derived certificate composition and the real Claim pilot

Join the proof mechanisms, operation contracts, projections, issued plans, and
application realization through Part IX's actual admission path. A hierarchy of
namespaces or report formats is not the required composition mechanism.

Deliver:

- normalized subject interfaces for the supported schema, domain, relationship,
  rule, operation, choreography, projection, plan, and application claims;
- required obligation/dependency closure derived from original source;
- exact integration of that closure into the certificate issuer and selected
  construction policy;
- proposition- and scope-preserving substitution, premise propagation, and any
  supported assumption discharge;
- immutable in-process issuance and explicit durable package re-admission;
- whole-catalog conditional induction where requested, with complete invariant
  and operation coverage rather than a caller-selected successful subset;
- exact issued operation/plan/handler bindings and separately classified physical
  realization evidence;
- the three Claim-pilot conclusions in [[#req-humanhelp-certification-pilot]]:
  semantic checking, production binding, and real browser behavior.

Acceptance rejects a copied report, omitted source dependency, false discharge,
wrong-subject derivation, stale provider/implementation binding, or substituted
executor even when an outer report still says success. Changing an upstream
policy reconsiders every dependent claim and preserves unrelated evidence only
when its applicability is established.

For Claim, the proof subject includes the actual relevant relationships and
command branches. A successful replay must not be rejected merely because the
Request is now claimed. The guard and frame arguments must cover the claimed
multi-record operation or retain precisely scoped implementation premises under
a profile that permits them.

A generic acyclic graph is not source-derived required closure. A supplied writer
snapshot is not all-physical-writer coverage. Abstract induction, gateway observation,
backend outcome, and installed-server adoption remain distinct evidence even when
joined in one report. The release must not hide mandatory unsupported judgments
by turning them into assertions.

*** Stage 14 -- Systematic mutation and generic boundary coverage

Expand the positive/negative cases already delivered with each boundary into a
systematic corpus. Each mutant has a predeclared expected first boundary, result,
and relevant prohibited effect. A failure somewhere downstream is insufficient.

Deliver coverage across schemas, nominal types, rule evaluation, knowledge,
provenance, authority, command binding, projection, resource ownership, transaction
footprints, dependencies, cache re-admission, rendered surfaces, actual host
installation, and release compatibility. Include one-step generated mutations
where their meaning is clear, plus hand-authored concurrency and recovery cases.

Use small non-HumanHelp reference domains to challenge accidental coupling. An
approval operation can exercise policy change and disclosure; a checkout-like
reservation can exercise command identity and uncertainty; an ephemeral typing
signal can exercise admitted receipt and expiry without inventing a durable
business fact. These are small contract-driven examples, not a requirement to
build three additional production products or a participant-routing fabric.

Acceptance pairs rejected malformed constructions with usable valid controls and
accepted coherent policy variations. Count required rule, branch, operation,
and outcome exercise separately. A visited model state does not show that every
predicate branch or physical path was exercised. Missing, unavailable, or
incomplete test results do not improve rejection percentages.

Generic browser cases use actual normalized HTMX/browser events. Backend cases
use actual qualified lowering. Concurrent cases preserve isolated invocation
contexts and complete result accounting. Expected injected failures are asserted
precisely; unrelated console, page, transport, or process failures remain failures.

This stage's runtime cases are part of operational acceptance as soon as their
boundary exists. Proof-specific campaigns can expand independently and do not
make full certification a prerequisite for ordinary application use.

*** Stage 15 -- Explainability, counterexamples, and source-level repair

Complete the read-only explanation surface built from Stage 1 onward. The source
of the explanation is the admitted semantic graph and evidence ledger, not a
second handwritten policy inventory.

Deliver:

- operation cards, policy/authority/disclosure views, transition and dependency
  views, opaque-premise reports, and assurance coverage;
- explanations of malformed constructions, missing knowledge, stale subjects,
  insufficient progression, unknown command outcome, and revoked effect rights;
- source-linked formal/model counterexample interpretation with exact bounds,
  representation relation, and trace origin;
- reverse traceability from formal premises to production obligations;
- repair suggestions scoped to the actual failure owner and evidence;
- explicit inspection limits and protected-data redaction;
- optional human or model-assisted intent review outside the trusted checker path.

Acceptance distinguishes a semantic counterexample, a production-correspondence
failure, an unavailable checker, and a well-formed but suspicious product policy.
A modeled trace does not establish that arbitrary production code took that trace.
A generated-backend claim must exercise a real generated trace; an early fixture
is labeled as a fixture and can validate the explanation interface separately.

A repair changes the owning source, implementation, lowering, or explicitly
reviewed requirement, then regenerates and rechecks the affected evidence.
Weakening an invariant or adding a premise changes the claim; it is not a hidden
implementation repair. Editing generated formal output alone cannot repair the
application. Heuristic review cannot issue proofs or modify execution by itself.

*** Stage 16 -- Independent formal soundness of the stable kernel

Formalize the concrete first target from Part X: the small closed propositional
rules, their semantics, and the formal acceptance relation. Then establish the
typed-proposition bridge for the application-rule subset whose meaning is transferred.

Deliver exact theorem statements, supported domains, axioms, proof/checker
versions, reproducible checks, and subject encodings. Keep separate the soundness
of mathematical inference rules, correctness of a formal checker, and the
correspondence of the production Clojure checker. They are different results.

Acceptance requires the quantified result appropriate to the declared scope.
Checking one finite derivation, enumerating one truth table, or covering every
rule tag does not prove the checker sound for all derivations. Resource limits,
malformed inputs, decoding, and interpretation boundaries remain explicit where
they affect the production acceptance claim.

A proof assistant can implement the external role through the contract in Part X.
Application authors continue to write Gesso semantics and host-language code;
they do not maintain a second HumanHelp policy in proof-assistant syntax.

Further formal scopes are added to close named gaps in typed evaluation, guarded
consequences, induction, knowledge, projection, progression, or browser refinement.
The operational application is not suspended until all those theorems exist.
A larger scope requires its own evidence rather than inheriting the first result.

*** Stage 17 -- Formal-to-production transfer and release-bound evidence

Connect the external results to the actual checker and runtime subjects that
consume them. The correspondence direction, observable behavior, representation,
and remaining trust must be stated for each claim.

Deliver:

- production-admission-to-formal-validity correspondence for the declared checker
  scope, with actual implementation and decoding/normalization identities;
- execution refinement where claimed, separately from admission soundness;
- progress/fairness/divergence conditions for any transferred liveness result;
- complete formal-assumption-to-production-obligation traceability;
- checked or explicitly trusted translation/extraction mechanisms under the
  selected profile;
- finite bounds or sound abstraction transfer, with incomplete results preserved;
- source-level counterexample explanation exercised through the actual backend
  where the release claims that capability;
- release import, cache applicability, invalidation, and installed-subject binding
  for the resulting evidence.

Acceptance substitutes an outdated theorem, different production checker, altered
subject, omitted obligation, or incompatible build and verifies the appropriate
rejection. A trusted translation premise remains visible; it cannot satisfy a
profile requiring that translation to be proved. Tests and conformance vectors
alone cannot discharge a required universal transfer theorem.

An atomic action in a model creates an atomic production obligation. Proof of the
model cannot establish that unguarded pre-reads and ordinary writes implement it.
A provider contract may legitimately remain qualified and trusted without claiming
a proof of all XTDB. A violated premise invalidates dependent applicability even
if the abstract theorem remains true as a conditional statement.

This stage strengthens the release machinery from Stage 11. It does not make
artifact freshness, installed enforcement, or real-browser acceptance optional
before external formal work is complete.

*** Stage 18 -- Qualified multi-node realization

Realize the existing authority and command semantics across actual independent
application processes. The baseline topology and acceptance scope are those of
[[#req-multi-node-realization]] and [[#milestone-multi-node-production]].

Deliver:

- at least two application processes, actual routing/failover, and a qualified
  shared authoritative backend;
- durable publication intent and a dispatcher with explicit distribution-boundary
  acknowledgment, retry, retention, and duplicate semantics;
- authorized distributed interest delivery with registration/reconnect fence,
  replay, or conservative gap handling;
- cross-host command lookup and compatible retry under the original binding;
- progression-safe coherent reads through another host;
- qualified session, principal, scope, assembly, asset, and protocol compatibility;
- measured resource/load bounds and declared recovery behavior;
- actual host-loss, publication-loss, silent-gap, reorder, retention-expiry, and
  rolling-release scenarios in the root evidence.

Acceptance preserves authority, command identity, selective adoption, and honest
uncertainty through host replacement. A later matching Request state does not
attribute the originating command. Outbox publication does not prove receipt by
every subscriber; live interest filtering does not itself close a registration gap.

HumanHelp's remote board still waits for permitted Refresh. A lost advisory does
not eliminate the user's independent authorized acquisition path. Current
Membership loss may require nondisclosure rather than eventual result lookup.
Progress claims name availability, fairness, retention, permission, and user action.

A small real topology can provide exploratory feedback before external proof or
full HumanHelp completion. It is then a prototype under an explicit narrower
scope. Production completion requires the actual fault and resource envelope.
Direct participant routing and persisted suspended workflows remain separate
capabilities, not prerequisites for ordinary authoritative rendezvous.

*** Useful integrated checkpoints

The shortest useful operational path combines the relevant portions of Stages 1,
2, 4–11 and the first Claim case from Stage 12. Stage 3 and formal work can run
alongside it when their semantic subjects are ready. The checkpoints are:

| Checkpoint | Concrete result | Required limitation |
|------------+-----------------+---------------------|
| Semantic operation | One public Claim contract with commands, dependencies, outcomes, and explicit premises | No assertion that a physical transaction already implements it |

one successful response. Adding more proof infrastructure while that path is
miswired does not repair its missing provider, stale artifact, or physical effect
boundary. Conversely, a working button does not discharge a required invariant
or omitted source dependency.

| [[#milestone-multi-node-production][Production multi-node]] | Stage 18 with applicable operational and release contracts | Two host labels, one successful balanced request, or untested recovery |

No row authorizes dropping a mandatory profile requirement. A release asking for
stronger assurance remains blocked when that requirement is unsupported or its
evidence is missing. A deliberately narrower release changes its declared scope
and retains the original full requirement set as unmet.

** Worked Claim path: one meaning through the stages

This example is an acceptance and evidence trace, not an invented API. Each row
identifies a concrete owner and the fact that its output can justify. It follows
self-claim; assigning another helper requires that operation's separate actor and
target-Membership conditions.

*** Static definition, invocation, and commit are separate

The static operation declaration identifies HumanHelp's public Claim semantics,
argument schema, guard dependencies, command contract, results, and recovery.
It does not contain a particular principal, command, or execution instance.

| Boundary | Actual work | Evidence produced or required |
|----------+-------------+-------------------------------|
| View construction | Derive an eligible Claim affordance from the model-owned contract and permitted projection | Bound operation/plan and displayed availability; no future authorization |
| Browser command boundary | Bind the stable command before first send and record its original intent | Correlation and recoverable command binding; no principal authority |
| Trusted invocation | Resolve the actual route/operation and bind authenticated principal and canonical arguments | Admitted invocation with current context and explicit execution/attempt identity |
| Existing-command branch | Check full binding and current disclosure before returning a compatible recorded result | Permitted historical command outcome without new incorporation |
| New-command branch | Guard current Request, Membership, Organization, associations, primary assignment, and command exclusion | Qualified atomic decision, not a pre-read eligibility flag |
| Owned submission | Lower/check the complete immutable transaction and use the actual provider boundary | Actual scoped submission/return observations and qualified outcome evidence |
| Durable incorporation | Commit Request/assignment change, command result, and required outbox intent together | Authoritative incorporation under the qualified backend premise |
| Result presentation | Apply the explicit model-to-presentation mapping under current effect permission | Permitted local settlement or retained unknown state |
| Remote notice | Dispatch authorized advisory under its delivery contract | Scoped debt or gap information; no board acquisition grant |
| Permitted acquisition | Read coherent authorized projection at sufficient actual provider basis | Candidate observation, separate from physical installation and command attribution |
| Browser completion | Admit and finish the current resource's installation batch | Adoption and discharge only for the justified covered scope |

The Request is a domain entity, not the transport request. The command uses
=:gesso/command-id=. Each HTTP delivery may use =:http-request-id=. Execution and
resource identities control their own lifetime and effects. Assembly generation
binds the admitted realization. Provider basis describes the actual authoritative
observation. None of these coordinates can silently replace another.

The logical proof subject may project RequestAssignment relationships into a
smaller representation. Its representation relation still accounts for the real
primary assignment, associations, and physical write footprint. Writing a helper
field into a toy Request map does not implement this relation.

*** Failure schedule: incorporation and knowledge diverge

Assume Alice has submitted a properly bound Claim and the active profile promises
durable publication intent. The following controlled schedule must be exercised:

1. The authoritative guard succeeds and the complete Claim transaction incorporates.
2. The response is lost before Alice receives sufficient outcome evidence.
3. The serving process stops before dispatching the outbox intent.
4. Alice's originating browser resource is retired during recovery or deployment.
5. A permitted recovery on another invocation uses the same command binding.
6. The surviving dispatcher retries the retained intent; delivery may duplicate.
7. Bob receives an authorized advisory but does not yet press Refresh.
8. Bob later grants Refresh, obtains an authorized observation at sufficient
   progression, and safely installs it.

The authoritative operation is committed after step 1. Alice may remain unknown
after steps 2–4. Retirement does not change the commit or authorize a new command
identifier. Step 5 may return a permitted recorded success after binding and
current disclosure checks; it must not rerun the new-command open-state guard and
reject solely because the first Claim succeeded.

If step 5 can only obtain a current card, presentation can be repaired while
command attribution stays unknown. Lost disclosure permission or expired evidence
retention can leave that attribution unresolved. The record must retain that
limit instead of claiming eventual command knowledge unconditionally.

Step 6 does not duplicate Claim. Step 7 records remote debt without adopting the
changed card. Step 8 adopts only what the actual observation, current authorization,
resource ownership, and physical completion justify. The scenario also has a
variant with no received advisory: Bob's explicit permitted Refresh still exists.
A revision-looking number copied into the response is not progression evidence.

*** Certification strengthens this same path

The Claim semantic guard, abstract transition, and declared catalog produce
source-bound obligations. The proof mechanism checks its supported conclusions;
the issuer validates the required dependency closure; the assembly binds the
issued operation and plan; the host adopts the actual handler and gateway.

For each step the report preserves whether the result is derived, kernel-checked,
exact-finite checked, assembly-verified, runtime-enforced, qualified under a trusted
provider premise, asserted, or tested. “Qualified” describes applicability and
support for a premise; it does not create a new proof evidence class.

A passing finite family needs meaningful rule and outcome exercise, but it does
not establish all real states or writers. A matching submitted vector needs
actual call-site provenance before it can describe an observed submission. A
committed provider record needs the relevant binding before it resolves this
command. An installed local wrapper needs the real server handoff before it
supports the deployed-entrypoint claim.

External kernel soundness then concerns the inference/checking rules used for the
stated subject. Its production transfer is separate from the Claim transaction's
execution refinement. A named theorem and a real browser success can both be
valid while an intermediate correspondence obligation remains unproved. The
selected profile determines whether its explicit premise is acceptable.

*** Changes propagate along the relevant edges

A policy change reconsiders its dependent Claim judgments, operation contract,
projection assumptions, assembly joins, and appropriate tests. A changed adapter
can preserve an abstract theorem while invalidating transaction correspondence
and backend qualification. A new browser artifact must establish its own exact
byte/manifest relation even when the semantic plan is compatible.

Unrelated search evidence stays reusable only where its complete dependencies are
unchanged; sharing a repository is not an edge, and hiding a real policy dependency
is not an optimization. Part XI governs cache re-admission and the release decision.

This trace never replaces the public model with a browser rule, the production
plan with a proof-only twin, or the actual provider with a success-shaped mock.
A mock can test a component under its assumed contract, but the integration claim
requires the actual owning boundary.

** Cross-stage acceptance invariants

These invariants apply whenever the corresponding boundary is present. They are
not a final ceremonial checklist that can excuse an earlier unchecked path.
The owning Parts define the complete contracts; a roadmap summary cannot weaken
them.

*** Gate A -- No silent semantic downgrade

A declared semantic operation retains its command, plan, provider, authority,
result, and recovery requirements through the actual invocation. Missing required
data rejects or renders an explicitly unavailable affordance. It cannot silently
drop the operation's managed contract and issue an ordinary request.

Explicit unavailability can be structurally valid while still failing a product
milestone that requires the operation to work. The independent capability oracle
prevents that distinction from disappearing.

*** Gate B -- One connected semantic subject

Runtime, tests, proof subjects, projected plans, and generated artifacts consume
one admitted meaning or an explicitly justified representation relation. A richer
test-only model cannot substitute for production. A second representation is
allowed; an unaccounted second application semantics is not.

The permanent executable semantic core, dedicated semantic checkers, small proof
kernel, and external proof checker retain different responsibilities. Stronger
proof does not replace the runtime or make a sidecar a new control channel.

*** Gate C -- Source ownership stays single

Public models own business truth; choreography owns interaction; projection and
build derive their realizations; application assembly joins them. The audit and
proof surfaces derive from those objects. They do not manually synchronize a
second rule inventory or inject HumanHelp-specific policy into the framework.

Opaque host code is part of the same construction through its explicit contract.
Its unproved properties remain premises rather than duplicated pretend rules.

*** Gate D -- Authority remains at the trusted boundary

Browser-supplied role or principal claims, certificates, plan-looking maps, basis
tokens, and DOM state grant no server authority. Trusted invocation binds identity,
and current public model rules govern protected reads, subscriptions,
command-result disclosure, and mutations.

A certificate about an operation cannot manufacture a current Membership or
Organization policy. A checked rendering cannot replace authorization when a
hostile client bypasses the page.

*** Gate E -- Exact artifact and implementation binding

Where exact correspondence is claimed, the actual bytes, plan registry, issued
callables, and installed bindings are checked. A name, timestamp, copied digest,
source similarity, or local report is not sufficient. The build receipt binds
the admitted manifest and qualified build path to its actual output.

Semantic compatibility and exact byte identity are separate relations. A changed
implementation requires reconsidering its physical evidence even if an abstract
contract remains reusable.

*** Gate F -- Dynamic premises remain dynamic

Static preflight need not predict current authorization, future availability,
transaction races, or callback schedules. It must require the declared compatible
handling and recovery paths in [[#req-preflight-dynamic-handling-coverage]].
Runtime boundaries then acquire or enforce concrete premises at their proper
use points.

An existing path proves neither that its scheduler runs nor that its required
user action occurs. Safety must continue when liveness premises fail.

*** Gate G -- Real physical integration remains required

Portable state-machine checks do not replace the real browser lifecycle, backend
transaction, installed server, or multi-node failure boundary. Each acceptance
claim identifies the actual subjects and observation origins it exercised.

A required failed, skipped, unavailable, unsupported, stale, missing, or incomplete
check does not pass. Expected negative tests must reach their intended boundary;
an unrelated earlier failure is not equivalent evidence.

*** Gate H -- Reject contradictions when they become knowable

A statically known incompatibility blocks construction. A concrete malformed
render blocks delivery through the real response boundary. Invalid invocation
blocks protected work; an invalid transaction guard blocks incorporation; expired
effect permission blocks physical mutation.

The first applicable boundary is specific to the obligation. A later render
failure cannot undo an already incorporated command, and diagnostics must not
claim that it did.

*** Gate I -- Representation does not confer admission

Raw maps, nominal names, opaque-looking values, copied reports, and serialized
objects do not gain stronger status by shape. The correct checker, trusted
acquisition, issuer, authorization, or persistence re-admission establishes the
status under its own threat model.

A local handle prevents ordinary same-shaped substitution; it is not a JVM
sandbox or a portable authorization credential. A source-rechecked report can be
useful evidence without becoming an executable capability.

*** Gate J -- Capability completeness is independent of closure

The required product inventory is not generated solely from the operations the
implementation exposes. Removing Reassign, a positive fixture, or the response
interaction cannot make the full HumanHelp requirement set smaller.

An unresolved required decision blocks its full milestone. Remote lifecycle
adoption is selected as explicit Refresh; the unresolved response interaction
remains separately identified. Tests must use the real selected policy.

*** Gate K -- Incorporation, delivery, and knowledge stay distinct

A timeout, process loss, or retired resource does not prove a submitted command
failed. A known commit stays committed after response or publication failure.
A current-state observation can supersede provisional presentation without
establishing command attribution.

Compatible replay checks recorded binding and permitted disclosure before new
business guards. A fresh request or capability is not a fresh logical command.
Concurrent attempts and retained command records follow their explicit protocol.

*** Gate L -- Recovery preserves scope and adoption permission

An advisory adds scoped requirements, not an acquisition grant. Current provider
basis and projection coverage determine what can be discharged. A local result
cannot import unrelated remote membership or erase unrelated debt.

Refresh works when no advisory was received. Reconnect, release retirement,
queued work, and continuity do not create unrequested acquisitions. Known loss
of authority retires protected projections as required, while already disclosed
offline data cannot be retrospectively erased.

*** Gate M -- Evidence retains its scope through composition

Each claim retains its proposition, subject, assumptions, evidence class,
quantification domain, and applicable implementation or assembly. Required
source-derived obligations cannot be replaced by a smaller submitted graph.

Finite exploration remains finite without a justified abstraction. An individual
observed history remains an observation. Passing tests on another artifact or
copying an identity cannot satisfy the current release's required gate.

*** Gate N -- Policy visibility has an honest inspection boundary

Named rules, public operations, authority/disclosure requirements, state transitions,
and opaque premises form a source-derived audit surface. Conditions visible to a
checked boundary cannot be silently counted as assured while left unclassified.

Closure applies to the reported generated or inspected subset. Arbitrary host
bodies do not acquire a complete policy inventory from an empty escape report.
A larger genuine domain policy is not a defect; no arbitrary size ratio replaces
inspection or product review.

*** Gate O -- Formal assumptions create production obligations

An atomic formal action requires a corresponding qualified physical mechanism.
A fresh observation, authenticated principal, exclusive command, preserved frame,
or eventually delivered message creates its own production premise or obligation.
Model success cannot hide that connection.

Guard dependencies and physical write footprints are complete for the claimed
scope. Real initializers and all relevant writers are accounted for when the
claim depends on them. Backend qualification is specific to the actual adapter,
version, configuration, and used semantics; observed violations invalidate
applicability rather than proving the conditional theorem false.

*** Gate P -- Intent review and repair preserve the evidence boundary

Human or model-assisted review can identify surprising but internally valid
policy. That review is advisory, not a proof result or automatic authorization
to alter semantics. Confirmed requirements become explicit admitted rules,
invariants, or contracts before mechanical checks can enforce them.

Repair occurs at the owning source or implementation boundary and triggers the
appropriate regeneration and rechecking. A changed assumption or weaker invariant
is a changed claim. Generated formal artifacts and report status fields cannot
be edited into an independent source of success.

** Worked stopped candidate: find the owner of each defect

Suppose a candidate has a successful abstract Claim proof, a browser bundle that
compiled, and several passing integration cases. The following mutations must
still block the relevant claims. This table specifies acceptance cases; it does
not assert that merely declaring a case implements or runs its checker.

| Defect introduced | First applicable owner | Evidence needed for a valid repair |
|-------------------+------------------------+------------------------------------|
| Required clock/provider omitted and handler falls back | Provider/assembly construction | Actual compatible provider binding and preserved semantic invocation |
| Policy changed while old Claim certificate is retained | Required subject/dependency admission | Rechecked current subject, full obligations, and applicable evidence |
| Dependency DAG is acyclic but omits an operation | Source-derived closure and induction catalog | Complete original operation/invariant coverage joined into issuance |
| Browser assigns itself a principal or privileged role | Trusted invocation and current model authorization | Principal acquired from trusted context and enforced policy |
| Membership changes after preparation | Atomic authoritative transition | Current guarded dependencies or a separately justified temporal contract |
| Transaction appends an extra write after checking | Owned gateway and full physical footprint | Exact submitted plan with all effective writes accounted for |
| Whole-document replacement loses an unrelated field | Qualified guard/frame lowering | Safe replacement/update mechanism under the actual concurrency contract |
| Existing successful command is rejected because Request is claimed | Command-resolution branch | Compatible recorded-result lookup before new-command eligibility |
| Timeout is settled from a matching current card | Command reconciliation and presentation mapping | Command-specific evidence or retained honest uncertainty |
| Callback passes receipt-time check, then mutates a successor resource | Final physical effect gate | Current owner/effect permission immediately before mutation |
| Remote lifecycle notice automatically refreshes Bob's board | Acquisition/adoption policy | Explicit Refresh grant or the specifically admitted local exception |
| Initial subscription misses a notice and reports no debt | Fence/replay/gap contract | Qualified continuity evidence or visible conservative recovery gap |
| Correct manifest is paired with different served JavaScript | Build/serving correspondence | Actual byte receipt and current admitted bootstrap/build binding |
| Local router is checked but server retains an old handler | Actual host installation | Verified serving-handler handoff and compatible invocation context |
| All exposed actions pass but Reassign is absent | Independent product acceptance | Required eligible Reassign control, selection, authority, and successful result |
| Stronger proof policy exists but is not invoked at startup | Normal construction/install path | Required policy evaluation bound to the actual candidate |
| Provider upgrade reuses invalidated qualification | Qualification applicability and activation | Relevant requalification or an explicit narrower permissible claim |
| External theorem concerns a different production checker | Formal evidence import and release binding | Correct representation/direction and exact applicable implementation |

The repair does not consist of replacing failed flags in a root map. Fix the
public semantic owner, provider, lowering, adapter, constructor, installation,
or product decision that owns the defect, then rederive the affected objects.
A repair at one boundary does not automatically discharge the other rows.

For example, adding an actual clock provider fixes the provider omission but
says nothing about an incomplete writer inventory. Rebuilding correct browser
bytes does not make the server use the issued handler. A correct transaction
does not authorize Bob's automatic adoption. These failures are connected by the
assembly but retain separate semantics and evidence.

A negative case records the first expected boundary and absence of the prohibited
effect where applicable. It does not demand rollback of a commit that legitimately
preceded a later failure. A paired valid case demonstrates that the intended
capability still works, preventing reject-all implementations from satisfying
the safety tests vacuously.

** Final unified invariants

*** Application meaning and executable construction

A Gesso application has one admitted semantic construction. Public models own
business policy and durable truth; choreographies describe interaction and
knowledge; projections produce local machines; views bind operations to
presentation. The portable executable core supplies the runtime semantics used
by the supported checks.

Full host-language power remains available through explicit interfaces. The
system proves supported claims, enforces concrete premises, and records what it
must trust or accept. It does not disguise an opaque implementation as a closed
proof-language expression or require ordinary application authors to reproduce
internal proof plumbing.

*** Authority, commands, and observations

The browser may be adversarial. Trusted server boundaries authenticate principals
and authorize actual reads, subscriptions, result disclosure, and mutations.
Current guards and the complete promised writes share the required atomic
mechanism. A certificate changes none of those dynamic facts.

Commands preserve their original binding across permitted retries. Incorporation,
provider outcome, delivery, participant knowledge, and current-state observation
remain separate. Unknown outcome survives timeout and execution retirement until
permitted evidence resolves it or its declared limits leave it unresolved.

Authoritative observations state actual basis, projection, and coverage. Domain
revision, valid time, provider progression, transport identity, execution identity,
resource instance, and assembly generation remain distinct coordinates.

*** Presentation, resources, and recovery

Optimism represents provisional intent derived from known facts under its
operation contract. It grants no authority and has explicit settlement and
recovery. A Create intent does not need a fictitious prior entity observation.

Retirement revokes the retiring owner's effect rights before cleanup; it does
not revoke an independent shared-resource owner's rights. Physical effects check
current permission at mutation and record adoption only after the required
completion. Failed abort or a reused logical DOM identifier cannot revive old
rights. Continuity preserves compatible local presentation, not stale business
truth or continuation authority.

Live advisories describe possible relevant change under an authorized scope.
Acquisition and adoption follow policy. HumanHelp's remote creation and lifecycle
updates require explicit Refresh, with only the declared scoped local exceptions.
Lost notice, reconnect, and release replacement retain honest recovery obligations.

*** Evidence, release, and topology

The executable semantic core, semantic checkers, proof kernel, external checker,
physical gateway, and deployed entrypoint each have a defined responsibility.
Required dependency closure, applicable evidence, and actual binding join their
claims without changing their evidence classes. A digest or report shape is not
a theorem or a capability.

Exact finite checking stays within its domain unless sound abstraction transfers
it. Formal results reach production only through the stated correspondence and
continued applicability of their premises. Backend qualification challenges the
specific external behaviors used; it does not promise discovery of every possible
provider defect or proof of the entire backend.

Release decisions bind tested and served realizations, enforce the requested
profile, and preserve mandatory unmet obligations separately from accepted
premises. Compatibility is directional and bounded. Code rollback does not undo
committed state, and command recovery may outlive a retired execution plan.

Multiple hosts realize the same logical authorities and command contracts.
Durable model facts are the ordinary rendezvous. Publication, subscriber continuity,
protected acquisition, and conditional progress retain explicit failure and
recovery assumptions. Host replacement alone proves neither exactly-once effects
nor eventual participant knowledge.

The completed design makes incorrect assembly difficult by constructing and
enforcing these relationships, while keeping errors local and explainable.
Usable product behavior, declared closure, actual enforcement, compositional
proof, external correspondence, and deployment resilience are connected goals
with distinct evidence. None can be claimed merely because the application starts.
